15.2Core Concept & Quick Guide

ส่วนนี้คือแกนหลักของหัวข้อ TypeScript เราจะเรียน 12 แนวคิดเรียงจากง่ายไปยาก เริ่มจากการติดตั้ง tsc และเขียน Type พื้นฐาน ไปจนถึง Generics, Mapped Types และการตรวจข้อมูลจากภายนอกด้วย zod ทุกแนวคิดมีโค้ดที่รันได้จริง ผลลัพธ์จริงที่ได้จากการรัน และข้อความ Error จริงจาก Compiler ของ TypeScript 7.0.2 คุณจึงเห็นได้ทันทีว่า TypeScript ช่วยจับ Bug ให้คุณตรงไหน

ก่อนเริ่ม คุณควรเขียน JavaScript ได้แล้ว (ตัวแปร ฟังก์ชัน Object, Array, Arrow Function, async/await และ ES Modules) จากหัวข้อ และใช้ Terminal ของ Ubuntu ได้คล่องจากหัวข้อ ถ้าส่วนไหนลืมไปแล้ว ให้กลับไปทบทวนก่อน เพราะ TypeScript คือ JavaScript ที่เพิ่มระบบ Type เข้าไปเท่านั้น ไวยากรณ์ส่วนที่เหลือเหมือนเดิมทุกอย่าง

ขั้นที่ 4: สร้าง tsconfig.json แบบ strict

ไฟล์ tsconfig.json บอก Compiler ว่าโค้ดอยู่ที่ไหน จะสร้าง JavaScript รุ่นไหน และจะตรวจเข้มงวดแค่ไหน ทั้งหัวข้อนี้ (รวม Mini Project ในส่วนที่ 4) ใช้ไฟล์นี้ไฟล์เดียวกัน ไฟล์ tsconfig.json ใส่ Comment ได้ เพราะ tsc อ่านไฟล์นี้แบบ JSON with Comments

{
  "compilerOptions": {
    // ตำแหน่งไฟล์: โค้ดต้นฉบับอยู่ใน src และผลลัพธ์ JavaScript ไปที่ dist
    "rootDir": "./src",
    "outDir": "./dist",

    // สภาพแวดล้อม: Node.js 24 ขึ้นไป แบบ ES Modules
    "module": "nodenext",
    "target": "es2024",
    "types": ["node"],
    "sourceMap": true,

    // ตรวจเข้มงวด
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitReturns": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,

    // ให้โค้ดรันได้ทั้งผ่าน tsc และผ่าน Node แบบ Type Stripping
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "erasableSyntaxOnly": true,
    "rewriteRelativeImportExtensions": true,
    "moduleDetection": "force",
    "skipLibCheck": true
  },
  "include": ["src"]
}
ตัวเลือกความหมาย
rootDir / outDirอ่านโค้ดจาก src แล้วเขียนไฟล์ .js ไปที่ dist โดยคงโครงสร้างโฟลเดอร์เดิม เช่น src/c09/main.ts กลายเป็น dist/c09/main.js
module: "nodenext"ใช้กติกาการ import แบบเดียวกับ Node.js จริง (อ่าน "type": "module" จาก package.json)
target: "es2024"สร้าง JavaScript รุ่น ES2024 ซึ่ง Node 24 และ 26 รันได้ทั้งหมด จึงไม่ต้องแปลงไวยากรณ์ใหม่ให้เป็นแบบเก่า
types: ["node"]โหลด Type ของ Node.js จาก @types/node เท่านั้น ไม่ดึงแพ็กเกจ @types อื่นเข้ามาเอง
sourceMapสร้างไฟล์ .js.map เพื่อให้ Error ตอนรันชี้กลับไปที่บรรทัดใน .ts ได้
strictเปิดการตรวจเข้มงวดชุดใหญ่ เช่น strictNullChecks และ noImplicitAny โปรเจกต์ใหม่ควรเปิดเสมอ
noUncheckedIndexedAccessการอ่าน arr[i] หรือ obj[key] จะได้ชนิด T | undefined บังคับให้เช็กก่อนใช้
exactOptionalPropertyTypesแยก "ไม่มี property" ออกจาก "มี property แต่ค่าเป็น undefined"
noImplicitReturnsฟังก์ชันที่ต้องคืนค่า ต้องคืนค่าในทุกเส้นทางของโค้ด
noImplicitOverrideMethod ที่เขียนทับของ Class แม่ต้องมีคำว่า override
noFallthroughCasesInSwitchห้าม case ที่มีโค้ดแต่ลืม break หรือ return แล้วไหลไป case ถัดไป
verbatimModuleSyntaxบังคับเขียน import type สำหรับสิ่งที่เป็น Type อย่างเดียว เพื่อให้ลบทิ้งได้ถูกต้องตอนรัน
isolatedModulesให้ทุกไฟล์แปลงเป็น JavaScript ได้โดยไม่ต้องดูไฟล์อื่น (เครื่องมืออย่าง Node.js ทำงานแบบนี้)
erasableSyntaxOnlyอนุญาตเฉพาะไวยากรณ์ TypeScript ที่ "ลบทิ้งได้" จึงห้าม enum, namespace และ Parameter Property ใน constructor ทำให้ไฟล์ .ts รันด้วย node ได้ตรงๆ
rewriteRelativeImportExtensionsเขียน import ... from "./math.ts" ได้ แล้ว tsc จะเปลี่ยนเป็น "./math.js" ให้ตอนสร้างไฟล์ใน dist
moduleDetection: "force"ถือว่าทุกไฟล์เป็น Module แยกกัน ตัวแปรชื่อซ้ำกันข้ามไฟล์จึงไม่ชนกัน
skipLibCheckไม่ตรวจไฟล์ .d.ts ของไลบรารีใน node_modules ช่วยให้ Compile เร็วขึ้น
include: ["src"]ตรวจและ Compile เฉพาะไฟล์ในโฟลเดอร์ src

หมายเหตุ

TypeScript 7 คือ Compiler ที่เขียนใหม่ด้วยภาษา Go จึงทำงานเร็วกว่าเดิมมาก แต่คำสั่งยังเป็น tsc เหมือนเดิม ส่วน TypeScript 6.0.3 คือรุ่นสุดท้ายที่เขียนด้วย JavaScript เครื่องมือบางตัวที่เรียกใช้ TypeScript API โดยตรงยังต้องใช้ 6.x เช่น typescript-eslint 8.71.2 ประกาศรองรับ typescript >=4.8.4 <6.1.0 ถ้าติดตั้งคู่กับ TypeScript 7 npm จะแจ้ง ERESOLVE ก่อนเพิ่มเครื่องมือแบบนี้ ให้ตรวจช่วงเวอร์ชันที่รองรับในหน้า npm ของเครื่องมือนั้นก่อนเสมอ

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

TypeScript คือ JavaScript ที่เพิ่มระบบ Static Type เข้าไป เราเขียนกำกับว่าตัวแปรหรือ Parameter แต่ละตัวต้องเป็นข้อมูลชนิดไหน เช่น price: number แล้วให้ Compiler ตรวจก่อนรันว่าโค้ดใช้ข้อมูลถูกชนิดหรือไม่ ถ้าส่ง string ไปให้ฟังก์ชันที่ต้องการ number เราจะรู้ทันทีตั้งแต่ตอนเขียน ไม่ต้องรอให้ลูกค้าเจอ Bug บนเว็บจริง

สิ่งที่ต้องเข้าใจตั้งแต่วันแรกมีสามข้อ

  • Type มีอยู่แค่ตอนพัฒนา ตอนรันจริง Type ทั้งหมดถูกลบทิ้ง (Type Erasure) เหลือแต่ JavaScript ธรรมดา Type จึงไม่ได้ช่วยตรวจข้อมูลตอนรัน (เรื่องนี้ต้องใช้ Runtime Validation ซึ่งจะเรียนในแนวคิดที่ 12)
  • tsc ทำสองงาน คือตรวจ Type (Type Check) และสร้างไฟล์ .js (Emit) ถ้าสั่ง tsc --noEmit จะตรวจอย่างเดียว
  • Node.js รันไฟล์ .ts ได้ตรงๆ ด้วยความสามารถชื่อ Type Stripping ซึ่งเปิดใช้โดยไม่ต้องใส่ Flag ตั้งแต่ Node 22.18.0 และ 23.6.0 จึงใช้ได้ทั้ง Node 24 และ 26 แต่ Node แค่ลบ Type ทิ้งแล้วรัน ไม่ตรวจ Type และไม่อ่าน tsconfig.json ใช้ได้เฉพาะไวยากรณ์ที่ลบทิ้งได้ (Erasable Syntax)

ควรใช้ TypeScript เมื่อโค้ดเริ่มมีหลายไฟล์ มีคนทำงานร่วมกันหลายคน หรือต้องดูแลโปรเจกต์ไปนานๆ งาน Backend ด้วย Node.js, Frontend ด้วย React, งาน AI Engineer ที่เรียก LLM API และเครื่องมือ CLI ในบริษัทส่วนใหญ่ใช้ TypeScript เป็นมาตรฐาน สำหรับสคริปต์สั้นๆ ที่ใช้ครั้งเดียวทิ้ง JavaScript ธรรมดาก็เพียงพอ

เปรียบเทียบ

TypeScript เหมือนวิศวกรตรวจแบบแปลนก่อนสร้างบ้าน ถ้าแบบเขียนว่าปลั๊กห้องครัวต้องรับไฟ 220V แต่ช่างไปต่อสายเส้นเล็กเกินไป วิศวกรจะทักตั้งแต่บนกระดาษ ไม่ต้องรอให้ไฟไหม้ก่อน พอสร้างเสร็จ ป้ายกำกับบนแบบแปลนไม่ได้ติดไปกับบ้าน (Type ถูกลบตอนรัน) ส่วน Type Stripping ของ Node.js เหมือนช่างที่ลงมือสร้างตามแบบทันทีโดยไม่ผ่านวิศวกร ทำงานเร็ว แต่ไม่มีใครตรวจให้

Primitive Types, Type Inference, Arrays และ Tuples

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Primitive Types คือชนิดข้อมูลพื้นฐานที่มีอยู่แล้วใน JavaScript ได้แก่ string (ข้อความ), number (ตัวเลขทุกแบบ ทั้งจำนวนเต็มและทศนิยม), boolean (true/false), bigint (จำนวนเต็มขนาดใหญ่มาก ลงท้ายด้วย n), null และ undefined ใน TypeScript เราเขียนชื่อชนิดเหล่านี้ด้วยตัวพิมพ์เล็กเสมอ (ไม่ใช่ String หรือ Number)

Type Inference คือการที่ TypeScript อนุมาน Type ให้เองจากค่าที่กำหนด เช่น let orderNo = 1001 จะได้ number โดยไม่ต้องเขียนอะไรเพิ่ม ในงานจริงเราจึงเขียน Type เอง (Annotation) เฉพาะจุดที่จำเป็น

  • Parameter ของฟังก์ชัน ต้องเขียนเสมอ เพราะ TypeScript เดาไม่ได้ว่าคนเรียกจะส่งอะไรมา
  • Array ว่าง เช่น const lines: string[] = [] เพราะยังไม่มีค่าให้อนุมาน
  • API สาธารณะ เช่นฟังก์ชันที่ export ให้ไฟล์อื่นใช้ เขียน Return Type ไว้เพื่อเป็นสัญญาที่ชัดเจน
  • ตัวแปรที่เริ่มเป็นค่าหนึ่งแต่จะเปลี่ยนเป็นอีกชนิดภายหลัง เช่น let couponCode: string | null = null

const กับ let อนุมานต่างกัน const shopName = "ร้านสมชายไอที" ได้ชนิดเป็น Literal "ร้านสมชายไอที" เพราะค่าเปลี่ยนไม่ได้ ส่วน let จะถูกขยาย (Widening) เป็น string หรือ number ทั่วไป Array เขียนได้สองแบบที่ความหมายเหมือนกัน คือ number[] และ Array<number> ส่วน Tuple คือ Array ที่จำนวนช่องและชนิดของแต่ละช่องตายตัว เช่น [name: string, price: number, qty: number] เหมาะกับข้อมูลสั้นๆ ที่ลำดับมีความหมาย

เปรียบเทียบ

Array เหมือนชั้นวางในร้านสะดวกซื้อที่วางได้แต่น้ำดื่ม (number[] ใส่ได้แต่ตัวเลข) จะยาวกี่ช่องก็ได้ ส่วน Tuple เหมือนกล่องข้าวเบนโตะที่มีช่องตายตัว ช่องแรกใส่ข้าว ช่องสองใส่กับ ช่องสามใส่ผลไม้ จะสลับช่องหรือเพิ่มช่องที่สี่ไม่ได้ ส่วน readonly คือกล่องที่ปิดฟิล์มแล้ว เปิดเพิ่มของไม่ได้

สร้างไฟล์สรุปตะกร้าสินค้าที่เก็บสินค้าแต่ละรายการเป็น Named Tuple แล้วคำนวณยอดเป็นเงินบาท

// src/c02-basics.ts — สรุปตะกร้าสินค้า ด้วย Primitive Types, Array และ Tuple

// 1) Primitive Types: ส่วนใหญ่ปล่อยให้ TypeScript อนุมาน (Type Inference) เอง
const shopName = "ร้านสมชายไอที"; // ชนิดเป็น literal "ร้านสมชายไอที" เพราะใช้ const
let orderNo = 1001;                 // ชนิดเป็น number เพราะใช้ let
const isMember: boolean = true;     // ใส่ annotation เองก็ได้ แต่ไม่จำเป็น
const totalViews: bigint = 9007199254740993n; // เลขใหญ่เกิน number ใช้ bigint (ลงท้ายด้วย n)
let couponCode: string | null = null;         // ยังไม่มีคูปอง จึงเป็น null ได้

// 2) Named Tuple: [ชื่อสินค้า, ราคาต่อชิ้น, จำนวน]
type CartItem = [name: string, price: number, qty: number];

// readonly array: ห้ามเพิ่ม/ลบสินค้าในตะกร้านี้หลังสร้างแล้ว
const cart: readonly CartItem[] = [
  ["คีย์บอร์ด", 1290, 1],
  ["เมาส์ไร้สาย", 590, 2],
  ["แผ่นรองเมาส์", 199, 3],
];

// 3) array ว่างต้องใส่ชนิดเอง ไม่อย่างนั้นจะอนุมานไม่ได้ว่าเก็บอะไร
const lines: string[] = [];
let subtotal = 0;

for (const [name, price, qty] of cart) {
  const lineTotal = price * qty;
  subtotal += lineTotal;
  lines.push(`${name.padEnd(12)} ${String(qty).padStart(2)} x ${price.toLocaleString("th-TH").padStart(6)} = ${lineTotal.toLocaleString("th-TH").padStart(7)} บาท`);
}

// 4) noUncheckedIndexedAccess: cart[0] อาจเป็น undefined ต้องเช็กก่อนใช้
const firstItem = cart[0];
const firstName = firstItem !== undefined ? firstItem[0] : "(ตะกร้าว่าง)";

couponCode = "SAVE10";
const discount = isMember && couponCode === "SAVE10" ? subtotal * 0.1 : 0;
orderNo += 1;

console.log(`${shopName} — ใบสั่งซื้อเลขที่ ${orderNo}`);
console.log(lines.join("\n"));
console.log(`สินค้าชิ้นแรก: ${firstName}`);
console.log(`ยอดก่อนลด: ${subtotal.toLocaleString("th-TH")} บาท`);
console.log(`ส่วนลดสมาชิก: ${discount.toLocaleString("th-TH")} บาท`);
console.log(`ยอดสุทธิ: ${(subtotal - discount).toLocaleString("th-TH")} บาท`);
console.log(`ยอดเข้าชมสะสม (bigint): ${totalViews + 1n}`);
console.log(`ชนิดของแต่ละค่า: ${typeof shopName}, ${typeof orderNo}, ${typeof isMember}, ${typeof totalViews}`);

Object Types: type alias กับ interface, Optional (?) และ readonly

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

ข้อมูลในงานจริงส่วนใหญ่เป็น Object เช่น ผู้ใช้ งาน หรือคำสั่งซื้อ Object Type คือการบรรยายรูปร่างของ Object ว่ามี property อะไร แต่ละตัวเป็นชนิดไหน TypeScript ให้ตั้งชื่อรูปร่างนี้ได้สองแบบ คือ type (Type Alias) และ interface ทั้งสองแบบใช้บรรยาย Object ได้เกือบเหมือนกัน ความต่างที่ควรรู้มีดังนี้

  • interface ใช้ได้กับ Object เท่านั้น ขยายด้วย extends ได้ และถ้าประกาศชื่อซ้ำ TypeScript จะรวมเป็นอันเดียว (Declaration Merging) เหมาะกับ "สัญญา" ที่ Class จะ implements หรือที่ไลบรารีเปิดให้คนอื่นขยาย
  • type ตั้งชื่อให้ Type อะไรก็ได้ ทั้ง Object, Union ("admin" | "member"), Tuple และ Type ที่คำนวณจาก Type อื่น ประกาศชื่อซ้ำไม่ได้
  • ข้อตกลงที่ใช้ในหัวข้อนี้: ใช้ type กับ Union และข้อมูลทั่วไป ใช้ interface กับ Object ที่จะถูก extends หรือ implements ในงานจริงให้ยึดตามข้อตกลงของทีม และใช้ให้สม่ำเสมอทั้งโปรเจกต์

เครื่องหมาย ? หลังชื่อ property ทำให้เป็น Optional (ไม่มีก็ได้) ส่วน readonly ทำให้กำหนดค่าได้ครั้งเดียวตอนสร้าง เพราะเราเปิด exactOptionalPropertyTypes ไว้ email?: string จึงหมายถึง "ไม่มี property email เลย หรือมีและเป็น string" แต่ไม่รวม "มีและเป็น undefined" ถ้าต้องการให้ใส่ undefined ได้ ต้องเขียน email?: string | undefined ให้ชัด นอกจากนี้ TypeScript ยังตรวจ Excess Property ด้วย คือถ้าเขียน Object Literal ที่มี property เกินจาก Type จะ Error ทันที ช่วยจับการพิมพ์ชื่อผิดได้ดีมาก

เปรียบเทียบ

Object Type เหมือนแบบฟอร์มสมัครสมาชิก ช่องที่มีดอกจันต้องกรอก (property ปกติ) ช่องที่เขียนว่า "ถ้ามี" เว้นได้ (?) เลขประจำตัวสมาชิกพิมพ์มาแล้ว แก้ไม่ได้ (readonly) และถ้าเขียนข้อมูลลงในช่องที่ไม่มีในฟอร์ม เจ้าหน้าที่จะส่งคืนให้แก้ (Excess Property Check) ส่วน interface ที่ extends กันเหมือนฟอร์มสมาชิกพิเศษที่มีทุกช่องของฟอร์มปกติ บวกช่องเพิ่มอีกสองสามช่อง

type Role = "admin" | "member";

interface User {

  role: Role;
  email?: string;       // optional: ไม่มี property นี้เลยก็ได้

Functions แบบมี Type: Parameter, Return Type, Optional/Default, Rest และ Overloads

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

ฟังก์ชันคือจุดที่ข้อมูลไหลเข้าและออกจากโค้ดแต่ละส่วน การใส่ Type ให้ฟังก์ชันจึงคุ้มค่าที่สุด เราใส่ Type ให้ Parameter ทุกตัว (ถ้าไม่ใส่และเปิด strict ไว้ จะได้ Error TS7006) และใส่ Return Type ให้ฟังก์ชันที่ export หรือมีหลายเส้นทาง เพื่อให้ TypeScript ตรวจว่าทุก return คืนค่าชนิดเดียวกันจริง

  • Optional Parameter (title?: string) ไม่ส่งมาก็ได้ ต้องอยู่หลัง Parameter ที่บังคับ
  • Default Parameter (percent: number = 10) ถ้าไม่ส่งมาจะใช้ค่าเริ่มต้น และ TypeScript อนุมาน Type จากค่านั้นได้
  • Rest Parameter (...amounts: number[]) รับกี่ตัวก็ได้ ได้มาเป็น Array
  • void ใช้กับฟังก์ชันที่ไม่ได้คืนค่า เช่นฟังก์ชันที่แค่พิมพ์ Log
  • Function Type Expression (type PriceRule = (price: number) => number) ตั้งชื่อ "รูปร่างของฟังก์ชัน" ไว้ใช้กับ Callback
  • Overloads เขียนลายเซ็น (Signature) หลายแบบให้ฟังก์ชันเดียว เมื่อชนิดของ Input กำหนดชนิดของ Output เช่น ส่ง number ได้ string แต่ส่ง number[] ได้ string[]

Callback ที่ส่งให้ map, filter หรือ reduce ไม่ต้องใส่ Type เพราะ TypeScript รู้จากชนิดของ Array อยู่แล้ว (Contextual Typing) ส่วน noImplicitReturns ที่เปิดไว้ใน tsconfig จะเตือนเมื่อฟังก์ชันลืม return ในบางเส้นทาง ซึ่งเป็น Bug ที่เจอบ่อยมากในโค้ดที่มี if ซ้อนกันหลายชั้น

เปรียบเทียบ

Type ของฟังก์ชันเหมือนป้ายที่ตู้กดน้ำ: "รับเหรียญ 10 บาท ได้น้ำ 1 ขวด" ใครหยอดแบงก์ก็รู้ทันทีว่าผิด Default Parameter เหมือนปุ่มที่ไม่เลือกขนาดจะได้ขนาดกลาง Rest Parameter เหมือนช่องหยอดเหรียญที่หยอดกี่เหรียญก็ได้ ส่วน Overloads เหมือนเครื่องชงกาแฟที่กดแก้วเดียวได้หนึ่งแก้ว แต่กดโหมดถาดได้กาแฟทั้งถาด เครื่องเดียวกันแต่ผลลัพธ์ขึ้นกับสิ่งที่เลือก

ชุดฟังก์ชันช่วยคำนวณราคาสำหรับร้านค้าออนไลน์ ครบทุกแบบของ Parameter รวมถึง Overload

// src/c04-functions.ts — ฟังก์ชันคำนวณราคาแบบมี Type

// 1) ระบุชนิด parameter และ return type, percent มีค่า default = 10
function calcDiscount(price: number, percent: number = 10): number {
  return Math.round(price * (percent / 100));
}

// 2) optional parameter (?) ต้องอยู่หลัง parameter ที่บังคับเสมอ
function greet(name: string, title?: string): string {
  return title !== undefined ? `สวัสดีคุณ${title} ${name}` : `สวัสดีคุณ ${name}`;
}

// 3) rest parameter: รับตัวเลขกี่ตัวก็ได้ แล้วได้มาเป็น number[]
function sum(...amounts: number[]): number {
  return amounts.reduce((total, n) => total + n, 0);
}

// 4) void: ฟังก์ชันที่ไม่ได้คืนค่าอะไรกลับมา
function logLine(message: string): void {
  console.log(`[ร้าน] ${message}`);
}

// 5) Function Type Expression: ตั้งชื่อ "รูปร่าง" ของฟังก์ชันไว้ใช้ซ้ำ
type PriceRule = (price: number) => number;
const addVat: PriceRule = (price) => Math.round(price * 1.07); // price อนุมานเป็น number เอง

// ฟังก์ชันที่รับ callback อีกที
function applyRule(prices: readonly number[], rule: PriceRule): number[] {
  return prices.map(rule);
}

// 6) Overloads: ลายเซ็นสองแบบ แต่มี implementation เดียว
function formatPrice(amount: number): string;
function formatPrice(amounts: readonly number[]): string[];
function formatPrice(input: number | readonly number[]): string | string[] {
  if (typeof input === "number") {
    return `${input.toLocaleString("th-TH")} บาท`;
  }
  return input.map((n) => `${n.toLocaleString("th-TH")} บาท`);
}

// 7) noImplicitReturns: ทุกทางต้อง return ค่า
function shippingFee(total: number): number {
  if (total >= 1000) {
    return 0;
  }
  return 50;
}

// callback ใน filter: TypeScript รู้เองว่า p เป็น number
const cheap = prices.filter((p) => p < 1000);
const one: string = formatPrice(1290);        // overload แบบที่ 1 คืน string

logLine(`สินค้าราคาไม่ถึงพัน: ${many.join(" | ")}`);
logLine(`ค่าส่งเมื่อซื้อ ${sum(...prices)} บาท = ${shippingFee(sum(...prices))} บาท`);
logLine(`ค่าส่งเมื่อซื้อ 590 บาท = ${shippingFee(590)} บาท`);

Union, Intersection, Literal Types และการใช้ Union แทน enum

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Union Type (A | B) แปลว่า "เป็น A หรือ B อย่างใดอย่างหนึ่ง" เช่น string | number ส่วน Literal Type คือ Type ที่เป็นค่าเดียวเป๊ะ เช่น "high" หรือ 404 เมื่อนำ Literal หลายค่ามารวมกันด้วย Union จะได้ชุดค่าที่อนุญาต เช่น type Priority = "low" | "medium" | "high" ถ้าพิมพ์ "hight" ผิดเพียงตัวเดียว TypeScript จะจับได้ทันที และ VS Code จะเสนอค่าที่ถูกต้องให้เลือกตอนพิมพ์

Intersection Type (A & B) แปลว่า "มีครบทั้ง A และ B" ใช้รวมรูปร่างของ Object หลายชิ้นเข้าด้วยกัน เช่น HasId & TaskData ได้ Object ที่มีทั้ง id และข้อมูลงาน ถ้านำ Type ที่ขัดกันมารวม เช่น { id: string } & { id: number } property นั้นจะกลายเป็น never (ไม่มีค่าใดใส่ได้)

หลายภาษามี enum สำหรับชุดค่าคงที่ TypeScript ก็มี แต่หัวข้อนี้เลือกใช้ Union ของ Literal แทน ด้วยเหตุผลต่อไปนี้

  • enum ไม่ใช่ไวยากรณ์ที่ลบทิ้งได้ เพราะ tsc ต้องสร้าง Object จริงขึ้นมาตอนรัน เมื่อเปิด erasableSyntaxOnly จะได้ Error TS1294
  • Node.js รันไฟล์ที่มี enum แบบ Type Stripping ไม่ได้ จะได้ ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX
  • Union ของ String Literal อ่านง่ายใน JSON และ Log เพราะค่าที่เก็บคือข้อความจริง เช่น "high" ไม่ใช่ตัวเลข 2
  • ถ้าต้องการรายการค่าไว้วนลูปหรือแสดงในเมนู ใช้ Array แบบ as const แล้วสร้าง Union จาก Array นั้นด้วย (typeof ARR)[number] ได้ ข้อมูลจึงมีแหล่งเดียว ไม่ต้องเขียนซ้ำสองที่
เปรียบเทียบ

Literal Union เหมือนเมนูร้านกาแฟที่มีให้เลือกแค่ "ร้อน", "เย็น" และ "ปั่น" พนักงานจะไม่รับออร์เดอร์ "อุ่นๆ" เพราะไม่มีในเมนู Union ของชนิดพื้นฐานเหมือนเครื่องจ่ายเงินที่รับได้ทั้งเงินสดหรือบัตร (อย่างใดอย่างหนึ่ง) ส่วน Intersection เหมือนตำแหน่งงานที่ต้องการคนที่ "ขับรถได้และพูดอังกฤษได้" ต้องมีครบทั้งสองอย่าง ถ้าประกาศว่าต้อง "อายุต่ำกว่า 20 และมากกว่า 60" ในคนเดียวกัน จะไม่มีใครสมัครได้เลย ซึ่งก็คือ never

สร้าง Priority และ Status จาก Array แบบ as const แล้วเรียงงานตามความสำคัญ

// src/c05-unions.ts — Union, Intersection และ Literal Types แทน enum

// 1) as const: ทำให้ array เป็น readonly tuple ของ literal
const PRIORITIES = ["low", "medium", "high"] as const;
const STATUSES = ["todo", "doing", "done"] as const;

// 2) สร้าง Union Type จาก array: "low" | "medium" | "high"
type Priority = (typeof PRIORITIES)[number];
type Status = (typeof STATUSES)[number];

// 3) Object แบบ as const ใช้แทน enum ได้ (ลบทิ้งตอนรันได้ทั้งหมด)
const PRIORITY_LABEL = {
  low: "ต่ำ",
  medium: "กลาง",
  high: "สูง",
} as const;

// 4) Intersection (&): รวมสอง type เข้าด้วยกัน
type HasId = { readonly id: string };
type TaskData = { title: string; priority: Priority; status: Status };
type Task = HasId & TaskData;

// 5) Union ของชนิดพื้นฐาน: รับได้ทั้ง string และ number
type TaskRef = string | number;
function toTaskId(ref: TaskRef): string {
  return typeof ref === "number" ? `T-${String(ref).padStart(3, "0")}` : ref;
}

Narrowing, Discriminated Unions, Exhaustive Check และ any / unknown / never

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

เมื่อตัวแปรเป็น Union เช่น string | number เราจะเรียกใช้ได้เฉพาะสิ่งที่ทุกชนิดในกลุ่มมีร่วมกัน Narrowing คือการตรวจด้วยเงื่อนไขของ JavaScript ธรรมดา แล้ว TypeScript จะ "บีบ" Type ให้แคบลงในบล็อกนั้นเอง วิธีตรวจที่ใช้บ่อยมีดังนี้

  • typeof x === "string" สำหรับชนิดพื้นฐาน
  • Truthiness (if (x)) และ x !== undefined / x !== null สำหรับตัดค่าว่างออก
  • x === "add" เทียบกับ Literal ตรงๆ รวมถึง switch
  • "title" in obj ตรวจว่า Object มี property นั้นหรือไม่
  • err instanceof Error สำหรับ Object ที่สร้างจาก Class และ Array.isArray(x) สำหรับ Array
  • User-defined Type Guard คือฟังก์ชันที่คืน x is T ใช้รวมเงื่อนไขหลายข้อไว้ในที่เดียว

Discriminated Union คือ Union ของ Object ที่ทุกแบบมี property ร่วมกันหนึ่งตัว (มักชื่อ kind หรือ type) ซึ่งเป็น Literal ต่างกัน เมื่อ switch (cmd.kind) TypeScript จะรู้ทันทีว่าใน case "add" ต้องมี title และใน case "done" ต้องมี id เราเพิ่ม Exhaustive Check ด้วยฟังก์ชันที่รับ never ไว้ที่ default ถ้าวันหนึ่งมีคนเพิ่มคำสั่งใหม่แต่ลืมจัดการ tsc จะ Error ทันที

สาม Type พิเศษที่ต้องแยกให้ออก:

  • any ปิดการตรวจทั้งหมด ทำอะไรกับค่าก็ได้ อันตรายเพราะ Bug เล็ดลอดได้ JSON.parse และ res.json() คืน any
  • unknown "ยังไม่รู้ว่าเป็นอะไร" รับค่าอะไรก็ได้ แต่ห้ามใช้จนกว่าจะ Narrow ให้รู้ชนิดก่อน เหมาะกับข้อมูลจากภายนอก
  • never "เป็นไปไม่ได้" ไม่มีค่าใดเป็น never ได้ ใช้กับฟังก์ชันที่ไม่มีวันคืนค่า (โยน Error เสมอ) และใช้ตรวจว่าจัดการ Union ครบทุกแบบ
เปรียบเทียบ

Discriminated Union เหมือนพัสดุที่มีสติกเกอร์สีบอกประเภทติดไว้: สีแดงคือของแตกง่าย สีเขียวคือของสด พนักงานดูแค่สีก็รู้ว่าต้องจัดการแบบไหน (Narrowing ด้วย kind) Exhaustive Check คือหัวหน้าที่ตรวจว่ามีโต๊ะรับพัสดุครบทุกสี ถ้าบริษัทเพิ่มสติกเกอร์สีม่วงแต่ยังไม่มีโต๊ะรับ ระบบจะแจ้งก่อนเปิดคลังสินค้า ส่วน unknown คือกล่องที่ไม่มีสติกเกอร์ ต้องแกะตรวจก่อนจึงจะส่งต่อได้ และ any คือการปล่อยผ่านทุกกล่องโดยไม่ตรวจเลย

// src/c06-narrowing.ts — ตัวแยกคำสั่ง (Command Parser) ด้วย Discriminated Union

// 1) Discriminated Union: ทุกแบบมี field "kind" ที่เป็น literal ต่างกัน
type Command =
  | { kind: "add"; title: string }
  | { kind: "list" }
  | { kind: "done"; id: string }
  | { kind: "remove"; id: string };

// ผลลัพธ์ของการแยกคำสั่ง: สำเร็จ หรือ ผิดพลาดพร้อมข้อความ
type ParseResult = { ok: true; command: Command } | { ok: false; error: string };

// 2) ฟังก์ชันช่วยสำหรับ Exhaustive Check: ถ้ามี case ที่ลืมจัดการ จะ error ตอน compile
function assertNever(value: never): never {
  throw new Error(`ไม่รู้จักค่า: ${JSON.stringify(value)}`);
}

// 3) User-defined Type Guard: บอก TypeScript ว่าถ้าคืน true แปลว่า value เป็น string
function isNonEmptyString(value: unknown): value is string {
  return typeof value === "string" && value.trim().length > 0;
}

function parseCommand(args: readonly string[]): ParseResult {
  const [name, arg] = args; // ทั้งสองตัวเป็น string | undefined
  switch (name) {
    case "add":
      return isNonEmptyString(arg)
        ? { ok: true, command: { kind: "add", title: arg } }
        : { ok: false, error: "add ต้องมีชื่องาน เช่น add \"อ่านหนังสือ\"" };
    case "list":
      return { ok: true, command: { kind: "list" } };
    case "done":
    case "remove":
      if (arg === undefined || !/^T-\d{3}$/.test(arg)) {
        return { ok: false, error: `${name} ต้องตามด้วยรหัสงานรูปแบบ T-001` };
      }
      return { ok: true, command: { kind: name, id: arg } }; // name ถูก narrow เป็น "done" | "remove"
    case undefined:
      return { ok: false, error: "ยังไม่ได้พิมพ์คำสั่ง" };
    default:
      return { ok: false, error: `ไม่รู้จักคำสั่ง "${name}"` };
  }
}

// 4) switch บน kind: ในแต่ละ case TypeScript รู้ว่ามี field อะไรบ้าง
function describe(cmd: Command): string {
  switch (cmd.kind) {
    case "add":
      return `เพิ่มงานใหม่: ${cmd.title}`;
    case "list":
      return "แสดงงานทั้งหมด";
    case "done":
      return `ทำเครื่องหมายเสร็จ: ${cmd.id}`;
    case "remove":
      return `ลบงาน: ${cmd.id}`;
    default:
      return assertNever(cmd); // ถ้าครบทุก case ตรงนี้ cmd มีชนิดเป็น never
  }
}

// 5) unknown: ข้อมูลจากภายนอกต้อง narrow ก่อนใช้
function readTitle(json: string): string {
  const data: unknown = JSON.parse(json); // JSON.parse คืน any จึงเก็บเป็น unknown ก่อน
  if (typeof data === "object" && data !== null && "title" in data && typeof data.title === "string") {
    return data.title;
  }
  return "(ไม่มี title ที่ถูกต้อง)";
}

// 6) instanceof และ Array.isArray
function errorMessage(err: unknown): string {
  if (err instanceof Error) return err.message;
  if (Array.isArray(err)) return `มี ${err.length} ข้อผิดพลาด`;
  return String(err);
}

Classes, Access Modifiers และการ implements Interface

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Class ใน TypeScript คือ Class ของ JavaScript ที่เพิ่ม Type ให้ Field, Constructor และ Method พร้อมเครื่องมือควบคุมการเข้าถึง (Access Modifiers) ใช้เมื่อข้อมูลกับพฤติกรรมต้องอยู่ด้วยกันและมีกฎที่ต้องรักษา เช่น บัญชีธนาคารที่ยอดเงินต้องเปลี่ยนผ่าน deposit และ withdraw เท่านั้น ห้ามใครไปแก้ตัวเลขตรงๆ หรือ Repository ที่ซ่อนวิธีเก็บข้อมูลไว้ข้างใน

  • public (ค่าเริ่มต้น) ใครก็เรียกได้
  • protected ใช้ได้ใน Class ตัวเองและ Class ลูก
  • private ของ TypeScript ใช้ได้เฉพาะใน Class ตัวเอง แต่ตรวจแค่ตอน Compile ตอนรันจริงยังเป็น property ธรรมดาที่มองเห็นได้
  • #name (Private Field ของ JavaScript) ซ่อนจริงตอนรัน แม้แต่ Object.keys หรือ JSON.stringify ก็มองไม่เห็น เหมาะกับข้อมูลที่ต้องปกป้องจริง
  • readonly กำหนดได้ใน Constructor ครั้งเดียว
  • implements สัญญาว่า Class มีทุกอย่างตาม interface ส่วน abstract คือ Class แม่ที่สร้าง Object ตรงๆ ไม่ได้ และบังคับให้ Class ลูกเขียน Method บางตัวเอง
  • override บอกชัดว่าตั้งใจเขียนทับ Method ของ Class แม่ เมื่อเปิด noImplicitOverride ถ้าลืมใส่จะ Error ช่วยกันกรณีตั้งชื่อชนโดยไม่ตั้งใจ

ข้อควรรู้สำคัญของโปรเจกต์นี้: Parameter Properties แบบ constructor(private x: number) ที่เห็นบ่อยในบทความเก่า เป็นไวยากรณ์ที่ลบทิ้งไม่ได้ (ต้องสร้างโค้ด this.x = x ให้) เมื่อเปิด erasableSyntaxOnly จึงต้องประกาศ Field เองแล้วกำหนดค่าใน Constructor ตามตัวอย่างด้านล่าง

เปรียบเทียบ

Class เหมือนตู้ ATM interface คือมาตรฐานที่ทุกธนาคารต้องมี (ฝาก ถอน ดูยอด) public คือปุ่มหน้าตู้ที่ลูกค้ากดได้ protected คือห้องหลังตู้ที่ช่างของธนาคารเข้าได้ private ของ TypeScript เหมือนป้าย "ห้ามเข้า" ที่ติดไว้ (คนเคารพป้ายก็ไม่เข้า แต่ประตูไม่ได้ล็อก) ส่วน #private คือตู้เซฟที่ล็อกจริง abstract class คือแบบแปลน ATM กลางที่ต้องให้แต่ละธนาคารกำหนดวงเงินถอนเอง

// src/c07-classes.ts — บัญชีธนาคารด้วย Class, Access Modifiers และ implements

// สัญญา (contract) ที่บัญชีทุกแบบต้องทำตาม
interface Account {
  readonly accountNo: string;
  readonly balance: number;
  deposit(amount: number): void;
  withdraw(amount: number): void;
}

// abstract class: สร้าง object ตรงๆ ไม่ได้ ต้องมีคลาสลูกมาสืบทอด
abstract class BaseAccount implements Account {
  // ประกาศ field เองทุกตัว (ไม่ใช้ parameter properties เพราะ erasableSyntaxOnly)
  readonly accountNo: string;
  readonly owner: string;
  protected history: string[] = []; // คลาสลูกเข้าถึงได้ แต่ภายนอกเข้าไม่ได้
  #balance = 0;                      // #private ของ JavaScript: ซ่อนจริงตอนรัน

  constructor(accountNo: string, owner: string) {
    this.accountNo = accountNo;
    this.owner = owner;
  }

  // getter: อ่านยอดเงินได้ แต่แก้ตรงๆ ไม่ได้
  get balance(): number {
    return this.#balance;
  }

  deposit(amount: number): void {
    this.assertPositive(amount);
    this.#balance += amount;
    this.history.push(`ฝาก ${amount.toLocaleString("th-TH")}`);
  }

  withdraw(amount: number): void {
    this.assertPositive(amount);
    const limit = this.withdrawLimit();
    if (amount > limit) {
      throw new Error(`ถอน ${amount.toLocaleString("th-TH")} บาทไม่ได้ ถอนได้สูงสุด ${limit.toLocaleString("th-TH")} บาท`);
    }
    this.#balance -= amount;
    this.history.push(`ถอน ${amount.toLocaleString("th-TH")}`);
  }

  // private ของ TypeScript: ตรวจตอน compile เท่านั้น
  private assertPositive(amount: number): void {
    if (!Number.isFinite(amount) || amount <= 0) {
      throw new Error(`จำนวนเงินต้องมากกว่า 0 (ได้รับ ${amount})`);
    }
  }

  // คลาสลูกต้องกำหนดเองว่าถอนได้เท่าไร
  protected abstract withdrawLimit(): number;

  statement(): string {
    return `${this.accountNo} (${this.owner}) ยอดคงเหลือ ${this.balance.toLocaleString("th-TH")} บาท | ${this.history.join(", ")}`;
  }
}

class SavingsAccount extends BaseAccount {
  readonly interestRate: number;

  constructor(accountNo: string, owner: string, interestRate: number) {
    super(accountNo, owner);
    this.interestRate = interestRate;
  }

  // override: บอกชัดว่าตั้งใจเขียนทับเมธอดของคลาสแม่ (noImplicitOverride บังคับ)
  protected override withdrawLimit(): number {
    return this.balance; // ออมทรัพย์ถอนได้ไม่เกินยอดที่มี
  }

  addInterest(): void {
    const interest = Math.round(this.balance * this.interestRate);
    this.deposit(interest);
    this.history.push(`(ดอกเบี้ย ${this.interestRate * 100}%)`);
  }
}

class CurrentAccount extends BaseAccount {
  readonly overdraft: number;

  constructor(accountNo: string, owner: string, overdraft: number) {
    super(accountNo, owner);
    this.overdraft = overdraft;
  }

  protected override withdrawLimit(): number {
    return this.balance + this.overdraft; // กระแสรายวันเบิกเกินบัญชีได้
  }
}

Generics และ Constraints

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Generics คือการเขียนฟังก์ชัน Class หรือ Type ที่มี "ช่องว่างสำหรับ Type" (Type Parameter) ซึ่งผู้ใช้จะเติมทีหลัง เช่น function first<T>(items: readonly T[]): T | undefined ถ้าส่ง User[] เข้าไป จะได้ User | undefined กลับมา ถ้าส่ง number[] จะได้ number | undefined โค้ดชุดเดียวใช้ได้กับทุกชนิด โดยยังรักษาข้อมูล Type ไว้ครบ ต่างจากการใช้ any ที่ใช้ได้กับทุกชนิดเหมือนกันแต่ทำให้ Type หายไปหมด

  • Type Argument Inference: ส่วนใหญ่ไม่ต้องเขียน first<User>(...) เพราะ TypeScript อนุมาน T จาก Argument ให้เอง
  • หลาย Type Parameter: เช่น pair<K, V>
  • Constraint (extends): จำกัดว่า T ต้องมีคุณสมบัติบางอย่าง เช่น T extends Entity หมายถึงต้องมี id เสมอ ข้างในจึงใช้ item.id ได้
  • keyof Constraint: K extends keyof T บังคับให้ K เป็นชื่อ property ที่มีจริงใน T และ T[K] คือ Type ของ property นั้น
  • Default Type Parameter: Result<T, E = string> ถ้าไม่ระบุ E จะเป็น string
  • Generic Interface และ Generic Class: เช่น Repository<T> ที่ใช้เก็บ Task, User หรือข้อมูลอะไรก็ได้ที่มี id

ใช้ Generics เมื่อเห็นว่ากำลังจะเขียนโค้ดที่เหมือนกันทุกบรรทัดซ้ำสองชุด ต่างกันแค่ Type เช่น TaskRepository กับ UserRepository ไลบรารีที่คุณใช้ทุกวันล้วนใช้ Generics เช่น Array<T>, Promise<T>, Map<K, V> และ useState<T> ของ React

เปรียบเทียบ

Generics เหมือนกล่องพัสดุไปรษณีย์ที่มีช่องเขียน "สิ่งของภายใน" กล่องแบบเดียวกันใส่หนังสือหรือเสื้อก็ได้ แต่เมื่อเขียนกำกับว่า "หนังสือ" แล้ว ปลายทางจะรู้ทันทีว่าเปิดออกมาจะเจอหนังสือ (Box<Book>) ส่วน Constraint เหมือนกล่องเก็บความเย็นที่รับเฉพาะของที่ "ต้องแช่เย็น" (T extends Chilled) ใส่ของอะไรก็ได้ที่อยู่ในกลุ่มนั้น แต่จะเอาเตารีดใส่ไม่ได้

// src/c08-generics.ts — Generic Repository ใช้ได้ทั้ง Task และ User

// 1) Generic Function: T คือ "ชนิดที่ผู้เรียกส่งมา"
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}

// 2) หลาย type parameter
function pair<K, V>(key: K, value: V): [K, V] {
  return [key, value];
}

// 3) keyof constraint: K ต้องเป็นชื่อ property ที่มีอยู่จริงใน T
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

// 4) Result<T, E> พร้อม default type parameter (E = string)
type Result<T, E = string> = { ok: true; value: T } | { ok: false; error: E };

// 5) Constraint ด้วย extends: ทุก Entity ต้องมี id
interface Entity {
  readonly id: string;
}

// 6) Generic Interface
interface Repository<T extends Entity> {
  findAll(): T[];
  findById(id: string): Result<T>;
  save(item: T): void;
  remove(id: string): boolean;
}

// 7) Generic Class ที่ implements Generic Interface
class InMemoryRepository<T extends Entity> implements Repository<T> {
  #items = new Map<string, T>();

  findAll(): T[] {
    return [...this.#items.values()];
  }

  findById(id: string): Result<T> {
    const item = this.#items.get(id);
    return item !== undefined ? { ok: true, value: item } : { ok: false, error: `ไม่พบรหัส ${id}` };
  }

  save(item: T): void {
    this.#items.set(item.id, item); // ใช้ item.id ได้เพราะ T extends Entity
  }

  remove(id: string): boolean {
    return this.#items.delete(id);
  }
}

Modules, Declaration Files (.d.ts), @types และการย้าย JavaScript มาเป็น TypeScript

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

โปรเจกต์จริงแบ่งโค้ดเป็นหลายไฟล์ (Module) แล้ว import/export หากัน TypeScript ใช้ไวยากรณ์ ES Modules แบบเดียวกับ JavaScript แต่ด้วย tsconfig ของเรา (module: "nodenext", rewriteRelativeImportExtensions, verbatimModuleSyntax) มีกติกาสามข้อที่ต้องจำ

  • Import ไฟล์ในโปรเจกต์ต้องใส่นามสกุล .ts เช่น import { baht } from "./math.ts" แล้ว tsc จะเปลี่ยนเป็น "./math.js" ให้ในไฟล์ผลลัพธ์ ไฟล์ .ts ต้นฉบับจึงรันด้วย node ได้ตรงๆ เช่นกัน
  • Type ต้อง import ด้วย import type เพื่อให้ทั้ง tsc และ Node รู้ว่าบรรทัดนี้ลบทิ้งได้ทั้งบรรทัด
  • Module ในตัวของ Node ใช้ prefix node: เช่น node:path และ node:fs/promises Type ของมันมาจาก @types/node

Declaration File (.d.ts) คือไฟล์ที่มีแต่ Type ไม่มีโค้ดที่รันได้ ใช้บอก TypeScript ว่าโค้ด JavaScript ตัวหนึ่ง export อะไรออกมาและเป็นชนิดไหน ไลบรารีบน npm หลายตัวแนบ .d.ts มาเอง (เช่น zod) ส่วนตัวที่ไม่มี ชุมชนเขียนไว้ให้ในแพ็กเกจชื่อ @types/ชื่อไลบรารี เช่น @types/node ถ้าไม่มีทั้งสองแบบ จะได้ Error TS7016 และเราต้องเขียน .d.ts เอง

เมื่อต้องย้ายโปรเจกต์ JavaScript เดิมมาเป็น TypeScript ไม่ต้องเขียนใหม่ทั้งหมดในวันเดียว ทำทีละขั้นได้ดังนี้

  1. ติดตั้ง typescript และสร้าง tsconfig ที่เปิด allowJs ให้ tsc อ่านไฟล์ .js ได้
  2. เติม // @ts-check บรรทัดแรกของไฟล์ .js ที่อยากให้ตรวจ แล้วบอก Type ผ่าน Comment แบบ JSDoc (@param {number} price)
  3. เมื่อแก้ Error ได้มากพอ เปิด checkJs เพื่อตรวจทุกไฟล์ .js
  4. เปลี่ยนนามสกุลเป็น .ts ทีละไฟล์ เริ่มจากไฟล์ที่ไม่ import ไฟล์อื่น (ไฟล์ปลายทาง) แล้วไล่ขึ้นไป
  5. สุดท้ายเปิด strict และตัวเลือกเข้มงวดอื่นๆ ทีละตัว

สำหรับโค้ดฝั่ง Browser ใช้ lib: ["dom"] แทน @types/node เพื่อให้รู้จัก document และ HTMLInputElement ซึ่งควรแยก tsconfig ออกมา เพราะโค้ด Node กับโค้ด Browser ใช้ API คนละชุด

Module เหมือนแผนกในบริษัทที่ส่งงานให้กันผ่านเอกสาร export คือเอกสารที่แผนกยอมให้คนนอกเห็น ไฟล์ .d.ts เหมือนคู่มือการใช้เครื่องจักรนำเข้า เครื่องทำงานได้อยู่แล้ว (โค้ด JavaScript) แต่ถ้าไม่มีคู่มือภาษาไทย ช่างก็ไม่รู้ว่าปุ่มไหนรับค่าอะไร @types คือคู่มือที่ชุมชนช่วยกันแปลไว้ให้ ส่วนการย้าย JavaScript มาเป็น TypeScript เหมือนรีโนเวทบ้านทีละห้อง คนยังอยู่อาศัยได้ตลอดเวลา ไม่ต้องรื้อทั้งหลัง

Best Practice
  • ใช้ import type กับทุกอย่างที่เป็น Type และให้ verbatimModuleSyntax ช่วยบังคับ โค้ดจะใช้ได้กับทุกเครื่องมือ (tsc, Node, esbuild, Vite)
  • ก่อนติดตั้ง @types/xxx ให้ดูก่อนว่าไลบรารีแนบ Type มาเองหรือยัง (บนหน้า npm จะมีไอคอน TS) ถ้ามีแล้ว ไม่ต้องติดตั้งซ้ำ
  • ย้ายโปรเจกต์ JavaScript ทีละไฟล์ และ Commit ทุกครั้งที่ย้ายเสร็จหนึ่งไฟล์ หลีกเลี่ยง Pull Request ยักษ์ที่เปลี่ยนนามสกุลทุกไฟล์พร้อมกัน
  • ให้ @types/node มีเวอร์ชันหลักตรงกับ Node ที่ใช้รันจริง (Node 24 ใช้ @types/node@24) จะได้ไม่เผลอใช้ API ที่ยังไม่มีในเวอร์ชันนั้น

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

เมื่อโปรเจกต์ใหญ่ขึ้น เราจะมี Type หลายตัวที่หน้าตาคล้ายกัน เช่น Task ที่เก็บในฐานข้อมูล, ข้อมูลที่ผู้ใช้ส่งมาตอนสร้างงาน (ยังไม่มี id) และข้อมูลตอนแก้ไข (ส่งมาแค่บาง field) ถ้าเขียนแยกสามชุด พอเพิ่ม field ใหม่ใน Task ก็ต้องตามแก้ทุกที่ และมักลืม แนวคิดนี้สอนให้ สร้าง Type ใหม่จาก Type เดิม ข้อมูลจะมีแหล่งความจริงเพียงแหล่งเดียว (Single Source of Truth)

  • keyof T ได้ Union ของชื่อ property ทั้งหมดของ T
  • typeof value (ในตำแหน่งของ Type) ได้ Type ของตัวแปรหรือฟังก์ชัน
  • Indexed Access T["status"] ได้ชนิดของ property เดียว และ T[number] ได้ชนิดของสมาชิกใน Array
  • satisfies ตรวจว่าค่าตรงกับ Type ที่ระบุ แต่ยังเก็บ Type ที่แคบกว่าซึ่งอนุมานได้ไว้

Utility Types คือ Generic Type ที่ติดมากับ TypeScript ตัวที่ใช้บ่อยที่สุดในงานจริงได้แก่

Utility Types เหมือนการถ่ายเอกสารแบบฟอร์มต้นฉบับแล้วดัดแปลง Omit คือเอาเทปลบปิดช่อง "เลขที่เอกสาร" เพราะเจ้าหน้าที่จะเติมเอง Partial คือฟอร์มขอแก้ไขข้อมูลที่กรอกเฉพาะช่องที่ต้องการเปลี่ยน Pick คือการตัดเอาแค่บางช่องมาใช้ Record<Status, number> คือตารางสรุปที่ต้องมีครบทุกแถว เมื่อแก้ฟอร์มต้นฉบับ สำเนาทุกแบบจะเปลี่ยนตามทันที เพราะสร้างมาจากต้นฉบับเดียวกัน

ตัวอย่างโค้ด

โมเดล Task ตัวเดียว แล้วสร้าง NewTask, TaskPatch, ScheduledTask และ Type อื่นๆ จากมัน (ไฟล์นี้ใช้ Top-level await ซึ่งใช้ได้เพราะเป็น ES Module และ target เป็น es2024)

// src/c10-utility.ts — สร้าง Type ใหม่จาก Type เดิมด้วย keyof, typeof และ Utility Types

const STATUSES = ["todo", "doing", "done"] as const;
type Status = (typeof STATUSES)[number];          // Indexed Access ด้วย [number]
type Priority = "low" | "medium" | "high";

interface Task {
  readonly id: string;
  title: string;
  priority: Priority;
  status: Status;
  dueDate?: string;
  readonly createdAt: string;
}

// keyof: ได้ Union ของชื่อ property ทั้งหมด
type TaskKey = keyof Task; // "id" | "title" | "priority" | "status" | "dueDate" | "createdAt"
// Indexed Access: ดึงชนิดของ property เดียวออกมา
type TaskStatus = Task["status"]; // "todo" | "doing" | "done"

// Omit: ข้อมูลที่ผู้ใช้ส่งมาตอนสร้างงาน (ระบบสร้าง id กับ createdAt ให้เอง)
type NewTask = Omit<Task, "id" | "createdAt">;
// Pick + Partial: แก้ได้เฉพาะ 3 field และส่งมาแค่บาง field ก็ได้
type TaskPatch = Partial<Pick<Task, "title" | "priority" | "status">>;
// Required: บังคับทุก field รวมถึง dueDate ที่เคยเป็น optional
type ScheduledTask = Required<Task>;

// satisfies: ตรวจว่าตรงกับ Record<Priority, number> แต่ยังเก็บชนิด literal เดิมไว้
const PRIORITY_WEIGHT = { low: 1, medium: 2, high: 3 } satisfies Record<Priority, number>;

let counter = 0;
function createTask(input: NewTask): Task {
  counter += 1;
  return { ...input, id: `T-${String(counter).padStart(3, "0")}`, createdAt: `2026-10-2${counter}T09:00:00.000Z` };
}

function updateTask(task: Task, patch: TaskPatch): Task {
  return { ...task, ...patch };
}

// Record<Status, number>: ต้องมี key ครบทั้ง 3 สถานะ
function countByStatus(tasks: readonly Task[]): Record<Status, number> {
  const result: Record<Status, number> = { todo: 0, doing: 0, done: 0 };
  for (const t of tasks) result[t.status] += 1;
  return result;
}

// ฟังก์ชัน async จำลองการโหลดข้อมูล
async function loadTasks(): Promise<Task[]> {
  return [
    createTask({ title: "อ่านบท Utility Types", priority: "high", status: "doing", dueDate: "2026-10-25" }),
    createTask({ title: "ทำแบบฝึกหัด keyof", priority: "medium", status: "todo" }),
    createTask({ title: "สรุป Cheat Sheet", priority: "low", status: "todo" }),
  ];
}

// ReturnType + Awaited: ได้ Task[] โดยไม่ต้องเขียนซ้ำ
type LoadedTasks = Awaited<ReturnType<typeof loadTasks>>;
// Parameters: ได้ tuple ของ parameter ของฟังก์ชัน
type UpdateArgs = Parameters<typeof updateTask>; // [task: Task, patch: TaskPatch]
// NonNullable: ตัด undefined และ null ออก
type DueDate = NonNullable<Task["dueDate"]>; // string

// อ่านค่าแบบ type-safe ด้วย keyof
function pluck<K extends keyof Task>(tasks: readonly Task[], key: K): Task[K][] {
  return tasks.map((t) => t[key]);
}

const tasks: LoadedTasks = await loadTasks(); // top-level await ใช้ได้ใน ES Module
const first = tasks[0];
if (first !== undefined) {
  const args: UpdateArgs = [first, { status: "done" }];
  tasks[0] = updateTask(...args);
}

const keys: TaskKey[] = ["id", "title", "status"];
const due: DueDate[] = tasks.flatMap((t) => (t.dueDate !== undefined ? [t.dueDate] : []));
const scheduled: ScheduledTask[] = tasks.filter((t): t is ScheduledTask => t.dueDate !== undefined);
const sorted = [...tasks].sort((a, b) => PRIORITY_WEIGHT[b.priority] - PRIORITY_WEIGHT[a.priority]);
const statusOfFirst: TaskStatus | undefined = tasks[0]?.status;

console.log(`ชื่อ field ที่จะแสดง: ${keys.join(", ")}`);
for (const t of sorted) {
  console.log(`  ${keys.map((k) => String(t[k])).join(" | ")}`);
}
console.log(`ชื่องานทั้งหมด: ${pluck(tasks, "title").join(" / ")}`);
console.log(`สถานะงานแรก: ${statusOfFirst}`);
console.log(`กำหนดส่ง: ${due.join(", ")} (มี ${scheduled.length} งานที่ตั้งวันส่ง)`);
console.log("นับตามสถานะ:", countByStatus(tasks));
console.log("น้ำหนักความสำคัญ:", PRIORITY_WEIGHT);

Mapped Types, Conditional Types และ Template Literal Types

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

แนวคิดนี้คือ "การเขียนโปรแกรมระดับ Type" (Type-level Programming) ซึ่งเป็นกลไกเบื้องหลังของ Utility Types ในแนวคิดที่ 10 และของไลบรารีดังๆ อย่าง zod, Prisma และ tRPC เมื่อเข้าใจแล้ว คุณจะอ่าน Type ที่ซับซ้อนในไลบรารีออก และสร้าง API ที่ใช้ผิดไม่ได้ให้ทีมของคุณเองได้

  • Mapped Type { [K in keyof T]: ... } วนทีละ key ของ T แล้วสร้าง property ใหม่ ใส่ Modifier ได้ เช่น -readonly (ลบ readonly ออก) และ ? (ทำให้เป็น Optional) Partial และ Readonly ก็เขียนด้วยวิธีนี้
  • Key Remapping ด้วย as เปลี่ยนชื่อ key ระหว่างวน เช่น title เป็น getTitle
  • Conditional Type T extends U ? X : Y คือ if ของระดับ Type ถ้า T เป็น Union จะกระจายตรวจทีละสมาชิก (Distributive) จึงใช้กรองสมาชิกของ Union ได้
  • infer ใช้ใน Conditional Type เพื่อ "จับ" ชนิดบางส่วนออกมา เช่น ชนิดของสมาชิกใน Array หรือชนิดที่ Promise จะคืน
  • Template Literal Type `task:${Status}` สร้าง Union ของข้อความจาก Union อื่น ได้ "task:todo" | "task:doing" | "task:done" ใช้คู่กับ Capitalize, Uppercase, Lowercase และ Uncapitalize ได้

ใช้เมื่อมีความสัมพันธ์ที่ต้องรักษาระหว่างชื่อกับชนิด เช่น ชื่อ Event ต้องคู่กับ Payload ที่ถูกต้อง ชื่อ Route ต้องคู่กับ Parameter หรือ Config ที่ต้องมีครบทุก Key ในงานทั่วไป อย่าใช้เพียงเพราะทำได้ Type ที่ซับซ้อนเกินจำเป็นจะทำให้ทีมอ่านโค้ดไม่ออกและ Compile ช้าลง

เปรียบเทียบ

Mapped Type เหมือนการทำจดหมายเวียน (Mail Merge) ใน Word: มีแม่แบบหนึ่งชุด แล้วระบบวนสร้างจดหมายให้ทุกรายชื่อในตาราง Key Remapping คือการเปลี่ยนคำขึ้นต้นตามแต่ละคน Template Literal Type เหมือนเครื่องพิมพ์ป้ายที่ต่อคำว่า "ชั้น" กับเลข 1 ถึง 3 ให้ได้ป้าย "ชั้น1", "ชั้น2", "ชั้น3" อัตโนมัติ ส่วน Conditional Type คือคนคัดแยกพัสดุที่ดูแต่ละชิ้นแล้วส่งไปคนละทางตามเงื่อนไข

// 1) Template Literal Type: สร้างชื่อ event จาก Status อัตโนมัติ
type TaskEventName = `task:${Status}`; // "task:todo" | "task:doing" | "task:done"

// 2) Mapped Type + Key Remapping (as): สร้าง map ของ event ทั้งหมดกับ payload
type TaskEvents = {
  [S in Status as `task:${S}`]: { id: string; title: string; status: S };
} & {
  "task:removed": { id: string };
};

// 3) EventBus แบบ Generic: ชื่อ event และ payload ต้องตรงกันเสมอ
type Handler<P> = (payload: P) => void;

class EventBus<Events extends Record<string, object>> {
  #handlers: { [E in keyof Events]?: Handler<Events[E]>[] } = {};

  on<E extends keyof Events>(event: E, handler: Handler<Events[E]>): void {
    const list = this.#handlers[event] ?? [];
    list.push(handler);
    this.#handlers[event] = list;
  }

  emit<E extends keyof Events>(event: E, payload: Events[E]): void {
    for (const handler of this.#handlers[event] ?? []) handler(payload);
  }
}

// 4) Mapped Type ที่ใช้ modifier: -readonly ลบ readonly ออก, ? ทำให้เป็น optional
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type Draft<T> = { [K in keyof T]?: T[K] };

// 5) Conditional Type แบบเรียกตัวเอง: DeepReadonly ล็อกทุกชั้น
type DeepReadonly<T> = T extends (infer U)[]
  ? readonly DeepReadonly<U>[]
  : T extends object
    ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
    : T;

// 6) Key Remapping + Capitalize: สร้างชื่อ getter เช่น getTitle, getStatus
type Getters<T> = { [K in keyof T & string as `get${Capitalize<K>}`]: () => T[K] };

// 7) infer: ดึงชนิดของสมาชิกใน array หรือชนิดที่ Promise จะคืน
type ElementOf<T> = T extends readonly (infer U)[] ? U : never;
type Unwrap<T> = T extends Promise<infer U> ? U : T;
// Distributive: Conditional Type กระจายไปทีละสมาชิกของ Union
type NotDone<S> = S extends "done" ? never : S; // NotDone<Status> = "todo" | "doing"

    getTags: () => task.tags,

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

ฟังก์ชัน async คืนค่าเป็น Promise<T> เสมอ เช่น async function fetchUsers(): Promise<Result<User[]>> TypeScript จะตรวจว่าเรา await ก่อนใช้ค่า และทุก return ข้างในตรงกับ T แต่มีจุดอ่อนสำคัญที่ต้องเข้าใจ: Type ไม่มีอยู่ตอนรัน (แนวคิดที่ 1) ข้อมูลที่มาจากภายนอกโปรแกรม เช่น res.json() ของ fetch, ไฟล์ JSON, ข้อมูลที่ผู้ใช้ส่งมา หรือข้อความที่ LLM ตอบกลับ อาจมีรูปร่างผิดจากที่เราคาดไว้ได้เสมอ และ res.json() ก็คืน any ซึ่ง TypeScript ไม่ตรวจอะไรเลย

Runtime Validation คือการตรวจข้อมูลจริงตอนโปรแกรมทำงาน ณ "ขอบ" ของระบบ (Boundary) ก่อนปล่อยเข้าไปข้างใน ไลบรารีที่นิยมที่สุดคือ zod (หัวข้อนี้ใช้ 4.6.7) จุดเด่นคือเขียน Schema ครั้งเดียว ได้ทั้งตัวตรวจตอนรัน และ TypeScript Type ผ่าน z.infer สองอย่างจึงไม่มีวันไม่ตรงกัน

  • z.object, z.string, z.array, z.enum และ z.email() ใช้สร้าง Schema
  • Schema.safeParse(data) คืน { success: true, data } หรือ { success: false, error } โดยไม่โยน Error (ส่วน parse จะโยน Error)
  • z.prettifyError(error) แปลง Error เป็นข้อความอ่านง่าย พร้อมบอกตำแหน่ง field ที่ผิด เช่น [1].email

สุดท้ายเราจะเขียน Test ด้วย node:test และ node:assert/strict ซึ่งมากับ Node.js ไม่ต้องติดตั้งอะไรเพิ่ม Test จะเรียก HTTP Server จำลองที่เปิดบน 127.0.0.1 port 0 (ให้ระบบเลือก port ว่างเอง) จึงไม่ต้องใช้อินเทอร์เน็ตหรือ API Key

import * as z from "zod";

// 1) Schema คือกฎที่ใช้ตรวจข้อมูลตอนรันจริง
export const RoleSchema = z.enum(["admin", "member"]);
export const UserSchema = z.object({
  id: z.string().regex(/^U-\d{2}$/, "id ต้องอยู่ในรูปแบบ U-01"),
  username: z.string().min(3),
  email: z.email(),
  role: RoleSchema,
});
export const UsersSchema = z.array(UserSchema);

// 2) z.infer: สร้าง TypeScript type จาก Schema (เขียนครั้งเดียว ได้ทั้งสองอย่าง)
export type User = z.infer<typeof UserSchema>;

// 3) Result: คืนผลสำเร็จหรือข้อผิดพลาด แทนการ throw ออกไปให้ผู้เรียก
export type Result<T, E = string> = { ok: true; value: T } | { ok: false; error: E };

// 4) async function คืน Promise<Result<User[]>> เสมอ
export async function fetchUsers(url: string): Promise<Result<User[]>> {
  let res: Response;
  try {
    res = await fetch(url);
  } catch (err) {
    return { ok: false, error: `เชื่อมต่อไม่ได้: ${err instanceof Error ? err.message : String(err)}` };
  }
  if (!res.ok) {
    return { ok: false, error: `Server ตอบกลับ HTTP ${res.status}` };
  }
  // res.json() ให้ชนิด any จึงเก็บเป็น unknown เพื่อบังคับให้ตรวจก่อนใช้
  const body: unknown = await res.json();
  const parsed = UsersSchema.safeParse(body);
  if (!parsed.success) {
    return { ok: false, error: z.prettifyError(parsed.error) };
  }
  return { ok: true, value: parsed.data }; // parsed.data มีชนิดเป็น User[] แล้ว
}

import { createServer } from "node:http";
import type { AddressInfo } from "node:net";

export type TestServer = { baseUrl: string; close: () => Promise<void> };

// routes: path -> ข้อมูล JSON ที่จะตอบกลับ, path อื่นจะได้ 404
export function startServer(routes: Record<string, unknown>): Promise<TestServer> {
  const server = createServer((req, res) => {
    const body = routes[req.url ?? ""];
    if (body === undefined) {
      res.writeHead(404, { "content-type": "application/json" });
      res.end(JSON.stringify({ message: "not found" }));
      return;
    }
    res.writeHead(200, { "content-type": "application/json" });
    res.end(JSON.stringify(body));
  });

  return new Promise((resolve) => {
    // port 0 = ให้ระบบเลือก port ว่างให้เอง
    server.listen(0, "127.0.0.1", () => {
      const { port } = server.address() as AddressInfo;
      resolve({
        baseUrl: `http://127.0.0.1:${port}`,
        close: () => new Promise<void>((done) => server.close(() => done())),
      });
    });
  });
}

Best Practice
  • ตรวจด้วย Schema ที่ขอบระบบเพียงครั้งเดียว (ตอนรับ Request, อ่านไฟล์, ได้ Response) จากนั้นภายในโปรแกรมให้เชื่อ Type ได้เต็มที่ ไม่ต้องตรวจซ้ำทุกฟังก์ชัน
  • ให้ Schema เป็นแหล่งความจริงแหล่งเดียว แล้วสร้าง Type ด้วย z.infer แทนการเขียน interface แยกอีกชุด
  • ใช้ safeParse คู่กับ Result ในโค้ดที่ต้องรายงานปัญหาให้ผู้ใช้ และเก็บ parse (ที่โยน Error) ไว้กับข้อมูลที่ "ต้องถูกเสมอ" เช่น Config ตอนเริ่มโปรแกรม
  • Test ต้องไม่ขึ้นกับอินเทอร์เน็ตหรือบริการภายนอก ใช้ Server จำลองบน 127.0.0.1 หรือข้อมูลบันทึกไว้แบบในตัวอย่างนี้ CI จะเสถียรและเร็ว

Checkpoint

ก่อนไปทำแบบฝึกหัดในส่วนที่ 3 ตรวจว่าคุณทำสิ่งต่อไปนี้ได้ด้วยตัวเอง

  • สร้างโปรเจกต์ใหม่ที่มี TypeScript 7.0.2 แบบ Local และ tsconfig แบบ strict ชุดเดียวกับส่วนนี้ แล้วรันได้ทั้ง npx tsc และ node src/app.ts

  • ออกแบบข้อมูลด้วย Object Type, Union ของ Literal และ Discriminated Union พร้อม Exhaustive Check ด้วย never
  • เขียน Generic Repository และสร้าง Type สำหรับ Input/Patch ด้วย Omit, Pick, Partial และ Record
  • ตรวจข้อมูลจากภายนอกด้วย zod ด้วย safeParse และเขียน Test ด้วย node:test ที่ผ่านด้วย npm test
