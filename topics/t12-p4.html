เป้าหมายของโปรเจกต์

สร้าง API ที่โฟลเดอร์ ~/projects/taskflow-api ด้วย FastAPI ผู้ใช้สมัครสมาชิกและเข้าสู่ระบบได้ (รหัสผ่านเก็บเป็น Argon2 Hash และได้ JWT กลับไป) จากนั้นจัดการงานของตัวเองได้ครบ CRUD พร้อมการแบ่งหน้าและกรองตามสถานะ ผู้ดูแลระบบ (admin) ดูรายชื่อผู้ใช้ทั้งหมดได้ ข้อมูลเก็บใน PostgreSQL 16 ผ่าน SQLAlchemy 2 และ Alembic ส่วน Test ใช้ SQLite ใน Memory จึงรันเร็วและไม่ต้องมี Database จริง

เมื่อทำเสร็จ คุณจะมี Repository บน GitHub ที่ CI เป็นสีเขียว มี README อธิบายสถาปัตยกรรม และมีตาราง OWASP API Security Top 10 ที่บอกว่าโปรเจกต์ป้องกันแต่ละข้ออย่างไร นี่คือสิ่งที่ผู้สัมภาษณ์งานตำแหน่ง Backend อยากเห็น

ฟีเจอร์ทั้งหมด

  • Auth: POST /api/v1/auth/register (201 หรือ 409 ถ้าอีเมลซ้ำ), POST /api/v1/auth/login (OAuth2 Form: username คืออีเมล และ password ได้ {access_token, token_type: "bearer"}), GET /api/v1/auth/me
  • Tasks CRUD ที่ /api/v1/tasks: GET รายการ พร้อม ?status=todo|doing|done&limit=20&offset=0 (limit สูงสุด 100) ตอบเป็น {items, total, limit, offset}, POST (201), GET /{task_id}, PATCH /{task_id} (แก้บางส่วน), DELETE /{task_id} (204) งานของผู้ใช้อื่นตอบ 404
  • Stats + Cache: GET /api/v1/tasks/stats ตอบ {todo, doing, done, cached} เก็บใน Redis ที่ Key stats:user:{id} นาน 60 วินาที ลบทิ้งเมื่อสร้าง แก้ หรือลบงาน และยังทำงานได้ (อ่านจาก Database) เมื่อ Redis ล่ม
  • Admin: GET /api/v1/admin/users ป้องกันด้วย require_role("admin") สมาชิกธรรมดาได้ 403
  • Role: member (ค่าเริ่มต้น) และ admin JWT มี Claim sub, role, iat, exp อายุ 30 นาที
  • Error รูปแบบเดียวกันทั้งระบบ: application/problem+json ที่มี type, title, status, detail, instance และ 422 มีรายการ errors เพิ่ม
  • Middleware: ใส่ request_id (ส่งกลับใน Header X-Request-ID) และเขียน Access Log เป็น JSON หนึ่งบรรทัดต่อ Request พร้อม duration_ms
  • Health Check: GET /health ตอบ {"status": "ok", "database": "ok"} หรือ 503
  • Rate Limit: Login ได้ 5 ครั้งต่อนาทีต่อ IP ด้วย Redis INCR/EXPIRE เกินแล้วได้ 429 พร้อม Retry-After
  • CORS: อนุญาตเฉพาะ http://localhost:5173
  • คุณภาพ: Alembic Migration, ชุด Test 15 ข้อด้วย SQLite + fakeredis, รายงาน Coverage
  • Deploy: Dockerfile, .dockerignore, compose.yaml (api, db, redis), .github/workflows/ci.yml, การรันหลัง nginx และ README ที่มีแผนภาพสถาปัตยกรรม

    config.py อ่านค่าทั้งหมดผ่าน pydantic-settings ข้อดีคือได้ Type ที่ถูกต้อง (เช่น access_token_expire_minutes เป็น int จริง) และแอปจะไม่ยอมเริ่มทำงานถ้าขาดค่าที่จำเป็น jwt_secret ไม่มีค่า default และต้องยาวอย่างน้อย 32 ตัวอักษร

class Settings(BaseSettings):

    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8", extra="ignore")

    app_name: str = "TaskFlow API"
    app_env: Literal["dev", "test", "prod"] = "dev"
    database_url: str = "postgresql+psycopg://taskflow:taskflow_dev_pw@localhost:5432/taskflow"
    redis_url: str = "redis://localhost:6379/0"  # ค่าว่าง = ปิด Cache และ Rate Limit
    jwt_secret: str = Field(min_length=32)  # ไม่มีค่า default จึงบังคับให้ตั้งเสมอ
    jwt_algorithm: str = "HS256"
    access_token_expire_minutes: int = 30
    cache_ttl_seconds: int = 60
    login_rate_limit: int = 5  # จำนวนครั้งที่ login ได้ต่อ IP ต่อ 1 นาที
    cors_origins: list[str] = ["http://localhost:5173"]
    log_level: str = "INFO"


@lru_cache
def get_settings() -> Settings:
    # สร้าง Settings ครั้งเดียวแล้วใช้ซ้ำทั้งแอป
    return Settings()

class Cache:
    """ห่อ Redis ไว้ ถ้า Redis ล่ม ให้คืน None และเขียน Log เตือน แทนการทำให้ API พัง"""

    def __init__(self, client: redis.Redis | None):
        self.client = client

    def _warn(self, op: str, key: str, exc: Exception) -> None:
        logger.warning("cache_unavailable", extra={"op": op, "key": key, "error": str(exc)})

    def get_json(self, key: str) -> Any | None:
        if self.client is None:
            return None
        try:
            raw = self.client.get(key)
        except redis.exceptions.RedisError as exc:
            self._warn("get", key, exc)
            return None
        return json.loads(raw) if raw is not None else None

    def set_json(self, key: str, value: Any, ttl: int) -> None:
        if self.client is None:
            return
        try:
            self.client.set(key, json.dumps(value), ex=ttl)  # ex = อายุของ Key เป็นวินาที
        except redis.exceptions.RedisError as exc:
            self._warn("set", key, exc)

    def delete(self, key: str) -> None:
        if self.client is None:
            return
        try:
            self.client.delete(key)
        except redis.exceptions.RedisError as exc:
            self._warn("delete", key, exc)

    def incr_with_ttl(self, key: str, ttl: int) -> int | None:
        """เพิ่มตัวนับทีละ 1 ถ้าเป็นครั้งแรกให้ตั้งอายุ Key คืน None ถ้า Redis ใช้ไม่ได้"""
        if self.client is None:
            return None
        try:
            count = self.client.incr(key)
            if count == 1:
                self.client.expire(key, ttl)
            return count
        except redis.exceptions.RedisError as exc:
            self._warn("incr", key, exc)
            return None

    def ttl(self, key: str) -> int:
        if self.client is None:
            return -2
        try:
            return self.client.ttl(key)
        except redis.exceptions.RedisError as exc:
            self._warn("ttl", key, exc)
            return -2

class JsonFormatter(logging.Formatter):
    """แปลง Log หนึ่งบรรทัดเป็น JSON หนึ่งบรรทัด ให้เครื่องมือค้นหา Log อ่านง่าย"""

            "time": datetime.fromtimestamp(record.created, tz=timezone.utc).isoformat(timespec="milliseconds"),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),

        return json.dumps(data, ensure_ascii=False, default=str)

        raise ConflictError("อีเมลนี้ถูกใช้แล้ว")
    try:
        return user_repo.create(
            db,
            email=payload.email,
            full_name=payload.full_name,
            hashed_password=hash_password(payload.password),
        )
    except IntegrityError:

        db.rollback()
        raise ConflictError("อีเมลนี้ถูกใช้แล้ว")


def authenticate(db: Session, email: str, password: str) -> User | None:
    user = user_repo.get_by_email(db, email)
    if user is None:
        verify_password(password, _DUMMY_HASH)
        return None
    return user if verify_password(password, user.hashed_password) else None


def check_login_rate_limit(cache: Cache, client_ip: str) -> None:
    # Fixed Window: นับครั้งใน Key rl:login:{ip} ที่หมดอายุใน 60 วินาที
    limit = get_settings().login_rate_limit
    key = f"rl:login:{client_ip}"
    count = cache.incr_with_ttl(key, 60)
    if count is not None and count > limit:
        retry_after = max(cache.ttl(key), 1)
        logger.warning("login_rate_limited", extra={"client_ip": client_ip, "count": count})
        raise TooManyRequestsError(
            "พยายามเข้าสู่ระบบบ่อยเกินไป กรุณารอสักครู่",
            headers={"Retry-After": str(retry_after)},

            raise HTTPException(status_code=403, detail="สิทธิ์ไม่เพียงพอ")
        return user

    return checker

@app.middleware("http")
async def request_context(request: Request, call_next):
    # รับ X-Request-ID จาก Proxy ถ้ามี ไม่อย่างนั้นสร้างใหม่ ใช้ตามรอย Request หนึ่งตัวใน Log
    request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
    request.state.request_id = request_id
    start = time.perf_counter()
    response = await call_next(request)
    duration_ms = round((time.perf_counter() - start) * 1000, 1)
    response.headers["X-Request-ID"] = request_id
    response.headers["X-Content-Type-Options"] = "nosniff"
    logger.info(
        "request",
        extra={
            "request_id": request_id,
            "method": request.method,
            "path": request.url.path,
            "status": response.status_code,
            "duration_ms": duration_ms,
        },
    )
    return response


def problem(request: Request, status: int, title: str, detail: str, headers=None, **extra) -> JSONResponse:
    # รูปแบบ Error ตาม RFC 9457 (Problem Details for HTTP APIs)
    body = {
        "type": "about:blank",
        "title": title,
        "status": status,
        "detail": detail,
        "instance": request.url.path,
        **extra,
    }
    return JSONResponse(body, status_code=status, headers=headers, media_type="application/problem+json")

Interview Questions

คำถามด้านล่างผสมระดับ Junior และ Mid-level ที่พบบ่อยในการสัมภาษณ์ตำแหน่ง Backend Developer ลองตอบออกเสียงก่อนเปิดดูแนวคำตอบ และพยายามยกตัวอย่างจาก TaskFlow API ที่คุณสร้างเอง ผู้สัมภาษณ์ให้คะแนนประสบการณ์จริงมากกว่าคำจำกัดความที่ท่องมา

1. Authentication กับ Authorization ต่างกันอย่างไร และในโปรเจกต์ของคุณทำแต่ละอย่างที่ตรงไหน (Junior)

แนวคำตอบ: Authentication คือการยืนยันว่า "คุณเป็นใคร" ส่วน Authorization คือการตัดสินว่า "คุณทำสิ่งนี้ได้ไหม" ถ้า Authentication ล้มเหลวตอบ 401 พร้อม Header WWW-Authenticate: Bearer ถ้ารู้ตัวตนแล้วแต่ไม่มีสิทธิ์ตอบ 403

  • Authentication: ตอน Login ตรวจรหัสผ่านกับ Argon2 Hash แล้วออก JWT อายุ 30 นาที ทุก Request ถัดไป Dependency get_current_user ตรวจลายเซ็นและ exp แล้วโหลด User จาก Database
  • Authorization ระดับ Function: require_role("admin") ที่ Router ของ admin สมาชิกธรรมดาได้ 403
  • Authorization ระดับ Object: ทุก Query ของงานมี WHERE owner_id = :current_user งานของคนอื่นตอบ 404 แทน 403 เพื่อไม่บอกว่ามี id นั้นอยู่จริง ข้อนี้คือการป้องกัน BOLA ซึ่งเป็นอันดับ 1 ของ OWASP API Security Top 10

จุดที่ควรพูดเพิ่ม: Role ต้องอ่านจากข้อมูลฝั่ง Server เสมอ ไม่รับจาก Body ของ Request และ Schema ขาเข้าใช้ extra="forbid" จึงส่ง "role": "admin" มาตอนสมัครไม่ได้

2. ทำไมเก็บรหัสผ่านด้วย Argon2 ไม่ใช้ SHA-256 และ JWT มีข้อดีข้อเสียอย่างไร ถ้าต้องการให้ Logout ทันทีจะทำอย่างไร (Junior ถึง Mid)

รหัสผ่าน: SHA-256 ออกแบบมาให้เร็ว GPU คำนวณได้หลายพันล้านครั้งต่อวินาที ถ้า Database หลุด ผู้โจมตีเดารหัสผ่านได้เร็วมาก Argon2id ออกแบบให้ช้าและใช้ Memory มาก (Memory-hard) การเดาแต่ละครั้งจึงแพง อีกทั้งใส่ Salt สุ่มให้ทุก Hash รหัสผ่านเดียวกันจึงได้ Hash ต่างกัน ในโปรเจกต์ใช้ pwdlib เพราะ passlib ไม่มีคนดูแลแล้ว

JWT: ข้อดีคือ Stateless ทุก Server ตรวจ Token เองได้ด้วย Secret ไม่ต้องถาม Session Store จึงขยายแนวนอนง่าย ข้อเสียคือ Payload แค่ Encode ด้วย Base64 ใครก็อ่านได้ จึงห้ามใส่ข้อมูลลับ และเพิกถอนก่อนหมดอายุไม่ได้โดยตรง

Logout ทันที: วิธีที่ใช้กันคือ (1) ให้ Access Token อายุสั้น เช่น 5–30 นาที คู่กับ Refresh Token ที่เก็บ Hash ไว้ใน Database และลบได้ (2) เก็บ Denylist ของ jti ใน Redis โดยตั้ง TTL เท่ากับอายุที่เหลือของ Token หรือ (3) เก็บ token_version ไว้ใน User แล้วเพิ่มค่าเมื่อ Logout ทุกเครื่อง Token เก่าที่มีเวอร์ชันต่ำกว่าจะใช้ไม่ได้ ทุกวิธีแลกความ Stateless บางส่วนกับการควบคุมที่มากขึ้น

3. ปัญหา N+1 Query คืออะไร ตรวจพบได้อย่างไร และแก้อย่างไร (Mid)

แนวคำตอบ: N+1 เกิดเมื่อโค้ด Query รายการหลักหนึ่งครั้ง แล้วไปโหลด Relationship ของแต่ละแถวทีละครั้ง เช่น ดึง User 100 คนแล้ววนอ่าน user.tasks SQLAlchemy จะ Lazy Load ทำให้เกิด 1 + 100 Query แม้แต่ละ Query จะเร็ว แต่ Round-trip ไป Database รวมกันทำให้ช้ามากเมื่อข้อมูลโต

  • ตรวจพบ: เปิด echo=True ตอนพัฒนา, นับ Query ด้วย Event ของ SQLAlchemy ใน Test, หรือดู APM/Tracing ที่แสดงจำนวน Span ของ Database ต่อหนึ่ง Request
  • แก้: selectinload(User.tasks) ได้ 2 Query (ดึง User แล้วดึง Task ทั้งหมดด้วย WHERE owner_id IN (...)) เหมาะกับ One-to-Many ส่วน joinedload ได้ Query เดียวด้วย JOIN เหมาะกับ Many-to-One
  • ป้องกัน: ตั้ง lazy="raise" ใน Relationship เพื่อให้ Error ทันทีถ้าโค้ดเผลอ Lazy Load และเขียน Test ที่ตรวจจำนวน Query ของ Endpoint สำคัญ

ควรพูดเรื่อง Index ต่อ: ใน TaskFlow มี Composite Index (owner_id, status) ตรงกับ Query หลัก ตรวจได้ด้วย EXPLAIN ว่า PostgreSQL ใช้ Index Scan แทน Seq Scan เมื่อข้อมูลมากพอ

4. อธิบาย Cache-aside และวิธีจัดการ Invalidation ถ้า Redis ล่มระบบควรทำอย่างไร (Mid)

แนวคำตอบ: Cache-aside คือแอปเป็นผู้จัดการ Cache เอง เมื่ออ่าน ให้ดู Cache ก่อน ถ้าไม่มี (Miss) ให้อ่านจาก Database แล้วเขียนลง Cache พร้อม TTL ครั้งต่อไปจะ Hit ใน TaskFlow GET /tasks/stats ใช้ Key stats:user:{id} อายุ 60 วินาที และตอบฟิลด์ cached ให้เห็นผล

  • Invalidation: ลบ Key ทันทีเมื่อสร้าง แก้ หรือลบงาน และมี TTL เป็นตาข่ายรองรับกรณีลืมลบ ทำให้ข้อมูลเก่า (Stale) อยู่ได้นานสุด 60 วินาที
  • Key ต้องแยกตามผู้ใช้: ถ้าใช้ Key รวม ข้อมูลของคนหนึ่งจะรั่วไปให้อีกคน
  • Redis ล่ม: Cache เป็นแค่ตัวเร่ง จึงต้อง Fail gracefully คลาส Cache จับ RedisError แล้วอ่านจาก Database แทน พร้อม Log WARNING และตั้ง Timeout สั้นเพื่อไม่ให้ Request ค้าง
  • Cache Stampede: เมื่อ Key ยอดนิยมหมดอายุพร้อมกัน Request จำนวนมากจะไปถล่ม Database พร้อมกัน แก้ด้วยการสุ่ม TTL (Jitter), ใช้ Lock ให้มีคนคำนวณใหม่คนเดียว หรือ Refresh ล่วงหน้าก่อนหมดอายุ

ควรบอกด้วยว่าไม่ควร Cache ทุกอย่าง เลือกเฉพาะข้อมูลที่อ่านบ่อย คำนวณแพง และยอมรับความล่าช้าได้ ส่วน HTTP Cache (Cache-Control, ETag) เป็นอีกชั้นที่ให้ Browser หรือ CDN ช่วย

5. ถ้า API ต้องรองรับผู้ใช้เพิ่มขึ้น 10 เท่า คุณจะ Deploy และ Scale อย่างไร (Mid)

แนวคำตอบที่ดีเริ่มจากการวัดก่อน: ดู Metrics ว่าคอขวดอยู่ที่ไหน (CPU ของแอป, Database, หรือ Network) ด้วย Latency p95/p99, Error Rate และ Throughput แล้วจึงตัดสินใจ

  1. แอปต้อง Stateless: ไม่เก็บ Session ใน Memory ใช้ JWT และเก็บ State ที่ใช้ร่วมกัน (Cache, Rate Limit) ใน Redis จึงเพิ่มจำนวน Instance ได้ทันที
  2. Horizontal Scaling: รันหลาย Container หรือหลายเครื่อง หลัง Load Balancer ที่ใช้ /health ตัดสินใจว่าส่งงานให้ใคร ในแต่ละเครื่องใช้ Uvicorn หลาย Worker
  3. Database: ใส่ Index ให้ Query ที่ช้า, ใช้ Connection Pooler อย่าง PgBouncer เพราะ Instance ที่เพิ่มขึ้นจะเปิด Connection มากจน PostgreSQL รับไม่ไหว, แยก Read Replica สำหรับงานอ่าน
  4. Cache หลายชั้น: Redis สำหรับผลคำนวณ และ CDN สำหรับไฟล์ Static หรือ Response สาธารณะ
  5. งานหนักแยกออกไป: อีเมล รายงาน หรือการประมวลผลไฟล์ ส่งเข้าคิว (RQ, Celery, RabbitMQ, SQS) ให้ Worker ทำ API จะตอบเร็วขึ้น
  6. การ Deploy: Build Image ใน CI, รัน Migration แบบ Backward-compatible ก่อนเปลี่ยนโค้ด, ใช้ Rolling Deploy ที่รอ Health Check ผ่านก่อนตัด Instance เก่า และเก็บ Log แบบ JSON พร้อม request_id เพื่อไล่ปัญหาข้าม Instance

แนวคิดเดียวกันใช้ได้กับ Node.js (Express 5 หรือ Fastify 5 กับ PM2 หรือ Container) และ Go (net/http ที่ใช้หลาย Core ได้ในหนึ่ง Process) ภาษาเปลี่ยน แต่หลัก Stateless, Health Check, Pooling, Cache และ Queue ยังเหมือนเดิม
