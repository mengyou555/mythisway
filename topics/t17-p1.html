17.1Learning Roadmap

ภาพรวมเส้นทาง

Git คือโปรแกรมที่จดประวัติการแก้ไขไฟล์ทุกครั้งที่คุณสั่ง ทำให้รู้ว่าใครแก้อะไร เมื่อไร และเพราะอะไร และย้อนกลับไปเวอร์ชันเก่าได้เสมอ ส่วน GitHub คือเว็บไซต์ที่เก็บ Repository ของ Git ไว้บน Cloud และมีเครื่องมือให้ทีมทำงานร่วมกัน เช่น Pull Request, Issues, Actions และ Pages นักพัฒนาเกือบทุกบริษัทใช้ Git ทุกวัน และผู้สัมภาษณ์งานสายเทคจำนวนมากเปิดดูโปรไฟล์ GitHub ของผู้สมัครก่อนเรียกสัมภาษณ์

หัวข้อนี้อยู่ลำดับที่ 2 ของเส้นทางที่แนะนำ ต่อจาก เหตุผลคือ ทุกชิ้นงานที่คุณสร้างหลังจากนี้ควรเก็บลง GitHub ตั้งแต่วันแรก เมื่อเรียนครบทุกหัวข้อ คุณจะมี Portfolio ที่สะสมมาหลายเดือนพร้อมประวัติ Commit จริง ซึ่งน่าเชื่อถือกว่า Portfolio ที่รีบทำขึ้นในสัปดาห์เดียว

เส้นทางนี้มี 13 ขั้นใน 3 ระดับ เริ่มจากเข้าใจว่า Git เก็บประวัติอย่างไรและสร้าง Commit ที่ดี ต่อด้วยการแตก Branch แก้ Conflict ส่งโค้ดขึ้น GitHub ผ่าน SSH และทำงานเป็นทีมด้วย Pull Request แล้วจบด้วยเครื่องมือระดับมืออาชีพ ได้แก่ Rebase, Reflog, Bisect, GitHub Actions และ GitHub Pages ขั้นสุดท้ายคือ Mini Project Portfolio Website บน GitHub Pages ที่พัฒนาด้วย Feature Branch และ Pull Request มี CI ตรวจ HTML และลิงก์ทุกครั้งที่เปิด PR และเผยแพร่เป็นเว็บจริงที่ส่งลิงก์ให้บริษัทดูได้

ใช้เวลารวมประมาณ 23–30 ชั่วโมง ถ้าเรียนวันละ 1–1.5 ชั่วโมง จะจบในราว 4 สัปดาห์ ทุกขั้นฝึกด้วย Git 2.43.0 บน Ubuntu 24.04 LTS ใน WSL2 ที่คุณใช้มาตั้งแต่ Day 0 แต่ละขั้นมี Checkpoint บอกว่าต้องทำอะไรได้ก่อนไปขั้นถัดไป ให้ทำ Checkpoint ให้ผ่านจริงก่อนเดินต่อ

เปรียบเทียบ

Git เหมือนการ Save เกม ที่ละเอียดมาก ทุกครั้งที่ Commit คือการกด Save พร้อมเขียนโน้ตว่าตอนนี้ทำอะไรไป ถ้าเล่นพลาดก็โหลดจุด Save เก่ากลับมาได้ ส่วน Branch คือการแยกไฟล์ Save ออกไปลองเส้นทางใหม่โดยไม่กระทบเส้นทางหลัก และ GitHub คือการอัปโหลดไฟล์ Save ทั้งหมดขึ้น Cloud ให้เพื่อนในทีมเล่นต่อจากจุดเดียวกันได้ และถึงคอมพิวเตอร์พังงานก็ไม่หาย

คำศัพท์ความหมายตัวอย่างในหัวข้อนี้
Version Control System (VCS)ระบบที่บันทึกการเปลี่ยนแปลงของไฟล์ตามเวลา ทำให้ดูประวัติ เปรียบเทียบ และย้อนกลับได้ แทนการตั้งชื่อไฟล์แบบ report_final_v3_จริง.docxGit คือ VCS ที่คนใช้มากที่สุดในโลก
Gitโปรแกรม VCS แบบกระจาย (Distributed) ที่ Linus Torvalds สร้างในปี 2005 เพื่อพัฒนา Linux Kernel ทำงานในเครื่องของคุณได้โดยไม่ต้องต่ออินเทอร์เน็ตGit 2.43.0 ที่ติดตั้งจาก apt ใน Ubuntu 24.04
GitHubบริการบน Cloud (Microsoft เป็นเจ้าของตั้งแต่ปี 2018) สำหรับเก็บ Repository ของ Git พร้อมเครื่องมือทำงานเป็นทีม คู่แข่งที่ใช้ Git เหมือนกันคือ GitLab และ Bitbucketบัญชีตัวอย่าง somchai-dev บน github.com
Repository (Repo)โฟลเดอร์โปรเจกต์ที่ Git ดูแล ข้อมูลประวัติทั้งหมดอยู่ในโฟลเดอร์ซ่อนชื่อ .git~/projects/learning-journal และ ~/projects/portfolio
Commitภาพถ่าย (Snapshot) ของไฟล์ทั้งโปรเจกต์ ณ เวลาหนึ่ง พร้อมชื่อผู้แก้ วันเวลา ข้อความอธิบาย และรหัส Hash ที่ไม่ซ้ำกันa22d77d docs: add README

เปรียบเทียบ

Git เหมือนกล้องถ่ายรูปกับอัลบั้มที่อยู่ในเครื่องของคุณ ถ่ายและเปิดดูได้แม้ไม่มีอินเทอร์เน็ต ส่วน GitHub เหมือนบริการฝากอัลบั้มออนไลน์ที่ให้เพื่อนเข้ามาดู แสดงความคิดเห็น และเสนอรูปเพิ่มได้ ใช้ Git โดยไม่มี GitHub ได้ แต่ใช้ GitHub โดยไม่เข้าใจ Git จะติดปัญหาตลอด หัวข้อนี้จึงสอน Git ให้แน่นก่อน แล้วค่อยขึ้น GitHub ใน Step 8

เหตุผลที่ Git และ GitHub เป็นทักษะหลักของทุกสายในหลักสูตรนี้

  • ทุกบริษัทซอฟต์แวร์ใช้ Git งานแรกของนักพัฒนาใหม่เกือบทุกที่คือ Clone Repository แตก Branch และเปิด Pull Request ถ้าทำไม่เป็นจะเริ่มงานไม่ได้
  • ทำงานผิดพลาดได้โดยไม่กลัว เมื่อมี Commit เป็นจุด Save คุณกล้าลองแก้โค้ดครั้งใหญ่ เพราะย้อนกลับได้ทุกเมื่อ
  • GitHub คือ Portfolio บริษัทดูได้ว่าคุณเขียนโค้ดอย่างไร เขียน README อย่างไร และทำงานสม่ำเสมอแค่ไหน
  • เครื่องมือยุคใหม่ผูกกับ Git ทั้ง CI/CD, Deploy อัตโนมัติ, Code Review และ AI Coding Assistant ทำงานบนพื้นฐานของ Commit และ Pull Request
  • ใช้ได้กับทุกภาษาและทุกสาย ทั้ง Python, JavaScript, Go, Kotlin, GDScript, SQL Script, Config ของอุปกรณ์เครือข่าย และเอกสาร Markdown

Prerequisites: ต้องรู้อะไรมาก่อน

หัวข้อนี้ต่อยอดจาก โดยตรง ก่อนเริ่มควรมีความรู้และสิ่งต่อไปนี้

  • จบ อย่างน้อยระดับ Beginner: ใช้ cd, ls -la, pwd, mkdir -p, cat, echo, > และ >> ได้คล่อง และแก้ไฟล์ด้วย nano ได้ (Git จะเปิด nano ให้เขียน Commit message)
  • เข้าใจไฟล์ซ่อนที่ขึ้นต้นด้วยจุด เช่น .git และ .gitignore และดูได้ด้วย ls -a
  • เคยสร้าง SSH Key ด้วย ssh-keygen -t ed25519 และรู้ว่า Private key ห้ามแชร์ ส่วน Public key (.pub) แชร์ได้ จาก Step 10 ของหัวข้อ Linux ถ้ายังไม่เคยทำ ให้ทำใน Step 8 ของหัวข้อนี้ได้
  • ทำ Day 0 เสร็จแล้ว: ตั้งค่า user.name, user.email, init.defaultBranch main และ core.editor nano และมี Repository ~/projects/learning-journal ที่ Commit แรกแล้ว
  • ติดตั้ง VS Code พร้อม Extension WSL และเปิดโฟลเดอร์ใน Ubuntu ด้วย code . ได้ เพราะจะใช้ Merge Editor ของ VS Code ใน Step 7
  • อ่านข้อความภาษาอังกฤษสั้นๆ ได้ เพราะ Git พิมพ์คำแนะนำที่ขึ้นต้นด้วย hint: บอกวิธีแก้ปัญหาไว้เกือบทุกครั้ง
  • มีอีเมลสำหรับสมัคร GitHub (สมัครใน Step 8) และมีแอป Authenticator บนมือถือสำหรับเปิด Two-factor authentication (2FA)

หัวข้อนี้เป็นพื้นฐานของทุกหัวข้อที่เหลือ โดยเฉพาะหัวข้อต่อไปนี้ที่ใช้ Git และ GitHub ทุกวัน

  • หัวข้อถัดไปในเส้นทาง เก็บ Script และ Mini Project ลง GitHub และใช้ .gitignore กัน .venv/ กับ __pycache__/
  • เผยแพร่เว็บด้วย GitHub Pages แบบเดียวกับ Mini Project ของหัวข้อนี้
  • ทำงานเป็นทีมด้วย Pull Request และตั้ง GitHub Actions รันชุดทดสอบทุกครั้งที่ Push
  • ต้องใช้ Branch และ Commit เล็กๆ เป็นจุด Save ก่อนให้ AI แก้โค้ด เพื่อย้อนกลับได้ทันทีเมื่อ AI ทำพัง
  • และ ใช้ .gitignore สำหรับไฟล์ Build และ Git LFS สำหรับไฟล์ภาพและเสียงขนาดใหญ่

Git ทำงานอย่างไร: ภาพรวม 4 พื้นที่

ความเข้าใจที่สำคัญที่สุดของทั้งหัวข้อคือ ไฟล์ของคุณอยู่ได้ใน 4 พื้นที่ และแต่ละคำสั่งของ Git คือการย้ายการเปลี่ยนแปลงจากพื้นที่หนึ่งไปอีกพื้นที่หนึ่ง ถ้าจำแผนภาพนี้ได้ คำสั่งส่วนใหญ่จะเข้าใจได้เองโดยไม่ต้องท่อง

  [ 1. Working Tree ]        ไฟล์จริงในโฟลเดอร์ที่คุณเปิดแก้ใน VS Code
          |                         ^
          | git add <ไฟล์>          | git restore <ไฟล์>  (ทิ้งการแก้ไขที่ยังไม่ add)
          v                         |
  [ 2. Staging Area ]        รายการที่เลือกไว้แล้วว่าจะเข้า Commit ถัดไป (เรียกอีกชื่อว่า Index)
          |                         ^
          | git commit -m "..."     | git restore --staged <ไฟล์>  (เอาออกจาก Staging)
          v                         |
  [ 3. Local Repository ]    ประวัติทุก Commit เก็บในโฟลเดอร์ .git ในเครื่องของคุณ
          |                         ^
          | git push                | git fetch  (ดึงประวัติใหม่มาเก็บ ยังไม่แตะไฟล์)
          v                         | git pull   (= git fetch + git merge หรือ git rebase)
  [ 4. Remote Repository ]   สำเนาบน GitHub ชื่อที่ใช้เรียกตามปกติคือ origin

  • Working Tree, Staging Area และ Repository ตามแผนภาพ 4 พื้นที่ด้านบน และสถานะของไฟล์ 4 แบบ: Untracked (ไฟล์ใหม่ที่ Git ยังไม่รู้จัก), Modified (แก้แล้วยังไม่ add), Staged (add แล้วรอ Commit) และ Committed (บันทึกแล้ว ไม่มีอะไรเปลี่ยน)
  • อ่าน git status ทุกบรรทัด และใช้รูปแบบย่อ git status -s: ?? คือ Untracked, A คือไฟล์ใหม่ที่ Staged แล้ว, M คือแก้แล้วยังไม่ Staged และ M คือแก้แล้ว Staged แล้ว
  • คำสั่งเลือกไฟล์เข้า Staging: git add ไฟล์, git add . (ทุกไฟล์ในโฟลเดอร์ปัจจุบัน ต้องตรวจ git status ก่อนเสมอ), git add -p (เลือกทีละส่วนของไฟล์), git rm (ลบไฟล์และบันทึกการลบ) และ git mv (เปลี่ยนชื่อไฟล์)
  • สร้าง Commit: git commit -m "ข้อความ" สำหรับข้อความบรรทัดเดียว, git commit เฉยๆ เพื่อเปิด nano เขียนข้อความยาว และ git commit -a ที่ add เฉพาะไฟล์ที่ Git รู้จักอยู่แล้วให้อัตโนมัติ (ไฟล์ใหม่จะไม่ถูกรวม)
  • ภายใน Commit มีอะไร: Snapshot ของไฟล์ทั้งหมด, ผู้เขียน (Author), วันเวลา, ข้อความ และ Parent (Commit ก่อนหน้า) ทุก Commit มีรหัส SHA-1 ยาว 40 ตัวอักษร ที่ปกติแสดงย่อ 7 ตัว เช่น a22d77d
  • HEAD คือป้ายที่บอกว่าตอนนี้คุณอยู่ที่ Commit ไหน (ปกติชี้ไปที่ Branch ปัจจุบัน) และ HEAD~1 คือ Commit ก่อนหน้านั้น 1 ขั้น
  • Git ไม่เก็บโฟลเดอร์ว่าง ถ้าต้องการให้มีโฟลเดอร์ใน Repository ให้ใส่ไฟล์เปล่าชื่อ .gitkeep ไว้ข้างใน (เป็นธรรมเนียม ไม่ใช่คำสั่งพิเศษของ Git)
ทำไมต้องเรียน
คำสั่ง Git ทุกคำสั่งต่อจากนี้คือการย้ายการเปลี่ยนแปลงระหว่าง 3 พื้นที่นี้ ถ้าเข้าใจตรงนี้ คำถามอย่าง "ทำไม Commit แล้วไฟล์ที่แก้ไม่เข้าไป" หรือ "ทำไม git diff ไม่แสดงอะไร" จะตอบได้เอง Staging Area ยังทำให้คุณแยกงานที่แก้ปนกันออกเป็นหลาย Commit ที่แต่ละอันมีเรื่องเดียว ซึ่งเป็นสิ่งที่ผู้รีวิวโค้ดต้องการ
ลงมือทำ
  • สร้าง ~/projects/git-lab/first-repo ด้วย git init แล้วรัน ls -a เพื่อดูโฟลเดอร์ .git
  • สร้างไฟล์ แก้ไฟล์ และรัน git status -s ทุกครั้งตามตัวอย่างด้านล่าง จนบอกได้ว่าไฟล์อยู่พื้นที่ไหน
  • แก้ 2 ไฟล์พร้อมกัน แล้ว Commit แยกเป็น 2 Commit ด้วยการ git add ทีละไฟล์

STEP 3

อ่านประวัติและความเปลี่ยนแปลงด้วย log, diff และ show

1 วัน · 1–1.5 ชม.
หัวข้อย่อย
  • git log และ Option ที่ใช้บ่อย: --oneline, -n 5, --stat (ไฟล์ไหนเปลี่ยนกี่บรรทัด), -p (แสดงเนื้อหาที่เปลี่ยน), --author="Somchai", --since="2 weeks ago", --grep="fix" และ -- ชื่อไฟล์ (ดูเฉพาะประวัติของไฟล์นั้น)
  • ดูกราฟของ Branch ด้วย git log --oneline --graph --all --decorate และสร้าง Alias สั้นๆ ด้วย git config --global alias.lg "log --oneline --graph --all --decorate" เพื่อพิมพ์แค่ git lg
  • git diff ใช้เทียบ 3 แบบ: git diff (Working Tree เทียบกับ Staging), git diff --staged (Staging เทียบกับ Commit ล่าสุด) และ git diff HEAD (ทุกอย่างที่ยังไม่ Commit) รวมถึงเทียบสอง Commit ด้วย git diff a22d77d af94733
  • อ่านผล Diff ให้เป็น: บรรทัด --- คือฝั่งเดิม, +++ คือฝั่งใหม่, @@ -1 +1,2 @@ คือตำแหน่งบรรทัด, บรรทัดที่ขึ้นต้นด้วย + คือเพิ่ม และ - คือลบ ส่วนข้อความภาษาไทยใน Markdown ดูง่ายขึ้นด้วย git diff --word-diff
  • git show ดูรายละเอียดของ Commit เดียว เช่น git show HEAD, git show HEAD~1 และดูเนื้อหาไฟล์ในอดีตด้วย git show HEAD~1:README.md โดยไม่ต้องย้อนไฟล์จริง
  • ค้นหาว่า Commit ไหนเพิ่มหรือลบข้อความหนึ่งด้วย git log -S "ลาเต้" (Pickaxe search) ซึ่งเร็วกว่าการไล่อ่านทีละ Commit มาก
  • Pager: ผลที่ยาวจะเปิดใน less ให้กด Space เลื่อนหน้า / ค้นหา และ q ออก ถ้าไม่ต้องการ Pager ใช้ git --no-pager log
  • เครื่องมือช่วยดู: แผง Source Control และ Timeline ของ VS Code, Extension GitLens และโปรแกรม tig 2.5.8 (sudo apt install -y tig) ซึ่งเป็นหน้าจอดูประวัติแบบโต้ตอบใน Terminal
ทำไมต้องเรียน
งานจริงใช้เวลาอ่านประวัติมากกว่าเขียน Commit ใหม่ เมื่อเกิดบั๊ก คำถามแรกคือ "แก้อะไรไปล่าสุด" และก่อน Commit ทุกครั้งควรดู git diff --staged เพื่อตรวจว่าไม่มีโค้ดทดลอง รหัสผ่าน หรือไฟล์ที่ไม่ตั้งใจหลุดเข้าไป การอ่าน Diff ยังเป็นทักษะหลักของ Code Review ใน Step 9
ลงมือทำ
  • ใน first-repo ให้แก้ไฟล์ แล้วรัน git diff, git add, git diff อีกครั้ง และ git diff --staged สังเกตว่าผลย้ายจากคำสั่งหนึ่งไปอีกคำสั่งหนึ่ง
  • สร้าง Alias git lg แล้วใช้แทน git log ตลอดหัวข้อนี้
  • ใช้ git log -S หา Commit ที่เพิ่มคำว่า "วันแรก" และเปิดดูด้วย git show

STEP 4

Commit อย่างมืออาชีพ: Conventional Commits และ .gitignore

1 วัน · 1–1.5 ชม.
หัวข้อย่อย
  • Atomic commit: 1 Commit มี 1 เรื่อง เช่น แก้บั๊กกับเปลี่ยนสีปุ่มต้องแยกเป็น 2 Commit ทำให้ Revert, Review และ Cherry-pick ได้ทีละเรื่อง และ Commit บ่อยๆ ทุกครั้งที่งานย่อยเสร็จและยังทำงานได้
  • รูปแบบข้อความที่ดี: บรรทัดแรก (Subject) ไม่เกินประมาณ 50 ตัวอักษร เขียนแบบคำสั่ง เช่น add ไม่ใช่ added แล้วเว้น 1 บรรทัด ตามด้วยเนื้อหา (Body) ที่อธิบายว่า ทำไม ต้องเปลี่ยน ตัดบรรทัดที่ประมาณ 72 ตัวอักษร
  • Conventional Commits 1.0.0: รูปแบบ type(scope): description เช่น feat(menu): add iced latte โดย type ที่ใช้บ่อยคือ feat (ความสามารถใหม่), fix (แก้บั๊ก), docs, style (จัดรูปแบบโค้ด ไม่เปลี่ยนการทำงาน), refactor, test, perf, build, ci, chore และ revert
  • Breaking change: ใส่ ! หลัง type เช่น feat!: drop support for old URL หรือใส่ Footer BREAKING CHANGE: ... และความเชื่อมโยงกับ Semantic Versioning: fix เพิ่มเลข PATCH, feat เพิ่มเลข MINOR และ Breaking change เพิ่มเลข MAJOR
  • ไวยากรณ์ .gitignore: *.log (ทุกไฟล์ที่ลงท้าย .log), build/ (ทั้งโฟลเดอร์), /todo.txt (เฉพาะที่ราก Repository), **/temp (ทุกระดับ), !keep.log (ยกเว้น) และ # สำหรับ Comment
  • สิ่งที่ต้อง Ignore เสมอ: ไฟล์ความลับ .env, Key และ Certificate, โฟลเดอร์ที่สร้างใหม่ได้ เช่น .venv/, node_modules/, __pycache__/, dist/, ไฟล์ Log และไฟล์ของระบบอย่าง .DS_Store และ Thumbs.db และใช้แม่แบบจาก Repository github/gitignore เป็นจุดเริ่ม
  • รูปแบบ .env กับ .env.example: เก็บค่าจริงใน .env ที่ถูก Ignore และ Commit ไฟล์ .env.example ที่มีแต่ชื่อตัวแปรไม่มีค่า เพื่อบอกคนในทีมว่าต้องตั้งค่าอะไรบ้าง
  • ไฟล์ที่ถูก Track ไปแล้ว .gitignore จะไม่มีผล ต้องเอาออกจากการ Track ด้วย git rm --cached ไฟล์ แล้ว Commit และตรวจว่ากฎไหนทำให้ไฟล์ถูก Ignore ด้วย git check-ignore -v ไฟล์ และ git status --ignored
ทำไมต้องเรียน
ประวัติ Commit คือเอกสารที่อยู่กับโปรเจกต์ตลอดไป ข้อความอย่าง update หรือ แก้งาน ไม่ช่วยใครเลยเมื่อต้องหาว่าบั๊กเริ่มเมื่อไร ทีมจำนวนมากใช้ Conventional Commits เพื่อสร้าง Changelog และกำหนดเลขเวอร์ชันอัตโนมัติ ส่วน .gitignore คือด่านแรกที่ป้องกันรหัสผ่านและ API Key หลุดขึ้น GitHub ซึ่งเป็นเหตุการณ์ด้านความปลอดภัยที่พบบ่อยมาก
ลงมือทำ
  • สร้าง .gitignore, .env และ .env.example ตามตัวอย่างด้านล่าง แล้วพิสูจน์ด้วย git check-ignore -v
  • เขียน Commit message แบบ Conventional Commits ให้ 5 สถานการณ์: เพิ่มหน้า About, แก้ลิงก์เสีย, แก้คำผิดใน README, ปรับโครงสร้าง CSS โดยหน้าตาไม่เปลี่ยน และเพิ่ม Workflow ของ CI
  • สร้างไฟล์ debug.log แล้ว Commit โดยตั้งใจ จากนั้นเอาออกจากการ Track ด้วย git rm --cached และเพิ่ม *.log ใน .gitignore

Security

ใส่ .env ใน .gitignore ก่อน สร้างไฟล์ .env เสมอ และตรวจ git status ก่อน git add . ทุกครั้ง ถ้าเผลอ Commit ความลับไปแล้ว การลบไฟล์ใน Commit ถัดไปไม่พอ เพราะความลับยังอยู่ในประวัติ วิธีจัดการที่ถูกต้องอยู่ใน Step 13

Checkpoint

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) เขียน Commit message แบบ Conventional Commits ให้ 5 สถานการณ์ในส่วนลงมือทำได้ถูกต้องทั้ง type และรูปแบบ (2) เขียน .gitignore ที่ Ignore .env แต่ยังเก็บ .env.example และพิสูจน์ด้วย git check-ignore -v (3) เอาไฟล์ที่ Track ไปแล้วออกจาก Git โดยไฟล์ในเครื่องยังอยู่ด้วย git rm --cached (4) อธิบายว่าทำไม Commit ที่ปนหลายเรื่องจึงเป็นปัญหาตอน Revert

หัวข้อย่อย
  • คิดก่อนสั่ง: ความผิดพลาดอยู่ที่พื้นที่ไหน (Working Tree, Staging, Commit ในเครื่อง หรือ Commit ที่ Push แล้ว) เพราะแต่ละพื้นที่ใช้คำสั่งต่างกัน ดูตารางตัดสินใจด้านล่าง
  • git restore ไฟล์ ทิ้งการแก้ไขที่ยังไม่ add ให้ไฟล์กลับไปเหมือน Staging หรือ Commit ล่าสุด และ git restore --source=HEAD~2 ไฟล์ ดึงไฟล์จาก Commit ในอดีตกลับมา (คำสั่ง restore และ switch มีตั้งแต่ Git 2.23 แทนคำสั่ง checkout แบบเดิมที่ทำหลายหน้าที่จนสับสน)
  • git restore --staged ไฟล์ เอาไฟล์ออกจาก Staging Area โดยการแก้ไขในไฟล์ยังอยู่ครบ
  • git commit --amend แก้ Commit ล่าสุด ทั้งแก้ข้อความ (git commit --amend -m "...") และเติมไฟล์ที่ลืม (git add ไฟล์ แล้ว git commit --amend --no-edit) โดย Git สร้าง Commit ใหม่ที่มีรหัสใหม่แทนอันเดิม
  • git revert รหัส-commit สร้าง Commit ใหม่ที่ทำตรงข้ามกับ Commit เดิม ประวัติเดิมยังอยู่ครบ จึงเป็นวิธีที่ปลอดภัยสำหรับ Commit ที่ Push และแชร์กับทีมแล้ว ส่วน Merge commit ต้องระบุฝั่งหลักด้วย git revert -m 1 รหัส
  • ไฟล์ Untracked ที่ไม่ต้องการ: ดูก่อนด้วย git clean -n (Dry run) แล้วค่อยลบจริงด้วย git clean -f ใส่ -d เพื่อรวมโฟลเดอร์
  • สิ่งที่กู้คืนไม่ได้: การแก้ไขที่ไม่เคย add หรือ Commit แล้วถูก git restore หรือ git clean ทับ หายถาวร เพราะ Git ไม่เคยบันทึกไว้ ส่วน Commit ที่ "หาย" ส่วนใหญ่กู้ได้ด้วย git reflog ใน Step 10
ทำไมต้องเรียน
มือใหม่หลายคนเมื่อ Git มีปัญหาจะลบโฟลเดอร์แล้ว Clone ใหม่ ซึ่งทำให้งานที่ยังไม่ Push หาย การรู้ว่าคำสั่งไหนปลอดภัยกับสถานการณ์ไหนทำให้คุณกล้าทดลอง และแก้ความผิดพลาดของตัวเองได้ภายในไม่กี่วินาที ในงานจริง git revert คือวิธีมาตรฐานในการถอนการเปลี่ยนแปลงที่ทำให้ระบบ Production พัง
ลงมือทำ
  • ทำตามทั้ง 5 สถานการณ์ในตารางด้านล่างใน first-repo และรัน git status กับ git log --oneline หลังแต่ละครั้ง
  • Commit โดยลืมไฟล์หนึ่งไฟล์ แล้วเติมด้วย git commit --amend --no-edit สังเกตว่ารหัส Commit เปลี่ยน
  • Revert Commit ที่อยู่ลึกลงไป 2 Commit และเปิดดูด้วย git show ว่า Commit ใหม่ทำอะไร

STEP 6

Branch, Merge และ Stash

2 วัน · 1.5–2 ชม.
หัวข้อย่อย
  • Branch คือป้ายชื่อที่ชี้ไปยัง Commit หนึ่ง และเลื่อนตามไปเองเมื่อ Commit ใหม่ การสร้าง Branch จึงเร็วมากและไม่คัดลอกไฟล์ ส่วน HEAD บอกว่าตอนนี้เราอยู่บน Branch ไหน
  • คำสั่งหลัก: git branch (ดูรายการ), git switch -c feature/contact (สร้างและย้ายไป), git switch main, git switch - (กลับ Branch ก่อนหน้า), git branch -m ชื่อใหม่ (เปลี่ยนชื่อ) และรู้ว่าคำสั่ง git checkout -b ในบทความเก่าทำงานเหมือน git switch -c
  • ตั้งชื่อ Branch ให้สื่อความหมาย: feature/about-page, fix/broken-link, docs/readme-install ใช้ตัวพิมพ์เล็กและขีดกลาง ไม่เว้นวรรค ไม่ใช้ภาษาไทย
  • Merge แบบ Fast-forward: เมื่อ main ไม่มี Commit ใหม่ระหว่างที่เราทำงาน Git แค่เลื่อนป้าย main ไปข้างหน้า ไม่มี Commit ใหม่เกิดขึ้น และบังคับให้รวมแบบนี้เท่านั้นด้วย git merge --ff-only
  • Merge commit (3-way merge): เมื่อทั้งสองฝั่งมี Commit ใหม่ Git สร้าง Commit ที่มี 2 Parent เพื่อรวมงาน และบังคับให้สร้าง Merge commit เสมอด้วย git merge --no-ff เพื่อเก็บร่องรอยว่างานชุดนี้มาจาก Branch ไหน
  • ลบ Branch ที่รวมแล้วด้วย git branch -d ชื่อ (Git ไม่ยอมลบถ้ายังไม่ได้ Merge) และ git branch -D ชื่อ (บังคับลบ ต้องแน่ใจก่อน) ดู Branch ที่รวมแล้วด้วย git branch --merged
  • Stash สำหรับงานค้าง: git stash push -m "ข้อความ" เก็บงานที่ยังไม่ Commit ไว้ชั่วคราว, -u รวมไฟล์ Untracked, git stash list, git stash show -p, git stash pop (นำกลับและลบออกจากรายการ), git stash apply (นำกลับแต่ยังเก็บไว้) และ git stash drop
  • Detached HEAD: เกิดเมื่อ git switch --detach รหัส หรือ git checkout รหัส เพื่อดูโค้ดในอดีต ถ้าจะ Commit ต่อจากตรงนั้นให้สร้าง Branch ด้วย git switch -c ชื่อ ก่อน มิฉะนั้นกลับด้วย git switch main
ทำไมต้องเรียน
ในงานจริง main ต้องอยู่ในสภาพที่ใช้งานได้เสมอ งานใหม่ทุกชิ้นจึงทำบน Branch แยก แล้วรวมเมื่อเสร็จและผ่านการรีวิว ถ้าหัวหน้าขอให้แก้บั๊กด่วนระหว่างที่คุณทำงานค้างอยู่ Stash ทำให้เก็บงานไว้ แล้วสลับไปแก้บั๊กได้ภายในไม่กี่วินาที ความเข้าใจเรื่อง Fast-forward กับ Merge commit ยังจำเป็นต่อการเลือกวิธี Merge ของ Pull Request ใน Step 9
ลงมือทำ
  • ทำตามตัวอย่างด้านล่างใน first-repo แล้ววาดกราฟบนกระดาษเทียบกับผลของ git log --oneline --graph --all
  • ลอง Merge แบบ --no-ff กับ Branch ที่ Fast-forward ได้ แล้วเปรียบเทียบกราฟ
  • แก้ไฟล์ค้างไว้ ใช้ git stash push -m "wip: contact form" สลับไป Branch อื่น แล้วกลับมา git stash pop

STEP 7

แก้ Merge Conflict ทีละขั้น

1–2 วัน · 1.5–2 ชม.
หัวข้อย่อย
  • Conflict เกิดเมื่อไร: ทั้งสอง Branch แก้บรรทัดเดียวกันของไฟล์เดียวกัน, ฝั่งหนึ่งลบไฟล์แต่อีกฝั่งแก้ไฟล์นั้น หรือทั้งสองฝั่งสร้างไฟล์ชื่อเดียวกัน ส่วนการแก้คนละบรรทัดหรือคนละไฟล์ Git รวมให้เองอัตโนมัติ
  • อ่าน Conflict marker: ส่วนระหว่าง <<<<<<< HEAD กับ ======= คือของ Branch ที่เรายืนอยู่ ส่วนระหว่าง ======= กับ >>>>>>> ชื่อ-branch คือของ Branch ที่กำลังรวมเข้ามา และตั้ง git config --global merge.conflictStyle zdiff3 เพื่อเห็นเนื้อหาดั้งเดิม (Base) ในส่วน ||||||| ด้วย
  • ขั้นตอนมาตรฐาน: git status ดูไฟล์ที่ชน → เปิดไฟล์และตัดสินใจว่าผลลัพธ์ที่ถูกต้องคืออะไร (เลือกฝั่งหนึ่ง รวมทั้งสองฝั่ง หรือเขียนใหม่) → ลบ Marker ทั้ง 3 แบบออก → git add ไฟล์ → git commit (หรือ git merge --continue)
  • ทางออกฉุกเฉิน: git merge --abort ยกเลิกการ Merge ทั้งหมดกลับไปสภาพก่อนเริ่ม และดูรายชื่อไฟล์ที่ยังชนอยู่ด้วย git diff --name-only --diff-filter=U
  • เลือกทั้งไฟล์จากฝั่งเดียว: git checkout --ours ไฟล์ หรือ git checkout --theirs ไฟล์ ซึ่งเหมาะกับไฟล์ที่อ่านไม่ได้ด้วยตา เช่น รูปภาพ (ระวังว่าความหมายของ ours กับ theirs สลับกันตอน Rebase)
  • Merge Editor ของ VS Code: กดปุ่ม Resolve in Merge Editor แล้วเลือก Accept Current, Accept Incoming หรือ Accept Both ทีละจุด พร้อมเห็นผลลัพธ์ด้านล่าง
  • Conflict ไม่ได้เกิดเฉพาะตอน Merge แต่เกิดได้ตอน git pull, git rebase, git stash pop และ git cherry-pick โดยใช้วิธีแก้เดียวกัน
  • ลดโอกาสเกิด Conflict: แตก Branch สั้นๆ และรวมบ่อย, ดึง main ล่าสุดก่อนเริ่มงาน, คุยกันในทีมว่าใครแก้ไฟล์ไหน และใช้ Formatter เดียวกันทั้งทีม เพื่อไม่ให้การจัดย่อหน้าต่างกันกลายเป็น Conflict
ทำไมต้องเรียน
Conflict เป็นเรื่องปกติของการทำงานเป็นทีม ไม่ใช่ความผิดพลาด แต่มือใหม่จำนวนมากตกใจแล้วลบงานของเพื่อนทิ้ง หรือ Commit ไฟล์ที่ยังมี <<<<<<< ค้างอยู่จนโปรแกรมพัง การแก้ Conflict อย่างมีขั้นตอนและตรวจผลก่อน Commit คือทักษะที่หัวหน้าทีมคาดหวังจากนักพัฒนาทุกระดับ
ลงมือทำ
  • สร้าง Conflict โดยตั้งใจตามตัวอย่างด้านล่าง (ราคาลาเต้ 60 กับ 65 บาท) แล้วแก้ให้เหลือ 60 บาท
  • สร้าง Conflict อีกครั้ง แล้วยกเลิกด้วย git merge --abort ตรวจว่าไฟล์กลับเป็นเหมือนเดิม
  • สร้าง Conflict ในห้องทดลอง hello-team ระหว่างสมชายกับมาลี แล้วแก้ผ่าน Merge Editor ของ VS Code

STEP 8

GitHub, SSH Key และ Remote: push, fetch, pull, clone

2–3 วัน · 2.5–3 ชม.
หัวข้อย่อย
  • สมัคร GitHub: เลือก Username ที่ดูเป็นมืออาชีพเพราะจะอยู่ใน URL ของ Portfolio (ตัวอย่างในหลักสูตรนี้ใช้ somchai-dev), ใส่รูปและ Bio, เปิด Two-factor authentication (2FA) ด้วยแอป Authenticator ซึ่ง GitHub กำหนดให้บัญชีที่ส่งโค้ดต้องเปิด และเก็บ Recovery codes ไว้ในที่ปลอดภัย
  • ปกป้องอีเมล: เปิด Keep my email addresses private และ Block command line pushes that expose my email ในหน้า Settings → Emails แล้วตั้ง git config --global user.email เป็นอีเมล noreply ที่ GitHub ให้ ซึ่งมีรูปแบบ ตัวเลข+username@users.noreply.github.com
  • SSH Key สำหรับ GitHub: ใช้ Key จากหัวข้อ Linux ได้เลย หรือสร้างใหม่ด้วย ssh-keygen -t ed25519 -C "อีเมล" ตั้ง Passphrase, ใช้ ssh-agent กับ ssh-add เพื่อไม่ต้องพิมพ์ Passphrase บ่อย แล้วนำ Public key (~/.ssh/id_ed25519.pub) ไปเพิ่มที่ Settings → SSH and GPG keys → New SSH key
  • ทดสอบด้วย ssh -T git@github.com และตรวจ Fingerprint ครั้งแรกให้ตรงกับที่ GitHub ประกาศในหน้า GitHub's SSH key fingerprints (ED25519 คือ SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU) ก่อนพิมพ์ yes
  • SSH กับ HTTPS: URL แบบ git@github.com:somchai-dev/portfolio.git ใช้ SSH Key ส่วนแบบ https://github.com/somchai-dev/portfolio.git ต้องใช้ Personal Access Token หรือ Credential Manager เพราะ GitHub เลิกรับรหัสผ่านบัญชีสำหรับคำสั่ง Git ตั้งแต่ปี 2021 หลักสูตรนี้ใช้ SSH
  • เชื่อม Repository เดิมกับ GitHub: สร้าง Repository เปล่าบนเว็บ (ไม่ติ๊กสร้าง README) แล้วใช้ git remote add origin URL, git remote -v, git push -u origin main (-u ผูก main กับ origin/main ครั้งเดียว ครั้งต่อไปพิมพ์แค่ git push) และดูการผูกด้วย git branch -vv
  • ดึงงานจากทีม: git clone URL (คัดลอกทั้ง Repository ครั้งแรก), git fetch (ดึงประวัติใหม่มาไว้ที่ origin/main แต่ยังไม่แตะไฟล์ของเรา), git fetch --prune (ลบป้าย Branch ที่ถูกลบบน Remote แล้ว) และ git pull (= fetch แล้ว merge หรือ rebase)
  • สถานการณ์ที่ต้องรู้: Push ถูกปฏิเสธด้วย (fetch first), ข้อความ divergent branches ตอน Pull และการตั้งค่า pull.rebase false ตามที่ฝึกในห้องทดลอง และห้ามแก้ด้วย git push --force บน Branch ที่ใช้ร่วมกัน
  • Push Learning Journal จาก Day 0 ขึ้น GitHub เป็น Repository แรก และตั้งนิสัย git pull ก่อนเริ่มงานทุกวัน กับ git push ทุกครั้งที่เลิกงาน
ทำไมต้องเรียน
Repository ที่อยู่แค่ในเครื่องหายได้ทันทีเมื่อคอมพิวเตอร์เสีย การ Push ขึ้น GitHub คือทั้งการสำรองข้อมูลและการแชร์งาน SSH Key ทำให้ Push ได้โดยไม่ต้องพิมพ์รหัสผ่านและปลอดภัยกว่า ส่วนความเข้าใจเรื่อง fetch กับ pull และการจัดการ Push ที่ถูกปฏิเสธ คือสิ่งที่จะเจอทุกวันเมื่อทำงานกับทีม ถ้าแก้ผิดวิธีด้วย --force อาจลบงานของเพื่อนร่วมทีมได้
ลงมือทำ
  • ทำห้องทดลอง hello-team ให้ครบตั้งแต่ต้นจนจบ แล้วให้มาลีทำ git pull เพื่อรับงานของสมชาย
  • สมัคร GitHub เปิด 2FA ตั้งอีเมล noreply เพิ่ม SSH Key และทดสอบด้วย ssh -T git@github.com
  • สร้าง Repository learning-journal บน GitHub แล้ว Push Learning Journal ขึ้นไปตามตัวอย่างด้านล่าง เปิดเว็บดูว่าไฟล์และประวัติ Commit ขึ้นครบ

STEP 9

Pull Request, Fork, Issues, Projects และ GitHub CLI

2–3 วัน · 2.5–3 ชม.
หัวข้อย่อย
  • ติดตั้ง GitHub CLI (gh) ตามคู่มือทางการสำหรับ Ubuntu ซึ่งเพิ่ม apt repository ของ GitHub เอง (แพ็กเกจ gh ใน apt ของ Ubuntu 24.04 เป็นรุ่น 2.45.0 ซึ่งเก่ากว่ามาก) แล้ว Login ด้วย gh auth login และตรวจด้วย gh auth status
  • วงจร Pull Request: แตก Branch → Commit → git push -u origin ชื่อ-branch → gh pr create → รอผล Check อัตโนมัติและ Review → แก้ตามความเห็นแล้ว Push เพิ่มใน Branch เดิม → Merge → ลบ Branch → git switch main และ git pull
  • วิธี Merge บน GitHub 3 แบบ: Create a merge commit (เก็บทุก Commit พร้อม Merge commit), Squash and merge (รวมทุก Commit ของ PR เป็น Commit เดียวบน main) และ Rebase and merge (เรียง Commit ต่อท้ายโดยไม่มี Merge commit) พร้อมเหตุผลในการเลือกใช้
  • เขียน PR ที่ดี: ชื่อแบบ Conventional Commits, คำอธิบายว่าทำอะไร ทำไม ทดสอบอย่างไร และภาพหน้าจอถ้าเปลี่ยนหน้าตา, PR เล็กที่รีวิวได้ในไม่กี่นาที, ใช้ Draft PR เมื่องานยังไม่เสร็จ และสร้างแม่แบบที่ .github/pull_request_template.md
  • มารยาทของ Code Review: วิจารณ์โค้ดไม่ใช่ตัวคน, ชี้จุดให้ชัดพร้อมเหตุผล, ใช้คำถามแทนคำสั่ง, แยกเรื่องเล็กด้วยคำว่า nit:, ชมสิ่งที่ทำดี, ใช้ Suggestion ของ GitHub เสนอโค้ดแก้ และฝั่งผู้ส่ง PR ต้องตอบทุกความเห็นและไม่ถือเป็นเรื่องส่วนตัว
  • GitHub Issues: บันทึกบั๊กและงานที่ต้องทำ, Labels, Assignees, Milestones, Issue templates และคำปิด Issue อัตโนมัติในคำอธิบาย PR เช่น Closes #3, Fixes #3 หรือ Resolves #3 ซึ่งทำงานเมื่อ PR ถูก Merge เข้า Branch หลัก รวมถึงคำสั่ง gh issue create และ gh issue list
  • GitHub Projects: บอร์ดแบบ Kanban (Todo, In Progress, Done) ที่ดึง Issue และ PR มาจัดลำดับงาน ใช้วางแผน Mini Project ของหัวข้อนี้
  • Fork กับ Clone: Fork คือสำเนา Repository ของคนอื่นที่อยู่ในบัญชี GitHub ของเรา ใช้ส่ง PR ให้โปรเจกต์ที่เราไม่มีสิทธิ์เขียน ตั้ง Remote ชื่อ upstream ชี้ไปที่ต้นฉบับ แล้วอัปเดตด้วย git fetch upstream หรือปุ่ม Sync fork หรือ gh repo sync และอ่าน CONTRIBUTING.md กับ Label good first issue ก่อนร่วมโปรเจกต์ Open Source
  • Branch protection และ Rulesets: บังคับว่า main ต้องรับงานผ่าน PR เท่านั้น ต้องผ่าน Status checks และห้าม Force push ซึ่งจะตั้งจริงใน Mini Project

STEP 10

เขียนประวัติใหม่อย่างปลอดภัย: Rebase, Reset และ Reflog

2 วัน · 2–2.5 ชม.
หัวข้อย่อย
  • Rebase คืออะไร: ย้าย Commit ของ Branch เราไปต่อท้าย Commit ล่าสุดของอีก Branch (git switch feature/x แล้ว git rebase main) ได้ประวัติเป็นเส้นตรงไม่มี Merge commit แต่ทุก Commit ที่ถูกย้ายจะได้รหัสใหม่ เพราะ Parent เปลี่ยน
  • Conflict ระหว่าง Rebase: แก้ไฟล์ → git add → git rebase --continue หรือข้าม Commit นั้นด้วย git rebase --skip หรือยกเลิกทั้งหมดด้วย git rebase --abort
  • Interactive rebase: git rebase -i HEAD~3 เปิดรายการ Commit ใน Editor ให้เปลี่ยนคำหน้าแต่ละบรรทัดเป็น pick, reword (แก้ข้อความ), edit, squash (รวมกับ Commit ก่อนหน้าและรวมข้อความ), fixup (รวมโดยทิ้งข้อความ) หรือ drop และใช้คู่กับ git commit --fixup รหัส แล้ว git rebase -i --autosquash main เพื่อเก็บงานแก้เล็กๆ ก่อนเปิด PR
  • กฎทองของ Rebase: ห้าม Rebase หรือ Amend Commit ที่ Push ขึ้นไปและคนอื่นใช้ต่อแล้ว เช่น main เพราะประวัติของทุกคนจะไม่ตรงกัน ถ้าเป็น Branch ของ PR ที่คุณทำคนเดียว ให้ Push ใหม่ด้วย git push --force-with-lease ซึ่งจะไม่ยอมเขียนทับถ้ามีคนอื่น Push อะไรเพิ่มไว้ ห้ามใช้ --force เปล่าๆ
  • git pull --rebase: ดึงงานแล้วเอา Commit ในเครื่องที่ยังไม่ Push ไปต่อท้าย แทนการสร้าง Merge commit ทุกครั้งที่ Pull ใช้เป็นครั้งคราว หรือตั้งเป็นค่าเริ่มต้นด้วย git config --global pull.rebase true เมื่อเข้าใจกฎทองแล้ว
  • git reset 3 โหมด (ดูตารางด้านล่าง): --soft ย้าย Branch กลับแต่เก็บการเปลี่ยนแปลงไว้ใน Staging, --mixed (ค่าเริ่มต้น) เก็บไว้ใน Working Tree และ --hard ทิ้งทั้งหมดรวมถึงไฟล์ที่ยังไม่ Commit ซึ่งอันตรายที่สุด
  • git reflog คือสมุดบันทึกว่า HEAD เคยชี้ที่ไหนบ้าง ใช้กู้ Commit ที่หายหลัง reset --hard, Rebase ที่ผิดพลาด หรือ Branch ที่ลบไป (git switch -c ชื่อ HEAD@{3}) รายการใน Reflog ถูกเก็บไว้ตามค่าเริ่มต้นประมาณ 90 วัน (Commit ที่ไม่มี Branch ชี้ถึงประมาณ 30 วัน) และอยู่ในเครื่องเท่านั้น ไม่ถูก Push
  • เลือก Merge หรือ Rebase: Rebase Branch ส่วนตัวให้ทันสมัยก่อนเปิด PR ใช้ Merge เมื่อรวมงานที่แชร์แล้ว และทำตามข้อตกลงของทีมเสมอ
ทำไมต้องเรียน
ก่อนส่ง PR นักพัฒนามืออาชีพจะจัด Commit อย่าง wip, fix typo, fix again ให้เหลือ Commit ที่มีความหมาย ทำให้ผู้รีวิวอ่านง่ายและประวัติของโปรเจกต์ใช้ค้นหาบั๊กได้ ส่วน Reflog คือตาข่ายนิรภัยที่ทำให้กล้าใช้คำสั่งเหล่านี้ เพราะรู้ว่างานที่ Commit แล้วเกือบทุกกรณีกู้คืนได้ คำถามเรื่อง Merge กับ Rebase และ reset 3 โหมดยังเป็นคำถามสัมภาษณ์ที่พบบ่อยมาก
ลงมือทำ
  • ใน first-repo สร้าง Branch ที่มี 3 Commit ชื่อ wip 1, wip 2, wip 3 แล้วใช้ git rebase -i รวมเป็น Commit เดียวชื่อ feat: add dessert menu
  • ให้ main มี Commit ใหม่ แล้ว Rebase Branch ของคุณไปต่อท้าย และแก้ Conflict ระหว่าง Rebase อย่างน้อย 1 ครั้ง
  • ทดลอง reset --soft, --mixed และ --hard กับ Commit ล่าสุดทีละโหมด และดู git status หลังแต่ละครั้ง
  • จำลองความผิดพลาดและกู้คืนด้วย Reflog ตามตัวอย่างด้านล่าง

STEP 11

เครื่องมือสืบสวนและออก Release: bisect, cherry-pick, blame, Tags และ Git LFS

2 วัน · 1.5–2 ชม.
หัวข้อย่อย
  • git blame ไฟล์ แสดงว่าแต่ละบรรทัดถูกแก้ล่าสุดใน Commit ไหน โดยใคร เมื่อไร ใช้ -L 10,20 ดูเฉพาะช่วงบรรทัด และ -w ไม่นับการเปลี่ยนแค่ช่องว่าง บน GitHub ใช้ปุ่ม Blame ในหน้าไฟล์ จุดประสงค์คือหาบริบทว่าทำไมโค้ดเป็นแบบนี้ ไม่ใช่หาคนผิด
  • ค้นในประวัติ: git log -S "ข้อความ" หา Commit ที่ทำให้ข้อความนั้นเพิ่มหรือหายไป, git log -G "regex" และ git grep "ข้อความ" ค้นในไฟล์ทั้ง Repository เร็วกว่า grep -r เพราะข้ามไฟล์ที่ไม่ได้ Track
  • git bisect ค้นหา Commit แรกที่ทำให้เกิดบั๊กด้วย Binary search: git bisect start, git bisect bad, git bisect good รหัส, ทดสอบแล้วตอบทีละขั้น และจบด้วย git bisect reset จาก 1,000 Commit ใช้ทดสอบประมาณ 10 ครั้งเท่านั้น
  • git bisect run ./check.sh ให้ Script ตัดสินเอง: exit code 0 คือดี, 1–127 (ยกเว้น 125) คือเสีย และ 125 คือข้าม Commit นี้ ทำให้ค้นหาได้อัตโนมัติทั้งหมด
  • git cherry-pick รหัส คัดลอก Commit เดียวจาก Branch หนึ่งไปใส่อีก Branch เช่น นำ Hotfix ไปใส่ Branch release/1.0 ใช้ -x เพื่อจดว่าคัดลอกมาจาก Commit ไหน และเมื่อชนให้แก้แล้ว git cherry-pick --continue หรือ --abort
  • Tags: Lightweight tag (git tag v1.0.0) กับ Annotated tag (git tag -a v1.0.0 -m "First release" ที่เก็บผู้สร้าง วันที่ และข้อความ ควรใช้สำหรับ Release), git tag -l "v1.*", git show v1.0.0, Push ด้วย git push origin v1.0.0 หรือ git push --follow-tags และลบด้วย git tag -d กับ git push origin --delete v1.0.0
  • Semantic Versioning (MAJOR.MINOR.PATCH): เพิ่ม MAJOR เมื่อมีการเปลี่ยนที่ทำให้ของเดิมใช้ไม่ได้, MINOR เมื่อเพิ่มความสามารถ, PATCH เมื่อแก้บั๊ก และ GitHub Releases ที่สร้างจาก Tag พร้อม Release notes ด้วย gh release create v1.0.0 --generate-notes
  • Git LFS (Large File Storage) ภาพรวม: Git ไม่เหมาะกับไฟล์ Binary ขนาดใหญ่ เพราะทุกเวอร์ชันถูกเก็บเต็มๆ ทำให้ Repository บวม และ GitHub ปฏิเสธไฟล์ที่ใหญ่กว่า 100 MiB (เตือนตั้งแต่ 50 MiB) Git LFS 3.4.1 (sudo apt install -y git-lfs) เก็บไฟล์ใหญ่แยกไว้ และใส่แค่ตัวชี้ใน Repository: git lfs install, git lfs track "*.psd" แล้ว Commit ไฟล์ .gitattributes โดย GitHub มีโควตาพื้นที่และ Bandwidth ของ LFS ซึ่งควรตรวจตัวเลขล่าสุดในหน้า Billing ก่อนใช้

STEP 12

GitHub Actions (CI) และ GitHub Pages (CD)

2–3 วัน · 2.5–3 ชม.
หัวข้อย่อย
  • CI/CD คืออะไร: Continuous Integration ตรวจทุกการเปลี่ยนแปลงอัตโนมัติ (Build, Lint, Test) ก่อนรวมเข้า main ส่วน Continuous Delivery/Deployment นำงานที่ผ่านการตรวจขึ้นระบบจริงอัตโนมัติ ลดงานมือและความผิดพลาดจากคน
  • โครงสร้างของ GitHub Actions: ไฟล์ YAML ในโฟลเดอร์ .github/workflows/ ประกอบด้วย name, on (Trigger), jobs แต่ละ Job มี runs-on (เครื่อง Runner เช่น ubuntu-latest ซึ่งปัจจุบันคือ Ubuntu 24.04) และ steps ซึ่งแต่ละ Step จะใช้ Action สำเร็จรูปด้วย uses หรือรันคำสั่ง Shell ด้วย run
  • Trigger ที่ใช้บ่อย: push, pull_request (กรองด้วย branches และ paths), workflow_dispatch (ปุ่มรันเองในแท็บ Actions) และ schedule ที่ใช้ Cron ตามเวลา UTC เช่น 0 1 * * 1 คือทุกวันจันทร์ 08:00 น. เวลาประเทศไทย
  • ไวยากรณ์ YAML ที่ต้องระวัง: ย่อหน้าด้วยช่องว่างเท่านั้น ห้ามใช้ Tab, รายการขึ้นต้นด้วย - , key: value ต้องมีช่องว่างหลัง : และข้อความที่มี * หรือ : ควรครอบด้วยเครื่องหมายคำพูด
  • Workflow ตรวจเว็บ: Action actions/checkout@v5 ดึงโค้ด, actions/setup-node@v5 ติดตั้ง Node.js 24 แล้วรัน npx --yes html-validate@11.16.2 ตรวจ HTML และ npx --yes linkinator@8.1.0 ตรวจลิงก์เสีย โดยรันคำสั่งเดียวกันในเครื่องให้ผ่านก่อน (ต้องติดตั้ง Node.js LTS ผ่าน nvm v0.40.8 ก่อน ดูส่วนที่ 2 ของหัวข้อนี้)
  • อ่านผลในแท็บ Actions และในหน้า PR: เครื่องหมายถูกสีเขียวหรือกากบาทสีแดงข้าง Commit, เปิด Log ของ Step ที่ล้มเหลว, กด Re-run jobs และตั้ง Branch protection ให้ PR ต้องผ่าน Check นี้ก่อน Merge ได้ (Required status checks)
  • ความปลอดภัยของ Actions: เก็บค่าลับใน Settings → Secrets and variables → Actions แล้วอ้างด้วย ${{ secrets.ชื่อ }}, ห้าม echo ค่าลับ, กำหนด permissions: contents: read ให้ GITHUB_TOKEN มีสิทธิ์น้อยที่สุด และระบุเวอร์ชันของ Action เสมอ (Major tag เช่น @v5 หรือรหัส Commit เต็มเพื่อความปลอดภัยสูงสุด)
  • GitHub Pages: เผยแพร่เว็บ Static (HTML, CSS, JavaScript) ฟรีสำหรับ Public repository ที่ URL https://somchai-dev.github.io/portfolio/ ตั้งค่าที่ Settings → Pages → Build and deployment ได้ 2 แบบ คือ Deploy from a branch (เลือก main และโฟลเดอร์ / (root) เหมาะกับเริ่มต้น) และ GitHub Actions (ใช้ Workflow ที่มี actions/configure-pages@v5, actions/upload-pages-artifact@v4 และ actions/deploy-pages@v4 เพื่อ Deploy หลังผ่านการตรวจเท่านั้น)
  • เรื่องที่ต้องรู้ของ Pages: ใช้ลิงก์แบบ Relative (css/style.css ไม่ใช่ /css/style.css) เพราะเว็บอยู่ใต้ /portfolio/, ไฟล์หน้าแรกต้องชื่อ index.html, สร้าง 404.html ได้, ใส่ไฟล์เปล่า .nojekyll เมื่อ Deploy จาก Branch เพื่อปิด Jekyll และการอัปเดตใช้เวลาประมาณ 1–10 นาที ส่วนนาทีของ Actions ฟรีไม่จำกัดสำหรับ Public repository บน Runner มาตรฐาน แต่ Private repository มีโควตาต่อเดือน ให้ตรวจตัวเลขล่าสุดในหน้า Billing

# เหตุการณ์ที่ทำให้ Workflow ทำงาน
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
  workflow_dispatch:

# ให้ GITHUB_TOKEN มีสิทธิ์แค่อ่านโค้ด (ให้สิทธิ์น้อยที่สุดเท่าที่จำเป็น)

  contents: read

jobs:
  check-site:
    runs-on: ubuntu-latest
    steps:
      - name: ดึงโค้ดของ Repository ลงเครื่อง Runner

      - name: ติดตั้ง Node.js เพื่อใช้ npx
        uses: actions/setup-node@v5

Branching Strategy, ความปลอดภัย, License, Profile README และ Mini Project

3–4 วัน · 3–4 ชม.
หัวข้อย่อย
  • Branching strategy 3 แบบที่ต้องรู้ (ดูตารางด้านล่าง): GitHub flow (main พร้อม Deploy เสมอ ทุกงานทำบน Branch สั้นๆ แล้วเปิด PR), Trunk-based development (ทุกคนรวมงานเข้า main บ่อยมาก วันละครั้งหรือมากกว่า และซ่อนงานที่ยังไม่เสร็จด้วย Feature flag) และ Git Flow (มี main, develop, feature/*, release/*, hotfix/* เหมาะกับซอฟต์แวร์ที่ออกเป็นเวอร์ชันตามรอบ)
  • ตั้งค่า Repository แบบมืออาชีพ: Branch protection หรือ Rulesets ของ main (ต้องผ่าน PR, ต้องผ่าน CI, ห้าม Force push), เลือกวิธี Merge ที่อนุญาต เช่น อนุญาตเฉพาะ Squash merge และเปิด Automatically delete head branches
  • ปกป้อง Secret: .env อยู่ใน .gitignore ตั้งแต่ Commit แรก, Commit เฉพาะ .env.example, ใช้ GitHub Secrets สำหรับ Actions และรู้ว่า GitHub มี Secret scanning กับ Push protection ที่ตรวจพบ Token รูปแบบที่รู้จักและบล็อกการ Push ได้ (สำหรับ Public repository เปิดให้อัตโนมัติ ตรวจสถานะได้ที่ Settings ส่วน Security ของ Repository เพราะชื่อเมนูอาจเปลี่ยนตามการอัปเดตของ GitHub) และสแกนในเครื่องได้ด้วย gitleaks (apt มีรุ่น 8.16.0)
  • ถ้า Secret หลุดขึ้น GitHub แล้ว ให้ทำตามลำดับ: (1) ยกเลิกหรือเปลี่ยน Key นั้นทันที ที่ผู้ให้บริการ ซึ่งสำคัญที่สุด เพราะถือว่ามีคนได้ไปแล้ว (2) ตรวจ Log การใช้งานของ Key ว่าถูกใช้ผิดปกติหรือไม่ (3) ลบออกจากประวัติด้วย git filter-repo --invert-paths --path .env (apt แพ็กเกจ git-filter-repo รุ่น 2.38.0) แล้ว Force push และให้ทีม Clone ใหม่ (4) แจ้งทีมหรือหัวหน้า การลบไฟล์ใน Commit ถัดไปอย่างเดียว ไม่พอ เพราะความลับยังอยู่ในประวัติและใน Fork หรือ Clone ของคนอื่น
  • Signed commits: เซ็น Commit ด้วย SSH Key ที่มีอยู่แล้ว (git config --global gpg.format ssh, git config --global user.signingkey ~/.ssh/id_ed25519.pub, git config --global commit.gpgsign true) และเพิ่ม Key เดียวกันใน GitHub แบบ Signing Key เพื่อให้ Commit ขึ้นป้าย Verified และรู้จัก Dependabot alerts ที่แจ้งเมื่อ Library ที่ใช้มีช่องโหว่
  • License: ถ้าไม่ใส่ License ผู้อื่นไม่มีสิทธิ์นำโค้ดไปใช้ตามกฎหมายลิขสิทธิ์ แม้ Repository จะเป็น Public, ความต่างของ MIT (ให้ใช้ได้กว้างที่สุด), Apache-2.0 (มีเรื่องสิทธิบัตรเพิ่ม) และ GPL-3.0 (งานที่ดัดแปลงต้องเปิดเผยโค้ดด้วย License เดียวกัน) เลือกด้วย choosealicense.com และเพิ่มผ่าน GitHub ด้วย Add file → Create new file → พิมพ์ชื่อ LICENSE → Choose a license template
  • Profile README: สร้าง Public repository ชื่อเดียวกับ Username (somchai-dev/somchai-dev) ใส่ README.md ที่แนะนำตัว ทักษะ โปรเจกต์พร้อมลิงก์ และช่องทางติดต่อ ซึ่งจะแสดงบนหน้าโปรไฟล์ แล้ว Pin Repository ที่ดีที่สุด 6 อันไว้ด้านบน
  • README ของโปรเจกต์ที่ดี: โปรเจกต์นี้คืออะไร ทำไมสร้าง ลิงก์ Live demo ภาพหน้าจอ วิธีรันในเครื่อง เทคโนโลยีที่ใช้ สิ่งที่ได้เรียนรู้ และ License
  • Mini Project Portfolio Website บน GitHub Pages: Repository portfolio (HTML และ CSS ล้วน) พัฒนาทีละ Feature ผ่าน Branch และ PR, มี CI ตรวจ HTML และลิงก์ทุก PR, Branch protection ที่บังคับให้ CI ผ่าน, Deploy ด้วย GitHub Pages, Tag v1.0.0 พร้อม Release, Profile README และ Push learning-journal ขึ้น GitHub (ทำครบทุกขั้นตอนในส่วนที่ 4 ของหัวข้อนี้)

Security

ถ้า GitHub แจ้งว่าพบ Secret ใน Repository ของคุณ หรือ Push protection บล็อกการ Push อย่ากดข้ามการเตือน ให้ถือว่า Key นั้นหลุดแล้วและทำตามลำดับด้านบนทันที ขั้นตอนที่ 1 (ยกเลิกหรือเปลี่ยน Key) ต้องทำก่อนการลบประวัติเสมอ เพราะการลบประวัติไม่ทำให้สำเนาที่คนอื่นได้ไปแล้วหายไป

Must-know Skills

ถ้าสรุปหัวข้อนี้ให้เหลือทักษะที่งานจริงและผู้สัมภาษณ์คาดหวังจากคนที่บอกว่า "ใช้ Git เป็น" จะได้รายการด้านล่าง ทุกข้อฝึกครบใน 13 ขั้นข้างบน

  1. อธิบาย Working Tree, Staging Area, Local Repository และ Remote ได้ เพราะทุกคำสั่งของ Git คือการย้ายการเปลี่ยนแปลงระหว่าง 4 พื้นที่นี้ ถ้าเข้าใจภาพนี้จะเดาผลของคำสั่งได้ก่อนกด Enter
  2. สร้าง Commit เล็กที่มีเรื่องเดียว พร้อมข้อความแบบ Conventional Commits เพราะทีมอ่านประวัติจากข้อความ Commit และเครื่องมืออัตโนมัติใช้คำนำหน้าอย่าง feat: กับ fix: สร้าง Changelog และเลขเวอร์ชัน
  3. ใช้ .gitignore และไม่ Commit ความลับ เพราะ Key ที่หลุดขึ้น Public repository ถูกสแกนและนำไปใช้ได้ภายในเวลาไม่นาน และการลบออกจากประวัติยุ่งยากกว่าการป้องกันมาก
  4. ย้อนกลับอย่างปลอดภัยด้วย restore, revert, reset และ reflog เพราะการแก้ความผิดพลาดโดยไม่ทำงานของตัวเองหรือของทีมหายคือสิ่งที่แยกมือใหม่ออกจากคนที่ทีมไว้ใจ
  5. แตก Branch, Merge และเลือกได้ว่าจะ Fast-forward หรือสร้าง Merge commit เพราะงานทุกชิ้นในบริษัททำบน Branch แยก แล้วรวมกลับเข้า main ผ่าน Pull Request
  6. แก้ Merge Conflict ได้เองอย่างใจเย็น เพราะ Conflict เกิดทุกครั้งที่หลายคนแก้ไฟล์เดียวกัน คนที่อ่านเครื่องหมาย <<<<<<<, ======= และ >>>>>>> ออกและตัดสินใจถูกจะไม่ทำงานของเพื่อนหาย
  7. ทำงานกับ Remote ผ่าน SSH ด้วย push, fetch, pull และ clone เพราะเป็นวิธีแลกเปลี่ยนงานกับทีมทุกวัน และการตั้ง SSH Key ให้ถูกต้องตั้งแต่แรกช่วยให้ไม่ต้องพิมพ์รหัสผ่านและปลอดภัยกว่า
  8. เปิด Pull Request ที่ดีและรีวิวโค้ดอย่างสุภาพ เพราะ PR คือจุดที่ทีมตรวจคุณภาพโค้ด และวิธีเขียน PR กับวิธีให้ความเห็นสะท้อนความเป็นมืออาชีพมากกว่าตัวโค้ดเสียอีก
  9. จัดประวัติให้สะอาดด้วย Rebase โดยไม่ละเมิดกฎทองของ Rebase เพราะประวัติที่อ่านง่ายช่วยให้หาบั๊กและรีวิวได้เร็ว แต่การ Rebase ประวัติที่แชร์แล้วทำให้งานของทีมพัง
  10. สืบสวนประวัติด้วย log, blame, bisect และ cherry-pick เพราะเมื่อระบบพัง คุณต้องหาให้ได้ว่า Commit ไหน ใคร และเพราะอะไร แล้วย้ายเฉพาะการแก้ไขที่ต้องการไปยัง Branch อื่น
  11. เขียน Workflow ของ GitHub Actions และ Deploy ด้วย GitHub Pages เพราะ CI/CD เป็นมาตรฐานของทุกทีม และการมี Workflow ที่ตรวจโค้ดอัตโนมัติใน Portfolio แสดงว่าคุณทำงานแบบมืออาชีพได้
  12. ดูแล Repository ให้พร้อมเป็น Portfolio ได้แก่ README ที่ดี, License, Tag และ Release, Branch protection และ Profile README เพราะผู้สัมภาษณ์มักเปิดดู GitHub ก่อนเรียกสัมภาษณ์ และตัดสินจากสิ่งที่เห็นในไม่กี่นาที

สิ่งที่ผู้สัมภาษณ์มักดูในโปรไฟล์ GitHub ของผู้สมัคร Junior: (1) Profile README ที่บอกว่าคุณเป็นใครและกำลังเรียนอะไร (2) Pinned repositories 4–6 ชิ้นที่มี README ดี มีลิงก์ Live demo และภาพหน้าจอ (3) ประวัติ Commit ที่สม่ำเสมอและข้อความ Commit ที่อ่านเข้าใจ (4) PR ที่มีคำอธิบายชัดเจน แม้จะเป็น PR ใน Repository ของตัวเอง (5) ไม่มีไฟล์ .env, Key หรือรหัสผ่านอยู่ในประวัติ
