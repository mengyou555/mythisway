12.1Learning Roadmap

ภาพรวมเส้นทาง

Backend คือส่วนของระบบที่ผู้ใช้มองไม่เห็น แต่ทำงานทุกครั้งที่มีคนกดปุ่มในแอป เช่น ตรวจรหัสผ่านตอน Login บันทึกคำสั่งซื้อลงฐานข้อมูล คำนวณยอดเงิน ส่งอีเมลยืนยัน และตอบข้อมูลกลับไปให้หน้าเว็บหรือแอปมือถือแสดงผล งานของ Backend Developer คือสร้างและดูแลระบบหลังบ้านนี้ให้ ถูกต้อง ปลอดภัย เร็ว และไม่ล่ม

หัวข้อนี้อยู่ลำดับที่ 11 ของเส้นทางที่แนะนำ (Phase 3) เพราะเป็นจุดที่รวมทุกอย่างที่คุณเรียนมาเข้าด้วยกัน ได้แก่ Linux และ Terminal จาก การเก็บโค้ดด้วย ภาษา Python จาก ฐานข้อมูลจาก ความรู้เรื่อง IP, Port, DNS และ HTTP จาก และการออกแบบ API จาก ทั้งหมดนี้จะกลายเป็น ระบบจริงที่ Deploy ได้ ไม่ใช่แค่ Script ที่รันบนเครื่องตัวเอง

เส้นทางนี้ใช้ Python + FastAPI เป็นภาษาและ Framework หลัก คู่กับ PostgreSQL 16 เป็นฐานข้อมูล Redis เป็น Cache และ Docker กับ GitHub Actions สำหรับการ Deploy และ CI แบ่งเป็น 13 ขั้นใน 3 ระดับ เริ่มจากเข้าใจว่า Request เดินทางอย่างไร ไปจนถึง Deploy API หลัง Reverse Proxy และวางแผนการ Scale ทุกขั้นฝึกบน Ubuntu 24.04 LTS ใน WSL2 และทุกแนวคิดจะเทียบให้เห็นว่าใน Node.js และ Go ทำอย่างไร เพราะหลักการของ Backend ใช้ได้กับทุกภาษา

ใช้เวลารวมประมาณ 109–142 ชั่วโมง ถ้าเรียนสัปดาห์ละ 7–9 ชั่วโมง จะจบในราว 4 เดือน (17 สัปดาห์) ผลงานสุดท้ายคือ Mini Project Production-ready REST API ระบบจัดการงาน (Task Management) ที่มีผู้ใช้ การ Login ด้วย JWT สิทธิ์ตาม Role ฐานข้อมูล PostgreSQL พร้อม Migration, Cache, Test, Docker และ CI ซึ่งเป็นผลงานที่ใส่ใน Portfolio เพื่อสมัครงาน Backend ได้จริง

  1. Beginner Step 1 · Backend ทำงานอย่างไร: Client-Server, HTTP และ Request Lifecycle
  2. Beginner Step 2 · FastAPI ตัวแรก: venv, Uvicorn, Routing, Path และ Query Parameters
  3. Beginner Step 3 · Pydantic Models, Validation, CRUD และ HTTP Status Code
  4. Beginner Step 4 · โครงสร้างโปรเจกต์, Dependency Injection, Configuration และ Error Handling
  5. Intermediate Step 5 · PostgreSQL 16 กับ SQLAlchemy 2: Model, Session และ Transaction
  6. Intermediate Step 6 · Relationships, ปัญหา N+1, Index, Pagination และ Alembic Migration
  7. Intermediate Step 7 · Authentication และ Authorization: Argon2, JWT และ Role
  8. Intermediate Step 8 · Automated Testing ด้วย pytest, TestClient และ Test Database
  9. Advanced Step 9 · Structured Logging, Middleware, Observability และ Background Tasks
  10. Advanced Step 10 · Caching ด้วย Redis: Cache-aside, TTL และ Invalidation
  11. Advanced Step 11 · API Security: OWASP API Top 10, CORS, Rate Limiting และ Secrets
  12. Advanced Step 12 · Docker, docker compose และ CI ด้วย GitHub Actions
  13. Advanced Step 13 · Deployment, Scaling และ Mini Project

เปรียบเทียบ

ให้นึกถึงร้านอาหาร Frontend คือหน้าร้านและเมนูที่ลูกค้าเห็น Backend คือครัวที่รับออร์เดอร์ ตรวจว่าสั่งได้จริง ปรุงอาหาร และส่งจานกลับไป Database คือห้องเก็บวัตถุดิบที่ต้องจดบัญชีให้ตรง Cache คือซอสที่เตรียมไว้ล่วงหน้าเพื่อเสิร์ฟได้เร็ว และ Authentication คือพนักงานที่ตรวจบัตรสมาชิกก่อนให้เข้าห้อง VIP ร้านที่ดีต้องทำอาหารอร่อย (ถูกต้อง) เสิร์ฟเร็ว (Performance) สะอาดปลอดภัย (Security) และรับลูกค้าได้มากขึ้นเมื่อร้านดัง (Scaling) ซึ่งคือสิ่งที่ Backend Developer ต้องดูแลทั้งหมด

Backend คืออะไร และทำงานอย่างไร

ก่อนเขียนโค้ดบรรทัดแรก ให้รู้จักคำศัพท์ที่จะเจอตลอดหัวข้อนี้ คำเหล่านี้เป็นคำถามสัมภาษณ์งาน Junior Backend ที่พบบ่อยมาก จึงควรอธิบายได้ด้วยคำพูดของตัวเอง

คำศัพท์ความหมายตัวอย่างในหัวข้อนี้
Clientโปรแกรมที่ส่ง Request ไปขอข้อมูลหรือสั่งงานBrowser, แอปมือถือ, curl และหน้า /docs ของ FastAPI
Serverโปรแกรมที่รอรับ Request ประมวลผล แล้วส่ง Response กลับ คำนี้หมายถึงได้ทั้งเครื่องคอมพิวเตอร์และโปรแกรมUvicorn ที่รันแอป FastAPI บน Port 8000
HTTP Request / Responseข้อความที่ Client กับ Server ส่งหากัน Request มี Method, Path, Headers และ Body ส่วน Response มี Status Code, Headers และ BodyGET /api/v1/tasks ได้ 200 OK พร้อม JSON รายการงาน
API และ EndpointAPI คือข้อตกลงว่าจะคุยกันอย่างไร Endpoint คือ Method + Path หนึ่งคู่ที่ทำงานหนึ่งอย่างPOST /api/v1/auth/login คือ Endpoint สำหรับ Login
Business Logicกฎของธุรกิจที่ระบบต้องบังคับใช้ ไม่ขึ้นกับว่าข้อมูลมาจากไหนผู้ใช้แก้ไขได้เฉพาะงานของตัวเอง ยกเว้น Admin
Databaseที่เก็บข้อมูลถาวรที่ยังอยู่แม้ปิด Server ใหม่ และรับประกันความถูกต้องด้วย TransactionPostgreSQL 16 เก็บตาราง users และ tasks
ORMObject-Relational Mapper แปลงแถวในตารางเป็น Object ของภาษาโปรแกรม ทำให้เขียน Query ด้วยโค้ด Python ได้SQLAlchemy 2 แปลงแถวในตาราง tasks เป็น Object Task
StatelessServer ไม่จำอะไรของ Client ไว้ในหน่วยความจำระหว่าง Request ทุก Request ต้องพกข้อมูลที่จำเป็นมาเอง เช่น Tokenทุก Request แนบ Authorization: Bearer <token> มาเอง ทำให้รัน Server กี่เครื่องก็ได้
Middlewareโค้ดที่ครอบทุก Request ทำงานก่อนและหลัง Handler เช่น จับเวลา เขียน Log หรือเพิ่ม HeaderMiddleware ที่ใส่ X-Request-ID และจับเวลาทุก Request
Cacheที่เก็บข้อมูลชั่วคราวซึ่งอ่านได้เร็วกว่าฐานข้อมูลมาก ใช้เก็บผลลัพธ์ที่คำนวณแพงและถูกอ่านบ่อยRedis เก็บสถิติงานของผู้ใช้ไว้ 60 วินาที
ASGI Serverโปรแกรมที่รับการเชื่อมต่อ HTTP จริงจาก Network แล้วส่งต่อให้แอป Python ตามมาตรฐาน ASGI (Asynchronous Server Gateway Interface)Uvicorn 0.54.0
Reverse ProxyServer ที่ยืนหน้าแอปของเรา รับ Request จาก Internet แล้วส่งต่อเข้าไป ทำหน้าที่ HTTPS, จำกัดขนาด Request และกระจายโหลดnginx 1.24 ส่งต่อไปที่ Uvicorn

Request Lifecycle: เส้นทางของ Request หนึ่งครั้ง

เมื่อผู้ใช้กดปุ่ม "ดูงานของฉัน" ในแอป Request หนึ่งครั้งจะเดินทางผ่านขั้นตอนต่อไปนี้ ทุกขั้นคือจุดที่อาจเกิดปัญหาได้ การรู้ลำดับนี้ทำให้คุณหาสาเหตุของ Bug ได้เร็ว

  1. Client สร้าง Request เช่น GET /api/v1/tasks?status=todo พร้อม Header Authorization
  2. DNS แปลงชื่อโดเมนเป็น IP Address (ทบทวนจาก )
  3. TCP และ TLS เปิดการเชื่อมต่อไปที่ Port 443 และเข้ารหัสด้วย HTTPS
  4. Reverse Proxy (nginx) รับ Request ถอดรหัส TLS ตรวจขนาด แล้วส่งต่อไปที่ Uvicorn บน 127.0.0.1:8000
  5. ASGI Server (Uvicorn) แปลงข้อมูลจาก Network เป็น Object ที่แอป Python เข้าใจ
  6. Middleware ทำงานก่อน เช่น สร้าง Request ID เริ่มจับเวลา และตรวจ CORS
  7. Routing FastAPI จับคู่ Method + Path กับฟังก์ชันที่รับผิดชอบ ถ้าไม่เจอจะตอบ 404
  8. Dependency Injection เตรียมของที่ฟังก์ชันต้องใช้ เช่น เปิด Database Session และตรวจ Token เพื่อหาผู้ใช้ปัจจุบัน ถ้า Token ผิดจะตอบ 401
  9. Validation Pydantic ตรวจ Path, Query และ Body ถ้าข้อมูลผิดรูปแบบจะตอบ 422 โดยไม่เข้าไปถึงโค้ดของเรา
  10. Handler, Service และ Repository ทำ Business Logic อ่านหรือเขียนฐานข้อมูลและ Cache
  11. Serialization แปลงผลลัพธ์เป็น JSON ตาม response_model และตัดฟิลด์ที่ไม่ควรส่งออก เช่น รหัสผ่านที่ Hash แล้ว
  12. Middleware ขากลับ เขียน Log บอกเวลาที่ใช้และ Status Code แล้วส่ง Response กลับผ่าน nginx ไปถึง Client

ทำไมใช้ Python + FastAPI และเทียบกับ Node.js และ Go

หลักสูตรนี้เลือก FastAPI เป็น Framework หลักด้วยเหตุผลต่อไปนี้

  • ต่อยอดจาก Python ที่เรียนมาแล้ว ใน คุณใช้ Type Hints, venv และ pytest มาแล้ว FastAPI ใช้ทั้งสามอย่างเป็นหัวใจของการทำงาน
  • Validation และเอกสาร API อัตโนมัติ แค่ประกาศ Type ของข้อมูล FastAPI ก็ตรวจข้อมูลขาเข้าและสร้างเอกสาร OpenAPI 3.1 ที่หน้า /docs ให้ทันที ซึ่งเชื่อมกับสิ่งที่เรียนใน
  • ใช้จริงในอุตสาหกรรม FastAPI เป็น Framework ยอดนิยมสำหรับ API ใหม่ในภาษา Python โดยเฉพาะระบบที่ต่อกับงาน AI และ Data ซึ่งเป็นหัวข้อถัดไปของเส้นทาง
  • รองรับทั้งโค้ดแบบ Sync และ Async มือใหม่เริ่มจาก def ธรรมดาได้ และขยับไปใช้ async def เมื่อเข้าใจ Event Loop แล้ว

ทุกแนวคิดของ Backend ใช้ได้กับทุกภาษา ตารางนี้เทียบเครื่องมือที่ทำหน้าที่เดียวกันใน 3 ภาษา ถ้าคุณเรียน มาแล้ว จะเห็นว่าเปลี่ยนแค่ชื่อเครื่องมือ ส่วนหลักคิดเหมือนเดิม และเมื่อไปเรียน ในหัวข้อถัดไป ก็ใช้ตารางนี้เป็นแผนที่ได้

Prerequisites: ต้องรู้อะไรมาก่อน

Backend เป็นหัวข้อแบบ Role ที่รวมหลายทักษะเข้าด้วยกัน ในลำดับที่แนะนำ คุณเรียนหัวข้อเหล่านี้จบแล้ว: และ ทักษะที่ต้องใช้จริงในหัวข้อนี้มีดังนี้

  • Python ระดับใช้งานได้ จาก : ฟังก์ชัน, Type Hints, Class และ dataclass, Exception, Decorator, Context Manager (with), Module และ Package, venv และ requirements.txt และเขียน Test ด้วย pytest ได้ ถ้าเลือกเส้นทาง JavaScript แทน ให้ใช้ และตารางเทียบด้านบน
  • SQL และ PostgreSQL จาก : CREATE TABLE พร้อม Constraint, SELECT + JOIN + GROUP BY, Index และ EXPLAIN, Transaction และ ACID, ใช้ sudo -u postgres psql สร้าง Role และ Database ได้ และรู้ว่าทำไม Parameterized Query ป้องกัน SQL Injection
  • API Design จาก : HTTP Method และ Status Code, การตั้งชื่อ Resource, Pagination, รูปแบบ Error แบบ RFC 9457 Problem Details, แนวคิด JWT และ OWASP API Security Top 10

  • Linux และ Git จาก และ : ใช้ Terminal คล่อง เข้าใจ Environment Variable และ Process ใช้ .gitignore สร้าง Branch, Pull Request และเขียน GitHub Actions Workflow พื้นฐานได้

STEP 1

Backend ทำงานอย่างไร: Client-Server, HTTP และ Request Lifecycle

1 สัปดาห์ · 4–6 ชม.
หัวข้อย่อย
  • หน้าที่ของ Frontend, Backend และ Database และงานที่ Backend รับผิดชอบ: Business Logic, เก็บข้อมูลถาวร, ยืนยันตัวตน, เชื่อมต่อระบบภายนอก เช่น Payment และอีเมล
  • Client-Server Model และโครงสร้างของ HTTP Request (Method, Path, Query String, Headers, Body) กับ HTTP Response (Status Line, Headers, Body) ทบทวนจาก
  • Request Lifecycle ทั้ง 12 ขั้นด้านบน ตั้งแต่ DNS, TCP/TLS, Reverse Proxy, ASGI Server, Middleware, Routing, Dependency, Validation, Handler ไปจนถึง Serialization
  • Stateless Server: ทำไม Server ไม่ควรเก็บสถานะของผู้ใช้ไว้ในตัวแปรของโปรแกรม และสถานะควรอยู่ที่ไหนแทน (Database, Cache, Token ที่ Client ถือ)
  • WSGI กับ ASGI ต่างกันอย่างไร, Uvicorn คืออะไร และความต่างของงานแบบ Blocking กับ Non-blocking I/O
  • สถาปัตยกรรมแบบ Monolith, Modular Monolith และ Microservices ข้อดีข้อเสีย และทำไมมือใหม่ควรเริ่มจาก Monolith ที่แบ่งชั้นดี
  • เครื่องมือดู Request จริง: curl -i (ดู Header ขากลับ), curl -v (ดูทั้งขาไปและขากลับ) และแท็บ Network ใน DevTools ของ Browser
ทำไมต้องเรียน
ปัญหาของ Backend ส่วนใหญ่ไม่ได้อยู่ในโค้ด Business Logic แต่อยู่ระหว่างทาง เช่น Port ไม่ตรง Header หาย Token ไม่ถูกส่ง หรือ Proxy ตัด Request ถ้ารู้ว่า Request ผ่านอะไรบ้าง คุณจะไล่หาจุดที่พังได้อย่างเป็นระบบแทนการเดา และหลัก Stateless คือสิ่งที่ทำให้ระบบ Scale ได้ในขั้นสุดท้าย
ลงมือทำ
  • เปิด Web Server ที่มากับ Python แล้วใช้ curl -i ขอไฟล์ที่มีอยู่และไฟล์ที่ไม่มี สังเกต Status Code และ Header ที่ต่างกัน
  • ดู Log ฝั่ง Server ว่าบันทึกอะไรเมื่อมี Request เข้ามา
  • วาด Request Lifecycle ด้วยมือหรือข้อความ ลงใน Learning Journal พร้อมเขียนว่าแต่ละขั้นอาจพังด้วยสาเหตุอะไร

1 สัปดาห์ · 7–9 ชม.
หัวข้อย่อย
  • สร้าง venv ใน ~/projects/backend-lab ติดตั้ง fastapi==0.148.0 และ uvicorn[standard]==0.54.0 แล้วบันทึกเวอร์ชันลง requirements.txt ด้วย python3 -m pip freeze

@app.get("/tasks")
def list_tasks(done: bool | None = None, limit: int = 10):
    # done และ limit คือ Query Parameter เช่น /tasks?done=false&limit=5
    result = TASKS
    if done is not None:
        result = [t for t in TASKS if t["done"] == done]
    return result[:limit]


@app.get("/tasks/{task_id}")
def get_task(task_id: int):
    # task_id คือ Path Parameter FastAPI แปลงเป็น int ให้อัตโนมัติ
    for task in TASKS:
        if task["id"] == task_id:
            return task
    raise HTTPException(status_code=404, detail="ไม่พบงานนี้")

  • ประกาศ Model แบบ SQLAlchemy 2: DeclarativeBase, Mapped[int], mapped_column(), String(200), unique=True, CheckConstraint, server_default=func.now() และ Mapped[str | None] สำหรับคอลัมน์ที่เป็น NULL ได้

  • SQLite กับ PostgreSQL ต่างกันอย่างไรในงาน Backend: ชนิดข้อมูล, การเขียนพร้อมกันหลาย Connection, Timezone และทำไม Production ต้องใช้ PostgreSQL แต่ Test ใช้ SQLite ได้

def transfer(src: str, dst: str, amount: int) -> None:
    # session.begin() จะ commit เมื่อจบบล็อก หรือ rollback ทั้งหมดถ้ามี Error
    with Session(engine) as db, db.begin():
        a = db.scalar(select(Account).where(Account.owner == src))
        b = db.scalar(select(Account).where(Account.owner == dst))
        b.balance += amount
        a.balance -= amount
        db.flush()  # ส่ง SQL ไปให้ฐานข้อมูลตรวจ Constraint ทันที

class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50))
    tasks: Mapped[list["Task"]] = relationship(back_populates="owner")


class Task(Base):
    __tablename__ = "tasks"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200))
    # index=True สร้าง Index ให้ Foreign Key เพื่อให้ค้นงานของแต่ละคนได้เร็ว
    owner_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)
    owner: Mapped[User] = relationship(back_populates="tasks")

  • โครงสร้าง JWT (Header.Payload.Signature), Claim มาตรฐาน sub (ต้องเป็น String), exp, iat, การเซ็นด้วย HS256 และ Secret ยาวอย่างน้อย 32 Byte ด้วย pyjwt==2.15.1 และการระบุ algorithms=["HS256"] ทุกครั้งที่ Decode
  • อายุของ Token: Access Token สั้น (15–30 นาที) จัดการ ExpiredSignatureError และแนวคิด Refresh Token, การ Logout และการเพิกถอน Token (Denylist ใน Redis)
  • OAuth2 Password Flow ของ FastAPI: OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login") และ OAuth2PasswordRequestForm (ต้องติดตั้ง python-multipart==0.0.32) ทำให้ปุ่ม Authorize ใน /docs ใช้งานได้
  • Dependency get_current_user ที่ Decode Token แล้วโหลดผู้ใช้จากฐานข้อมูล และ require_role("admin") แบบ Dependency Factory สำหรับ Endpoint ของผู้ดูแลระบบ
  • Ownership Check ป้องกัน BOLA (Broken Object Level Authorization) ซึ่งเป็นอันดับ 1 ของ OWASP API Security Top 10: ผู้ใช้เปิดงานของคนอื่นต้องได้ 404 เหมือนงานที่ไม่มีอยู่ เพื่อไม่บอกใบ้ว่ามีงานนั้นอยู่จริง
  • ข้อความ Error ตอน Login ต้องไม่บอกว่าผิดที่อีเมลหรือรหัสผ่าน (ตอบ "อีเมลหรือรหัสผ่านไม่ถูกต้อง" เสมอ) เพื่อไม่ให้ผู้โจมตีรู้ว่ามีอีเมลนี้ในระบบ

# auth_demo.py: Hash รหัสผ่านด้วย Argon2 และสร้าง/ตรวจ JWT
import os
from datetime import UTC, datetime, timedelta

import jwt
from pwdlib import PasswordHash

# อ่าน Secret จาก Environment Variable (ยาวอย่างน้อย 32 bytes) ห้ามเขียนค่าจริงลงในโค้ด
SECRET = os.environ.get("JWT_SECRET", "dev-only-secret-change-me-0123456789abcdef")
password_hash = PasswordHash.recommended()  # ใช้ Argon2 เป็นค่าเริ่มต้น

hashed = password_hash.hash("S0mchai-Pass!2026")
print("hash:", hashed[:30] + "...")
print("รหัสถูก:", password_hash.verify("S0mchai-Pass!2026", hashed))
print("รหัสผิด:", password_hash.verify("12345678", hashed))

now = datetime.now(UTC)
# sub ต้องเป็น string ตามมาตรฐาน JWT
token = jwt.encode({"sub": "1", "role": "member", "exp": now + timedelta(minutes=30)}, SECRET, algorithm="HS256")
print("token:", token[:36] + "...")
print("payload:", jwt.decode(token, SECRET, algorithms=["HS256"]))

expired = jwt.encode({"sub": "1", "exp": now - timedelta(seconds=1)}, SECRET, algorithm="HS256")
try:
    jwt.decode(expired, SECRET, algorithms=["HS256"])
except jwt.ExpiredSignatureError as e:
    print("Token หมดอายุ:", e)

Security

Payload ของ JWT แค่เข้ารหัสแบบ Base64URL ไม่ได้ถูกเข้ารหัสลับ ใครได้ Token ไปก็อ่านข้างในได้ จึงห้ามใส่ข้อมูลลับ เช่น รหัสผ่านหรือเลขบัตรประชาชน ลงใน Payload และถ้าใช้ Secret สั้นกว่า 32 Byte PyJWT 2.15.1 จะแสดงคำเตือน InsecureKeyLengthWarning: The HMAC key is 18 bytes long, which is below the minimum recommended length of 32 bytes for SHA256 ให้สุ่ม Secret ใหม่ด้วย python3 -c "import secrets; print(secrets.token_hex(32))" แล้วเก็บไว้ใน .env

STEP 9

Structured Logging, Middleware, Observability และ Background Tasks

1 สัปดาห์ · 7–9 ชม.
หัวข้อย่อย
  • Module logging ของ Python: Logger, Handler, Formatter, ระดับ DEBUG, INFO, WARNING, ERROR, CRITICAL และการตั้งระดับจาก LOG_LEVEL ใน Settings
  • Structured Logging: เขียน Log เป็น JSON หนึ่งบรรทัดต่อหนึ่งเหตุการณ์ ส่งออก stdout ตามหลัก 12-Factor และห้าม Log รหัสผ่าน, Token, Secret และข้อมูลส่วนบุคคลเกินจำเป็น (คำนึงถึง พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล หรือ PDPA)
  • HTTP Middleware ด้วย @app.middleware("http"): สร้างหรือรับ X-Request-ID, จับเวลาด้วย time.perf_counter(), เขียน Access Log แบบ JSON และส่ง Request ID กลับใน Response Header เพื่อไล่ปัญหาข้ามระบบ

  • Health Check: Liveness (โปรเซสยังไม่ตาย) กับ Readiness (พร้อมรับงาน เช่น ต่อฐานข้อมูลได้) และ /health ที่ตอบ 503 เมื่อฐานข้อมูลใช้ไม่ได้ เพื่อให้ Load Balancer หยุดส่งงานมาที่เครื่องนี้
  • BackgroundTasks ของ FastAPI: งานที่รันหลังส่ง Response แล้ว เช่น บันทึก Audit Log หรือส่งอีเมลต้อนรับ (จำลองด้วยการเขียน Log) และข้อจำกัดว่างานจะหายถ้า Process ล่ม
  • Task Queue สำหรับงานที่ต้องเชื่อถือได้: Producer, Broker (Redis หรือ RabbitMQ), Worker, การ Retry และ Idempotency ด้วยเครื่องมืออย่าง RQ 2.12.0 หรือ Celery 5.6.3 (เรียนเป็นแนวคิดในหัวข้อนี้)

Caching ด้วย Redis: Cache-aside, TTL และ Invalidation

4–5 วัน · 5–7 ชม.
หัวข้อย่อย
  • เมื่อไรควร Cache: ข้อมูลที่ถูกอ่านบ่อยแต่เปลี่ยนไม่บ่อย และคำนวณแพง เช่น สถิติหรือรายงาน และเมื่อไรไม่ควร: ข้อมูลที่ต้องถูกต้องทุกวินาที เช่น ยอดเงินคงเหลือ
  • ติดตั้ง Redis จาก apt (redis-server 7.0.15 บน Ubuntu 24.04) เปิดด้วย sudo service redis-server start และใช้ redis-cli: PING, SET ... EX, GET, TTL, DEL, KEYS (ใช้บนเครื่องตัวเองเท่านั้น), INCR และ EXPIRE
  • การตั้งชื่อ Key ให้เป็นระบบ เช่น stats:user:1 และชนิดข้อมูลพื้นฐานของ Redis: String, Hash, List, Set และ Sorted Set
  • รูปแบบ Cache-aside: อ่าน Cache ก่อน ถ้าไม่เจอ (Miss) ไปอ่านฐานข้อมูลแล้วเขียนลง Cache พร้อม TTL ถ้าเจอ (Hit) ตอบเลย และใส่ฟิลด์ cached ใน Response ช่วงพัฒนาเพื่อให้เห็นผล
  • Invalidation: ลบ Key ทันทีเมื่อข้อมูลต้นทางเปลี่ยน (สร้าง แก้ไข ลบงาน) และ TTL เป็นตาข่ายนิรภัยกรณีลืมลบ รวมถึงปัญหา Cache Stampede และข้อมูลเก่า (Stale Data)
  • redis==8.1.0 (redis-py): redis.Redis.from_url("redis://localhost:6379/0", decode_responses=True), เก็บค่าเป็น JSON และให้ระบบยังทำงานได้ (ช้าลง) ถ้า Redis ล่ม
  • ความต่างของ Server-side Cache (Redis) กับ HTTP Cache (Cache-Control, ETag) ที่เรียนใน และงานอื่นของ Redis เช่น ตัวนับ Rate Limit, Session Store และ Broker ของ Queue
ทำไมต้องเรียน
ฐานข้อมูลมักเป็นคอขวดแรกเมื่อผู้ใช้เพิ่มขึ้น Cache ที่ออกแบบดีลดงานของฐานข้อมูลได้มาก และทำให้ Response เร็วขึ้นจากหลักสิบมิลลิวินาทีเหลือไม่ถึงมิลลิวินาที แต่ Cache ที่ลบไม่ถูกจังหวะทำให้ผู้ใช้เห็นข้อมูลผิด ซึ่งแย่กว่าช้า คำกล่าวที่นักพัฒนารู้จักกันดีคือ ปัญหาที่ยากที่สุดในวิทยาการคอมพิวเตอร์ข้อหนึ่งคือ Cache Invalidation
ลงมือทำ
  • ติดตั้งและเปิด Redis แล้วทดลองคำสั่งใน redis-cli ตามตัวอย่าง
  • สร้าง GET /api/v1/tasks/stats ที่นับงานตามสถานะของผู้ใช้ และ Cache ผลไว้ที่ Key stats:user:{id} นาน 60 วินาที
  • ลบ Key นี้ทุกครั้งที่ผู้ใช้สร้าง แก้ไข หรือลบงาน แล้วเขียน Test ยืนยันด้วย fakeredis

API Security: OWASP API Top 10, CORS, Rate Limiting และ Secrets

1 สัปดาห์ · 7–9 ชม.
หัวข้อย่อย
  • OWASP API Security Top 10 ฉบับปี 2023 ครบ 10 ข้อและวิธีป้องกันใน FastAPI: API1 Broken Object Level Authorization (ตรวจเจ้าของทุกครั้ง), API2 Broken Authentication (Argon2, Token อายุสั้น, จำกัดการเดารหัส), API3 Broken Object Property Level Authorization (แยก Schema ขาเข้าขาออก), API4 Unrestricted Resource Consumption (จำกัด limit, ขนาด Body และ Rate Limit), API5 Broken Function Level Authorization (require_role), API6 Unrestricted Access to Sensitive Business Flows, API7 Server Side Request Forgery, API8 Security Misconfiguration, API9 Improper Inventory Management และ API10 Unsafe Consumption of APIs
  • Input Validation และ Mass Assignment: ใช้ model_config = ConfigDict(extra="forbid") ให้ปฏิเสธฟิลด์ที่ไม่รู้จัก และไม่เคยรับ role หรือ owner_id จาก Body
  • CORS ด้วย CORSMiddleware: ระบุ Origin ของ Frontend ให้ชัด เช่น http://localhost:5173 ห้ามใช้ "*" คู่กับ allow_credentials=True และเข้าใจว่า CORS ป้องกัน Browser ไม่ได้ป้องกัน curl
  • Rate Limiting: ตอบ 429 Too Many Requests พร้อม Header Retry-After สร้างเองแบบ Fixed Window ด้วย Redis INCR + EXPIRE หรือทำที่ nginx ด้วย limit_req โดยเฉพาะที่ Endpoint Login
  • จัดการ Secret: .env บนเครื่อง, GitHub Actions Secrets ใน CI, Secret Manager ของ Cloud บน Production, การหมุนเปลี่ยน Secret (Rotation) และ Secret Scanning ของ GitHub ที่เรียนใน
  • HTTPS ที่ Reverse Proxy, Security Headers เช่น Strict-Transport-Security และ X-Content-Type-Options: nosniff และการปิด /docs บน Production ถ้า API ไม่ได้เปิดให้คนนอกใช้

  • SQL Injection: ORM และ Bound Parameter ป้องกันให้ แต่ถ้าต่อ String เป็น SQL เองใน text() ช่องโหว่จะกลับมาทันที

  • คำสั่งประจำ: docker compose up -d --build, ps, logs -f api, exec, down และ down -v (ลบ Volume ซึ่งลบข้อมูลด้วย)
  • Continuous Integration ด้วย GitHub Actions: ไฟล์ .github/workflows/ci.yml, Trigger push และ pull_request, Job ที่ติดตั้ง Python 3.12 แล้วรัน pytest โดยใช้ SQLite และ fakeredis จึงไม่ต้องมีฐานข้อมูลจริงใน CI
  • แยก requirements.txt (ใช้ตอนรันจริง) กับ requirements-dev.txt (pytest, pytest-cov, fakeredis, httpx2, pip-audit) และตั้ง Branch Protection ให้ Merge ได้เมื่อ CI ผ่านเท่านั้น ตามที่เรียนใน

ลำดับการ Deploy ที่ปลอดภัยคือ (1) CI ผ่าน (2) สร้าง Image ใหม่ (3) รัน alembic upgrade head โดย Migration ต้องเข้ากันได้กับโค้ดเวอร์ชันเก่าที่ยังรันอยู่ เช่น เพิ่มคอลัมน์แบบ Nullable ก่อน ค่อยบังคับ NOT NULL ใน Release ถัดไป (4) เปิด Instance ใหม่และรอให้ Readiness Check ผ่าน (5) ค่อยปิด Instance เก่า ถ้ามีปัญหาให้ย้อนกลับไปใช้ Image เวอร์ชันก่อนหน้าได้ทันที

ก่อนจบหัวข้อนี้ คุณต้องทำสิ่งเหล่านี้ได้: (1) curl -i http://localhost/health ได้ 200 พร้อม Header Server: nginx (2) ปิด Uvicorn แล้ว nginx ตอบ 502 Bad Gateway และอธิบายได้ว่าทำไม (3) อธิบายด้วยแผนภาพได้ว่าระบบของคุณจะรับผู้ใช้เพิ่ม 10 เท่าอย่างไร โดยพูดถึง Load Balancer, Stateless Server, Redis, Read Replica และ Queue (4) อธิบายความต่างของ Liveness กับ Readiness Check ได้ (5) Repository ของ TaskFlow API บน GitHub มี README, CI สีเขียว, Dockerfile, compose.yaml และ Test ครบตามส่วนที่ 4

Must-know Skills

ทักษะต่อไปนี้คือสิ่งที่ผู้สัมภาษณ์งาน Backend คาดหวังจาก Junior และเป็นฐานของงานระดับ Mid เรียงจากพื้นฐานไปขั้นสูง ถ้าคุณอธิบายและทำทุกข้อได้ด้วยโปรเจกต์ของตัวเอง คุณพร้อมสมัครงานแล้ว

  1. อธิบาย Request Lifecycle และ HTTP ได้ครบ เพราะทุกปัญหาของ Backend ตั้งแต่ CORS, 401, 502 จนถึง Timeout จะแก้ได้เร็วเมื่อคุณรู้ว่า Request ผ่าน DNS, TCP, TLS, Reverse Proxy, Middleware, Router และฐานข้อมูลตามลำดับอย่างไร
  2. ออกแบบ REST API ด้วย Method, Path และ Status Code ที่ถูกต้อง เพราะ API คือสัญญาระหว่าง Backend กับ Frontend, Mobile และบริการอื่น สัญญาที่สม่ำเสมอทำให้ทีมอื่นใช้ได้โดยไม่ต้องถามคุณทุกครั้ง
  3. Validate ข้อมูลขาเข้าและควบคุมข้อมูลขาออกด้วย Pydantic Schema เพราะข้อมูลจาก Client เชื่อไม่ได้เสมอ และการแยก Schema ขาเข้ากับขาออกป้องกันทั้ง Mass Assignment และการเผลอส่ง password_hash ออกไป
  4. จัดโครงสร้างโค้ดเป็นชั้น Router, Service และ Repository พร้อม Dependency Injection เพราะโค้ดที่แยกหน้าที่ชัดเจนแก้ไขง่าย เขียน Test ง่าย และคนใหม่ในทีมอ่านเข้าใจได้เร็ว
  5. ใช้ SQL และ ORM อย่างเข้าใจ: Transaction, Relationship, Index และ N+1 เพราะฐานข้อมูลคือหัวใจของระบบและเป็นคอขวดแรกเกือบทุกครั้ง Query ที่เขียนพลาดเพียงจุดเดียวทำให้ทั้งระบบช้าหรือข้อมูลผิดได้
  6. เปลี่ยนโครงสร้างฐานข้อมูลอย่างปลอดภัยด้วย Migration เพราะฐานข้อมูล Production มีข้อมูลจริงที่ลบทิ้งไม่ได้ ทุกการเปลี่ยนแปลงต้องทำซ้ำได้ ย้อนกลับได้ และผ่านการ Review เหมือนโค้ด
  7. ทำ Authentication และ Authorization ให้ถูกต้อง เพราะการ Hash รหัสผ่านด้วย Argon2, JWT อายุสั้น และการตรวจสิทธิ์ทั้งระดับ Role และระดับเจ้าของข้อมูล คือสิ่งที่ป้องกันช่องโหว่อันดับต้นของ OWASP API Top 10
  8. เขียน Automated Test ด้วย pytest, Fixture และ Test Database เพราะ Test คือสิ่งที่ทำให้คุณแก้โค้ดได้อย่างมั่นใจ และ CI ที่ไม่มี Test ก็ไม่ได้ป้องกันอะไรเลย
  9. จัดการ Configuration, Secret และ Error Response อย่างเป็นระบบ เพราะ Secret ที่หลุดขึ้น GitHub ถูก Bot เก็บไปใช้ภายในไม่กี่นาที และ Error Response ที่มีรูปแบบเดียวกันทำให้ Client จัดการข้อผิดพลาดได้ถูกต้อง
  10. ทำ Structured Logging, Health Check และอ่าน Log เพื่อหาสาเหตุปัญหา เพราะใน Production คุณ Debug ด้วย Breakpoint ไม่ได้ Log ที่มี request_id คือเครื่องมือเดียวที่จะบอกได้ว่าเกิดอะไรขึ้นตอนตีสอง
  11. ใช้ Redis ทำ Cache แบบ Cache-aside พร้อม TTL และ Invalidation เพราะ Cache คือวิธีที่คุ้มที่สุดในการทำให้ระบบเร็วขึ้น แต่ต้องลบให้ถูกจังหวะ ไม่เช่นนั้นผู้ใช้จะเห็นข้อมูลเก่า
  12. บรรจุแอปด้วย Docker และตั้ง CI บน GitHub Actions เพราะบริษัทส่วนใหญ่ Deploy เป็น Container และตรวจโค้ดทุก Pull Request ด้วย CI ผู้ที่ทำสองอย่างนี้ได้เข้าทีมแล้วทำงานได้ทันที
  13. อธิบายแนวคิด Scaling และ System Design พื้นฐาน เพราะการรู้ว่า Load Balancer, Stateless Server, Cache, Queue และ Read Replica แก้ปัญหาอะไร คือสิ่งที่ใช้ตัดสินระดับ Mid ในการสัมภาษณ์
Best Practice

เงินเดือนของสาย Backend แตกต่างกันมากตามประสบการณ์ ขนาดและประเภทบริษัท (Startup, ธนาคาร, บริษัทต่างชาติ) ภาษาและ Stack ที่ใช้ ทักษะภาษาอังกฤษ และสถานที่ทำงานหรือการทำงานแบบ Remote หลักสูตรนี้จึงไม่ระบุตัวเลข ให้หาข้อมูลล่าสุดด้วยตัวเองดังนี้

  • ค้นหาตำแหน่ง "Backend Developer", "Python Developer" และ "Software Engineer" บน JobsDB และ LinkedIn Jobs แล้วจดช่วงเงินเดือนจากประกาศที่ระบุตัวเลข อย่างน้อย 20 ประกาศ แยกตามระดับประสบการณ์
  • อ่านคุณสมบัติในประกาศเหล่านั้นแล้วเทียบกับรายการ Must-know Skills ข้างบน เพื่อดูว่าตลาดต้องการอะไรเพิ่ม เช่น Cloud ยี่ห้อใด หรือ Message Queue ตัวใด
  • ดูรายงานเงินเดือนประจำปีที่บริษัทจัดหางานด้าน IT เผยแพร่ และถามคนที่ทำงานในตำแหน่งนั้นจริงผ่าน LinkedIn หรือชุมชนนักพัฒนาไทย
