17.2Core Concept & Quick Guide

ส่วนนี้คือคู่มือใช้งานจริงของ Git และ GitHub แบบ W3Schools มีทั้งหมด 12 แนวคิด เรียงจากง่ายไปยาก แต่ละแนวคิดมีคำอธิบายสั้นๆ ตัวอย่างที่พิมพ์ตามได้ทั้งชุด ผลลัพธ์ที่ได้จากการรันจริง ตารางอธิบายทีละบรรทัด ข้อผิดพลาดที่มือใหม่เจอบ่อยพร้อมข้อความ Error จริง และแบบฝึกให้ลองเอง แนวคิดที่ 1–4 ตรงกับ Step 1–5 ในส่วนที่ 1 ของหัวข้อนี้ แนวคิดที่ 5–8 ตรงกับ Step 6–9 และแนวคิดที่ 9–12 ตรงกับ Step 10–13

ทุกตัวอย่างพิมพ์ใน Terminal ของ Ubuntu บน WSL2 ตามที่เตรียมไว้ในหัวข้อ ตัวอย่างทั้งหมดอยู่ใน ~/projects/git-lab/ แยกโฟลเดอร์ตามแนวคิด (c01-first-repo ถึง c12-site) และทุกชุดเริ่มด้วย rm -rf โฟลเดอร์ของตัวเอง เพื่อให้รันซ้ำกี่ครั้งก็ได้ผลเหมือนเดิม ส่วนที่ต้องใช้ GitHub จริง เช่น Pull Request หรือ GitHub Actions เราจะจำลองด้วย Bare repository ในเครื่องก่อน เพื่อให้เห็นผลลัพธ์จริงของ push, fetch และ pull แล้วค่อยอธิบายว่าบน GitHub จะเห็นอะไร

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Version Control คือระบบที่บันทึกประวัติการเปลี่ยนแปลงของไฟล์ทุกครั้งที่เราสั่ง ทำให้ย้อนดูได้ว่าใครแก้อะไร เมื่อไร และเพราะอะไร และย้อนกลับไปเวอร์ชันเก่าได้โดยไม่ต้องตั้งชื่อไฟล์แบบ report_final_v3_จริงๆ.docx อีกต่อไป Git คือโปรแกรม Version Control ที่ทำงานในเครื่องของเรา ส่วน GitHub คือเว็บไซต์ที่รับฝาก Repository ของ Git ไว้บน Internet และเพิ่มเครื่องมือทำงานเป็นทีม เช่น Pull Request, Issues และ Actions เปรียบง่ายๆ คือ Git ใช้ได้โดยไม่มี GitHub แต่ GitHub ทำงานบน Git เสมอ

Repository (เรียกสั้นๆ ว่า Repo) คือโฟลเดอร์โปรเจกต์ที่ Git ดูแล สร้างได้ด้วย git init ซึ่งจะสร้างโฟลเดอร์ซ่อนชื่อ .git ไว้ข้างใน ประวัติทั้งหมดเก็บอยู่ในโฟลเดอร์นี้ ถ้าลบ .git ทิ้ง ไฟล์งานยังอยู่ แต่ประวัติหายหมด ภายในเครื่องของเรา การเปลี่ยนแปลงจะเดินทางผ่าน 3 พื้นที่ ดังแผนภาพนี้ (พื้นที่ที่ 4 คือ Remote จะเรียนในแนวคิดที่ 7)

  [ 1. Working Tree ]        ไฟล์จริงในโฟลเดอร์ ที่คุณเปิดแก้ใน VS Code หรือ nano
          |                         ^
          | git add <ไฟล์>          | git restore <ไฟล์>  (แนวคิดที่ 4)
          v                         |
  [ 2. Staging Area ]        รายการที่เลือกไว้แล้วว่าจะเข้า Commit ถัดไป (ไฟล์ .git/index)
          |                         ^
          | git commit -m "..."     | git restore --staged <ไฟล์>  (แนวคิดที่ 4)
          v                         |
  [ 3. Local Repository ]    ประวัติทุก Commit ในโฟลเดอร์ .git   HEAD = Commit ล่าสุดที่เรายืนอยู่

ไฟล์แต่ละไฟล์จึงมีสถานะได้ 4 แบบ ซึ่งดูได้จาก git status

  • Untracked: ไฟล์ใหม่ที่ Git ยังไม่เคยรู้จัก git status -s แสดงเป็น ??
  • Modified: ไฟล์ที่ Git รู้จักแล้ว และถูกแก้หลัง Commit ล่าสุด แสดงเป็น M (มีช่องว่างนำหน้า หมายถึงแก้ใน Working Tree แต่ยังไม่ add)
  • Staged: ไฟล์ที่ git add แล้ว รอเข้า Commit แสดงเป็น A (ไฟล์ใหม่) หรือ M (ไฟล์เดิมที่แก้) ในคอลัมน์ซ้าย ถ้าเห็น MM แปลว่า add ไปแล้วรอบหนึ่ง แล้วแก้ต่ออีก
  • Committed: ไฟล์ที่ตรงกับ Commit ล่าสุดทุกตัวอักษร git status -s จะไม่แสดงไฟล์นั้นเลย

Commit คือภาพถ่าย (Snapshot) ของทุกไฟล์ที่ Staged ณ เวลานั้น พร้อมข้อมูลกำกับ คือ ชื่อและอีเมลผู้เขียน (Author), วันเวลา, ข้อความอธิบาย (Message), Commit ก่อนหน้า (Parent) และรหัสประจำตัวยาว 40 ตัวอักษรที่คำนวณด้วย SHA-1 จากเนื้อหาทั้งหมด ถ้าเนื้อหาเปลี่ยนแม้ตัวอักษรเดียว รหัสก็เปลี่ยน ใช้แนวคิดนี้ทุกครั้งที่เริ่มโปรเจกต์ใหม่ และทุกครั้งที่งานเสร็จเป็นชิ้นที่มีความหมาย เช่น เพิ่มหน้าใหม่เสร็จ หรือแก้บั๊กหนึ่งตัวเสร็จ

เปรียบเทียบ

การถ่ายรูปหมู่ Working Tree คือทุกคนที่อยู่ในงาน git add คือการเรียกคนที่จะถ่ายมายืนหน้ากล้อง (Staging Area) ใครยังไม่ถูกเรียกก็จะไม่อยู่ในรูป git commit คือการกดชัตเตอร์ รูปที่ได้ถูกเก็บลงอัลบั้ม (Local Repository) พร้อมเขียนใต้รูปว่าถ่ายเมื่อไร ใครถ่าย และเป็นงานอะไร รูปในอัลบั้มไม่เปลี่ยนตามคนที่ขยับทีหลัง ถ้าอยากได้ภาพใหม่ต้องถ่ายใหม่

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

ประวัติที่บันทึกไว้จะมีค่าก็ต่อเมื่อเราอ่านมันได้ Git มีคำสั่งอ่านประวัติหลัก 3 ตัว คือ git log แสดงรายการ Commit ย้อนจากล่าสุดไปเก่าสุด, git diff แสดงว่าบรรทัดไหนเปลี่ยนไปอย่างไร และ git show แสดงรายละเอียดของ Commit เดียวหรือเนื้อหาไฟล์ ณ Commit ใดก็ได้ ใช้ทุกครั้งก่อน Commit (ตรวจว่าจะบันทึกอะไร), ตอนรีวิวงานเพื่อน และตอนหาว่าบั๊กเริ่มเข้ามาเมื่อไร

คำสั่งสำคัญที่ควรรู้มีดังนี้

  • git log --oneline หนึ่ง Commit ต่อหนึ่งบรรทัด, --graph --all วาดเส้นของทุก Branch, -n 3 เฉพาะ 3 Commit ล่าสุด, --stat บอกจำนวนบรรทัดที่เปลี่ยนต่อไฟล์, -p แสดง diff เต็มของแต่ละ Commit
  • กรองประวัติ: --author="Somchai" เฉพาะผู้เขียนคนนี้, --since="1 week ago" เฉพาะช่วงเวลา และ -- menu.md เฉพาะ Commit ที่แตะไฟล์นี้
  • git diff เทียบ Working Tree กับ Staging Area (สิ่งที่แก้แต่ยังไม่ add), git diff --staged เทียบ Staging Area กับ Commit ล่าสุด (สิ่งที่กำลังจะ Commit) และ git diff HEAD~2 HEAD เทียบสอง Commit
  • การอ้าง Commit: HEAD คือ Commit ปัจจุบัน, HEAD~1 คือ Commit ก่อนหน้า 1 ขั้น, HEAD~2 ก่อนหน้า 2 ขั้น หรือใช้รหัสย่อ เช่น f8ef866
  • git show <commit> ดูรายละเอียด Commit และ git show HEAD~2:menu.md ดูเนื้อหาไฟล์ ณ Commit นั้นโดยไม่แตะไฟล์ปัจจุบัน
เปรียบเทียบ

git log คือสารบัญของสมุดบันทึกประจำวัน บอกว่าแต่ละวันเขียนเรื่องอะไร git show คือการเปิดอ่านหน้าวันใดวันหนึ่งแบบเต็มๆ ส่วน git diff คือการวางเอกสารสองฉบับเทียบกัน แล้วใช้ปากกาแดงขีดฆ่าส่วนที่ถูกลบ (-) และปากกาเขียวเขียนส่วนที่เพิ่ม (+)

ประวัติ Git ที่ดีอ่านแล้วเข้าใจได้ทันทีว่าโปรเจกต์เปลี่ยนไปอย่างไร หลักการของ Commit ที่ดีมี 3 ข้อ (1) หนึ่ง Commit หนึ่งเรื่อง เช่น แก้บั๊กกับเพิ่มฟีเจอร์ให้แยกกัน (2) หัวเรื่อง (Subject) สั้น ไม่เกิน 50–72 ตัวอักษร เขียนแบบคำสั่ง เช่น add ไม่ใช่ added (3) ถ้าเหตุผลไม่ชัด ให้เขียน เนื้อความ (Body) อธิบาย "ทำไม" โดยเว้น 1 บรรทัดหลังหัวเรื่อง เวลาแก้หลายเรื่องในไฟล์เดียว ใช้ git add -p เลือกเข้า Staging ทีละส่วน (Hunk) ได้

ทีมส่วนใหญ่ใช้รูปแบบ Conventional Commits 1.0.0 คือ type(scope): คำอธิบาย โดย type ที่ใช้บ่อยมีดังนี้: feat ฟีเจอร์ใหม่, fix แก้บั๊ก, docs เอกสาร, style จัดรูปแบบโค้ดโดยไม่เปลี่ยนการทำงาน, refactor ปรับโครงสร้างโค้ด, test เพิ่มหรือแก้เทสต์, chore งานดูแลทั่วไป, ci แก้ระบบ CI ส่วน scope ในวงเล็บระบุส่วนที่แก้ เช่น feat(menu): add mocha และถ้าการเปลี่ยนแปลงทำให้ของเดิมใช้ไม่ได้ (Breaking change) ให้ใส่ ! เช่น feat(api)!: remove v1 endpoint รูปแบบนี้ทำให้เครื่องมือสร้าง Changelog และกำหนดเลขเวอร์ชันได้อัตโนมัติ

ส่วน .gitignore คือไฟล์ที่บอก Git ว่าไฟล์ไหน "ไม่ต้องสนใจ" ได้แก่ ไฟล์ที่โปรแกรมสร้างเอง (__pycache__/, node_modules/, *.log), ไฟล์ของระบบปฏิบัติการ (.DS_Store ของ macOS, Thumbs.db ของ Windows) และที่สำคัญที่สุดคือไฟล์ความลับ .env ที่เก็บรหัสผ่านหรือ API key ซึ่งห้าม Commit เด็ดขาด เราจะ Commit ไฟล์ .env.example ที่มีแต่ชื่อตัวแปรแต่ไม่มีค่าแทน เพื่อให้คนอื่นรู้ว่าต้องตั้งค่าอะไรบ้าง สร้าง .gitignore ตั้งแต่ Commit แรกของทุกโปรเจกต์

เปรียบเทียบ

ข้อความ Commit คือป้ายติดกล่องตอนย้ายบ้าน ป้าย "ของ" ไม่ช่วยอะไร แต่ป้าย "ครัว: จานชามแตกง่าย" บอกทั้งหมวดและเนื้อหา Conventional Commits คือการตกลงกันทั้งบ้านว่าจะเขียนป้ายรูปแบบเดียวกัน ส่วน .gitignore คือรายการของที่ไม่ต้องขนไป เช่น ถุงขยะและกล่องเปล่า ส่วน .env คือกุญแจบ้านที่ต้องพกติดตัว ห้ามใส่กล่องไปกับรถขนของ

ตอนนี้ git add . ได้อย่างปลอดภัย เพราะไฟล์ที่ไม่ควรขึ้น Git ถูกกันไว้แล้ว ต่อจากนั้นจำลองความผิดพลาดที่เจอบ่อย คือ Commit ไฟล์ secret.txt ไปก่อน แล้วค่อยเพิ่มชื่อลง .gitignore (ไฟล์นี้มีค่าปลอม ไม่ใช่รหัสจริง)

# Commit ชุดแรกที่มี .gitignore และ .env.example
git add .
git commit -m "chore: add .gitignore and .env.example"

# จำลองว่าเผลอ Commit secret.txt ไปแล้ว

git commit -m "feat: add config"

# เพิ่มชื่อลง .gitignore ทีหลัง แล้วลองแก้ไฟล์
echo "secret.txt" >> .gitignore
echo "password=changed" > secret.txt
git status -s                 # secret.txt ยังขึ้น M เพราะถูกติดตามอยู่แล้ว

# เลิกติดตามไฟล์ แต่ไม่ลบไฟล์ออกจากเครื่อง

Best Practice
  • สร้าง .gitignore เป็นไฟล์แรกของทุกโปรเจกต์ เริ่มจากแม่แบบของภาษาที่ใช้ ที่ github.com/github/gitignore
  • ตั้ง Global ignore สำหรับไฟล์ของเครื่องตัวเอง เช่น .DS_Store หรือไฟล์ตั้งค่า Editor: สร้าง ~/.gitignore_global แล้วรัน git config --global core.excludesFile ~/.gitignore_global
  • Commit .env.example ที่มีชื่อตัวแปรครบทุกตัวแต่ไม่มีค่า และเขียนใน README ว่าให้คัดลอกเป็น .env ด้วย cp .env.example .env
  • ใช้ git add -p เมื่อไฟล์เดียวมีการแก้หลายเรื่อง เพื่อแยกเป็นหลาย Commit ที่อ่านง่าย

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

ทุกคนทำพลาด เช่น แก้ไฟล์จนพัง add ไฟล์ผิด พิมพ์ข้อความ Commit ผิด หรือ Commit โค้ดที่มีบั๊กขึ้นไปแล้ว Git มีคำสั่งย้อนกลับหลายตัว และแต่ละตัวเหมาะกับสถานการณ์ต่างกัน หลักการเลือกคือดูว่า "ความผิดพลาดอยู่ในพื้นที่ไหน" และ "แชร์ให้คนอื่นไปแล้วหรือยัง" ใช้ตารางนี้ตัดสินใจ

สถานการณ์คำสั่งผลลัพธ์ความเสี่ยง
แก้ไฟล์แล้วพัง ยังไม่ได้ addgit restore <ไฟล์>ไฟล์กลับไปเหมือน Commit ล่าสุด (หรือเหมือน Staging ถ้า add ไว้)สูง: การแก้ที่ยังไม่เคย Commit หายถาวร กู้คืนไม่ได้
add ไฟล์ผิดเข้า Staginggit restore --staged <ไฟล์>เอาออกจาก Staging ไฟล์จริงไม่เปลี่ยนไม่มี
ข้อความ Commit ล่าสุดผิด หรือลืม add ไฟล์ และยังไม่ Pushgit commit --amendแทนที่ Commit ล่าสุดด้วย Commit ใหม่ (รหัสเปลี่ยน)ห้ามใช้กับ Commit ที่ Push แล้ว
Commit ที่มีปัญหาถูก Push และแชร์ไปแล้วgit revert <commit>สร้าง Commit ใหม่ที่กลับด้านการเปลี่ยนแปลงนั้น ประวัติเดิมยังอยู่ครบต่ำ: ปลอดภัยที่สุดสำหรับงานทีม
อยากได้ไฟล์เดียวจาก Commit เก่าgit restore --source=HEAD~1 <ไฟล์>เขียนทับไฟล์ใน Working Tree ด้วยเวอร์ชันเก่ากลาง: ทับการแก้ที่ยังไม่ Commit ของไฟล์นั้น

บทเรียนเก่าบนอินเทอร์เน็ตจะใช้ git checkout -- <ไฟล์> แทน git restore <ไฟล์> และ git reset HEAD <ไฟล์> แทน git restore --staged <ไฟล์> ซึ่งยังใช้ได้ แต่คำสั่ง restore ชัดเจนกว่าและเป็นสิ่งที่ git status แนะนำในปัจจุบัน ส่วน git reset แบบย้าย Branch จะเรียนในแนวคิดที่ 10

เปรียบเทียบ

นึกถึงการเขียนรายงานส่งอาจารย์ git restore คือขยำกระดาษร่างทิ้งแล้วเริ่มจากฉบับที่ถ่ายเอกสารเก็บไว้ (ร่างที่ขยำทิ้งเอาคืนไม่ได้) --amend คือแก้คำผิดบนหน้าปกก่อนส่ง ซึ่งทำได้เพราะยังไม่มีใครเห็น ส่วน git revert คือรายงานที่ส่งไปแล้ว จะดึงกลับมาแก้ไม่ได้ จึงต้องส่ง "ใบแก้คำผิด" ตามไปอีกแผ่น ทุกคนเห็นทั้งฉบับเดิมและใบแก้

Best Practice
  • ก่อนรัน git restore <ไฟล์> ให้ดู git diff <ไฟล์> ก่อนเสมอ เพื่อยืนยันว่าสิ่งที่จะทิ้งไม่มีอะไรสำคัญ
  • กฎของทีม: Commit ที่ Push แล้วให้แก้ด้วย revert เท่านั้น --amend ใช้กับ Commit ในเครื่องที่ยังไม่มีใครเห็น
  • เมื่อ revert ให้เขียนเหตุผลในเนื้อความ Commit (ไม่ใส่ --no-edit แล้วเขียนใน nano) เช่น "แบนเนอร์ทำให้หน้าเว็บกระพริบบนมือถือ"
  • ถ้าไม่แน่ใจว่าจะใช้คำสั่งไหน ให้อ่านคำแนะนำในวงเล็บของ git status ก่อน เพราะ Git บอกคำสั่งที่เหมาะกับสถานะปัจจุบันไว้แล้ว

Branch, Merge (Fast-forward กับ Merge commit) และ Stash

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Branch คือป้ายชื่อที่ชี้ไปยัง Commit หนึ่ง และเลื่อนตามไปเองทุกครั้งที่เรา Commit บน Branch นั้น ส่วน HEAD คือป้ายที่บอกว่าตอนนี้เรายืนอยู่บน Branch ไหน การสร้าง Branch จึงเร็วมากเพราะ Git ไม่ได้คัดลอกไฟล์ แค่สร้างป้ายใหม่ ใช้ Branch ทุกครั้งที่เริ่มงานชิ้นใหม่ เพื่อให้ main อยู่ในสภาพใช้งานได้เสมอ และทดลองได้โดยไม่กระทบงานหลัก ทีมส่วนใหญ่ตั้งชื่อตามประเภทงาน เช่น feature/contact, fix/broken-link, docs/readme

เมื่องานบน Branch เสร็จ เราจะรวมกลับด้วย git merge ซึ่งเกิดได้ 2 แบบ

  • Fast-forward: ถ้า main ไม่มี Commit ใหม่ตั้งแต่แยก Branch ออกไป Git แค่เลื่อนป้าย main ไปข้างหน้า ไม่มี Commit ใหม่เกิดขึ้น ประวัติเป็นเส้นตรง
  • Merge commit (3-way merge): ถ้าทั้งสองฝั่งมี Commit ใหม่ Git จะสร้าง Commit พิเศษที่มี Parent 2 ตัว รวมงานของทั้งสองฝั่ง โดยใช้กลยุทธ์ชื่อ ort ซึ่งเป็นค่าเริ่มต้นของ Git รุ่นปัจจุบัน ถ้าอยากได้ Merge commit เสมอแม้ Fast-forward ได้ ให้ใช้ git merge --no-ff

Stash คือที่พักงานชั่วคราว ใช้เมื่อกำลังแก้งานค้างอยู่แล้วต้องสลับ Branch ด่วน เช่น ต้องไปแก้บั๊กบน main คำสั่ง git stash push -m "ข้อความ" เก็บการแก้ทั้งหมดออกไปพัก ทำให้ Working Tree สะอาด จากนั้น git stash pop นำกลับมาและลบออกจากรายการ ส่วน git stash apply นำกลับมาแต่ยังเก็บไว้ในรายการ ถ้ามีไฟล์ใหม่ที่ยังไม่ add ต้องใช้ git stash -u ถ้างานค้างนานกว่าหนึ่งวัน ให้ Commit เป็น wip บน Branch ของตัวเองดีกว่า เพราะ Stash ลืมง่ายและไม่ขึ้น Remote

เปรียบเทียบ

Branch เหมือนที่คั่นหนังสือ หนังสือ (ประวัติ) มีเล่มเดียว แต่เราวางที่คั่นได้หลายอัน แต่ละอันระบุว่าอ่านถึงหน้าไหน การ Merge แบบ Fast-forward คือการเลื่อนที่คั่น main ไปหน้าที่ที่คั่น feature อยู่ ส่วน Merge commit คือการเขียนหน้าสรุปใหม่ที่รวมสองเส้นเรื่องเข้าด้วยกัน Stash คือการหยิบงานบนโต๊ะใส่ลิ้นชักชั่วคราวเพื่อเคลียร์โต๊ะไปทำงานด่วน

แก้ Merge Conflict ทีละขั้น

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Merge Conflict เกิดเมื่อสอง Branch แก้ บรรทัดเดียวกัน ของไฟล์เดียวกันไปคนละแบบ (หรือฝั่งหนึ่งลบไฟล์ อีกฝั่งแก้ไฟล์นั้น) Git ไม่เดาแทนเราว่าแบบไหนถูก จึงหยุด Merge ไว้กลางทาง ใส่เครื่องหมายลงในไฟล์ และรอให้เราตัดสินใจ Conflict ไม่ใช่ความผิดพลาดของใคร เป็นเรื่องปกติของการทำงานเป็นทีม และเกิดได้ทั้งตอน merge, pull, rebase, revert และ cherry-pick

ขั้นตอนแก้มีลำดับตายตัว: (1) อ่าน git status หาไฟล์ที่ขึ้น both modified (2) เปิดไฟล์ หาเครื่องหมาย 3 ชุด <<<<<<< HEAD (ฝั่งของเรา), ======= (เส้นแบ่ง) และ >>>>>>> ชื่อbranch (ฝั่งที่รวมเข้ามา) (3) แก้ให้เหลือเนื้อหาที่ถูกต้อง จะเลือกฝั่งเดียว เก็บทั้งสอง หรือเขียนใหม่ก็ได้ แล้วลบเครื่องหมายทั้งหมด (4) git add ไฟล์เพื่อบอกว่าแก้แล้ว (5) git commit (หรือ git merge --continue) ถ้าสับสนจนอยากเริ่มใหม่ ใช้ git merge --abort กลับไปสถานะก่อน Merge ได้เสมอ

ใน VS Code ที่เปิดจาก WSL ด้วย code . ไฟล์ที่มี Conflict จะแสดงปุ่มเหนือแต่ละจุด ได้แก่ Accept Current Change (ฝั่ง HEAD), Accept Incoming Change (ฝั่งที่รวมเข้ามา), Accept Both Changes และปุ่ม Resolve in Merge Editor ที่เปิดหน้าจอ 3 ช่องให้เลือกทีละส่วน ปุ่มเหล่านี้แค่แก้ไฟล์ให้ เรายังต้อง git add และ Commit เหมือนเดิม

Remote, SSH Key และการ push, fetch, pull, clone

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Remote คือ Repository อีกชุดที่อยู่นอกเครื่อง เช่น บน GitHub ซึ่ง Repository ในเครื่องจำไว้ด้วยชื่อสั้นๆ ชื่อมาตรฐานคือ origin คำสั่งที่ใช้กับ Remote มี 4 ตัวหลัก: git push ส่ง Commit ของเราขึ้นไป, git fetch ดึง Commit ใหม่ของคนอื่นลงมาเก็บไว้ใน Remote-tracking branch เช่น origin/main โดยยังไม่แตะไฟล์งาน, git pull คือ fetch แล้วตามด้วย merge (ค่าเริ่มต้นของหลักสูตร pull.rebase false) หรือ rebase (ถ้าใช้ git pull --rebase) และ git clone คัดลอก Repository ทั้งหมดลงเครื่องพร้อมตั้ง origin ให้

เมื่อมีคน Push ก่อนเรา การ Push ของเราจะถูกปฏิเสธ (rejected (fetch first)) เพราะ Git ไม่ยอมให้ทับงานของคนอื่น เราต้อง pull มารวมก่อนแล้วค่อย Push ใหม่ คำสั่ง git branch -vv บอกได้ว่า Branch ของเรานำหน้า (ahead) หรือตามหลัง (behind) Remote อยู่กี่ Commit ส่วน git fetch --prune ลบ Remote-tracking branch ที่ถูกลบบน Remote ไปแล้ว

การเชื่อมต่อ GitHub ใช้ได้ 2 แบบ คือ HTTPS (https://github.com/somchai-dev/learning-journal.git) ซึ่งต้องใช้ Personal Access Token แทนรหัสผ่าน และ SSH (git@github.com:somchai-dev/learning-journal.git) ซึ่งใช้คู่กุญแจ (Key pair) ที่สร้างครั้งเดียวแล้วไม่ต้องพิมพ์อะไรอีก หลักสูตรนี้ใช้ SSH ใช้แนวคิดนี้ทุกครั้งที่ต้องสำรองงานขึ้น GitHub หรือทำงานร่วมกับคนอื่น

Best Practice
  • เริ่มวันทำงานด้วย git switch main และ git pull ก่อนแตก Branch ใหม่เสมอ
  • ใช้ git fetch ตามด้วย git log --oneline --all ดูว่าเพื่อนเปลี่ยนอะไรก่อนรวม เมื่อไม่แน่ใจ

  • รัน git fetch --prune เป็นประจำ เพื่อลบ origin/... ของ Branch ที่ถูกลบบน GitHub แล้ว

Pull Request, Fork, Code Review และ GitHub CLI

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Pull Request (PR) คือคำขอบน GitHub ให้รวม Branch หนึ่งเข้าอีก Branch หนึ่ง พร้อมพื้นที่ให้ทีมอ่าน diff แสดงความเห็น และรอผลตรวจอัตโนมัติ (Checks) ก่อนกด Merge วงจรของ PR คือ: แตก Branch → Commit → git push -u origin feature/... → เปิด PR (gh pr create) → รอ Checks และ Code Review → แก้ตามความเห็นแล้ว Push เพิ่มเข้า Branch เดิม (PR อัปเดตเอง) → Merge → ลบ Branch → git switch main และ git pull ปุ่ม Merge บน GitHub มี 3 แบบ: Create a merge commit (เก็บทุก Commit และมี Merge commit), Squash and merge (รวมทุก Commit ของ PR เป็น Commit เดียว นิยมที่สุดสำหรับ PR เล็ก) และ Rebase and merge (นำ Commit ไปต่อท้ายเป็นเส้นตรง)

PR ที่ดีมีหัวเรื่องแบบ Conventional Commits และคำอธิบายที่ตอบ 4 ข้อ: ทำอะไร, ทำไม, ทดสอบอย่างไร และภาพหน้าจอ (ถ้าเปลี่ยนหน้าตา) ใส่ Closes #1 หรือ Fixes #1 เพื่อปิด Issue หมายเลข 1 อัตโนมัติเมื่อ Merge Issue ใช้บันทึกบั๊กและงานที่ต้องทำ ติด Label ได้ และจัดลงบอร์ด GitHub Projects ที่มีคอลัมน์ Todo, In Progress, Done

Fork คือสำเนา Repository ของคนอื่นที่อยู่ในบัญชี GitHub ของเรา ใช้เมื่อไม่มีสิทธิ์ Push เข้า Repository ต้นฉบับ เช่น โปรเจกต์ Open Source เรา Clone Fork ของเราลงเครื่อง (origin) และเพิ่ม Remote ชื่อ upstream ชี้ไปที่ต้นฉบับ เพื่อดึงงานใหม่มาอัปเดต Fork ส่วน Code Review มีมารยาทสำคัญ: ติชมที่โค้ด ไม่ใช่ที่ตัวคน, ใช้คำถามแทนคำสั่ง ("ถ้าใช้ const ตรงนี้จะดีกว่าไหม"), ขึ้นต้นด้วย nit: สำหรับเรื่องเล็กที่ไม่บังคับแก้, ใช้ปุ่ม Suggestion เสนอโค้ดที่เจ้าของ PR กดรับได้ทันที และเลือก Approve หรือ Request changes ให้ชัดเจน

เปรียบเทียบ

PR คือการส่งร่างบทความให้บรรณาธิการ คุณไม่ได้แก้หนังสือพิมพ์ฉบับจริงเอง แต่ส่งร่างพร้อมบันทึกว่าแก้อะไรเพราะอะไร บรรณาธิการขีดเขียนความเห็น คุณแก้แล้วส่งร่างเดิมกลับไป จนได้รับอนุมัติจึงตีพิมพ์ ส่วน Fork คือการถ่ายเอกสารหนังสือทั้งเล่มของสำนักพิมพ์อื่นมาเขียนในฉบับของเรา แล้วส่งหน้าที่แก้กลับไปเสนอเขา

Rebase และ Interactive Rebase พร้อมกฎทอง

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Rebase คือการนำ Commit ของ Branch เราไป "เล่นซ้ำ" (Replay) ต่อท้าย Commit ล่าสุดของอีก Branch ผลคือประวัติเป็นเส้นตรงเหมือนเราเพิ่งเริ่มงานจาก main ล่าสุด ไม่มี Merge commit แต่ Commit ที่ถูกเล่นซ้ำจะเป็น Commit ใหม่ที่มีรหัสใหม่ เสมอ แม้เนื้อหาเหมือนเดิม ใช้เมื่อต้องการอัปเดต Feature branch ให้ทัน main ก่อนเปิดหรือก่อน Merge PR และใช้ git pull --rebase เมื่อไม่อยากได้ Merge commit จากการ Pull

Interactive Rebase (git rebase -i HEAD~3) เปิดรายการ Commit ให้เราจัดการก่อนส่งให้คนอื่นดู คำสั่งในรายการมีดังนี้: pick เก็บไว้ตามเดิม, reword แก้ข้อความ, squash รวมกับ Commit ก่อนหน้าและรวมข้อความด้วย, fixup รวมกับ Commit ก่อนหน้าแต่ทิ้งข้อความของตัวเอง, drop ทิ้ง Commit และสลับบรรทัดเพื่อเรียงลำดับใหม่ได้ ทางลัดที่นิยมคือ git commit --fixup <commit> ตามด้วย git rebase -i --autosquash ซึ่งจัดบรรทัด fixup ให้อัตโนมัติ ถ้าระหว่าง Rebase เกิด Conflict ให้แก้ไฟล์ git add แล้ว git rebase --continue หรือข้ามด้วย --skip หรือยกเลิกทั้งหมดด้วย --abort

ระวัง

กฎทอง: ห้าม Rebase Commit ที่คนอื่นมีแล้ว (Commit ที่ Push ขึ้น Branch ที่ใช้ร่วมกัน เช่น main) เพราะ Rebase สร้าง Commit ใหม่แทนของเดิม ประวัติในเครื่องเพื่อนจะไม่ตรงกับ Remote เกิด Commit ซ้ำและ Conflict วุ่นวาย Rebase ได้เฉพาะ Commit ในเครื่องที่ยังไม่ Push หรือ Feature branch ที่เราทำคนเดียว และเมื่อต้อง Push ทับ Branch ของตัวเองหลัง Rebase ให้ใช้ git push --force-with-lease (ปลอดภัยกว่า --force เพราะจะไม่ทับถ้ามีคนอื่น Push เพิ่มเข้ามา) และห้ามใช้กับ main เด็ดขาด

เปรียบเทียบ

Merge เหมือนการเย็บสมุดสองเล่มติดกันพร้อมใบปะหน้าว่า "รวมเล่มวันนี้" ส่วน Rebase เหมือนการคัดลอกบันทึกของเราใหม่ทั้งหมดต่อท้ายสมุดเล่มหลักล่าสุด อ่านง่ายเป็นเรื่องเดียว แต่เป็นลายมือชุดใหม่ ถ้าเพื่อนถ่ายเอกสารฉบับเก่าไปแล้ว ฉบับของเพื่อนจะไม่ตรงกับของเรา Interactive Rebase คือการเรียบเรียงบันทึกก่อนส่งครู รวมหน้าที่เขียนว่า "แก้คำผิด" เข้ากับหน้าหลัก และฉีกหน้าที่ไม่ต้องการทิ้ง

Reset, Reflog และการลบ Secret ออกจากประวัติ

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

git reset <commit> ย้ายป้าย Branch ปัจจุบันถอยกลับไปที่ Commit ที่ระบุ Commit ที่อยู่หลังจากนั้นจะหายไปจากประวัติของ Branch มี 3 โหมดที่ต่างกันตรงว่า "การเปลี่ยนแปลงของ Commit ที่ถอยออกมาไปอยู่ที่ไหน"

  • --soft: เก็บไว้ใน Staging Area พร้อม Commit ใหม่ทันที เหมาะกับการรวมหลาย Commit เป็นอันเดียว หรือเขียนข้อความใหม่
  • --mixed (ค่าเริ่มต้นเมื่อไม่ใส่โหมด): เก็บไว้ใน Working Tree แต่ไม่ Staged เหมาะกับการเลือก add ใหม่เป็นหลาย Commit
  • --hard: ทิ้งทั้ง Staging และ Working Tree ไฟล์กลับไปเหมือน Commit ปลายทางทุกตัวอักษร งานที่ยังไม่ Commit หายถาวร

ใช้ reset กับ Commit ในเครื่องที่ยังไม่ Push เท่านั้น ถ้า Commit แชร์ไปแล้วให้ใช้ git revert (แนวคิดที่ 4) ตาข่ายนิรภัยของทุกอย่างคือ Reflog ซึ่งบันทึกทุกครั้งที่ HEAD ขยับในเครื่องเรา (Commit, reset, switch, rebase, merge) อ้างถึงด้วย HEAD@{n} ทำให้กู้ Commit ที่หายจาก reset --hard หรือจาก Branch ที่ลบไปได้ Reflog เก็บไว้ประมาณ 90 วันตามค่าเริ่มต้น อยู่ในเครื่องเราเท่านั้น และไม่มีงานที่ไม่เคย Commit

เรื่องที่ร้ายแรงที่สุดคือ Secret หลุดเข้าประวัติ เช่น Commit ไฟล์ .env การลบไฟล์ใน Commit ใหม่ไม่พอ เพราะค่ายังอยู่ใน Commit เก่า ลำดับการรับมือคือ (1) Revoke หรือ Rotate key ทันที ที่ผู้ให้บริการ ถือว่า key นั้นถูกขโมยไปแล้ว (2) ตรวจ Log การใช้งานว่ามีการใช้ผิดปกติหรือไม่ (3) ลบไฟล์ออกจากทุก Commit ด้วย git filter-repo (4) Force push และให้ทุกคนในทีม Clone ใหม่ (5) แจ้งทีมและผู้เกี่ยวข้อง GitHub ช่วยป้องกันด้วย Secret scanning (ตรวจหา key ที่รู้จักใน Repository) และ Push protection (บล็อกการ Push ที่มี key ตั้งแต่ต้น)

เปรียบเทียบ

reset คือการย้อนเข็มนาฬิกาของสมุดบันทึก --soft ฉีกหน้าออกแต่เก็บเนื้อหาไว้ในแฟ้มพร้อมเย็บใหม่ --mixed ฉีกหน้าออกแล้ววางเนื้อหาไว้บนโต๊ะ --hard ฉีกแล้วเผาทิ้ง ส่วน Reflog คือกล้องวงจรปิดในห้องที่บันทึกว่าเคยมีหน้าไหนอยู่ตรงไหน ทำให้ตามหาหน้าที่ฉีกไปได้ ถ้าหน้านั้นเคยถูกเย็บเข้าเล่ม (Commit) มาก่อน

ระวัง

git filter-repo เขียนประวัติใหม่ทั้ง Repository รหัสของทุก Commit ตั้งแต่จุดที่แก้จะเปลี่ยน และโดยออกแบบ มันจะลบ Remote origin ออกเพื่อกันการ Push พลาด ใช้กับ Clone ใหม่ที่สำรองไว้แล้วเท่านั้น และทำหลังจาก Revoke key ไปแล้ว ตัวอย่างนี้ใช้ --force เพราะเป็น Repository ฝึกที่สร้างเองในเครื่อง ไม่ใช่ Clone ใหม่

# ติดตั้ง (ถ้ายังไม่ได้ติดตั้งในส่วนเตรียมเครื่อง)
sudo apt install -y git-filter-repo
# เตรียม Repository ที่เผลอ Commit .env แล้วลบใน Commit ถัดมา
rm -rf ~/projects/git-lab/c10-secret
mkdir -p ~/projects/git-lab/c10-secret && cd ~/projects/git-lab/c10-secret
git init -q

git add README.md
git commit -q -m "docs: add README"

git add .env
git commit -q -m "feat: add config"
git rm -q .env
echo ".env" > .gitignore
git add .gitignore
git commit -q -m "chore: remove .env and ignore it"

# ไฟล์ถูกลบแล้ว แต่ประวัติยังมี และยังเปิดอ่านค่าได้

# ลองรันแบบปกติ (ไม่ใช่ Clone ใหม่ จะถูกปฏิเสธ)

  • เปิด Secret scanning และ Push protection ใน Settings → Code security ของ Repository และใช้ .env + .gitignore ตั้งแต่ Commit แรก
  • เมื่อ Secret หลุด ให้ Revoke ก่อนลบประวัติเสมอ เพราะคนอื่นอาจ Clone หรือบอตอาจเก็บค่าไปแล้วก่อนที่คุณจะลบ

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

เมื่อโปรเจกต์โตขึ้น คำถามที่เจอบ่อยคือ "บั๊กนี้เข้ามาตั้งแต่เมื่อไร" และ "บรรทัดนี้ใครเขียน เพราะอะไร" Git มีเครื่องมือสืบสวน 3 ตัว: git blame -L 7,7 ไฟล์ บอกว่าบรรทัดที่ 7 มาจาก Commit ไหน ใครเขียน เมื่อไร, git log -S 'ข้อความ' หา Commit ที่เพิ่มหรือลบข้อความนั้น และ git bisect ค้นหาแบบแบ่งครึ่ง (Binary search) ว่า Commit ไหนเป็นตัวแรกที่ทำให้พัง เราบอกแค่ Commit ที่ดี 1 อันและที่เสีย 1 อัน Git จะพาไปทดสอบตรงกลางทีละครั้ง จาก 1,000 Commit ใช้ทดสอบเพียงราว 10 ครั้ง และถ้ามีสคริปต์ทดสอบ git bisect run จะทำให้อัตโนมัติทั้งหมด โดยดูจาก Exit code ของสคริปต์: 0 = ดี, 1–127 (ยกเว้น 125) = เสีย, 125 = ข้าม Commit นี้ (เช่น Build ไม่ได้)

git cherry-pick <commit> คัดลอกการเปลี่ยนแปลงของ Commit เดียวไปสร้างเป็น Commit ใหม่บน Branch ปัจจุบัน ใช้บ่อยกับ Hotfix คือแก้บั๊กบน main แล้วนำการแก้นั้นไปใส่ Branch ของเวอร์ชันที่ปล่อยไปแล้ว ใส่ -x เพื่อให้ข้อความ Commit บันทึกว่าคัดลอกมาจาก Commit ไหน ส่วน Tag คือป้ายถาวรติด Commit ที่เป็นเวอร์ชันสำคัญ มี 2 แบบ: Lightweight (git tag v1.0.0 มีแค่ชื่อ) และ Annotated (git tag -a v1.0.0 -m "..." เก็บผู้สร้าง วันที่ และข้อความ ใช้กับ Release เสมอ) ตั้งชื่อตาม Semantic Versioning 2.0.0 คือ MAJOR.MINOR.PATCH: เพิ่ม MAJOR เมื่อเปลี่ยนแบบใช้ร่วมกับของเดิมไม่ได้, MINOR เมื่อเพิ่มฟีเจอร์, PATCH เมื่อแก้บั๊ก

Tag ไม่ขึ้น Remote กับ git push ธรรมดา ต้องสั่ง git push origin v1.0.0 หรือ git push origin --tags บน GitHub นำ Tag ไปสร้าง Release ได้ ซึ่งเป็นหน้าประกาศเวอร์ชันพร้อม Release notes และไฟล์ดาวน์โหลด สร้างจาก Terminal ด้วย gh release create v1.0.0 --generate-notes (GitHub เขียน Release notes จากรายชื่อ PR ให้อัตโนมัติ คำสั่งนี้ต้องรันกับ Repository บน GitHub จริง) สุดท้าย Git LFS (Large File Storage) ใช้เก็บไฟล์ Binary ขนาดใหญ่ เช่น .psd ภาพ เสียง หรือโมเดล AI: รัน git lfs install ครั้งเดียวต่อเครื่อง แล้ว git lfs track "*.psd" ซึ่งเขียนกฎลงไฟล์ .gitattributes (ต้อง Commit ไฟล์นี้ด้วย) Git จะเก็บแค่ตัวชี้ ส่วนไฟล์จริงไปอยู่ที่ Server ของ LFS บน GitHub มีโควตาพื้นที่และปริมาณดาวน์โหลดจำกัด ให้ตรวจเงื่อนไขล่าสุดในเอกสารของ GitHub ก่อนใช้กับไฟล์จำนวนมาก

  • เขียนสคริปต์ทดสอบให้ใช้กับ git bisect run ได้ ยิ่งมีเทสต์อัตโนมัติ ยิ่งหาบั๊กย้อนหลังได้เร็ว

  • cherry-pick ใช้กับ Hotfix เป็นครั้งคราว ถ้าต้องย้ายหลาย Commit ระหว่าง Branch บ่อยๆ แปลว่าควรทบทวนการแตก Branch

CI (Continuous Integration) คือการตรวจทุกการเปลี่ยนแปลงอัตโนมัติ เช่น Lint, Test หรือ Validate ทุกครั้งที่ Push หรือเปิด PR เพื่อจับข้อผิดพลาดก่อนเข้า main ส่วน CD (Continuous Delivery/Deployment) คือการนำงานที่ผ่านการตรวจขึ้นระบบจริงอัตโนมัติ GitHub Actions ทำทั้งสองอย่างจากไฟล์ YAML ในโฟลเดอร์ .github/workflows/ โครงสร้างของ Workflow คือ name (ชื่อที่แสดงในแท็บ Actions), on (Trigger เช่น push, pull_request พร้อม branches, workflow_dispatch สำหรับปุ่มรันเอง และ schedule ที่ใช้ Cron ตามเวลา UTC), permissions (สิทธิ์ของ GITHUB_TOKEN ให้น้อยที่สุด เช่น contents: read), jobs แต่ละ Job รันบนเครื่อง Runner ตาม runs-on และมี steps ซึ่งแต่ละ Step จะ uses Action สำเร็จรูป (ส่งค่าด้วย with:) หรือ run คำสั่ง Shell ตั้งตัวแปรด้วย env, ให้ Job รอกันด้วย needs และอ่านค่าลับด้วย ${{ secrets.NAME }} ซึ่งห้าม echo ออกมา

GitHub Pages เผยแพร่เว็บ Static ฟรีสำหรับ Public repository ที่ URL https://somchai-dev.github.io/portfolio/ เมื่อตั้ง Settings → Pages → Source เป็น GitHub Actions เราจะ Deploy ผ่าน Workflow ที่ใช้ actions/configure-pages@v5, actions/upload-pages-artifact@v4 และ actions/deploy-pages@v4 ซึ่งต้องการสิทธิ์ pages: write กับ id-token: write และ Environment ชื่อ github-pages เพราะเว็บอยู่ใต้ /portfolio/ ลิงก์ทุกตัวต้องเป็นแบบ Relative (css/style.css) ไม่ใช่ขึ้นต้นด้วย / หลักการสำคัญคือ รันคำสั่งตรวจเดียวกับ CI ในเครื่องให้ผ่านก่อน Push ใช้แนวคิดนี้กับทุกโปรเจกต์ที่อยู่บน GitHub เริ่มจาก Mini Project ในส่วนที่ 4 และต่อยอดในหัวข้อ และ

เปรียบเทียบ

CI คือแผนกตรวจคุณภาพในโรงงาน สินค้าทุกชิ้นที่ออกจากสายพาน (ทุก PR) ต้องผ่านเครื่องตรวจอัตโนมัติ ชิ้นไหนไม่ผ่านจะถูกติดป้ายแดงและไม่ได้ไปต่อ ส่วน CD คือรถส่งของที่จะออกเดินทางทันทีเมื่อสินค้าผ่านการตรวจและเข้าคลังหลัก (main) ไฟล์ YAML คือคู่มือขั้นตอนที่แปะไว้ให้พนักงานทุกกะทำตามเหมือนกันทุกครั้ง

ตัวอย่างโค้ด

ไฟล์ Workflow ที่ 1: CI (เหมือนใน Step 12 ของส่วนที่ 1 ทุกบรรทัด) วางไว้ที่ .github/workflows/ci.yml ใน Repository

# ชื่อ Workflow ที่จะแสดงในแท็บ Actions
name: CI

# เหตุการณ์ที่ทำให้ Workflow ทำงาน
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
  workflow_dispatch:

# ให้ GITHUB_TOKEN มีสิทธิ์แค่อ่านโค้ด (ให้สิทธิ์น้อยที่สุดเท่าที่จำเป็น)
permissions:
  contents: read

jobs:
  check-site:
    runs-on: ubuntu-latest
    steps:
      - name: ดึงโค้ดของ Repository ลงเครื่อง Runner
        uses: actions/checkout@v5

      - name: ติดตั้ง Node.js เพื่อใช้ npx
        uses: actions/setup-node@v5
        with:
          node-version: 24

      - name: ตรวจโครงสร้าง HTML
        run: npx --yes html-validate@11.16.2 "**/*.html"

      - name: ตรวจลิงก์และรูปภาพที่เสีย (เฉพาะไฟล์ในเว็บของเรา)
        run: npx --yes linkinator@8.1.0 . --recurse --skip "^https://"

ไฟล์ Workflow ที่ 2: Deploy ขึ้น GitHub Pages เขียนตามโครงสร้างของ Starter workflow ทางการของ GitHub สำหรับเว็บ Static วางไว้ที่ .github/workflows/pages.yml

# Deploy เว็บ Static ขึ้น GitHub Pages ทุกครั้งที่มีงานเข้า main
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

# สิทธิ์ที่ Pages ต้องใช้: อ่านโค้ด เขียน Pages และขอ Token ยืนยันตัวตน
permissions:
  contents: read
  pages: write
  id-token: write

# ให้ Deploy ทีละครั้ง ไม่ยกเลิกรอบที่กำลังทำอยู่
concurrency:
  group: "pages"
  cancel-in-progress: false

jobs:
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - name: ดึงโค้ด
        uses: actions/checkout@v5

      - name: ตั้งค่า Pages
        uses: actions/configure-pages@v5

      - name: อัปโหลดไฟล์เว็บทั้งโฟลเดอร์เป็น Artifact
        uses: actions/upload-pages-artifact@v4
        with:
          path: '.'

      - name: Deploy ขึ้น GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4

Best Practice
  • รันคำสั่งเดียวกับ CI ในเครื่องให้ผ่านก่อน Push ทุกครั้ง และระบุเวอร์ชันของเครื่องมือ (html-validate@11.16.2) เพื่อให้ผลเหมือนกันทุกที่
  • ระบุเวอร์ชันของ Action ทุกตัว (@v5) งานที่ต้องการความปลอดภัยสูงให้ปักเป็นรหัส Commit เต็มของ Action
  • ตั้ง permissions ให้น้อยที่สุดในทุก Workflow และเก็บค่าลับใน Settings → Secrets and variables → Actions เท่านั้น
  • ตั้ง Ruleset ให้ main: ต้องผ่าน PR, ต้องผ่าน Check check-site และห้าม Force push

ทำต่อใน c12-site

  1. เปลี่ยนลิงก์ CSS ใน projects.html เป็น /css/style.css แล้วรัน linkinator จะพบว่ายังผ่าน (exit code 0) เพราะ linkinator เปิด Server ที่มีโฟลเดอร์ c12-site เป็นราก แต่บน Pages รากของ Domain คือ https://somchai-dev.github.io/ ไม่ใช่ /portfolio/ ให้อธิบายด้วยคำพูดของคุณว่าทำไมลิงก์นี้จึงพังเฉพาะบน Pages แล้วแก้กลับเป็นแบบ Relative

  3. เพิ่ม Trigger schedule ให้ ci.yml รันทุกวันจันทร์ 08:00 น. เวลาประเทศไทย (เขียน Cron เป็นเวลา UTC)
  4. บน GitHub จริง: Push เว็บนี้เป็น Repository ใหม่ เปิด PR ที่ตั้งใจลบ alt ดูว่า Check เป็นสีแดง แล้วแก้ให้เป็นสีเขียว
