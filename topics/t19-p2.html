19.2Core Concept & Quick Guide

ส่วนนี้คือคู่มือใช้งานจริงของหัวข้อ Linux แบ่งเป็น 12 แนวคิด เรียงจากง่ายไปยาก แนวคิดที่ 1–3 เป็นระดับ Beginner (เดินในระบบไฟล์ จัดการไฟล์ อ่านไฟล์และหาความช่วยเหลือ) แนวคิดที่ 4–8 เป็นระดับ Intermediate (Permission, apt, Pipe และ Redirection, Text Processing, Environment Variables) และแนวคิดที่ 9–12 เป็นระดับ Advanced (Process, systemd, Network และ SSH, Bash Script กับ cron) ทุกแนวคิดมีคำอธิบาย ตัวอย่างที่รันได้จริง ผลลัพธ์ที่ได้จริง ตารางอธิบายทีละบรรทัด ข้อผิดพลาดที่พบบ่อย และแบบฝึก "ลองเอง"

ให้พิมพ์ตามทุกตัวอย่างด้วยมือตัวเองใน Terminal ของ Ubuntu ไม่ใช่แค่อ่าน ผลลัพธ์ทั้งหมดในหน้านี้ได้จากการรันจริงบน Ubuntu 24.04 LTS ด้วยผู้ใช้ชื่อ somchai ค่าที่ขึ้นกับเครื่อง เช่น วันเวลา PID, IP Address, ชื่อเครื่อง และขนาดไฟล์ จะต่างจากเครื่องของคุณ จุดไหนที่ค่าต่างกันจะมีหมายเหตุบอกไว้เสมอ

เตรียมเครื่องสำหรับหัวข้อนี้

ก่อนเริ่มแนวคิดที่ 1 ให้ตรวจว่าเครื่องพร้อม 4 ข้อ: (1) Ubuntu เป็นเวอร์ชัน 24.04 (2) ติดตั้งชุดเครื่องมือของหัวข้อครบ (3) เวอร์ชันของเครื่องมือตรงกับหลักสูตร และ (4) มีโฟลเดอร์ฝึก ~/projects/linux-lab ถ้าคุณทำ Step 6 ใน Part 1 ไปแล้ว ขั้นที่ 2 จะขึ้นว่าทุกแพ็กเกจติดตั้งไว้แล้ว ซึ่งถูกต้อง

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Operating System (OS) คือซอฟต์แวร์หลักที่ดูแลฮาร์ดแวร์ทั้งหมดของเครื่อง แกนกลางของ OS เรียกว่า Kernel ซึ่งคุยกับ CPU, RAM และ Disk โดยตรง เราไม่ได้สั่ง Kernel เอง แต่สั่งผ่าน Shell (บน Ubuntu คือ Bash) ซึ่งรับคำสั่งที่เราพิมพ์ แปลความหมาย แล้วเรียกโปรแกรมให้ทำงาน ส่วน Terminal คือหน้าต่างที่ใช้พิมพ์และแสดงผล เช่น Windows Terminal หรือ Terminal ใน VS Code เมื่อเปิด Ubuntu จะเห็นบรรทัดรอรับคำสั่งที่เรียกว่า Prompt แบบนี้ somchai@DESKTOP-K7Q2M4P:~$ อ่านได้ว่า ผู้ใช้ somchai อยู่บนเครื่องชื่อ DESKTOP-K7Q2M4P ตอนนี้อยู่ที่โฟลเดอร์ ~ (Home ของตัวเอง) และเครื่องหมาย $ บอกว่าเป็นผู้ใช้ทั่วไป ถ้าเป็นผู้ใช้ root (ผู้ดูแลสูงสุด) จะเห็น # แทน

ระบบไฟล์ของ Linux เป็นต้นไม้ต้นเดียว เริ่มที่ / (Root Directory) ไม่มีไดรฟ์ C: หรือ D: แบบ Windows ทุกไฟล์มีที่อยู่ที่เรียกว่า Path ซึ่งเขียนได้ 2 แบบ Absolute Path ขึ้นต้นด้วย / เสมอและบอกทางจากรากต้นไม้ เช่น /home/somchai/projects ใช้ได้จากทุกที่ ส่วน Relative Path ไม่ขึ้นต้นด้วย / และนับจากโฟลเดอร์ที่อยู่ตอนนี้ เช่น projects/linux-lab ชื่อพิเศษที่ต้องจำคือ . (โฟลเดอร์ปัจจุบัน), .. (โฟลเดอร์แม่ หรือขึ้นไป 1 ชั้น), ~ (Home ของเรา) และ - (โฟลเดอร์ก่อนหน้า ใช้กับ cd) ไฟล์ที่ชื่อขึ้นต้นด้วยจุด เช่น .bashrc, .profile และ .bash_logout เป็น Hidden File (Dotfile) ซึ่ง ls ธรรมดาจะไม่แสดง ต้องใช้ ls -a

ทักษะแป้นพิมพ์ที่ทำให้พิมพ์เร็วขึ้นหลายเท่า:

  • Tab เติมชื่อคำสั่ง ไฟล์ หรือโฟลเดอร์ให้อัตโนมัติ ถ้ามีหลายตัวเลือกให้กด Tab 2 ครั้งเพื่อดูทั้งหมด
  • ↑ และ ↓ เลื่อนดูคำสั่งที่เคยพิมพ์ คำสั่ง history แสดงประวัติทั้งหมดพร้อมหมายเลข และ !! คือรันคำสั่งล่าสุดซ้ำ (เช่น sudo !! เมื่อลืมใส่ sudo)
  • Ctrl+R ค้นหาคำสั่งเก่าด้วยคำบางส่วน กดซ้ำเพื่อหาย้อนไปอีก กด Enter เพื่อรัน หรือ Esc เพื่อนำมาแก้ก่อน
  • Ctrl+C ยกเลิกคำสั่งที่กำลังทำงาน (ใน Terminal ไม่ใช่การคัดลอก) และ Ctrl+L หรือ clear ล้างหน้าจอ
  • Linux แยกตัวพิมพ์เล็กและใหญ่ (Case Sensitive): docs, Docs และ DOCS เป็น 3 ชื่อที่ต่างกัน
  • ชื่อที่มีช่องว่างต้องครอบด้วยเครื่องหมายคำพูด "my notes" หรือใส่ \ หน้าช่องว่าง my\ notes ไม่เช่นนั้น Shell จะเข้าใจว่าเป็น 2 คำ
เปรียบเทียบ

ระบบไฟล์เหมือนอาคารสำนักงานหลังใหญ่ / คือล็อบบี้ชั้นล่าง ทุกห้องในอาคารเดินไปถึงได้จากล็อบบี้ pwd คือการดูป้ายบอกว่า "ตอนนี้ฉันยืนอยู่ห้องไหน" ls คือการมองว่าในห้องนี้มีอะไรบ้าง ส่วน cd คือการเดินไปห้องอื่น Absolute Path เหมือนบอกทางว่า "จากล็อบบี้ ขึ้นชั้น home ไปห้อง somchai" ซึ่งใช้ได้ไม่ว่าคุณยืนอยู่ตรงไหน ส่วน Relative Path เหมือนบอกว่า "จากตรงนี้ เดินเข้าห้องถัดไป" ซึ่งใช้ได้เฉพาะเมื่อรู้ว่าตอนนี้ยืนอยู่ที่ไหน

ตัวอย่างโค้ด

ตัวอย่างนี้ไม่ต้องติดตั้งอะไรเพิ่ม เปิด Terminal ของ Ubuntu แล้วพิมพ์ทีละบรรทัด สังเกตผลของ pwd หลัง cd ทุกครั้ง

# สร้างโฟลเดอร์ฝึก 3 โฟลเดอร์ในคำสั่งเดียว (โฟลเดอร์ที่ 3 มีช่องว่างในชื่อ)
mkdir -p ~/projects/linux-lab/c01/{docs,images,'my notes'}
# กลับ Home แล้วดูว่าอยู่ที่ไหน
cd ~ && pwd
# เข้าโฟลเดอร์ด้วย Relative Path (นับจาก Home ที่อยู่ตอนนี้)
cd projects/linux-lab/c01 && pwd
# เข้าโฟลเดอร์ด้วย Absolute Path (ขึ้นต้นด้วย /)
cd /home/somchai/projects/linux-lab/c01/docs && pwd
# ขึ้นไป 1 ชั้น
cd .. && pwd
# กลับไปโฟลเดอร์ก่อนหน้า (cd - จะพิมพ์ Path ให้เอง)
cd -
# ขึ้นไป 1 ชั้นแล้วเข้า "my notes" ต้องใส่เครื่องหมายคำพูดเพราะมีช่องว่าง
cd ../"my notes" && pwd
# ดูรายละเอียดของทุกอย่างใน c01 รวมถึง . และ ..
ls -la ~/projects/linux-lab/c01

Best Practice
  • ตั้งชื่อไฟล์และโฟลเดอร์ด้วยตัวพิมพ์เล็ก ไม่มีช่องว่าง ใช้ - หรือ _ แทน เช่น my-notes ทำให้พิมพ์ง่ายและไม่พังใน Script
  • ใน Script และ cron ใช้ Absolute Path เสมอ เพราะโฟลเดอร์ปัจจุบันตอนที่ Script รันอาจไม่ใช่ที่ที่คุณคิด
  • กด Tab ทุกครั้งที่พิมพ์ชื่อไฟล์ ถ้า Tab ไม่เติมให้ แปลว่าชื่อผิดหรือไฟล์ไม่มี จะรู้ก่อนกด Enter
  • เก็บงานไว้ใน Home ของ Linux (~/projects) ไม่ใช่ใน /mnt/c จะเร็วกว่าและ Permission ถูกต้อง
  • ก่อนรันคำสั่งที่เปลี่ยนแปลงไฟล์ ให้ดู Prompt หรือพิมพ์ pwd เพื่อยืนยันว่าอยู่ในโฟลเดอร์ที่ถูกต้อง

จัดการไฟล์และโฟลเดอร์ด้วย touch, mkdir, cp, mv, rm และ Wildcards

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

งานประจำวันบน Linux คือการสร้าง คัดลอก ย้าย เปลี่ยนชื่อ และลบไฟล์ ใน Windows เราลากไฟล์ด้วยเมาส์ แต่บน Server ไม่มีหน้าจอให้ลาก ทุกอย่างทำผ่านคำสั่งไม่กี่ตัว ข้อดีคือทำกับไฟล์ร้อยไฟล์ได้ในคำสั่งเดียว ด้วย Wildcards (เรียกอีกชื่อว่า Globbing) และ Brace Expansion

  • touch file สร้างไฟล์เปล่า (ถ้ามีไฟล์อยู่แล้วจะแค่อัปเดตเวลาแก้ไข) mkdir dir สร้างโฟลเดอร์ และ mkdir -p a/b/c สร้างทุกชั้นที่ยังไม่มีโดยไม่ Error ถ้ามีอยู่แล้ว
  • cp คัดลอก ต้องใส่ -r เมื่อคัดลอกโฟลเดอร์ -i ถามก่อนเขียนทับ และ -v บอกว่าทำอะไรไปบ้าง
  • mv ใช้ได้ทั้ง ย้าย และ เปลี่ยนชื่อ เพราะการเปลี่ยนชื่อก็คือการย้ายไปชื่อใหม่ในที่เดิม ใส่ -i เพื่อกันเขียนทับไฟล์ปลายทาง
  • rm ลบไฟล์ rm -r ลบโฟลเดอร์พร้อมของข้างใน rm -i ถามก่อนลบ ส่วน rmdir ลบได้เฉพาะโฟลเดอร์ว่าง Linux ไม่มีถังขยะใน Terminal ลบแล้วหายทันที
  • Wildcards: * แทนตัวอักษรกี่ตัวก็ได้ ? แทน 1 ตัว [0-9] แทน 1 ตัวที่เป็นตัวเลข [abc] แทน 1 ตัวที่เป็น a, b หรือ c โดย Shell จะแทนที่ด้วย ชื่อไฟล์ที่มีอยู่จริง เท่านั้น
  • Brace Expansion: {a,b} และ {001..005} สร้างข้อความตามที่เขียน ไม่สนว่ามีไฟล์อยู่หรือไม่ จึงใช้สร้างไฟล์ใหม่จำนวนมากได้ แต่ Wildcard ใช้ได้เฉพาะกับไฟล์ที่มีแล้ว
  • file บอกชนิดของไฟล์จากเนื้อหา stat แสดงข้อมูลละเอียด (ขนาด สิทธิ์ เวลา) และ ln -s target link สร้าง Symbolic Link หรือทางลัดไปยังไฟล์อื่น

ใช้แนวคิดนี้ทุกครั้งที่จัดโครงสร้างโปรเจกต์ ย้ายไฟล์ Log เก่าไปเก็บ สำรองไฟล์ Config ก่อนแก้ หรือล้างไฟล์ชั่วคราว ตั้งชื่อไฟล์ให้ดีตั้งแต่แรกจะทำให้ Wildcard ทำงานง่าย: ใช้ตัวพิมพ์เล็ก ไม่มีช่องว่าง (ใช้ - หรือ _ แทน) และใช้วันที่แบบ ISO 2026-10-19 ซึ่งเรียงตามตัวอักษรแล้วตรงกับลำดับเวลาพอดี

เปรียบเทียบ

cp เหมือนถ่ายเอกสารแล้ววางสำเนาไว้อีกลิ้นชัก ต้นฉบับยังอยู่ mv เหมือนหยิบแฟ้มไปใส่ลิ้นชักอื่นหรือเปลี่ยนป้ายชื่อแฟ้ม rm คือเครื่องทำลายเอกสาร ใส่เข้าไปแล้วเอาคืนไม่ได้ ส่วน Wildcard order-*.txt เหมือนบอกพนักงานว่า "หยิบทุกแฟ้มที่ป้ายขึ้นต้นด้วย order และลงท้ายด้วย .txt" พนักงานจะหยิบเฉพาะแฟ้มที่มีอยู่จริงบนชั้น

ตัวอย่างนี้จำลองโฟลเดอร์ของร้านค้าออนไลน์เล็ก ๆ ที่มีโฟลเดอร์คำสั่งซื้อ รายงาน และที่เก็บไฟล์เก่า ใช้ tree ที่ติดตั้งไว้ในขั้นเตรียมเครื่องเพื่อดูผลรวม

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

เกือบทุกอย่างใน Linux เป็นไฟล์ข้อความ ทั้งไฟล์ Config ใน /etc และไฟล์ Log ใน /var/log การอ่านไฟล์ให้เร็วและเลือกดูเฉพาะส่วนที่ต้องการจึงเป็นทักษะที่ใช้ทุกวัน แต่ละคำสั่งเหมาะกับงานต่างกัน:

  • cat file พิมพ์ทั้งไฟล์ออกมา เหมาะกับไฟล์สั้น cat -n ใส่เลขบรรทัดให้
  • less file เปิดไฟล์ยาวทีละหน้า กด Space ไปหน้าถัดไป ลูกศรเลื่อนทีละบรรทัด / แล้วพิมพ์คำเพื่อค้นหา n ไปคำที่พบถัดไป g ไปต้นไฟล์ G ไปท้ายไฟล์ และ q ออก
  • head -n 5 ดู 5 บรรทัดแรก tail -n 5 ดู 5 บรรทัดสุดท้าย และ tail -f เฝ้าดูบรรทัดใหม่ที่ถูกเขียนต่อท้ายแบบสด ๆ (กด Ctrl+C เพื่อหยุด) ซึ่งใช้ดู Log ตอนแก้ปัญหา
  • wc -l -w -c นับบรรทัด คำ และไบต์
  • nano 7.2 คือ Text Editor ที่ง่ายที่สุด เมนูอยู่ด้านล่างจอ ^ หมายถึง Ctrl: Ctrl+O แล้ว Enter บันทึก Ctrl+X ออก Ctrl+W ค้นหา Ctrl+K ตัดบรรทัด Ctrl+U วาง Ctrl+G ดูคู่มือ
  • Vim มีในทุก Server และบางโปรแกรมเปิดให้อัตโนมัติ ให้รู้วิธีเอาตัวรอด: กด i เพื่อพิมพ์ Esc เพื่อหยุดพิมพ์ :w บันทึก :wq บันทึกแล้วออก :q! ออกโดยไม่บันทึก ถ้าอยากเก่ง Vim ให้รัน vimtutor ใช้เวลาประมาณ 30 นาที

เมื่อไม่รู้วิธีใช้คำสั่ง ให้หาคำตอบในเครื่องก่อนค้นเว็บ: man ls เปิดคู่มือเต็ม (อ่านด้วยปุ่มเดียวกับ less) โดย Section 1 คือคำสั่งทั่วไป Section 5 คือรูปแบบไฟล์ Config และ Section 8 คือคำสั่งของผู้ดูแลระบบ ls --help ดูตัวเลือกแบบสั้น help cd ใช้กับคำสั่งที่อยู่ใน Bash เอง (Builtin) type และ which บอกว่าคำสั่งมาจากไหน whatis บอกหน้าที่ใน 1 บรรทัด apropos หรือ man -k ค้นหาคำสั่งจากคำอธิบาย และ tldr แสดงตัวอย่างใช้งานจริงแบบสั้น (ครั้งแรกจะดาวน์โหลดคู่มือจาก tldr.sh อัปเดตด้วย tldr --update)

cat เหมือนเทกระดาษทั้งปึกลงบนโต๊ะ less เหมือนเปิดหนังสือทีละหน้า head คืออ่านแค่หน้าปก tail คืออ่านหน้าสุดท้าย และ tail -f เหมือนยืนดูเครื่องพิมพ์ใบเสร็จที่พิมพ์รายการใหม่ออกมาเรื่อย ๆ ส่วน man คือคู่มือเล่มหนาที่แถมมากับเครื่อง และ tldr คือกระดาษโน้ตสรุปที่เพื่อนเขียนให้

Permissions, Ownership, Users และ sudo (chmod, chown, umask)

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Linux ออกแบบมาให้หลายคนใช้เครื่องเดียวกันได้ ทุกไฟล์จึงมี เจ้าของ (Owner) มี กลุ่ม (Group) และมี Permission 3 ชุด สำหรับ 3 กลุ่มคน คือ u = เจ้าของ (user), g = สมาชิกในกลุ่ม (group) และ o = คนอื่นทั้งหมด (others) แต่ละชุดมี 3 สิทธิ์ อ่านจากผล ls -l เช่น -rwxr-x--- ได้ว่า ตัวแรกคือชนิด (- ไฟล์, d โฟลเดอร์, l Link) ตามด้วย rwx ของเจ้าของ r-x ของกลุ่ม และ --- ของคนอื่น

สิทธิ์ (ตัวเลข)กับไฟล์กับโฟลเดอร์
r (4)อ่านเนื้อหาได้ดูรายชื่อไฟล์ข้างในด้วย ls ได้
w (2)แก้ไขเนื้อหาได้สร้าง ลบ หรือเปลี่ยนชื่อไฟล์ข้างในได้
x (1)รันเป็นโปรแกรมได้เข้าไปข้างในด้วย cd และเข้าถึงไฟล์ข้างในได้

เลขของแต่ละชุดคือผลบวก เช่น rwx = 4+2+1 = 7 และ r-x = 4+1 = 5 ค่าที่เจอบ่อย: 755 โปรแกรมหรือโฟลเดอร์ที่ทุกคนใช้ได้แต่แก้ได้แค่เจ้าของ 644 ไฟล์ทั่วไป 700 โฟลเดอร์ส่วนตัว 600 ไฟล์ลับ เช่น SSH Key และ 750 แชร์ให้กลุ่มทีม ส่วนแบบตัวอักษร (Symbolic) เช่น u+x เพิ่ม x ให้เจ้าของ g-w เอา w ออกจากกลุ่ม o-r เอา r ออกจากคนอื่น a+r ให้ทุกคนอ่านได้ umask คือค่าที่ "หักสิทธิ์ออก" ตอนสร้างไฟล์ใหม่ ผู้ใช้ทั่วไปบน Ubuntu มักเป็น 0002 ไฟล์ใหม่จึงเป็น 664 และโฟลเดอร์ใหม่เป็น 775 แต่บางระบบเป็น 0022 (ได้ 644/755) ให้ตรวจเครื่องตัวเองด้วย umask

ผู้ใช้และกลุ่มเก็บอยู่ใน /etc/passwd และ /etc/group (ทุกคนอ่านได้) ส่วนรหัสผ่านที่ Hash แล้วอยู่ใน /etc/shadow ซึ่งอ่านได้เฉพาะ root คำสั่ง id และ groups บอกว่าเราเป็นใครและอยู่กลุ่มไหน งานที่กระทบทั้งระบบต้องใช้สิทธิ์ root ผ่าน sudo ซึ่งให้สิทธิ์ทีละคำสั่งและบันทึกไว้ว่าใครสั่งอะไร ปลอดภัยกว่าเข้าเป็น root ตลอดเวลา (Prompt ของ root ลงท้ายด้วย #) ใช้แนวคิดนี้เมื่อรัน Script ไม่ได้ ต้องปกป้องไฟล์ที่มี Password หรือ API Key แชร์โฟลเดอร์ให้ทีม หรือตั้งค่า Server ให้แต่ละ Service ทำงานด้วยผู้ใช้ของตัวเอง

  • sudo chown user:group file เปลี่ยนเจ้าของและกลุ่ม sudo chgrp group file เปลี่ยนเฉพาะกลุ่ม
  • sudo adduser ชื่อ สร้างผู้ใช้ sudo groupadd ชื่อ สร้างกลุ่ม sudo usermod -aG กลุ่ม ผู้ใช้ เพิ่มเข้ากลุ่ม (ต้องมี -a) sudo deluser --remove-home ชื่อ ลบผู้ใช้พร้อม Home และ su - ชื่อ สลับเป็นผู้ใช้อื่น
  • sudo -l ดูว่าเราใช้ sudo ทำอะไรได้บ้าง และแก้ไฟล์สิทธิ์ sudo ด้วย sudo visudo เท่านั้น เพราะมันตรวจ Syntax ก่อนบันทึก
  • สิทธิ์พิเศษที่ควรรู้จัก: /tmp เป็น drwxrwxrwt ตัว t คือ Sticky Bit ทุกคนเขียนได้แต่ลบได้เฉพาะไฟล์ของตัวเอง และ /usr/bin/passwd เป็น -rwsr-xr-x ตัว s คือ setuid ทำให้ผู้ใช้ทั่วไปเปลี่ยนรหัสผ่านตัวเองใน /etc/shadow ได้
  • ไฟล์ใน /mnt/c แสดงเป็น rwxrwxrwx ทุกไฟล์ เพราะ Windows ใช้ระบบสิทธิ์ต่างจาก Linux อีกเหตุผลที่ควรทำงานใน ~
เปรียบเทียบ

ไฟล์เหมือนห้องในหอพัก เจ้าของห้อง (u) มีกุญแจเต็มชุด เพื่อนร่วมชั้น (g) อาจได้กุญแจเข้าห้องนั่งเล่นอย่างเดียว คนนอก (o) ไม่ได้อะไรเลย chmod คือการเปลี่ยนกุญแจ chown คือการโอนห้องให้คนอื่น ซึ่งต้องให้นิติบุคคล (root ผ่าน sudo) ทำให้ และ sudo เหมือนการยืมกุญแจผีจากนิติบุคคลมาใช้ครั้งเดียว โดยมีสมุดบันทึกว่าใครยืมไปเมื่อไร

จัดการแพ็กเกจด้วย apt (update, install, remove, search)

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

บน Windows เราดาวน์โหลดไฟล์ .exe จากเว็บมาติดตั้งเอง บน Ubuntu เราติดตั้งโปรแกรมจาก Repository ซึ่งเป็นคลังโปรแกรมที่ Ubuntu ตรวจและเซ็นรับรองแล้ว โปรแกรมแต่ละตัวมาในรูป แพ็กเกจ (.deb) และอาจต้องใช้แพ็กเกจอื่นด้วย เรียกว่า Dependency เครื่องมือ apt จะคำนวณและติดตั้ง Dependency ให้อัตโนมัติ ส่วน dpkg คือเครื่องมือระดับล่างที่ติดตั้งไฟล์ .deb ทีละไฟล์และบอกได้ว่าแพ็กเกจไหนวางไฟล์ไว้ที่ใด

  • sudo apt update ดาวน์โหลด รายชื่อ แพ็กเกจล่าสุด ไม่ได้อัปเกรดอะไร ต้องรันก่อนติดตั้งทุกครั้ง
  • sudo apt upgrade อัปเกรดแพ็กเกจที่มีอยู่ โดยไม่ลบแพ็กเกจใด ส่วน sudo apt full-upgrade ยอมลบหรือเพิ่มแพ็กเกจเพื่อให้อัปเกรดได้ครบ
  • apt search คำ ค้นหา apt show ชื่อ ดูรายละเอียด apt policy ชื่อ ดูว่าติดตั้งเวอร์ชันไหนอยู่ และเวอร์ชันไหนจะได้ถ้าติดตั้ง
  • sudo apt install -y ชื่อ ติดตั้งโดยตอบ yes ให้อัตโนมัติ sudo apt remove ลบโปรแกรมแต่เก็บไฟล์ Config ไว้ sudo apt purge ลบพร้อม Config และ sudo apt autoremove ลบ Dependency ที่ไม่มีใครใช้แล้ว
  • apt list --installed และ apt list --upgradable ดูรายการ dpkg -l ชื่อ ดูสถานะ dpkg -L ชื่อ ดูว่าแพ็กเกจวางไฟล์ไว้ที่ไหน และ dpkg -S /path/file ถามกลับว่าไฟล์นี้มาจากแพ็กเกจไหน
  • รายชื่อ Repository บน Ubuntu 24.04 อยู่ในไฟล์ /etc/apt/sources.list.d/ubuntu.sources ซึ่งใช้รูปแบบใหม่ที่เรียกว่า deb822 (บรรทัด Types:, URIs:, Suites:, Components:)

apt ออกแบบมาให้คนพิมพ์ มีแถบความคืบหน้าและสีสัน ถ้าส่งผลลัพธ์ของ apt ต่อให้คำสั่งอื่นจะเห็นคำเตือน WARNING: apt does not have a stable CLI interface. Use with caution in scripts. ใน Script จึงควรใช้ apt-get และ apt-cache ซึ่งรูปแบบผลลัพธ์คงที่ ส่วนช่องทางอื่น เช่น Snap, PPA หรือไฟล์ .deb จากเว็บ ใช้ได้เมื่อจำเป็น แต่ต้องเชื่อถือผู้ทำ เพราะไม่ได้ผ่านการตรวจของ Ubuntu และอาจทำให้ Dependency ขัดกัน ใช้แนวคิดนี้ทุกครั้งที่ต้องการเครื่องมือใหม่ และอัปเดตความปลอดภัยของเครื่องอย่างน้อยสัปดาห์ละครั้ง

เปรียบเทียบ

apt เหมือนแอป App Store ในมือถือ apt update คือการโหลดหน้าร้านใหม่ให้เห็นราคาและเวอร์ชันล่าสุด (ยังไม่ได้ซื้ออะไร) apt upgrade คือกด "อัปเดตทั้งหมด" ส่วน Dependency เหมือนสั่งเครื่องชงกาแฟแล้วร้านแถมปลั๊กแปลงที่จำเป็นต้องใช้มาให้ด้วย และ autoremove คือการเก็บปลั๊กแปลงที่ไม่มีเครื่องไหนใช้แล้วทิ้งไป

ทุกโปรแกรมใน Linux มีช่องทางข้อมูลมาตรฐาน 3 ช่อง แต่ละช่องมีหมายเลข (File Descriptor): stdin (0) ข้อมูลเข้า ปกติมาจากคีย์บอร์ด stdout (1) ผลลัพธ์ปกติ และ stderr (2) ข้อความ Error ทั้ง stdout และ stderr ออกหน้าจอเหมือนกัน เราจึงมองไม่เห็นว่าเป็นคนละช่อง จนกว่าจะเริ่มเปลี่ยนทิศทาง Redirection คือการเปลี่ยนว่าช่องเหล่านี้ไปที่ไหน และ Pipe (|) คือการต่อ stdout ของคำสั่งหนึ่งเข้า stdin ของคำสั่งถัดไป ซึ่งเป็นหัวใจของปรัชญา Unix: เครื่องมือเล็ก ๆ ที่ทำงานเดียวให้ดี แล้วนำมาต่อกัน

ลำดับของ 2>&1 มีผล เพราะ Bash ทำ Redirection จากซ้ายไปขวา > file 2>&1 แปลว่า "ย้าย stdout ไปไฟล์ก่อน แล้วให้ stderr ตาม stdout ไป" ทั้งสองช่องจึงลงไฟล์ ส่วน 2>&1 > file แปลว่า "ให้ stderr ไปที่ที่ stdout อยู่ตอนนี้ (คือหน้าจอ) แล้วค่อยย้าย stdout ไปไฟล์" Error จึงยังขึ้นจอ ใช้แนวคิดนี้เมื่อต้องเก็บผลลัพธ์ลงไฟล์ แยก Error ออกจากผลปกติ ปิดข้อความที่ไม่ต้องการ ต่อคำสั่งเป็นสายเพื่อวิเคราะห์ข้อมูล และเขียน Log ของ cron job (แนวคิดที่ 12)

เปรียบเทียบ

นึกถึงท่อประปาในบ้าน stdout คือท่อน้ำดี stderr คือท่อน้ำทิ้ง ปกติทั้งสองท่อไหลลงอ่างเดียวกัน (หน้าจอ) > คือการต่อท่อน้ำดีไปลงถังใหม่ (เททิ้งของเก่า) >> คือเติมลงถังเดิม 2> คือแยกท่อน้ำทิ้งไปอีกถัง /dev/null คือท่อระบายลงดิน และ | คือการต่อท่อจากเครื่องกรองหนึ่งไปเข้าอีกเครื่องหนึ่งเป็นสายพาน

Best Practice
  • งานอัตโนมัติ (cron, Script) ให้เก็บ Log ครบทั้งสองช่องด้วย >> job.log 2>&1 เพื่อย้อนดูได้เมื่อมีปัญหา
  • ใช้ 2>/dev/null เฉพาะเมื่อแน่ใจว่า Error นั้นไม่สำคัญ การทิ้ง Error ทุกครั้งทำให้หาสาเหตุปัญหาไม่เจอ
  • ใน Script ของตัวเอง ส่งข้อความ Error ไป stderr ด้วย echo "ERROR: ..." >&2 เพื่อให้ผู้ใช้แยกผลลัพธ์กับ Error ได้
  • สร้าง Pipe ทีละชั้น: รันชั้นแรกดูผล แล้วค่อยเพิ่ม | ... ทีละตัว จะหาจุดผิดง่ายกว่าเขียนยาวทีเดียว

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Log, CSV และไฟล์ Config เป็นข้อความทั้งหมด เครื่องมือกลุ่มนี้ทำให้ตอบคำถามจากไฟล์ขนาดหลายล้านบรรทัดได้ในไม่กี่วินาที โดยไม่ต้องเปิด Excel หรือเขียนโปรแกรม เช่น "IP ไหนเข้าเว็บบ่อยที่สุด" หรือ "มี Error 404 กี่ครั้ง" แต่ละตัวทำงานเดียวแล้วต่อกันด้วย Pipe จากแนวคิดที่ 6

  • grep กรองบรรทัดที่ตรง Pattern: -i ไม่สนตัวพิมพ์เล็กใหญ่ -n แสดงเลขบรรทัด -v กลับด้าน (บรรทัดที่ไม่ตรง) -c นับ -r ค้นทั้งโฟลเดอร์ -l แสดงแค่ชื่อไฟล์ -w ตรงทั้งคำ -o แสดงเฉพาะส่วนที่ตรง และ -E ใช้ Regex แบบขยาย
  • Regex พื้นฐาน: ^ ต้นบรรทัด $ ท้ายบรรทัด . ตัวอักษรใดก็ได้ 1 ตัว * ซ้ำ 0 ครั้งขึ้นไป + ซ้ำ 1 ครั้งขึ้นไป ? มีหรือไม่มีก็ได้ [0-9] ตัวเลข 1 ตัว และ (a|b) a หรือ b (สามตัวหลังต้องใช้ grep -E)
  • sort เรียง: -n ตัวเลข -r กลับด้าน -k เลือกช่อง -t ตัวแบ่งช่อง -u ตัดซ้ำ -h ขนาดแบบ 1K 2M uniq ตัดบรรทัดซ้ำ ที่อยู่ติดกัน จึงต้อง sort ก่อนเสมอ -c นับจำนวน -d แสดงเฉพาะที่ซ้ำ
  • cut ตัดช่อง (-d, ตัวแบ่ง -f3 ช่องที่ 3) tr แปลงหรือลบตัวอักษร (tr 'a-z' 'A-Z', -d ลบ, -s บีบตัวซ้ำ)
  • sed แก้ข้อความแบบสตรีม: s/เก่า/ใหม่/ แทนที่ครั้งแรกของบรรทัด /g ทุกครั้ง /pattern/d ลบบรรทัด -n '2,4p' พิมพ์บรรทัด 2 ถึง 4 และ -i.bak แก้ไฟล์จริงพร้อมสำรองไฟล์เดิม
  • awk ภาษาเล็ก ๆ สำหรับข้อมูลเป็นคอลัมน์: $1 ช่องแรก -F',' ตัวแบ่ง NR เลขบรรทัด NR>1 ข้ามหัวตาราง และบล็อก END ทำงานตอนจบ ใช้หาผลรวมและค่าเฉลี่ย บน Ubuntu 24.04 คำสั่ง awk คือ mawk 1.3.4 ให้เขียนแบบ POSIX awk ไม่ใช้ความสามารถเฉพาะของ gawk
  • find ค้นหาไฟล์ตามเงื่อนไข: -name / -iname ชื่อ -type f ไฟล์ -type d โฟลเดอร์ -size +10M ขนาด -mtime -7 แก้ไขภายใน 7 วัน -exec cmd {} \; รันคำสั่งกับทุกไฟล์ที่พบ และ -delete ลบ (ต้องรันแบบไม่มี -delete ดูผลก่อนเสมอ)
  • xargs แปลงรายการจาก stdin เป็น Argument ของคำสั่ง ใช้คู่ find -print0 | xargs -0 เพื่อให้ชื่อไฟล์ที่มีช่องว่างปลอดภัย

Environment Variables, PATH, ~/.bashrc และ alias

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

ตัวแปรใน Shell มี 2 แบบ Shell Variable (CITY=Bangkok) อยู่เฉพาะใน Shell ปัจจุบัน ส่วน Environment Variable คือตัวแปรที่ถูก export แล้ว โปรแกรมลูก (Child Process) ทุกตัวที่ Shell เปิดจะได้รับสำเนาไปด้วย โปรแกรมจำนวนมากอ่านการตั้งค่าจาก Environment Variable เช่น EDITOR บอกว่าใช้ Editor ตัวไหน LANG บอกภาษาและ Encoding และแอปของเราอ่าน API Key จาก Environment Variable แทนการเขียนลงในโค้ด ดูทั้งหมดด้วย env หรือ printenv ตัวแปรที่ควรรู้จัก: $HOME, $USER, $SHELL, $PWD, $LANG และรูปแบบ ${VAR:-default} ซึ่งใช้ค่า default เมื่อ VAR ว่างหรือไม่มี

PATH คือรายการโฟลเดอร์คั่นด้วย : เมื่อพิมพ์ ls Bash จะไล่หาไฟล์ชื่อ ls ในแต่ละโฟลเดอร์จาก ซ้ายไปขวา เจอที่แรกก็ใช้ตัวนั้น ถ้าไม่เจอเลยจะขึ้น command not found (ตรวจด้วย which หรือ type -a) โปรแกรมส่วนตัวควรอยู่ใน ~/.local/bin ซึ่ง ~/.profile ของ Ubuntu เพิ่มเข้า PATH ให้ตอน Login ถ้าโฟลเดอร์นั้นมีอยู่แล้ว ถ้าเพิ่งสร้างให้ใช้ export PATH="$HOME/.local/bin:$PATH"

  • ~/.bashrc ทำงานทุกครั้งที่เปิด Terminal แบบโต้ตอบ เป็นที่ใส่ alias, function, PS1 (หน้าตา Prompt) และ HISTCONTROL / HISTTIMEFORMAT (การเก็บประวัติคำสั่ง)
  • ~/.profile ทำงานตอน Login เหมาะกับ export ค่า PATH และ /etc/environment เป็นค่าของทั้งระบบทุกผู้ใช้ (ต้องใช้ sudo)
  • source ~/.bashrc โหลดไฟล์ใหม่ใน Shell ปัจจุบันโดยไม่ต้องเปิด Terminal ใหม่ alias ชื่อ='คำสั่ง' ตั้งชื่อย่อ unalias ลบ และ function ใช้เมื่อต้องรับ Argument
  • WSL เชื่อม Windows ให้: code . เปิด VS Code explorer.exe . เปิดโฟลเดอร์ใน File Explorer clip.exe คัดลอกลง Clipboard wslpath -w แปลง Path เป็นแบบ Windows และ WSL ต่อ PATH ของ Windows (เช่น /mnt/c/Windows/system32) ไว้ท้าย PATH ของ Linux
  • ไฟล์ที่สร้างด้วย Notepad บน Windows ใช้ตัวขึ้นบรรทัดแบบ CRLF (\r\n) ถ้านำมาเป็น Script ใน Linux จะเจอ $'\r': command not found

ใช้แนวคิดนี้เมื่อติดตั้งเครื่องมือแล้วเรียกไม่เจอ ต้องการทำให้คำสั่งยาว ๆ สั้นลง เก็บค่าลับไว้นอกโค้ด (ใส่ในไฟล์ .env และเพิ่ม .env ใน .gitignore ตามที่จะเรียนใน ) หรือแก้ปัญหา "บนเครื่องเรารันได้ แต่ใน cron รันไม่ได้" ซึ่งเกือบทุกครั้งเกิดจาก PATH ต่างกัน

Processes, Signals และ Job Control (ps, top, kill, jobs, nohup)

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Process คือโปรแกรมที่กำลังทำงาน แต่ละตัวมีหมายเลขประจำตัว PID และรู้ว่าใครเปิดมันขึ้นมาผ่าน PPID (PID ของพ่อแม่) Process มีสถานะ (STAT) เช่น R กำลังใช้ CPU, S หลับรอเหตุการณ์ (สถานะที่พบบ่อยที่สุด), T ถูกหยุดชั่วคราว, Z Zombie (จบแล้วแต่พ่อแม่ยังไม่เก็บกวาด) และ D รอ Disk ที่ขัดจังหวะไม่ได้ เมื่อเว็บช้า เครื่องร้อน หรือโปรแกรมค้าง ผู้ดูแลระบบต้องหาให้เจอว่า Process ไหนเป็นต้นเหตุ แล้วสั่งให้หยุดอย่างถูกวิธี

  • ดู Process: ps aux (ทุกตัว พร้อม %CPU %MEM) ps -ef (มี PPID) ps -o pid,ppid,stat,etime,cmd -p PID (เลือกคอลัมน์เอง) pgrep -a ชื่อ หา PID จากชื่อ และ pkill ชื่อ ส่ง Signal ตามชื่อ
  • ดูแบบสด: top (กด P เรียงตาม CPU, M เรียงตาม Memory, q ออก) และ htop 3.3.0 ที่ใช้ง่ายกว่า (F3 ค้นหา, F6 เลือกการเรียง, F9 ส่ง Signal)
  • Signal คือข้อความสั้นที่ส่งถึง Process: SIGINT (2) เกิดจาก Ctrl+C, SIGTERM (15) ค่าเริ่มต้นของ kill ขอให้ปิดอย่างเรียบร้อย, SIGKILL (9) บังคับตายทันที โปรแกรมดักไม่ได้และไม่มีโอกาสเก็บกวาด จึงใช้เป็นทางสุดท้าย, SIGHUP (1) ส่งเมื่อปิด Terminal และ SIGTSTP เกิดจาก Ctrl+Z หยุดชั่วคราว ดูรายการทั้งหมดด้วย kill -l
  • Job Control: ใส่ & ท้ายคำสั่งให้ทำงานเบื้องหลัง jobs ดูงานของ Terminal นี้ fg %1 ดึงงานที่ 1 กลับมาข้างหน้า bg %1 ให้งานที่หยุดอยู่ทำต่อเบื้องหลัง nohup ทำให้งานไม่ตายเมื่อปิด Terminal และ disown ปล่อยงานที่รันอยู่ให้เป็นอิสระจาก Shell สำหรับงานยาวที่ต้องกลับมาดูภายหลัง tmux 3.4 สะดวกที่สุด
  • ใน Script ใช้ trap ดัก Signal เพื่อเก็บกวาด (ลบไฟล์ชั่วคราว ปิดการเชื่อมต่อ) ก่อนจบ
  • สุขภาพเครื่อง: free -h ดู RAM uptime ดู Load Average ของ 1, 5, 15 นาที (เทียบกับจำนวน CPU จาก nproc ถ้า Load สูงกว่าจำนวน CPU นาน ๆ แปลว่างานล้น) และข้อมูลดิบอยู่ใน /proc/loadavg
เปรียบเทียบ

Process เหมือนพนักงานในร้านอาหาร PID คือเลขบัตรพนักงาน PPID คือเลขของหัวหน้าที่จ้างมา Signal คือวิธีสื่อสาร: SIGTERM คือบอกว่า "ช่วยเก็บโต๊ะแล้วเลิกงานได้" พนักงานเก็บของให้เรียบร้อยก่อนกลับ SIGKILL คือเรียก รปภ. ลากออกจากร้านทันที จานยังวางค้างอยู่บนโต๊ะ และ nohup คือบอกพนักงานว่า "ถึงผู้จัดการกะกลับบ้านแล้วก็ทำงานต่อไป"

ตัวอย่างโค้ด

สร้างงานจำลอง worker.sh ที่เขียน heartbeat ลง Log ทุกวินาที และปิดตัวอย่างเรียบร้อยเมื่อได้รับ SIGTERM หรือ SIGINT

#!/usr/bin/env bash
# worker.sh: งานจำลองที่ทำงานไปเรื่อย ๆ และปิดตัวอย่างปลอดภัยเมื่อได้รับสัญญาณ
set -euo pipefail

LOG_FILE="worker.log"
TMP_FILE="/tmp/worker-$$.tmp"

cleanup() {
    rm -f -- "$TMP_FILE"
    echo "$(date +%T) ลบไฟล์ชั่วคราวแล้ว" >> "$LOG_FILE"
}

trap 'echo "$(date +%T) ได้รับสัญญาณ TERM กำลังปิดอย่างปลอดภัย" >> "$LOG_FILE"; cleanup; exit 0' TERM
trap 'echo "$(date +%T) ได้รับสัญญาณ INT (Ctrl+C) กำลังปิด" >> "$LOG_FILE"; cleanup; exit 130' INT

echo "$(date +%T) เริ่มทำงาน PID=$$" >> "$LOG_FILE"
touch "$TMP_FILE"
count=0
while true; do
    count=$((count + 1))
    echo "$(date +%T) heartbeat $count" >> "$LOG_FILE"
    sleep 1
done
cd ~/projects/linux-lab/c09
chmod +x worker.sh

# รันเบื้องหลังด้วย nohup เก็บ stdout และ stderr ไว้ใน worker.out
nohup ./worker.sh > worker.out 2>&1 &
# $! คือ PID ของงานเบื้องหลังล่าสุด เก็บไว้ในตัวแปร
PID=$!
echo "PID=$PID"
sleep 3

# ดูรายละเอียด Process และหาด้วยชื่อ
ps -o pid,ppid,stat,etime,cmd -p "$PID"
pgrep -af worker.sh

# ส่ง SIGTERM (ค่าเริ่มต้นของ kill) แล้วรอให้ปิดตัว
kill "$PID"
sleep 1.5
tail -n 3 worker.log
ps -p "$PID" > /dev/null || echo "process $PID จบแล้ว"

  • Script ที่สร้างไฟล์ชั่วคราวหรือ Lock ต้องมี trap สำหรับ TERM, INT และ EXIT เพื่อเก็บกวาดเสมอ
  • เก็บ PID ด้วย $! หรือ pgrep แทนการคัดลอกตัวเลขด้วยตา และระวัง pkill -f ที่อาจจับ Process อื่นที่มีคำเดียวกันใน Command Line
  • งานที่ต้องรันตลอดและเริ่มใหม่เองเมื่อพัง ไม่ควรใช้ nohup ให้ทำเป็น systemd Service ซึ่งมี Log และ Restart ในตัว

ฝึกส่ง Signal แบบต่าง ๆ ให้ worker.sh

  1. รัน ./worker.sh แบบปกติ (ไม่มี &) รอ 3 วินาทีแล้วกด Ctrl+C จากนั้นดู tail -n 3 worker.log และ echo $? (ควรได้ 130)
  2. รันเบื้องหลังอีกครั้ง แล้วส่ง kill -9 PID ดูว่า Log ไม่มีบรรทัดปิดงาน และตรวจไฟล์ค้างด้วย ls /tmp/worker-*.tmp แล้วลบทิ้งเอง
  3. รัน sleep 500 กด Ctrl+Z ใช้ jobs ดูสถานะ bg %1 ให้ทำต่อเบื้องหลัง แล้ว kill %1
  4. เปิด htop กด F3 ค้น sleep แล้วใช้ F9 ส่ง SIGTERM
  5. รัน nproc, uptime และ free -h แล้วสรุปว่าเครื่องของคุณ Load เทียบกับจำนวน CPU เป็นอย่างไร
แนวคิดที่ 10Advanced

Services ด้วย systemd: systemctl, journalctl และ Log ใน /var/log

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Service (หรือ Daemon) คือโปรแกรมที่ทำงานเบื้องหลังตลอดเวลา เช่น Web Server, ฐานข้อมูล, SSH Server และ cron บน Ubuntu ผู้จัดการ Service คือ systemd ซึ่งเป็น Process หมายเลข 1 (PID 1) ตัวแรกที่เริ่มเมื่อเปิดเครื่อง หน้าที่ของ systemd คือเปิด Service ตามลำดับที่ถูกต้อง เริ่มใหม่ให้เมื่อพัง และเก็บ Log ของทุก Service ไว้ในที่เดียวเรียกว่า Journal Service แต่ละตัวอธิบายด้วยไฟล์ Unit นามสกุล .service ไฟล์ของแพ็กเกจอยู่ใน /usr/lib/systemd/system/ และไฟล์ที่เราเขียนเองอยู่ใน /etc/systemd/system/

  • WSL: Ubuntu 24.04 บน WSL เปิด systemd ให้เป็นค่าเริ่มต้นผ่านไฟล์ /etc/wsl.conf ส่วน [boot] บรรทัด systemd=true ตรวจด้วย ps -p 1 -o comm= ถ้าได้ systemd ก็พร้อม ถ้าได้ init ให้เพิ่มบรรทัดนั้นด้วย sudo nano /etc/wsl.conf แล้วรัน wsl --shutdown ใน PowerShell และเปิด Ubuntu ใหม่
  • systemctl status ดูสถานะ start / stop / restart เปิด ปิด เริ่มใหม่ reload ให้อ่าน Config ใหม่โดยไม่หยุด (ถ้า Service รองรับ) enable / disable ให้เปิดหรือไม่เปิดเองตอนบูต (enable --now ทำทั้ง enable และ start) is-active / is-enabled ตอบคำเดียวเหมาะกับ Script --failed ดู Service ที่พัง list-units --type=service --state=running ดูที่กำลังทำงาน และ daemon-reload ให้ systemd อ่านไฟล์ Unit ใหม่หลังแก้
  • journalctl -u ชื่อ ดู Log ของ Service -n 20 20 บรรทัดล่าสุด -f ดูสด --since "10 min ago" ตามเวลา -p err เฉพาะระดับ Error ขึ้นไป -b ตั้งแต่บูตครั้งนี้ และ --no-pager พิมพ์ออกมาตรง ๆ ไม่เปิด less
  • /var/log ยังมีไฟล์ Log แบบข้อความ เช่น apt/history.log (ประวัติการติดตั้ง) และ dpkg.log ส่วน syslog และ auth.log จะมีเฉพาะเมื่อติดตั้ง rsyslog ข้อความของ Kernel ดูด้วย sudo dmesg
  • ถ้าไม่มี systemd จะใช้คำสั่งรุ่นเก่า sudo service cron status / start / stop แทนได้

ใช้แนวคิดนี้เมื่อติดตั้งโปรแกรมแบบ Server แล้วต้องตรวจว่าทำงานไหม ต้องการให้แอปของตัวเองทำงานตลอดและเริ่มใหม่เองเมื่อพัง หรือตามหาสาเหตุที่ Service เปิดไม่ขึ้น ซึ่งคำตอบเกือบทุกครั้งอยู่ใน journalctl -u

เปรียบเทียบ

systemd เหมือนผู้จัดการอาคาร Service คือร้านค้าในอาคาร ไฟล์ Unit คือสัญญาเช่าที่ระบุว่าร้านเปิดกี่โมง ต้องรอร้านไหนเปิดก่อน และถ้าร้านปิดกะทันหันให้เปิดใหม่ไหม enable คือการลงชื่อให้เปิดร้านอัตโนมัติทุกเช้า start คือสั่งเปิดตอนนี้เลย และ journalctl คือสมุดบันทึกเหตุการณ์ของ รปภ. ที่จดทุกอย่างของทุกร้านไว้เล่มเดียว

Best Practice
  • อ่าน systemctl status และ journalctl -u ชื่อ -n 50 --no-pager ก่อนแก้อะไรทุกครั้งที่ Service มีปัญหา
  • เขียนไฟล์ Unit ให้ Service รันด้วยผู้ใช้ที่ไม่ใช่ root ใช้ Path เต็ม และมี Restart=on-failure
  • หลังแก้ Config ของ Service ให้ทดสอบ Syntax ก่อน (เช่น sudo nginx -t, sudo sshd -t) แล้วใช้ reload ถ้า Service รองรับ เพื่อไม่ตัดผู้ใช้ที่เชื่อมต่ออยู่
  • บน WSL ทุก Service หยุดเมื่อ WSL ปิด (เช่นหลัง wsl --shutdown หรือ Windows รีสตาร์ต) งานที่ต้องทำงานตลอดจริงควรอยู่บน Server หรือ Cloud

ปรับ Service hello-web

  1. เปลี่ยน Port ในไฟล์ Unit เป็น 8081 รัน daemon-reload แล้ว restart และทดสอบด้วย curl -s localhost:8081
  2. เปิดหน้าเว็บ http://localhost:8081 ในเบราว์เซอร์ของ Windows (WSL ส่งต่อ localhost ให้) แล้วดูบรรทัดใหม่ใน journalctl -u hello-web -f
  3. ทดสอบ Restart: หา Main PID แล้วส่ง sudo kill -9 PID รอ 3 วินาที ดู systemctl status ว่า PID ใหม่ขึ้นมาเองหรือไม่
  4. รัน systemctl list-units --type=service --state=running --no-pager แล้วเลือก Service 3 ตัวที่ไม่รู้จักมาอ่าน Description
  5. รัน journalctl -p err -b --no-pager | tail -n 10 ดู Error ตั้งแต่บูตครั้งนี้ แล้วปิดงานด้วย sudo systemctl disable --now hello-web และ sudo rm /etc/systemd/system/hello-web.service ตามด้วย sudo systemctl daemon-reload

งานเกือบทุกสายต้องสื่อสารผ่านเครือข่าย IP Address คือที่อยู่ของเครื่อง Port คือหมายเลขช่องทางของแต่ละโปรแกรมในเครื่องเดียวกัน (เว็บ 80/443, SSH 22, PostgreSQL 5432) DNS แปลงชื่ออย่าง ubuntu.com เป็น IP และ localhost (127.0.0.1) คือเครื่องตัวเอง คำสั่งที่ใช้ตรวจเครือข่ายบน Ubuntu:

  • ip -br a ดู IP ของแต่ละการ์ดแบบสั้น (ip a แบบละเอียด) ip route ดูเส้นทาง โดย default via คือ Gateway และ hostname -I แสดงเฉพาะ IP
  • ping -c 3 host ทดสอบว่าติดต่อถึงไหม curl -I ดูเฉพาะ Header ของเว็บ curl -s ไม่แสดงแถบความคืบหน้า curl -o file บันทึกลงไฟล์ และ wget ดาวน์โหลดไฟล์
  • ss -tulpn ดูว่าโปรแกรมไหนรอรับการเชื่อมต่อ (Listen) ที่ Port ใด (t TCP, u UDP, l Listen, p ชื่อโปรแกรม ต้องใช้ sudo จึงจะเห็นของผู้ใช้อื่น, n แสดงเป็นตัวเลข)
  • dig ubuntu.com, dig +short ubuntu.com และ nslookup (จาก bind9-dnsutils 9.18) ถาม DNS ส่วน /etc/hosts กำหนดชื่อเองในเครื่อง และ /etc/resolv.conf บอกว่าใช้ DNS Server ไหน (บน WSL ไฟล์นี้ถูกสร้างอัตโนมัติ มักเป็น nameserver 10.255.255.254 เมื่อเปิด DNS Tunneling ค่าต่างกันได้)
  • เครือข่ายของ WSL2: ค่าเริ่มต้นเป็นแบบ NAT การ์ด eth0 ได้ IP วง 172.x.x.x/20 ซึ่งต่างจาก IP ของ Windows แต่ WSL ส่งต่อ localhost ให้ เปิดเว็บใน WSL ที่ Port 8000 แล้วเข้า http://localhost:8000 จากเบราว์เซอร์ Windows ได้ทันที บน Windows 11 เลือกโหมด Mirrored ได้ด้วย networkingMode=mirrored ใต้ [wsl2] ในไฟล์ %UserProfile%\.wslconfig

SSH คือการเข้าใช้ Terminal ของเครื่องอื่นอย่างปลอดภัยผ่านการเข้ารหัส เป็นวิธีหลักที่ใช้ดูแล Server และใช้ส่งโค้ดขึ้น GitHub แทนการพิมพ์รหัสผ่าน เราใช้ SSH Key ซึ่งมี 2 ไฟล์: Private Key (เก็บไว้กับตัว ห้ามให้ใคร) และ Public Key (นามสกุล .pub นำไปวางในไฟล์ ~/.ssh/authorized_keys ของเครื่องปลายทาง) คำสั่งที่เกี่ยวข้อง: ssh-keygen -t ed25519 สร้าง Key, ssh-copy-id ส่ง Public Key ไปปลายทาง, ssh-agent / ssh-add จำ Passphrase ไว้ระหว่างใช้งาน, ~/.ssh/config ตั้งชื่อย่อให้ Server, scp คัดลอกไฟล์ และ rsync -avz ซิงก์โฟลเดอร์ ฝั่ง Server บน Ubuntu 24.04 ใช้ openssh-server 9.6p1 ซึ่งเปิดรับการเชื่อมต่อผ่าน ssh.socket (Socket Activation)

Security

ฝึก SSH, การสแกน Port และคำสั่งเครือข่ายทั้งหมด เฉพาะกับ localhost หรือเครื่องที่คุณเป็นเจ้าของ การเข้าถึงหรือทดลองกับระบบของผู้อื่นโดยไม่ได้รับอนุญาตเป็นความผิดตาม พ.ร.บ.ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ และห้ามส่ง Private Key (ไฟล์ที่ไม่มี .pub) ให้ใครหรืออัปโหลดขึ้น GitHub เด็ดขาด

เปรียบเทียบ

IP คือบ้านเลขที่ Port คือหมายเลขห้องในบ้าน DNS คือสมุดโทรศัพท์ที่แปลงชื่อเป็นบ้านเลขที่ ส่วน SSH Key เหมือนแม่กุญแจกับลูกกุญแจ Public Key คือแม่กุญแจที่แจกไปติดประตูได้หลายบ้าน (ใครเห็นก็ไม่เป็นไร) Private Key คือลูกกุญแจดอกเดียวที่เปิดแม่กุญแจเหล่านั้นได้ และ Passphrase คือรหัสของกล่องที่เก็บลูกกุญแจอีกชั้น

Best Practice
  • ใช้ Key ชนิด ed25519 พร้อม Passphrase และใช้ ssh-agent แทนการสร้าง Key ที่ไม่มี Passphrase
  • เมื่อ Login ด้วย Key ได้แล้ว ให้ปิดการ Login ด้วยรหัสผ่านและห้าม root Login: สร้างไฟล์ /etc/ssh/sshd_config.d/99-hardening.conf ใส่ PasswordAuthentication no และ PermitRootLogin no ตรวจด้วย sudo sshd -t แล้ว sudo systemctl restart ssh (เปิด Terminal ที่ Login ค้างไว้ 1 หน้าต่างเผื่อตั้งผิด)
  • ใช้ ~/.ssh/config ตั้งชื่อย่อให้ทุก Server แทนการจำ IP และ User
  • เวลาแก้ปัญหาเครือข่าย ไล่จากล่างขึ้นบน: มี IP ไหม (ip -br a) ไป Gateway ได้ไหม (ping) แปลชื่อได้ไหม (dig) Port เปิดไหม (ss) แอปตอบไหม (curl -v) รายละเอียดเพิ่มเติมอยู่ในหัวข้อ

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Bash Script คือไฟล์ที่รวมคำสั่งทั้งหมดที่เรียนมาไว้ด้วยกัน เพื่อให้งานที่ทำซ้ำ (สำรองข้อมูล ตรวจเครื่อง Deploy แอป) ทำได้ในคำสั่งเดียวและได้ผลเหมือนเดิมทุกครั้ง cron คือ Service ที่รัน Script ตามเวลาที่กำหนดโดยไม่ต้องมีคนกด สองอย่างนี้รวมกันคือพื้นฐานของ Automation ที่ผู้ดูแลระบบ DevOps และ Backend Developer ใช้ทุกวัน Script ที่ เชื่อถือได้ ต้องหยุดเมื่อเกิดข้อผิดพลาด บอกผู้ใช้ชัดเจนว่าผิดอะไร และคืน Exit code ที่ถูกต้อง

  • โครงพื้นฐาน: บรรทัดแรก #!/usr/bin/env bash (Shebang) ตามด้วย set -euo pipefail (Strict Mode): -e หยุดเมื่อคำสั่งล้มเหลว -u หยุดเมื่อใช้ตัวแปรที่ไม่ได้กำหนด -o pipefail ให้ Pipe ล้มเหลวถ้าคำสั่งใดในสายล้มเหลว
  • ตัวแปรและ Quoting: ใส่ "$var" ในเครื่องหมายคำพูดคู่เสมอ $(คำสั่ง) นำผลคำสั่งมาใช้ $(( 2 + 3 )) คำนวณเลขจำนวนเต็ม ${var:-default} ค่าเริ่มต้น ${var:?ข้อความ} หยุดพร้อมข้อความถ้าไม่มีค่า และ readonly ทำให้เปลี่ยนค่าไม่ได้
  • Argument: $0 ชื่อ Script $1 $2 ตัวที่ 1 และ 2 $# จำนวน Argument "$@" ทุกตัวโดยรักษาช่องว่างในแต่ละตัว
  • เงื่อนไขและลูป: if [[ -d "$dir" ]]; then ... fi โดย -d โฟลเดอร์มีจริง -f ไฟล์มีจริง -z ข้อความว่าง -n ไม่ว่าง -eq / -gt / -lt เปรียบเทียบตัวเลข =~ ตรวจด้วย Regex ส่วน case ใช้แยกหลายกรณี for x in ...; do ... done และ while read -r line; do ... done อ่านทีละบรรทัด
  • Function และ Exit code: name() { local x=...; } ใช้ local ให้ตัวแปรอยู่เฉพาะใน Function $? คือ Exit code ของคำสั่งล่าสุด (0 = สำเร็จ) exit 1 จบพร้อมรหัส ข้อความ Error ส่งออก stderr ด้วย >&2 และ trap 'cleanup' EXIT เก็บกวาดทุกครั้งที่จบ
  • เครื่องมือคุณภาพ: shellcheck 0.9.0 ตรวจหาบั๊กที่พบบ่อยก่อนรัน และ bash -x script.sh แสดงทุกคำสั่งที่รันจริงพร้อมค่าตัวแปร ใช้ไล่หาจุดผิด
  • Disk และ Archive: tar -czf a.tar.gz -C parent dir สร้าง tar -tzf ดูรายการข้างใน tar -xzf a.tar.gz -C dest แตกไฟล์ df -h ดูพื้นที่ Disk และ du -sh ดูขนาดโฟลเดอร์
  • cron: แก้ตารางงานด้วย crontab -e ดูด้วย crontab -l แต่ละบรรทัดมี 5 ช่องเวลา นาที ชั่วโมง วันที่ เดือน วันในสัปดาห์ ตามด้วยคำสั่ง เช่น 0 2 * * * คือตี 2 ทุกวัน และ */5 * * * * คือทุก 5 นาที

ข้อควรรู้ของ cron: (1) cron ใช้ PATH สั้นมาก (/usr/bin:/bin) จึงต้องใช้ Path เต็มของทุกไฟล์และโปรแกรม (2) ไม่มี Terminal ให้แสดงผล ต้องเก็บ Log เองด้วย >> file.log 2>&1 (3) เครื่องหมาย % ใน crontab มีความหมายพิเศษ (ขึ้นบรรทัดใหม่) ต้องเขียนเป็น \% (4) บน WSL Service cron ต้องทำงานอยู่ และ WSL ต้องเปิดอยู่ ถ้าปิด WSL งานจะไม่รัน ตรวจว่างานรันจริงด้วย journalctl -u cron หรือ grep CRON /var/log/syslog (ถ้ามี rsyslog)

เปรียบเทียบ

Script เหมือนสูตรอาหารที่เขียนละเอียดจนใครทำก็ได้รสเดียวกัน Strict Mode คือกฎในครัวว่า "ถ้าขั้นไหนพลาด ให้หยุดทำทันที อย่าเสิร์ฟจานที่ไหม้" ShellCheck คือเชฟอาวุโสที่อ่านสูตรก่อนแล้วชี้จุดที่จะพัง ส่วน cron คือนาฬิกาปลุกที่ตั้งให้เปิดเตาอบตอนตี 2 ทุกวัน แต่นาฬิกานี้ทำงานเฉพาะเมื่อไฟในครัวเปิดอยู่ (WSL ต้องทำงาน)

#!/usr/bin/env bash
# backup.sh: สำรองโฟลเดอร์เป็นไฟล์ .tar.gz และเก็บไว้แค่ N ไฟล์ล่าสุด
# วิธีใช้: backup.sh <source_dir> [keep]
set -euo pipefail

readonly BACKUP_DIR="$HOME/backups"
readonly DEFAULT_KEEP=5

# พิมพ์ข้อความพร้อมวันเวลา
log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*"
}

# พิมพ์ข้อความผิดพลาดออกทาง stderr
err() {
    log "ERROR: $*" >&2
}

usage() {
    echo "วิธีใช้: $(basename "$0") <source_dir> [keep]" >&2
    echo "  keep = จำนวนไฟล์สำรองที่จะเก็บไว้ (ค่าเริ่มต้น $DEFAULT_KEEP)" >&2
}

main() {
    # ตรวจจำนวน Argument: ต้องมี 1 หรือ 2 ตัว
    if [[ $# -lt 1 || $# -gt 2 ]]; then
        usage
        exit 2
    fi

    local src="$1"
    local keep="${2:-$DEFAULT_KEEP}"

    if [[ ! -d "$src" ]]; then
        err "ไม่พบโฟลเดอร์: $src"
        exit 1
    fi
    if [[ ! "$keep" =~ ^[0-9]+$ || "$keep" -lt 1 ]]; then
        err "keep ต้องเป็นจำนวนเต็มตั้งแต่ 1 ขึ้นไป: $keep"
        exit 1
    fi

    mkdir -p "$BACKUP_DIR"

    local name parent stamp archive
    name="$(basename "$src")"
    parent="$(cd "$(dirname "$src")" && pwd)"
    stamp="$(date +%Y%m%d-%H%M%S)"
    archive="$BACKUP_DIR/${name}-${stamp}.tar.gz"

    log "เริ่มสำรอง $src"
    tar -czf "$archive" -C "$parent" "$name"
    log "สร้างไฟล์ $archive"

    # ลบไฟล์เก่าที่เกินจำนวน keep
    # ชื่อไฟล์มีวันเวลาแบบ YYYYMMDD-HHMMSS จึงเรียงชื่อจากมากไปน้อย = ใหม่ไปเก่า
    local old
    find "$BACKUP_DIR" -maxdepth 1 -name "${name}-*.tar.gz" | sort -r | tail -n +"$((keep + 1))" | while read -r old; do
        rm -- "$old"
        log "ลบไฟล์เก่า $(basename "$old")"
    done

    log "เสร็จ ขนาด $(du -h "$archive" | cut -f1) เก็บไว้ $keep ไฟล์ล่าสุด"
}

main "$@"
cd ~/projects/linux-lab/c12

# ให้สิทธิ์รัน และตรวจด้วย ShellCheck

Best Practice
  • ทุก Script เริ่มด้วย Shebang และ set -euo pipefail ใส่เครื่องหมายคำพูดรอบตัวแปรทุกตัว และผ่าน shellcheck ก่อน Commit
  • ตรวจ Input ทุกตัว แสดงวิธีใช้เมื่อเรียกผิด ส่ง Error ไป stderr และคืน Exit code ที่มีความหมาย (0 สำเร็จ ไม่ใช่ 0 ล้มเหลว) เพื่อให้ cron, CI และ Script อื่นนำไปตัดสินใจต่อได้
  • สำรอง crontab ก่อนแก้ ใช้ Path เต็ม เก็บ Log ของทุกงาน และทดสอบคำสั่งในบรรทัด cron ด้วยมือก่อนตั้งเวลาจริง
  • ไฟล์สำรองที่อยู่เครื่องเดียวกับต้นฉบับยังไม่ใช่การสำรองที่ดีพอ ในงานจริงต้องส่งสำเนาไปอีกที่ด้วย (กฎ 3-2-1: 3 สำเนา 2 สื่อ 1 ที่อยู่นอกสถานที่) และต้องลองกู้คืนเป็นระยะ
