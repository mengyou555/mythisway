Multiple Choice

เลือกคำตอบที่ถูกต้องที่สุดเพียงข้อเดียว แต่ละข้อมี 4 ตัวเลือก เฉลยพร้อมเหตุผลของทุกตัวเลือกอยู่ท้ายหน้า

  1. ง่าย

    คำสั่ง git add menu.md ทำอะไร

    1. ส่งไฟล์ menu.md ขึ้น GitHub ทันที
    2. นำสภาพปัจจุบันของ menu.md จาก Working Tree เข้า Staging Area เพื่อเตรียม commit
    3. สร้าง commit ใหม่ที่มี menu.md อยู่ข้างใน
    4. สั่งให้ Git เลิกติดตามไฟล์ menu.md
  2. ง่าย

    สมชายเพิ่มบรรทัด มอคค่า 70 บาท ใน menu.md แล้วรันคำสั่งด้านล่าง แต่ git diff ไม่แสดงอะไรเลย เกิดอะไรขึ้น และต้องใช้คำสั่งใดจึงจะเห็นความเปลี่ยนแปลง

    git add menu.md
git diff
    1. ไฟล์ไม่ได้ถูกแก้ไขจริง เพราะ git add ยกเลิกการแก้ไขไปแล้ว
    2. ต้องใช้ git log เท่านั้น เพราะ git diff ใช้ได้กับไฟล์ที่ commit แล้วเท่านั้น
    3. git diff เทียบ Working Tree กับ Staging Area ซึ่งตอนนี้เหมือนกันแล้ว ต้องใช้ git diff --staged
    4. Repository เสีย ต้องรัน git init ใหม่
  3. กลาง

    สมชายสร้าง feature/contact จาก main แล้ว commit 1 ครั้ง ระหว่างนั้นไม่มีใครเพิ่ม commit ใดบน main เลย เมื่อเขาสลับกลับไปที่ main แล้วรัน git merge feature/contact จะเกิดอะไรขึ้น

    1. Fast-forward: Git เลื่อน pointer ของ main ไปที่ commit ล่าสุดของ feature/contact โดยไม่สร้าง merge commit
    2. Git สร้าง merge commit ใหม่ด้วย strategy ort ทุกครั้ง ไม่ว่าประวัติจะเป็นอย่างไร
    3. เกิด Merge Conflict เพราะสอง Branch มีไฟล์ไม่เท่ากัน
    4. Git จะ rebase feature/contact ลงบน main และเปลี่ยน hash ของทุก commit
  4. ง่าย

    สมชายแก้ราคาลาเต้ในไฟล์เมนูที่เคยผิดให้ถูกต้อง ข้อความ commit ใดเขียนตามรูปแบบ Conventional Commits 1.0.0 ได้ถูกต้องที่สุด

    1. update
    2. Fixed the price!!!
    3. fix update latte price
    4. fix(menu): correct latte price to 65 baht
  5. กลาง

    สมชายรัน git push แล้วได้ผลลัพธ์ด้านล่าง (ผลจริงจาก Remote จำลอง) ขั้นตอนถัดไปที่ถูกต้องที่สุดคืออะไร

    1. รัน git push --force ทันที เพราะงานของเราใหม่กว่า
    2. ลบโฟลเดอร์ทิ้ง clone ใหม่ แล้วพิมพ์งานของตัวเองใหม่ทั้งหมด
    3. รัน git commit --amend แล้ว push อีกครั้ง
    4. รัน git pull เพื่อดึงงานของเพื่อนมารวม แก้ conflict ถ้ามี แล้วจึง git push
  6. ยาก

    ตาม "กฎทองของ Rebase" สถานการณ์ใดที่ใช้ git rebase ได้อย่างปลอดภัย

    1. rebase Branch main ที่ทุกคนในทีม pull ไปแล้ว จากนั้น force push
    2. rebase Branch feature/login ที่เพื่อนอีก 2 คน push commit เข้ามาทำงานร่วมด้วย
    3. rebase Branch feature/about ที่คุณสร้างเองในเครื่องและยังไม่เคย push ให้ใคร
    4. rebase Branch release/1.0 ที่ใช้สร้าง Release ส่งให้ลูกค้าไปแล้ว

    commit feat: add broken banner ถูก push ขึ้น main และเพื่อนในทีม pull ไปแล้ว ต่อมาพบว่าทำให้หน้าเว็บพัง วิธีใดปลอดภัยที่สุดสำหรับการย้อนการเปลี่ยนแปลงนี้

    1. git revert <hash> แล้ว git push
    2. git reset --hard HEAD~1 แล้ว git push --force
    3. git commit --amend แล้ว git push
    4. git restore index.html
  8. กลาง

    สมชายแก้ README.md ค้างไว้ และสร้างไฟล์ใหม่ notes.md ที่ยังไม่เคย add เลย แล้วหัวหน้าขอให้สลับไปแก้บั๊กด่วนบน Branch อื่น เขาต้องการเก็บงานทั้ง 2 ไฟล์ไว้ชั่วคราวให้ Working Tree สะอาด ควรใช้คำสั่งใด

    1. git stash
    2. git stash -u -m "wip: readme and notes"
    3. git stash pop
    4. git restore .
  9. ยาก

    สมชายรัน git reset --hard HEAD~1 โดยไม่ตั้งใจ ทำให้ commit feat: add mocha (ยังไม่เคย push) หายไปจาก git log เขาจึงดู Reflog ได้ผลด้านล่าง คำสั่งใดนำ commit นั้นกลับมาเป็นปลายของ main ได้

638f7cf HEAD@{1}: commit: feat: add mocha
5c9b6cf (HEAD -> main) HEAD@{2}: commit (initial): feat: add menu
    1. git revert HEAD
    2. git reset --hard HEAD@{1}
    3. git restore menu.md
    4. กู้ไม่ได้แล้ว เพราะ --hard ลบ commit ถาวร
  10. กลาง

    สมชาย fork Repository malee-dev/recipes มาเป็น somchai-dev/recipes แล้ว clone fork ของตัวเองลงเครื่อง (origin ชี้ไปที่ fork) ต่อมามาลีเพิ่ม commit ใหม่ใน Repository ต้นฉบับ สมชายควรทำอย่างไรเพื่อให้ main ในเครื่องได้ commit ใหม่ของมาลี

    1. git remote add upstream <URL ของ malee-dev/recipes> แล้ว git fetch upstream และ git merge upstream/main
    2. git pull origin main เพียงคำสั่งเดียว
    3. git push upstream main
    4. ลบ fork บน GitHub แล้ว fork ใหม่ทุกครั้งที่ต้นฉบับมี commit ใหม่
  11. ยาก

    สมชายเพิ่งพบว่า push ไฟล์ .env ที่มี API key ของจริงขึ้น Public Repository ไปเมื่อ 10 นาทีที่แล้ว สิ่งแรกที่ต้องทำคืออะไร

    1. ลบ .env ใน commit ใหม่แล้ว push ก็เพียงพอ
    2. เปลี่ยน Repository เป็น Private
    3. Revoke หรือ Rotate key นั้นที่ผู้ให้บริการทันที แล้วจึงลบออกจากประวัติและแจ้งทีม
    4. รัน git filter-repo --invert-paths --path .env ลบออกจากประวัติ แล้วถือว่าจบเรื่อง
  12. ยาก

    สมชายสร้างไฟล์ Workflow ด้านล่างแล้ว push ขึ้น GitHub แต่เปิด PR กี่ครั้งก็ไม่เห็น Workflow ทำงานในแท็บ Actions เลย สาเหตุที่เป็นไปได้มากที่สุดคืออะไร

    2. runs-on ต้องเป็น windows-latest เพราะผู้เรียนใช้ Windows

    4. โฟลเดอร์ต้องชื่อ .github/workflows (มีตัว s) แต่ไฟล์นี้อยู่ใน .github/workflow

สถานการณ์

พี่สาวของสมชายเปิดร้านกาแฟและอยากเก็บไฟล์เมนูไว้ใน Git เพื่อดูย้อนหลังได้ว่าเปลี่ยนราคาเมื่อไร ร้านมีไฟล์ .env สำหรับเก็บ API key ของระบบแจ้งเตือนออร์เดอร์ (ในแบบฝึกหัดนี้ใช้ค่าปลอม fake-key-for-lab-only) และโปรแกรมของร้านสร้างไฟล์ app.log ทุกวัน สองไฟล์นี้ห้ามเข้า Repository เด็ดขาด ระหว่างทำงานสมชายยังพลาด 2 ครั้ง คือเผลอ add โน้ตส่วนตัว และพิมพ์ข้อความ commit ผิด ซึ่งต้องแก้ให้เรียบร้อยก่อนส่งงาน

สิ่งที่ต้องทำ
  1. สร้างโฟลเดอร์ ~/projects/git-lab/ch1 แล้วสร้าง Repository ด้วย git init
  2. สร้าง menu.md ที่มี 2 บรรทัดคือ # เมนูร้านกาแฟ และ ลาเต้ 60 บาท แล้ว commit ด้วยข้อความ feat: add menu
  3. สร้างไฟล์ .env (เนื้อหา API_KEY=fake-key-for-lab-only), .env.example (เนื้อหา API_KEY=) และ app.log จากนั้นเขียน .gitignore ให้ Git ไม่สนใจ .env และไฟล์ทุกไฟล์ที่ลงท้ายด้วย .log พร้อมคอมเมนต์อธิบาย ตรวจด้วย git status -s และ git check-ignore -v
  4. commit เฉพาะ .gitignore และ .env.example ด้วยข้อความ chore: add .gitignore and .env.example
  5. เพิ่มบรรทัด มอคค่า 70 บาท ใน menu.md และสร้างไฟล์ draft.txt (โน้ตส่วนตัว) แล้วจงใจพิมพ์ git add . เพื่อจำลองความผิดพลาด จากนั้นเอา draft.txt ออกจาก Staging Area โดยไม่ลบไฟล์
  6. commit ด้วยข้อความที่พิมพ์ผิดว่า feat: add mocah แล้วแก้ข้อความเป็น feat: add mocha โดยไม่สร้าง commit ใหม่เพิ่ม (commit นี้ยังไม่เคย push)
  7. ตรวจผลงานด้วย git log --oneline, git ls-files และ git status -s

ระบบราคาของร้านเก็บไว้ในไฟล์ prices.txt มีประวัติ 10 commit และออก Release v1.0.0 ให้สาขาต่าง ๆ ใช้ไปแล้วที่ commit ที่ 8 วันนี้สาขาหนึ่งแจ้งว่าเครื่องคิดเงินแสดงราคาติดลบ ไม่มีใครจำได้ว่าบั๊กเข้ามาตอนไหน สมชายต้องหา commit ต้นเหตุให้เจอแบบอัตโนมัติ แก้บั๊กบน Branch ของตัวเอง เก็บประวัติให้สะอาดก่อนส่ง รวมเข้า main แล้วส่งการแก้ไขเดียวกันไปยัง Branch release/1.0 พร้อมออก tag v1.0.1 โดยไม่เอางานใหม่ที่ยังไม่พร้อมบน main ติดไปด้วย

เริ่มจากสร้างสถานการณ์จำลองด้วยสคริปต์ด้านล่าง บันทึกเป็น ~/projects/git-lab/ch3-setup.sh (ไว้นอกโฟลเดอร์ ch3 เพราะสคริปต์จะลบโฟลเดอร์ ch3 ทิ้งทุกครั้งที่รัน)

#!/usr/bin/env bash
# สร้างสถานการณ์จำลองสำหรับโจทย์ที่ 3 (รันซ้ำได้ เพราะลบของเดิมก่อน)
set -e
LAB=~/projects/git-lab/ch3
rm -rf "$LAB"
mkdir -p "$LAB"
cd "$LAB"
# Remote จำลอง แทน GitHub
git init --bare -q remotes/shop.git
git clone -q remotes/shop.git shop 2>/dev/null
cd shop
items=("อเมริกาโน่ 50 บาท" "ลาเต้ 60 บาท" "มอคค่า 70 บาท" "คาปูชิโน่ 65 บาท" "ชาเขียว 55 บาท"
       "โกโก้ 50 บาท" "ลาเต้เย็น -5 บาท" "ชาไทย 45 บาท" "น้ำส้ม 40 บาท" "ครัวซองต์ 55 บาท")
for i in "${!items[@]}"; do
  n=$((i + 1))
  echo "${items[$i]}" >> prices.txt
  git add prices.txt
  git commit -q -m "feat: add price $n"
  # ออก Release v1.0.0 ให้ลูกค้าหลัง commit ที่ 8
  if [ "$n" -eq 8 ]; then
    git tag -a v1.0.0 -m "First release"
  fi
done
# push main และ tag ขึ้น Remote จำลอง
git push -q -u origin main --follow-tags
echo "พร้อมแล้ว: $(git rev-list --count HEAD) commits, tags: $(git tag)"

ข้อ 1

คำตอบ: add คือ git add README.md

git add นำไฟล์จาก Working Tree เข้า Staging Area จากนั้น git commit จึงบันทึกสิ่งที่อยู่ใน Staging Area เป็น snapshot ใหม่ ถ้าข้ามขั้นนี้ Git จะตอบว่า nothing added to commit but untracked files present (use "git add" to track)

ข้อ 2

คำตอบ: ??

ใน git status -s รหัส ?? หมายถึงไฟล์ Untracked คือ Git เห็นว่ามีไฟล์อยู่ในโฟลเดอร์แต่ยังไม่เคยติดตาม ผลจริงจากการทดสอบคือ ?? notes.md ถ้า git add notes.md แล้ว รหัสจะเปลี่ยนเป็น A (Added) ส่วนไฟล์ที่ Git ติดตามอยู่แล้วและถูกแก้ จะเป็น M (แก้แต่ยังไม่ stage) หรือ M (stage แล้ว)

ข้อ 3

คำตอบ: --staged คือ git restore --staged draft.txt

ตัวเลือก --staged สั่งให้ git restore คืนค่า Staging Area ของไฟล์นั้นให้เหมือน commit ล่าสุด แต่ไม่แตะไฟล์ใน Working Tree เนื้อหาใน draft.txt จึงอยู่ครบ ในโจทย์ที่ 1 จะเห็นว่าสถานะเปลี่ยนจาก A draft.txt เป็น ?? draft.txt ข้อควรระวังคือ ถ้าพิมพ์ git restore draft.txt โดยไม่มี --staged กับไฟล์ที่เคย commit แล้ว Git จะทิ้งการแก้ไขใน Working Tree ทันทีและกู้คืนไม่ได้

ข้อ 4

คำตอบ: -c คือ git switch -c feature/contact

-c ย่อมาจาก create คือสร้าง Branch ใหม่ที่ชี้ไปยัง commit ปัจจุบันแล้วสลับไปอยู่บน Branch นั้นในคำสั่งเดียว Git ตอบว่า Switched to a new branch 'feature/contact' ถ้ามี Branch ชื่อนี้อยู่แล้วจะได้ fatal: a branch named 'feature/contact' already exists ให้ใช้ git switch feature/contact (ไม่มี -c) แทน คำสั่งรุ่นเก่าที่ทำงานเหมือนกันคือ git checkout -b feature/contact

ข้อ 5

คำตอบ: ======= (เครื่องหมายเท่ากับ 7 ตัว)

Conflict marker มี 3 ส่วน: <<<<<<< HEAD เริ่มโค้ดฝั่ง Branch ที่เรายืนอยู่, ======= คั่นกลาง และ >>>>>>> main ปิดท้ายโค้ดฝั่ง Branch ที่ merge เข้ามา ตอนแก้ conflict ต้องลบทั้ง 3 บรรทัดนี้ออกให้หมด เหลือแต่เนื้อหาสุดท้ายที่ตกลงกันแล้ว จึงค่อย git add

ข้อ 6

คำตอบ: -u คือ git push -u origin main (ชื่อเต็มคือ --set-upstream)

-u ตั้ง upstream ให้ main ในเครื่องติดตาม origin/main Git จะยืนยันด้วยข้อความ branch 'main' set up to track 'origin/main'. ครั้งต่อไปจึงพิมพ์ git push หรือ git pull เฉย ๆ ได้ และ git status จะบอกได้ว่าเรานำหน้าหรือตามหลัง Remote กี่ commit

ข้อ 7

คำตอบ: --soft คือ git reset --soft HEAD~1

--soft เลื่อน Branch ถอยไป 1 commit แต่เก็บการเปลี่ยนแปลงของ commit นั้นไว้ใน Staging Area สถานะจึงเป็น A c.txt (ตัว A อยู่คอลัมน์แรก แปลว่า stage แล้ว) ถ้าใช้ --mixed ซึ่งเป็นค่าเริ่มต้น ไฟล์จะหลุดออกจาก Staging Area กลายเป็น ?? c.txt และถ้าใช้ --hard ไฟล์จะหายไปจาก Working Tree ด้วย จากการทดสอบจริง git reset HEAD~1 (mixed) ให้ผล ?? c.txt

ข้อ 8

คำตอบ: 125

git bisect run ตีความ exit code ดังนี้: 0 คือ good, 1 ถึง 127 ยกเว้น 125 คือ bad และ 125 คือ "ทดสอบไม่ได้ ให้ข้าม" (เหมือนสั่ง git bisect skip) ส่วน exit code ตั้งแต่ 128 ขึ้นไปจะทำให้ bisect หยุดทำงานทันที การใช้ 125 กับ commit ที่ยังไม่มีไฟล์ จึงไม่ทำให้ Git เข้าใจผิดว่า commit นั้นเสีย

ข้อ 9

คำตอบ: read คือ contents: read

Workflow ที่แค่ checkout โค้ดมาตรวจ ต้องการเพียงสิทธิ์อ่าน การกำหนด permissions ระดับ Workflow จะจำกัดสิทธิ์ของ GITHUB_TOKEN ที่ทุก Job ได้รับ ถ้ามี Action ตัวใดถูกโจมตีหรือมีช่องโหว่ ความเสียหายจะจำกัดอยู่แค่การอ่าน ไม่สามารถ push หรือแก้ Repository ได้ ส่วน Workflow ของ GitHub Pages ต้องเพิ่ม pages: write และ id-token: write เฉพาะใน Workflow นั้น

คำตอบ: A เมื่อ main ไม่มี commit ใหม่หลังแยก Branch ประวัติของ feature/contact จึงต่อจาก main เป็นเส้นตรง Git แค่เลื่อน pointer ของ main ไปข้างหน้า และแสดงข้อความ Updating ... ตามด้วย Fast-forward ไม่มี merge commit ใหม่เกิดขึ้น (เห็นได้ในโจทย์ที่ 2 ขั้นที่ 6)

ข้อ 5

คำตอบ: D ข้อความ (fetch first) และ hint บอกตรง ๆ ว่า Remote มี commit ที่เรายังไม่มี (เพื่อนเพิ่ง push) Git จึงไม่ยอมให้ push ทับ วิธีที่ถูกคือ git pull เพื่อ fetch และ merge งานของเพื่อนเข้ามา แก้ conflict ถ้ามี แล้ว git push อีกครั้ง งานของทั้งสองคนจะอยู่ครบ

  • A ผิดเพราะ git push --force จะเขียนทับประวัติบน Remote ทำให้ commit ของเพื่อนหายไปจาก main ห้ามใช้กับ Branch ที่ใช้ร่วมกันเด็ดขาด
  • B ผิดเพราะเสียเวลาโดยไม่จำเป็นและเสี่ยงทำงานหาย Git มีเครื่องมือรวมงานอยู่แล้ว การ clone ใหม่ไม่ได้แก้ปัญหาที่ต้องรวมงานสองฝั่งเข้าด้วยกัน
  • C ผิดเพราะ --amend แค่เขียน commit ล่าสุดของเราใหม่ Remote ก็ยังมี commit ของเพื่อนที่เราไม่มีอยู่ดี push จึงถูกปฏิเสธเหมือนเดิม
ข้อ 6

คำตอบ: C กฎทองของ Rebase คือ "ห้าม rebase commit ที่คนอื่นมีอยู่แล้ว" เพราะ rebase สร้าง commit ใหม่ที่มี hash ใหม่ Branch ที่สร้างเองและยังไม่เคย push ไม่มีใครอื่นมีสำเนา การเขียนประวัติใหม่จึงไม่กระทบใคร

  • A ผิดเพราะ main เป็นประวัติที่ทุกคนใช้ร่วมกัน หลัง force push ทุกคนจะมีประวัติไม่ตรงกับ Remote เมื่อ pull จะเกิด commit ซ้ำซ้อนหรือ conflict จำนวนมาก
  • B ผิดเพราะเพื่อนสองคนมี commit ของ Branch นี้ในเครื่องแล้ว ถ้า rebase แล้ว force push งานที่เพื่อน push ทีหลังอาจหายหรือต้องแก้ประวัติยุ่งยาก
  • D ผิดเพราะ Release ที่ส่งให้ลูกค้าแล้วต้องตรวจย้อนได้ว่ามาจาก commit ใด ถ้า rebase hash จะเปลี่ยน tag และบันทึกของ Release จะชี้ไปยัง commit ที่ไม่อยู่บน Branch แล้ว
ข้อ 7

คำตอบ: A git revert <hash> สร้าง commit ใหม่ที่ย้อนการเปลี่ยนแปลงของ commit ที่ระบุ ประวัติเดิมไม่ถูกแก้ จึงปลอดภัยกับ Branch ที่ push และแชร์แล้ว เพื่อนแค่ git pull ตามปกติ และ git log จะเห็น Revert "feat: add broken banner" บอกเหตุผลชัดเจน

  • B ผิดเพราะ reset --hard ร่วมกับ push --force เป็นการเขียนประวัติที่แชร์แล้วใหม่ เพื่อนที่ pull ไปแล้วจะมีประวัติไม่ตรงกับ Remote และถ้ามีใคร push commit อื่นไว้ก่อน งานนั้นจะหายไปด้วย
  • C ผิดเพราะ --amend ใช้แก้ commit ล่าสุดที่ยังไม่ push เท่านั้น ถ้าใช้กับ commit ที่ push แล้วจะได้ hash ใหม่และ push ถูกปฏิเสธแบบ non-fast-forward
  • D ผิดเพราะ git restore จัดการเฉพาะการแก้ไขที่ยังไม่ commit ใน Working Tree ไม่สามารถย้อน commit ที่บันทึกและ push ไปแล้วได้

คำตอบ: B git stash ปกติเก็บเฉพาะไฟล์ที่ Git ติดตามอยู่ ต้องเพิ่ม -u (--include-untracked) จึงจะเก็บไฟล์ใหม่ที่ยังไม่เคย add อย่าง notes.md ไปด้วย ส่วน -m ช่วยตั้งชื่อให้จำได้ว่า stash นี้คืออะไร จากการทดสอบจริง หลัง git stash -u -m "wip: readme and notes" Git ตอบ Saved working directory and index state On main: wip: readme and notes คำสั่ง git status -s ไม่แสดงอะไรเลย และ git stash list แสดง stash@{0}: On main: wip: readme and notes (git stash ที่ไม่ระบุคำสั่งย่อยเท่ากับ git stash push)

คำตอบ: B Reflog บันทึกทุกตำแหน่งที่ HEAD เคยชี้ บรรทัด HEAD@{1}: commit: feat: add mocha คือตำแหน่งก่อน reset คำสั่ง git reset --hard HEAD@{1} (หรือใช้ hash 638f7cf แทน) จึงย้าย main กลับไปที่ commit นั้น ผลจริงจากการทดสอบคือ HEAD is now at 638f7cf feat: add mocha ในกรณีนี้ใช้ --hard ได้เพราะ Working Tree ไม่มีงานค้างที่ยังไม่ commit

  • D ผิดเพราะ commit ที่ reset ทิ้งยังอยู่ในฐานข้อมูลของ Git และอ้างถึงได้ผ่าน Reflog อีกระยะหนึ่ง (commit ที่ไม่มี Branch ชี้อยู่แล้วแบบนี้ ค่าเริ่มต้นคือ 30 วันตาม gc.reflogExpireUnreachable ส่วน entry ที่ยังเข้าถึงได้เก็บ 90 วัน) สิ่งที่ --hard ลบถาวรจริงคืองานที่ยังไม่เคย commit

  • B ผิดเพราะ key อาจถูกคัดลอกไปแล้วในช่วงที่เป็น Public และ fork หรือสำเนาที่คนอื่น clone ไปก็ยังมีอยู่ การเปลี่ยนเป็น Private ไม่ทำให้ key ที่รั่วใช้ไม่ได้

  • อ่าน conflict ให้ออก ส่วน <<<<<<< HEAD คือของ feature/promo (Branch ที่ยืนอยู่) ส่วนหลัง ======= คือของ main บรรทัดมอคค่าและบรรทัดโปรโมชันไม่ชนกัน Git จึงรวมให้เองโดยอัตโนมัติ
  • แก้ตามการตัดสินใจของทีม ไม่ได้เลือกฝั่งใดฝั่งหนึ่ง แต่เขียนบรรทัดใหม่ที่รวมความหมายของทั้งสองฝั่ง ตรวจด้วย grep ว่าไม่เหลือ marker แล้วจึง git add และ git commit --no-edit ซึ่งใช้ข้อความ Merge branch 'main' into feature/promo ที่ Git เตรียมไว้

แนวคิด
  • ทำให้การทดสอบเป็นอัตโนมัติก่อน แล้วให้ Git ค้นหาแทนเรา check.sh ใช้ exit code สื่อสารกับ git bisect run Git ใช้ Binary Search กับ 10 commit ทดสอบเพียง 3 ครั้ง (commit ที่ 5, 7 และ 6) ก็รู้ว่า feat: add price 7 คือ first bad commit ไม่ว่าประวัติจะยาวเป็นพัน commit ก็ใช้จำนวนรอบเพิ่มขึ้นเพียงเล็กน้อย
  • สคริปต์ทดสอบอยู่นอก Repository check.sh อยู่ที่ ../check.sh ระหว่าง bisect Git สลับไฟล์ใน Working Tree ไปมา ถ้าสคริปต์อยู่ใน Repository อาจหายไปใน commit เก่าที่ยังไม่มีสคริปต์นี้
  • ต้อง git bisect reset ทุกครั้ง ระหว่าง bisect HEAD อยู่ในสถานะ detached ถ้าลืม reset แล้วเริ่มแก้งานเลย จะ commit ลงบน commit เก่าที่ไม่มี Branch ชี้อยู่ ผลลัพธ์ Switched to branch 'main' ยืนยันว่ากลับมาแล้ว
  • เก็บกวาดประวัติก่อนแชร์ตามกฎทอง fix/negative-price ยังไม่เคย push ไม่มีใครมีสำเนา การใช้ fixup รวม wip เข้าไปจึงปลอดภัย ผลคือ commit เดียวที่ diff ชัดเจน: -ลาเต้เย็น -5 บาท เป็น +ลาเต้เย็น 55 บาท
  • ใช้ cherry-pick ส่ง Hotfix ไป Branch ของ Release release/1.0 เริ่มจาก v1.0.0 ถ้า merge main เข้าไปทั้งก้อน เมนูใหม่ของ commit ที่ 9 และ 10 จะติดไปด้วย git cherry-pick -x คัดลอกเฉพาะ commit แก้บั๊ก ได้ hash ใหม่ (5801fe3) และ -x เพิ่มบรรทัด (cherry picked from commit ...) ไว้ใน message เพื่อให้ตามรอยกลับไปหา commit ต้นฉบับได้ Git รวมให้อัตโนมัติ (Auto-merging prices.txt) เพราะบรรทัดที่แก้ไม่ชนกับบรรทัดที่ต่างกันระหว่างสอง Branch
  • ทดสอบซ้ำทุกจุดที่ส่งงาน check.sh ถูกรันทั้งบน main หลัง merge และบน release/1.0 ก่อนและหลัง cherry-pick เพื่อยืนยันว่าบั๊กมีอยู่จริงและหายไปจริง
  • Tag ตาม Semantic Versioning การแก้บั๊กโดยไม่เพิ่มฟีเจอร์ใหม่จะเพิ่มเลข PATCH จึงเป็น v1.0.1 ใช้ annotated tag (-a) เพื่อเก็บผู้สร้าง วันที่ และข้อความ แล้ว push tag แยกต่างหาก ใน git ls-remote บรรทัด refs/tags/v1.0.1^{} คือ commit ที่ annotated tag ชี้ไป (Git เรียกว่า peeled tag)
