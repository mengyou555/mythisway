คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

API (Application Programming Interface) คือ "สัญญา" ที่บอกว่าโปรแกรมหนึ่งจะขออะไรจากอีกโปรแกรมได้บ้าง ต้องส่งข้อมูลหน้าตาแบบไหน และจะได้อะไรกลับมา ฝั่งที่ขอเรียกว่า Client (เช่น แอปมือถือ หน้าเว็บ หรือสคริปต์) ฝั่งที่ให้บริการเรียกว่า Server ทั้งสองฝั่งไม่จำเป็นต้องรู้ว่าอีกฝั่งเขียนด้วยภาษาอะไร ขอแค่ทำตามสัญญาเดียวกัน

API มีสองความหมายที่ควรแยกให้ออก Library API คือฟังก์ชันที่เราเรียกในโค้ดภาษาเดียวกัน เช่น json.dumps() ใน Python ส่วน Web API คือ API ที่เรียกข้ามเครือข่ายผ่าน HTTP หัวข้อนี้เน้น Web API ซึ่งมีหลายรูปแบบ (API Style) ดังนี้

  • REST: ใช้ HTTP ตรงไปตรงมา มองข้อมูลเป็น Resource ที่มี URL ของตัวเอง เป็นแบบที่พบบ่อยที่สุดและเป็นแกนของหัวข้อนี้
  • GraphQL: มี Endpoint เดียว Client เขียน Query บอกเองว่าอยากได้ฟิลด์ไหน เหมาะกับหน้าจอที่ต้องการข้อมูลหลายชนิดในครั้งเดียว
  • gRPC: ใช้ HTTP/2 และ Protocol Buffers (ข้อมูลแบบ Binary) เร็วและกระชับ นิยมใช้ระหว่าง Service ภายในองค์กร
  • Webhook: กลับทิศกับปกติ คือ Server เป็นฝ่ายส่ง HTTP Request ไปบอก Client เมื่อมีเหตุการณ์เกิดขึ้น เช่น "หนังสือเกินกำหนดคืน"
  • WebSocket / SSE: เปิดการเชื่อมต่อค้างไว้เพื่อส่งข้อมูลแบบ Real-time เช่น แชตหรือราคาหุ้น
  • SOAP: รุ่นเก่าที่ใช้ XML และมีกฎเข้มงวด ยังพบในระบบธนาคารและหน่วยงานรัฐบางแห่ง

ไม่ว่าจะใช้สไตล์ไหน พื้นฐานคือ HTTP ทุกครั้งที่ Client คุยกับ Server จะมี Request หนึ่งก้อนและ Response หนึ่งก้อน Request ประกอบด้วย Method (เช่น GET), Path (เช่น /books), Query String (ส่วนหลัง ?), Header และ Body ส่วน Response ประกอบด้วย Status Line (เช่น 200 OK), Header และ Body การอ่านสองก้อนนี้ให้ออกคือทักษะที่ใช้ทุกวันตอน Debug API คุณควรใช้ curl -i และ curl -v ทุกครั้งที่ไม่แน่ใจว่า API ตอบอะไรกลับมาจริงๆ

เปรียบเทียบ

API เหมือนเคาน์เตอร์บริการของห้องสมุด คุณ (Client) ไม่ต้องเดินเข้าไปค้นในโกดังเอง แค่กรอกใบคำขอตามแบบฟอร์ม (Request) ยื่นให้บรรณารักษ์ (Server) แล้วรับใบตอบกลับ (Response) ใบคำขอมีหัวกระดาษบอกว่าขออะไร (Method และ Path) มีช่องข้อมูลประกอบ (Header) และเนื้อหาที่แนบมา (Body) ส่วนใบตอบกลับมีตราประทับผล (Status Code) เช่น "พบแล้ว" หรือ "ไม่พบ" แบบฟอร์มที่ตกลงกันไว้ล่วงหน้านั่นแหละคือ API

ตัวอย่างโค้ด

เราจะสร้าง Web API ตัวแรกด้วย Python Standard Library ล้วนๆ ไม่ต้องติดตั้งอะไรเพิ่ม เพื่อให้เห็นว่า HTTP Server ทำงานอย่างไรโดยไม่มี Framework ช่วย สร้างไฟล์ ~/projects/api-lab/c01-http/server.py

# server.py : Web API ตัวแรก ใช้แค่ Python Standard Library (ไม่ต้อง pip install อะไรเลย)
import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

# ข้อมูลตัวอย่าง 3 เล่ม (เก็บใน Memory ปิดโปรแกรมแล้วหาย)
BOOKS = [
    {"id": "bk_0001", "title": "Python 101", "author": "Somchai Jaidee",
     "isbn": "9786160000011", "published_year": 2024, "status": "available"},
    {"id": "bk_0002", "title": "API Design ฉบับเริ่มต้น", "author": "Suda Meesuk",
     "isbn": "9786160000028", "published_year": 2025, "status": "available"},
    {"id": "bk_0003", "title": "SQL for Everyone", "author": "Anan Rakdee",
     "isbn": "9786160000035", "published_year": 2023, "status": "on_loan"},
]


class LibraryHandler(BaseHTTPRequestHandler):
    def send_json(self, status, payload):
        # แปลง dict เป็น JSON แล้วเข้ารหัสเป็น bytes แบบ UTF-8 (ภาษาไทยจะไม่เพี้ยน)
        body = json.dumps(payload, ensure_ascii=False).encode("utf-8")
        self.send_response(status)                     # Status Line เช่น HTTP/1.0 200 OK
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()                             # บรรทัดว่างคั่น Header กับ Body
        self.wfile.write(body)                         # Body

    def do_GET(self):
        # ตัด Query String (ส่วนหลัง ?) ออก เหลือแค่ Path
        path = self.path.split("?", 1)[0]
        if path == "/books":
            self.send_json(200, {"data": BOOKS, "next_cursor": None})
            return
        if path.startswith("/books/"):
            book_id = path.removeprefix("/books/")
            for book in BOOKS:
                if book["id"] == book_id:
                    self.send_json(200, book)
                    return
            self.send_json(404, {"error": "book_not_found", "book_id": book_id})
            return
        self.send_json(404, {"error": "not_found", "path": path})


if __name__ == "__main__":
    # ผูกกับ 127.0.0.1 เท่านั้น เครื่องอื่นในเครือข่ายเรียกไม่ได้ (ปลอดภัยกว่า 0.0.0.0)
    server = ThreadingHTTPServer(("127.0.0.1", 8000), LibraryHandler)
    print("Server พร้อมแล้วที่ http://127.0.0.1:8000  (กด Ctrl+C เพื่อหยุด)")
    try:
        server.serve_forever()
    except KeyboardInterrupt:
        print("\nปิด Server แล้ว")

Best Practice
  • เวลา Debug ให้เริ่มจาก curl -i เสมอ เพราะ Status Code และ Header บอกปัญหาได้มากกว่า Body
  • ตอบ Content-Type ให้ตรงกับเนื้อหาจริงทุกครั้ง API ที่ตอบ JSON ต้องเป็น application/json
  • ระหว่างพัฒนาให้ผูก Server กับ 127.0.0.1 ไม่ใช่ 0.0.0.0 เพื่อไม่ให้เครื่องอื่นในเครือข่ายเข้าถึงโดยไม่ตั้งใจ
  • ในงานจริงเราไม่เขียน Server ด้วย http.server (ไม่เหมาะกับ Production) แต่ใช้ Framework อย่าง FastAPI ซึ่งเริ่มในแนวคิดถัดไป

HTTP Methods, Safe/Idempotent และ Status Codes ด้วย FastAPI

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

HTTP Method คือ "คำกริยา" ของ Request บอกว่าอยากทำอะไรกับ Resource ส่วน Status Code คือตัวเลขสามหลักที่ Server ใช้บอกผล ถ้าเลือกสองอย่างนี้ถูก Client ทุกตัว (เบราว์เซอร์ แอปมือถือ Proxy และ Cache) จะเข้าใจ API ของเราได้ทันทีโดยไม่ต้องอ่านโค้ด ถ้าเลือกผิด เช่น ใช้ GET ลบข้อมูล หรือตอบ 200 ทั้งที่ Error ระบบรอบข้างจะทำงานผิดพลาดแบบหาสาเหตุยาก

คุณสมบัติสองข้อที่ต้องรู้จักคือ Safe หมายถึง Method ที่ไม่เปลี่ยนข้อมูลบน Server และ Idempotent หมายถึงส่ง Request เดิมซ้ำกี่ครั้ง สถานะสุดท้ายบน Server ก็เหมือนส่งครั้งเดียว Client และ Proxy ใช้สองข้อนี้ตัดสินใจว่า "ลองใหม่อัตโนมัติได้ไหม" เมื่อเครือข่ายหลุด

Methodใช้ทำอะไรSafeIdempotentStatus ที่พบบ่อยเมื่อสำเร็จ
GETอ่าน Resource หรือรายการใช่ใช่200
HEADเหมือน GET แต่ขอแค่ Header (ไม่มี Body)ใช่ใช่200
OPTIONSถามว่า Resource นี้รองรับอะไรบ้าง (ใช้ใน CORS Preflight)ใช่ใช่200 หรือ 204
POSTสร้าง Resource ใหม่ หรือสั่ง Actionไม่ไม่201 + Location
PUTแทนที่ Resource ทั้งก้อนไม่ใช่200 หรือ 204
PATCHแก้บางฟิลด์ไม่ไม่รับประกัน200
DELETEลบ Resourceไม่ใช่204

Status Code แบ่งเป็นกลุ่มตามหลักแรก: 2xx สำเร็จ, 3xx ให้ไปที่อื่น, 4xx Client ส่งมาผิด, 5xx Server พังเอง ตารางนี้คือชุดที่หลักสูตรนี้ใช้ตลอด

เปรียบเทียบ

นึกถึงสวิตช์ไฟกับปุ่มกดเรียกลิฟต์ การกด "ตั้งไฟเป็นเปิด" (PUT) กี่ครั้งไฟก็ยังเปิดเหมือนเดิม จึงเป็น Idempotent ส่วนการหยอดเหรียญซื้อน้ำ (POST) หยอดสองครั้งก็ได้น้ำสองขวดและเสียเงินสองเท่า จึงไม่ Idempotent ส่วนการมองดูว่าไฟเปิดอยู่ไหม (GET) ไม่ได้เปลี่ยนอะไรเลย จึงเป็นทั้ง Safe และ Idempotent

# main.py : FastAPI ตัวแรก สาธิต HTTP Methods และ Status Codes
from fastapi import FastAPI, HTTPException, Response
from pydantic import BaseModel

app = FastAPI(title="Library API (c02)")

# ข้อมูลตัวอย่างเก็บใน dict โดยใช้ book_id เป็น key
BOOKS: dict[str, dict] = {
    "bk_0001": {"id": "bk_0001", "title": "Python 101", "author": "Somchai Jaidee",
                "isbn": "9786160000011", "published_year": 2024, "status": "available"},
    "bk_0002": {"id": "bk_0002", "title": "API Design ฉบับเริ่มต้น", "author": "Suda Meesuk",
                "isbn": "9786160000028", "published_year": 2025, "status": "available"},
    "bk_0003": {"id": "bk_0003", "title": "SQL for Everyone", "author": "Anan Rakdee",
                "isbn": "9786160000035", "published_year": 2023, "status": "on_loan"},
}
next_number = 4  # เลขลำดับของหนังสือเล่มถัดไป (bk_0004)


class BookIn(BaseModel):
    # Schema ของ Body ตอนสร้าง/แทนที่ทั้งเล่ม: ทุกฟิลด์ต้องมี ยกเว้น status
    title: str
    author: str
    isbn: str
    published_year: int
    status: str = "available"


class BookPatchIn(BaseModel):
    # PATCH ส่งมาเฉพาะฟิลด์ที่อยากแก้ จึงให้ทุกฟิลด์เป็น None ได้
    title: str | None = None
    author: str | None = None
    status: str | None = None


def find_book(book_id: str) -> dict:
    if book_id not in BOOKS:
        raise HTTPException(status_code=404, detail=f"ไม่พบหนังสือ {book_id}")
    return BOOKS[book_id]


@app.get("/books")
def list_books():
    return {"data": list(BOOKS.values()), "next_cursor": None}


@app.get("/books/{book_id}")
def get_book(book_id: str):
    return find_book(book_id)


@app.post("/books", status_code=201)
def create_book(book: BookIn, response: Response):
    global next_number
    book_id = f"bk_{next_number:04d}"
    next_number += 1
    BOOKS[book_id] = {"id": book_id, **book.model_dump()}
    # 201 Created ควรบอกที่อยู่ของ Resource ใหม่ใน Header Location
    response.headers["Location"] = f"/books/{book_id}"
    return BOOKS[book_id]


@app.put("/books/{book_id}")
def replace_book(book_id: str, book: BookIn):
    find_book(book_id)
    # PUT = แทนที่ทั้งก้อน ส่งซ้ำกี่ครั้งผลก็เหมือนเดิม (Idempotent)
    BOOKS[book_id] = {"id": book_id, **book.model_dump()}
    return BOOKS[book_id]


@app.patch("/books/{book_id}")
def patch_book(book_id: str, patch: BookPatchIn):
    current = find_book(book_id)
    # exclude_unset=True : เอาเฉพาะฟิลด์ที่ Client ส่งมาจริง
    current.update(patch.model_dump(exclude_unset=True))
    return current


@app.delete("/books/{book_id}", status_code=204)
def delete_book(book_id: str):
    find_book(book_id)
    del BOOKS[book_id]
    # 204 No Content : สำเร็จแต่ไม่มี Body จึงคืน Response ว่าง
    return Response(status_code=204)

Best Practice
  • POST ที่สร้างของใหม่ตอบ 201 พร้อม Location และคืน Resource ที่สร้างใน Body เพื่อให้ Client ไม่ต้อง GET ซ้ำ
  • DELETE ตอบ 204 ไม่มี Body ส่วน 404 จากการลบซ้ำเป็นเรื่องปกติ Client ควรถือว่า "ไม่มีแล้ว" เหมือนกัน
  • ใช้ PUT เมื่อ Client ส่งข้อมูลครบทุกฟิลด์ และใช้ PATCH เมื่อแก้บางฟิลด์ อย่าให้ PUT ทำงานแบบ PATCH
  • อย่าให้ GET เปลี่ยนข้อมูลเด็ดขาด เพราะเบราว์เซอร์ Crawler และ Cache เรียก GET ได้เองโดยไม่ถามผู้ใช้

แนวคิดที่ 3Beginner

ออกแบบ JSON: snake_case, วันที่ RFC 3339, เงินเป็นสตางค์ และ null กับฟิลด์ที่ไม่ได้ส่ง

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

JSON คือรูปแบบข้อมูลที่ API ส่วนใหญ่ใช้ส่ง Request และ Response มีชนิดข้อมูลแค่ 6 แบบ ได้แก่ string, number, boolean (true/false), null, object ({}) และ array ([]) JSON ไม่มีชนิด "วันที่" และไม่มีชนิด "เงิน" เราจึงต้องตกลงกันเองว่าจะเขียนสิ่งเหล่านี้อย่างไร การตกลงนี้คือส่วนหนึ่งของ API Design ถ้าตกลงไม่ดีตั้งแต่ต้น การแก้ทีหลังจะกลายเป็น Breaking Change ที่ทำให้ Client ทุกตัวพัง

หลักสูตรนี้ใช้ข้อตกลง (Convention) ชุดเดียวทุก Endpoint ดังนี้

  • ชื่อฟิลด์เป็น snake_case เช่น published_year ไม่ใช่ publishedYear เลือกแบบไหนก็ได้ แต่ต้องใช้แบบเดียวทั้ง API
  • วันและเวลาเป็น RFC 3339 พร้อม Timezone เช่น "2026-10-15T10:00:00+07:00" ฟิลด์ลงท้ายด้วย _at ส่วนวันที่อย่างเดียวเขียน "2026-10-29" และลงท้ายด้วย _date
  • เงินเป็นจำนวนเต็มหน่วยสตางค์ เช่น ค่าปรับ 25.50 บาท เก็บเป็น "fine_satang": 2550 เพราะ float คำนวณทศนิยมไม่แม่น
  • ID เป็น string ทึบ (Opaque) เช่น bk_0001, mb_0001, ln_0001 Client ห้ามเดาความหมายหรือคำนวณจาก ID
  • Enum เป็นตัวพิมพ์เล็ก snake_case เช่น available, on_loan, lost
  • รายการห่อด้วย Envelope {"data": [...], "next_cursor": null} เพื่อเพิ่มข้อมูลแบ่งหน้าได้ภายหลังโดยไม่ทำให้ Client พัง
  • แยก null กับ "ไม่ได้ส่ง" ใน PATCH: ส่ง "subtitle": null แปลว่า "ลบค่า subtitle" แต่ไม่ส่ง subtitle มาเลยแปลว่า "ไม่แตะ subtitle"
เปรียบเทียบ

การออกแบบ JSON เหมือนการออกแบบแบบฟอร์มราชการ ถ้าช่องวันเกิดไม่บอกว่าเป็น พ.ศ. หรือ ค.ศ. ไม่บอกว่าเรียงวัน/เดือน/ปีแบบไหน คนกรอกแต่ละคนจะเขียนไม่เหมือนกัน และเจ้าหน้าที่ต้องเดาเอง ช่องจำนวนเงินก็เหมือนกัน ถ้าไม่ระบุหน่วย บางคนเขียน "25.5" บางคนเขียน "25 บาท 50 สตางค์" แบบฟอร์มที่ดีจึงบอกรูปแบบชัดเจนทุกช่องตั้งแต่แรก

# json_design.py : ออกแบบ JSON ของ Library API ด้วย Pydantic (ไม่ต้องเปิด Server)
import json
from datetime import date, datetime
from enum import Enum
from zoneinfo import ZoneInfo

from pydantic import BaseModel, ValidationError

BKK = ZoneInfo("Asia/Bangkok")  # เขตเวลาไทย +07:00


class BookStatus(str, Enum):
    # Enum เป็นตัวพิมพ์เล็กแบบ snake_case เสมอ
    available = "available"
    on_loan = "on_loan"
    lost = "lost"


class Book(BaseModel):
    id: str                     # ID เป็น String ทึบ (Opaque) เช่น bk_0001
    title: str
    author: str
    isbn: str                   # ISBN เป็น String เพราะเลข 0 นำหน้าต้องไม่หาย
    published_year: int
    status: BookStatus


class Loan(BaseModel):
    id: str
    book_id: str
    member_id: str
    borrowed_at: datetime       # ฟิลด์ลงท้าย _at = วันและเวลา (RFC 3339)
    due_date: date              # ฟิลด์ลงท้าย _date = วันที่อย่างเดียว
    returned_at: datetime | None = None
    fine_satang: int = 0        # เงินเก็บเป็นจำนวนเต็มหน่วยสตางค์ ห้ามใช้ float


class BookPatch(BaseModel):
    # ใช้กับ PATCH : ทุกฟิลด์ไม่บังคับ
    title: str | None = None
    subtitle: str | None = None
    status: BookStatus | None = None


print("== 1) Loan เป็น JSON ==")
loan = Loan(
    id="ln_0001", book_id="bk_0003", member_id="mb_0002",
    borrowed_at=datetime(2026, 10, 15, 10, 0, tzinfo=BKK),
    due_date=date(2026, 10, 29),
)
print(loan.model_dump_json(indent=2))

print("== 2) ทำไมเงินห้ามเป็น float ==")
print("0.1 + 0.2 =", 0.1 + 0.2)
print("10 + 20 สตางค์ =", 10 + 20, "สตางค์")

print("== 3) null กับ ฟิลด์ที่ไม่ได้ส่ง ==")
print("ส่ง {'subtitle': None} ->", BookPatch(**{"subtitle": None}).model_dump(exclude_unset=True))
print("ส่ง {}                  ->", BookPatch().model_dump(exclude_unset=True))

print("== 4) Validation ==")
try:
    Book(id="bk_0009", title="X", author="Y", isbn="9786160000099",
         published_year=2026, status="borrowed")
except ValidationError as e:
    print(e)
try:
    Loan(id="ln_0009", book_id="bk_0001", member_id="mb_0001",
         borrowed_at="2026-10-15T10:00:00+07:00", due_date="2026-10-29", fine_satang=25.5)
except ValidationError as e:
    print(e)

print("== 5) json.dumps กับ datetime ตรงๆ ==")
try:
    json.dumps({"borrowed_at": datetime(2026, 10, 15, 10, 0, tzinfo=BKK)})
except TypeError as e:
    print("TypeError:", e)

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

REST (Representational State Transfer) คือแนวทางออกแบบ API ที่มองทุกอย่างเป็น Resource (สิ่งของ) แต่ละ Resource มี URL ของตัวเอง แล้วใช้ HTTP Method เป็นคำกริยากระทำกับมัน REST มีข้อกำหนด (Constraints) หลักดังนี้

  • Client-Server: แยกหน้าที่ชัดเจน Client ดูแลหน้าจอ Server ดูแลข้อมูล แต่ละฝั่งพัฒนาแยกกันได้
  • Stateless: ทุก Request ต้องมีข้อมูลครบในตัวเอง (เช่น Token) Server ไม่จำว่า Request ก่อนหน้าเป็นอะไร ทำให้เพิ่ม Server กี่เครื่องก็ได้
  • Cacheable: Response ต้องบอกได้ว่าเก็บ Cache ได้หรือไม่ (แนวคิดที่ 12)
  • Uniform Interface: ทุก Resource ใช้กติกาเดียวกัน คือ URL ระบุสิ่งของ Method ระบุการกระทำ และ Status Code บอกผล
  • Layered System: Client ไม่ต้องรู้ว่าระหว่างทางมี Load Balancer, Cache หรือ API Gateway กี่ชั้น

กฎการตั้งชื่อ URL ที่ใช้ในหลักสูตรนี้: ใช้คำนามพหูพจน์ (/books ไม่ใช่ /book) ตัวพิมพ์เล็กทั้งหมด คั่นคำด้วย - ห้ามมีคำกริยาใน URL ห้ามมี / ปิดท้าย ซ้อน Resource ได้ไม่เกิน 2 ชั้น (/members/{member_id}/loans) และห้ามใส่ข้อมูลลับใน URL เพราะ URL ถูกบันทึกใน Log ทุกที่ที่ผ่าน

คำถามที่มือใหม่ติดบ่อยคือ "ถ้าการกระทำไม่ใช่ CRUD จะทำอย่างไร เช่น ยืมหนังสือ" คำตอบคือมองการกระทำนั้นเป็น Resource ใหม่ การยืมคือ "สร้างรายการยืม" จึงเป็น POST /loans ส่วนการคืนเป็นเหตุการณ์ของรายการยืมหนึ่งรายการ จึงเป็น POST /loans/{loan_id}/return

สองแนวคิดเสริมที่ควรรู้จัก HATEOAS คือการแนบลิงก์ "ทำอะไรต่อได้" ไปใน Response เช่น รายการยืมที่ยังไม่คืนจะมีลิงก์ return ส่วน Richardson Maturity Model แบ่งความเป็น REST เป็น 4 ระดับ: Level 0 ยิงทุกอย่างไปที่ URL เดียว, Level 1 มี Resource แยก URL, Level 2 ใช้ Method และ Status Code ถูกต้อง, Level 3 มี HATEOAS API ส่วนใหญ่ในงานจริงอยู่ที่ Level 2 ซึ่งเพียงพอแล้ว

เปรียบเทียบ

URL แบบ REST เหมือนระบบเลขที่บ้าน ทุกหลังมีที่อยู่ของตัวเอง (/books/bk_0001) และมีซอยย่อยที่ชัดเจน (/members/mb_0001/loans) ส่วน Method คือสิ่งที่คุณทำกับบ้านหลังนั้น เช่น มาดู (GET) ซ่อมบางส่วน (PATCH) หรือรื้อ (DELETE) คุณไม่ตั้งชื่อซอยว่า "ซอยไปซ่อมบ้าน" เพราะการกระทำไม่ใช่สถานที่ URL ก็เช่นกัน ไม่ควรมีคำกริยา

from pydantic import BaseModel

BOOKS = {

    "mb_0002": {"id": "mb_0002", "name": "Suda Meesuk", "email": "suda@example.com", "max_active_loans": 3},

LOANS = {
    "ln_0001": {"id": "ln_0001", "book_id": "bk_0003", "member_id": "mb_0002",

class LoanCreate(BaseModel):
    book_id: str
    member_id: str


def with_links(loan: dict) -> dict:
    # แนบลิงก์ไปยังสิ่งที่ทำต่อได้ (แนวคิด HATEOAS แบบย่อ)
    links = {"self": f"/loans/{loan['id']}", "member": f"/members/{loan['member_id']}"}
    if loan["returned_at"] is None:
        links["return"] = f"/loans/{loan['id']}/return"
    return {**loan, "links": links}


@app.get("/books")
def list_books():
    return {"data": list(BOOKS.values()), "next_cursor": None}


@app.get("/members/{member_id}")
def get_member(member_id: str):
    if member_id not in MEMBERS:
        raise HTTPException(404, f"ไม่พบสมาชิก {member_id}")
    return MEMBERS[member_id]


@app.get("/members/{member_id}/loans")
def list_member_loans(member_id: str):
    # Resource ซ้อน 2 ชั้น: รายการยืมของสมาชิกคนหนึ่ง
    get_member(member_id)
    loans = [with_links(l) for l in LOANS.values() if l["member_id"] == member_id]
    return {"data": loans, "next_cursor": None}


@app.post("/loans", status_code=201)
def create_loan(body: LoanCreate, response: Response):
    # "ยืมหนังสือ" ไม่ใช่ /borrowBook แต่คือ "สร้าง Resource การยืม"
    if body.member_id not in MEMBERS:
        raise HTTPException(404, f"ไม่พบสมาชิก {body.member_id}")
    book = BOOKS.get(body.book_id)
    if book is None:
        raise HTTPException(404, f"ไม่พบหนังสือ {body.book_id}")
    if book["status"] != "available":
        raise HTTPException(409, f"หนังสือ {body.book_id} ถูกยืมอยู่")
    loan_id = f"ln_{len(LOANS) + 1:04d}"
    now = datetime.now(BKK).replace(microsecond=0)
    LOANS[loan_id] = {
        "id": loan_id, "book_id": body.book_id, "member_id": body.member_id,
        "borrowed_at": now.isoformat(), "due_date": (now.date() + timedelta(days=14)).isoformat(),
        "returned_at": None, "fine_satang": 0,
    }
    book["status"] = "on_loan"
    response.headers["Location"] = f"/loans/{loan_id}"
    return with_links(LOANS[loan_id])


@app.post("/loans/{loan_id}/return")
def return_loan(loan_id: str):
    # การ "คืน" เป็น Action ที่ไม่ใช่ CRUD จึงทำเป็น Sub-resource ด้วย POST
    loan = LOANS.get(loan_id)
    if loan is None:
        raise HTTPException(404, f"ไม่พบการยืม {loan_id}")
    if loan["returned_at"] is not None:
        raise HTTPException(409, f"การยืม {loan_id} คืนไปแล้ว")
    loan["returned_at"] = datetime.now(BKK).replace(microsecond=0).isoformat()
    BOOKS[loan["book_id"]]["status"] = "available"
    return with_links(loan)

Best Practice
  • เริ่มออกแบบจากการเขียนตาราง Endpoint (Method, Path, ความหมาย, Status) ก่อนเขียนโค้ด แล้วให้เพื่อนร่วมทีมรีวิว
  • ข้อมูลที่ระบุตัวตนผู้ใช้ เช่น member_id ของคนที่ยืม ในระบบจริงควรมาจาก Token ไม่ใช่จาก Body (แนวคิดที่ 10 จะทำให้ดู)
  • ใช้ Sub-resource เฉพาะเมื่อความสัมพันธ์เป็นแบบเจ้าของชัดเจน และไม่ซ้อนเกิน 2 ชั้น

Query Parameters: Filtering, Sorting และ Pagination แบบ Offset กับ Cursor

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

Path Parameter ระบุว่า "สิ่งไหน" เช่น /books/bk_0001 ส่วน Query Parameter (หลัง ?) ปรับแต่ง "วิธีดู" รายการ เช่น กรอง เรียง และแบ่งหน้า ห้องสมุดจริงอาจมีหนังสือหลายแสนเล่ม ถ้า GET /books ส่งทั้งหมดในครั้งเดียว Server จะช้า เครือข่ายจะหนัก และแอปมือถือจะค้าง เราจึงต้องมีสามเครื่องมือนี้

  • Filtering: ?author=Suda%20Meesuk, ?status=available, ?q=python (ค้นจากชื่อ), ?published_after=2024
  • Sorting: ?sort=-published_year,title เครื่องหมาย - แปลว่ามากไปน้อย และต้องมี Allow-list ฟิลด์ที่เรียงได้ เพื่อกันการเรียงตามฟิลด์ที่ไม่มี Index
  • Offset Pagination: ?limit=20&offset=40 คือ "ข้าม 40 รายการแล้วเอา 20" เข้าใจง่าย กระโดดไปหน้าไหนก็ได้ แต่ช้าเมื่อ offset ใหญ่ และข้อมูลเลื่อนเมื่อมีการเพิ่มหรือลบระหว่างเปิดหน้า
  • Cursor Pagination: ?limit=20&cursor=... คือ "เอา 20 รายการถัดจากตัวสุดท้ายที่เห็น" Cursor เป็นข้อความทึบ (base64url ของ {"after_id": "bk_0010"}) ไม่มีปัญหาข้อมูลเลื่อน และเร็วคงที่ เหมาะกับ Feed และข้อมูลจำนวนมาก แต่กระโดดไปหน้า 50 ตรงๆ ไม่ได้

ข้อตกลงของหลักสูตรนี้: limit ค่าเริ่มต้น 20 สูงสุด 100 (เกินได้ 422) รายการแบบ Cursor ตอบ {"data": [...], "next_cursor": "..."} และใส่ Header Link ตาม RFC 8288 ที่มี rel="next" ส่วนแบบ Offset เพิ่ม limit, offset และ total นอกจากนี้ยังมีเทคนิค Sparse Fieldsets เช่น ?fields=id,title ให้ Client เลือกฟิลด์ที่ต้องการ ช่วยลดขนาด Response ได้อีก

เปรียบเทียบ

Offset เหมือนบอกเพื่อนว่า "อ่านต่อจากหน้า 41" ถ้าระหว่างนั้นมีคนแทรกกระดาษเพิ่มไว้หน้าแรก เนื้อหาที่หน้า 41 จะเลื่อนไป เพื่อนจะอ่านซ้ำบางย่อหน้า ส่วน Cursor เหมือนสอดที่คั่นหนังสือไว้ "หลังบรรทัดนี้" ต่อให้มีคนแทรกหน้าใหม่ไว้ข้างหน้า ที่คั่นก็ยังอยู่ตรงเดิม

import base64
import binascii
import json

from fastapi import FastAPI, HTTPException, Query, Request, Response
from pydantic import BaseModel

app = FastAPI(title="Library API (c05)")

CANONICAL = [
    ("Python 101", "Somchai Jaidee", "available"),
    ("API Design ฉบับเริ่มต้น", "Suda Meesuk", "available"),
    ("SQL for Everyone", "Anan Rakdee", "on_loan"),
]


def seed() -> list[dict]:
    # สร้างหนังสือ 25 เล่มแบบกำหนดแน่นอน (รันกี่ครั้งก็ได้ข้อมูลเดิม)
    books = []
    for n in range(1, 26):
        title, author, status = (f"Book {n:02d}", "Anan Rakdee", "available")
        if n <= 3:
            title, author, status = CANONICAL[n - 1]
        books.append({"id": f"bk_{n:04d}", "title": title, "author": author,
                      "published_year": 2018 + (n - 1) % 8, "status": status})
    return books


BOOKS = seed()
SORTABLE = {"id", "title", "published_year"}   # Allow-list ฟิลด์ที่เรียงได้


def apply_filters(books, author, status, q):
    if author:
        books = [b for b in books if b["author"] == author]
    if status:
        books = [b for b in books if b["status"] == status]
    if q:
        books = [b for b in books if q.lower() in b["title"].lower()]
    return books


def apply_sort(books, sort: str):
    # รูปแบบ ?sort=-published_year,title  (เครื่องหมาย - = มากไปน้อย)
    keys = [k.strip() for k in sort.split(",") if k.strip()]
    for k in keys:
        if k.lstrip("-") not in SORTABLE:
            raise HTTPException(400, f"เรียงตาม '{k}' ไม่ได้ ใช้ได้เฉพาะ {sorted(SORTABLE)}")
    # เรียงจาก key สุดท้ายไปหา key แรก และปิดท้ายด้วย id เป็น Tiebreaker เสมอ
    books = sorted(books, key=lambda b: b["id"])
    for k in reversed(keys):
        books = sorted(books, key=lambda b: b[k.lstrip("-")], reverse=k.startswith("-"))
    return books


@app.get("/books")
def list_books_offset(
    limit: int = Query(20, ge=1, le=100),
    offset: int = Query(0, ge=0),
    author: str | None = None,
    status: str | None = None,
    q: str | None = None,
    sort: str = "id",
):
    books = apply_sort(apply_filters(BOOKS, author, status, q), sort)
    page = books[offset: offset + limit]
    return {"data": page, "limit": limit, "offset": offset, "total": len(books)}


def encode_cursor(after_id: str) -> str:
    raw = json.dumps({"after_id": after_id}).encode()
    # base64url และตัด = ท้ายออก ให้ใส่ใน URL ได้สะอาด
    return base64.urlsafe_b64encode(raw).decode().rstrip("=")


def decode_cursor(cursor: str) -> str:
    try:
        padded = cursor + "=" * (-len(cursor) % 4)   # เติม = กลับให้ครบก่อนถอด
        return json.loads(base64.urlsafe_b64decode(padded))["after_id"]
    except (binascii.Error, ValueError, KeyError, TypeError):
        raise HTTPException(400, "cursor ไม่ถูกต้อง")


@app.get("/books/feed")
def list_books_cursor(request: Request, response: Response,
                      limit: int = Query(20, ge=1, le=100), cursor: str | None = None):
    books = sorted(BOOKS, key=lambda b: b["id"])  # Cursor ต้องเรียงด้วยค่าที่ไม่ซ้ำ
    if cursor:
        after_id = decode_cursor(cursor)
        books = [b for b in books if b["id"] > after_id]
    page = books[:limit]
    has_more = len(books) > limit
    next_cursor = encode_cursor(page[-1]["id"]) if has_more else None
    if next_cursor:
        # RFC 8288 : บอกลิงก์หน้าถัดไปใน Header Link ด้วย
        next_url = request.url.include_query_params(cursor=next_cursor)
        response.headers["Link"] = f'<{next_url}>; rel="next"'
    return {"data": page, "next_cursor": next_cursor}

#!/usr/bin/env bash
# follow.sh : เดินตาม next_cursor ไปจนหมด แล้วนับจำนวนหนังสือทั้งหมด
set -euo pipefail
BASE_URL="${BASE_URL:-http://127.0.0.1:8000}"
cursor=""
total=0
page=1
while : ; do
  if [ -z "$cursor" ]; then
    resp=$(curl -s "$BASE_URL/books/feed?limit=10")
  else
    resp=$(curl -s "$BASE_URL/books/feed?limit=10&cursor=$cursor")
  fi
  count=$(echo "$resp" | jq '.data | length')
  first=$(echo "$resp" | jq -r '.data[0].id')
  last=$(echo "$resp" | jq -r '.data[-1].id')
  echo "หน้า $page: $count เล่ม ($first ถึง $last)"
  total=$((total + count))
  cursor=$(echo "$resp" | jq -r '.next_cursor // empty')
  [ -z "$cursor" ] && break
  page=$((page + 1))
done
echo "รวมทั้งหมด $total เล่ม"

Best Practice
  • ทุก Endpoint ที่คืนรายการต้องแบ่งหน้าตั้งแต่วันแรก และมีค่าสูงสุดของ limit เสมอ (กัน OWASP API4: Unrestricted Resource Consumption)
  • ใช้ Cursor สำหรับ Feed หรือข้อมูลที่เปลี่ยนบ่อยและมีจำนวนมาก ใช้ Offset เมื่อข้อมูลน้อยและผู้ใช้ต้องการกระโดดไปหน้าที่ระบุ
  • Cursor ต้องทึบ Client ห้ามแกะหรือสร้างเอง เพื่อให้ฝั่ง Server เปลี่ยนวิธีทำงานภายในได้โดยไม่ทำให้ Client พัง
  • ให้ทั้ง next_cursor ใน Body และ Header Link เพื่อให้ Client เลือกใช้แบบที่สะดวก

Error Format มาตรฐานด้วย RFC 9457 Problem Details (application/problem+json)

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

จากแนวคิดก่อนๆ Error ของเรามีหลายหน้าตา บางที่เป็น {"detail": "..."} บางที่เป็น {"detail": [...]} บางที่เป็น {"error": "..."} Client ต้องเขียนโค้ดแยกรับทีละแบบ ซึ่งเปราะบางมาก RFC 9457 Problem Details for HTTP APIs (ออกปี 2023 แทนที่ RFC 7807) คือมาตรฐานกลางของรูปแบบ Error ใช้ Media Type application/problem+json และมีสมาชิกหลัก 5 ตัว

  • type: URI ที่ระบุ "ชนิด" ของปัญหา เช่น https://example.com/problems/book-unavailable Client ใช้ค่านี้ตัดสินใจในโค้ด ค่าต้องคงที่ และควรเปิดดูเป็นเอกสารได้
  • title: สรุปสั้นของชนิดปัญหา ไม่เปลี่ยนตามแต่ละครั้ง
  • status: HTTP Status Code ต้องตรงกับ Status จริงของ Response
  • detail: อธิบายเฉพาะครั้งนี้ให้มนุษย์อ่าน
  • instance: ครั้งนี้เกิดที่ไหน (มักใช้ Path ของ Request)

เราเพิ่มสมาชิกเสริม (Extension Members) ได้ตามต้องการ หลักสูตรนี้ใช้ errors (รายการ {field, message} ของ 422) และ trace_id (ใช้ค้น Log เมื่อเกิด 500) ทีมควรทำ Error Catalog คือตารางรวมทุก type ที่ API อาจตอบ เพื่อให้ทีม Frontend และทีม Support ใช้อ้างอิง

# problems.py : สร้าง Error ตามมาตรฐาน RFC 9457 Problem Details
import logging
import uuid

from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

PROBLEM_BASE = "https://example.com/problems/"
logger = logging.getLogger("library.errors")


class ProblemError(Exception):
    """Error ทางธุรกิจที่เรารู้จัก โยนจาก Endpoint แล้วให้ Handler แปลงเป็น problem+json"""

    def __init__(self, slug: str, title: str, status: int, detail: str,
                 headers: dict | None = None, **extra):
        self.slug, self.title, self.status, self.detail = slug, title, status, detail
        self.headers, self.extra = headers, extra   # headers เช่น WWW-Authenticate, Retry-After


def problem_response(request: Request, slug: str, title: str, status: int,
                     detail: str, headers: dict | None = None, **extra) -> JSONResponse:
    body = {
        "type": PROBLEM_BASE + slug,   # URI ระบุ "ชนิด" ของปัญหา (คงที่ เอาไปเขียนเอกสารได้)
        "title": title,                # สรุปสั้นของชนิดปัญหา (ไม่เปลี่ยนตามแต่ละครั้ง)
        "status": status,              # ต้องตรงกับ HTTP Status Code จริง
        "detail": detail,              # อธิบายเฉพาะครั้งนี้ ให้คนอ่านเข้าใจ
        "instance": request.url.path,  # ครั้งนี้เกิดที่ไหน
        **extra,                       # Extension Members เช่น errors, trace_id
    }
    return JSONResponse(body, status_code=status, headers=headers,
                        media_type="application/problem+json")


STATUS_TO_SLUG = {
    401: ("unauthorized", "Unauthorized"),
    403: ("forbidden", "Forbidden"),
    404: ("not-found", "Not Found"),
    405: ("method-not-allowed", "Method Not Allowed"),
}


def install_problem_handlers(app: FastAPI) -> None:
    @app.exception_handler(ProblemError)
    async def handle_problem(request: Request, exc: ProblemError):
        return problem_response(request, exc.slug, exc.title, exc.status, exc.detail,
                                headers=exc.headers, **exc.extra)

    # ต้องจับ HTTPException ของ Starlette (ตัวแม่) จึงจะครอบ 404/405 ของ Route ที่ไม่มีอยู่จริงด้วย
    @app.exception_handler(StarletteHTTPException)
    async def handle_http(request: Request, exc: StarletteHTTPException):
        slug, title = STATUS_TO_SLUG.get(exc.status_code, ("http-error", "HTTP Error"))
        return problem_response(request, slug, title, exc.status_code, str(exc.detail),
                                headers=getattr(exc, "headers", None))

    @app.exception_handler(RequestValidationError)
    async def handle_validation(request: Request, exc: RequestValidationError):
        errors = [
            {"field": ".".join(str(p) for p in e["loc"][1:]), "message": e["msg"]}
            for e in exc.errors()
        ]
        return problem_response(request, "validation-error", "Validation Error", 422,
                                f"ข้อมูลไม่ผ่านการตรวจสอบ {len(errors)} จุด", errors=errors)

    @app.exception_handler(Exception)
    async def handle_unexpected(request: Request, exc: Exception):
        trace_id = uuid.uuid4().hex
        # เก็บ Traceback เต็มไว้ใน Log ฝั่ง Server เท่านั้น ห้ามส่งให้ Client
        logger.exception("unhandled error trace_id=%s", trace_id)
        return problem_response(request, "internal-error", "Internal Server Error", 500,
                                "ระบบขัดข้อง โปรดแจ้ง trace_id นี้กับผู้ดูแล", trace_id=trace_id)

Best Practice
  • ทุก Error ของ API ต้องเป็น application/problem+json รวมถึง 404/405 ของ Framework และ 500 ที่ไม่คาดคิด

  • 422 ต้องรายงานทุกฟิลด์ที่ผิดในครั้งเดียว ไม่ใช่ทีละฟิลด์

  • Status Code ตรงตามสัญญา (201 ไม่ใช่ 200)
  • Header สำคัญ เช่น Location และ Content-Type (application/problem+json เมื่อ Error)

#!/usr/bin/env bash
# smoke.sh : ตรวจเร็วๆ ว่า API ที่รันอยู่จริงตอบ Status Code ถูกต้อง
set -euo pipefail
BASE_URL="${BASE_URL:-http://127.0.0.1:8000}"
failed=0

check() {
  # check "ชื่อการทดสอบ" รหัสที่คาดหวัง  [อาร์กิวเมนต์อื่นของ curl ...]
  local name="$1" expected="$2"
  shift 2
  local got
  got=$(curl -s -o /dev/null -w '%{http_code}' "$@" || true)   # || true : ให้ set -e ไม่หยุดสคริปต์เมื่อต่อ Server ไม่ได้
  if [ "$got" = "$expected" ]; then
    echo "PASS  $name ($got)"
  else
    echo "FAIL  $name (ได้ $got แต่คาดหวัง $expected)"
    failed=1
  fi
}

check "list books"          200 "$BASE_URL/books"
check "get one book"        200 "$BASE_URL/books/bk_0001"
check "unknown book"        404 "$BASE_URL/books/bk_9999"
check "create book"         201 -X POST "$BASE_URL/books" -H 'Content-Type: application/json' \
  -d '{"title":"Smoke Test","author":"Bot","isbn":"9786160000998","published_year":2026}'
check "invalid book"        422 -X POST "$BASE_URL/books" -H 'Content-Type: application/json' -d '{}'
check "borrow on-loan book" 409 -X POST "$BASE_URL/loans" -H 'Content-Type: application/json' \
  -d '{"book_id":"bk_0003","member_id":"mb_0001"}'

if [ "$failed" -ne 0 ]; then
  echo "สรุป: มีบางข้อไม่ผ่าน"
  exit 1
fi
echo "สรุป: ผ่านทั้งหมด"

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

OpenAPI Specification คือมาตรฐานสำหรับเขียน "สัญญา" ของ REST API เป็นไฟล์ YAML หรือ JSON ที่ทั้งคนและเครื่องอ่านได้ ไฟล์เดียวบอกครบว่า API มี Endpoint อะไร รับ Parameter อะไร Body หน้าตาแบบไหน ตอบ Status อะไรได้บ้าง และต้องยืนยันตัวตนอย่างไร จากไฟล์นี้เราสร้างได้ทั้งเอกสาร (Swagger UI, Redoc) Mock Server, Client SDK และใช้ตรวจว่า Server ทำตามสัญญาจริง เวอร์ชัน 3.1 ใช้ JSON Schema 2020-12 เต็มรูปแบบ

มีสองแนวทางในการได้ไฟล์นี้มา

แนวทางทำอย่างไรข้อดีข้อควรระวัง
Code-firstเขียนโค้ดก่อน แล้วให้ Framework สร้าง Spec (FastAPI สร้าง /openapi.json ให้อัตโนมัติ)เร็ว Spec ตรงกับโค้ดเสมอออกแบบโดยไม่ได้คุยกับผู้ใช้ API ก่อน และสัญญาเปลี่ยนตามโค้ดโดยไม่ตั้งใจได้ง่าย
Design-first (Contract-first)เขียน openapi.yaml ก่อน รีวิวกับทีม Frontend แล้วจึงเขียนโค้ดตามทีม Frontend เริ่มงานได้ทันทีด้วย Mock Server ถกเถียงเรื่องการออกแบบก่อนมีโค้ดซึ่งแก้ง่ายกว่ามากต้องมีวินัยตรวจว่าโค้ดตรงกับ Spec (Lint, Test)
แบบผสม (Hybrid)ออกแบบและรีวิวด้วย openapi.yaml ก่อน แล้วเขียนโค้ดด้วย FastAPI และใช้ Test ตรวจว่า /openapi.json ที่ได้ตรงกับสัญญาได้ข้อดีของทั้งสองแบบ ทีมคุยกันจากสัญญาเดียวและโค้ดสร้างเอกสารให้เองต้องมี Test เทียบสองไฟล์ ไม่อย่างนั้นจะค่อยๆ ไม่ตรงกัน (Drift)

พื้นฐาน YAML ที่ต้องรู้: ใช้ช่องว่าง (Space) เยื้องเท่านั้น ห้ามใช้ Tab, รายการขึ้นต้นด้วย - , ข้อความหลายบรรทัดใช้ |, Comment ขึ้นต้นด้วย # และ key ที่เป็นตัวเลขเช่น Status Code ต้องใส่เครื่องหมายคำพูดเป็น '200' ส่วนโครงสร้างระดับบนสุดของ OpenAPI มี openapi, info, servers, tags, paths, components และ security

with open("openapi.yaml", encoding="utf-8") as f:
    spec = yaml.safe_load(f)

print("OpenAPI version :", spec["openapi"])
print("API             :", spec["info"]["title"], spec["info"]["version"])
print("Schemas         :", ", ".join(spec["components"]["schemas"]))

global_security = spec.get("security", [])
print("\nOperations:")
for path, item in spec["paths"].items():
    for method, op in item.items():
        # Operation ไหนไม่กำหนด security เอง จะใช้ค่า global
        security = op.get("security", global_security)
        need_auth = "ต้องมี Token" if security else "สาธารณะ"
        codes = ",".join(op["responses"])
        print(f"  {method.upper():6} {path:18} {op['operationId']:11} {need_auth:13} [{codes}]")

Best Practice
  • เก็บ openapi.yaml ไว้ใน Git ร่วมกับโค้ด และรีวิว Spec ใน Pull Request เหมือนรีวิวโค้ด
  • ทุก Operation ต้องมี operationId, summary, tags และ Response ของ Error อย่างน้อยหนึ่งตัวที่เป็น 4xx
  • ใส่ Example ที่สมจริง (ใช้ข้อมูลตัวอย่างชุดเดียวกับระบบ) เพราะ Mock Server และเอกสารใช้ Example เหล่านี้โดยตรง
  • ประกาศ Security แบบ Global ให้ปลอดภัยไว้ก่อน แล้วเปิดเป็นสาธารณะทีละ Operation ด้วย security: [] ดีกว่าลืมใส่ Security ให้ Operation ที่ควรป้องกัน
ลองเอง

ต่อยอด openapi.yaml แล้วรัน python3 check_spec.py ตรวจทุกครั้ง

  1. เพิ่ม Operation returnLoan ที่ POST /loans/{loan_id}/return พร้อม Parameter LoanId ใน components/parameters และ Response 200, 401, 404
  2. เพิ่ม Schema Member (id, name, email ที่มี format: email, max_active_loans) และ Operation getMember ที่ GET /members/{member_id}
  3. เพิ่ม Response 401 ให้ GET /books/{book_id} แล้วถามตัวเองว่าสมเหตุสมผลไหม ในเมื่อ Operation นี้เป็นสาธารณะ
  4. เปิด http://127.0.0.1:8000/docs ของแอปแนวคิดที่ 6 แล้วลองกด Try it out กับ POST /books โดยส่ง ISBN ผิด ดูว่า Swagger UI แสดง 422 อย่างไร

Contract-first: Lint ด้วย Spectral และ Mock Server ด้วย Prism

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

เมื่อมี openapi.yaml แล้ว เราใช้มันขับเคลื่อนการทำงานทั้งทีมแบบ Contract-first วงจรคือ ออกแบบ แล้วเขียน openapi.yaml แล้ว Lint แล้วรีวิว แล้วเปิด Mock Server ให้ทีม Frontend ใช้ แล้วเขียนโค้ดจริง แล้วตรวจว่าโค้ดตรงกับสัญญา เครื่องมือสองตัวที่ทำให้วงจรนี้เกิดขึ้นได้คือ

  • Spectral (@stoplight/spectral-cli 6.17.0): ตัว Lint ตรวจว่า Spec ถูกโครงสร้าง OpenAPI และตรงตามกฎของทีม เช่น Path ต้องเป็น kebab-case ฟิลด์ต้องเป็น snake_case ใช้ชุดกฎ spectral:oas เป็นฐาน แล้วเพิ่มกฎของเราเอง
  • Prism (@stoplight/prism-cli 5.16.0): Mock Server ที่อ่าน Spec แล้วตอบ Response จาก Example ทันทีโดยไม่ต้องเขียนโค้ด Server และยังตรวจ Request ที่เข้ามาว่าตรง Schema ไหม ทีม Frontend จึงเริ่มงานได้ตั้งแต่วันแรก

Lint สำคัญมากเมื่อต้องแยกแยะ Breaking Change (การเปลี่ยนที่ทำให้ Client เดิมพัง) ออกจาก Non-breaking Change

Authentication และ Authorization: API Key, OAuth 2.0/OIDC และ JWT ด้วย PyJWT

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

สองคำนี้ฟังคล้ายกันแต่ต่างกันชัดเจน Authentication (AuthN) คือ "คุณเป็นใคร" เช่น ตรวจ Token แล้วรู้ว่าเป็นสมาชิก mb_0001 ถ้าไม่ผ่านตอบ 401 Unauthorized พร้อม Header WWW-Authenticate บอกวิธียืนยันตัวตน ส่วน Authorization (AuthZ) คือ "คุณทำสิ่งนี้ได้ไหม" เช่น mb_0001 ดูรายการยืมของ mb_0002 ไม่ได้ ถ้าไม่ผ่านตอบ 403 Forbidden (ชื่อ 401 ว่า Unauthorized เป็นความผิดพลาดทางประวัติศาสตร์ของ HTTP ความหมายจริงคือ Unauthenticated)

วิธียืนยันตัวตนที่พบบ่อยใน API มีสามแบบ

  • API Key: ข้อความลับยาวๆ ส่งใน Header เช่น X-API-Key ง่ายและเหมาะกับการเรียกระหว่างระบบ (Server-to-Server) ฝั่ง Server ต้องเก็บแค่ Hash ของ Key (เช่น hashlib.sha256) เทียบด้วย hmac.compare_digest และรองรับการเปลี่ยน Key (Rotation) โดยให้ Key เก่ากับใหม่ใช้ได้พร้อมกันช่วงหนึ่ง
  • OAuth 2.0: มาตรฐานการ "มอบสิทธิ์" มีบทบาท 4 ตัว คือ Resource Owner (ผู้ใช้), Client (แอป), Authorization Server (ผู้ออก Token) และ Resource Server (API ของเรา) Flow ที่ควรรู้คือ Authorization Code + PKCE สำหรับแอปที่มีผู้ใช้ล็อกอิน และ Client Credentials สำหรับระบบคุยกับระบบโดยไม่มีผู้ใช้
  • OpenID Connect (OIDC): ชั้นที่ต่อบน OAuth 2.0 เพื่อ "ล็อกอิน" เพิ่ม ID Token ที่บอกว่าผู้ใช้เป็นใคร (ให้แอปอ่าน) แยกจาก Access Token ที่ใช้เรียก API (ให้ API ตรวจ) ห้ามเอา ID Token มาเรียก API

ลำดับการทำงานของ Authorization Code + PKCE แบบย่อ

ผู้ใช้        แอป (Client)                  Authorization Server            Library API
  |  กดล็อกอิน  |                                       |                              |
  |-----------> | สร้าง code_verifier (สุ่ม) และ          |                              |
  |             | code_challenge = SHA256(verifier)     |                              |
  |             |--- พาไปหน้า /authorize?code_challenge=... ------------->|              |
  |  กรอกรหัสผ่าน และกดยินยอม scope -------------------------------->|                  |
  |             |<-- redirect กลับพร้อม code (ใช้ได้ครั้งเดียว) ----------|                  |
  |             |--- POST /token ส่ง code + code_verifier -------------->|                  |
  |             |<-- access_token (JWT อายุสั้น) + refresh_token + id_token|                  |
  |             |--- GET /members/mb_0001/loans  Authorization: Bearer access_token -------->|
  |             |<-- 200 (API ตรวจลายเซ็น iss aud exp และ scope เอง) ------------------------|

JWT (JSON Web Token) คือรูปแบบ Access Token ที่นิยมที่สุด มี 3 ส่วนคั่นด้วยจุด header.payload.signature แต่ละส่วนเข้ารหัสแบบ base64url ซึ่ง ไม่ใช่การเข้ารหัสลับ ใครก็แกะอ่านได้ ลายเซ็นมีไว้กันการแก้ไขเท่านั้น Claim สำคัญได้แก่ sub (เป็นของใคร), exp (หมดอายุเมื่อไร), iat (ออกเมื่อไร), iss (ใครออก), aud (ใช้กับ API ไหน) และ scope (ทำอะไรได้) หลุมพรางของ JWT ที่ต้องรู้: ยอมรับ alg: none, ไม่ล็อกอัลกอริทึม, Secret สั้นหรือเดาง่าย, ไม่ตรวจ exp หรือ aud, ใส่ข้อมูลลับใน Payload, Token อายุยาวเกินไป และเก็บ Token ใน localStorage ของเบราว์เซอร์ซึ่ง JavaScript ที่ถูกฝัง (XSS) อ่านได้

เปรียบเทียบ

JWT เหมือนบัตรผ่านงานสัมมนาที่พิมพ์ชื่อ วันหมดอายุ และโซนที่เข้าได้ ไว้บนบัตร และมีตราประทับนูนของผู้จัด ใครหยิบไปอ่านก็อ่านได้ (ไม่ใช่ความลับ) แต่ถ้าแก้ตัวหนังสือบนบัตร ตราประทับจะไม่ตรง เจ้าหน้าที่หน้าห้องต้องตรวจทั้งตราประทับ วันหมดอายุ และโซน (Authorization) ถ้าเจ้าหน้าที่ยอมรับบัตรที่เขียนว่า "ไม่ต้องตรวจตรา" (alg: none) ใครก็ปลอมบัตรเข้าห้อง VIP ได้

# main.py : ตรวจ JWT (Authentication) และตรวจสิทธิ์ (Authorization) ใน Library API
import os
from datetime import datetime, timedelta
from zoneinfo import ZoneInfo

import jwt  # มาจากแพ็กเกจ PyJWT
from fastapi import Depends, FastAPI, Response
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from pydantic import BaseModel

from problems import ProblemError, install_problem_handlers

SECRET = os.environ.get("JWT_SECRET")
if not SECRET:
    raise SystemExit(
        "ไม่พบ JWT_SECRET ใน Environment\n"
        "สร้างค่าใหม่ด้วยคำสั่ง:\n"
        "  export JWT_SECRET=$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
    )
ISSUER = "https://auth.example.com"
AUDIENCE = "library-api"
BKK = ZoneInfo("Asia/Bangkok")

app = FastAPI(title="Library API (c10)")
install_problem_handlers(app)
bearer = HTTPBearer(auto_error=False)   # ปิด auto_error เพื่อตอบ 401 เป็น problem+json เอง

BOOKS = {"bk_0001": {"id": "bk_0001", "status": "available"},
         "bk_0002": {"id": "bk_0002", "status": "available"},
         "bk_0003": {"id": "bk_0003", "status": "on_loan"}}
LOANS = {"ln_0001": {"id": "ln_0001", "book_id": "bk_0003", "member_id": "mb_0002",
                     "due_date": "2026-10-29", "returned_at": None}}


def unauthorized(detail: str) -> ProblemError:
    # 401 ต้องมี WWW-Authenticate บอก Client ว่าต้องยืนยันตัวตนแบบไหน
    return ProblemError("unauthorized", "Unauthorized", 401, detail,
                        headers={"WWW-Authenticate": 'Bearer realm="library-api"'})


def get_current_user(creds: HTTPAuthorizationCredentials | None = Depends(bearer)) -> dict:
    if creds is None:
        raise unauthorized("ต้องส่ง Header Authorization: Bearer <token>")
    try:
        claims = jwt.decode(
            creds.credentials, SECRET,
            algorithms=["HS256"],          # ล็อกอัลกอริทึม ห้ามเชื่อค่า alg ใน Token
            audience=AUDIENCE, issuer=ISSUER,
            options={"require": ["exp", "iat", "sub", "aud", "iss"]},
        )
    except jwt.ExpiredSignatureError:
        raise unauthorized("token expired")
    except jwt.InvalidTokenError as e:
        raise unauthorized(f"token ใช้ไม่ได้ ({type(e).__name__})")
    claims["scopes"] = set(claims.get("scope", "").split())
    return claims


def require_scope(scope: str):
    def checker(user: dict = Depends(get_current_user)) -> dict:
        if scope not in user["scopes"] and "admin" not in user["scopes"]:
            raise ProblemError("forbidden", "Forbidden", 403, f"Token นี้ไม่มี scope {scope}")
        return user
    return checker


@app.get("/members/{member_id}/loans")
def list_member_loans(member_id: str, user: dict = Depends(get_current_user)):
    # กัน BOLA: ดูได้เฉพาะของตัวเอง เว้นแต่เป็น admin
    if user["sub"] != member_id and "admin" not in user["scopes"]:
        raise ProblemError("forbidden", "Forbidden", 403, "ดูรายการยืมของสมาชิกคนอื่นไม่ได้")
    return {"data": [l for l in LOANS.values() if l["member_id"] == member_id], "next_cursor": None}


class LoanCreate(BaseModel):
    book_id: str


@app.post("/loans", status_code=201)
def create_loan(body: LoanCreate, response: Response, user: dict = Depends(require_scope("loans:write"))):
    book = BOOKS.get(body.book_id)
    if book is None:
        raise ProblemError("book-not-found", "Book Not Found", 404, f"ไม่พบหนังสือรหัส {body.book_id}")
    if book["status"] != "available":
        raise ProblemError("book-unavailable", "Book Unavailable", 409, f"หนังสือ {body.book_id} ถูกยืมอยู่")
    loan_id = f"ln_{len(LOANS) + 1:04d}"
    due = (datetime.now(BKK) + timedelta(days=14)).date().isoformat()
    # member_id มาจาก Token (sub) ไม่รับจาก Body เพื่อไม่ให้ยืมในนามคนอื่น
    LOANS[loan_id] = {"id": loan_id, "book_id": body.book_id, "member_id": user["sub"],
                      "due_date": due, "returned_at": None}
    book["status"] = "on_loan"
    response.headers["Location"] = f"/loans/{loan_id}"
    return LOANS[loan_id]

# make_token.py : จำลอง Authorization Server ออก Access Token (ใช้ในแล็บเท่านั้น)
import argparse
import os
from datetime import datetime, timedelta, timezone

import jwt

parser = argparse.ArgumentParser(description="สร้าง JWT สำหรับทดสอบ Library API")
parser.add_argument("--sub", default="mb_0001", help="รหัสสมาชิกเจ้าของ Token")
parser.add_argument("--scope", default="books:read loans:write", help="สิทธิ์ คั่นด้วยช่องว่าง")
parser.add_argument("--expired", action="store_true", help="สร้าง Token ที่หมดอายุไปแล้ว")
args = parser.parse_args()

secret = os.environ.get("JWT_SECRET")
if not secret:
    raise SystemExit("ไม่พบ JWT_SECRET ใน Environment (ดูวิธีสร้างในหัวข้อนี้)")

now = datetime.now(timezone.utc)
issued = now - timedelta(hours=1) if args.expired else now
claims = {
    "iss": "https://auth.example.com",   # ใครออก Token
    "aud": "library-api",                # Token นี้ใช้กับ API ไหน
    "sub": args.sub,                     # Token นี้เป็นของใคร
    "scope": args.scope,                 # ทำอะไรได้บ้าง
    "iat": issued,                       # ออกเมื่อไร
    "exp": issued + timedelta(minutes=15),  # หมดอายุใน 15 นาที
}
print(jwt.encode(claims, secret, algorithm="HS256"))

Best Practice
  • ใช้ผู้ให้บริการ Identity มาตรฐาน (OIDC) แทนการเขียนระบบล็อกอินเอง และให้ API ทำหน้าที่ตรวจ Token อย่างเดียว
  • ตรวจ Token ครบทุกข้อ: ลายเซ็น, อัลกอริทึมที่ล็อกไว้, exp, iss, aud แล้วจึงตรวจ scope และความเป็นเจ้าของข้อมูล (BOLA) ในทุก Endpoint
  • Access Token อายุสั้น (5 ถึง 15 นาที) ใช้ Refresh Token ขอใหม่ และส่ง Token ทาง Header เท่านั้น ห้ามใส่ใน URL
  • ระบบที่มีหลาย Service ให้ใช้อัลกอริทึมแบบ Public Key (เช่น RS256 หรือ ES256) เพื่อให้ API ตรวจได้โดยไม่ต้องถือ Secret ที่ใช้เซ็น
  • 401 ใช้เมื่อไม่รู้ตัวตน 403 ใช้เมื่อรู้ตัวตนแต่ไม่มีสิทธิ์ และทั้งคู่ต้องเป็น problem+json

Versioning, Idempotency-Key และ Rate Limiting (429 + Retry-After)

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

เมื่อ API มีผู้ใช้จริง จะเจอปัญหาสามเรื่องที่ไม่เกี่ยวกับฟีเจอร์ แต่เกี่ยวกับความทนทาน (Reliability) ของสัญญา

1. Versioning: วันหนึ่งเราจำเป็นต้องทำ Breaking Change เช่น เปลี่ยน GET /books จาก Array เปล่าๆ เป็น Envelope {"data": [...]} แอปมือถือรุ่นเก่าที่ผู้ใช้ยังไม่อัปเดตจะพังทันที Versioning ทำให้เวอร์ชันเก่าและใหม่อยู่ร่วมกันได้ชั่วคราว แล้วค่อยปิดเวอร์ชันเก่าตามกำหนดที่ประกาศไว้

วิธีตัวอย่างข้อดีข้อเสีย
ใน URL/v1/booksเห็นชัด ทดสอบด้วยเบราว์เซอร์และ curl ง่าย Cache แยกตาม URL อัตโนมัติURL ของ Resource เดียวกันเปลี่ยนเมื่อขึ้นเวอร์ชันใหม่
ใน HeaderAPI-Version: 2026-10-01URL คงที่ เปลี่ยนเวอร์ชันละเอียดตามวันที่ได้มองไม่เห็นใน URL ลืมส่งง่าย ต้องตั้ง Vary ให้ Cache ถูก
ใน Media TypeAccept: application/vnd.library.v2+jsonถูกหลัก HTTP มากที่สุดซับซ้อน เครื่องมือหลายตัวรองรับไม่ดี

หลักสูตรนี้ใช้แบบ URL (/v1) และประกาศว่าเวอร์ชันเก่าจะเลิกใช้ด้วย Header มาตรฐานสามตัว ได้แก่ Deprecation (RFC 9745 ค่าเป็น @ ตามด้วย Unix seconds ของวันที่เริ่มเลิกใช้), Sunset (RFC 8594 วันที่จะปิดจริง) และ Link ที่มี rel="deprecation" ชี้ไปยังเอกสารวิธีย้าย

2. Idempotency-Key: POST ไม่ Idempotent (แนวคิดที่ 2) ถ้าแอปกด "ยืม" แล้วเครือข่ายหลุดก่อนได้คำตอบ แอปไม่รู้ว่ายืมสำเร็จหรือยัง ถ้าลองใหม่อาจยืมซ้ำสองรายการ วิธีแก้คือให้ Client สร้างรหัสสุ่ม (เช่น UUID) หนึ่งค่าต่อ "หนึ่งความตั้งใจ" ส่งใน Header Idempotency-Key และใช้ค่าเดิมทุกครั้งที่ลองใหม่ Server จำผลลัพธ์ของ Key นั้นไว้ ถ้าเจอ Key เดิมกับ Body เดิมก็ส่งผลเดิมซ้ำ (Replay) โดยไม่ทำงานซ้ำ ถ้าเจอ Key เดิมแต่ Body ต่าง แปลว่า Client ใช้ Key ผิด ตอบ 422

3. Rate Limiting: จำกัดจำนวน Request ต่อ Client ต่อช่วงเวลา กัน Client ตัวเดียวใช้ทรัพยากรจนคนอื่นใช้ไม่ได้ (OWASP API4) เมื่อเกินให้ตอบ 429 Too Many Requests พร้อม Retry-After บอกว่าต้องรอกี่วินาที อัลกอริทึมพื้นฐานคือ Fixed Window (นับใหม่ทุก N วินาที เข้าใจง่ายแต่ยิงรวดที่รอยต่อหน้าต่างได้) และ Token Bucket (เติม "เหรียญ" เข้าถังด้วยอัตราคงที่ ยอมให้ยิงรวดได้เท่าขนาดถัง นิยมใช้ใน API Gateway) ส่วน Header มาตรฐาน RateLimit ของ IETF ยังเป็นฉบับร่าง (Draft) อยู่ ให้ตรวจสถานะล่าสุดที่ datatracker.ietf.org ก่อนนำมาใช้ ฝั่ง Client ต้องลองใหม่อย่างสุภาพ คือทำตาม Retry-After ถ้ามี และถ้าไม่มีให้ใช้ Exponential Backoff + Jitter (รอนานขึ้นเป็นเท่าตัวและสุ่มเวลาเล็กน้อย)

เปรียบเทียบ

Idempotency-Key เหมือนเลขที่ใบสั่งซื้อในร้านอาหาร ถ้าพนักงานส่งใบเลขที่ 42 เข้าครัวซ้ำเพราะไม่แน่ใจว่าส่งไปแล้วหรือยัง ครัวดูเลขแล้วรู้ว่าทำไปแล้ว ไม่ทำซ้ำ ส่วน Rate Limiting เหมือนบัตรคิวที่ธนาคาร ให้บริการได้ทีละจำนวน คนที่มาเกินจะได้ป้ายว่า "โปรดกลับมาอีก 10 นาที" (Retry-After) แทนที่จะปล่อยให้ทุกคนแย่งกันจนเคาน์เตอร์ล่ม

def client_id(x_api_key: str | None = Header(default=None)) -> str:
    # แล็บนี้ใช้ X-API-Key แค่ระบุตัว Client (การตรวจตัวตนจริงดูหัวข้อ c10)

def rate_limit(response: Response, api_key: str = Depends(client_id)) -> str:
    now = time.monotonic()
    started, count = windows.get(api_key, (now, 0))
    if now - started >= WINDOW_SECONDS:          # หมดหน้าต่างเดิม เริ่มนับใหม่
        started, count = now, 0
    if count >= LIMIT:
        retry_after = math.ceil(WINDOW_SECONDS - (now - started))

                           f"เรียกเกิน {LIMIT} ครั้งต่อ {WINDOW_SECONDS} วินาที",
                           headers={"Retry-After": str(retry_after)})
    windows[api_key] = (started, count + 1)
    response.headers["X-RateLimit-Remaining"] = str(LIMIT - count - 1)
    return api_key

# client_retry.py : Client ที่ลองใหม่อย่างสุภาพ ทำตาม Retry-After และใช้ Exponential Backoff + Jitter
import random
import time
import uuid

import httpx

BASE_URL = "http://127.0.0.1:8000"
HEADERS = {"X-API-Key": "lab-client-retry"}


def backoff_seconds(attempt: int) -> float:
    # 0.5, 1, 2, 4 ... วินาที แล้วสุ่มลดลงบางส่วน (Jitter) กัน Client ทุกตัวยิงพร้อมกัน
    base = 0.5 * (2 ** attempt)
    return round(random.uniform(base / 2, base), 2)


def request_with_retry(client: httpx.Client, method: str, url: str, max_retries: int = 3, **kwargs):
    for attempt in range(max_retries + 1):
        try:
            r = client.request(method, url, **kwargs)
        except httpx.TransportError as e:          # ต่อไม่ติด หรือ Timeout
            if attempt == max_retries:
                raise
            wait = backoff_seconds(attempt)
            print(f"  เครือข่ายมีปัญหา ({type(e).__name__}) รอ {wait} วินาที")
            time.sleep(wait)
            continue
        if r.status_code not in (429, 502, 503, 504) or attempt == max_retries:
            return r
        retry_after = r.headers.get("Retry-After")
        wait = float(retry_after) if retry_after else backoff_seconds(attempt)
        print(f"  ได้ {r.status_code} รอ {wait} วินาทีตาม {'Retry-After' if retry_after else 'backoff'}")
        time.sleep(wait)
    return r


with httpx.Client(base_url=BASE_URL, headers=HEADERS, timeout=5.0) as client:
    for i in range(1, 8):
        r = request_with_retry(client, "GET", "/v1/books")
        print(f"ครั้งที่ {i}: {r.status_code}")

    # POST ที่ลองใหม่ได้อย่างปลอดภัย เพราะสร้าง Idempotency-Key ฝั่ง Client ครั้งเดียวแล้วใช้ซ้ำทุกรอบ
    key = str(uuid.uuid4())
    body = {"book_id": "bk_0002", "member_id": "mb_0001"}
    first = request_with_retry(client, "POST", "/v1/loans", json=body, headers={"Idempotency-Key": key})
    again = request_with_retry(client, "POST", "/v1/loans", json=body, headers={"Idempotency-Key": key})
    print("POST ครั้งแรก:", first.status_code, first.json()["id"])
    print("POST ซ้ำด้วย Key เดิม:", again.status_code, again.json()["id"],
          "Idempotent-Replayed =", again.headers.get("Idempotent-Replayed"))

HTTP Caching (ETag/304), CORS, Webhook ที่เซ็นด้วย HMAC และ OWASP API Top 10

คืออะไร ทำไมต้องใช้ และใช้เมื่อไร

แนวคิดสุดท้ายรวมเรื่องที่อยู่ "ขอบ" ของ API คือจุดที่ API คุยกับ Cache, เบราว์เซอร์ และระบบภายนอก ทั้งสี่เรื่องนี้ถ้าทำผิดจะเกิดปัญหาด้านประสิทธิภาพหรือความปลอดภัยทันที

1. HTTP Caching: Header Cache-Control บอกว่า Response เก็บไว้ใช้ซ้ำได้แค่ไหน ค่าที่ใช้บ่อยคือ max-age=60 (ใช้ซ้ำได้ 60 วินาทีโดยไม่ต้องถาม), no-cache (เก็บได้แต่ต้องถาม Server ก่อนใช้ทุกครั้ง), no-store (ห้ามเก็บเลย ใช้กับข้อมูลส่วนตัวที่อ่อนไหว), private (เก็บได้เฉพาะในเบราว์เซอร์ของผู้ใช้) และ public (Cache กลางทางเก็บได้) ส่วน ETag คือ "ลายนิ้วมือ" ของเนื้อหา Client ส่งกลับมาใน If-None-Match ถ้าไม่เปลี่ยน Server ตอบ 304 Not Modified ไม่มี Body ประหยัดแบนด์วิดท์ และ ETag เดียวกันยังใช้กัน "แก้ทับกัน" (Lost Update) ได้ด้วย Client ส่ง If-Match ตอน PATCH ถ้ามีคนแก้ไปก่อนแล้ว Server ตอบ 412 Precondition Failed

2. CORS (Cross-Origin Resource Sharing): เบราว์เซอร์มีกฎ Same-Origin Policy คือ JavaScript ของหน้าเว็บที่ http://localhost:5500 อ่าน Response จาก http://127.0.0.1:8000 ไม่ได้ (Origin ต่างกันเมื่อ Scheme, Host หรือ Port ต่างกัน) เว้นแต่ API อนุญาตด้วย Header Access-Control-Allow-Origin สำหรับ Request ที่ไม่ธรรมดา (เช่น PATCH หรือมี Header Authorization) เบราว์เซอร์จะส่ง Preflight เป็น OPTIONS มาถามก่อน CORS เป็นกลไกของเบราว์เซอร์เท่านั้น curl และ Server อื่นไม่สนใจ CORS จึงไม่ใช่ระบบความปลอดภัยแทน Authentication และห้ามใช้ Access-Control-Allow-Origin: * คู่กับ Credentials (Cookie หรือ Authorization) เพราะมาตรฐานห้ามและเบราว์เซอร์จะปฏิเสธ

3. Webhook: Server ของห้องสมุดส่ง Event เช่น loan.overdue ไปหา URL ของระบบอื่น ผู้รับต้องมั่นใจว่า Event มาจากห้องสมุดจริงและไม่ถูกแก้ วิธีมาตรฐานคือผู้ส่งเซ็นด้วย HMAC-SHA256 ของ timestamp.raw_body โดยใช้ Secret ที่รู้กันสองฝ่าย ส่งมาใน Header X-Webhook-Timestamp และ X-Webhook-Signature: sha256=... ผู้รับคำนวณซ้ำแล้วเทียบด้วย hmac.compare_digest ปฏิเสธ timestamp ที่เก่าเกิน 300 วินาที (กัน Replay) และจำ id ของ Event เพื่อไม่ประมวลผลซ้ำ (ในหลักสูตรนี้ Event ซ้ำตอบ 409)

4. OWASP API Security Top 10 (2023): รายการความเสี่ยงที่พบบ่อยที่สุดของ API ใช้เป็น Checklist ก่อนขึ้นระบบจริง ตารางท้ายแนวคิดนี้บอกว่าแต่ละข้อป้องกันด้วยแนวคิดไหนในหลักสูตร

def make_etag(data: dict) -> str:
    # แปลงเป็น JSON รูปแบบเดียวเสมอ (เรียง key, ไม่มีช่องว่าง) แล้ว hash ใส่เครื่องหมายคำพูดตามมาตรฐาน
    canonical = json.dumps(data, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
    return '"' + hashlib.sha256(canonical.encode()).hexdigest()[:16] + '"'


def etag_matches(header_value: str, etag: str) -> bool:
    # รองรับหลายค่า คั่นด้วย , และค่าที่ขึ้นต้น W/ (Weak) สำหรับ If-None-Match
    candidates = [v.strip().removeprefix("W/") for v in header_value.split(",")]
    return "*" in candidates or etag in candidates


def get_book_or_404(book_id: str) -> dict:
    if book_id not in BOOKS:
        raise ProblemError("book-not-found", "Book Not Found", 404, f"ไม่พบหนังสือรหัส {book_id}")
    return BOOKS[book_id]


@app.get("/books/{book_id}")
def get_book(book_id: str, response: Response, if_none_match: str | None = Header(default=None)):
    book = get_book_or_404(book_id)
    etag = make_etag(book)
    headers = {"ETag": etag, "Cache-Control": "no-cache"}   # no-cache = เก็บได้ แต่ต้องถามใหม่ทุกครั้ง
    if if_none_match and etag_matches(if_none_match, etag):
        return Response(status_code=304, headers=headers)  # ไม่เปลี่ยน ไม่ต้องส่ง Body ซ้ำ
    response.headers.update(headers)
    return book


class BookPatch(BaseModel):
    title: str | None = None
    status: str | None = None


@app.patch("/books/{book_id}")
def patch_book(book_id: str, patch: BookPatch, response: Response,
               if_match: str | None = Header(default=None)):
    book = get_book_or_404(book_id)
    current = make_etag(book)
    # If-Match ใช้ Strong Comparison: ต้องตรงทุกตัวอักษร (ไม่รับ W/)
    if if_match is not None and current not in [v.strip() for v in if_match.split(",")]:
        raise ProblemError("precondition-failed", "Precondition Failed", 412,
                           "ข้อมูลถูกแก้ไขไปแล้ว โปรด GET ใหม่แล้วลองอีกครั้ง", current_etag=current)
    book.update(patch.model_dump(exclude_unset=True))
    response.headers["ETag"] = make_etag(book)
    return book

seen_event_ids: set[str] = set()


@app.post("/webhooks/library", status_code=204)
async def receive_webhook(request: Request,
                          x_webhook_timestamp: str = Header(),
                          x_webhook_signature: str = Header()):
    raw = await request.body()   # ต้องใช้ Body ดิบ (bytes) ห้ามแปลงเป็น JSON แล้วแปลงกลับ
    if not x_webhook_timestamp.isdigit() or abs(time.time() - int(x_webhook_timestamp)) > TOLERANCE_SECONDS:
        raise ProblemError("unauthorized", "Unauthorized", 401, "timestamp เก่าเกิน 300 วินาที หรือรูปแบบผิด")
    signed = x_webhook_timestamp.encode() + b"." + raw
    expected = "sha256=" + hmac.new(WEBHOOK_SECRET.encode(), signed, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, x_webhook_signature):   # เทียบแบบเวลาคงที่ กัน Timing Attack
        raise ProblemError("unauthorized", "Unauthorized", 401, "ลายเซ็น Webhook ไม่ถูกต้อง")
    event = json.loads(raw)
    if event["id"] in seen_event_ids:
        raise ProblemError("duplicate-event", "Duplicate Event", 409, f"เคยรับ event {event['id']} แล้ว")
    seen_event_ids.add(event["id"])
    print(f"รับ event {event['id']} ชนิด {event['type']} ของ loan {event['data']['loan_id']}")
    return Response(status_code=204)

import argparse
import hashlib
import hmac
import json
import os
import time

import httpx

parser = argparse.ArgumentParser()
parser.add_argument("--url", default="http://127.0.0.1:8000/webhooks/library")
parser.add_argument("--event-id", default="evt_0001")
parser.add_argument("--tamper", action="store_true", help="แก้ Body หลังเซ็นแล้ว (จำลองคนดักแก้ข้อมูล)")
parser.add_argument("--old", action="store_true", help="ใช้ timestamp เมื่อ 10 นาทีก่อน (จำลอง Replay)")
args = parser.parse_args()

secret = os.environ.get("WEBHOOK_SECRET")
if not secret:
    raise SystemExit("ไม่พบ WEBHOOK_SECRET ใน Environment")

event = {
    "id": args.event_id,
    "type": "loan.overdue",
    "created_at": "2026-10-30T09:00:00+07:00",
    "data": {"loan_id": "ln_0001", "member_id": "mb_0002", "due_date": "2026-10-29"},
}
raw = json.dumps(event, separators=(",", ":")).encode()
timestamp = str(int(time.time()) - (600 if args.old else 0))
signature = hmac.new(secret.encode(), timestamp.encode() + b"." + raw, hashlib.sha256).hexdigest()

if args.tamper:
    raw = raw.replace(b"mb_0002", b"mb_0001")   # เปลี่ยนเนื้อหาหลังเซ็น

r = httpx.post(args.url, content=raw, headers={
    "Content-Type": "application/json",
    "X-Webhook-Timestamp": timestamp,
    "X-Webhook-Signature": f"sha256={signature}",
})
print(r.status_code, r.text or "(ไม่มี Body)")

Best Practice
  • ทุก GET ของ Resource เดี่ยวควรมี ETag และทุก PATCH/PUT ควรรองรับ If-Match เพื่อกันการแก้ทับกัน
  • ข้อมูลส่วนตัว (เช่น รายการยืมของสมาชิก) ใช้ Cache-Control: private, no-store หรือ no-cache ห้ามให้ Cache กลางทางเก็บ
  • CORS ใช้ Allow-list ที่ตั้งค่าจาก Environment แยกตามสภาพแวดล้อม (Dev, Staging, Production)
  • Webhook ต้องมีลายเซ็น, timestamp, Event ID และผู้รับต้องตอบ 2xx เร็วๆ แล้วไปประมวลผลต่อเบื้องหลัง
  • ใช้ OWASP API Top 10 เป็น Checklist ในการรีวิว API ทุกครั้งก่อนขึ้นระบบจริง
