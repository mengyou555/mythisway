8.1Learning Roadmap

ภาพรวมเส้นทาง

API Design คือการออกแบบ "สัญญา" ที่โปรแกรมสองฝั่งใช้คุยกัน ฝั่งหนึ่งเรียกว่า Client (เช่น แอปมือถือ หน้าเว็บ หรือสคริปต์ของบริษัทคู่ค้า) อีกฝั่งเรียกว่า Server (โปรแกรมที่เก็บข้อมูลและทำงานให้) สัญญานี้บอกว่า Client ต้องส่งอะไรมา ส่งไปที่ไหน และจะได้อะไรกลับไป ถ้าสัญญาชัดเจน ทีม Frontend ทีม Mobile และทีม Backend ก็ทำงานพร้อมกันได้โดยไม่ต้องรอกัน

หัวข้อนี้อยู่ลำดับที่ 10 ของเส้นทางที่แนะนำ ต่อจาก เหตุผลคือคุณเข้าใจ HTTP จาก แล้ว และเขียนภาษาฝั่ง Server ได้แล้วทั้ง และ ตอนนี้จึงพร้อมเรียนวิธีออกแบบ API อย่างเป็นระบบ ไม่ใช่แค่ "เขียนให้มันทำงานได้" แต่ออกแบบให้คนอื่นใช้ง่าย ปลอดภัย และแก้ไขต่อได้โดยไม่ทำให้ Client เดิมพัง

เส้นทางนี้มี 13 ขั้นใน 3 ระดับ ระดับ Beginner ปูพื้นเรื่อง API คืออะไร HTTP สำหรับ API การออกแบบ JSON และหลักการ REST ระดับ Intermediate สอน Query Parameter และ Pagination รูปแบบ Error ตามมาตรฐาน RFC 9457 การสร้าง Reference API ด้วย FastAPI การเขียน OpenAPI 3.1 และการทำงานแบบ Contract-first ด้วย Spectral และ Prism ระดับ Advanced ลงลึกเรื่อง Authentication และ Authorization, Versioning, Idempotency, Rate Limiting, Caching, CORS, Webhook, ความปลอดภัยตาม OWASP API Security Top 10 (2023) และเปรียบเทียบ REST กับ GraphQL และ gRPC

ใช้เวลารวมประมาณ 37–50 ชั่วโมง (ช่วงที่วางไว้สำหรับหัวข้อนี้คือ 30–50 ชั่วโมง) ถ้าเรียนวันละ 1–1.5 ชั่วโมง สัปดาห์ละ 6 วัน จะจบในราว 7–8 สัปดาห์ ทุกขั้นมี Checkpoint ที่บอกชัดว่าคุณต้องทำอะไรได้ก่อนไปขั้นถัดไป

  1. Beginner Step 1 · API คืออะไร รูปแบบของ API และแนวคิดเรื่อง "สัญญา"
  2. Beginner Step 2 · HTTP สำหรับ API: Method, Safe, Idempotent, Status Code และ Header
  3. Beginner Step 3 · ออกแบบ JSON: โครงสร้างข้อมูล ชนิดข้อมูล และ Naming Convention
  4. Beginner Step 4 · หลักการ REST และการตั้งชื่อ Resource กับ URL
  5. Intermediate Step 5 · Query Parameter: Filtering, Sorting และ Pagination (Offset กับ Cursor)
  6. Intermediate Step 6 · ออกแบบ Error ด้วย RFC 9457 Problem Details
  7. Intermediate Step 7 · สร้าง Reference API ด้วย FastAPI และทดสอบด้วย curl กับ pytest
  8. Intermediate Step 8 · OpenAPI 3.1: เขียนสเปกด้วย YAML และสร้างเอกสารด้วย Swagger UI / Redoc
  9. Intermediate Step 9 · Contract-first Workflow: Lint ด้วย Spectral และ Mock ด้วย Prism
  10. Advanced Step 10 · Authentication และ Authorization: API Key, OAuth 2.0, OpenID Connect และ JWT
  11. Advanced Step 11 · Evolution และ Reliability: Versioning, Idempotency Key, Rate Limiting และ Caching
  12. Advanced Step 12 · API Security: CORS และ OWASP API Security Top 10 (2023)
  13. Advanced Step 13 · Webhook, GraphQL, gRPC และ Mini Project: Library API Spec

เปรียบเทียบ

API เหมือนเมนูและพนักงานรับออร์เดอร์ของร้านอาหาร ลูกค้า (Client) ไม่ต้องเดินเข้าครัว (Server) และไม่ต้องรู้ว่าเชฟทำอาหารอย่างไร ลูกค้าแค่สั่งตามเมนู เช่น "ข้าวผัดกุ้ง 1 จาน ไม่ใส่ผัก" แล้วได้อาหารตามที่เมนูสัญญาไว้ ถ้าสั่งของที่ไม่มีในเมนู พนักงานก็ตอบกลับอย่างสุภาพว่าไม่มี (เหมือน Status Code 404) การออกแบบ API ก็คือการออกแบบเมนูนี้ ให้อ่านง่าย สั่งได้ไม่กำกวม และเมื่อร้านปรับสูตรในครัว ลูกค้าก็ยังสั่งแบบเดิมได้

คำศัพท์ที่ต้องรู้ก่อนเริ่ม

คำศัพท์ 12 คำนี้จะเจอตลอดทั้งหัวข้อ ทั้งใน Part 2 แบบฝึกหัดใน Part 3 และ Mini Project ใน Part 4 และเป็นคำที่ผู้สัมภาษณ์งานตำแหน่ง Backend Developer มักถามให้อธิบาย

คำศัพท์ความหมายตัวอย่างที่จะเจอในหัวข้อนี้
APIย่อมาจาก Application Programming Interface คือช่องทางที่โปรแกรมหนึ่งเปิดให้โปรแกรมอื่นเรียกใช้ พร้อมกติกาว่าต้องเรียกอย่างไรLibrary API ที่ให้ Client ค้นหนังสือ สมัครสมาชิก และยืมหนังสือ
Endpointจุดที่ Client เรียกได้ ประกอบด้วย Method กับ PathGET /books และ POST /loans
Resourceสิ่งที่ API จัดการ มักเป็นคำนาม มีตัวตน (ID) ของตัวเองหนังสือ (book) สมาชิก (member) การยืม (loan)
Request / Responseข้อความที่ Client ส่งไป และข้อความที่ Server ตอบกลับ แต่ละข้อความมี Header และอาจมี BodyRequest ที่มี Body เป็น JSON และ Response ที่มี Status Code 201
Status Codeตัวเลข 3 หลักที่บอกผลของ Request เช่น 2xx สำเร็จ 4xx Client ผิด 5xx Server ผิด200 OK, 201 Created, 404 Not Found, 429 Too Many Requests
Headerข้อมูลกำกับของ Request หรือ Response ในรูป ชื่อ: ค่าContent-Type, Authorization, ETag, Retry-After
Payload / Bodyเนื้อหาหลักของข้อความ ใน API สมัยใหม่ส่วนใหญ่เป็น JSON{"title": "Python 101", "isbn": "9786160000011"}
Schemaคำอธิบายรูปร่างของข้อมูล เช่น มีฟิลด์อะไร ชนิดอะไร ฟิลด์ไหนบังคับSchema Book ใน components/schemas ของ OpenAPI
Contractข้อตกลงที่เขียนไว้เป็นลายลักษณ์อักษรระหว่าง Client กับ Server ว่า API ทำงานอย่างไรไฟล์ openapi.yaml ที่ทุกทีมยึดเป็นความจริงเดียวกัน
OpenAPIมาตรฐานเปิดสำหรับเขียน Contract ของ HTTP API ด้วย YAML หรือ JSON หัวข้อนี้ใช้เวอร์ชัน 3.1เปิดดูเอกสารด้วย Swagger UI และ Redoc ตรวจด้วย Spectral
Mock ServerServer ปลอมที่ตอบตามตัวอย่างใน Contract ใช้ทดลองก่อนเขียน Server จริงnpx @stoplight/prism-cli@5.16.0 mock openapi.yaml
Authentication / AuthorizationAuthentication ตอบว่า "คุณเป็นใคร" Authorization ตอบว่า "คุณทำสิ่งนี้ได้หรือไม่"401 Unauthorized เมื่อไม่ส่ง Token และ 403 Forbidden เมื่อ Token ถูกแต่ไม่มีสิทธิ์

รูปแบบของ API ที่จะเจอในงานจริง

API มีหลายรูปแบบ (API Style) แต่ละแบบเหมาะกับงานต่างกัน หัวข้อนี้เน้น REST over HTTP + JSON เพราะเป็นแบบที่ใช้มากที่สุดในงาน Backend และเป็นพื้นฐานที่ทำให้เข้าใจแบบอื่นได้เร็ว ส่วนแบบอื่นจะเรียนเปรียบเทียบใน Step 13

รูปแบบลักษณะเหมาะกับเรียนในขั้นไหน
REST (HTTP + JSON)มองทุกอย่างเป็น Resource ที่มี URL ใช้ HTTP Method บอกการกระทำ ใช้ Status Code บอกผลPublic API, Web API และ Mobile Backend ทั่วไปStep 2–12
GraphQLมี Endpoint เดียว Client เขียน Query บอกเองว่าต้องการฟิลด์ไหน Server มี Schema แบบ Strongly Typedหน้าจอที่ต้องดึงข้อมูลหลายชนิดพร้อมกัน และ Client หลายแบบที่ต้องการข้อมูลไม่เท่ากันStep 13
gRPCเรียกฟังก์ชันข้ามเครื่อง (RPC) บน HTTP/2 ส่งข้อมูลแบบ Binary ด้วย Protocol Buffers มี StreamingService คุยกันภายในองค์กร (Microservices) ที่ต้องการความเร็วและ Type ที่เข้มงวดStep 13
Webhookกลับทิศ: Server ของผู้ให้บริการเป็นฝ่ายส่ง HTTP POST มาหาเราเมื่อมีเหตุการณ์เกิดขึ้นแจ้งผลการชำระเงิน แจ้งว่ามี Commit ใหม่ แจ้งว่าคิวงานเสร็จStep 13
WebSocket / Server-Sent Eventsเปิดการเชื่อมต่อค้างไว้ Server ส่งข้อมูลมาได้ตลอดเวลาแชต แจ้งเตือนแบบ Real-time และการ Stream คำตอบของ LLMกล่าวถึงใน Step 1 (เรียนลึกใน )
SOAPรูปแบบเก่าที่ใช้ XML และมีมาตรฐานเข้มงวดระบบธนาคารหรือระบบราชการรุ่นเก่าที่ยังต้องเชื่อมต่อกล่าวถึงใน Step 1

  • บทบาทของ Client และ Server ในระบบจริง เช่น แอปมือถือธนาคาร หน้าเว็บร้านค้า และ Service ภายในบริษัทที่เรียกกันเอง
  • รูปแบบของ API: REST, GraphQL, gRPC, Webhook, WebSocket และ SOAP ว่าต่างกันอย่างไรในระดับภาพรวม
  • Public API, Partner API และ Internal API ต่างกันอย่างไร และทำไม Public API ต้องออกแบบรอบคอบที่สุด (แก้ทีหลังยากที่สุด)
  • แนวคิด "API คือสัญญา" (API as a Contract) และ "API คือผลิตภัณฑ์" (API as a Product) ที่ผู้ใช้คือนักพัฒนาคนอื่น
  • ลักษณะของ API ที่ดี: คาดเดาได้ (Predictable) สม่ำเสมอ (Consistent) มีเอกสาร ปลอดภัย และเปลี่ยนแปลงได้โดยไม่ทำให้ Client เดิมพัง
  • ลองเรียก Public API ที่ไม่ต้องใช้ Key ด้วยเบราว์เซอร์และ curl แล้วสังเกตว่า Response เป็น JSON
  • วิธีอ่านเอกสาร API ของผู้ให้บริการจริง: หา Base URL, วิธียืนยันตัวตน, รายการ Endpoint, ตัวอย่าง Request และรูปแบบ Error
ทำไมต้องเรียน
งานเกือบทุกสายในหลักสูตรนี้ต้องเรียกหรือสร้าง API ไม่ว่าจะเป็น Backend ที่สร้าง API ให้แอป Frontend ที่เรียก API มาแสดงผล หรือ AI Engineer ที่เรียก LLM API ถ้าเข้าใจว่า API คือสัญญา คุณจะเริ่มคิดจากมุมของ "คนที่ต้องใช้" ไม่ใช่แค่ "คนที่เขียน" ซึ่งเป็นความต่างระหว่าง API ที่คนชอบใช้กับ API ที่คนบ่น
ใช้เวลา
2–3 ชั่วโมง: อ่านและดูภาพรวม 1 ชั่วโมง ลองเรียก API ด้วยเบราว์เซอร์และ curl 30 นาที อ่านเอกสาร API จริง 1 ชุดแล้วจดสรุป 30–60 นาที
ฝึกอะไร
เลือกเอกสาร API ของบริการที่คุณใช้อยู่ 1 แห่ง แล้วเขียนสรุปลงไฟล์ ~/projects/api-lab/notes/step01.md ว่า Base URL คืออะไร ยืนยันตัวตนอย่างไร มี Endpoint อะไรบ้าง 5 ตัว และ Error หน้าตาเป็นอย่างไร
Checkpoint

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) อธิบายเป็นภาษาของตัวเองได้ภายใน 1 นาทีว่า API คืออะไร และยกตัวอย่าง Client กับ Server ได้ 3 คู่ (2) บอกความต่างของ REST, GraphQL, gRPC และ Webhook ได้อย่างละ 1 ประโยค (3) ใช้ curl เรียก API ที่ไม่ต้องใช้ Key แล้วชี้ได้ว่าส่วนไหนของ Response คือ JSON (4) อ่านเอกสาร API จริงแล้วสรุป Base URL, วิธียืนยันตัวตน และ Endpoint 5 ตัวได้

STEP 2

HTTP สำหรับ API: Method, Safe, Idempotent, Status Code และ Header

สัปดาห์ที่ 1–2 · 4–5 ชม.
หัวข้อย่อย
  • โครงสร้าง HTTP Request (Method, Path, Query String, Header, Body) และ HTTP Response (Status Line, Header, Body) อ่านจากผลของ curl -i และ curl -v
  • HTTP Method หลัก: GET อ่าน, POST สร้างหรือสั่งงาน, PUT แทนที่ทั้งก้อน, PATCH แก้บางส่วน, DELETE ลบ, และ HEAD กับ OPTIONS
  • คุณสมบัติ Safe (ไม่เปลี่ยนข้อมูลบน Server: GET, HEAD, OPTIONS) และ Idempotent (ส่งซ้ำกี่ครั้งผลบน Server เท่ากับส่งครั้งเดียว: GET, HEAD, OPTIONS, PUT, DELETE) และทำไม POST กับ PATCH ไม่ Idempotent โดยธรรมชาติ
  • Status Code กลุ่ม 2xx: 200 OK, 201 Created (พร้อม Header Location), 202 Accepted (งานที่ทำเบื้องหลัง), 204 No Content
  • Status Code กลุ่ม 3xx ที่เกี่ยวกับ API: 301, 304 Not Modified (ใช้กับ Caching ใน Step 11)
  • Status Code กลุ่ม 4xx: 400, 401, 403, 404, 405, 409 Conflict, 412 Precondition Failed, 415 Unsupported Media Type, 422 Unprocessable Content, 429 Too Many Requests และวิธีเลือกระหว่าง 400 กับ 422 และระหว่าง 401 กับ 403
  • Status Code กลุ่ม 5xx: 500, 502, 503 (มักมาพร้อม Retry-After), 504 และหลักว่าห้ามใช้ 5xx กับความผิดของ Client
  • Header สำคัญ: Content-Type, Accept, Authorization, Location, Cache-Control, ETag, Retry-After, User-Agent และ Header ที่ตั้งเอง
  • ใช้ curl ให้คล่อง: -i, -v, -X, -H, -d, --json, -s, -o /dev/null -w '%{http_code}' และส่งผลต่อให้ jq
ทำไมต้องเรียน
HTTP คือภาษากลางของ Web API ถ้าเลือก Method หรือ Status Code ผิด Client จะตัดสินใจผิดตามไปด้วย เช่น ตอบ 200 พร้อมข้อความ Error ใน Body ทำให้ระบบ Monitoring มองไม่เห็นปัญหา หรือใช้ GET ลบข้อมูล ทำให้ Crawler ที่แค่เปิดลิงก์ลบข้อมูลไปโดยไม่ตั้งใจ ความรู้เรื่อง Idempotent เป็นพื้นฐานของการ Retry อย่างปลอดภัยใน Step 11
ใช้เวลา
4–5 ชั่วโมง: Method และ Safe/Idempotent 1 ชั่วโมง Status Code 1.5 ชั่วโมง Header 1 ชั่วโมง ฝึก curl กับ Server ตัวอย่างบนเครื่องตัวเอง 1–1.5 ชั่วโมง
ฝึกอะไร
รัน Server ตัวอย่างจาก Part 2 แนวคิดที่ 1–2 บน 127.0.0.1:8000 แล้วยิงทุก Method ด้วย curl -i จดว่าแต่ละครั้งได้ Status Code อะไร และ Header ไหนเปลี่ยนไป
ระวัง

มือใหม่มักใช้ 200 OK กับทุกกรณีแล้วใส่ "success": false ใน Body วิธีนี้ทำให้ Client, Proxy, ระบบ Cache และระบบ Monitoring ตีความผิดทั้งหมด ให้ Status Code บอกผลจริงเสมอ

Checkpoint

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) บอกได้ว่า Method ไหน Safe และ Method ไหน Idempotent ครบทั้ง 7 Method โดยไม่เปิดดู (2) เลือก Status Code ที่ถูกต้องให้สถานการณ์ 10 แบบได้ เช่น สร้างสำเร็จ (201), ลบสำเร็จไม่มี Body (204), ไม่ได้ส่ง Token (401), ยืมหนังสือที่ถูกยืมไปแล้ว (409), ข้อมูลผิดรูปแบบ (422), ยิงถี่เกินไป (429) (3) ใช้ curl -i ส่ง POST พร้อม JSON Body แล้วอ่าน Status Code, Content-Type และ Location จาก Response ได้ (4) อธิบายได้ว่าทำไมห้ามใช้ GET กับการกระทำที่เปลี่ยนข้อมูล

STEP 3

ออกแบบ JSON: โครงสร้างข้อมูล ชนิดข้อมูล และ Naming Convention

สัปดาห์ที่ 2 · 2–3 ชม.
หัวข้อย่อย
  • ชนิดข้อมูลของ JSON ทั้ง 6 แบบ (string, number, boolean, null, object, array) และสิ่งที่ JSON ไม่มี เช่น วันที่ จำนวนเงิน และ Comment
  • Naming Convention: เลือก snake_case หรือ camelCase แล้วใช้แบบเดียวทั้ง API หัวข้อนี้ใช้ snake_case ให้ตรงกับ Python และ Pydantic
  • วันที่และเวลาใช้รูปแบบ RFC 3339 / ISO 8601 พร้อม Timezone เช่น "2026-10-19T09:30:00+07:00" และวันที่อย่างเดียว เช่น "2026-11-02"
  • จำนวนเงิน: ห้ามใช้ Float ให้ใช้จำนวนเต็มในหน่วยย่อยที่สุด (สตางค์) เช่น "fine_satang": 2500 หรือส่งเป็น String ทศนิยมพร้อมสกุลเงิน
  • ID: ใช้ String ที่ Client ไม่ต้องตีความ (Opaque ID) และไม่เปิดเผยลำดับภายใน ความต่างของ Auto-increment ID กับ UUID
  • null กับ "ไม่มีฟิลด์" ต่างกันอย่างไร และสำคัญอย่างไรกับ PATCH
  • รูปร่างของ Response: ส่ง Object ตรง ๆ กับห่อด้วย Envelope เช่น {"data": [...], "next_cursor": "..."} และเหตุผลที่ Collection ควรห่อด้วย Object เสมอ (เพิ่มฟิลด์ทีหลังได้)
  • Enum เป็น String ตัวพิมพ์เล็ก เช่น "status": "on_loan" และการออกแบบให้เพิ่มค่าใหม่ได้โดยไม่ทำให้ Client พัง
ทำไมต้องเรียน
JSON คือสิ่งที่ Client เห็นมากที่สุด ถ้าชื่อฟิลด์ไม่สม่ำเสมอ วันที่ไม่มี Timezone หรือเงินเป็น Float ทุกทีมที่ใช้ API ต้องเขียนโค้ดแก้ปัญหาเอง และเมื่อ API เผยแพร่ไปแล้ว การเปลี่ยนชื่อฟิลด์ถือเป็น Breaking Change ที่แก้ยากมาก
ใช้เวลา
2–3 ชั่วโมง: ชนิดข้อมูลและ Naming 45 นาที วันที่ เงิน และ ID 45 นาที ฝึกออกแบบ JSON ของ Book, Member และ Loan 1–1.5 ชั่วโมง
ฝึกอะไร
เขียนไฟล์ ~/projects/api-lab/notes/library-json.md ที่มีตัวอย่าง JSON ของ Book, Member และ Loan ครบทุกฟิลด์ แล้วตรวจว่าเป็น JSON ที่ถูกต้องด้วย jq . book.json
Best Practice

เขียน "พจนานุกรมฟิลด์" (Field Glossary) ของ API ไว้ตั้งแต่แรก เช่น ทุกเวลาลงท้ายด้วย _at (created_at, returned_at) ทุกวันที่ลงท้ายด้วย _on หรือ _date (due_date) ทุก Boolean ขึ้นต้นด้วย is_ หรือ has_ แล้วใช้ตามนี้ตลอด Spectral ใน Step 9 จะช่วยตรวจกฎเหล่านี้ให้อัตโนมัติ

Checkpoint

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) เขียน JSON ของ Book, Member และ Loan ที่ผ่าน jq . และใช้ snake_case ทุกฟิลด์ (2) เขียนเวลาในรูปแบบ RFC 3339 พร้อม Timezone ได้ถูกต้อง (3) อธิบายได้ว่าทำไมไม่ควรเก็บเงินเป็น Float และเสนอทางเลือกได้ 2 แบบ (4) อธิบายความต่างของ "phone": null กับการไม่ส่งฟิลด์ phone ใน Request แบบ PATCH ได้

STEP 4

หลักการ REST และการตั้งชื่อ Resource กับ URL

สัปดาห์ที่ 2–3 · 3–4 ชม.
หัวข้อย่อย
  • ที่มาของ REST (Roy Fielding, ปี 2000) และข้อจำกัดหลัก: Client-Server, Stateless, Cacheable, Uniform Interface, Layered System
  • Stateless หมายความว่าทุก Request ต้องมีข้อมูลครบในตัว (เช่น Token) Server ไม่จำว่า Request ก่อนหน้าคืออะไร และผลดีต่อการขยายระบบ
  • Resource เป็นคำนามพหูพจน์: /books, /books/{book_id}, /members ไม่ใช่คำกริยาอย่าง /getBooks หรือ /createMember
  • Nested Resource กับความสัมพันธ์: /members/{member_id}/loans และกฎว่าไม่ควรซ้อนลึกเกิน 2 ระดับ
  • การกระทำที่ไม่ใช่ CRUD: มองเป็น Resource ใหม่ (POST /loans แทน "ยืม", POST /loans/{loan_id}/return สำหรับ "คืน") และเมื่อไรใช้ Sub-resource แบบคำกริยาได้
  • รูปแบบ URL: ตัวพิมพ์เล็ก คั่นคำด้วย - ใน Path ไม่มีนามสกุลไฟล์ ไม่มี / ท้าย และไม่ใส่ข้อมูลลับใน URL
  • HATEOAS (กล่าวโดยย่อ): ใส่ลิงก์ไปยังการกระทำถัดไปใน Response และระดับความเป็น REST ตาม Richardson Maturity Model (Level 0–3)
  • ออกแบบตาราง Endpoint ของ Library API ทั้งระบบ: Method, Path, ความหมาย, Status Code เมื่อสำเร็จ และ Status Code เมื่อผิดพลาด
ทำไมต้องเรียน
URL คือหน้าตาของ API ถ้าตั้งชื่อดี นักพัฒนาเดาได้เองว่า Endpoint ถัดไปชื่ออะไรโดยไม่ต้องเปิดเอกสาร การเข้าใจ Stateless ทำให้ออกแบบระบบที่เพิ่ม Server ได้หลายเครื่องโดยไม่มีปัญหา และตาราง Endpoint ที่ได้จากขั้นนี้จะกลายเป็นโครงของไฟล์ OpenAPI ใน Step 8 โดยตรง
ใช้เวลา
3–4 ชั่วโมง: หลักการ REST และ Stateless 1 ชั่วโมง Resource และ URL Naming 1 ชั่วโมง ออกแบบตาราง Endpoint ของ Library API และรีวิวกับรายการตรวจ 1–2 ชั่วโมง
ฝึกอะไร
สร้างตาราง Endpoint ของ Library API อย่างน้อย 12 แถวในไฟล์ ~/projects/api-lab/notes/endpoints.md ครอบคลุม books, members, loans และการคืนหนังสือ แล้วเก็บไว้ใช้ต่อใน Step 8 และ Mini Project
เปรียบเทียบ

URL แบบ REST เหมือนที่อยู่บ้าน: /members/42/loans อ่านได้ว่า "สมาชิกหมายเลข 42 → รายการยืมของเขา" ส่วน Method คือสิ่งที่คุณทำกับที่อยู่นั้น เช่น ไปดู (GET) ส่งของไปให้ (POST) หรือรื้อถอน (DELETE) ที่อยู่ไม่ควรมีคำกริยา เพราะการกระทำบอกด้วย Method อยู่แล้ว

Checkpoint

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) แก้ URL ที่ออกแบบผิด 5 แบบให้ถูกตามหลัก REST ได้ เช่น /getAllBooks → GET /books และ /deleteMember?id=7 → DELETE /members/7 (2) อธิบายคำว่า Stateless พร้อมตัวอย่างได้ (3) มีตาราง Endpoint ของ Library API อย่างน้อย 12 แถว ที่ระบุ Method, Path และ Status Code ทั้งกรณีสำเร็จและกรณีผิดพลาด (4) ออกแบบการกระทำ "ยืม" และ "คืน" หนังสือเป็น Resource ได้ และบอกเหตุผลได้

ระดับ Intermediate: Query, Error, Reference API และ OpenAPI

ระดับนี้คุณจะลงมือสร้างของจริง เริ่มจากออกแบบการค้นหาและแบ่งหน้า กำหนดรูปแบบ Error มาตรฐาน แล้วสร้าง Reference API ด้วย FastAPI เพื่อเห็นว่าการออกแบบแต่ละข้อกลายเป็นโค้ดอย่างไร จากนั้นเขียน Contract เป็นไฟล์ OpenAPI 3.1 ด้วยมือ และจบด้วยการทำงานแบบ Contract-first ที่ทีมจริงใช้ คือเขียนสเปกก่อน ตรวจด้วย Spectral เปิด Mock ด้วย Prism แล้วค่อยเขียนโค้ด

STEP 5

Query Parameter: Filtering, Sorting และ Pagination (Offset กับ Cursor)

สัปดาห์ที่ 3 · 3–4 ชม.
หัวข้อย่อย
  • เมื่อไรใช้ Path Parameter (ระบุตัวตน เช่น /books/{book_id}) และเมื่อไรใช้ Query Parameter (กรอง เรียง แบ่งหน้า เช่น /books?author=somchai)
  • Filtering: ฟิลด์ตรงตัว (?status=available), ค้นหาข้อความ (?q=python), ช่วงค่า (?published_after=2020-01-01) และการรวมหลายเงื่อนไข
  • Sorting: รูปแบบ ?sort=-published_year,title (เครื่องหมาย - แปลว่าเรียงจากมากไปน้อย) และการจำกัดว่าฟิลด์ไหนเรียงได้
  • Offset Pagination: ?limit=20&offset=40 ข้อดี (กระโดดไปหน้าใดก็ได้ ทำง่ายด้วย SQL LIMIT/OFFSET) และข้อเสีย (ช้าเมื่อ Offset สูง ข้อมูลซ้ำหรือหายเมื่อมีการเพิ่มหรือลบระหว่างเลื่อนหน้า)
  • Cursor Pagination: ?limit=20&cursor=eyJpZCI6NDB9 ที่ Cursor เป็น Opaque String (เช่น Base64 ของ ID ตัวสุดท้าย) ข้อดีเรื่องความเร็วและความถูกต้อง และข้อจำกัดที่กระโดดหน้าไม่ได้
  • บอก Client ว่ามีหน้าถัดไปหรือไม่: ฟิลด์ next_cursor ใน Body และ Header Link ที่มี rel="next" ตาม RFC 8288
  • ค่าเริ่มต้นและค่าสูงสุดของ limit (เช่น ค่าเริ่มต้น 20 สูงสุด 100) และการตอบ 422 เมื่อส่งค่าผิด
  • Sparse Fieldset (?fields=id,title) และการขยายข้อมูลที่เกี่ยวข้อง (?expand=member) แบบเลือกได้
ทำไมต้องเรียน
ทุก Endpoint ที่คืนรายการต้องแบ่งหน้าตั้งแต่วันแรก ถ้าคืนข้อมูลทั้งหมดในครั้งเดียว วันที่ห้องสมุดมีหนังสือ 1 แสนเล่ม Server จะช้าและ Client จะค้าง การเพิ่ม Pagination ทีหลังเป็น Breaking Change เพราะ Client เดิมคาดว่าจะได้ข้อมูลครบ การเลือก Offset หรือ Cursor ให้เหมาะกับงานเป็นคำถามสัมภาษณ์ที่พบบ่อย
ใช้เวลา

รันตัวอย่าง Part 2 แนวคิดที่ 5 ที่มีหนังสือ 25 เล่ม แล้วเดินครบทุกหน้าทั้งแบบ Offset และ Cursor ด้วย curl และ jq จากนั้นลองเพิ่มหนังสือระหว่างเลื่อนหน้า แล้วสังเกตว่าแบบไหนได้ข้อมูลซ้ำ

STEP 6

ออกแบบ Error ด้วย RFC 9457 Problem Details

สัปดาห์ที่ 3–4 · 2–3 ชม.
หัวข้อย่อย
  • ปัญหาของ Error ที่แต่ละ Endpoint ตอบไม่เหมือนกัน และเหตุผลที่ต้องมีรูปแบบ Error เดียวทั้ง API
  • RFC 9457 "Problem Details for HTTP APIs" (ออกปี 2023 แทน RFC 7807) และ Media Type application/problem+json
  • ฟิลด์มาตรฐาน: type (URI ที่ระบุชนิดปัญหา), title (สรุปสั้นที่ไม่เปลี่ยนตามกรณี), status (ตรงกับ HTTP Status Code), detail (คำอธิบายเฉพาะกรณีนี้), instance (URI ของเหตุการณ์นี้)
  • Extension Member: เพิ่มฟิลด์ของตัวเอง เช่น errors ที่เป็นรายการฟิลด์ที่ผิด สำหรับ Validation Error และ trace_id สำหรับตามหา Log
  • การจับคู่สถานการณ์กับ Status Code และ type เช่น หนังสือถูกยืมไปแล้ว → 409 + https://example.com/problems/book-unavailable
  • ข้อความ Error ที่ช่วยผู้ใช้: บอกว่าผิดอะไรและแก้อย่างไร แต่ไม่เปิดเผย Stack Trace, SQL หรือข้อมูลภายใน
  • เขียน Error Catalog: ตารางรวมทุก type ที่ API อาจตอบ พร้อม Status Code และวิธีแก้ เพื่อใส่ในเอกสาร
  • Error ของ 5xx: ตอบรูปแบบเดียวกัน แต่ detail เป็นข้อความกลาง ๆ และบันทึกรายละเอียดจริงลง Log ฝั่ง Server
ทำไมต้องเรียน
Client ใช้เวลาจัดการ Error มากกว่ากรณีสำเร็จหลายเท่า ถ้า Error มีรูปแบบมาตรฐาน Client เขียนโค้ดจัดการครั้งเดียวใช้ได้ทุก Endpoint และแสดงข้อความที่เข้าใจได้ให้ผู้ใช้ปลายทาง การใช้ RFC 9457 ยังทำให้เครื่องมือและไลบรารีหลายตัวเข้าใจ Error ของคุณได้ทันที Mini Project ในหัวข้อนี้กำหนดให้ทุก Error ใช้รูปแบบนี้
ใช้เวลา
2–3 ชั่วโมง: อ่านโครงสร้าง RFC 9457 45 นาที ออกแบบ Error Catalog ของ Library API 1 ชั่วโมง ลองใช้กับ FastAPI ใน Part 2 แนวคิดที่ 6 อีก 45–75 นาที
ฝึกอะไร
เขียน Error Catalog ของ Library API อย่างน้อย 8 รายการ เช่น validation-error (422), book-not-found (404), book-unavailable (409), loan-limit-reached (409), unauthorized (401), forbidden (403), rate-limited (429), internal-error (500)
Security

อย่าส่ง Exception Message จาก Database หรือ Stack Trace กลับไปใน detail เด็ดขาด ข้อมูลเหล่านี้บอกผู้โจมตีว่าคุณใช้ Database อะไร ชื่อตารางอะไร และมีช่องโหว่ตรงไหน ให้ส่ง trace_id กลับไปแทน แล้วใช้ค่านี้ค้นหารายละเอียดใน Log ฝั่ง Server

Checkpoint

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) เขียน Problem Details JSON ที่ถูกต้องตาม RFC 9457 สำหรับกรณีหนังสือถูกยืมไปแล้วได้ โดยมีครบทั้ง 5 ฟิลด์มาตรฐาน (2) บอกได้ว่า Response แบบนี้ต้องมี Content-Type: application/problem+json (3) ออกแบบ Validation Error ที่บอกได้ว่าผิดกี่ฟิลด์และผิดฟิลด์ไหน (4) มี Error Catalog ของ Library API อย่างน้อย 8 รายการพร้อม Status Code

STEP 10

Authentication และ Authorization: API Key, OAuth 2.0, OpenID Connect และ JWT

สัปดาห์ที่ 6 · 4–5 ชม.
หัวข้อย่อย
  • ความต่างของ Authentication (คุณเป็นใคร) กับ Authorization (คุณทำสิ่งนี้ได้ไหม) และการเลือก 401 Unauthorized (พร้อม Header WWW-Authenticate) กับ 403 Forbidden
  • API Key: ส่งใน Header เช่น X-API-Key ไม่ใช่ใน URL เก็บใน Server แบบ Hash หมุนเวียน (Rotate) ได้ และเหมาะกับ Server-to-Server ไม่ใช่การยืนยันตัวตนของผู้ใช้
  • OAuth 2.0 ในระดับแนวคิด: บทบาท Resource Owner, Client, Authorization Server, Resource Server และ Flow ที่ควรใช้ปัจจุบัน คือ Authorization Code + PKCE (แอปที่มีผู้ใช้) และ Client Credentials (Server-to-Server)
  • OpenID Connect (OIDC): ชั้นยืนยันตัวตนบน OAuth 2.0 ที่เพิ่ม ID Token ความต่างระหว่าง Access Token (ใช้เรียก API) กับ ID Token (บอกว่าผู้ใช้เป็นใคร) และเหตุผลที่ไม่ควรเขียนระบบ Login เองเมื่อใช้ Identity Provider ได้
  • โครงสร้าง JWT: Header, Payload, Signature คั่นด้วยจุด ถอดรหัส Base64URL ดูข้างในได้ (Payload ไม่ได้เข้ารหัส) Claim สำคัญ: sub, exp, iat, iss, aud, scope
  • จุดอ่อนของ JWT ที่ต้องรู้: ยอมรับ alg: none, ไม่กำหนดรายการ Algorithm ที่ยอมรับตอน Verify, Secret สั้นเดาได้, ไม่ตรวจ exp/aud/iss, ใส่ข้อมูลลับใน Payload, Token อายุยาวที่เพิกถอนไม่ได้ และการเก็บ Token ใน localStorage
  • สร้างและตรวจ JWT ด้วย PyJWT 2.15.1 (jwt.encode, jwt.decode(..., algorithms=["HS256"], audience=...)) และผูกเข้ากับ FastAPI ผ่าน Dependency
  • Authorization แบบ Scope และ Role (เช่น loans:write, Role librarian) และการตรวจความเป็นเจ้าของ Object ทุกครั้ง เพื่อกัน BOLA (สมาชิกคนหนึ่งดูรายการยืมของคนอื่นด้วยการเปลี่ยน ID)
ทำไมต้องเรียน
ช่องโหว่ของ API ที่พบบ่อยที่สุดในโลกจริงเกิดจากการตรวจสิทธิ์ผิดพลาด ไม่ใช่จากการเข้ารหัสที่อ่อน OWASP จัด Broken Object Level Authorization ไว้เป็นอันดับ 1 การเข้าใจ OAuth 2.0, OIDC และจุดอ่อนของ JWT ทำให้คุณคุยกับทีม Security ได้ตรงประเด็น และเลือกใช้ Identity Provider ได้ถูกต้อง แทนการเขียนระบบเองที่มีช่องโหว่
ใช้เวลา
4–5 ชั่วโมง: Authentication กับ Authorization และ API Key 1 ชั่วโมง OAuth 2.0 และ OIDC (แนวคิดและแผนภาพ Flow) 1.5 ชั่วโมง JWT และจุดอ่อน 1 ชั่วโมง ลงมือกับ PyJWT และ FastAPI 1–1.5 ชั่วโมง
ฝึกอะไร
เพิ่มการยืนยันตัวตนแบบ Bearer JWT ให้ Reference API จาก Step 7 อ่าน Secret จาก Environment Variable JWT_SECRET (ถ้าไม่ได้ตั้ง ให้โปรแกรมหยุดพร้อมข้อความชัดเจน) แล้วเขียน Test ที่ยืนยันว่าไม่มี Token ได้ 401, Token หมดอายุได้ 401, Token ที่ไม่มี Scope ได้ 403 และสมาชิกดูรายการยืมของคนอื่นไม่ได้
Security

ห้ามใส่ Secret หรือ API Key จริงในโค้ดหรือใน Git ให้อ่านจาก Environment Variable เสมอ เช่น os.environ["JWT_SECRET"] และเพิ่ม .env ลงใน .gitignore ตั้งแต่ Commit แรก ถ้าเผลอ Push Secret ขึ้น GitHub ให้ถือว่า Secret นั้นรั่วแล้ว และเปลี่ยนใหม่ทันที การลบ Commit ทีหลังไม่ช่วย

STEP 11

Evolution และ Reliability: Versioning, Idempotency Key, Rate Limiting และ Caching

สัปดาห์ที่ 6–7 · 3–4 ชม.
หัวข้อย่อย
  • Versioning 3 แบบ: ใน URL (/v1/books), ใน Header (เช่น API-Version: 2026-10-01) และใน Media Type (Accept: application/vnd.library.v2+json) ข้อดีข้อเสียของแต่ละแบบ และเหตุผลที่ API ส่วนใหญ่เลือกแบบ URL
  • Breaking กับ Non-breaking Change, การเพิ่มฟิลด์แบบไม่ทำให้ Client พัง และการประกาศเลิกใช้ด้วย Header Deprecation และ Sunset พร้อมช่วงเวลาให้ย้ายที่ชัดเจน
  • Idempotency Key สำหรับ POST: Client ส่ง Header Idempotency-Key ที่เป็น UUID เมื่อ Network หลุดแล้ว Retry ด้วย Key เดิม Server คืนผลเดิมแทนการสร้างซ้ำ และตอบ 409 หรือ 422 เมื่อใช้ Key เดิมกับ Body ที่ต่างไป
  • Retry อย่างถูกต้องฝั่ง Client: Retry เฉพาะ Request ที่ Idempotent หรือมี Idempotency Key ใช้ Exponential Backoff พร้อม Jitter และเคารพ Retry-After
  • Rate Limiting: อัลกอริทึม Fixed Window, Sliding Window และ Token Bucket การตอบ 429 Too Many Requests พร้อม Retry-After และการบอกโควตาที่เหลือผ่าน Header (รูปแบบมาตรฐานของ Header กลุ่ม RateLimit ยังเป็น Draft ของ IETF ให้ตรวจสถานะล่าสุดก่อนใช้)
  • HTTP Caching: Cache-Control (max-age, no-store, private, public), ETag กับ If-None-Match ที่ได้ 304 Not Modified และ Last-Modified
  • Conditional Update ป้องกันการเขียนทับกัน: ส่ง If-Match พร้อม ETag ตอน PUT/PATCH แล้วได้ 412 Precondition Failed เมื่อข้อมูลถูกคนอื่นแก้ไปก่อน
  • งานที่ใช้เวลานาน: ตอบ 202 Accepted พร้อม Location ของ Resource สถานะงาน แล้วให้ Client ตรวจสถานะ (Polling) หรือรอ Webhook
ทำไมต้องเรียน
API ที่มีผู้ใช้จริงต้องอยู่ได้หลายปี ต้องรับมือกับ Network ที่หลุดกลางทาง Client ที่ส่งซ้ำ และผู้ใช้ที่ยิงถี่ผิดปกติ ความรู้ในขั้นนี้ป้องกันปัญหาที่สร้างความเสียหายจริง เช่น สมาชิกถูกบันทึกการยืมซ้ำสองครั้ง หรือการชำระค่าปรับซ้ำเพราะผู้ใช้กดปุ่มสองครั้ง หัวข้อนี้เป็นคำถามสัมภาษณ์ระดับ Mid-level ที่พบบ่อย
ใช้เวลา
3–4 ชั่วโมง: Versioning และ Deprecation 45 นาที Idempotency Key และ Retry 1 ชั่วโมง Rate Limiting 45 นาที Caching และ Conditional Request 1–1.5 ชั่วโมง
ฝึกอะไร
เพิ่ม 3 ความสามารถให้ Reference API: POST /loans รองรับ Idempotency-Key, Rate Limit แบบง่ายที่ตอบ 429 พร้อม Retry-After และ GET /books/{book_id} ที่ส่ง ETag แล้วตอบ 304 เมื่อ Client ส่ง If-None-Match ตรงกัน ยืนยันทุกข้อด้วย curl -i
เปรียบเทียบ

Idempotency Key เหมือนเลขที่ใบสั่งซื้อ ถ้าคุณโทรสั่งพิซซ่าแล้วสายหลุด พอโทรกลับไปบอกเลขที่ใบสั่งซื้อเดิม ร้านจะตอบว่า "ออร์เดอร์นี้รับไว้แล้วค่ะ" แทนที่จะอบพิซซ่าถาดที่สอง ส่วน ETag เหมือนเลขรุ่นของเมนู ถ้าเมนูยังเป็นรุ่นเดิม พนักงานก็บอกว่า "เหมือนเดิมครับ" (304) ไม่ต้องยื่นเล่มใหม่ให้

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) เลือกวิธี Versioning ให้ Library API พร้อมเหตุผล และเขียนแผนเลิกใช้ v1 ที่ระบุ Header Deprecation และ Sunset ได้ (2) ส่ง POST /loans สองครั้งด้วย Idempotency-Key เดียวกันแล้วได้ Loan เพียงรายการเดียว (3) ยิงเกินโควตาแล้วได้ 429 พร้อม Retry-After (4) ได้ 304 Not Modified จาก If-None-Match และได้ 412 จาก If-Match ที่ล้าสมัย

STEP 12

API Security: CORS และ OWASP API Security Top 10 (2023)

สัปดาห์ที่ 7 · 2–3 ชม.
หัวข้อย่อย
  • CORS คืออะไร: เบราว์เซอร์บังคับ Same-Origin Policy และ Server ใช้ Header Access-Control-Allow-Origin บอกว่ายอมให้ Origin ไหนเรียกได้ (CORS ไม่ได้ป้องกัน curl หรือ Server อื่น)
  • Preflight Request: เบราว์เซอร์ส่ง OPTIONS พร้อม Origin, Access-Control-Request-Method, Access-Control-Request-Headers และ Server ตอบ Access-Control-Allow-Methods, Access-Control-Allow-Headers, Access-Control-Max-Age
  • ตั้งค่า CORS ใน FastAPI ด้วย CORSMiddleware แบบระบุ Origin ชัดเจน และเหตุผลที่ห้ามใช้ * คู่กับ allow_credentials=True
  • OWASP API Security Top 10 (2023) ครบ 10 ข้อ: API1 Broken Object Level Authorization, API2 Broken Authentication, API3 Broken Object Property Level Authorization, API4 Unrestricted Resource Consumption, API5 Broken Function Level Authorization
  • OWASP API Security Top 10 (2023) ต่อ: API6 Unrestricted Access to Sensitive Business Flows, API7 Server Side Request Forgery, API8 Security Misconfiguration, API9 Improper Inventory Management, API10 Unsafe Consumption of APIs
  • การป้องกัน Mass Assignment (ส่วนหนึ่งของ API3): แยก Model ที่รับเข้ากับ Model ที่เก็บ เพื่อไม่ให้ Client ตั้งค่า role หรือ is_admin เองได้ และการไม่คืนฟิลด์ลับใน Response
  • สุขอนามัยพื้นฐาน: บังคับ HTTPS, จำกัดขนาด Body, ตั้ง Timeout, ปิด /docs ใน Production ถ้าไม่ต้องการเปิดเผย, เก็บรายการ API ทุกเวอร์ชัน (Inventory) และบันทึก Log ที่ไม่มีข้อมูลส่วนบุคคลหรือ Token
  • สร้าง Security Checklist ของ Library API ที่จับคู่ทุกข้อของ OWASP กับวิธีป้องกันในโค้ดและใน Contract
ทำไมต้องเรียน
API คือประตูหน้าบ้านของข้อมูลทั้งหมดในระบบ และเป็นเป้าหมายหลักของการโจมตีระบบเว็บและแอปมือถือในปัจจุบัน OWASP API Security Top 10 เป็นภาษากลางที่ทีม Security ใช้ตรวจ API ถ้าคุณออกแบบโดยคิดถึง 10 ข้อนี้ตั้งแต่ต้น จะแก้ไขน้อยลงมากตอนตรวจความปลอดภัยก่อนเปิดใช้งาน ส่วน CORS เป็นปัญหาที่ทีม Frontend เจอบ่อยที่สุดเมื่อเชื่อมกับ Backend เป็นครั้งแรก
ใช้เวลา
2–3 ชั่วโมง: CORS และ Preflight พร้อมลองจาก Browser Console 1 ชั่วโมง อ่าน OWASP API Top 10 ครบ 10 ข้อ 1 ชั่วโมง เขียน Security Checklist 30–60 นาที
ฝึกอะไร
เปิด Reference API ที่พอร์ต 8000 และหน้าเว็บทดลองด้วย python3 -m http.server 5500 แล้วเรียก fetch() จาก Browser Console ให้เห็น CORS Error ก่อน จากนั้นตั้ง CORSMiddleware ให้ยอมเฉพาะ http://localhost:5500 และยืนยัน Preflight ด้วย curl -i -X OPTIONS
ระวัง

CORS ไม่ใช่ระบบความปลอดภัยของ API มันเป็นกติกาที่เบราว์เซอร์ใช้ปกป้องผู้ใช้ ผู้โจมตีที่ใช้ curl หรือเขียนสคริปต์เองไม่สนใจ CORS เลย API ของคุณจึงยังต้องมี Authentication, Authorization และ Rate Limit ครบเสมอ

Checkpoint

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) อธิบายได้ว่าเบราว์เซอร์ส่ง Preflight เมื่อไร และอ่าน Header ของ Preflight Response จาก curl -i -X OPTIONS ได้ (2) ตั้ง CORSMiddleware ให้ยอมเฉพาะ Origin ที่กำหนด แล้วยืนยันว่า Origin อื่นไม่ได้รับ Access-Control-Allow-Origin (3) บอกชื่อ OWASP API Security Top 10 (2023) ได้ครบ 10 ข้อ พร้อมตัวอย่างใน Library API ข้อละ 1 สถานการณ์ (4) มี Security Checklist ของ Library API ที่ระบุวิธีป้องกันครบทุกข้อ

Webhook, GraphQL, gRPC และ Mini Project: Library API Spec

หัวข้อย่อย
  • Webhook: ผู้ให้บริการส่ง POST พร้อม Event JSON ไปยัง URL ของผู้รับ การออกแบบ Payload (id, type, created_at, data) และการตอบ 2xx ให้เร็วแล้วค่อยประมวลผลเบื้องหลัง
  • ความปลอดภัยของ Webhook: เซ็น Body ด้วย HMAC-SHA256 ใส่ใน Header (เช่น X-Signature) ผู้รับตรวจด้วย hmac.compare_digest ใส่ Timestamp กัน Replay Attack และตรวจ Event ID ซ้ำ (เพราะ Webhook อาจส่งซ้ำได้)
  • Retry ของ Webhook: ผู้ส่ง Retry แบบ Exponential Backoff เมื่อไม่ได้ 2xx ผู้รับต้องออกแบบให้ประมวลผลซ้ำได้อย่างปลอดภัย (Idempotent Consumer) และการอธิบาย Webhook ใน OpenAPI 3.1 ด้วย Key webhooks
  • GraphQL เทียบกับ REST: Schema, Query, Mutation, ข้อดีเรื่อง Over-fetching และ Under-fetching ข้อเสียเรื่อง Caching ผ่าน HTTP, ปัญหา N+1 และการจำกัดความซับซ้อนของ Query
  • gRPC เทียบกับ REST: ไฟล์ .proto, Protocol Buffers, HTTP/2, Streaming 4 แบบ และเหตุผลที่นิยมใช้ภายในองค์กรมากกว่าเปิดให้เบราว์เซอร์เรียกตรง
  • เกณฑ์เลือกรูปแบบ API: ผู้ใช้คือใคร (Public, Partner, Internal), ความต้องการ Real-time, เครื่องมือที่ทีมมี และค่าใช้จ่ายในการดูแล
  • เริ่ม Mini Project: ออกแบบ Library API (books, members, loans) แบบ Contract-first ด้วย OpenAPI 3.1 ที่มี Schema, ตัวอย่าง, Error แบบ RFC 9457, Pagination และ Auth แล้ว Lint ด้วย Spectral และ Mock ด้วย Prism
  • ปิดงาน Mini Project: Reference Implementation ด้วย FastAPI, curl Test Script, pytest, README และ Push ขึ้น GitHub เพื่อใช้เป็นพอร์ตโฟลิโอ (รายละเอียดเต็มใน Part 4)
ทำไมต้องเรียน
ในงานจริงคุณจะไม่ได้ใช้แค่ REST อย่างเดียว ระบบชำระเงินและบริการ SaaS ส่วนใหญ่ส่ง Webhook มาหาคุณ และบริษัทขนาดกลางถึงใหญ่มักมี GraphQL หรือ gRPC อยู่ด้วย การรู้ว่าแต่ละแบบเหมาะกับอะไรช่วยให้ตัดสินใจทางสถาปัตยกรรมได้ดีขึ้น ส่วน Mini Project คือหลักฐานที่จับต้องได้ว่าคุณออกแบบ API ได้ครบทั้งกระบวนการ ซึ่งผู้สัมภาษณ์เปิดดูได้ทันทีจาก GitHub

Must-know Skills

ทักษะ 12 ข้อนี้คือสิ่งที่ผู้สัมภาษณ์งาน Backend และ Full-stack คาดหวังว่าคุณต้องทำได้จริง ไม่ใช่แค่รู้ชื่อ ทุกข้อมีอยู่ใน Checkpoint ของขั้นใดขั้นหนึ่งข้างบน

  1. เลือก HTTP Method และ Status Code ให้ถูกกับสถานการณ์ เพราะ Client, Proxy, Cache และระบบ Monitoring ทั้งหมดตัดสินใจจากสองสิ่งนี้ ถ้าเลือกผิด ระบบรอบข้างจะทำงานผิดตามไปด้วย
  2. เข้าใจ Safe และ Idempotent เพราะเป็นพื้นฐานของการ Retry อย่างปลอดภัย ซึ่งเป็นเรื่องที่ทำให้เงินหรือข้อมูลถูกบันทึกซ้ำได้ถ้าเข้าใจผิด
  3. ตั้งชื่อ Resource, URL และฟิลด์ JSON อย่างสม่ำเสมอ เพราะ API ที่คาดเดาได้ช่วยให้ผู้ใช้เรียนรู้เร็ว และการเปลี่ยนชื่อหลังเผยแพร่แล้วเป็น Breaking Change ที่แพงมาก
  4. ออกแบบ Filtering, Sorting และ Pagination เพราะทุก Endpoint ที่คืนรายการต้องรองรับข้อมูลที่โตขึ้นทุกวัน และการเลือก Offset หรือ Cursor ส่งผลต่อทั้งความเร็วและความถูกต้อง
  5. ตอบ Error ด้วยรูปแบบ RFC 9457 Problem Details เพราะ Client จะเขียนโค้ดจัดการ Error ได้ครั้งเดียวใช้ทุก Endpoint และผู้ใช้ปลายทางได้ข้อความที่เข้าใจได้
  6. อ่านและเขียน OpenAPI 3.1 ด้วย YAML เพราะเป็นภาษามาตรฐานของ Contract ที่ใช้สร้างเอกสาร Mock SDK และ Test ได้จากไฟล์เดียว
  7. ทำงานแบบ Contract-first ด้วย Spectral และ Prism เพราะทำให้หลายทีมเริ่มงานพร้อมกันได้ และจับข้อผิดพลาดของการออกแบบได้ก่อนเขียนโค้ด ซึ่งถูกกว่าแก้หลังเปิดใช้งานมาก
  8. ทดสอบ API ด้วย curl และ pytest เพราะ curl -i คือเครื่องมือหาสาเหตุปัญหาที่เร็วที่สุด และ Test อัตโนมัติคือสิ่งเดียวที่ยืนยันได้ว่า API ยังทำตามสัญญาหลังแก้โค้ด
  9. ออกแบบ Authentication และ Authorization และรู้จุดอ่อนของ JWT เพราะช่องโหว่ API ที่พบบ่อยที่สุดมาจากการตรวจสิทธิ์ผิดพลาด ไม่ใช่จากการเข้ารหัสที่อ่อน
  10. วางแผน Versioning และ Deprecation เพราะ API ที่มีผู้ใช้จริงต้องเปลี่ยนแปลงได้โดยไม่ทิ้ง Client เดิม และต้องสื่อสารการเลิกใช้ล่วงหน้าอย่างชัดเจน
  11. ใช้ Idempotency Key, Rate Limiting และ HTTP Caching เพราะเป็นสามเครื่องมือหลักที่ทำให้ API ทนต่อ Network ที่ไม่เสถียร การใช้งานเกินขนาด และภาระที่สูงขึ้น
  12. ตรวจ API ตาม OWASP API Security Top 10 (2023) เพราะเป็นภาษากลางที่ทีม Security ใช้ และช่วยให้คุณปิดช่องโหว่ตั้งแต่ขั้นออกแบบ ไม่ต้องรอให้ถูกพบหลังเปิดใช้งาน

เรียนจบแล้วไปต่อที่ไหน

เมื่อจบหัวข้อนี้ คุณจะมีทั้งความรู้และผลงานที่พร้อมนำไปต่อยอดในหัวข้ออื่นของหลักสูตร ทางเลือกที่แนะนำมีดังนี้

  • กลับไปปรับ API ใน Mini Project ของ ให้มี OpenAPI, Error แบบ RFC 9457, Cursor Pagination และ Idempotency Key ตามที่เรียนในหัวข้อนี้

  • ต่อยอดฝั่งข้อมูลด้วย เพื่อทำ Cursor Pagination บน PostgreSQL และสร้าง Index ที่รองรับการกรองและเรียงลำดับ
  • ต่อยอดฝั่งความปลอดภัย โดยนำ Security Checklist ตาม OWASP API Top 10 ไปฝึกตรวจ API ของตัวเองในหัวข้อที่เกี่ยวกับ Cyber Security ของหลักสูตร โดยทดลองในเครื่องและ Container ของตัวเองเท่านั้น
