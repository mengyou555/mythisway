Multiple Choice

เลือกคำตอบที่ถูกที่สุดเพียงข้อเดียว ทุกข้อมี 4 ตัวเลือก (A–D) ระดับความยากคละกัน ในเฉลยจะอธิบายทั้งเหตุผลของคำตอบที่ถูก และเหตุผลที่ตัวเลือกอื่นผิดทีละข้อ

  1. ง่าย

    HTTP Method ใดเป็น Idempotent (ส่งซ้ำกี่ครั้งก็ได้สถานะสุดท้ายบน Server เหมือนเดิม) แต่ ไม่ Safe (เปลี่ยนแปลงข้อมูลบน Server)

    1. GET
    2. POST
    3. PUT
    4. HEAD
  2. ง่าย

    ทีมต้องการ Endpoint สำหรับ "ยืมหนังสือ bk_0001 ให้สมาชิก mb_0001" แบบใดออกแบบตามหลัก REST ของหลักสูตรนี้ได้ดีที่สุด

    1. GET /borrowBook?book_id=bk_0001&member_id=mb_0001
    2. POST /loans พร้อม Body {"book_id": "bk_0001", "member_id": "mb_0001"}
    3. POST /books/bk_0001/borrow/mb_0001/
    4. GET /Members/MB_0001/Loans/Create?book=bk_0001
  3. กลาง

    สมชายล็อกอินแล้วได้ JWT ที่ถูกต้อง มี sub เป็น mb_0001 และยังไม่หมดอายุ จากนั้นเขาลองเปลี่ยน URL เป็น GET /members/mb_0002/loans เพื่อดูรายการยืมของสุดา ตามแนวทางของหลักสูตรนี้ API ควรตอบอย่างไร

    1. 403 Forbidden แบบ application/problem+json เพราะยืนยันตัวตนผ่านแล้ว แต่ไม่มีสิทธิ์ดูข้อมูลของสมาชิกคนอื่น
    2. 401 Unauthorized พร้อม WWW-Authenticate: Bearer เพราะต้องให้ล็อกอินใหม่
    3. 200 OK แต่ส่ง {"data": []} เพื่อไม่ให้รู้ว่ามีข้อมูลอยู่
    4. 400 Bad Request เพราะ member_id ใน URL ไม่ตรงกับ Token
  4. ง่าย

    DELETE /books/bk_0004 ลบหนังสือสำเร็จ และ Server ไม่ต้องส่งข้อมูลอะไรกลับไป Status Code ใดเหมาะสมที่สุดตามแนวทางของหลักสูตรนี้

    1. 200 OK พร้อม Body {"error": null}
    2. 201 Created
    3. 304 Not Modified
    4. 204 No Content
  5. กลาง

    แอปมือถือแสดงหนังสือใหม่เรียงจากใหม่ไปเก่า และเลื่อนหน้าด้วย ?limit=20&offset=20, ?limit=20&offset=40 ไปเรื่อย ๆ ผู้ใช้แจ้งว่าบางครั้งเห็นหนังสือเล่มเดิมซ้ำสองครั้งตอนเลื่อนลงไป ข้อใดอธิบายสาเหตุและวิธีแก้ได้ถูกต้อง

    1. ระหว่างที่ผู้ใช้เลื่อน มีหนังสือใหม่ถูกเพิ่มเข้ามาด้านบน ทำให้ทุกเล่มเลื่อนตำแหน่งลง Offset จึงชี้ไปที่รายการเดิมซ้ำ ควรเปลี่ยนเป็น Cursor Pagination ที่อ้างอิงจากรายการสุดท้ายของหน้าก่อน (มี id เป็นตัวตัดสินเมื่อค่าเรียงเท่ากัน)
    2. ค่า limit=20 น้อยเกินไป ถ้าเพิ่มเป็น limit=100 ปัญหาจะหายไป
    3. ควรเปลี่ยนเป็น Cursor Pagination เพราะทำให้ผู้ใช้กระโดดไปหน้าที่ 50 ได้ทันทีโดยไม่ต้องโหลดหน้าก่อนหน้า
    4. ควรใส่ Cache-Control: no-store ใน Response เพราะรายการซ้ำเกิดจาก Cache ของมือถือ
  6. ยาก

    Client เก็บ Response ของ GET /books/bk_0001 ไว้ พร้อม ETag: "a1b2c3" ต่อมาส่ง Request ใหม่พร้อม If-None-Match: "a1b2c3" และหนังสือเล่มนี้ยังไม่ถูกแก้ไขเลย Server ที่ทำตามมาตรฐาน HTTP ควรตอบอย่างไร

    1. 200 OK พร้อม Body เต็มและ ETag: "a1b2c3" เหมือนเดิม
    2. 412 Precondition Failed
    3. 304 Not Modified ไม่มี Body ให้ Client ใช้ข้อมูลที่เก็บไว้ต่อ
    4. 204 No Content
  7. ง่าย

    ค่าปรับคืนหนังสือช้าคือ 25.50 บาท ควรออกแบบฟิลด์ใน JSON แบบใดตาม Convention ของหลักสูตรนี้

    1. "fine": 25.5
    2. "fineSatang": 2550
    3. "fine_satang": "2550"
    4. "fine_satang": 2550
  8. กลาง

    ใน OpenAPI 3.1 ต้องการบอกว่าฟิลด์ returned_at เป็นข้อความหรือเป็น null ได้ ควรเขียน Schema อย่างไร

    1. type: string คู่กับ nullable: true
    2. type: [string, 'null']
    3. type: string คู่กับ required: false ภายใน property
    4. type: string คู่กับ x-nullable: true
  9. ยาก

    ข้อใดเป็นแนวทางที่ถูกต้องเกี่ยวกับ JWT

    1. Payload ของ JWT ถูกเข้ารหัสไว้ จึงใส่รหัสผ่านหรือเลขบัตรประชาชนลงไปได้อย่างปลอดภัย
    2. ใช้ HS256 กับ Secret สั้น ๆ อย่าง "secret" ได้ ถ้า API ใช้ HTTPS อยู่แล้ว
    3. ถ้า Header ของ Token เขียนว่า "alg": "none" ให้ข้ามการตรวจลายเซ็นได้ เพราะเป็น Token ภายในองค์กร
    4. Server ต้องกำหนด algorithms=["HS256"] เองตอน decode และตรวจ exp, aud, iss ทุกครั้ง เพราะ Payload เป็นแค่ base64url ที่ใครก็อ่านได้ ลายเซ็นมีไว้กันการแก้ไขเท่านั้น
  10. กลาง

    ในขั้นตอนแบบ Contract-first ข้อใดอธิบายหน้าที่ของ Spectral และ Prism ได้ถูกต้อง

    1. Spectral ตรวจ (Lint) ไฟล์ openapi.yaml ตามกฎมาตรฐานและกฎของทีม ส่วน Prism สร้าง Mock Server จาก Spec โดยตอบด้วย example ที่เขียนไว้ ทีม Frontend จึงเริ่มงานได้ก่อน Backend เสร็จ
    2. Spectral เป็น Mock Server ส่วน Prism เป็นตัว Lint ที่ตรวจชื่อ property ให้เป็น snake_case
    3. Prism เก็บข้อมูลจริงลงฐานข้อมูล หลัง POST /members แล้ว GET /members จะเห็นสมาชิกที่เพิ่งสร้าง
    4. Spectral อ่าน Spec แล้วสร้างโค้ด FastAPI ให้อัตโนมัติ จึงไม่ต้องเขียน Backend เอง
  11. ยาก

    แอปมือถือส่ง POST /v1/loans พร้อม Idempotency-Key: k-001 และ Body {"book_id": "bk_0001", "member_id": "mb_0001"} ได้ 201 ไปแล้ว ต่อมาแอปมีบั๊ก ส่ง Request ใหม่ด้วย Idempotency-Key: k-001 เดิม แต่ Body เป็น {"book_id": "bk_0002", "member_id": "mb_0001"} Server ที่ออกแบบตามหลักสูตรนี้ควรตอบอย่างไร

    1. ตอบ 201 ซ้ำด้วยข้อมูลการยืม bk_0001 เดิม โดยไม่บอกอะไรเพิ่ม
    2. สร้างการยืม bk_0002 ใหม่และตอบ 201 เพราะ Body ต่างกัน ถือเป็นคำขอใหม่
    3. ตอบ 422 แบบ application/problem+json ที่มี type ลงท้ายด้วย idempotency-key-reused โดยไม่สร้างการยืมใหม่
    4. ตอบ 500 Internal Server Error เพราะเป็นสถานการณ์ที่ไม่ควรเกิดขึ้น
  12. ยาก

    ผู้ทดสอบระบบ (ในระบบทดสอบของบริษัทเอง) พบว่าแค่เปลี่ยน URL จาก /members/mb_0001/loans เป็น /members/mb_0002/loans ก็เห็นรายการยืมของสมาชิกคนอื่นได้ ช่องโหว่นี้ตรงกับ OWASP API Security Top 10 (2023) ข้อใด และควรแก้อย่างไร

    1. API4:2023 Unrestricted Resource Consumption แก้โดยเพิ่ม Rate Limit 5 ครั้งต่อ 10 วินาที
    2. API1:2023 Broken Object Level Authorization (BOLA) แก้โดยตรวจทุก Request ว่า sub ใน Token ตรงกับ member_id ที่ขอ (ยกเว้นผู้มี scope admin)
    3. API2:2023 Broken Authentication แก้โดยบังคับให้ผู้ใช้ตั้งรหัสผ่านยาวขึ้น
    4. API8:2023 Security Misconfiguration แก้โดยตั้ง allow_origins ของ CORS ให้แคบลง

สิ่งที่ต้องทำ
  1. ในโฟลเดอร์ ~/projects/api-lab/ch3-reliability เขียน main.py ที่ใช้ APIRouter(prefix="/v1") มี GET /v1/books และ POST /v1/loans ข้อมูลตั้งต้นคือหนังสือ bk_0001–bk_0003 (bk_0003 ถูกยืมอยู่), สมาชิก mb_0001 และ mb_0002 และการยืม ln_0001 การยืมใหม่ต้องได้ id ln_0002 เป็นต้นไป
  2. ทุก Endpoint ใต้ /v1 ต้องมี Header X-API-Key (ไม่มีให้ตอบ 401) และใช้ค่า hash ของ key เป็นตัวแยก Client ทุก Error ต้องเป็น application/problem+json ตาม RFC 9457 รวมถึง 422 จากการตรวจ Body ที่ต้องมีรายการ errors
  3. เพิ่ม Rate Limit แบบ Fixed Window 5 Request ต่อ 10 วินาทีต่อ Client กับทุก Endpoint ใต้ /v1 เมื่อเกินให้ตอบ 429 ที่มี type ลงท้ายด้วย rate-limited และ Header Retry-After เป็นจำนวนวินาทีที่ต้องรอ ตัวนับต้องรับนาฬิกาที่เปลี่ยนได้ตอนทดสอบ
  4. บังคับให้ POST /v1/loans ต้องมี Header Idempotency-Key (ไม่มีให้ตอบ 400) ถ้า Client เดิมส่ง key เดิมกับ Body เดิม ให้ตอบ Response ที่บันทึกไว้ซ้ำพร้อม Header Idempotent-Replayed: true โดยไม่สร้างการยืมใหม่ ถ้า key เดิมแต่ Body ต่างให้ตอบ 422 ที่มี type ลงท้ายด้วย idempotency-key-reused และ key ของ Client หนึ่งต้องไม่ชนกับ Client อื่น
  5. ตรวจกฎธุรกิจ ได้แก่ 404 เมื่อไม่พบหนังสือหรือสมาชิก และ 409 book-unavailable เมื่อหนังสือถูกยืมอยู่ ส่วน "ตรวจ key, สร้างการยืม, บันทึกผล" ต้องทำภายใต้ Lock เดียวกัน เพื่อกัน Request ซ้ำที่มาถึงพร้อมกัน
  6. เขียน test_main.py อย่างน้อย 12 เทสต์ (นับรวม parametrize) ที่ครอบคลุม 401, 400, 201 + Location, Replay, Key ซ้ำแต่ Body ต่าง, Key แยกตาม Client, 409, 422 หลายแบบ, 429 พร้อม Retry-After, การรีเซ็ตเมื่อครบหน้าต่างเวลา และ Rate Limit แยกตาม Client แล้วรัน python3 -m pytest -v ให้ผ่านทั้งหมด
  7. เขียน demo.sh ที่ใช้ curl สาธิตการ Retry ด้วย key เดิม, key เดิมแต่ Body ต่าง และการยิง GET /v1/books 7 ครั้งติดกัน แล้วรันกับ uvicorn main:app --port 8000

ข้อ 1

คำตอบ: 201 (Created) และ Location

201 Created บอกว่า Request สำเร็จและมี Resource ใหม่เกิดขึ้น ต่างจาก 200 OK ที่แปลว่าสำเร็จเฉย ๆ ส่วน Header Location: /books/bk_0004 บอก Client ว่าจะอ่านหนังสือเล่มนี้ได้ที่ URL ไหน Client จึงไม่ต้องเดา id หรือประกอบ URL เอง ใน FastAPI ทำได้ด้วย status_code=201 ใน Decorator และ response.headers["Location"] = "/books/bk_0004"

ข้อ 2

คำตอบ: -i, 204, 404

  • curl -i (ย่อจาก --include จะตอบ --include หรือ -si ก็ถูก) แสดง Status Line และ Header ของ Response ก่อน Body ถ้าอยากเห็นทั้ง Request และ Response แบบละเอียด ให้ใช้ -v แทน (แต่ผลจะมีเครื่องหมาย < และ > นำหน้า ไม่ตรงกับหน้าตาในโจทย์) ส่วน -I (ตัวใหญ่) ไม่ใช่คำตอบที่ดี เพราะ -I แปลว่า "ส่ง HEAD" การใช้คู่กับ -X DELETE ทำให้คำสั่งขัดกันเองและอ่านสับสน
  • 204 No Content ใช้เมื่อทำสำเร็จแต่ไม่มี Body ส่งกลับ เป็นค่ามาตรฐานของ DELETE ในหลักสูตรนี้
  • การลบซ้ำครั้งที่สองได้ 404 เพราะสมาชิกถูกลบไปแล้ว สิ่งที่ควรสังเกตคือ DELETE ยังนับเป็น Idempotent เพราะ "สถานะบน Server" หลังลบกี่ครั้งก็เหมือนกัน คือไม่มี mb_0003 แม้ Status Code ที่ตอบกลับจะต่างกันก็ตาม ผลลัพธ์นี้ตรงกับที่ได้จากการรันจริงในโจทย์ที่ 1 (first DELETE status=204 และ second DELETE status=404)

คำตอบ: A ในขั้นตอน Contract-first ทีมเขียน openapi.yaml ก่อน แล้วใช้ Spectral ตรวจคุณภาพของ Spec ตามกฎ spectral:oas และกฎของทีม จากนั้นใช้ Prism อ่าน Spec เดียวกันเพื่อเปิด Mock Server ที่ตอบด้วย example และตรวจ Request ตาม Schema ทีม Frontend จึงพัฒนาและทดสอบได้ทันทีโดยไม่ต้องรอ Backend

  • B ผิดเพราะสลับหน้าที่กัน Spectral คือ Linter ส่วน Prism คือ Mock Server (และ Validation Proxy) กฎ snake_case เป็นกฎที่เขียนใน .spectral.yaml
  • C ผิดเพราะ Prism ไม่เก็บข้อมูลจริง ทุก Response มาจาก example หรือข้อมูลที่สุ่มตาม Schema (โหมด -d) หลัง POST แล้ว GET จะยังได้ example เดิม นี่เป็นข้อผิดพลาดที่มือใหม่เจอบ่อยเมื่อใช้ Mock
  • D ผิดเพราะ Spectral ไม่สร้างโค้ด มันแค่ตรวจ Spec การสร้างโค้ดจาก Spec ต้องใช้เครื่องมืออื่น และทีมยังต้องเขียน Logic ทางธุรกิจเองอยู่ดี
ข้อ 11

คำตอบ: C Idempotency-Key ผูกกับ "คำขอเดิม" ถ้า key เดิมมาพร้อม Body ต่าง แปลว่า Client มีบั๊กหรือใช้ key ซ้ำผิดที่ Server ต้องปฏิเสธอย่างชัดเจนด้วย 422 และ type idempotency-key-reused โดยไม่สร้างข้อมูลใหม่ และไม่ตอบผลของคำขอเก่า Server ตรวจได้ด้วยการเก็บ hash ของ Body คู่กับ key แล้วเทียบทุกครั้ง ซึ่งพิสูจน์ได้ด้วยเทสต์ test_same_key_different_body_is_422 ในโจทย์ที่ 3

  • A ผิดเพราะ Client ขอยืม bk_0002 แต่ได้ข้อมูลการยืม bk_0001 กลับไปเงียบ ๆ แอปจะแสดงผลผิดโดยไม่มีใครรู้ การ Replay ใช้ได้เฉพาะเมื่อ Body เหมือนเดิม
  • B ผิดเพราะทำให้ Idempotency-Key ไม่มีความหมาย และถ้าเป็นการ Retry ที่ Body ถูกสร้างใหม่ผิดพลาด อาจเกิดการยืมซ้ำที่ระบบนี้ตั้งใจป้องกัน
  • D ผิดเพราะ 5xx หมายถึง Server ผิดพลาด แต่กรณีนี้ Client ทำผิด จึงต้องเป็น 4xx และ 500 ยังทำให้ Client บางตัว Retry ซ้ำไปเรื่อย ๆ
ข้อ 12

คำตอบ: B การเปลี่ยน id ของ Object ใน URL แล้วเข้าถึงข้อมูลของคนอื่นได้คือ API1:2023 Broken Object Level Authorization (BOLA) ซึ่งเป็นอันดับหนึ่งของ OWASP API Security Top 10 วิธีแก้คือตรวจสิทธิ์ระดับ Object ในทุก Endpoint ที่รับ id เช่น เทียบ sub ใน Token กับ member_id ใน path และอนุญาตเฉพาะเจ้าของหรือผู้ที่มี scope admin การทดสอบลักษณะนี้ต้องทำกับระบบของตัวเองหรือระบบที่ได้รับอนุญาตเท่านั้น การเข้าถึงข้อมูลของระบบผู้อื่นโดยไม่ได้รับอนุญาตผิด พ.ร.บ.ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์

  • A ผิดเพราะ API4 เกี่ยวกับการใช้ทรัพยากรเกินขอบเขต เช่น ยิงถี่หรือขอข้อมูลทีละมาก ๆ Rate Limit ไม่ได้ห้ามการอ่านข้อมูลของคนอื่น ผู้โจมตียังอ่านได้ 5 ครั้งต่อ 10 วินาที
  • C ผิดเพราะ API2 เกี่ยวกับกลไกยืนยันตัวตนที่อ่อนแอ เช่น ไม่ตรวจลายเซ็น Token หรือไม่ป้องกันการเดารหัสผ่าน ในกรณีนี้ผู้ทดสอบยืนยันตัวตนถูกต้องแล้ว ปัญหาอยู่ที่การตรวจสิทธิ์หลังจากนั้น
  • D ผิดเพราะ CORS เป็นกลไกของเบราว์เซอร์ที่คุมว่าเว็บจาก Origin ไหนอ่าน Response ได้ ผู้โจมตีที่ใช้ curl หรือแอปของตัวเองไม่ถูก CORS บังคับเลย จึงแก้ BOLA ไม่ได้

# main.py — Members API สำหรับห้องสมุดชุมชน (โจทย์ที่ 1)
from fastapi import FastAPI, HTTPException, Response, status
from pydantic import BaseModel, Field

app = FastAPI(title="Community Library Members API", version="1.0.0")

# ข้อมูลตัวอย่างเก็บในหน่วยความจำ (หายเมื่อปิด Server)
MEMBERS: dict[str, dict] = {
    "mb_0001": {"id": "mb_0001", "name": "Somchai Jaidee",
                "email": "somchai@example.com", "max_active_loans": 3},
    "mb_0002": {"id": "mb_0002", "name": "Suda Meesuk",
                "email": "suda@example.com", "max_active_loans": 3},
}
next_number = 3  # เลขถัดไปสำหรับ id ใหม่ (mb_0003)


class MemberCreate(BaseModel):
    # ข้อมูลที่ Client ส่งมาตอนสมัคร: ไม่มี id เพราะ Server เป็นคนสร้าง
    name: str = Field(min_length=1, max_length=100)
    email: str = Field(pattern=r"^[^@\s]+@[^@\s]+\.[^@\s]+$")
    max_active_loans: int = Field(default=3, ge=1, le=10)


@app.get("/members")
def list_members():
    # ห่อรายการด้วย envelope {"data": [...]} ตามมาตรฐานของหลักสูตร
    return {"data": list(MEMBERS.values()), "next_cursor": None}


@app.get("/members/{member_id}")
def get_member(member_id: str):
    member = MEMBERS.get(member_id)
    if member is None:
        raise HTTPException(status_code=404, detail=f"member {member_id} not found")
    return member


@app.post("/members", status_code=status.HTTP_201_CREATED)
def create_member(body: MemberCreate, response: Response):
    global next_number
    # อีเมลซ้ำเป็นการชนกับกฎธุรกิจ จึงตอบ 409 Conflict
    email = body.email.lower()
    if any(m["email"] == email for m in MEMBERS.values()):
        raise HTTPException(status_code=409, detail=f"email {email} is already registered")
    member_id = f"mb_{next_number:04d}"
    next_number += 1
    member = {"id": member_id, "name": body.name, "email": email,
              "max_active_loans": body.max_active_loans}
    MEMBERS[member_id] = member
    # บอก Client ว่า Resource ใหม่อยู่ที่ URL ไหน
    response.headers["Location"] = f"/members/{member_id}"
    return member


@app.delete("/members/{member_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_member(member_id: str):
    if MEMBERS.pop(member_id, None) is None:
        raise HTTPException(status_code=404, detail=f"member {member_id} not found")
    # 204 ต้องไม่มี Body จึงคืน Response เปล่า
    return Response(status_code=204)

แนวคิด
  • ใช้คำนามพหูพจน์และให้ Method เป็นตัวบอกการกระทำ ทั้ง 4 Endpoint ใช้แค่ 2 path คือ /members (Collection) และ /members/{member_id} (สมาชิกหนึ่งคน) ส่วน "ดู สร้าง ลบ" บอกด้วย GET, POST และ DELETE การลบด้วย GET แบบเดิมอันตราย เพราะ GET ต้องเป็น Safe Method ที่ใครเรียกซ้ำก็ไม่เกิดผลเสีย
  • Status Code ต้องบอกผลลัพธ์ได้โดยไม่ต้องอ่าน Body แอปมือถือแค่ดู 201, 409, 422, 204 หรือ 404 ก็รู้ว่าควรทำอะไรต่อ เช่น 409 ให้แสดงข้อความ "อีเมลนี้สมัครแล้ว" และ 422 ให้ไฮไลต์ช่องที่กรอกผิด
  • Server เป็นคนสร้าง id โมเดล MemberCreate จึงไม่มีฟิลด์ id และ Server บอกที่อยู่ของ Resource ใหม่ผ่าน Location การแยกโมเดลรับเข้ากับโมเดลส่งออกยังช่วยป้องกัน Mass Assignment (API3:2023) เพราะ Client ส่ง id มาเองไม่ได้
  • ปรับข้อมูลให้เป็นรูปแบบมาตรฐานก่อนเปรียบเทียบ อีเมลถูกแปลงเป็นตัวพิมพ์เล็กก่อนตรวจซ้ำและก่อนเก็บ ทำให้ ANAN@example.com ถูกจับว่าซ้ำกับ anan@example.com ตามที่เห็นในผลลัพธ์ข้อ 3
  • ห่อ Collection ด้วย envelope {"data": [...], "next_cursor": null} ทำให้วันหน้าเพิ่ม Pagination ได้โดยไม่เปลี่ยนโครงสร้าง Response จึงไม่เป็น Breaking Change
  • Error ในโจทย์นี้ยังใช้รูปแบบเริ่มต้นของ FastAPI คือ {"detail": "..."} เพื่อให้โจทย์ระดับเริ่มต้นสั้นลง ในงานจริงควรเปลี่ยนเป็น application/problem+json ตามแนวคิดที่ 6 ของ Part 2 ซึ่งเป็นไอเดียต่อยอดข้อแรกด้านล่าง
ไอเดียต่อยอด
  1. เปลี่ยน Error ทุกตัวเป็น RFC 9457 Problem Details โดยเพิ่ม Exception Handler ที่ตอบ application/problem+json พร้อม type https://example.com/problems/member-not-found และเพิ่ม type ใหม่สำหรับอีเมลซ้ำ แล้วแก้ check.sh ให้ตรวจ Content-Type ด้วย
  2. เพิ่ม PATCH /members/{member_id} ที่แก้ได้เฉพาะ name และ max_active_loans โดยใช้ model_dump(exclude_unset=True) เพื่อแยก "ไม่ได้ส่งฟิลด์" ออกจาก "ส่งมาเป็น null" และตรวจว่าการแก้อีเมลให้ซ้ำคนอื่นต้องได้ 409
  3. เพิ่ม Cursor Pagination ให้ GET /members ด้วย ?limit= (1–100) และ ?cursor= แล้วเขียนลูปใน Bash ที่เดินตาม next_cursor จนเป็น null
  4. แปลง check.sh เป็นเทสต์ด้วย pytest และ TestClient (แนวคิดที่ 7 ของ Part 2) พร้อม fixture ที่รีเซ็ตข้อมูลก่อนทุกเทสต์ เพื่อให้รันใน CI ได้โดยไม่ต้องเปิด Server
  5. เปิด http://127.0.0.1:8000/docs ดู Swagger UI ที่ FastAPI สร้างให้ เทียบกับตาราง endpoints.md ว่าตรงกันหรือไม่ แล้วเพิ่ม responses={404: ..., 409: ...} ใน Decorator ให้เอกสารแสดง Error ครบ

#!/usr/bin/env bash
# mock-check.sh — ตรวจว่า Prism Mock ตอบตาม Contract (PASS/FAIL ต่อข้อ)
set -euo pipefail
BASE_URL="${BASE_URL:-http://127.0.0.1:4010}"
TOKEN="Bearer test-token"   # Prism ตรวจแค่ว่ามี Bearer Token หรือไม่ ไม่ได้ตรวจลายเซ็น
fails=0

# check <ชื่อ> <status ที่คาด> <content-type ที่คาด> <อาร์กิวเมนต์ curl...>
check() {
  local name="$1" want_status="$2" want_type="$3"; shift 3
  local result status ctype
  result=$(curl -s -o /dev/null -w '%{http_code} %{content_type}' "$@")
  status="${result%% *}"
  ctype="${result#* }"
  if [[ "$status" == "$want_status" && "$ctype" == "$want_type"* ]]; then
    echo "PASS  $name -> $status $ctype"
  else
    echo "FAIL  $name -> got $status $ctype, want $want_status $want_type"
    fails=$((fails + 1))
  fi
}

check "list members"           200 application/json         "$BASE_URL/members"
check "get member example"     200 application/json         "$BASE_URL/members/mb_0001"
check "force 404 via Prefer"   404 application/problem+json -H 'Prefer: code=404' "$BASE_URL/members/mb_9999"
check "create without token"   401 application/problem+json -X POST "$BASE_URL/members" \
      -H 'Content-Type: application/json' -d '{"name":"Anan Rakdee","email":"anan@example.com"}'
check "create with token"      201 application/json         -X POST "$BASE_URL/members" \
      -H "Authorization: $TOKEN" -H 'Content-Type: application/json' \
      -d '{"name":"Anan Rakdee","email":"anan@example.com"}'
check "create invalid body"    422 application/problem+json -X POST "$BASE_URL/members" \
      -H "Authorization: $TOKEN" -H 'Content-Type: application/json' -d '{"name":""}'
check "bad member_id pattern"  422 application/problem+json "$BASE_URL/members/abc"
check "limit over 100"         422 application/problem+json "$BASE_URL/members?limit=500"

echo "-----"
if (( fails > 0 )); then
  echo "$fails check(s) failed"
  exit 1
fi
echo "all checks passed"

แนวคิด
  • Contract เป็นแหล่งความจริงเดียว ทั้ง Spectral, Prism และเอกสารอ่านจาก openapi.yaml ไฟล์เดียว เมื่อทีมตกลงเปลี่ยนอะไร ให้แก้ที่ Contract ก่อน แล้วเครื่องมือทุกตัวจะเห็นการเปลี่ยนแปลงพร้อมกัน
  • แยกส่วนที่ใช้ซ้ำไว้ใน components Error 4 แบบถูกเขียนครั้งเดียวใน components/responses และพารามิเตอร์ Limit ก็กำหนดขอบเขต 1–100 ไว้ที่เดียว ถ้าวันหน้าเปลี่ยนค่าสูงสุด ก็แก้จุดเดียว
  • ใส่ example ที่สมจริง Prism ตอบด้วย example ที่เราเขียน ทีม Frontend จึงเห็นข้อมูลหน้าตาเหมือนของจริง ใช้ named examples (somchai, suda) เมื่ออยากให้ Frontend เลือกทดสอบได้หลายกรณี
  • Prism เลือก Error ตามสิ่งที่ประกาศไว้ใน Operation นั้น ตอนเขียนครั้งแรก listMembers ประกาศแค่ '400' สำหรับ cursor ผิด ผลคือ limit=500 ได้ 400 พร้อม example ของ "Invalid cursor" ซึ่งทำให้ Frontend เข้าใจผิด สคริปต์ตรวจจึงจับได้ดังนี้

  • ส่วน getMember ไม่ได้ประกาศ 422 ไว้ แต่ /members/abc ยังได้ 422 เพราะ Prism สร้าง Problem Details ของตัวเอง (type https://stoplight.io/prism/errors#UNPROCESSABLE_ENTITY) เมื่อหา Response ที่เหมาะสมใน Spec ไม่เจอ สคริปต์ผ่านก็จริง แต่ Body ไม่ใช่ type ของเรา ควรประกาศ '422' ให้ getMember ด้วยเพื่อให้ Contract ครบ

# main.py — POST /v1/loans ที่ปลอดภัยต่อการ Retry และมี Rate Limit (โจทย์ที่ 3)
import hashlib
import json
import math
import threading
import time
from datetime import datetime, timedelta
from zoneinfo import ZoneInfo

from fastapi import APIRouter, Depends, FastAPI, Header, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field

BKK = ZoneInfo("Asia/Bangkok")
PROBLEM_BASE = "https://example.com/problems/"


# ---------- Problem Details (RFC 9457) ----------
class ProblemError(Exception):
    def __init__(self, status: int, slug: str, title: str, detail: str,
                 headers: dict[str, str] | None = None):
        self.status, self.slug, self.title = status, slug, title
        self.detail, self.headers = detail, headers or {}


def problem_response(status: int, slug: str, title: str, detail: str,
                     headers: dict[str, str] | None = None, **extra) -> JSONResponse:
    body = {"type": PROBLEM_BASE + slug, "title": title, "status": status,
            "detail": detail, **extra}
    return JSONResponse(body, status_code=status, headers=headers,
                        media_type="application/problem+json")


# ---------- Rate limiter แบบ Fixed Window แยกตาม Client ----------
class FixedWindowLimiter:
    def __init__(self, limit: int, window_seconds: int, clock=time.monotonic):
        self.limit = limit
        self.window = window_seconds
        self.clock = clock                       # ฉีดนาฬิกาปลอมได้ตอนเขียนเทสต์
        self.counters: dict[str, tuple[float, int]] = {}
        self.lock = threading.Lock()

    def hit(self, client_id: str) -> int | None:
        """คืน None ถ้ายังไม่เกินโควตา หรือคืนจำนวนวินาทีที่ต้องรอ (Retry-After)"""
        now = self.clock()
        with self.lock:
            start, count = self.counters.get(client_id, (now, 0))
            if now - start >= self.window:      # หมดหน้าต่างเวลาเดิม เริ่มนับใหม่
                start, count = now, 0
            if count >= self.limit:
                return max(1, math.ceil(start + self.window - now))
            self.counters[client_id] = (start, count + 1)
            return None

    def reset(self) -> None:
        with self.lock:
            self.counters.clear()


limiter = FixedWindowLimiter(limit=5, window_seconds=10)


def client_id_from_key(x_api_key: str | None = Header(default=None)) -> str:
    # Lab นี้ใช้ค่า X-API-Key เป็นตัวแยก Client (ของจริงต้องตรวจกับ key ที่ hash เก็บไว้)
    if not x_api_key:
        raise ProblemError(401, "unauthorized", "Unauthorized", "missing X-API-Key header")
    # เก็บเป็น hash เพื่อไม่ให้ key ตัวจริงค้างอยู่ใน memory/log
    return hashlib.sha256(x_api_key.encode()).hexdigest()[:16]


def rate_limit(client_id: str = Depends(client_id_from_key)) -> str:
    wait = limiter.hit(client_id)
    if wait is not None:
        raise ProblemError(429, "rate-limited", "Too many requests",
                           f"limit is {limiter.limit} requests per {limiter.window} seconds",
                           headers={"Retry-After": str(wait)})
    return client_id


# ---------- ข้อมูลในหน่วยความจำ ----------
def seed() -> dict:
    return {
        "books": {
            "bk_0001": {"id": "bk_0001", "title": "Python 101", "status": "available"},
            "bk_0002": {"id": "bk_0002", "title": "API Design ฉบับเริ่มต้น", "status": "available"},
            "bk_0003": {"id": "bk_0003", "title": "SQL for Everyone", "status": "on_loan"},
        },
        "members": {"mb_0001", "mb_0002"},
        "loans": {
            "ln_0001": {"id": "ln_0001", "book_id": "bk_0003", "member_id": "mb_0002",
                        "borrowed_at": "2026-10-15T10:00:00+07:00",
                        "due_date": "2026-10-29", "returned_at": None, "fine_satang": 0},
        },
        "next_loan": 2,
        # คีย์คือ (client_id, idempotency_key) ค่าคือ hash ของ body + response ที่บันทึกไว้
        "idempotency": {},
    }


DB = seed()
DB_LOCK = threading.Lock()


def reset_state() -> None:
    global DB
    DB = seed()
    limiter.reset()


class LoanCreate(BaseModel):
    book_id: str = Field(pattern=r"^bk_[0-9]{4}$")
    member_id: str = Field(pattern=r"^mb_[0-9]{4}$")


# ---------- แอปและ Router /v1 ----------
app = FastAPI(title="Library Loans API", version="1.0.0")
v1 = APIRouter(prefix="/v1", dependencies=[Depends(rate_limit)])


@app.exception_handler(ProblemError)
async def handle_problem(request: Request, exc: ProblemError):
    return problem_response(exc.status, exc.slug, exc.title, exc.detail, exc.headers,
                            instance=request.url.path)


@app.exception_handler(RequestValidationError)
async def handle_validation(request: Request, exc: RequestValidationError):
    errors = [{"field": ".".join(str(p) for p in e["loc"][1:]), "message": e["msg"]}
              for e in exc.errors()]
    return problem_response(422, "validation-error", "Validation error",
                            "request did not pass validation", errors=errors,
                            instance=request.url.path)


@v1.get("/books")
def list_books():
    return {"data": list(DB["books"].values()), "next_cursor": None}


@v1.post("/loans", status_code=201)
def create_loan(body: LoanCreate,
                client_id: str = Depends(rate_limit),
                idempotency_key: str | None = Header(default=None, max_length=100)):
    if not idempotency_key:
        raise ProblemError(400, "idempotency-key-missing", "Idempotency-Key required",
                           "POST /v1/loans needs an Idempotency-Key header (use a UUID)")
    # hash ของ body ในรูปแบบมาตรฐาน (เรียง key) เพื่อเทียบว่าเป็นคำขอเดิมหรือไม่
    body_hash = hashlib.sha256(
        json.dumps(body.model_dump(), sort_keys=True).encode()).hexdigest()
    store_key = (client_id, idempotency_key)

    # ล็อกทั้งช่วง "ตรวจ-สร้าง-บันทึก" กันคำขอซ้ำที่มาพร้อมกันสร้าง loan สองรายการ
    with DB_LOCK:
        saved = DB["idempotency"].get(store_key)
        if saved is not None:
            if saved["body_hash"] != body_hash:
                raise ProblemError(422, "idempotency-key-reused", "Idempotency-Key reused",
                                   "this Idempotency-Key was already used with a different body")
            return JSONResponse(saved["body"], status_code=saved["status"],
                                headers={**saved["headers"], "Idempotent-Replayed": "true"})

        book = DB["books"].get(body.book_id)
        if book is None:
            raise ProblemError(404, "book-not-found", "Book not found",
                               f"book {body.book_id} not found")
        if body.member_id not in DB["members"]:
            raise ProblemError(404, "member-not-found", "Member not found",
                               f"member {body.member_id} not found")
        if book["status"] != "available":
            raise ProblemError(409, "book-unavailable", "Book unavailable",
                               f"book {body.book_id} is {book['status']}")

        loan_id = f"ln_{DB['next_loan']:04d}"
        DB["next_loan"] += 1
        now = datetime.now(BKK).replace(microsecond=0)
        loan = {"id": loan_id, "book_id": body.book_id, "member_id": body.member_id,
                "borrowed_at": now.isoformat(),
                "due_date": (now.date() + timedelta(days=14)).isoformat(),
                "returned_at": None, "fine_satang": 0}
        DB["loans"][loan_id] = loan
        book["status"] = "on_loan"
        headers = {"Location": f"/v1/loans/{loan_id}"}
        # บันทึกผลลัพธ์ไว้ตอบซ้ำ (ของจริงควรเก็บใน Redis/DB พร้อมวันหมดอายุ เช่น 24 ชม.)
        DB["idempotency"][store_key] = {"body_hash": body_hash, "status": 201,
                                        "body": loan, "headers": headers}
    return JSONResponse(loan, status_code=201, headers=headers)


app.include_router(v1)

แนวคิด
  • Client เป็นคนสร้าง Idempotency-Key แอปสร้าง UUID ใหม่หนึ่งค่าต่อ "ความตั้งใจหนึ่งครั้ง" (กดยืมหนึ่งครั้ง) แล้วใช้ค่าเดิมทุกครั้งที่ Retry Server จึงรู้ว่า Request ที่มาซ้ำคือเรื่องเดิม ถ้า Server สร้าง key เอง Client ที่ไม่ได้รับ Response ครั้งแรกจะไม่มีทางรู้ key นั้น
  • เก็บ key แยกตาม Client คีย์ของ dict คือ (client_id, idempotency_key) ถ้าเก็บรวมทั้งระบบ เมื่อสอง Client บังเอิญใช้ key เดียวกัน Client ที่สองจะได้ข้อมูลการยืมของ Client แรก ซึ่งเป็นทั้งบั๊กและการรั่วไหลของข้อมูล เทสต์ test_keys_are_scoped_per_client พิสูจน์ว่าไม่เกิดปัญหานี้
  • เทียบ Body ด้วย hash แบบมาตรฐาน json.dumps(..., sort_keys=True) ทำให้ {"book_id": ..., "member_id": ...} กับ JSON ที่สลับลำดับ key ได้ hash เดียวกัน เพราะความหมายเหมือนกัน และเก็บแค่ hash ไม่ต้องเก็บ Body ทั้งก้อน
  • Lock ครอบทั้ง "ตรวจ-สร้าง-บันทึก" Endpoint แบบ def ของ FastAPI รันใน Thread Pool ถ้าสอง Request ที่มี key เดียวกันมาถึงพร้อมกัน และไม่มี Lock ทั้งคู่อาจตรวจไม่เจอ key แล้วสร้างการยืมคนละรายการ ในระบบจริงที่มีหลาย Process ต้องใช้กลไกของฐานข้อมูลหรือ Redis แทน threading.Lock เช่น Unique Constraint บนคู่ (client, key)
  • Rate Limit แบบ Fixed Window เก็บ (เวลาเริ่มหน้าต่าง, จำนวนครั้ง) ต่อ Client เมื่อครบ 10 วินาทีก็เริ่มนับใหม่ Retry-After คำนวณจากเวลาที่เหลือของหน้าต่าง และปัดขึ้นด้วย math.ceil เพื่อไม่ให้ Client กลับมาเร็วเกินไป ในการสาธิตด้วย curl Request ที่ 6 มาถึงหลัง Request แรกไม่ถึงหนึ่งวินาที จึงได้ Retry-After=10 ส่วนในเทสต์ที่เลื่อนเวลาไป 3 วินาทีได้ 7 พอดี
  • ฉีดนาฬิกาเข้าไปแทนการรอจริง FixedWindowLimiter รับ clock เป็นฟังก์ชัน เทสต์จึงแทนด้วย lambda: fake["now"] แล้วเลื่อนเวลาเองได้ เทสต์จึงเร็วและให้ผลเหมือนเดิมทุกครั้ง ไม่ขึ้นกับความเร็วของเครื่อง
  • Dependency ที่ระดับ Router ใส่ rate_limit ใน APIRouter(dependencies=[...]) ทำให้ทุก Endpoint ใต้ /v1 ถูกจำกัดอัตโนมัติ และเพราะ FastAPI Cache ผลของ Dependency ตัวเดียวกันภายใน Request เดียว การเรียก Depends(rate_limit) ซ้ำใน create_loan จึงไม่นับซ้ำ เทสต์ test_replays_also_count_toward_limit ยืนยันว่า POST 5 ครั้งผ่าน และครั้งที่ 6 ได้ 429 ถ้านับซ้ำ ครั้งที่ 3 ก็จะโดนแล้ว
  • ใช้ 429 ไม่ใช่ 503 429 Too Many Requests บอกว่า Client คนนี้ส่งเกินโควตา ส่วน 503 แปลว่า Server มีปัญหาทั้งระบบ การตอบ 429 พร้อม Retry-After ทำให้ Client ที่เขียนดีรอแล้วลองใหม่ได้ถูกจังหวะ ซึ่งเป็นการป้องกัน API4:2023 Unrestricted Resource Consumption การทดสอบยิงถี่แบบนี้ให้ทำกับ 127.0.0.1 หรือระบบของตัวเองเท่านั้น การยิงใส่ระบบของผู้อื่นโดยไม่ได้รับอนุญาตผิด พ.ร.บ.ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์
ไอเดียต่อยอด
  1. ย้ายที่เก็บ Idempotency และตัวนับ Rate Limit ไปไว้ใน Redis (รันด้วย Docker) โดยตั้งวันหมดอายุของ key เป็น 24 ชั่วโมง และใช้คำสั่ง INCR คู่กับ EXPIRE สำหรับตัวนับ เพื่อให้ทำงานถูกต้องเมื่อรัน uvicorn หลาย Worker
  2. เปลี่ยน Fixed Window เป็น Token Bucket ที่อนุญาตให้ยิงต่อเนื่องได้เป็นช่วงสั้น ๆ (Burst) แล้วเขียนเทสต์ที่พิสูจน์ว่าจะไม่เกิดกรณียิงได้เกือบ 2 เท่าของโควตา (เกือบ 10 ครั้ง) ภายในช่วงเวลาสั้น ๆ รอบรอยต่อของสองหน้าต่างเวลา ซึ่งเป็นจุดอ่อนของ Fixed Window
  3. เพิ่ม Header ที่บอกโควตาและจำนวนครั้งที่เหลือในทุก Response ตามร่างมาตรฐาน RateLimit Header Fields ของ IETF โดยตรวจชื่อและรูปแบบ Header ฉบับล่าสุดที่ IETF Datatracker ก่อนลงมือ เพราะมาตรฐานนี้ยังเป็นฉบับร่าง (Draft) และรูปแบบเคยเปลี่ยนมาแล้ว
  4. เขียน client_retry.py ด้วย httpx 0.28.1 ที่สร้าง Idempotency-Key ครั้งเดียว แล้ว Retry ด้วย Exponential Backoff กับ Jitter และเคารพ Retry-After เมื่อได้ 429 จากนั้นทดสอบกับ Server นี้
  5. เก็บ Response ของ Error บางประเภทด้วย เช่น 409 book-unavailable เพื่อให้ Retry ได้ผลเดิมเสมอ และเขียนเทสต์ที่ส่ง Request ซ้ำพร้อมกันจากหลาย Thread ด้วย concurrent.futures.ThreadPoolExecutor เพื่อพิสูจน์ว่า Lock ป้องกันการยืมซ้ำได้จริง
  6. ตรวจ X-API-Key กับรายการ key ที่เก็บเป็น hash SHA-256 ใน Environment Variable หรือฐานข้อมูล และเปรียบเทียบด้วย hmac.compare_digest ตามแนวคิดที่ 10 ของ Part 2 แทนการยอมรับทุกค่า
