Mini Project: E-commerce Database

เป้าหมายของโปรเจกต์

ออกแบบและสร้างฐานข้อมูลร้านค้าออนไลน์บน PostgreSQL 16 ให้มีคุณภาพแบบที่ใช้ในงานจริง แล้วใช้มันตอบคำถามธุรกิจด้วย SQL งานนี้ตั้งใจให้เป็น Repository ที่คุณเปิดให้ผู้สัมภาษณ์ดูได้ทันที เพราะมันแสดงทักษะที่บริษัทต้องการครบทั้ง Data Modeling, การเขียน Query ที่ซับซ้อน, การปรับ Performance, ความปลอดภัย และการเชื่อมต่อจาก Python

หัวใจของโปรเจกต์คือ ทุกอย่างสร้างใหม่ได้ด้วยคำสั่งเดียว และได้ผลเหมือนเดิมทุกครั้ง ข้อมูลตัวอย่างสร้างด้วยเลขคณิตแบบกำหนดแน่นอน (Deterministic) ไม่ใช้ random() ดังนั้นผลลัพธ์ทุกตัวเลขในหน้านี้จะตรงกับที่คุณได้บนเครื่องตัวเอง (ยกเว้นเวลาที่ใช้รัน ซึ่งขึ้นกับเครื่อง)

ฟีเจอร์ที่จะได้

  • 6 ตาราง customers, categories, products, orders, order_items, payments พร้อม Constraint ครบทุกชนิด ได้แก่ Primary Key, Foreign Key, UNIQUE, NOT NULL, CHECK และ DEFAULT
  • Seed แบบ Deterministic หมวดสินค้า 10 หมวด 2 ระดับ สินค้า 30 รายการ ลูกค้า 500 คน คำสั่งซื้อ 5,000 รายการ ระหว่าง 2025-01-01 ถึง 2026-06-30 และข้อมูลการชำระเงิน
  • ER Diagram ทั้งแบบตัวอักษร (ASCII) และแบบ Mermaid ที่ GitHub วาดเป็นรูปให้อัตโนมัติ
  • Query วิเคราะห์ 20 ข้อ แต่ละไฟล์ขึ้นต้นด้วยคำถามธุรกิจเป็นภาษาไทย ผลลัพธ์จริงเก็บไว้ใน results/
  • Index Tuning วัดด้วย EXPLAIN (ANALYZE, BUFFERS) ก่อนและหลังสร้าง Index แล้วบันทึกไว้ใน docs/explain.md
  • report.py สคริปต์ Python ใช้ psycopg 3 กับ Parameterized Query รับค่า --month และ --top พิมพ์รายงานภาษาไทยและบันทึก CSV ได้
  • Role อ่านอย่างเดียว ecommerce_report สำหรับทีมทำรายงาน พร้อมพิสูจน์ว่าเขียนข้อมูลไม่ได้
  • Backup และทดสอบ Restore ด้วย pg_dump -Fc และ pg_restore แล้วเทียบจำนวนแถวอัตโนมัติ
  • README ที่อธิบายโปรเจกต์ครบ พร้อมนำขึ้น GitHub

  2. Step 2: ออกแบบ Schema และเขียน CREATE TABLE ทั้ง 6 ตาราง

    ไฟล์นี้คือแบบแปลนของฐานข้อมูล ทุกคอลัมน์ถูกเลือกชนิดข้อมูลและ Constraint อย่างตั้งใจ เพื่อให้ฐานข้อมูลปฏิเสธข้อมูลผิดตั้งแต่ต้นทาง แทนที่จะปล่อยให้โค้ดของแอปตรวจเองทั้งหมด

    -- schema/01_tables.sql : สร้าง 6 ตารางของร้านค้าออนไลน์ พร้อม Constraint ครบ
-- ตารางลูกค้า
CREATE TABLE customers (
    customer_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name   TEXT        NOT NULL,
    email       TEXT        NOT NULL UNIQUE,
    phone       TEXT,                                   -- ไม่บังคับกรอก จึงเป็น NULL ได้
    province    TEXT        NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ตารางหมวดสินค้า อ้างอิงตัวเองเพื่อทำหมวดแม่-หมวดลูก
CREATE TABLE categories (
    category_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        TEXT NOT NULL UNIQUE,
    parent_id   INTEGER REFERENCES categories (category_id)
);

-- ตารางสินค้า ราคาใช้ NUMERIC เพื่อไม่ให้ทศนิยมเพี้ยน
CREATE TABLE products (
    product_id  INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku         TEXT          NOT NULL UNIQUE,
    name        TEXT          NOT NULL,
    category_id INTEGER       NOT NULL REFERENCES categories (category_id),
    price       NUMERIC(10,2) NOT NULL CHECK (price >= 0),
    stock       INTEGER       NOT NULL DEFAULT 0 CHECK (stock >= 0),
    is_active   BOOLEAN       NOT NULL DEFAULT TRUE
);

-- ตารางคำสั่งซื้อ สถานะต้องเป็นค่าใดค่าหนึ่งใน 5 ค่านี้เท่านั้น
CREATE TABLE orders (
    order_id     INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  INTEGER       NOT NULL REFERENCES customers (customer_id),
    ordered_at   TIMESTAMPTZ   NOT NULL,
    status       TEXT          NOT NULL
                 CHECK (status IN ('pending', 'paid', 'shipped', 'delivered', 'cancelled')),
    shipping_fee NUMERIC(10,2) NOT NULL DEFAULT 0 CHECK (shipping_fee >= 0)
);

-- รายการสินค้าในคำสั่งซื้อ (ตาราง Junction ระหว่าง orders กับ products)
-- unit_price คือราคา ณ วันที่ซื้อ เก็บไว้เป็นประวัติ ไม่ใช่ข้อมูลซ้ำซ้อน
CREATE TABLE order_items (
    order_id   INTEGER       NOT NULL REFERENCES orders (order_id) ON DELETE CASCADE,
    product_id INTEGER       NOT NULL REFERENCES products (product_id),
    quantity   INTEGER       NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(10,2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);

-- การชำระเงิน 1 คำสั่งซื้อมีได้ไม่เกิน 1 รายการ (UNIQUE บน order_id)
CREATE TABLE payments (
    payment_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id   INTEGER       NOT NULL UNIQUE REFERENCES orders (order_id) ON DELETE CASCADE,
    method     TEXT          NOT NULL
               CHECK (method IN ('credit_card', 'promptpay', 'bank_transfer', 'cod')),
    amount     NUMERIC(10,2) NOT NULL CHECK (amount > 0),
    paid_at    TIMESTAMPTZ,
    status     TEXT          NOT NULL CHECK (status IN ('success', 'failed', 'refunded'))
);
    เหตุผลของการออกแบบแต่ละจุด
    ส่วนของ Schemaเหตุผล
    GENERATED ALWAYS AS IDENTITYวิธีสร้างเลขลำดับอัตโนมัติตามมาตรฐาน SQL ที่ PostgreSQL แนะนำ แทน SERIAL แบบเก่า และกันไม่ให้ใครใส่เลข id เองโดยไม่ตั้งใจ
    NUMERIC(10,2) สำหรับเงินเก็บทศนิยมแบบแม่นยำ ไม่เพี้ยนแบบ REAL หรือ DOUBLE PRECISION (เช่น 0.1 + 0.2 ไม่เท่ากับ 0.3)
    TIMESTAMPTZ สำหรับ ordered_atเก็บเวลาพร้อม Time Zone ทำให้คำนวณช่วงเวลาได้ถูกต้องแม้ผู้ใช้อยู่คนละประเทศ
    email TEXT NOT NULL UNIQUEลูกค้า 1 คนใช้อีเมลเดียว และ UNIQUE สร้าง Index ให้อัตโนมัติ ค้นหาด้วยอีเมลจึงเร็ว
    phone TEXT (ไม่มี NOT NULL)ลูกค้าบางคนไม่ให้เบอร์โทร เราจึงยอมให้เป็น NULL ได้ เบอร์โทรเก็บเป็น TEXT เพราะต้องเก็บเลข 0 นำหน้า และไม่ได้เอาไปคำนวณ
    parent_id REFERENCES categoriesSelf-referencing Foreign Key ทำให้มีหมวดแม่และหมวดลูกได้ไม่จำกัดชั้น ใช้ Recursive CTE ไล่ลำดับชั้นได้
    CHECK (status IN (...))บังคับให้สถานะมีแค่ 5 ค่า ถ้าโค้ดพิมพ์ผิดเป็น 'shipping' ฐานข้อมูลจะปฏิเสธทันที
    PRIMARY KEY (order_id, product_id)Composite Primary Key กันสินค้าเดียวกันซ้ำในคำสั่งซื้อเดียว ถ้าซื้อ 2 ชิ้นให้เพิ่ม quantity แทน
    ON DELETE CASCADE ที่ order_items และ paymentsถ้าลบคำสั่งซื้อ รายการสินค้าและการชำระเงินของคำสั่งซื้อนั้นจะถูกลบตามไปด้วย ไม่เหลือแถวกำพร้า แต่ products ไม่ใช้ CASCADE เพราะเราไม่อยากให้การลบสินค้าไปลบประวัติการขาย
    unit_price ใน order_itemsเป็น Snapshot ราคา ณ วันที่ซื้อ ถ้าวันหน้าขึ้นราคาสินค้า ยอดขายในอดีตต้องไม่เปลี่ยน จึงไม่ใช่ข้อมูลซ้ำซ้อนที่ขัดกับ Normalization
    order_id ... UNIQUE ใน paymentsทำให้ความสัมพันธ์ orders กับ payments เป็น 1 ต่อ 0..1 คือคำสั่งซื้อหนึ่งมีการชำระเงินได้ไม่เกิน 1 รายการ
    ทดสอบว่า Constraint ทำงานจริง

--    p 0-149 = ลูกค้า 251-400 ซื้อคนละ 1 ครั้ง, p 150-249 = ลูกค้า 401-450 ซื้อคนละ 2 ครั้ง

--    ลูกค้า 451-500 ไม่เคยซื้อเลย
--    day ใช้ sqrt ทำให้ยอดสั่งซื้อค่อย ๆ เพิ่มขึ้นตามเวลา (ร้านกำลังโต)
WITH base AS (
    SELECT g,
           (g * 7919) % 5000                                   AS p,
           floor(546 * sqrt((g - 1) / 5000.0))::int            AS day
    FROM generate_series(1, 5000) AS g
), picked AS (
    SELECT g, day,
           CASE WHEN p < 150 THEN 251 + p
                WHEN p < 250 THEN 401 + (p - 150) % 50
                ELSE 1 + ((g * g * 31 + g * 17) % 997) % 250 END AS customer_id
    FROM base
)
INSERT INTO orders (customer_id, ordered_at, status)
SELECT customer_id,
       TIMESTAMPTZ '2025-01-01 00:00:00+07'
           + day * INTERVAL '1 day'
           + (8 + (g * 13) % 14) * INTERVAL '1 hour'
           + ((g * 7) % 60) * INTERVAL '1 minute',
       CASE WHEN (g + customer_id) % 19 = 0 THEN 'cancelled'
            WHEN customer_id % 8 = 3 AND g % 9 = 0 THEN 'cancelled'  -- ภูเก็ตยกเลิกบ่อยกว่า
            WHEN day >= 536 THEN (ARRAY['pending','paid','shipped'])[1 + g % 3]
            WHEN day >= 520 THEN 'shipped'
            ELSE 'delivered' END
FROM picked
ORDER BY g;

       w.product_id,
       1 + ((o.order_id + k) % 6 = 0)::int + ((o.order_id + k) % 15 = 0)::int,

FROM orders AS o

ORDER BY o.order_id, k

SET shipping_fee = CASE WHEN t.subtotal >= 1000 THEN 0 ELSE 50 END
FROM (SELECT order_id, SUM(quantity * unit_price) AS subtotal

--    pending บางรายการจ่ายไม่ผ่าน = failed
INSERT INTO payments (order_id, method, amount, paid_at, status)
SELECT o.order_id,
       m.method,
       t.subtotal + o.shipping_fee,
       CASE WHEN o.status = 'pending' THEN NULL
            WHEN m.method = 'cod' THEN o.ordered_at + INTERVAL '3 days'  -- เก็บเงินปลายทาง
            ELSE o.ordered_at + INTERVAL '10 minutes' END,
       CASE WHEN o.status = 'cancelled' THEN 'refunded'
            WHEN o.status = 'pending'   THEN 'failed'
            ELSE 'success' END
FROM orders AS o
JOIN (SELECT order_id, SUM(quantity * unit_price) AS subtotal
      FROM order_items GROUP BY order_id) AS t ON t.order_id = o.order_id
CROSS JOIN LATERAL (
    SELECT (ARRAY['promptpay','promptpay','promptpay','credit_card','credit_card',
                  'bank_transfer','cod'])[1 + o.order_id % 7] AS method
) AS m
WHERE o.status IN ('paid', 'shipped', 'delivered')
   OR (o.status = 'cancelled' AND o.order_id % 3 = 0)
   OR (o.status = 'pending'   AND o.order_id % 4 = 0)
ORDER BY o.order_id;

    q02: ยอดขายตามหมวดระดับบนสุด (Recursive CTE)
    -- q02: หมวดสินค้าระดับบนสุดหมวดไหนทำยอดขายได้มากที่สุด (ไล่หมวดลูกขึ้นไปหาหมวดแม่ด้วย Recursive CTE)
WITH RECURSIVE tree AS (
    -- Anchor: หมวดระดับบนสุด ตั้ง root_name เป็นชื่อตัวเอง
    SELECT category_id, name AS root_name
    FROM categories
    WHERE parent_id IS NULL
    UNION ALL
    -- Recursive: หมวดลูกรับ root_name ต่อจากหมวดแม่
    SELECT c.category_id, t.root_name
    FROM categories AS c
    JOIN tree AS t ON c.parent_id = t.category_id
)
SELECT t.root_name                                  AS top_category,
       SUM(oi.quantity * oi.unit_price)             AS revenue,
       round(100.0 * SUM(oi.quantity * oi.unit_price)
             / SUM(SUM(oi.quantity * oi.unit_price)) OVER (), 2) AS pct
FROM order_items AS oi
JOIN orders   AS o ON o.order_id   = oi.order_id
JOIN products AS p ON p.product_id = oi.product_id
JOIN tree     AS t ON t.category_id = p.category_id
WHERE o.status IN ('paid', 'shipped', 'delivered')
GROUP BY t.root_name
ORDER BY revenue DESC;

    q05: มูลค่าเฉลี่ยต่อคำสั่งซื้อ (AOV) รายปี
    -- q05: มูลค่าเฉลี่ยต่อคำสั่งซื้อ (Average Order Value) ของแต่ละปีเป็นเท่าไร
WITH order_totals AS (
    SELECT o.order_id,
           o.ordered_at,
           SUM(oi.quantity * oi.unit_price) AS total
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.order_id
    WHERE o.status IN ('paid', 'shipped', 'delivered')
    GROUP BY o.order_id, o.ordered_at
)
SELECT EXTRACT(YEAR FROM ordered_at)::int AS year,
       COUNT(*)                           AS orders,
       SUM(total)                         AS revenue,
       round(AVG(total), 2)               AS aov
FROM order_totals
GROUP BY EXTRACT(YEAR FROM ordered_at)
ORDER BY year;

    q13: แบ่งกลุ่มลูกค้าแบบ RFM ด้วย NTILE
    -- q13: แบ่งกลุ่มลูกค้าแบบ RFM (Recency, Frequency, Monetary) ด้วย NTILE(4)
-- คะแนน 4 = ดีที่สุด, วันอ้างอิงคือ 2026-06-30
WITH rfm AS (
    SELECT o.customer_id,
           DATE '2026-06-30' - MAX(o.ordered_at)::date AS recency_days,
           COUNT(DISTINCT o.order_id)                  AS frequency,
           SUM(oi.quantity * oi.unit_price)            AS monetary
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.order_id
    WHERE o.status IN ('paid', 'shipped', 'delivered')
    GROUP BY o.customer_id
), scored AS (
    SELECT customer_id,
           NTILE(4) OVER (ORDER BY recency_days DESC) AS r,   -- ซื้อล่าสุดยิ่งใกล้ ยิ่งได้คะแนนสูง
           NTILE(4) OVER (ORDER BY frequency)         AS f,
           NTILE(4) OVER (ORDER BY monetary)          AS m
    FROM rfm
)
SELECT CASE
           WHEN r = 4 AND f = 4 AND m = 4 THEN '1 Champions'
           WHEN r >= 3 AND f >= 3         THEN '2 Loyal'
           WHEN r >= 3                    THEN '3 Promising'
           WHEN r = 2                     THEN '4 Need Attention'
           ELSE                                '5 At Risk'
       END                 AS segment,
       COUNT(*)            AS customers
FROM scored
GROUP BY 1
ORDER BY 1;

import argparse

import sys
from datetime import date, datetime

# อ่าน Connection String จาก Environment Variable ห้ามเขียนรหัสผ่านลงในโค้ด
DATABASE_URL = os.environ.get("DATABASE_URL", "postgresql:///ecommerce")

PAID = ("paid", "shipped", "delivered")   # สถานะที่นับเป็นยอดขาย

SUMMARY_SQL = """
    SELECT COUNT(DISTINCT o.order_id)        AS orders,
           COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS revenue
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.order_id
    WHERE o.status = ANY(%(statuses)s)

TOP_SQL = """
    SELECT p.sku, p.name,
           SUM(oi.quantity)                 AS units,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM orders AS o

    JOIN products    AS p  ON p.product_id  = oi.product_id
    WHERE o.status = ANY(%(statuses)s)
      AND o.ordered_at >= %(start)s::date
      AND o.ordered_at <  %(start)s::date + INTERVAL '1 month'
    GROUP BY p.product_id, p.sku, p.name
    ORDER BY revenue DESC, p.sku
    LIMIT %(top)s
"""


def parse_month(text: str) -> date:
    """แปลง 'YYYY-MM' เป็นวันที่ 1 ของเดือน ถ้ารูปแบบผิดให้ argparse แจ้ง Error"""
    try:
        return datetime.strptime(text, "%Y-%m").date()
    except ValueError:
        raise argparse.ArgumentTypeError(f"รูปแบบเดือนต้องเป็น YYYY-MM แต่ได้ '{text}'")


def build_report(conn, start: date, top: int) -> tuple[dict, list[dict]]:
    """ดึงตัวเลขสรุปและสินค้าขายดี ทุกค่าส่งผ่าน Placeholder ไม่ต่อสตริงเอง"""
    params = {"statuses": list(PAID), "start": start, "top": top}
    with conn.cursor(row_factory=dict_row) as cur:
        cur.execute(SUMMARY_SQL, params)
        summary = cur.fetchone()
        cur.execute(TOP_SQL, params)
        top_rows = cur.fetchall()
    return summary, top_rows


def print_report(start: date, summary: dict, top_rows: list[dict]) -> None:

        print(f"{i:>2}. {row['sku']}  {row['name']:<20} {row['units']:>5} ชิ้น {row['revenue']:>14,.2f}")

    with open(path, "w", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=["sku", "name", "units", "revenue"])
        writer.writeheader()
        writer.writerows(top_rows)
    print(f"บันทึก CSV แล้วที่ {path}")


def main() -> int:
    parser = argparse.ArgumentParser(description="รายงานยอดขายรายเดือน")
    parser.add_argument("--month", type=parse_month, default=parse_month("2026-06"),
                        help="เดือนที่ต้องการ รูปแบบ YYYY-MM (ค่าเริ่มต้น 2026-06)")
    parser.add_argument("--top", type=int, default=5, help="จำนวนสินค้าขายดีที่จะแสดง")
    parser.add_argument("--csv", help="ถ้าระบุ จะบันทึกสินค้าขายดีเป็นไฟล์ CSV")
    args = parser.parse_args()

    if not 1 <= args.top <= 50:
        parser.error("--top ต้องอยู่ระหว่าง 1 ถึง 50")

    try:
        with psycopg.connect(DATABASE_URL) as conn:
            summary, top_rows = build_report(conn, args.month, args.top)
    except psycopg.OperationalError as e:
        print(f"เชื่อมต่อฐานข้อมูลไม่ได้: {e}", file=sys.stderr)
        return 1

    print_report(args.month, summary, top_rows)
    if args.csv:
        write_csv(args.csv, top_rows)
    return 0


if __name__ == "__main__":

  9. Step 9: Role อ่านอย่างเดียวสำหรับทีมรายงาน และ Backup พร้อมทดสอบ Restore

    ระบบจริงไม่ให้ทุกคนใช้ Role เจ้าของตาราง ทีมทำรายงานควรอ่านได้อย่างเดียว ถ้าสคริปต์ของทีมนั้นมีบั๊กหรือถูกเจาะ ข้อมูลก็จะไม่ถูกแก้หรือลบ นี่คือหลัก Least Privilege (ให้สิทธิ์น้อยที่สุดที่ยังทำงานได้) และอีกเรื่องที่ขาดไม่ได้คือ Backup ซึ่งต้อง ทดสอบ Restore จริง ด้วย เพราะ Backup ที่ไม่เคยลอง Restore อาจใช้ไม่ได้ในวันที่ต้องการ

    9.1 สร้าง Role ecommerce_report
    -- scripts/roles.sql : สร้าง Role อ่านอย่างเดียวสำหรับทีมทำรายงาน (รันด้วยสิทธิ์ postgres)
-- วิธีใช้: sudo -u postgres psql -d ecommerce -v owner="$USER" < scripts/roles.sql
-- :owner คือเจ้าของตาราง (ชื่อผู้ใช้ Linux ของเรา) ส่งเข้ามาด้วย -v

-- 1) สร้าง Role เฉพาะเมื่อยังไม่มี (\gexec รันผลลัพธ์ของ SELECT เป็นคำสั่ง SQL)
SELECT 'CREATE ROLE ecommerce_report NOLOGIN'
WHERE NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'ecommerce_report') \gexec

-- 2) ให้สิทธิ์แค่เชื่อมต่อ มองเห็น Schema และอ่านตาราง ไม่มีสิทธิ์เขียน
GRANT CONNECT ON DATABASE ecommerce TO ecommerce_report;
GRANT USAGE ON SCHEMA public TO ecommerce_report;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO ecommerce_report;

-- 3) ตารางที่ owner สร้างในอนาคตจะอ่านได้ทันทีโดยไม่ต้อง GRANT ซ้ำ
ALTER DEFAULT PRIVILEGES FOR ROLE :"owner" IN SCHEMA public
    GRANT SELECT ON TABLES TO ecommerce_report;

-- 4) ให้ owner สลับไปเป็น ecommerce_report ได้ด้วย SET ROLE เพื่อทดสอบสิทธิ์
GRANT ecommerce_report TO :"owner";

DB="${DB:-ecommerce}"
RESTORE_DB="${DB}_restore"
mkdir -p backups                       # backups/ อยู่ใน .gitignore ไม่ขึ้น GitHub

pg_dump -Fc -d "$DB" -f "backups/$DB.dump"
ls -lh "backups/$DB.dump" | awk '{print "    ขนาดไฟล์:", $5}'

echo "==> Restore ลงฐานข้อมูลใหม่ $RESTORE_DB"
dropdb --if-exists "$RESTORE_DB"
createdb "$RESTORE_DB"
pg_restore --no-owner -d "$RESTORE_DB" "backups/$DB.dump"

## ความปลอดภัย

## สิ่งที่ได้เรียนรู้

- การออกแบบ Schema ด้วย Constraint ช่วยกันข้อมูลผิดได้ตั้งแต่ระดับฐานข้อมูล
- Seed แบบ Deterministic ทำให้ผล Query ตรวจสอบซ้ำได้ทุกครั้ง
- Index ต้องสร้างจากการวัดผล ไม่ใช่การเดา

1. WHERE กับ HAVING ต่างกันอย่างไร และ SQL ประมวลผลคำสั่ง SELECT ตามลำดับใด (Junior)

คำตอบที่ดี: WHERE กรอง แถว ก่อนจัดกลุ่ม ส่วน HAVING กรอง กลุ่ม หลังจาก GROUP BY คำนวณ Aggregate เสร็จแล้ว จึงใช้ SUM() หรือ COUNT() ใน HAVING ได้ แต่ใช้ใน WHERE ไม่ได้

ลำดับการประมวลผลเชิงตรรกะคือ FROM และ JOIN → WHERE → GROUP BY → HAVING → SELECT (รวม Window Function) → DISTINCT → ORDER BY → LIMIT/OFFSET ลำดับนี้อธิบายได้ว่าทำไมชื่อเล่นที่ตั้งด้วย AS ใน SELECT ใช้ใน ORDER BY ได้ แต่ใช้ใน WHERE ไม่ได้ และทำไม Window Function ใช้ใน WHERE ไม่ได้ ต้องครอบด้วย CTE ก่อน

ข้อควรพูดเพิ่ม: ถ้าเงื่อนไขกรองได้ตั้งแต่ระดับแถว ควรใส่ใน WHERE เพราะลดจำนวนแถวก่อนจัดกลุ่ม ทำให้เร็วกว่าและใช้ Index ได้

-- เดือนที่มียอดขายเกิน 8 ล้านบาท นับเฉพาะคำสั่งซื้อที่ไม่ถูกยกเลิก
SELECT date_trunc('month', o.ordered_at) AS month,
       SUM(oi.quantity * oi.unit_price)  AS revenue
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.order_id
WHERE o.status <> 'cancelled'                       -- กรองแถวก่อนจัดกลุ่ม
GROUP BY month
HAVING SUM(oi.quantity * oi.unit_price) > 8000000   -- กรองกลุ่มหลังรวมยอด
ORDER BY month;
2. INNER JOIN กับ LEFT JOIN ต่างกันอย่างไร และจะหาลูกค้าที่ไม่เคยสั่งซื้อเลยได้อย่างไร (Junior)

คำตอบที่ดี: INNER JOIN คืนเฉพาะแถวที่จับคู่ได้ทั้งสองตาราง ส่วน LEFT JOIN คืนทุกแถวของตารางซ้าย ถ้าแถวไหนไม่มีคู่ คอลัมน์ของตารางขวาจะเป็น NULL ในฐานข้อมูล shop ที่มีลูกค้า 8 คนและคำสั่งซื้อ 14 รายการ INNER JOIN ได้ 14 แถว แต่ LEFT JOIN ได้ 15 แถว เพราะมีลูกค้า 1 คน (Anan Thongkham) ที่ไม่เคยสั่งซื้อ

การหาลูกค้าที่ไม่เคยสั่งซื้อทำได้สองแบบที่ให้ผลเหมือนกัน คือ Anti Join ด้วย LEFT JOIN ... WHERE o.order_id IS NULL หรือ NOT EXISTS ซึ่งอ่านตรงความหมายกว่า ควรหลีกเลี่ยง NOT IN (subquery) เพราะถ้า Subquery คืนค่า NULL แม้แถวเดียว ผลจะว่างทั้งหมดจาก Three-valued Logic

ข้อควรพูดเพิ่ม: กับดักที่พบบ่อยคือใส่เงื่อนไขของตารางขวาใน WHERE หลัง LEFT JOIN เช่น WHERE o.status = 'paid' ซึ่งทิ้งแถวที่เป็น NULL ไป ทำให้กลายเป็น INNER JOIN โดยไม่รู้ตัว ต้องย้ายเงื่อนไขนั้นไปไว้ใน ON

-- ลูกค้าที่ไม่เคยมีคำสั่งซื้อ
SELECT c.customer_id, c.name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1 FROM orders AS o WHERE o.customer_id = c.customer_id
);

คำตอบที่ดี: SQL Injection เกิดเมื่อโปรแกรมนำข้อความจากผู้ใช้ไปต่อเป็นส่วนหนึ่งของคำสั่ง SQL โดยตรง ผู้โจมตีจึงใส่ข้อความที่เปลี่ยนความหมายของคำสั่งได้ เช่น ใส่ x' OR '1'='1 ในช่องค้นหาอีเมล แล้วได้ข้อมูลลูกค้าทุกคนออกไป หรือใส่คำสั่งลบตาราง

วิธีป้องกันหลักคือ Parameterized Query ส่งตัวคำสั่งกับค่าแยกกัน ใน psycopg 3 ใช้ %s หรือ %(name)s และส่งค่าเป็นอาร์กิวเมนต์ที่สองของ execute() ใน sqlite3 ใช้ ? ห้ามใช้ f-string, + หรือ % ของ Python สร้าง SQL เอง สำหรับชื่อตารางหรือคอลัมน์ที่ต้องเปลี่ยนได้ (ซึ่ง Placeholder ใช้ไม่ได้) ให้ตรวจกับ Allowlist แล้วใช้ psycopg.sql.Identifier

ข้อควรพูดเพิ่ม: ป้องกันหลายชั้น (Defense in Depth) คือ ตรวจรูปแบบข้อมูลนำเข้า ใช้ Role ที่มีสิทธิ์น้อยที่สุด เช่น Role รายงานที่ SELECT ได้อย่างเดียวแบบ ecommerce_report และไม่แสดงข้อความ Error ของฐานข้อมูลให้ผู้ใช้ปลายทางเห็น

# ผิด: ต่อสตริงเอง ผู้ใช้ควบคุมคำสั่ง SQL ได้
cur.execute(f"SELECT * FROM customers WHERE email = '{email}'")

# ถูก: ส่งค่าแยกผ่าน Placeholder ฐานข้อมูลมองเป็นข้อมูลเสมอ
cur.execute("SELECT * FROM customers WHERE email = %s", (email,))
4. ถ้ามี Query ที่ช้าบน Production คุณจะหาสาเหตุและแก้อย่างไร (Mid)

คำตอบที่ดี: ผมจะวัดก่อนแก้เสมอ ขั้นตอนคือ

  1. หา Query ที่ช้าจริงจาก Log หรือ pg_stat_statements ไม่เดาเอง
  2. รัน EXPLAIN (ANALYZE, BUFFERS) บนข้อมูลที่ขนาดใกล้เคียงของจริง (ถ้าเป็นคำสั่งแก้ข้อมูลต้องครอบด้วย BEGIN/ROLLBACK) แล้วดูว่ามี Seq Scan ที่ Rows Removed by Filter สูงมาก, จำนวน rows ที่ Planner ประมาณผิดจากของจริงมาก หรือ Sort ที่ล้นหน่วยความจำหรือไม่
  3. แก้ตามสาเหตุ เช่น สร้าง Index บนคอลัมน์ที่กรองหรือ JOIN (Foreign Key ใน PostgreSQL ไม่มี Index อัตโนมัติ), ใช้ Composite Index ตามกฎ Leftmost Prefix, ใช้ Partial Index สำหรับเงื่อนไขที่เจาะจง, เขียน Query ใหม่ไม่ให้ห่อคอลัมน์ด้วยฟังก์ชัน หรือรัน ANALYZE ถ้าสถิติเก่า
  4. วัดซ้ำและบันทึกผลก่อนและหลัง แล้วสร้าง Index บน Production ด้วย CREATE INDEX CONCURRENTLY เพื่อไม่ล็อกตาราง

ตัวอย่างจากโปรเจกต์: คิวคำสั่งซื้อ pending เดิมเป็น Seq Scan อ่าน 74 Buffers หลังสร้าง Partial Index ON orders (ordered_at) WHERE status = 'pending' เหลือ 2 Buffers และไม่ต้อง Sort

ข้อควรพูดเพิ่ม: Index ไม่ได้ฟรี ทุก Index ทำให้ INSERT และ UPDATE ช้าลงและใช้พื้นที่ดิสก์ และ Planner อาจเลือก Seq Scan อย่างถูกต้องเมื่อตารางเล็กหรือ Query ต้องการแถวเป็นสัดส่วนใหญ่

5. ACID คืออะไร และจะป้องกันการขายสินค้าเกินสต็อกเมื่อมีคนสั่งพร้อมกันได้อย่างไร (Mid)

คำตอบที่ดี: ACID คือคุณสมบัติสี่ข้อของ Transaction

  • Atomicity สำเร็จทั้งหมดหรือไม่เกิดอะไรเลย เช่น สร้างคำสั่งซื้อ เพิ่มรายการสินค้า และตัดสต็อก ถ้าขั้นใดล้มเหลวต้องย้อนทั้งหมด
  • Consistency ข้อมูลผ่าน Constraint ทุกข้อเสมอ เช่น CHECK (stock >= 0)
  • Isolation Transaction ที่ทำพร้อมกันไม่รบกวนกันตามระดับ Isolation Level ที่เลือก
  • Durability เมื่อ COMMIT แล้วข้อมูลไม่หายแม้เครื่องดับ (PostgreSQL ใช้ WAL) และเสริมด้วย Backup

ปัญหาขายเกินสต็อกคือ Lost Update สองคนอ่านสต็อกได้ 1 ชิ้นพร้อมกัน แล้วต่างคนต่างขาย วิธีแก้มีหลายระดับ

  1. ล็อกแถวก่อนตรวจด้วย SELECT ... FOR UPDATE ภายใน Transaction คนที่สองจะรอจนคนแรก Commit แล้วเห็นสต็อกล่าสุด
  2. เขียนเป็นคำสั่งเดียวที่มีเงื่อนไข UPDATE products SET stock = stock - 1 WHERE product_id = 4 AND stock >= 1 แล้วตรวจจำนวนแถวที่ถูกแก้
  3. ใช้ REPEATABLE READ หรือ SERIALIZABLE แล้วให้แอปลองใหม่ (Retry) เมื่อเจอ could not serialize access due to concurrent update
  4. มี CHECK (stock >= 0) เป็นด่านสุดท้ายเสมอ

ข้อควรพูดเพิ่ม: ค่าเริ่มต้นของ PostgreSQL คือ READ COMMITTED และควรทำ Transaction ให้สั้น ล็อกแถวตามลำดับเดียวกันทุกครั้ง (เช่น เรียงตาม product_id) เพื่อลดโอกาสเกิด deadlock detected

BEGIN;
-- ล็อกแถวสินค้า คนอื่นที่จะแก้แถวนี้ต้องรอจนเรา COMMIT หรือ ROLLBACK
SELECT stock FROM products WHERE product_id = 4 FOR UPDATE;
-- แอปตรวจว่าสต็อกพอ แล้วจึงทำต่อ
INSERT INTO orders (customer_id, order_date, status) VALUES (1, DATE '2026-10-20', 'paid');
UPDATE products SET stock = stock - 1 WHERE product_id = 4;
COMMIT;
