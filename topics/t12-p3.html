    1. เพราะ SHA-256 ถอดกลับเป็นรหัสผ่านเดิมได้ แต่ Argon2 ถอดกลับไม่ได้
    2. เพราะ Argon2 เป็นการเข้ารหัสสองทาง ทำให้ Admin เปิดดูรหัสผ่านเดิมได้เมื่อผู้ใช้ลืม
    3. เพราะผลลัพธ์ของ SHA-256 ยาวเกินกว่าที่คอลัมน์ในฐานข้อมูลจะเก็บได้
    4. เพราะ Argon2 ถูกออกแบบให้ช้าและใช้หน่วยความจำมากโดยตั้งใจ และใส่ Salt สุ่มในทุก Hash ทำให้การเดารหัสด้วย GPU ทีละพันล้านครั้งแพงมาก ส่วน SHA-256 เร็วมากและไม่มี Salt ถ้าเรียกตรง ๆ แบบนี้

    3. ควรตั้ง allow_origins=["*"] คู่กับ allow_credentials=True เพราะเปิดกว้างและปลอดภัยที่สุด
    4. CORS ใช้แทน Rate Limiting ได้ เพราะ Request จาก Origin แปลกจะถูกตัดตั้งแต่ที่ Server

คำตอบ: incr, expire และ Retry-After

INCR เพิ่มค่าและคืนค่าใหม่ในขั้นตอนเดียวแบบ Atomic แม้มี Request พร้อมกันหลายร้อยตัวจาก Server หลายเครื่อง ตัวนับก็ไม่ผิด ถ้า Key ยังไม่มี Redis ถือว่าเริ่มจาก 0 ครั้งแรกจึงได้ 1 เราจึงเรียก EXPIRE key 60 เฉพาะตอน count == 1 เพื่อเริ่มหน้าต่างเวลา 60 วินาที เมื่อ Key หมดอายุ ตัวนับก็เริ่มใหม่ ส่วน Header Retry-After เป็น Header มาตรฐานของ HTTP ที่ใช้คู่กับ 429 เพื่อบอกจำนวนวินาทีที่ Client ควรรอ (แนวคิดที่ 11)

ระวัง

ถ้าโปรแกรมล่มระหว่าง INCR กับ EXPIRE Key จะไม่มีอายุและ IP นั้นจะถูกบล็อกตลอดไป งานจริงจึงมักรวมสองคำสั่งด้วย Pipeline แบบ Transaction (r.pipeline()) หรือ Lua Script ให้ทำงานเป็นก้อนเดียว

  • D ผิดเพราะ nginx ยังทำงานและฟัง Port 80 อยู่ curl จึงเชื่อมต่อได้และได้คำตอบ HTTP กลับมา curl: (7) จะเกิดเมื่อไม่มีอะไรฟัง Port 80 เลย เช่น เมื่อ nginx เองหยุดทำงาน

    # ฟังก์ชันกลางสำหรับหา Ticket ถ้าไม่พบให้ตอบ 404

    global next_id
    ticket = {"id": next_id, **payload.model_dump(), "status": "received"}
    tickets[next_id] = ticket
    next_id += 1

    items = [t for t in tickets.values() if status is None or t["status"] == status]

แนวคิด
  • แยก Schema ตามทิศทางของข้อมูล: TicketCreate คือสิ่งที่ Client ส่งเข้ามา TicketUpdate คือสิ่งที่แก้ได้ และ TicketOut คือสิ่งที่ยอมให้ออกไป การใส่ response_model=TicketOut ทำให้ FastAPI กรอง Field ที่ไม่ได้ประกาศ (phone) ออกก่อนส่ง ข้อมูลส่วนตัวจึงไม่รั่วแม้ Handler จะ return dict ทั้งก้อน
  • ให้ Pydantic ทำ Validation แทน if-else: Field(min_length=..., max_length=...), pattern=r"^0\d{9}$" และ Literal[...] ทำให้ Error ทุก Field ถูกรายงานพร้อมกันในครั้งเดียว (กรณีที่ 2 มี Error 4 รายการ) ผู้ใช้จึงแก้ได้ครบในรอบเดียว
  • กัน Mass Assignment ด้วย extra="forbid": ลูกค้าแอบส่ง "status":"done" มาได้ 422 แบบ extra_forbidden และฝั่ง Server ยังเขียนทับ "status": "received" หลัง model_dump() อีกชั้นหนึ่ง เป็นการป้องกันสองชั้น
  • PATCH แก้เฉพาะที่ส่งมา: model_dump(exclude_unset=True) ได้ dict ที่มีแค่ Field ที่ Client ส่งจริง แล้วนำไป update() ข้อมูลเดิม
  • รวม Logic ที่ใช้ซ้ำไว้ที่เดียว: find_ticket() ทำให้ GET, PATCH และ DELETE ตอบ 404 ด้วยข้อความเดียวกันเสมอ ส่วน Path(gt=0) กันค่า 0 และค่าติดลบตั้งแต่ชั้น Validation
  • ตอบ Status Code ให้ตรงความหมาย: 201 ตอนสร้าง, 204 ตอนลบซึ่งไม่มี Body (บรรทัดของกรณีที่ 7 จึงขึ้นต้นด้วยช่องว่างตามด้วย -> 204) และ 404 เมื่อหาไม่พบ

def create_access_token(employee: Employee) -> str:
    now = datetime.now(UTC)
    claims = {"sub": str(employee.id), "role": employee.role, "iat": now,
              "exp": now + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)}
    return jwt.encode(claims, JWT_SECRET, algorithm="HS256")


def get_current_employee(token: Annotated[str, Depends(oauth2_scheme)], db: DbSession) -> Employee:
    try:
        payload = jwt.decode(token, JWT_SECRET, algorithms=["HS256"])
    except jwt.InvalidTokenError:  # รวม ExpiredSignatureError ด้วย
        raise UNAUTHORIZED
    employee = db.get(Employee, int(payload["sub"]))
    if employee is None:
        raise UNAUTHORIZED
    return employee


CurrentEmployee = Annotated[Employee, Depends(get_current_employee)]


def require_role(role: str):
    # Dependency Factory: สร้าง Dependency ที่ตรวจ Role จากฐานข้อมูล ไม่เชื่อค่าจาก Client
    def checker(employee: CurrentEmployee) -> Employee:
        if employee.role != role:
            raise HTTPException(status_code=403, detail="ไม่มีสิทธิ์ทำรายการนี้")
        return employee
    return checker

แนวคิด
  • Fail fast เรื่อง Secret: แอปตรวจความยาว JWT_SECRET ตั้งแต่ตอน import ถ้าไม่ผ่านจะหยุดทันที ดีกว่าปล่อยให้แอปเปิดด้วย Secret ว่างที่ใครก็ปลอม Token ได้ ใน Mini Project ของ Part 4 งานนี้ย้ายไปอยู่ใน pydantic-settings ซึ่งทำได้เป็นระบบกว่า
  • Authentication กับ Authorization แยกชั้นกัน: get_current_employee ตอบคำถามว่า "คุณคือใคร" (ไม่ผ่านได้ 401 พร้อม WWW-Authenticate: Bearer) ส่วน require_role("manager") ตอบคำถามว่า "คุณทำสิ่งนี้ได้ไหม" (ไม่ผ่านได้ 403) Dependency Factory ทำให้ใช้ซ้ำกับ Role อื่นได้ด้วยบรรทัดเดียว
  • เชื่อแค่ข้อมูลจาก Server: Role อ่านจากแถวในฐานข้อมูลที่ได้จาก sub ใน Token ไม่ได้อ่านจาก Body ส่วน employee_id ของใบลามาจาก Token เสมอ และ extra="forbid" ทำให้การแอบส่ง role ตอนสมัครได้ 422
  • Object-level Authorization: GET /leaves/{leave_id} ตอบ 404 เมื่อเป็นใบลาของคนอื่น ป้องกัน BOLA ตาม OWASP API1 ในเฉลยนี้ยอมให้ manager ดูได้ทุกใบ เพราะหัวหน้าต้องเห็นใบลาก่อนอนุมัติ

    def set_json(self, key: str, value: dict, ttl: int) -> None:
        try:
            self.client.set(key, json.dumps(value, ensure_ascii=False), ex=ttl)
        except redis.exceptions.RedisError as exc:
            log(logging.WARNING, "cache set failed", key=key, error=type(exc).__name__)

    def delete(self, key: str) -> None:
        try:
            self.client.delete(key)
        except redis.exceptions.RedisError as exc:
            log(logging.WARNING, "cache delete failed", key=key, error=type(exc).__name__)

    def retry_after(self, key: str, limit: int, window: int) -> int | None:
        """Fixed Window: คืนจำนวนวินาทีที่ต้องรอ ถ้าเกินโควตา หรือ None ถ้ายังไม่เกิน"""
        try:
            count = self.client.incr(key)
            if count == 1:
                self.client.expire(key, window)  # เริ่มนับหน้าต่างเวลาใหม่
            if count > limit:
                ttl = self.client.ttl(key)
                return ttl if ttl > 0 else window
            return None
        except redis.exceptions.RedisError as exc:
            # Fail-open: Redis ล่มแล้วยังขายของได้ แต่บันทึก Log ไว้ให้ทีมรู้
            log(logging.WARNING, "rate limit skipped", key=key, error=type(exc).__name__)
            return None

    def ping(self) -> bool:
        try:
            return bool(self.client.ping())
        except redis.exceptions.RedisError:
            return False

async def access_log(request: Request, call_next):
    # ใช้ X-Request-ID จาก Client ถ้ามี ไม่งั้นสร้างใหม่ เพื่อไล่ Log ข้ามระบบได้

def limit_buy(request: Request, cache: CacheDep) -> None:

                            headers={"Retry-After": str(wait)})

def buy(product_id: int, cache: CacheDep):
    with stock_lock:
        product = PRODUCTS.get(product_id)
        if product is None:
            raise HTTPException(status_code=404, detail="ไม่พบสินค้านี้")
        if product["stock"] <= 0:

    return {"product_id": product_id, "remaining": remaining}

แนวคิด
  • Cache-aside: อ่าน Cache ก่อน ถ้าไม่เจอ (Miss) ให้ถามฐานข้อมูลแล้วเขียนผลลง Cache พร้อม TTL 30 วินาที ครั้งต่อไปจะเป็น Hit ผลจริงลดเวลาจากราว 319 ms เหลือราว 3.5 ms ต่อ Request ฐานข้อมูลจึงรับภาระน้อยลงมากในช่วงคนเข้าพร้อมกัน
  • Invalidation ทุกครั้งที่ข้อมูลเปลี่ยน: ทั้ง PATCH ราคาและการกดซื้อ (สต็อกเปลี่ยน) เรียก cache.delete() ทันที ผลจริงคือ redis-cli EXISTS product:1 ได้ 0 หลังลดราคา และการอ่านครั้งถัดไปเป็น Miss ที่ได้ราคาใหม่ 790 บาท TTL เป็นแค่ตาข่ายกันพลาดชั้นที่สอง ไม่ใช่วิธีหลักในการทำให้ข้อมูลถูกต้อง
  • Rate Limit แบบ Fixed Window: INCR ตัวนับ rl:buy:{ip} และตั้ง EXPIRE 60 วินาทีเมื่อเป็นครั้งแรก เกิน 5 ครั้งตอบ 429 พร้อม Retry-After ที่อ่านจาก TTL จริงของ Key การใส่ไว้ใน dependencies=[Depends(limit_buy)] ทำให้ตรวจก่อนเข้า Handler Request ที่เกินโควตาจึงไม่แตะสต็อกเลย
  • Graceful Degradation: คลาส Cache จับ RedisError ทุกจุด อ่าน Cache ไม่ได้ให้ถือเป็น Miss เขียนไม่ได้ก็ข้าม และ Rate Limit เลือกแบบ Fail-open (ยอมให้ผ่าน) เพราะการหยุดขายทั้งระบบเสียหายกว่าการไม่มี Rate Limit ชั่วคราว ระบบที่ต้องการความปลอดภัยสูงกว่า เช่น หน้า Login อาจเลือก Fail-closed แทน การเลือกนี้ต้องคุยกับทีมและเขียนเหตุผลไว้
  • ตั้ง Timeout และ Retry ให้สั้น: redis-py 8 มีการ Retry พร้อม Backoff เป็นค่าเริ่มต้น ถ้าไม่ปรับ ทุก Request จะค้างหลายวินาทีเมื่อ Redis ล่ม socket_connect_timeout=0.5 คู่กับ Retry(NoBackoff(), 1) ทำให้ล้มเร็วและไปถามฐานข้อมูลแทนทันที ผลจริงคือเรียกสินค้าตอน Redis ล่มใช้เวลาราว 304 ms ซึ่งเกือบเท่ากับเวลา Query ล้วน ๆ
  • Structured Log ที่ไล่ได้: Log ทุกบรรทัดเป็น JSON ที่มี request_id, method, path, status และ duration_ms ระบบรวม Log อย่าง Loki หรือ Elasticsearch จึงค้นหาได้ทันที เช่น หา Request ที่ status เป็น 429 หรือช้ากว่า 200 ms และ Header x-request-id ที่ส่งกลับไปช่วยให้ทีม Support ไล่ปัญหาจากฝั่งลูกค้าได้
  • กัน Race Condition ของสต็อก: threading.Lock() กันไม่ให้สอง Request ใน Process เดียวกันตัดชิ้นสุดท้ายพร้อมกัน (FastAPI รัน Handler แบบ def ใน Thread Pool) แต่ Lock นี้ใช้ได้แค่ใน Process เดียว ถ้ารันหลาย Worker หรือหลายเครื่อง ต้องย้ายการตัดสต็อกไปทำแบบ Atomic ที่ฐานข้อมูลแทน (ดูไอเดียต่อยอดข้อ 1)
  • Test ที่ไม่ต้องพึ่ง Redis จริง: แยก get_cache() เป็น Dependency แล้วสลับเป็น fakeredis ผ่าน dependency_overrides ทำให้ Test รันได้ทุกที่ รวมถึงใน CI ส่วนกรณี Redis ล่มทดสอบด้วยการชี้ไปที่ Port ที่ไม่มีอะไรฟังอยู่ ซึ่งเหมือนของจริงกว่าการ Mock

  1. ย้ายสินค้าไปเก็บใน PostgreSQL 16 แล้วตัดสต็อกด้วย UPDATE products SET stock = stock - 1 WHERE id = :id AND stock > 0 เพียงคำสั่งเดียว แล้วดูจำนวนแถวที่ถูกแก้ ถ้าเป็น 0 แปลว่าของหมด วิธีนี้ถูกต้องแม้รันหลาย Worker และหลายเครื่อง จึงเลิกใช้ threading.Lock ได้
  2. เปลี่ยน Rate Limit เป็น Sliding Window ด้วย Sorted Set (ZADD, ZREMRANGEBYSCORE, ZCARD) รวมใน Pipeline เดียว เพื่อแก้ปัญหาของ Fixed Window ที่ยอมให้ยิงได้ 10 ครั้งในช่วงรอยต่อของสองหน้าต่างเวลา
  3. ป้องกัน Cache Stampede ตอน Cache ของสินค้ายอดนิยมหมดอายุพร้อมกันหลายพัน Request โดยใช้ Lock ใน Redis (SET lock:product:1 1 NX EX 5) ให้มีแค่ Request เดียวไปถามฐานข้อมูล และสุ่มบวกลบ TTL เล็กน้อย (Jitter) ไม่ให้ทุก Key หมดอายุพร้อมกัน
  4. เพิ่ม Endpoint /metrics ที่นับจำนวน Cache Hit, Cache Miss และ Request ที่โดน 429 แล้วลองต่อกับ Prometheus และ Grafana ตามแนวคิดที่ 9 เพื่อดูอัตรา Hit และ p95 ของ duration_ms ระหว่างทดสอบโหลด
  5. เขียนสคริปต์ทดสอบโหลดด้วย Locust หรือ k6 ยิง 500 Request พร้อมกันไปที่ /products/1 แล้วเปรียบเทียบเวลาตอบเมื่อเปิดและปิด Cache บันทึกผลลง README เป็นหลักฐานใน Portfolio
