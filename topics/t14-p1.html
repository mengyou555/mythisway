14.1Learning Roadmap

ภาพรวมเส้นทาง

SQL (Structured Query Language) คือภาษาที่ใช้สร้าง จัดเก็บ แก้ไข และวิเคราะห์ข้อมูลใน ฐานข้อมูลเชิงสัมพันธ์ (Relational Database) เกือบทุกระบบที่คุณใช้ในชีวิตประจำวันเก็บข้อมูลด้วยวิธีนี้ ทั้งแอปธนาคาร ร้านค้าออนไลน์ ระบบจองตั๋ว ระบบโรงพยาบาล และแอปบนมือถือ เมื่อกดดูประวัติการสั่งซื้อในแอป เบื้องหลังคือคำสั่ง SQL ที่ดึงข้อมูลจากตาราง orders มาแสดง

หัวข้อนี้อยู่ลำดับที่ 5 ของเส้นทางที่แนะนำ ต่อจาก Linux, Git และ GitHub, Python และ Prompt Engineering เหตุผลคือ ข้อมูลคือหัวใจของทุกระบบ และเมื่อคุณเขียน Python เป็นแล้ว ก็ใช้ Python เชื่อมต่อกับ Database ได้ทันที SQL เป็นทักษะหลัก (Core) ของสาย Backend, Full-stack JavaScript และ Data Scientist และเป็นทักษะที่ควรรู้ของสาย AI Engineer, Cyber Security, Android และ Product Builder

เส้นทางนี้แบ่งเป็น 13 ขั้นใน 3 ระดับ เริ่มจาก SQLite 3.45 ซึ่งติดตั้งคำสั่งเดียวและเก็บฐานข้อมูลทั้งก้อนไว้ในไฟล์เดียว ไม่ต้องตั้งค่า Server จึงเหมาะกับการฝึกช่วงแรก จากนั้นย้ายไปใช้ PostgreSQL 16 ซึ่งเป็นฐานข้อมูลระดับ Production ที่บริษัทจำนวนมากใช้จริง ทุกขั้นใช้ฐานข้อมูลตัวอย่างชุดเดียวกัน คือร้านค้าออนไลน์เล็กๆ ที่มีลูกค้า หมวดสินค้า สินค้า คำสั่งซื้อ และรายการสินค้าในคำสั่งซื้อ คุณจึงไม่ต้องเรียนรู้ข้อมูลใหม่ทุกบท และเห็นได้ชัดว่าแต่ละคำสั่งให้คำตอบทางธุรกิจอะไร

เปรียบเทียบ

ฐานข้อมูลเหมือนห้องเก็บเอกสารของบริษัทที่มีตู้หลายใบ ตู้แต่ละใบคือ ตาราง (Table) เช่น ตู้ลูกค้า ตู้สินค้า ตู้คำสั่งซื้อ แฟ้มแต่ละแฟ้มในตู้คือ แถว (Row) และช่องที่ต้องกรอกในแฟ้ม เช่น ชื่อ อีเมล เมือง คือ คอลัมน์ (Column) ส่วน SQL คือภาษาที่ใช้สั่งพนักงานห้องเอกสาร เช่น "ช่วยหาแฟ้มลูกค้าทุกคนที่อยู่เชียงใหม่ แล้วเรียงตามวันที่สมัคร" พนักงานจะไปค้นให้เอง คุณไม่ต้องบอกว่าต้องเปิดตู้ไหนก่อนหลัง

SQL และฐานข้อมูลเชิงสัมพันธ์คืออะไร

ก่อนเริ่มพิมพ์คำสั่ง ให้รู้จักคำศัพท์ต่อไปนี้ เพราะจะเจอทุกขั้นของหัวข้อนี้ และเป็นคำถามสัมภาษณ์งานระดับ Junior ที่พบบ่อย

คำศัพท์ความหมายตัวอย่างในร้านค้าตัวอย่างของหัวข้อนี้
Databaseชุดข้อมูลที่จัดเก็บอย่างเป็นระบบ เพื่อให้ค้นหา แก้ไข และป้องกันข้อมูลผิดพลาดได้ไฟล์ shop.db ของ SQLite และฐานข้อมูลชื่อ shop ใน PostgreSQL
DBMS / RDBMSโปรแกรมที่จัดการฐานข้อมูล (Database Management System) ถ้าเก็บข้อมูลเป็นตารางที่มีความสัมพันธ์กัน เรียกว่า RDBMSSQLite 3.45.1 และ PostgreSQL 16 รายชื่ออื่นที่จะได้ยินบ่อยคือ MySQL, MariaDB, Microsoft SQL Server และ Oracle Database
Tableที่เก็บข้อมูลเรื่องเดียวกัน มีโครงสร้างคอลัมน์ตายตัวcustomers, categories, products, orders, order_items
Row (Record)ข้อมูลหนึ่งรายการในตารางลูกค้าหนึ่งคน เช่น Somchai Jaidee ที่สมัครวันที่ 2025-01-15
Column (Field)คุณสมบัติหนึ่งอย่างของข้อมูล มีชื่อและชนิดข้อมูล (Data Type) กำกับemail ชนิด TEXT และ price ชนิด NUMERIC(10,2)
Primary Key (PK)คอลัมน์ที่ใช้ระบุแต่ละแถวได้ไม่ซ้ำกัน ห้ามเป็นค่าว่างcustomers.customer_id และ PK แบบหลายคอลัมน์ (order_id, product_id) ของ order_items
Foreign Key (FK)คอลัมน์ที่ชี้ไปยัง Primary Key ของอีกตาราง ใช้สร้างความสัมพันธ์และกันข้อมูลกำพร้าorders.customer_id ชี้ไปที่ customers.customer_id
Schemaโครงสร้างของฐานข้อมูลทั้งหมด คือมีตารางอะไร คอลัมน์อะไร และกฎอะไรบ้าง ใน PostgreSQL ยังหมายถึงกลุ่มของตารางด้วย เช่น Schema publicไฟล์ shop_schema_sqlite.sql และ shop_schema_pg.sql
Queryคำสั่ง SQL ที่ส่งให้ฐานข้อมูลทำงาน มักหมายถึงคำสั่งที่ถามข้อมูลด้วย SELECTSELECT name FROM customers WHERE city = 'Bangkok';
DialectSQL มีมาตรฐานกลาง (ISO/ANSI SQL) แต่ละ RDBMS เพิ่มความสามารถและไวยากรณ์ของตัวเอง เรียกว่า DialectPostgreSQL มี ILIKE และ date_trunc() ส่วน SQLite ใช้ strftime() แทน

คำสั่ง SQL แบ่งเป็น 5 กลุ่มตามหน้าที่ การรู้กลุ่มช่วยให้จำได้ว่าคำสั่งไหนเปลี่ยนโครงสร้าง คำสั่งไหนเปลี่ยนข้อมูล และคำสั่งไหนอันตรายต้องระวัง

เหตุผลที่ควรเรียน SQL อย่างจริงจังมีดังนี้

  • อายุยาวและเปลี่ยนช้า SQL มีมาตั้งแต่ทศวรรษ 1970 และยังเป็นภาษามาตรฐานของงานข้อมูล สิ่งที่เรียนวันนี้ใช้ได้อีกหลายปี ต่างจาก Framework ที่เปลี่ยนบ่อย
  • ใช้ได้แทบทุกสายงาน Backend ใช้เก็บข้อมูลของแอป Data Scientist ใช้ดึงข้อมูลมาวิเคราะห์ Cyber Security ต้องเข้าใจ SQL Injection และ Android ใช้ SQLite เก็บข้อมูลในเครื่อง
  • ตอบคำถามธุรกิจได้เอง คำถามอย่าง "เดือนไหนขายดีที่สุด" หรือ "ลูกค้าคนไหนไม่ได้กลับมาซื้อซ้ำ" ตอบได้ด้วย Query เดียว ไม่ต้องรอให้คนอื่นทำรายงานให้
  • เป็นคำถามสัมภาษณ์ที่เจอบ่อย ตำแหน่ง Backend, Data Analyst และ Data Engineer มักมีแบบทดสอบเขียน SQL เช่น JOIN, GROUP BY และ Window Functions
  • ทำงานกับ AI ได้ดีขึ้น ผู้ช่วย AI เขียน SQL ให้ได้เร็ว แต่คนที่อ่าน SQL เป็นเท่านั้นที่ตรวจได้ว่า Query ที่ได้ถูกต้อง ปลอดภัย และไม่ช้าเกินไป ซึ่งต่อยอดจากสิ่งที่เรียนใน
หมายเหตุ

ยังมีฐานข้อมูลอีกกลุ่มที่เรียกว่า NoSQL เช่น MongoDB (เก็บข้อมูลเป็นเอกสาร JSON) และ Redis (เก็บแบบ Key-Value ในหน่วยความจำ) ระบบเหล่านี้เหมาะกับงานบางแบบ แต่ฐานข้อมูลเชิงสัมพันธ์ยังเป็นตัวเลือกแรกของระบบส่วนใหญ่ และ PostgreSQL เองก็เก็บข้อมูล JSON ได้ด้วยชนิด JSONB หัวข้อนี้จึงเน้นฐานข้อมูลเชิงสัมพันธ์ให้แน่นก่อน

Prerequisites: ต้องรู้อะไรมาก่อน

หัวข้อนี้ ไม่บังคับว่าต้องเรียนหัวข้อใดมาก่อน แต่ถ้าเรียนตามเส้นทางที่แนะนำ คุณจะผ่านหัวข้อเหล่านี้มาแล้ว และจะใช้ความรู้จากหัวข้อเหล่านั้นตลอดทาง

  • ใช้ Terminal ของ Ubuntu 24.04 ใน WSL2 ได้คล่อง ทั้ง cd, ls, mkdir, การติดตั้งโปรแกรมด้วย sudo apt install, การ Redirect ด้วย < และ > และการใช้ sudo ซึ่งจำเป็นตั้งแต่ Step 1 และสำคัญมากใน Step 7 ตอนเริ่ม Service ของ PostgreSQL
  • สร้าง Repository, Commit และ Push ได้ เพราะคุณจะเก็บไฟล์ .sql ทุกขั้นไว้ใน Git และ Push Mini Project ขึ้น GitHub
  • เขียนฟังก์ชัน ใช้ list, dict, tuple และสร้าง venv ด้วย python3 -m venv .venv ได้ ซึ่งจำเป็นใน Step 13 ตอนเชื่อม Python กับฐานข้อมูล
  • (ไม่บังคับ) ช่วยให้ใช้ผู้ช่วย AI อธิบาย Error หรือแนะนำ Query ได้อย่างมีประสิทธิภาพ โดยยังตรวจผลลัพธ์เองได้
  • ใช้คณิตศาสตร์ระดับมัธยมได้ เช่น ผลรวม ค่าเฉลี่ย ร้อยละ และการเปรียบเทียบมากกว่าน้อยกว่า
  • อ่านข้อความ Error ภาษาอังกฤษสั้นๆ ได้ เช่น UNIQUE constraint failed หรือ relation "orders" does not exist เพราะฐานข้อมูลบอกสาเหตุของปัญหาผ่านข้อความเหล่านี้เสมอ

SQL เป็นพื้นฐานของหัวข้อต่อไปนี้ เมื่อเรียนจบหัวข้อนี้จะเรียนต่อได้ราบรื่นขึ้น

  • เก็บข้อมูลของ API ใน PostgreSQL ใช้ Transaction และ Index ที่เรียนใน Step 11–12
  • และ เขียน API ที่อ่านและเขียนฐานข้อมูลด้วย Parameterized Query แบบเดียวกับ Step 13
  • ดึงข้อมูลด้วย SQL ก่อนวิเคราะห์ต่อด้วย pandas และใช้ Window Functions จาก Step 10
  • เก็บประวัติการสนทนา เอกสาร และผลลัพธ์ของ LLM ลงฐานข้อมูล
  • เข้าใจกลไกของ SQL Injection ทั้งฝั่งโจมตีในห้องทดลองและฝั่งป้องกัน
  • แอป Android ใช้ SQLite ผ่านไลบรารี Room เก็บข้อมูลไว้ในเครื่อง

SQLite กับ PostgreSQL: ทำไมเรียนทั้งสองตัว

หัวข้อนี้ใช้ฐานข้อมูลสองตัว ช่วงแรก (Step 1–6) ใช้ SQLite เพราะไม่ต้องตั้งค่าอะไรเลย ฐานข้อมูลทั้งหมดอยู่ในไฟล์เดียว พังก็ลบไฟล์แล้วสร้างใหม่ได้ในไม่กี่วินาที ช่วงหลัง (Step 7–13) ใช้ PostgreSQL 16 ซึ่งทำงานเป็น Server แบบที่บริษัทใช้จริง มีผู้ใช้ สิทธิ์ การทำงานพร้อมกันหลายคน และเครื่องมือสำรองข้อมูล SQL พื้นฐานประมาณ 80% เขียนเหมือนกันทั้งสองตัว ส่วนที่ต่างกันจะสอนชัดเจนใน Step 7

  • ทำไมไม่เก็บข้อมูลใน Excel หรือไฟล์ CSV: ฐานข้อมูลบังคับกฎความถูกต้องได้ (เช่น อีเมลห้ามซ้ำ) หลายโปรแกรมใช้พร้อมกันได้ ค้นหาข้อมูลหลายล้านแถวได้เร็วด้วย Index และเชื่อมข้อมูลหลายตารางเข้าหากันได้
  • คำศัพท์หลัก: Database, RDBMS, Table, Row, Column, Primary Key, Foreign Key และ Schema พร้อมตัวอย่างจากร้านค้าตัวอย่าง
  • SQL เป็นภาษาแบบ Declarative คือบอกว่า "อยากได้อะไร" แล้วฐานข้อมูลคิดเองว่าจะไปหาอย่างไร ต่างจาก Python ที่ต้องเขียนขั้นตอนเอง และกลุ่มคำสั่ง DQL, DDL, DML, TCL, DCL

STEP 2

SELECT: กรอง เรียง จำกัดผล และเข้าใจ NULL

2 วัน · 3–4 ชม.
หัวข้อย่อย
  • WHERE กับตัวเปรียบเทียบ =, <> (หรือ !=), <, >, <=, >= และการเปรียบเทียบข้อความกับตัวเลข
  • รวมเงื่อนไขด้วย AND, OR, NOT และใส่วงเล็บกำกับลำดับ เพราะ AND ทำก่อน OR เสมอ
  • IN (...) แทน OR หลายตัว และ BETWEEN a AND b ซึ่งรวมค่าทั้งสองขอบ เช่น ราคาระหว่าง 500 ถึง 3000 บาท
  • LIKE กับ Wildcard % (กี่ตัวอักษรก็ได้) และ _ (หนึ่งตัวอักษร) ข้อควรรู้: LIKE ของ SQLite ไม่สนตัวพิมพ์เล็กใหญ่สำหรับอักษรอังกฤษ แต่ PostgreSQL สนใจ และมี ILIKE ไว้ค้นหาแบบไม่สนตัวพิมพ์
  • ORDER BY หลายคอลัมน์ พร้อม ASC และ DESC และตำแหน่งของ NULL ในการเรียง (NULLS FIRST / NULLS LAST)
  • LIMIT และ OFFSET สำหรับแบ่งหน้า (Pagination) สูตรหน้าที่ n คือ LIMIT ขนาดหน้า OFFSET (n - 1) * ขนาดหน้า และ DISTINCT สำหรับตัดค่าซ้ำ
  • NULL คือ "ไม่ทราบค่า" ไม่ใช่ศูนย์หรือข้อความว่าง การเปรียบเทียบใดๆ กับ NULL ได้ผลเป็น NULL (Three-valued Logic) จึงต้องใช้ IS NULL และ IS NOT NULL ห้ามใช้ = NULL
  • COALESCE(ค่า, ค่าสำรอง) สำหรับแทน NULL ด้วยค่าที่อ่านง่าย และ NULLIF(a, b) สำหรับเปลี่ยนค่าที่ไม่ต้องการให้เป็น NULL เช่น กันการหารด้วยศูนย์
  • ลำดับการทำงานจริงของ Query (Logical Order): FROM → WHERE → SELECT → ORDER BY → LIMIT ซึ่งอธิบายได้ว่าทำไมใช้ Alias จาก SELECT ใน WHERE ไม่ได้
ทำไมต้องเรียน
งานจริงแทบไม่เคยต้องการ "ข้อมูลทั้งหมด" แต่ต้องการ "ข้อมูลบางส่วนที่ตรงเงื่อนไข เรียงตามลำดับที่เหมาะสม" เช่น หน้าแสดงสินค้าที่แบ่งหน้าละ 20 ชิ้น หรือรายชื่อลูกค้าที่ยังไม่ยืนยันอีเมล ส่วน NULL เป็นต้นเหตุอันดับต้นของรายงานที่ตัวเลขผิดแบบเงียบๆ เช่น ใช้ WHERE city <> 'Bangkok' แล้วลูกค้าที่ไม่ได้ระบุเมืองหายไปจากผลลัพธ์โดยไม่มี Error ใดๆ
ลงมือทำ
  • หาสินค้าที่ราคาระหว่าง 500 ถึง 3000 บาท เรียงจากถูกไปแพง
  • หาสินค้าที่ชื่อมีคำว่า phone ทั้งแบบตัวพิมพ์เล็กและใหญ่ แล้วสังเกตผลของ LIKE ใน SQLite
  • แบ่งหน้ารายชื่อลูกค้า หน้าละ 3 คน แล้วแสดงหน้าที่ 2 และหน้าที่ 3
  • เปรียบเทียบจำนวนแถวของ WHERE city <> 'Bangkok' กับ WHERE city <> 'Bangkok' OR city IS NULL แล้วอธิบายว่าทำไมต่างกัน
ใช้เวลา
3–4 ชั่วโมง ใช้เวลากับเรื่อง NULL อย่างน้อย 1 ชั่วโมง เพราะเป็นเรื่องที่คนทำงานมาหลายปีก็ยังพลาด

       COALESCE(city, 'ไม่ระบุ') AS city,   -- ถ้า city เป็น NULL ให้แสดงคำว่า ไม่ระบุ แทน
       joined_on
FROM customers
WHERE city IN ('Bangkok', 'Phuket')
   OR city IS NULL                          -- NULL ต้องใช้ IS NULL ห้ามใช้ = NULL
ORDER BY joined_on;

STEP 3

สร้างตารางด้วย Data Types และ Constraints

2 วัน · 3–4 ชม.
หัวข้อย่อย
  • รูปแบบคำสั่ง CREATE TABLE, CREATE TABLE IF NOT EXISTS, DROP TABLE IF EXISTS และหลักการตั้งชื่อแบบ snake_case ตัวพิมพ์เล็กทั้งหมด ชื่อตารางเป็นพหูพจน์ เช่น customers
  • ชนิดข้อมูลใน SQLite: INTEGER, REAL, TEXT, BLOB และ NUMERIC รวมถึงแนวคิด Type Affinity ที่ยอมให้ใส่ข้อความลงคอลัมน์ตัวเลขได้ และตาราง STRICT (SQLite 3.37 ขึ้นไป) ที่บังคับชนิดข้อมูลจริง
  • ชนิดข้อมูลที่จะใช้ใน PostgreSQL (ดูไว้ก่อน): INTEGER, BIGINT, NUMERIC(10,2) สำหรับเงิน, TEXT และ VARCHAR(n), BOOLEAN, DATE, TIMESTAMPTZ และเหตุผลที่ห้ามเก็บเงินเป็น REAL หรือ FLOAT ในระบบจริง
  • PRIMARY KEY แบบคอลัมน์เดียวและแบบหลายคอลัมน์ (Composite Key) เช่น PRIMARY KEY (order_id, product_id)
  • NOT NULL, UNIQUE, DEFAULT และ CHECK เช่น CHECK (price >= 0) และ CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled'))
  • FOREIGN KEY ด้วย REFERENCES และพฤติกรรมเมื่อลบแถวแม่: ON DELETE RESTRICT, ON DELETE CASCADE และ ON DELETE SET NULL พร้อมข้อควรจำว่า SQLite ต้องสั่ง PRAGMA foreign_keys = ON; ทุกครั้งที่เชื่อมต่อ
  • ALTER TABLE ... ADD COLUMN และ ALTER TABLE ... RENAME COLUMN สำหรับแก้โครงสร้างโดยไม่ลบข้อมูล และข้อจำกัดของ SQLite ที่เพิ่ม Constraint ให้ตารางเดิมไม่ได้
  • อ่านข้อความ Error ของ Constraint: NOT NULL constraint failed, UNIQUE constraint failed, CHECK constraint failed และ FOREIGN KEY constraint failed
ทำไมต้องเรียน
Constraint คือด่านป้องกันชั้นสุดท้ายของความถูกต้องของข้อมูล โค้ดของแอปอาจมีบั๊ก มีหลายแอปเขียนฐานข้อมูลเดียวกัน หรือมีคนแก้ข้อมูลด้วยมือ แต่ Constraint ทำงานทุกครั้งไม่ว่าข้อมูลมาจากไหน ข้อมูลที่ผิดตั้งแต่ต้น เช่น ราคาติดลบ อีเมลซ้ำ หรือคำสั่งซื้อที่ชี้ไปหาลูกค้าที่ไม่มีอยู่จริง แก้ทีหลังยากและแพงกว่าการป้องกันตั้งแต่ออกแบบตารางมาก
ลงมือทำ
  • อ่านไฟล์ shop_schema_sqlite.sql ทีละบรรทัด แล้วเขียนอธิบายลง Learning Journal ว่าแต่ละ Constraint ป้องกันข้อมูลผิดแบบไหน
  • สร้างตาราง reviews ใหม่ ที่มีคะแนน 1–5 (CHECK), ลูกค้าหนึ่งคนรีวิวสินค้าเดียวได้ครั้งเดียว (UNIQUE สองคอลัมน์) และวันที่รีวิวมีค่าเริ่มต้น (DEFAULT CURRENT_TIMESTAMP)
  • ลองใส่ข้อมูลที่ผิดกฎทุกแบบ แล้วจดข้อความ Error ที่ได้
  • ปิด PRAGMA foreign_keys แล้วลองใส่คำสั่งซื้อของลูกค้าที่ไม่มีอยู่ เพื่อดูว่าทำไมต้องเปิดไว้เสมอ

STEP 4

INSERT, UPDATE, DELETE และ Transaction เบื้องต้น

1–2 วัน · 2–3 ชม.
หัวข้อย่อย
  • INSERT INTO ตาราง (คอลัมน์, ...) VALUES (...) ทั้งแบบแถวเดียวและหลายแถวในคำสั่งเดียว และเหตุผลที่ต้องระบุชื่อคอลัมน์เสมอ
  • INSERT INTO ... SELECT ... สำหรับคัดลอกข้อมูลจาก Query ลงตารางอื่น เช่น สร้างตารางสำรองก่อนแก้ข้อมูล
  • UPDATE ... SET ... WHERE ... รวมถึงการคำนวณจากค่าเดิม เช่น SET stock = stock - 1 และการแก้หลายคอลัมน์ในคำสั่งเดียว
  • DELETE FROM ... WHERE ... และกฎทอง: รัน SELECT ด้วย WHERE เดียวกันก่อนทุกครั้ง เพื่อดูว่าจะกระทบกี่แถว
  • RETURNING (SQLite 3.35 ขึ้นไปและ PostgreSQL) สำหรับดูค่าที่เพิ่งเพิ่มหรือแก้ เช่น INSERT ... RETURNING customer_id และ changes() ของ SQLite สำหรับดูจำนวนแถวที่ถูกแก้
  • UPSERT ด้วย INSERT ... ON CONFLICT (email) DO UPDATE SET ... ใช้ได้ทั้ง SQLite และ PostgreSQL สำหรับ "ถ้ามีแล้วให้แก้ ถ้ายังไม่มีให้เพิ่ม"
  • BEGIN, COMMIT และ ROLLBACK ในฐานะ "ตาข่ายนิรภัย" ก่อนแก้ข้อมูลจำนวนมาก (Transaction แบบเต็มเรียนใน Step 12)
  • Foreign Key ป้องกันการลบลูกค้าที่ยังมีคำสั่งซื้ออยู่ และวิธีจัดการที่ถูกต้อง เช่น เปลี่ยนสถานะแทนการลบ (Soft Delete)
ทำไมต้องเรียน
คำสั่งในขั้นนี้เปลี่ยนข้อมูลจริง และฐานข้อมูลไม่มีปุ่ม Undo UPDATE หรือ DELETE ที่ลืม WHERE จะกระทบทุกแถวในตารางทันที ซึ่งเป็นความผิดพลาดที่ทำให้หลายบริษัทต้องกู้ข้อมูลจาก Backup การฝึกนิสัย "SELECT ก่อน แล้วค่อยแก้ภายใน Transaction" ตั้งแต่วันแรกจะป้องกันความเสียหายแบบนี้ได้ตลอดอาชีพ
ลงมือทำ
  • เพิ่มลูกค้าใหม่ชื่อ Kanya Srisuk ด้วย INSERT ... RETURNING customer_id
  • เพิ่มคำสั่งซื้อให้ลูกค้าคนนี้ 1 รายการ พร้อม order_items 2 ชิ้น และลด stock ของสินค้าทั้งสองชิ้นให้ถูกต้อง
  • ทดลองลดราคาภายใน BEGIN แล้ว ROLLBACK ตามตัวอย่างด้านล่าง
  • ลองลบลูกค้า Somchai Jaidee แล้วอ่าน Error ที่ได้ จากนั้นรีเซ็ตฐานข้อมูลกลับเป็นค่าเริ่มต้น
ใช้เวลา
2–3 ชั่วโมง ทำให้เป็นนิสัยว่าทุกครั้งก่อน UPDATE และ DELETE ต้องมี SELECT นำก่อน

-- เปลี่ยนใจ ยกเลิกทุกอย่างที่ทำหลัง BEGIN
ROLLBACK;
-- ราคากลับเป็นค่าเดิม

STEP 5

Aggregate, GROUP BY, HAVING, CASE และฟังก์ชันข้อความกับวันที่

2 วัน · 3–4 ชม.
หัวข้อย่อย
  • Aggregate Functions: COUNT(*), COUNT(คอลัมน์) (ไม่นับ NULL), COUNT(DISTINCT คอลัมน์), SUM, AVG, MIN, MAX และ ROUND
  • GROUP BY หนึ่งคอลัมน์และหลายคอลัมน์ พร้อมกฎสำคัญ: ทุกคอลัมน์ใน SELECT ที่ไม่ได้อยู่ใน Aggregate ต้องอยู่ใน GROUP BY (SQLite ยอมให้ผ่านแต่อาจได้ค่าที่ไม่แน่นอน ส่วน PostgreSQL จะแจ้ง Error must appear in the GROUP BY clause)
  • HAVING กรองหลังจัดกลุ่ม ต่างจาก WHERE ที่กรองก่อนจัดกลุ่ม และลำดับการทำงาน FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
  • CASE WHEN ... THEN ... ELSE ... END สำหรับจัดกลุ่มตามช่วงค่า เช่น ช่วงราคา และ Conditional Aggregation เช่น SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END)
  • ฟังก์ชันวันที่ของ SQLite: date(), strftime('%Y-%m', order_date), julianday() และการเปรียบเทียบวันที่ที่เก็บเป็นข้อความรูปแบบ ISO 'YYYY-MM-DD'
  • ฟังก์ชันข้อความ: upper(), lower(), length(), substr(), replace(), trim(), instr() และการต่อข้อความด้วย ||
  • กับดักทศนิยม: ใน SQLite 5 / 2 ได้ 2 เพราะเป็นการหารจำนวนเต็ม ต้องเขียน 5 * 1.0 / 2 หรือ CAST ก่อน และ PostgreSQL ก็หารจำนวนเต็มแบบเดียวกัน
  • อ่านโจทย์ธุรกิจแล้วแปลงเป็น Query: "ยอดขายรายเดือน", "จำนวนสินค้าในแต่ละหมวด", "อัตราการยกเลิกคำสั่งซื้อ"
ทำไมต้องเรียน
รายงานเกือบทุกฉบับในบริษัท ทั้ง Dashboard ยอดขาย สรุปผลรายเดือน และ KPI ของทีม สร้างจาก GROUP BY คนที่เขียน Aggregate ได้แม่นยำจะตอบคำถามของผู้บริหารได้เองภายในไม่กี่นาที ส่วน CASE ทำให้แปลงข้อมูลดิบเป็นหมวดหมู่ที่คนอ่านเข้าใจได้ในขั้นเดียว ขั้นนี้ยังเป็นพื้นฐานโดยตรงของ Window Functions ใน Step 10
ลงมือทำ
  • นับจำนวนคำสั่งซื้อแยกตามสถานะ แล้วเรียงจากมากไปน้อย
  • หายอดขายรายเดือนตามตัวอย่างด้านล่าง แล้วแก้ให้แสดงเฉพาะเดือนที่มียอดขายเกิน 20,000 บาทด้วย HAVING
  • ใช้ CASE แบ่งสินค้าตามช่วงราคา แล้วนับจำนวนและหาค่าเฉลี่ยของแต่ละช่วง
  • หาอัตราการยกเลิกคำสั่งซื้อเป็นร้อยละ โดยระวังการหารจำนวนเต็ม
ใช้เวลา

SELECT strftime('%Y-%m', o.order_date)        AS month,
       COUNT(DISTINCT o.order_id)            AS orders,
       SUM(oi.quantity * oi.unit_price)      AS revenue
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.order_id
WHERE o.status <> 'cancelled'
GROUP BY month
ORDER BY month;

         WHEN price < 1000  THEN '1) under 1,000'
         WHEN price < 10000 THEN '2) 1,000-9,999'
         ELSE                    '3) 10,000+'
       END                AS price_band,
       COUNT(*)           AS products,
       SUM(stock)         AS units_in_stock,
       ROUND(AVG(price))  AS avg_price
FROM products
WHERE is_active = 1
GROUP BY price_band
HAVING COUNT(*) >= 3
ORDER BY price_band;

STEP 6

JOIN ทุกแบบและ Set Operations

3 วัน · 4–6 ชม.
หัวข้อย่อย
  • ทำไมต้องแยกข้อมูลเป็นหลายตาราง แล้วนำกลับมารวมกันด้วยคีย์ และการตั้งชื่อย่อตาราง (Table Alias) เช่น customers AS c
  • INNER JOIN ... ON ... เอาเฉพาะแถวที่จับคู่ได้ทั้งสองฝั่ง และการ JOIN ต่อกันหลายตาราง เช่น orders → order_items → products → categories
  • LEFT JOIN เอาทุกแถวจากตารางซ้าย และรูปแบบ Anti Join LEFT JOIN ... WHERE ขวา.คีย์ IS NULL สำหรับหา "สิ่งที่ไม่มีคู่" เช่น ลูกค้าที่ไม่เคยสั่งซื้อ
  • RIGHT JOIN และ FULL OUTER JOIN (SQLite รองรับตั้งแต่ 3.39 และ PostgreSQL รองรับมานาน) และเหตุผลที่ทีมส่วนใหญ่เขียน LEFT JOIN แทน RIGHT JOIN เพื่อให้อ่านง่าย
  • Self Join: JOIN ตารางเดียวกันสองครั้ง เช่น categories AS child กับ categories AS parent เพื่อแสดงหมวดย่อยคู่กับหมวดแม่
  • CROSS JOIN จับคู่ทุกแถว (8 ลูกค้า × 14 คำสั่งซื้อ = 112 แถว) ใช้สร้างตารางทุกคู่ เช่น ทุกหมวดคูณทุกเดือน และอันตรายของการลืมเงื่อนไข ON
  • กับดัก: เงื่อนไขของตารางขวาใน LEFT JOIN ต้องอยู่ใน ON ไม่ใช่ WHERE มิฉะนั้นจะกลายเป็น INNER JOIN และปัญหาแถวเพิ่มขึ้น (Fan-out) เมื่อ SUM หลัง JOIN ตารางแบบหนึ่งต่อหลาย
  • Set Operations: UNION (ตัดแถวซ้ำ), UNION ALL (เก็บแถวซ้ำและเร็วกว่า), INTERSECT และ EXCEPT พร้อมกฎว่าจำนวนและชนิดคอลัมน์ของทั้งสอง Query ต้องตรงกัน
ทำไมต้องเรียน
ข้อมูลในระบบจริงกระจายอยู่หลายสิบหรือหลายร้อยตาราง แทบทุกคำถามที่มีประโยชน์ต้องใช้ JOIN เช่น "ลูกค้าคนไหนซื้อสินค้าหมวดหนังสือ" ต้องผ่าน 4 ตาราง ความผิดพลาดของ JOIN ไม่ค่อยทำให้เกิด Error แต่ทำให้ได้ตัวเลขผิด เช่น ยอดขายเพิ่มเป็นสองเท่าจาก Fan-out หรือลูกค้าหายไปจากรายงานเพราะใช้ INNER JOIN แทน LEFT JOIN JOIN จึงเป็นคำถามสัมภาษณ์ SQL ที่พบบ่อยที่สุด
ลงมือทำ
  • แสดงคำสั่งซื้อทุกรายการพร้อมชื่อลูกค้า ชื่อสินค้า และชื่อหมวด (JOIN 5 ตาราง)
  • หาลูกค้าที่ไม่เคยสั่งซื้อ และหมวดที่ไม่มีสินค้า ด้วย Anti Join
  • แสดงหมวดย่อยทุกหมวดคู่กับชื่อหมวดแม่ด้วย Self Join
  • ใช้ UNION รวมรายชื่อเมืองของลูกค้าที่สั่งซื้อในเดือนมกราคมกับเดือนมิถุนายน แล้วเปรียบเทียบกับ UNION ALL และ INTERSECT
ใช้เวลา
4–6 ชั่วโมง เป็นขั้นที่ควรใช้เวลามากที่สุดในระดับ Intermediate วาดแผนภาพทุกครั้งที่ไม่แน่ใจว่าผลจะมีกี่แถว

FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name
ORDER BY total_orders DESC, c.name;

ก่อนไปขั้นถัดไป คุณต้องทำสิ่งเหล่านี้ได้: (1) วาดแผนภาพและบอกจำนวนแถวที่จะได้จาก INNER, LEFT, FULL และ CROSS JOIN ระหว่าง customers กับ orders ก่อนรันจริง (2) เขียน JOIN 5 ตารางแสดงชื่อลูกค้า ชื่อสินค้า และชื่อหมวดของทุกรายการที่ขายได้ (3) หาลูกค้าที่ไม่เคยสั่งซื้อและสินค้าที่ไม่เคยขายได้ด้วย Anti Join (4) แสดงหมวดย่อยคู่กับหมวดแม่ด้วย Self Join (5) อธิบายความต่างของ UNION กับ UNION ALL และบอกได้ว่าเมื่อไรควรใช้แบบไหน

STEP 7

ย้ายสู่ PostgreSQL 16 และ psql

2 วัน · 3–4 ชม.
หัวข้อย่อย
  • สถาปัตยกรรม Client–Server: Server (postgres) ทำงานเป็น Service ฟังที่ Port 5432 ส่วน psql คือ Client ที่ส่งคำสั่งไปให้ และ Cluster ของ Ubuntu ชื่อ 16/main ที่เก็บ Config ไว้ที่ /etc/postgresql/16/main/
  • ติดตั้งด้วย sudo apt install -y postgresql, เริ่ม Service ด้วย sudo service postgresql start และตรวจด้วย sudo service postgresql status (ถ้าเปิด systemd ใน WSL ไว้ Service จะเริ่มเองเมื่อเปิด Ubuntu)
  • Role ของ PostgreSQL กับผู้ใช้ Linux: Role postgres คือ Superuser ที่ติดตั้งมาพร้อมกัน เข้าใช้ด้วย sudo -u postgres psql เฉพาะงานดูแลระบบ ส่วนงานประจำวันให้สร้าง Role ของตัวเองด้วย sudo -u postgres createuser --createdb "$USER" ซึ่งทำให้ล็อกอินได้โดยไม่ต้องใช้รหัสผ่านผ่านกลไก Peer Authentication
  • สร้างฐานข้อมูลด้วย createdb shop โหลดไฟล์ด้วย psql -d shop -v ON_ERROR_STOP=1 -f ไฟล์.sql และลบด้วย dropdb --if-exists shop
  • Meta-commands ของ psql: \l (รายชื่อฐานข้อมูล), \c (เปลี่ยนฐานข้อมูล), \dt (รายชื่อตาราง), \d products (โครงสร้างตาราง), \du (รายชื่อ Role), \x (แสดงผลแนวตั้ง), \timing (จับเวลา), \i (รันไฟล์), \? (ความช่วยเหลือ) และ \q (ออก)
  • ไฟล์ ~/.psqlrc สำหรับตั้งค่าให้แสดง NULL เป็นคำว่า NULL ซึ่งปกติ psql แสดงเป็นช่องว่าง
  • ความต่างของ SQLite กับ PostgreSQL ที่ต้องรู้: เลขอัตโนมัติ, Boolean, ชนิดวันที่, ฟังก์ชันวันที่และข้อความ, LIKE กับ ILIKE, ความเข้มงวดของชนิดข้อมูล และความเข้มงวดของ GROUP BY (ดูตารางด้านล่าง)
  • ฟังก์ชันวันที่ของ PostgreSQL: CURRENT_DATE, now(), date_trunc('month', ...), EXTRACT(YEAR FROM ...), to_char(..., 'YYYY-MM'), age(), การลบวันที่ได้จำนวนวัน และ INTERVAL '7 days'
  • อ่าน Error การเชื่อมต่อที่เจอบ่อย: Server ไม่ทำงาน, ไม่มี Role และไม่มี Database (ดูกล่องระวังด้านล่าง)

STEP 8

Subquery, CTE และ View

2 วัน · 3–4 ชม.
หัวข้อย่อย
  • Scalar Subquery: Query ที่คืนค่าเดียวแล้วนำไปเปรียบเทียบ เช่น สินค้าที่ราคาสูงกว่าค่าเฉลี่ย WHERE price > (SELECT AVG(price) FROM products)
  • Subquery กับ IN และ NOT IN พร้อมกับดักสำคัญ: ถ้า Subquery ของ NOT IN มีค่า NULL แม้แต่แถวเดียว ผลลัพธ์จะว่างทั้งหมด
  • EXISTS และ NOT EXISTS สำหรับถามว่า "มีแถวที่เกี่ยวข้องอยู่หรือไม่" ซึ่งปลอดภัยกับ NULL และมักเร็วกว่า NOT IN
  • Correlated Subquery: Subquery ที่อ้างถึงคอลัมน์ของ Query ด้านนอก ทำงานหนึ่งครั้งต่อแถว เช่น วันที่สั่งซื้อล่าสุดของลูกค้าแต่ละคน
  • Derived Table: Subquery ใน FROM ที่ต้องตั้งชื่อ Alias เสมอ
  • CTE (Common Table Expression) ด้วย WITH ชื่อ AS (...) แบ่ง Query ยาวเป็นขั้นตอนที่ตั้งชื่อได้ อ่านจากบนลงล่างได้เหมือนโค้ด Python และใช้หลาย CTE ต่อกันได้
  • CREATE VIEW, CREATE OR REPLACE VIEW และ DROP VIEW สำหรับเก็บ Query ที่ใช้บ่อยไว้เรียกเหมือนตาราง ใช้ซ่อนความซับซ้อนและจำกัดคอลัมน์ที่ผู้ใช้บางกลุ่มเห็นได้
  • Materialized View ของ PostgreSQL (CREATE MATERIALIZED VIEW และ REFRESH MATERIALIZED VIEW) ที่เก็บผลลัพธ์จริงไว้ ทำให้อ่านเร็วแต่ข้อมูลไม่สดจนกว่าจะ Refresh
ทำไมต้องเรียน
คำถามธุรกิจหลายข้อต้องคิดเป็นหลายขั้น เช่น "ลูกค้าที่ยอดซื้อสูงกว่าค่าเฉลี่ยของลูกค้าทั้งหมด" ต้องหาค่าเฉลี่ยก่อนแล้วจึงเปรียบเทียบ Subquery และ CTE ทำให้เขียนแบบนี้ได้ใน Query เดียว CTE ยังทำให้ Query ยาว 50 บรรทัดอ่านและแก้ไขได้ ซึ่งสำคัญมากเมื่อทำงานเป็นทีม ส่วน View เป็นเครื่องมือที่ทีมข้อมูลใช้สร้าง "ตารางสำเร็จรูป" ให้คนอื่นใช้ต่อโดยไม่ต้องเขียน JOIN ซ้ำทุกครั้ง
ลงมือทำ
  • หาสินค้าที่ราคาสูงกว่าค่าเฉลี่ยของสินค้าที่ยังเปิดขาย ด้วย Scalar Subquery
  • หาสินค้าที่ไม่เคยขายได้ ทั้งด้วย NOT EXISTS, NOT IN และ LEFT JOIN แล้วยืนยันว่าทั้งสามแบบได้ผลเหมือนกัน
  • เขียน CTE สองขั้น: ขั้นแรกหายอดซื้อรวมของลูกค้าแต่ละคน ขั้นที่สองเลือกเฉพาะคนที่ยอดสูงกว่าค่าเฉลี่ย
  • สร้าง View order_totals ตามตัวอย่าง แล้วใช้ View นั้นตอบคำถามอีก 2 ข้อ
ใช้เวลา
3–4 ชั่วโมง ให้ลองเขียนคำถามเดียวกันทั้งแบบ Subquery และแบบ CTE เพื่อเปรียบเทียบความอ่านง่าย
-- 1) Subquery แบบ NOT EXISTS: สินค้าที่ยังไม่เคยถูกสั่งซื้อเลย
SELECT p.product_id, p.name, p.stock
FROM products AS p
WHERE NOT EXISTS (
    SELECT 1 FROM order_items AS oi WHERE oi.product_id = p.product_id
)
ORDER BY p.product_id;

-- 2) View: เก็บ Query ยอดรวมของแต่ละคำสั่งซื้อไว้ใช้ซ้ำ
CREATE OR REPLACE VIEW order_totals AS
SELECT o.order_id, c.name AS customer, o.order_date, o.status,
       SUM(oi.quantity * oi.unit_price) AS total
FROM orders AS o
JOIN customers   AS c  ON c.customer_id = o.customer_id
JOIN order_items AS oi ON oi.order_id   = o.order_id
GROUP BY o.order_id, c.name, o.order_date, o.status;

-- 3) ใช้ View เหมือนตารางปกติ: ลูกค้าที่ใช้จ่ายเกิน 20,000 บาท
SELECT customer, COUNT(*) AS orders, SUM(total) AS spent
FROM order_totals
WHERE status <> 'cancelled'
GROUP BY customer
HAVING SUM(total) > 20000
ORDER BY spent DESC;

STEP 9

Data Modeling และ Normalization

2 วัน · 3–4 ชม.
หัวข้อย่อย
  • จากความต้องการทางธุรกิจสู่ตาราง: หา Entity (คำนามหลัก เช่น ลูกค้า สินค้า คำสั่งซื้อ), Attribute (คุณสมบัติ) และ Relationship (ความสัมพันธ์) จากประโยคที่เจ้าของร้านเล่า
  • Cardinality: หนึ่งต่อหนึ่ง (1:1), หนึ่งต่อหลาย (1:N) และหลายต่อหลาย (M:N) ซึ่งต้องแก้ด้วยตารางกลาง (Junction Table) เช่น order_items ที่เชื่อม orders กับ products
  • เขียน ER Diagram แบบข้อความ หรือด้วยไวยากรณ์ erDiagram ของ Mermaid ซึ่ง GitHub แสดงผลเป็นรูปให้ในไฟล์ Markdown
  • ความผิดปกติของข้อมูล (Anomalies) ในตารางแบบแบน: Update Anomaly (แก้ไม่ครบทุกแถว), Insert Anomaly (เพิ่มข้อมูลบางอย่างไม่ได้) และ Delete Anomaly (ลบแล้วข้อมูลอื่นหายไปด้วย)
  • 1NF: ทุกช่องเก็บค่าเดียว (Atomic) ไม่มีกลุ่มคอลัมน์ซ้ำอย่าง product1, product2, product3 และทุกแถวระบุได้ด้วย Primary Key
  • 2NF: ผ่าน 1NF และทุกคอลัมน์ขึ้นกับ Primary Key ทั้งชุด ไม่ใช่แค่บางส่วน เช่น ถ้า order_items มี product_name จะผิด 2NF เพราะชื่อสินค้าขึ้นกับ product_id อย่างเดียว
  • 3NF: ผ่าน 2NF และไม่มีคอลัมน์ที่ขึ้นกับคอลัมน์อื่นที่ไม่ใช่คีย์ (Transitive Dependency) เช่น ถ้า customers มีทั้ง city และ region โดยภาคขึ้นกับเมือง ควรแยกตาราง cities
  • Denormalization อย่างมีเหตุผล: เก็บ unit_price ซ้ำใน order_items เพราะต้องการราคา ณ วันที่ซื้อ, เก็บยอดรวมไว้ในตารางสรุปหรือ Materialized View เพื่อให้รายงานเร็ว และต้นทุนที่ตามมาคือต้องดูแลให้ข้อมูลตรงกัน
  • Natural Key กับ Surrogate Key: ใช้อีเมลเป็นคีย์ (Natural) หรือใช้เลขที่ระบบสร้าง (Surrogate) พร้อม UNIQUE บนอีเมล และเหตุผลที่ระบบส่วนใหญ่เลือกแบบหลัง
ทำไมต้องเรียน
ตารางที่ออกแบบผิดตั้งแต่ต้นจะทำให้ทุก Query หลังจากนั้นยากขึ้น ข้อมูลขัดแย้งกันเอง และแก้ไขภายหลังได้ยากมากเมื่อระบบมีข้อมูลจริงหลายล้านแถว การออกแบบ Schema เป็นทักษะที่แยกนักพัฒนาที่ "เขียน Query ได้" ออกจากคนที่ "สร้างระบบได้" และเป็นหัวใจของ Mini Project ในหัวข้อนี้ คำถามสัมภาษณ์ตำแหน่ง Backend มักให้ออกแบบตารางจากโจทย์สั้นๆ เช่น ระบบจองห้องประชุม

STEP 10

Window Functions และ Recursive CTE

2–3 วัน · 3–5 ชม.
หัวข้อย่อย
  • แนวคิดของ Window Function: คำนวณข้ามหลายแถวที่เกี่ยวข้องกัน โดย ไม่ยุบแถว แบบ GROUP BY รูปแบบคือ ฟังก์ชัน() OVER (PARTITION BY ... ORDER BY ... กรอบ)
  • จัดอันดับด้วย ROW_NUMBER(), RANK() และ DENSE_RANK() และความต่างเมื่อมีค่าเท่ากัน (Ties) เช่น 1, 2, 2, 4 กับ 1, 2, 2, 3
  • PARTITION BY สำหรับเริ่มนับใหม่ในแต่ละกลุ่ม และรูปแบบ "Top-N ต่อกลุ่ม" เช่น สินค้าขายดี 2 อันดับแรกของแต่ละหมวด ด้วย CTE + ROW_NUMBER() แล้วกรอง WHERE rn <= 2
  • ยอดสะสม (Running Total) ด้วย SUM(...) OVER (ORDER BY month) และสัดส่วนต่อยอดรวม ด้วย revenue / SUM(revenue) OVER ()
  • ค่าเฉลี่ยเคลื่อนที่ (Moving Average) ด้วยกรอบ ROWS BETWEEN 2 PRECEDING AND CURRENT ROW และความต่างของกรอบแบบ ROWS กับ RANGE
  • LAG() และ LEAD() สำหรับเทียบกับแถวก่อนหน้าหรือถัดไป เช่น ยอดขายเดือนนี้เทียบเดือนก่อน และอัตราการเติบโตเป็นร้อยละพร้อม NULLIF กันหารด้วยศูนย์
  • FIRST_VALUE(), NTILE(4) และข้อจำกัดที่ใช้ Window Function ใน WHERE ไม่ได้ เพราะคำนวณหลัง WHERE และ GROUP BY ต้องห่อด้วย CTE ก่อน
  • WITH RECURSIVE: ส่วนเริ่มต้น (Anchor) + UNION ALL + ส่วนเรียกซ้ำ (Recursive Member) และเงื่อนไขหยุด ใช้กับข้อมูลแบบต้นไม้ เช่น หมวดสินค้า ผังองค์กร และรายการวัตถุดิบ พร้อมวิธีกันวนไม่รู้จบด้วยคอลัมน์ depth
  • สร้างลำดับวันที่ด้วย generate_series() ของ PostgreSQL เพื่อเติมเดือนที่ไม่มียอดขายให้เป็น 0 ในรายงาน และข้อควรรู้ว่า SQLite รองรับ Window Functions ตั้งแต่ 3.25 และ WITH RECURSIVE เช่นกัน
ทำไมต้องเรียน
Window Functions คือเครื่องมือหลักของงานวิเคราะห์ข้อมูล คำถามอย่าง "ยอดขายสะสมถึงเดือนนี้", "เติบโตจากเดือนก่อนกี่เปอร์เซ็นต์" หรือ "สินค้าขายดี 3 อันดับแรกของแต่ละหมวด" ถ้าไม่มี Window Functions ต้องเขียน Subquery ซ้อนกันหลายชั้นหรือดึงข้อมูลไปคำนวณใน Python ทั้งที่ทำได้ใน Query เดียว และเป็นหัวข้อที่แบบทดสอบ SQL ของตำแหน่ง Data Analyst และ Data Scientist ถามแทบทุกครั้ง
ลงมือทำ
  • จัดอันดับสินค้าตามจำนวนชิ้นที่ขายได้ด้วย ROW_NUMBER, RANK และ DENSE_RANK พร้อมกัน แล้วอธิบายแถวที่ค่าไม่เท่ากัน
  • หาสินค้าขายดีอันดับ 1 ของแต่ละหมวดด้วย PARTITION BY
  • รันตัวอย่างยอดสะสมด้านล่าง แล้วเพิ่มคอลัมน์อัตราการเติบโตเป็นร้อยละและค่าเฉลี่ยเคลื่อนที่ 3 เดือน
  • รันตัวอย่าง Recursive CTE ด้านล่าง แล้วแก้ให้แสดงจำนวนสินค้าในแต่ละหมวดรวมหมวดลูกทั้งหมด

3–5 ชั่วโมง เป็นขั้นที่ต้องฝึกซ้ำหลายรอบ ให้เขียนคำถามเดียวกันทั้งแบบ GROUP BY และแบบ Window เพื่อเห็นความต่าง
-- ยอดขายรายเดือน + ยอดสะสม + ส่วนต่างจากเดือนก่อน
WITH monthly AS (
    SELECT date_trunc('month', o.order_date)::date AS month,
           SUM(oi.quantity * oi.unit_price)     AS revenue
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.order_id
    WHERE o.status <> 'cancelled'
    GROUP BY 1
)
SELECT month,
       revenue,
       SUM(revenue) OVER (ORDER BY month)            AS running_total,
       revenue - LAG(revenue) OVER (ORDER BY month)  AS diff_prev_month
FROM monthly
ORDER BY month;

-- แสดงต้นไม้หมวดสินค้าทุกระดับด้วย Recursive CTE
WITH RECURSIVE tree AS (
    -- ส่วนเริ่มต้น (Anchor): หมวดหลักที่ไม่มีหมวดแม่
    SELECT category_id, name, parent_id, name::text AS path, 1 AS depth
    FROM categories
    WHERE parent_id IS NULL
    UNION ALL
    -- ส่วนเรียกซ้ำ (Recursive): หาหมวดลูกของแถวที่ได้ในรอบก่อน
    SELECT c.category_id, c.name, c.parent_id,
           t.path || ' > ' || c.name, t.depth + 1
    FROM categories AS c
    JOIN tree AS t ON c.parent_id = t.category_id
)
SELECT category_id, depth, path
FROM tree
ORDER BY path;

STEP 11

Index, EXPLAIN และ Performance

2–3 วัน · 3–5 ชม.
หัวข้อย่อย
  • ฐานข้อมูลหาข้อมูลอย่างไรเมื่อไม่มี Index (อ่านทุกแถว: Full Table Scan หรือ Seq Scan) และ Index แบบ B-tree ทำงานอย่างไร (ข้อมูลที่เรียงไว้แล้วพร้อมตัวชี้ไปยังแถวจริง)
  • CREATE INDEX, CREATE UNIQUE INDEX, DROP INDEX และการตั้งชื่อแบบ idx_ตาราง_คอลัมน์ รวมถึงข้อเท็จจริงว่า Primary Key และ UNIQUE สร้าง Index ให้อัตโนมัติ แต่ PostgreSQL ไม่สร้าง Index ให้ Foreign Key
  • เลือกคอลัมน์ที่ควรทำ Index: คอลัมน์ใน WHERE, คีย์ที่ใช้ JOIN และคอลัมน์ใน ORDER BY ที่มีค่าหลากหลาย (Selectivity สูง)
  • Composite Index เช่น (customer_id, order_date) และกฎคอลัมน์ซ้ายสุด (Leftmost Prefix) ที่ทำให้ Index นี้ช่วย WHERE customer_id = 1 ได้ แต่ไม่ช่วย WHERE order_date = ... อย่างเดียว
  • Index เฉพาะของ PostgreSQL: Partial Index (WHERE status = 'pending'), Expression Index (lower(email)) และ Index Only Scan
  • อ่านแผนการทำงาน: EXPLAIN QUERY PLAN ของ SQLite (SCAN กับ SEARCH ... USING INDEX) และ EXPLAIN / EXPLAIN ANALYZE ของ PostgreSQL (Seq Scan, Index Scan, Bitmap Heap Scan, Nested Loop, Hash Join, cost, rows และ actual time)
  • สร้างข้อมูลทดสอบจำนวนมากด้วย generate_series() เพราะตารางเล็กๆ ฐานข้อมูลจะเลือก Seq Scan เสมอซึ่งเป็นเรื่องปกติ และสั่ง ANALYZE ให้สถิติเป็นปัจจุบัน
  • ต้นทุนของ Index: INSERT, UPDATE, DELETE ช้าลงและใช้พื้นที่ Disk เพิ่ม จึงไม่ควรทำ Index ทุกคอลัมน์
  • นิสัยที่ทำให้ Index ใช้ไม่ได้: ครอบคอลัมน์ด้วยฟังก์ชัน, LIKE '%คำ' ที่ขึ้นต้นด้วย Wildcard, การแปลงชนิดข้อมูลโดยไม่ตั้งใจ และปัญหา N+1 Query จากโค้ดแอปที่ส่ง Query ทีละแถว
ทำไมต้องเรียน
Query ที่ใช้เวลา 2 มิลลิวินาทีตอนมีข้อมูล 100 แถว อาจใช้เวลาหลายวินาทีเมื่อมีข้อมูล 10 ล้านแถว และทำให้ทั้งระบบช้าเมื่อมีผู้ใช้พร้อมกันหลายคน การอ่าน EXPLAIN เป็นทำให้คุณแก้ปัญหาความช้าด้วยหลักฐาน ไม่ใช่การเดา และการเพิ่ม Index ที่ถูกต้องเพียงตัวเดียวมักทำให้ Query เร็วขึ้นหลายร้อยเท่า ทักษะนี้เป็นสิ่งที่ Backend Developer ระดับ Mid ขึ้นไปถูกคาดหวังให้ทำได้
ลงมือทำ
  • รัน EXPLAIN QUERY PLAN ใน SQLite ก่อนและหลังสร้าง Index ตามตัวอย่างด้านล่าง
  • ใน PostgreSQL สร้างตาราง big_orders 200,000 แถวด้วย generate_series() แล้วเปรียบเทียบ EXPLAIN ANALYZE ของการค้นหาด้วย customer_id ก่อนและหลังมี Index
  • สร้าง Composite Index แล้วทดลองว่า Query แบบไหนใช้ Index ได้และแบบไหนใช้ไม่ได้
  • ทดลอง WHERE lower(email) = 'somchai@example.com' ก่อนและหลังสร้าง Expression Index

STEP 12

Transaction, ACID, Isolation Level, สิทธิ์ผู้ใช้ และ Backup

3 วัน · 4–5 ชม.
หัวข้อย่อย
  • ACID ด้วยตัวอย่างการขายสินค้า 1 ชิ้น (สร้างคำสั่งซื้อ + เพิ่มรายการ + ตัด stock): Atomicity (สำเร็จทั้งหมดหรือไม่เกิดเลย), Consistency (ไม่ละเมิด Constraint), Isolation (คนอื่นไม่เห็นงานที่ยังไม่เสร็จ) และ Durability (Commit แล้วไม่หายแม้ไฟดับ)
  • BEGIN, COMMIT, ROLLBACK, SAVEPOINT และ ROLLBACK TO SAVEPOINT และพฤติกรรมของ PostgreSQL ที่เมื่อเกิด Error ใน Transaction แล้วจะแจ้ง current transaction is aborted, commands ignored until end of transaction block จนกว่าจะ ROLLBACK
  • ปัญหาเมื่อทำงานพร้อมกัน: Dirty Read, Non-repeatable Read, Phantom Read และ Lost Update
  • Isolation Level ของ PostgreSQL: READ COMMITTED (ค่าเริ่มต้น), REPEATABLE READ และ SERIALIZABLE (ถ้าสั่ง READ UNCOMMITTED PostgreSQL จะทำงานแบบ READ COMMITTED) และการกำหนดด้วย BEGIN ISOLATION LEVEL ...
  • ทดลองเปิด Terminal สองหน้าต่าง (Session A และ B) แก้ข้อมูลแถวเดียวกัน แล้วสังเกตผลของแต่ละ Isolation Level (ดูตารางด้านล่าง) รวมถึง Error could not serialize access due to concurrent update ที่แอปต้องลองใหม่ (Retry)
  • ล็อกแถวด้วย SELECT ... FOR UPDATE เพื่อกันขายของเกินจำนวนในคลัง, Error deadlock detected และหลักการทำ Transaction ให้สั้นที่สุด
  • Role และสิทธิ์: CREATE ROLE ... LOGIN, ตั้งรหัสผ่านด้วย \password, GRANT / REVOKE ระดับฐานข้อมูล Schema และตาราง, ALTER DEFAULT PRIVILEGES สำหรับตารางที่สร้างในอนาคต, ดูสิทธิ์ด้วย \du และ \dp และหลัก Least Privilege
  • สำรองและกู้คืน: pg_dump แบบไฟล์ SQL ธรรมดากับแบบ Custom (-Fc), กู้คืนด้วย psql -f หรือ pg_restore, กู้คืนลงฐานข้อมูลใหม่เพื่อทดสอบ, สำรอง Role ด้วย pg_dumpall --globals-only, ตั้งเวลาสำรองด้วย cron จากหัวข้อ Linux และคำสั่ง .backup กับ .dump ของ SQLite
  • (ทางเลือกเสริม) รัน PostgreSQL 18 ใน Container ด้วย Docker Desktop 4.95.0 (WSL 2 backend) ที่ Port อื่น เช่น 5433 เพื่อทดลองรุ่นใหม่โดยไม่กระทบรุ่น 16 ที่ใช้อยู่

Must-know Skills

ถ้าต้องสรุปหัวข้อนี้ให้เหลือทักษะที่ผู้สัมภาษณ์และงานจริงคาดหวังจากคนที่ "เขียน SQL เป็น" จะได้รายการนี้

  1. เขียน SELECT พร้อม WHERE, ORDER BY, LIMIT และ DISTINCT ได้แม่นยำ เพราะเป็นพื้นฐานของทุก Query และการแบ่งหน้าข้อมูลในแอปทุกตัวใช้รูปแบบนี้
  2. จัดการ NULL อย่างถูกต้องด้วย IS NULL และ COALESCE เพราะ NULL ทำให้แถวหายไปจากผลลัพธ์หรือทำให้ตัวเลขผิดโดยไม่มี Error เตือน
  3. ออกแบบตารางด้วย Data Types และ Constraints ที่เหมาะสม เพราะ Constraint ป้องกันข้อมูลผิดได้ทุกครั้งไม่ว่าข้อมูลจะมาจากแอปใด และเงินต้องใช้ NUMERIC ไม่ใช่ทศนิยมแบบ Float
  4. แก้ไขข้อมูลอย่างปลอดภัยด้วย SELECT ก่อน UPDATE/DELETE ภายใน Transaction เพราะฐานข้อมูลไม่มีปุ่ม Undo และความผิดพลาดหนึ่งครั้งอาจทำให้ต้องกู้ข้อมูลจาก Backup
  5. สรุปข้อมูลด้วย GROUP BY, HAVING และ CASE เพราะรายงานและ Dashboard เกือบทุกฉบับในบริษัทสร้างจากคำสั่งกลุ่มนี้
  6. เลือก JOIN ที่ถูกแบบและคาดจำนวนแถวได้ก่อนรัน เพราะ JOIN ผิดแบบไม่ทำให้เกิด Error แต่ทำให้ลูกค้าหายจากรายงานหรือยอดขายเพิ่มเป็นสองเท่า
  7. แบ่ง Query ซับซ้อนเป็นขั้นด้วย Subquery, CTE และ View เพราะทำให้ Query ยาวอ่านง่าย ทดสอบทีละขั้นได้ และทีมนำไปใช้ต่อได้
  8. วิเคราะห์ข้อมูลด้วย Window Functions เพราะยอดสะสม การจัดอันดับ และการเทียบกับช่วงก่อนหน้า เป็นคำถามประจำของงานข้อมูลและแบบทดสอบสัมภาษณ์
  9. ออกแบบ Schema ถึง 3NF และรู้ว่าเมื่อไร Denormalize ได้ เพราะ Schema ที่ดีลดบั๊กของข้อมูลได้ตลอดอายุของระบบ และเป็นทักษะที่ใช้ในการสัมภาษณ์ออกแบบระบบ
  10. ใช้ Index และอ่าน EXPLAIN ANALYZE เพราะการแก้ Query ที่ช้าด้วยหลักฐานคือสิ่งที่ทำให้ระบบรองรับผู้ใช้จำนวนมากได้
  11. เข้าใจ Transaction, ACID และ Isolation Level เพราะระบบที่มีผู้ใช้หลายคนพร้อมกันต้องป้องกันปัญหาอย่างการขายของเกินจำนวนในคลัง
  12. จัดสิทธิ์ด้วย GRANT และสำรองกู้คืนด้วย pg_dump / pg_restore เพราะหลัก Least Privilege จำกัดความเสียหายเมื่อรหัสผ่านรั่ว และ Backup ที่ทดสอบแล้วคือประกันชีวิตของข้อมูล
  13. เรียก SQL จาก Python ด้วย Parameterized Query เสมอ เพราะเป็นวิธีป้องกัน SQL Injection ที่ได้ผลที่สุด และเป็นรูปแบบที่ Backend และงานข้อมูลใช้ทุกวัน
