Mini Project: Library API Spec

เป้าหมาย

ออกแบบ REST API ของระบบห้องสมุด (หนังสือ สมาชิก การยืมคืน) แบบ Contract-first คือเขียน "สัญญา" ด้วย OpenAPI 3.1 ให้เสร็จก่อน แล้วค่อยใช้สัญญานั้นเป็นศูนย์กลางของทุกอย่าง ทั้งการตรวจคุณภาพ (Lint) การทำ Mock Server ให้ทีม Frontend ใช้ก่อน Backend เสร็จ และการเขียน Reference Implementation ที่มีเทสต์คอยยืนยันว่าโค้ดตรงกับสัญญา

เมื่อทำเสร็จ คุณจะมี Repository ชื่อ library-api-spec บน GitHub ที่แสดงให้ผู้สัมภาษณ์เห็นว่าคุณออกแบบ API เป็นระบบ ไม่ใช่แค่เขียน Endpoint ได้

เปรียบเทียบ

เหมือนการสร้างบ้าน: openapi.yaml คือแบบแปลนที่สถาปนิกเซ็นรับรอง Spectral คือวิศวกรที่ตรวจว่าแบบถูกมาตรฐาน Prism คือบ้านตัวอย่างที่ลูกค้าเดินดูได้ก่อนสร้างจริง ส่วน FastAPI คือบ้านจริงที่ต้องสร้างให้ตรงแบบ และเทสต์คือผู้ตรวจรับงานที่เอาแบบมาเทียบกับบ้านทุกห้อง

ฟีเจอร์ที่จะได้

  • openapi.yaml (OpenAPI 3.1.0) มี 10 Operation ใน 3 tag: listBooks, createBook, getBook, updateBook, deleteBook, createMember, getMember, listMemberLoans, createLoan, returnLoan
  • components ครบ: schemas 11 ตัว (Book, BookCreate, BookPatch, BookPage, Member, MemberCreate, Loan, LoanCreate, LoanPage, Problem, ValidationProblem), parameters 6 ตัว, responses 8 ตัว และ securitySchemes bearerAuth (JWT)
  • Error ทุกตัวเป็น application/problem+json ตาม RFC 9457 มี type เป็น https://example.com/problems/<slug>
  • Cursor Pagination พร้อม Header Link: rel="next", ETag กับ If-None-Match (304) และ If-Match (412), Idempotency-Key สำหรับการยืม, กฎ BOLA ว่าสมาชิกดูได้เฉพาะข้อมูลของตัวเอง
  • .spectral.yaml ใช้ชุดกฎ spectral:oas บวกกฎของทีม 4 ข้อ และ npm run lint ผ่านแบบไม่มี error
  • npm run mock เปิด Prism Mock Server ที่ 127.0.0.1:4010
  • Reference Implementation ด้วย FastAPI ในโฟลเดอร์ app/ ใช้ข้อมูลตัวอย่างมาตรฐานของหลักสูตร
  • เทสต์ pytest 31 ข้อ รวมเทสต์สัญญาที่ตรวจว่าทุก operationId ในสเปกมี Route จริง
  • scripts/smoke.sh รันได้ทั้งกับ Mock และ Server จริง แสดง PASS/FAIL ทีละข้อ
  • README พร้อมตาราง Endpoint, Error Catalog และเอกสาร Redoc แบบไฟล์เดียว

  2. Step 2: เขียนสัญญา openapi.yaml

    นี่คือขั้นที่สำคัญที่สุดของโปรเจกต์ ในงานจริงทีมจะ Review ไฟล์นี้ผ่าน Pull Request ก่อนใครจะเริ่มเขียนโค้ด ก่อนพิมพ์ ให้ตัดสินใจเรื่องเหล่านี้ให้ชัด แล้วเขียนลงสเปกให้ครบ:

    • Resource และ URL: ใช้คำนามพหูพจน์ (/books, /members, /loans) การยืมคือการสร้าง Resource ใหม่ POST /loans และการคืนคือ Action ที่ทำเป็น Sub-resource POST /loans/{loan_id}/return
    • ใครเรียกอะไรได้: GET ของหนังสือเป็นสาธารณะ ส่วนการเขียนทุกอย่างใช้ security: - bearerAuth: [] ราย Operation และบอก scope ที่ต้องใช้ไว้ใน description
    • Response ทุกแบบ: ทุก Operation ต้องประกาศทั้งกรณีสำเร็จและกรณี Error ที่เป็นไปได้ โดยอ้างถึง components/responses เพื่อไม่ต้องเขียนซ้ำ
    • Example ที่สมจริง: ใช้ข้อมูลตัวอย่างมาตรฐาน (bk_0001–bk_0003, mb_0001–mb_0002, ln_0001) เพราะ Prism จะเอา Example เหล่านี้ไปตอบ Frontend

    openapi: 3.1.0ใช้ OpenAPI 3.1 ซึ่ง Schema คือ JSON Schema 2020-12 จึงเขียน type: [string, 'null'] แทน nullable: true ของ 3.0 ได้

    serversมีสองเครื่อง: Reference (8000) และ Mock (4010) เครื่องมือเอกสารจะให้เลือก Server ได้
    '200': ที่มีเครื่องหมาย 'Key ที่เป็นตัวเลขต้องครอบด้วย Quote เพราะ YAML จะอ่าน 200 เป็นตัวเลข แต่ OpenAPI ต้องการ String
    isbn: '9786160000011'ISBN เป็นรหัส ไม่ใช่ตัวเลขที่เอาไปคำนวณ จึงเป็น String และต้องครอบ Quote ใน Example
    parameters ระดับ Pathเขียน BookId ครั้งเดียวใต้ /books/{book_id} แล้วใช้ร่วมกันทั้ง GET, PATCH, DELETE
    headers: Link, ETag, LocationHeader ใน Response ก็เป็นส่วนหนึ่งของสัญญา Client ต้องรู้ว่าจะได้ Header อะไรกลับไป

    security: - bearerAuth: []ใส่ราย Operation เฉพาะที่ต้องยืนยันตัวตน Operation ที่ไม่มีบรรทัดนี้คือ Endpoint สาธารณะ
    additionalProperties: falseใน BookCreate, BookPatch, MemberCreate, LoanCreate: ห้ามส่งฟิลด์เกิน กัน Mass Assignment (OWASP API3) เช่นส่ง status หรือ id มาเอง

    Best Practice
    • ทุก Operation มี operationId แบบ camelCase ที่ไม่ซ้ำกัน เครื่องมือ Generate Client SDK จะใช้ชื่อนี้เป็นชื่อฟังก์ชัน
    • ใส่ description ที่บอกกฎทางธุรกิจ (เช่น ยืมได้ไม่เกิน 3 เล่ม, กฎ BOLA) ไว้ในสเปก ไม่ใช่เก็บไว้ในหัวของ Backend Developer
    • ใช้ $ref ไปที่ components เสมอเมื่อของชิ้นเดียวกันถูกใช้มากกว่าหนึ่งที่

    """เก็บ books, members, loans และผลของ Idempotency-Key ไว้ใน dict"""

    def __init__(self):
        self.reset()

    def reset(self):
        # deepcopy เพื่อไม่ให้การแก้ข้อมูลไปกระทบข้อมูลตั้งต้น (สำคัญมากตอนรันเทสต์)

        self.members = {m["id"]: m for m in copy.deepcopy(SEED_MEMBERS)}
        self.loans = {ln["id"]: ln for ln in copy.deepcopy(SEED_LOANS)}
        # key คือ (sub ของผู้เรียก, Idempotency-Key) แยกตาม Client
        self.idempotency = {}

        return [ln for ln in self.loans.values()

    @model_validator(mode="after")

import logging

from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

PROBLEM_BASE = "https://example.com/problems/"

log = logging.getLogger("library")

# Error จากตัว Framework (เช่น path ที่ไม่มีอยู่) แปลงเป็น slug กลาง
FRAMEWORK_PROBLEMS = {
    404: ("not-found", "Not Found"),
    405: ("method-not-allowed", "Method Not Allowed"),
}


class ProblemError(Exception):
    """โยน Exception นี้จากโค้ดใดก็ได้ แล้ว handler จะแปลงเป็น problem+json"""

    def __init__(self, status, slug, title, detail=None, headers=None):
        super().__init__(detail or title)
        self.status, self.slug, self.title = status, slug, title
        self.detail, self.headers = detail, headers


def problem_response(request, status, slug, title, detail=None, headers=None, **extra):
    body = {"type": PROBLEM_BASE + slug, "title": title, "status": status}
    if detail:
        body["detail"] = detail
    body["instance"] = request.url.path
    body.update(extra)
    return JSONResponse(body, status_code=status, headers=headers, media_type=PROBLEM_MEDIA_TYPE)


def install_problem_handlers(app: FastAPI):
    @app.exception_handler(ProblemError)
    async def handle_problem(request: Request, exc: ProblemError):
        return problem_response(request, exc.status, exc.slug, exc.title, exc.detail, exc.headers)

    # ต้องลงทะเบียนกับ HTTPException ของ starlette จึงจะจับ 404/405 ของ Router ได้ด้วย
    @app.exception_handler(StarletteHTTPException)
    async def handle_http(request: Request, exc: StarletteHTTPException):
        slug, title = FRAMEWORK_PROBLEMS.get(exc.status_code, ("http-error", "HTTP Error"))
        return problem_response(request, exc.status_code, slug, title, headers=exc.headers)

    @app.exception_handler(RequestValidationError)
    async def handle_validation(request: Request, exc: RequestValidationError):
        errors = [{"field": ".".join(str(p) for p in e["loc"]), "message": e["msg"]}
                  for e in exc.errors()]
        return problem_response(request, 422, "validation-error", "Validation Error",
                                f"ข้อมูลที่ส่งมาไม่ถูกต้อง {len(errors)} จุด", errors=errors)

    @app.exception_handler(Exception)
    async def handle_unexpected(request: Request, exc: Exception):
        # เก็บรายละเอียดไว้ใน log ฝั่ง Server เท่านั้น ห้ามส่ง stack trace ให้ Client
        trace_id = uuid.uuid4().hex
        log.exception("unhandled error trace_id=%s", trace_id)
        return problem_response(request, 500, "internal-error", "Internal Server Error",
                                "เกิดข้อผิดพลาดภายใน แจ้งผู้ดูแลพร้อม trace_id", trace_id=trace_id)

def _unauthorized(detail, error=None):
    challenge = 'Bearer realm="library-api"'
    if error:
        challenge += f', error="{error}"'
    return ProblemError(401, "unauthorized", "Unauthorized", detail,
                        headers={"WWW-Authenticate": challenge})


def get_current_user(creds: HTTPAuthorizationCredentials | None = Depends(bearer)) -> dict:
    if creds is None:
        raise _unauthorized("ต้องส่ง Authorization Bearer token")
    try:
        claims = jwt.decode(
            creds.credentials,
            os.environ["JWT_SECRET"],          # ตรวจแล้วตอนเริ่ม Server ว่ามีค่า
            algorithms=["HS256"],              # ล็อก algorithm กันการโจมตีแบบ alg none
            audience=AUDIENCE,
            issuer=ISSUER,
            options={"require": ["exp", "iat", "sub"]},
        )
    except jwt.ExpiredSignatureError:
        raise _unauthorized("token expired", "invalid_token")
    except jwt.InvalidTokenError:
        raise _unauthorized("token ไม่ถูกต้อง", "invalid_token")
    claims["scopes"] = set(claims.get("scope", "").split())
    return claims


def require_scope(scope: str):
    """สร้าง Dependency ที่บังคับว่า token ต้องมี scope นี้ (หรือ admin)"""

    def checker(user: dict = Depends(get_current_user)) -> dict:
        if scope not in user["scopes"] and "admin" not in user["scopes"]:
            raise ProblemError(403, "forbidden", "Forbidden", f"token นี้ไม่มี scope {scope}")
        return user

    return checker

def find_or_404(table: dict, key: str, slug: str, title: str, label: str) -> dict:
    item = table.get(key)
    if item is None:
        raise ProblemError(404, slug, title, f"ไม่พบ{label}รหัส {key}")
    return item


def etag_of(book: dict) -> str:
    # ETag = hash ของ JSON ที่เรียง key แล้ว ข้อมูลเหมือนเดิมจะได้ค่าเดิมเสมอ (ต้องมีเครื่องหมาย " ครอบ)
    raw = json.dumps(book, sort_keys=True, ensure_ascii=False).encode("utf-8")
    return '"' + hashlib.sha256(raw).hexdigest()[:16] + '"'


def encode_cursor(sort: str, last_key: list) -> str:
    raw = json.dumps({"s": sort, "k": last_key}, separators=(",", ":")).encode()
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()


def decode_cursor(cursor: str, sort: str) -> list:
    try:
        padded = cursor + "=" * (-len(cursor) % 4)   # เติม = ที่ตัดทิ้งไปตอน encode
        data = json.loads(base64.urlsafe_b64decode(padded))
        if data["s"] != sort or len(data["k"]) != 2:
            raise ValueError("sort ไม่ตรงกับ cursor")
        return data["k"]
    except (binascii.Error, ValueError, KeyError, TypeError):
        raise ProblemError(400, "bad-request", "Bad Request",
                           "cursor ไม่ถูกต้อง ให้ใช้ค่า next_cursor จาก Response เท่านั้น")


def comes_after(book: dict, field: str, desc: bool, last_key: list) -> bool:
    # เรียงด้วย (field, id) โดยใช้ id เป็นตัวตัดสินเมื่อค่า field เท่ากัน
    value, last_value, last_id = book[field], last_key[0], last_key[1]
    if value == last_value:
        return book["id"] > last_id
    return value < last_value if desc else value > last_value


def body_hash(payload: dict) -> str:
    return hashlib.sha256(json.dumps(payload, sort_keys=True).encode()).hexdigest()

@app.get("/books", operation_id="listBooks", response_model=BookPage, tags=["books"])
def list_books(request: Request, response: Response,
               q: str | None = Query(None, max_length=100),
               author: str | None = None,
               status: BookStatus | None = None,
               sort: SortField = "id",
               limit: int = Query(20, ge=1, le=100),
               cursor: str | None = None):
    items = list(store.books.values())
    if q:
        needle = q.casefold()
        items = [b for b in items if needle in b["title"].casefold() or needle in b["author"].casefold()]
    if author:
        items = [b for b in items if b["author"] == author]
    if status:
        items = [b for b in items if b["status"] == status]
    field, desc = sort.lstrip("-"), sort.startswith("-")
    items.sort(key=lambda b: b["id"])                    # ตัวตัดสินรอง: id จากน้อยไปมาก
    items.sort(key=lambda b: b[field], reverse=desc)     # sort ของ Python เสถียร ลำดับ id จึงยังอยู่
    if cursor:
        last_key = decode_cursor(cursor, sort)
        items = [b for b in items if comes_after(b, field, desc, last_key)]
    page = items[:limit]
    next_cursor = None
    if len(items) > limit:
        tail = page[-1]
        next_cursor = encode_cursor(sort, [tail[field], tail["id"]])
        next_url = request.url.include_query_params(cursor=next_cursor)
        response.headers["Link"] = f'<{next_url}>; rel="next"'
    return {"data": page, "next_cursor": next_cursor}

@app.post("/loans", operation_id="createLoan", response_model=Loan, status_code=201, tags=["loans"])
def create_loan(payload: LoanCreate, response: Response,

                                                     min_length=8, max_length=100),
                user: dict = Depends(require_scope("loans:write"))):
    if idempotency_key is None:
        raise ProblemError(400, "bad-request", "Bad Request", "ต้องส่ง Header Idempotency-Key")
    ensure_owner(user, payload.member_id)
    store_key = (user["sub"], idempotency_key)          # แยก key ตาม Client
    request_hash = body_hash(payload.model_dump())
    saved = store.idempotency.get(store_key)
    if saved:
        if saved["hash"] != request_hash:
            raise ProblemError(422, "idempotency-key-reused", "Idempotency Key Reused",
                               "Idempotency-Key นี้เคยใช้กับ Body อื่นแล้ว")
        # key เดิม + Body เดิม: ส่งผลเดิมกลับไป ไม่สร้างรายการยืมซ้ำ
        response.headers["Location"] = f"/loans/{saved['loan']['id']}"
        response.headers["Idempotent-Replayed"] = "true"
        return saved["loan"]

    book = find_or_404(store.books, payload.book_id, "book-not-found", "Book Not Found", "หนังสือ")
    member = find_or_404(store.members, payload.member_id, "member-not-found",
                         "Member Not Found", "สมาชิก")
    if book["status"] != "available":
        raise ProblemError(409, "book-unavailable", "Book Unavailable",
                           f"หนังสือ {book['id']} ถูกยืมอยู่")
    if len(store.active_loans(member["id"])) >= member["max_active_loans"]:
        raise ProblemError(409, "loan-limit-reached", "Loan Limit Reached",
                           f"สมาชิก {member['id']} ยืมครบ {member['max_active_loans']} เล่มแล้ว")

    now = datetime.now(BANGKOK).replace(microsecond=0)
    loan = {"id": store.next_id("ln"), "book_id": book["id"], "member_id": member["id"],
            "borrowed_at": now.isoformat(), "due_date": (now + timedelta(days=LOAN_DAYS)).date().isoformat(),
            "returned_at": None, "fine_satang": 0}
    store.loans[loan["id"]] = loan
    book["status"] = "on_loan"
    store.idempotency[store_key] = {"hash": request_hash, "loan": loan}   # เก็บเฉพาะผลที่สำเร็จ

    loan = find_or_404(store.loans, loan_id, "loan-not-found", "Loan Not Found", "รายการยืม")
    ensure_owner(user, loan["member_id"])
    if loan["returned_at"] is None:          # คืนซ้ำได้ผลเดิม (Idempotent)

        days_late = (now.date() - date.fromisoformat(loan["due_date"])).days
        loan["returned_at"] = now.isoformat()
        loan["fine_satang"] = max(days_late, 0) * FINE_PER_DAY_SATANG

    return loan

คำถามที่พบบ่อยในการสัมภาษณ์ตำแหน่ง Backend, Full-stack และ AI Engineer ระดับ Junior ถึง Mid-level ลองตอบด้วยตัวเองก่อนเปิดดูแนวคำตอบ และพยายามยกตัวอย่างจาก Mini Project ของคุณเอง เพราะผู้สัมภาษณ์ชอบคำตอบที่มาจากประสบการณ์จริง

1. (Junior–Mid) REST, GraphQL และ gRPC ต่างกันอย่างไร และจะเลือกใช้แบบไหนเมื่อไร

แนวคำตอบ: ทั้งสามเป็นรูปแบบ (Style) ของ API ที่แก้ปัญหาต่างกัน

  • REST: มองทุกอย่างเป็น Resource ที่มี URL ของตัวเอง ใช้ HTTP Method และ Status Code ตามความหมายมาตรฐาน ได้ประโยชน์จาก HTTP Caching (ETag, Cache-Control) เครื่องมือเยอะ เรียกด้วย curl ได้ทันที และมี OpenAPI เป็นสัญญา เหมาะกับ Public API และระบบส่วนใหญ่
  • GraphQL: มี Endpoint เดียว Client เขียน Query ระบุฟิลด์ที่ต้องการเอง แก้ปัญหา Over-fetching และ Under-fetching เหมาะกับหน้าจอที่ต้องดึงข้อมูลหลายชนิดพร้อมกัน เช่น Mobile App แต่ต้องระวังเรื่อง Query ที่ซับซ้อนเกินไป (ต้องจำกัดความลึก) และ HTTP Caching ใช้ได้ยากกว่าเพราะส่วนใหญ่เป็น POST
  • gRPC: ใช้ Protocol Buffers บน HTTP/2 ข้อมูลเป็น Binary ขนาดเล็กและเร็ว มี Streaming สองทาง สร้างโค้ด Client/Server จากไฟล์ .proto เหมาะกับการคุยกันระหว่าง Microservice ภายในองค์กร ไม่เหมาะกับการเรียกตรงจาก Browser

จุดที่ทำให้คำตอบโดดเด่น: บอกว่าองค์กรใหญ่มักใช้ผสมกัน เช่น REST สำหรับ Public API, gRPC ระหว่าง Service ภายใน และ GraphQL เป็นชั้น Gateway ให้ Frontend และย้ำว่าไม่ว่าเลือกแบบไหน หลัก Contract-first ยังใช้ได้เหมือนกัน (OpenAPI, GraphQL Schema, ไฟล์ .proto)

2. (Mid) POST ไม่ Idempotent แล้วจะทำให้การยืมหนังสือหรือการจ่ายเงินปลอดภัยเมื่อ Client ต้อง Retry ได้อย่างไร

แนวคำตอบ: ใช้ Idempotency-Key: Client สร้างค่าสุ่ม (เช่น UUID) หนึ่งค่าต่อหนึ่งการกระทำ แล้วส่งใน Header ทุกครั้งที่ Retry การกระทำนั้น Server เก็บ key คู่กับ hash ของ Body และผลลัพธ์ที่ส่งไป

  1. key ใหม่: ทำงานตามปกติ แล้วบันทึกผล
  2. key เดิม + Body เดิม: ไม่ทำซ้ำ ส่งผลเดิมกลับไป (ในโปรเจกต์ของผมใส่ Header Idempotent-Replayed: true ให้ด้วย)
  3. key เดิม + Body ต่าง: เป็นความผิดของ Client ตอบ 422 idempotency-key-reused

รายละเอียดที่ควรพูดถึง: key ต้องแยกตาม Client (ผมใช้คู่ (sub, key)) ไม่งั้นคนสองคนที่บังเอิญได้ key ซ้ำจะเห็นผลของกันและกัน, key ต้องมีอายุ (เช่น 24 ชั่วโมง) ไม่เก็บถาวร, ในระบบที่มีหลาย Server ต้องเก็บไว้ในที่กลางอย่าง Redis หรือฐานข้อมูล และต้องกันกรณีสอง Request ที่ใช้ key เดียวกันมาถึงพร้อมกันด้วย Lock หรือ Unique Constraint ฝั่ง Client ควร Retry แบบ Exponential Backoff พร้อม Jitter และเคารพ Retry-After

3. (Junior–Mid) Offset Pagination กับ Cursor Pagination ต่างกันอย่างไร ถ้าออกแบบ Feed ที่มีข้อมูลเพิ่มตลอดเวลาจะเลือกแบบไหน

แนวคำตอบ:

  • Offset (?limit=20&offset=40): เข้าใจง่าย กระโดดไปหน้าที่ต้องการได้ และบอกจำนวนทั้งหมดได้ แต่ถ้ามีรายการใหม่แทรกเข้ามาระหว่างที่ผู้ใช้เลื่อน รายการจะซ้ำหรือหายข้ามหน้า และฐานข้อมูลต้องนับข้ามแถวทิ้งทุกครั้ง ยิ่ง offset มากยิ่งช้า
  • Cursor (?limit=20&cursor=...): Server ส่ง next_cursor ที่จำตำแหน่งรายการสุดท้ายไว้ หน้าถัดไปคือ "รายการที่อยู่หลังตำแหน่งนี้" จึงไม่ซ้ำไม่หายเมื่อข้อมูลเปลี่ยน และ Query ใช้ Index ได้เร็วคงที่ แต่กระโดดไปหน้า 50 ตรง ๆ ไม่ได้

สำหรับ Feed เลือก Cursor ส่วนหน้าจอ Admin ที่ต้องมีเลขหน้าและข้อมูลไม่ค่อยเปลี่ยนใช้ Offset ได้

จุดที่ทำให้คำตอบโดดเด่น: การเรียงต้องมีตัวตัดสินที่ไม่ซ้ำเสมอ (เช่น (published_year, id)) ไม่งั้นรายการที่ค่าเท่ากันจะกระโดด, Cursor ต้องเป็นค่าทึบ (Opaque) ที่ Client ห้ามแกะ, ต้องจำกัด limit สูงสุด (ผมใช้ 100 เกินได้ 422) เพื่อกัน OWASP API4 และควรส่ง Header Link: rel="next" ด้วย

4. (Mid) JWT เป็น Stateless แล้วถ้าต้องการยกเลิก (Revoke) Token ของผู้ใช้ที่โดนขโมยบัญชีจะทำอย่างไร

แนวคำตอบ: Server ตรวจ JWT ด้วยลายเซ็นอย่างเดียว จึงยกเลิก Token ที่ออกไปแล้วไม่ได้โดยตรง ต้องออกแบบรองรับตั้งแต่แรก

  • Access Token อายุสั้น (5–15 นาที) คู่กับ Refresh Token ที่เก็บสถานะในฐานข้อมูล เมื่อต้องการยกเลิกก็ลบหรือปิด Refresh Token ความเสียหายจำกัดอยู่ที่อายุของ Access Token ที่เหลือ
  • Denylist ด้วย jti: ใส่รหัสเฉพาะใน Token แล้วเก็บรายการที่ถูกยกเลิกไว้ใน Redis จนกว่าจะหมดอายุ แลกกับการต้องเช็กที่เก็บข้อมูลทุก Request
  • Token Version ต่อผู้ใช้: เก็บเลขเวอร์ชันในข้อมูลผู้ใช้และใส่ใน Token เมื่อเปลี่ยนรหัสผ่านก็เพิ่มเลข Token เก่าทั้งหมดใช้ไม่ได้ทันที
  • หมุน Signing Key: ใช้ในกรณีร้ายแรงที่ Key รั่ว ทำให้ Token ทุกใบใช้ไม่ได้

ข้อผิดพลาดที่ควรพูดถึงว่าหลีกเลี่ยง: ไม่ล็อก Algorithm (โดนโจมตีแบบ alg: none), ไม่ตรวจ exp, aud, iss, ใส่ข้อมูลลับใน Payload (JWT แค่เข้ารหัส base64url อ่านได้ทุกคน), ใช้ Secret อ่อน และเก็บ Token ไว้ใน localStorage ที่ถูกขโมยได้ถ้าเว็บมีช่องโหว่ XSS

5. (Mid) คุณจะจัดการ Versioning ของ API อย่างไร และอะไรนับเป็น Breaking Change

แนวคำตอบ: เป้าหมายแรกคือ หลีกเลี่ยงการออกเวอร์ชันใหม่ ด้วยการเปลี่ยนแบบไม่ Breaking เป็นหลัก เช่น เพิ่ม Endpoint ใหม่ เพิ่มฟิลด์ใหม่ใน Response เพิ่ม Query Parameter ที่ไม่บังคับ ส่วนการเปลี่ยนที่นับเป็น Breaking ได้แก่ ลบหรือเปลี่ยนชื่อฟิลด์, เปลี่ยน type, เพิ่มฟิลด์ required ใน Request, เปลี่ยนความหมายของ Status Code, เพิ่มค่า enum ใน Response ที่ Client เขียนโค้ดแบบไม่รองรับค่าใหม่ และเปลี่ยนวิธียืนยันตัวตน

เมื่อจำเป็นต้อง Breaking มีสามแบบหลัก:

  • URL (/v1/books): เห็นชัด ทดสอบด้วย curl ง่าย และ Route แยกที่ Gateway ได้ เป็นแบบที่ใช้กันมากที่สุดใน Public API
  • Header (เช่น Header เวอร์ชันที่ทีมกำหนดเอง): URL สะอาด แต่มองไม่เห็นและ Cache ต้องตั้ง Vary ให้ถูก
  • Media Type (Accept: application/vnd.example.v2+json): ถูกหลัก HTTP ที่สุด แต่ใช้ยากที่สุดสำหรับผู้ใช้ API

จุดที่ทำให้คำตอบโดดเด่น: พูดถึงกระบวนการ ไม่ใช่แค่รูปแบบ URL ได้แก่ ตรวจ Breaking Change อัตโนมัติด้วยการ Diff ไฟล์ OpenAPI ใน CI, ประกาศเลิกใช้ล่วงหน้าด้วย Header Sunset (RFC 8594) และ Link ไปหน้าอธิบาย, ดู Log ว่าใครยังเรียกเวอร์ชันเก่าอยู่ก่อนปิด และเก็บรายการเวอร์ชันทั้งหมดให้ครบ (OWASP API9 Improper Inventory Management)
