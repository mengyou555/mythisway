Mini Project: Portfolio Website บน GitHub Pages

เป้าหมาย

สร้างเว็บ Portfolio ส่วนตัวของ สมชาย ใจดี ด้วย HTML และ CSS ล้วน (ไม่มี Framework และไม่มีขั้นตอน Build) เก็บไว้ใน Repository ของตัวเองชื่อ somchai-dev/portfolio พัฒนาทีละฟีเจอร์บน Branch แยก แล้วรวมเข้า main ผ่าน Pull Request ทุกครั้ง ทุก PR ถูกตรวจอัตโนมัติด้วย GitHub Actions และทุกครั้งที่ main เปลี่ยน เว็บจะถูก Deploy ขึ้น https://somchai-dev.github.io/portfolio/ เอง

เมื่อทำเสร็จ คุณจะมีสิ่งที่บริษัทอยากเห็นจากผู้สมัครสายเทคครบในที่เดียว ได้แก่ เว็บที่เปิดได้จริง, ประวัติ Commit ที่อ่านรู้เรื่อง, Pull Request ที่มีคำอธิบาย, CI ที่ตรวจงานทุกครั้ง, Release แรก v1.0.0, หน้า Profile README และ Repository learning-journal จาก Day 0 ที่ขึ้น GitHub แล้ว

เปรียบเทียบ

ให้นึกถึงร้านอาหารที่เปิดครัวให้ลูกค้าเห็น เว็บ Portfolio คือจานอาหารที่เสิร์ฟ ส่วนประวัติ Git, Pull Request และ CI คือครัวที่สะอาดและมีขั้นตอนชัดเจน ผู้สัมภาษณ์งานหลายคนเปิดดู "ครัว" บน GitHub ก่อนจะชิม "อาหาร" เสียอีก

ฟีเจอร์ของโปรเจกต์

  • หน้าเว็บ 3 หน้า: index.html (แนะนำตัว รูป ทักษะ ติดต่อ), projects.html (การ์ดโปรเจกต์) และ 404.html ทุกหน้ามี lang="th", meta viewport และใช้ลิงก์แบบ Relative เท่านั้น พร้อม css/style.css แบบ Mobile-first ที่มี Media query เดียวที่ 720px และรูป images/profile.png
  • ไฟล์ตั้งค่า Git: .gitignore, .gitattributes (บรรทัดแบบ LF), LICENSE แบบ MIT ปี 2026 และ README.md ที่มี Live demo, ภาพหน้าจอ, วิธีรัน, เทคโนโลยี และสิ่งที่ได้เรียนรู้
  • ทำงานแบบทีม: ทุกงานมี Issue บน GitHub Projects board อยู่บน Branch ของตัวเอง และ Merge ผ่าน PR ที่ตั้งชื่อตาม Conventional Commits พร้อม Closes #N
  • CI และ CD: ci.yml ตรวจ HTML และลิงก์เสียทุก PR (คุณจะจงใจทำให้ Check เป็นสีแดงแล้วแก้ให้เขียว) และ pages.yml Deploy ขึ้น GitHub Pages ทุกครั้งที่ main เปลี่ยน
  • ป้องกัน main และ Release: Ruleset ที่บังคับ PR, บังคับ Check check-site และห้าม Force push จากนั้นออก Annotated tag v1.0.0 พร้อม GitHub Release
  • หน้าโปรไฟล์: Profile README ใน Repository somchai-dev/somchai-dev และ Push learning-journal จาก Day 0 ขึ้น GitHub แล้วปักหมุดทั้งสองงาน

เครื่องมือและเวอร์ชันที่ใช้

Git 2.43.0 บน Ubuntu 24.04 ใน WSL2, GitHub CLI (gh) รุ่นล่าสุดจาก apt repository ทางการของ cli.github.com (ห้ามใช้ gh 2.45.0 ที่มากับ Ubuntu), Node.js 24 LTS ผ่าน nvm v0.40.8 (ใช้กับ Node 26 ได้) สำหรับรัน html-validate@11.16.2 และ linkinator@8.1.0 ผ่าน npx, Python 3.12 ของระบบสำหรับสร้างรูปชั่วคราวและเปิดเว็บเซิร์ฟเวอร์ทดสอบ และ GitHub Actions ที่ใช้ checkout@v5, setup-node@v5, configure-pages@v5, upload-pages-artifact@v4, deploy-pages@v4 บน ubuntu-latest ส่วน HTML และ CSS เขียนเองทั้งหมด ไม่มี Framework

หมายเหตุ

โปรเจกต์นี้ทำ 2 รอบ เพื่อให้คุณเห็นผลลัพธ์จริงทุกคำสั่งก่อนแตะ GitHub

  1. รอบซ้อม: ใช้ Remote จำลองในเครื่อง ~/projects/git-lab/remotes/portfolio.git (สร้างด้วย git init --bare เหมือนส่วนที่ 2 ของหัวข้อนี้) แล้ว "กด Merge PR" ด้วยคำสั่ง git merge --no-ff ในเครื่อง ทุกผลลัพธ์ในหน้านี้มาจากการรันจริงแบบนี้
  2. รอบจริง: ลบโฟลเดอร์ ~/projects/portfolio แล้วทำทุก Step ใหม่ โดยมีความต่างแค่ 2 จุด คือ (1) ใน Step 1 ใช้ URL ของ GitHub เป็น origin และ (2) ตอน Merge ให้ใช้กล่อง "รอบจริงบน GitHub" (เปิด PR ด้วย gh pr create และ Merge บน GitHub) แทนกล่อง "รอบซ้อม" ไฟล์และคำสั่ง Commit ทั้งหมดเหมือนเดิมทุกตัวอักษร

รหัส Commit (Hash), เวลา และขนาดไฟล์ในเครื่องของคุณจะต่างจากในหน้านี้ ตอน Push ไปยัง GitHub จริงจะเห็นบรรทัดเพิ่ม เช่น Enumerating objects และ Writing objects ซึ่งเป็นความคืบหน้าของการส่งข้อมูล และบรรทัด To จะเป็น git@github.com:somchai-dev/portfolio.git แทน Path ในเครื่อง

    # สร้างไฟล์ PNG สีเดียวไว้เป็นรูปชั่วคราว ใช้แค่ Standard Library ของ Python
# วิธีใช้: python3 make_png.py ไฟล์ปลายทาง ความกว้าง ความสูง
import struct
import sys
import zlib

path = sys.argv[1]
width = int(sys.argv[2])
height = int(sys.argv[3])
color = bytes([74, 144, 217])  # สีฟ้า (R, G, B)

# ทุกแถวของภาพขึ้นต้นด้วยไบต์ 0 (ไม่ใช้ Filter) ตามด้วยสีของทุกพิกเซล
raw = b"".join(b"\x00" + color * width for _ in range(height))


def chunk(tag, data):
    # หนึ่ง Chunk ของ PNG = ความยาว + ชื่อ + ข้อมูล + CRC
    crc = zlib.crc32(tag + data) & 0xFFFFFFFF
    return struct.pack(">I", len(data)) + tag + data + struct.pack(">I", crc)


header = struct.pack(">IIBBBBB", width, height, 8, 2, 0, 0, 0)
png = (
    b"\x89PNG\r\n\x1a\n"
    + chunk(b"IHDR", header)
    + chunk(b"IDAT", zlib.compress(raw, 9))
    + chunk(b"IEND", b"")
)
with open(path, "wb") as f:
    f.write(png)
print(f"สร้าง {path} แล้ว ขนาด {width}x{height} พิกเซล ({len(png)} ไบต์)")

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  check-site:
    runs-on: ubuntu-latest
    steps:
      - name: ดึงโค้ดของ Repository ลงเครื่อง Runner
        uses: actions/checkout@v5

      - name: ติดตั้ง Node.js เพื่อใช้ npx
        uses: actions/setup-node@v5
        with:
          node-version: 24

      - name: ตรวจโครงสร้าง HTML
        run: npx --yes html-validate@11.16.2 "**/*.html"

      - name: ตรวจลิงก์และรูปภาพที่เสีย (เฉพาะไฟล์ในเว็บของเรา)
        run: npx --yes linkinator@8.1.0 . --recurse --skip "^https://"

  contents: read

  id-token: write

      name: github-pages

1. Git กับ GitHub ต่างกันอย่างไร และ Working Tree, Staging Area, Repository คืออะไร (Junior)

คำตอบตัวอย่าง: Git คือโปรแกรม Version control แบบกระจาย (Distributed) ที่ทำงานในเครื่องของเราได้โดยไม่ต้องต่ออินเทอร์เน็ต ส่วน GitHub คือบริการบนเว็บที่เก็บ Repository ของ Git ไว้ให้ทีมแชร์กัน และเพิ่มเครื่องมือทำงานร่วมกัน เช่น Pull Request, Issues, Projects, Actions และ Pages ถ้าไม่มี GitHub ก็ยังใช้ Git ได้ เช่น ใช้ GitLab หรือ Remote แบบ bare บนเซิร์ฟเวอร์ของบริษัท

Git มี 3 พื้นที่หลัก

  • Working Tree: ไฟล์จริงที่เราแก้อยู่ในโฟลเดอร์
  • Staging Area (Index): พื้นที่เตรียมว่า Commit ถัดไปจะมีการเปลี่ยนแปลงอะไรบ้าง ใช้ git add นำเข้า ทำให้เลือกได้ว่าหนึ่ง Commit มีแค่เรื่องเดียว
  • Repository (โฟลเดอร์ .git): ที่เก็บ Commit ทั้งหมด แต่ละ Commit คือ Snapshot ของทั้งโปรเจกต์ พร้อมผู้เขียน วันที่ ข้อความ และ Parent โดยอ้างถึงด้วย Hash

จุดที่ทำให้คำตอบโดดเด่น: ยกตัวอย่างว่าใน Portfolio ผมแก้ index.html และ style.css พร้อมกัน แต่ใช้ git add index.html แยก Commit ทีละเรื่อง ประวัติจึงอ่านง่ายและ Revert ทีละเรื่องได้

2. git merge กับ git rebase ต่างกันอย่างไร และเมื่อไรห้ามใช้ rebase (Junior ถึง Mid)

คำตอบตัวอย่าง: ทั้งสองคำสั่งใช้รวมงานจากอีก Branch เข้ามา แต่เก็บประวัติต่างกัน

  • merge: ไม่แก้ Commit เดิม ถ้า Branch แยกกันจะสร้าง Merge commit ที่มี 2 Parent ประวัติเป็นความจริงทุกอย่างแต่กราฟอาจซับซ้อน ถ้า Branch ปลายทางไม่มี Commit ใหม่จะเป็น Fast-forward คือแค่เลื่อน Pointer
  • rebase: นำ Commit ของเราไปเล่นซ้ำบน Base ใหม่ ได้ประวัติเป็นเส้นตรงอ่านง่าย แต่ทุก Commit ที่ถูกย้ายได้ Hash ใหม่ คือกลายเป็น Commit ใหม่

กฎทอง: ห้าม Rebase Commit ที่คนอื่นมีแล้ว เช่น Commit ที่ Push ขึ้น main เพราะเพื่อนร่วมทีมยังอ้างอิง Hash เดิม เมื่อเขา Pull จะเกิดประวัติซ้ำซ้อนหรือ Conflict ที่ไม่ควรเกิด ผมใช้ git rebase main หรือ git rebase -i เก็บกวาด Commit เฉพาะบน Feature branch ของตัวเองก่อนเปิด PR และถ้า Branch นั้น Push ไปแล้วจะใช้ git push --force-with-lease ซึ่งปลอดภัยกว่า --force เพราะจะไม่ยอมเขียนทับถ้ามีคนอื่น Push Commit ใหม่เข้ามา

จุดที่ทำให้คำตอบโดดเด่น: พูดถึงวิธี Merge บน GitHub 3 แบบ (Merge commit, Squash and merge, Rebase and merge) และบอกว่าทีมควรเลือกแบบเดียวให้ตรงกัน เช่น ใน Portfolio ผมใช้ Merge commit เพื่อให้กราฟเห็นว่างานแต่ละชิ้นมาจาก PR ไหน

3. ถ้า Push ไฟล์ที่มี API Key ขึ้น GitHub โดยไม่ตั้งใจ คุณจะทำอะไรบ้าง (Junior ถึง Mid)

คำตอบตัวอย่าง: ผมถือว่า Key นั้นรั่วแล้วทันที เพราะ Bot สแกน Public repository ตลอดเวลา และแม้จะลบในภายหลัง Key ยังอยู่ในประวัติและอาจมีคน Clone หรือ Fork ไปแล้ว ลำดับที่ผมทำคือ

  1. Revoke หรือ Rotate Key ก่อนเป็นอันดับแรก ที่ผู้ให้บริการ แล้วออก Key ใหม่ นี่คือขั้นที่หยุดความเสียหายได้จริง
  2. ตรวจ Log การใช้งาน ของ Key ว่ามีการเรียกใช้ผิดปกติหรือค่าใช้จ่ายแปลก ๆ หรือไม่ และแจ้งหัวหน้าหรือทีม Security
  3. ลบออกจากประวัติ ด้วย git filter-repo --invert-paths --path .env แล้ว Force push และขอให้ทีม Clone ใหม่ การลบไฟล์ใน Commit ใหม่อย่างเดียวไม่พอ เพราะ Commit เก่ายังมี Key
  4. ป้องกันไม่ให้เกิดซ้ำ: ใส่ .env ใน .gitignore, Commit .env.example ที่ไม่มีค่าจริงแทน, ใช้ GitHub Secrets ใน Actions และเปิด Secret scanning กับ Push protection ของ GitHub ซึ่งจะบล็อก Push ที่มีรูปแบบของ Secret ที่รู้จัก

จุดที่ทำให้คำตอบโดดเด่น: เน้นว่าการ Rotate Key สำคัญกว่าการแก้ประวัติ Git และไม่ปิดบังเหตุการณ์ การรีบแจ้งทีมแสดงถึงความรับผิดชอบที่บริษัทต้องการ

4. เล่าขั้นตอนตั้งแต่ได้รับงานจนงานขึ้น Production ผ่าน Pull Request (Mid)

คำตอบตัวอย่าง: ผมใช้ GitHub flow ซึ่งมี main ที่พร้อม Deploy เสมอ และงานทุกชิ้นอยู่บน Branch สั้น ๆ

  1. รับ Issue ย้ายการ์ดไป In Progress แล้ว git switch main, git pull และ git switch -c feature/ชื่องาน จาก main ล่าสุด
  2. Commit ทีละเรื่องด้วย Conventional Commits และรันการตรวจชุดเดียวกับ CI ในเครื่องก่อน Push
  3. git push -u origin feature/ชื่องาน แล้วเปิด PR ที่บอกว่าทำอะไร ทำไม ทดสอบอย่างไร พร้อม Closes #N และภาพหน้าจอถ้าเป็นงาน UI
  4. CI รันอัตโนมัติ ถ้าแดงก็อ่าน Log แล้วแก้ด้วย Commit เพิ่มใน Branch เดิม Reviewer ให้ความเห็น ผมตอบทุกความเห็นและ Push การแก้
  5. เมื่อ Check ผ่านและได้ Approve ตาม Ruleset จึง Merge ลบ Branch และ Workflow ของ CD Deploy main ขึ้นระบบ จากนั้นตรวจระบบจริงอีกครั้ง

ใน Portfolio ผมจงใจเปิด PR ที่มีลิงก์ไปยัง resume.pdf ซึ่งไม่มีอยู่ CI ขึ้นสีแดงเพราะ linkinator เจอ [404] resume.pdf และ Ruleset ทำให้กด Merge ไม่ได้ ผมแก้ใน Branch เดิมจน Check เขียวแล้วจึง Merge และ pages.yml Deploy ขึ้น GitHub Pages ให้เอง

จุดที่ทำให้คำตอบโดดเด่น: พูดถึงการป้องกัน main (ต้องผ่าน PR, Required status checks, ห้าม Force push) และ Code review etiquette เช่น วิจารณ์ที่โค้ดไม่ใช่ที่คน ใช้คำถามแทนคำสั่ง และใส่ nit: กับความเห็นเล็กน้อยที่ไม่บังคับแก้

5. git reset, git revert และ git restore ต่างกันอย่างไร ถ้าเผลอ reset --hard จะกู้คืนได้ไหม (Mid)

คำตอบตัวอย่าง: ทั้งสามคำสั่งใช้ "ย้อน" แต่ย้อนคนละระดับ

  • git restore: ทำงานระดับไฟล์ git restore ไฟล์ ทิ้งการแก้ใน Working Tree ส่วน git restore --staged ไฟล์ แค่นำออกจาก Staging ไม่แตะประวัติ
  • git revert: สร้าง Commit ใหม่ที่กลับผลของ Commit เดิม ประวัติเดิมไม่หาย จึงเป็นวิธีที่ถูกต้องสำหรับ Commit ที่ Push หรือแชร์แล้ว
  • git reset: ย้าย Branch pointer ถอยกลับ --soft เก็บการแก้ไว้ใน Staging, --mixed (ค่าเริ่มต้น) เก็บไว้ใน Working Tree และ --hard ทิ้งทั้งหมด ใช้กับ Commit ที่ยังอยู่แค่ในเครื่องเท่านั้น

ถ้าเผลอ git reset --hard Commit ที่เคยมียังกู้ได้ ด้วย git reflog ซึ่งบันทึกทุกตำแหน่งที่ HEAD เคยอยู่ (เก็บไว้ประมาณ 90 วันโดยค่าเริ่มต้น) เช่น

# ดูตำแหน่งก่อนหน้าของ HEAD
git reflog -n 5
# กลับไปตำแหน่งก่อน reset (หรือสร้าง Branch กู้ภัยจากตำแหน่งนั้น)
git reset --hard HEAD@{1}
git branch rescue HEAD@{1}

แต่การแก้ที่ไม่เคย Commit หรือ Stash ไม่อยู่ใน Reflog จึงหายถาวร นี่คือเหตุผลที่ผม Commit บ่อย ๆ บน Feature branch และตรวจ git status ก่อนใช้คำสั่งที่ทิ้งข้อมูลทุกครั้ง

จุดที่ทำให้คำตอบโดดเด่น: สรุปเป็นกฎง่าย ๆ ว่า "ยังไม่ Push ใช้ reset หรือ amend ได้ Push แล้วใช้ revert" และบอกข้อจำกัดของ Reflog อย่างตรงไปตรงมา

แหล่งเรียนต่อ

  • Git Documentation – เอกสารทางการของ Git มี Reference ของทุกคำสั่งและวิดีโอแนะนำพื้นฐาน ใช้เปิดดูตัวเลือกของคำสั่งที่ไม่แน่ใจ ฟรี
  • Pro Git (Scott Chacon และ Ben Straub) – หนังสือ Git ฉบับเต็มที่อ่านออนไลน์ได้ฟรี อธิบายตั้งแต่พื้นฐานจนถึงการทำงานภายในของ Git เหมาะอ่านบทที่ 3 (Branching) และบทที่ 7 (Git Tools) หลังจบหัวข้อนี้ ฟรี
  • Learn Git Branching – เกมฝึก Branch, Merge, Rebase และ Cherry-pick แบบเห็นภาพกราฟใน Browser เหมาะทบทวนแนวคิดที่ 5 และ 9 ฟรี
  • GitHub Docs – เอกสารทางการของ GitHub ครอบคลุม Pull Request, Issues, Projects, Rulesets และ Secret scanning ฟรี
  • GitHub Actions Documentation – ไวยากรณ์ Workflow, Event ทุกแบบ, Secrets และตัวอย่าง CI สำหรับภาษาต่าง ๆ ใช้ต่อยอด ci.yml ในหัวข้อ Backend () ฟรี
  • GitHub Pages Documentation – การตั้งค่า Pages, Custom domain, HTTPS และการ Deploy ด้วย GitHub Actions ฟรี
  • GitHub CLI Manual – คู่มือทุกคำสั่งของ gh เช่น gh pr, gh issue และ gh release ฟรี
  • Conventional Commits 1.0.0 – ข้อกำหนดการเขียน Commit message ที่ใช้ตลอดหัวข้อนี้ พร้อมตัวอย่างและคำถามที่พบบ่อย ฟรี
  • Semantic Versioning 2.0.0 – กติกาการตั้งเลขเวอร์ชัน MAJOR.MINOR.PATCH ที่ใช้กับ Tag และ Release ฟรี
  • Choose a License – เว็บของ GitHub ที่ช่วยเลือก Open source license ให้เหมาะกับโปรเจกต์ เปรียบเทียบ MIT, Apache 2.0 และ GPL ได้ง่าย ฟรี
  • GitHub Foundations (GH-900) บน Microsoft Learn – หน้าข้อมูลใบรับรองพื้นฐานของ GitHub พร้อมเส้นทางเรียนฟรีบน Microsoft Learn ส่วนการสอบมีค่าใช้จ่าย ใบรับรองระดับถัดไปคือ GH-200 Actions, GH-300 Copilot, GH-500 Advanced Security และ GH-100 Administration ตรวจราคาและรายละเอียดล่าสุดในหน้านี้ก่อนสมัคร มีค่าใช้จ่าย
