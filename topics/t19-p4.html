Mini Project: Server Health Monitor

เป้าหมาย

สร้างเครื่องมือชื่อ Server Health Monitor สำหรับ Ubuntu 24.04 บน WSL2 ที่วัดค่า CPU, RAM, Disk และ Load average ของเครื่อง เทียบกับเกณฑ์ในไฟล์ Config แล้วเขียนผลลงไฟล์ Log วันละหลายร้อยบรรทัดโดยไม่ต้องมีคนกดรัน เมื่อค่าไหนเกินเกณฑ์ สคริปต์จะคืน Exit code ที่บอกระดับความรุนแรง เหมือนที่ระบบ Monitoring จริงอย่าง Nagios ใช้

งานนี้คืองานประจำวันของ System Administrator, DevOps Engineer และ Site Reliability Engineer (SRE) ในย่อส่วน เมื่อทำเสร็จ คุณจะมี Repository บน GitHub ที่แสดงว่าคุณเขียน Bash ที่เชื่อถือได้ (Strict mode, getopts, Function, Lock), ตั้ง Cron job ได้, จัดการ Log ด้วย logrotate ได้, อ่านข้อมูลระบบจาก /proc ได้ และเขียนชุดทดสอบอัตโนมัติที่ผ่าน ShellCheck ทุกไฟล์

ฟีเจอร์ทั้งหมด

  • วัด 4 ค่า: CPU % (อ่าน /proc/stat สองครั้งห่างกัน 1 วินาที), RAM % (จาก /proc/meminfo), Disk % (จาก df -P) และ Load average 1 นาที (จาก /proc/loadavg)
  • เกณฑ์อยู่ในไฟล์ Config config/health.conf แยกจากโค้ด แก้เกณฑ์ได้โดยไม่ต้องแตะสคริปต์ และสคริปต์ตรวจว่าทุกค่าเป็นจำนวนเต็มก่อนใช้
  • สถานะ 3 ระดับ OK / WARN / CRIT ต่อค่า และสถานะรวมที่ใช้ค่าที่แย่ที่สุด
  • Log หนึ่งบรรทัดต่อการรันหนึ่งครั้ง ในรูปแบบ key=value ที่ใช้ grep และ awk ค้นต่อได้ทันที
  • Exit code แบบ Nagios: 0 = OK, 1 = WARN, 2 = CRIT, 3 = UNKNOWN
  • ตัวเลือกด้วย getopts: -c FILE เลือก Config, -q โหมดเงียบสำหรับ cron, -h แสดงวิธีใช้
  • กันการรันซ้อนด้วย flock: ถ้ารอบก่อนยังไม่จบ รอบใหม่จะจบทันทีด้วย Exit code 3
  • สคริปต์สรุปรายงาน bin/health-report.sh นับจำนวนครั้งที่ตรวจ นับตามสถานะ และหาค่าเฉลี่ยกับค่าสูงสุด
  • รันเองทุก 5 นาที ด้วย cron และ หมุนไฟล์ Log ทุกวัน ด้วย logrotate แบบระดับผู้ใช้ (ไม่ต้องใช้ root)
  • ชุดทดสอบอัตโนมัติ tests/run-tests.sh 9 ข้อ รวมการตรวจด้วย ShellCheck

เปรียบเทียบ

Server Health Monitor คือพยาบาลที่เดินมาวัดสัญญาณชีพผู้ป่วยทุก 5 นาที วัดชีพจร (CPU) ความดัน (RAM) อุณหภูมิ (Disk) แล้วจดลงแฟ้มประจำเตียง (Log) ถ้าค่าไหนเกินเกณฑ์ที่หมอเขียนไว้ (Config) ก็ติดป้ายเหลืองหรือแดง (WARN/CRIT) และทุกเที่ยงคืนจะย้ายแฟ้มเก่าไปเก็บในตู้ (logrotate) เพื่อไม่ให้แฟ้มหนาเกินไป

ระวัง

cron บน WSL ทำงานเฉพาะตอนที่ WSL เปิดอยู่เท่านั้น ถ้าปิดหน้าต่าง Terminal ทั้งหมดแล้ว WSL หยุดเอง (ประมาณ 8 วินาทีหลังไม่มีโปรเซสค้าง) Cron job ก็จะไม่รัน ผลคือใน Log จะมีช่วงเวลาที่ขาดหายไป ซึ่งเป็นเรื่องปกติของ WSL ไม่ใช่ความผิดของสคริปต์ บน Server จริงที่เปิด 24 ชั่วโมงจะไม่เจอปัญหานี้

หมายเหตุ

โปรเจกต์นี้ใช้ความรู้จากส่วนที่ 2 แทบทุกแนวคิด โดยเฉพาะแนวคิดที่ 4 (Permissions), 6 (Redirection), 7 (awk), 9 (Signals), 10 (systemd) และ 12 (Bash Scripting กับ cron) ถ้าตรงไหนไม่แน่ใจ ให้ย้อนกลับไปอ่านแนวคิดนั้นก่อน ส่วนการ Push ขึ้น GitHub ใช้ความรู้จากหัวข้อ

    นี่คือหัวใจของโปรเจกต์ สคริปต์แบ่งเป็น Function ย่อยที่ทำหน้าที่เดียว (อ่านค่า, จัดระดับ, เขียน Log) และมี main เป็นตัวคุมลำดับ วิธีนี้ทำให้อ่านง่าย ทดสอบง่าย และแก้ทีละส่วนได้ สร้างไฟล์ด้วย nano bin/health-check.sh แล้ววางโค้ดทั้งหมดนี้

    #!/usr/bin/env bash
# health-check.sh : ตรวจสุขภาพเครื่อง (CPU, RAM, Disk, Load average)
# เทียบกับเกณฑ์ใน config แล้วเขียน Log หนึ่งบรรทัดต่อการรันหนึ่งครั้ง
# Exit code: 0=OK 1=WARN 2=CRIT 3=UNKNOWN
set -euo pipefail

readonly EXIT_UNKNOWN=3

# หาโฟลเดอร์โปรเจกต์จากตำแหน่งของสคริปต์เอง (bin/..) จึงรันจากที่ไหนก็ได้
PROJECT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
readonly PROJECT_DIR

CONFIG_FILE="$PROJECT_DIR/config/health.conf"
QUIET=0

usage() {
  cat <<'USAGE'
Usage: health-check.sh [-c CONFIG] [-q] [-h]
  -c CONFIG  path to config file (default: <project>/config/health.conf)
  -q         quiet mode: write the log line only, print nothing on stdout
  -h         show this help
Exit codes: 0=OK  1=WARN  2=CRIT  3=UNKNOWN
USAGE
}

# พิมพ์ข้อความผิดพลาดไปที่ stderr แล้วจบด้วย exit 3 (UNKNOWN)
die() {
  echo "health-check: $*" >&2
  exit "$EXIT_UNKNOWN"
}

# โหลด config และตรวจว่าเกณฑ์ทุกตัวเป็นจำนวนเต็ม
load_config() {
  [[ -f "$CONFIG_FILE" ]] || die "ไม่พบไฟล์ config: $CONFIG_FILE"
  # shellcheck source=/dev/null
  source "$CONFIG_FILE"

  local name value
  for name in CPU_WARN CPU_CRIT MEM_WARN MEM_CRIT DISK_WARN DISK_CRIT; do
    value="${!name:-}"
    [[ "$value" =~ ^[0-9]+$ ]] || die "ค่า $name ต้องเป็นจำนวนเต็ม (ตอนนี้คือ '$value')"
  done

  # ค่าเริ่มต้นเมื่อ config ไม่ได้กำหนดไว้
  DISK_PATH="${DISK_PATH:-/}"
  LOG_FILE="${LOG_FILE:-$PROJECT_DIR/logs/health.log}"
  [[ -e "$DISK_PATH" ]] || die "ไม่พบ DISK_PATH: $DISK_PATH"
}

# กันไม่ให้รันซ้อนกัน (เช่น cron รอบใหม่มาถึงตอนรอบเก่ายังไม่จบ)
acquire_lock() {
  local log_dir
  log_dir="$(dirname "$LOG_FILE")"
  mkdir -p "$log_dir"
  exec 9>"$log_dir/.lock"
  flock -n 9 || die "มีการตรวจอีกตัวกำลังทำงานอยู่ (lock: $log_dir/.lock)"
}

# CPU %: อ่านบรรทัดแรกของ /proc/stat สองครั้งห่างกัน 1 วินาที แล้วคำนวณส่วนต่าง
read_cpu() {
  local _ user nice system idle iowait irq softirq steal
  local total1 idle1 total2 idle2 dtotal didle

  read -r _ user nice system idle iowait irq softirq steal _ < /proc/stat
  total1=$((user + nice + system + idle + iowait + irq + softirq + steal))
  idle1=$((idle + iowait))

  sleep 1

  read -r _ user nice system idle iowait irq softirq steal _ < /proc/stat
  total2=$((user + nice + system + idle + iowait + irq + softirq + steal))
  idle2=$((idle + iowait))

  dtotal=$((total2 - total1))
  didle=$((idle2 - idle1))
  if (( dtotal <= 0 )); then
    echo 0
  else
    echo $(( 100 * (dtotal - didle) / dtotal ))
  fi
}

# RAM %: (MemTotal - MemAvailable) / MemTotal จาก /proc/meminfo
read_mem() {
  awk '/^MemTotal:/ {t = $2}
       /^MemAvailable:/ {a = $2}
       END { if (t > 0) printf "%d\n", (t - a) * 100 / t; else print 0 }' /proc/meminfo
}

# Disk %: คอลัมน์ที่ 5 ของ df -P (ตัดเครื่องหมาย % ออก)
read_disk() {
  df -P "$DISK_PATH" | awk 'NR == 2 {gsub("%", "", $5); print $5}'
}

# Load average 1 นาที: ช่องแรกของ /proc/loadavg
read_load() {
  local load1 _
  read -r load1 _ < /proc/loadavg
  echo "$load1"
}

# จัดระดับ: classify <ค่า> <เกณฑ์ WARN> <เกณฑ์ CRIT>
classify() {
  local value=$1 warn=$2 crit=$3
  if (( value >= crit )); then
    echo CRIT
  elif (( value >= warn )); then
    echo WARN
  else
    echo OK
  fi
}

# แปลงสถานะเป็นตัวเลข เพื่อหาว่าตัวไหนแย่ที่สุด
rank() {
  case $1 in
    OK) echo 0 ;;
    WARN) echo 1 ;;
    CRIT) echo 2 ;;
    *) echo 3 ;;
  esac
}

# ต่อท้าย Log หนึ่งบรรทัด
write_log() {
  echo "$1" >> "$LOG_FILE"
}

main() {
  local opt
  while getopts ":c:qh" opt; do
    case $opt in
      c) CONFIG_FILE=$OPTARG ;;
      q) QUIET=1 ;;
      h) usage; exit 0 ;;
      :) usage >&2; die "ตัวเลือก -$OPTARG ต้องมีค่าตามหลัง" ;;
      \?) usage >&2; die "ไม่รู้จักตัวเลือก -$OPTARG" ;;
    esac
  done

  load_config
  acquire_lock

  local cpu mem disk load1 cpu_s mem_s disk_s overall s line
  cpu="$(read_cpu)"
  mem="$(read_mem)"
  disk="$(read_disk)"
  load1="$(read_load)"

  cpu_s="$(classify "$cpu" "$CPU_WARN" "$CPU_CRIT")"
  mem_s="$(classify "$mem" "$MEM_WARN" "$MEM_CRIT")"
  disk_s="$(classify "$disk" "$DISK_WARN" "$DISK_CRIT")"

  # สถานะรวม: ตัวที่แย่ที่สุดชนะ
  overall=OK
  for s in "$cpu_s" "$mem_s" "$disk_s"; do
    if (( $(rank "$s") > $(rank "$overall") )); then
      overall=$s
    fi
  done

  line="$(date '+%Y-%m-%dT%H:%M:%S%z') host=$(hostname) status=$overall cpu=$cpu mem=$mem disk=$disk load1=$load1"

    printf '%-6s %s\n' LOAD1 "$load1"
    echo "STATUS: $overall"
    echo "log -> $LOG_FILE"
  fi

  return "$(rank "$overall")"
}

  6. Step 6: เขียนชุดทดสอบอัตโนมัติ tests/run-tests.sh

    ชุดทดสอบทำให้คุณแก้โค้ดได้อย่างมั่นใจ ถ้าแก้แล้วพัง การทดสอบจะบอกทันที สคริปต์นี้ทดสอบ 9 เรื่อง ใช้ mktemp -d สร้างโฟลเดอร์ชั่วคราวสำหรับ Config และ Log ทดสอบ (จึงไม่ปน Log จริง) และใช้ trap ... EXIT ลบโฟลเดอร์นั้นเสมอไม่ว่าจะจบแบบไหน

else

fi

# 4) -q ต้องไม่พิมพ์อะไรออก stdout

if [[ -z $out ]]; then

else
  fail "quiet mode printed: $out"
fi

# 5) เกณฑ์เป็น 0 ทั้งหมด ต้องได้ CRIT (exit 2)

rc=$?
if [[ $rc -eq 2 ]]; then
  pass "zero thresholds give CRIT (exit 2)"
else
  fail "zero thresholds gave exit $rc (expected 2)"
fi

# 6) ไม่มีไฟล์ config ต้องได้ UNKNOWN (exit 3)
"$CHECK" -q -c "$TMP_DIR/missing.conf" 2>/dev/null
rc=$?
if [[ $rc -eq 3 ]]; then
  pass "missing config gives UNKNOWN (exit 3)"
else
  fail "missing config gave exit $rc (expected 3)"
fi

# 7) ค่าใน config ไม่ใช่ตัวเลข ต้องได้ UNKNOWN (exit 3)
"$CHECK" -q -c "$BAD_CONF" 2>/dev/null
rc=$?

  pass "invalid threshold gives UNKNOWN (exit 3)"
else
  fail "invalid threshold gave exit $rc (expected 3)"
fi

# 8) ถ้ามีอีกตัวถือ lock อยู่ ต้องได้ UNKNOWN (exit 3)
flock "$TMP_DIR/.lock" sleep 3 &
holder=$!
sleep 0.5
"$CHECK" -q -c "$NORMAL_CONF" 2>/dev/null
rc=$?
wait "$holder"
if [[ $rc -eq 3 ]]; then
  pass "second run while locked gives UNKNOWN (exit 3)"
else
  fail "second run while locked gave exit $rc (expected 3)"
fi

if "$REPORT" "$TMP_DIR/health.log" | grep -q '^checks'; then
  pass "health-report prints the checks line"
else
  fail "health-report did not print the checks line"
fi

echo "----"
echo "Result: $PASS passed, $FAIL failed"
if (( FAIL > 0 )); then
  exit 1
fi

  7. Step 7: ตั้งเวลาให้รันทุก 5 นาทีด้วย cron

    เก็บบรรทัด cron ไว้ในไฟล์ของโปรเจกต์ เพื่อให้ติดตั้งซ้ำบนเครื่องใหม่ได้และมีประวัติใน Git ทุก Path ใน cron ต้องเป็น Absolute path เพราะ cron รันด้วย PATH ที่สั้นมาก (/usr/bin:/bin) และไม่ได้อ่าน ~/.bashrc

  8. Step 8: หมุนไฟล์ Log ทุกวันด้วย logrotate (ไม่ต้องใช้ root)

    ถ้ารันทุก 5 นาที Log จะเพิ่มวันละ 288 บรรทัด ปีละกว่าแสนบรรทัด logrotate แก้ปัญหานี้ด้วยการเปลี่ยนชื่อไฟล์เก่าตามวันที่ บีบอัด และลบไฟล์ที่เก่ากว่าที่กำหนด ปกติ logrotate ของระบบรันด้วย root จาก /etc/logrotate.d/ แต่เราใช้ Config ของเราเองกับ State file ของเราเอง จึงไม่ต้องแตะไฟล์ระบบ

    # logrotate config ระดับผู้ใช้ (ไม่ต้องใช้ root) ต้องรันพร้อม -s <state file>
/home/somchai/projects/server-health-monitor/logs/health.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    dateext
    create 0640
}
    คำสั่งใน Configความหมาย
    dailyหมุนวันละครั้ง (เมื่อรันแล้วพบว่าผ่านมาครบวัน)
    rotate 7เก็บไฟล์เก่าไว้ 7 ชุด ชุดที่ 8 จะถูกลบ
    compress + delaycompressบีบอัดด้วย gzip แต่เว้นไฟล์ล่าสุดไว้หนึ่งรอบ ไฟล์ของเมื่อวานจึงยังเปิดอ่านด้วย less ได้ตรง ๆ
    missingokถ้ายังไม่มีไฟล์ Log ก็ไม่ต้องแจ้ง Error
    notifemptyไม่หมุนไฟล์ว่าง
    dateextต่อท้ายชื่อด้วยวันที่ เช่น health.log-20261020 แทนเลข .1 .2 ทำให้รู้ทันทีว่าเป็นของวันไหน
    create 0640สร้างไฟล์ใหม่ว่างหลังหมุน ให้เจ้าของอ่านเขียนได้ กลุ่มอ่านได้ คนอื่นไม่มีสิทธิ์

    # Server Health Monitor

Bash tool that checks CPU, RAM, Disk and load average on Ubuntu, logs one line per run, and alerts with Nagios-style exit codes. Runs every 5 minutes with cron and rotates its own logs with logrotate (no root needed).

## Features

- CPU % from `/proc/stat` (two samples, 1 second apart)
- RAM % from `/proc/meminfo` (MemTotal - MemAvailable)
- Disk % from `df -P`, load average from `/proc/loadavg`
- Thresholds in `config/health.conf` (WARN / CRIT per metric)
- One `key=value` log line per run, easy to parse with awk or grep
- Exit codes: 0 OK, 1 WARN, 2 CRIT, 3 UNKNOWN
- `flock` lock: overlapping runs exit 3 instead of running twice
- `bin/health-report.sh`: summary of the log (counts, average, max)
- Automated tests in `tests/run-tests.sh`; every script passes ShellCheck

## Requirements

- Ubuntu 24.04 LTS on WSL2 (or any Linux with systemd)
- bash 5.2, coreutils, mawk or gawk, util-linux (`flock`)
- cron, logrotate, shellcheck (for tests)

```bash
sudo apt update && sudo apt install -y cron logrotate shellcheck
```

## Usage

```bash

```

| Exit code | Status  | Meaning                              |
|-----------|---------|--------------------------------------|
| 0         | OK      | all metrics below WARN               |
| 1         | WARN    | at least one metric >= WARN          |
| 2         | CRIT    | at least one metric >= CRIT          |
| 3         | UNKNOWN | bad option, missing or invalid config, or another run holds the lock |

Interview Questions

คำถามด้านล่างพบบ่อยในการสัมภาษณ์ตำแหน่ง Junior System Administrator, DevOps Engineer และ Backend Developer ที่ต้องดูแล Server เอง ข้อ 1–2 เป็นระดับ Junior ข้อ 3–5 เป็นระดับ Mid-level ลองตอบด้วยตัวเองก่อนเปิดดูคำตอบตัวอย่าง และฝึกพูดออกเสียง เพราะผู้สัมภาษณ์ดูทั้งความรู้และวิธีคิดเป็นขั้นตอน

1. สิทธิ์ 755 กับ 644 ต่างกันอย่างไร และทำไม Private key ของ SSH ต้องเป็น 600 (Junior)

คำตอบที่ดี: ตัวเลขสามหลักคือสิทธิ์ของ เจ้าของ / กลุ่ม / คนอื่น ตามลำดับ แต่ละหลักเป็นผลบวกของ r=4, w=2, x=1

  • 755 = rwxr-xr-x เจ้าของอ่าน เขียน รันได้ คนอื่นอ่านและรันได้ ใช้กับสคริปต์และโฟลเดอร์
  • 644 = rw-r--r-- เจ้าของอ่านเขียนได้ คนอื่นอ่านอย่างเดียว ใช้กับไฟล์ข้อมูลและ Config ทั่วไป
  • 600 = rw------- เฉพาะเจ้าของเท่านั้น

จุดที่ควรพูดเพิ่มเพื่อแสดงความเข้าใจลึก: บนโฟลเดอร์ x หมายถึง "เข้าไปได้" (cd และเข้าถึงไฟล์ข้างใน) ส่วน r หมายถึง "ดูรายชื่อไฟล์" ได้ ดังนั้นโฟลเดอร์ที่มี r แต่ไม่มี x จะเห็นชื่อไฟล์แต่เปิดไฟล์ไม่ได้

Private key ต้องเป็น 600 เพราะใครอ่านไฟล์นี้ได้ก็สวมรอยเป็นเราได้ และ OpenSSH ตรวจเรื่องนี้เองด้วย ถ้าสิทธิ์กว้างเกินจะปฏิเสธไม่ใช้กุญแจพร้อมข้อความ WARNING: UNPROTECTED PRIVATE KEY FILE! และ Permissions 0644 for '...' are too open. ส่วนโฟลเดอร์ ~/.ssh ควรเป็น 700

ปิดท้ายด้วยหลักการ: ให้สิทธิ์น้อยที่สุดที่งานต้องใช้ (Principle of Least Privilege) และไม่ใช้ chmod 777 แก้ปัญหา Permission denied เพราะเท่ากับให้ทุกคนแก้ไขไฟล์ได้

2. โปรแกรมค้างไม่ตอบสนอง คุณจะหยุดมันอย่างไร และ SIGTERM ต่างจาก SIGKILL อย่างไร (Junior)

คำตอบที่ดี: ทำเป็นลำดับขั้น ไม่กระโดดไปใช้ kill -9 ทันที

  1. หา PID ก่อน ด้วย pgrep -af ชื่อโปรแกรม หรือ ps aux | grep ชื่อ และยืนยันว่าเป็นตัวที่ถูกต้อง
  2. ส่ง kill PID ซึ่งคือ SIGTERM (15) เป็นการขอให้ปิด โปรแกรมดักสัญญาณนี้ได้ จึงมีโอกาสบันทึกข้อมูล ปิดการเชื่อมต่อ และลบไฟล์ชั่วคราว (ใน Bash ใช้ trap '...' TERM)
  3. รอสักครู่แล้วตรวจด้วย ps -p PID ถ้ายังอยู่จึงใช้ kill -9 PID ซึ่งคือ SIGKILL (9) Kernel หยุดโปรเซสทันที โปรแกรมดักหรือปฏิเสธไม่ได้ จึงไม่มีโอกาสเก็บกวาด อาจทิ้งไฟล์ Lock หรือข้อมูลที่เขียนไม่ครบไว้

ถ้าเป็น Service ที่ systemd ดูแล ควรใช้ sudo systemctl stop ชื่อ หรือ restart แทน เพราะ systemd ส่ง SIGTERM ก่อนแล้วจึงส่ง SIGKILL ให้เองเมื่อหมดเวลารอ และไม่สับสนกับการ Restart อัตโนมัติ จุดเสริมที่ดี: Ctrl+C คือ SIGINT (2) และโปรเซสในสถานะ D (รอ I/O) อาจไม่ตายแม้ใช้ SIGKILL จนกว่า I/O จะจบ

3. ได้รับแจ้งว่าดิสก์ของ Server เต็ม 100% คุณจะไล่หาสาเหตุและแก้อย่างไร (Mid-level)

คำตอบที่ดี: อธิบายเป็นขั้นตอนจากภาพกว้างไปหาจุดเล็ก และแยกการแก้เฉพาะหน้ากับการป้องกันระยะยาว

  1. ยืนยันปัญหา: df -h ดูว่า Filesystem ไหนเต็ม และ df -i ดูว่าเต็มเพราะ Inode หมด (ไฟล์เล็กจำนวนมาก) หรือเปล่า
  2. หาโฟลเดอร์ที่ใหญ่: sudo du -xh --max-depth=1 / | sort -h แล้วไล่ลงไปทีละชั้น (-x ไม่ข้ามไป Filesystem อื่น) จุดที่พบบ่อยคือ /var/log, /var/lib/docker, /tmp และโฟลเดอร์ Backup
  3. หาไฟล์ใหญ่: sudo find /var -xdev -type f -size +500M -exec ls -lh {} \;
  4. กรณีลบแล้วพื้นที่ไม่คืน: ไฟล์ที่ถูกลบแต่โปรเซสยังเปิดค้างอยู่จะยังกินพื้นที่ ตรวจด้วย sudo lsof +L1 แล้ว Restart Service นั้น
  5. แก้เฉพาะหน้าอย่างปลอดภัย: ลด Log ของ systemd ด้วย sudo journalctl --vacuum-size=200M, ล้าง Cache ของ apt ด้วย sudo apt clean และถ้าต้องล้างไฟล์ Log ที่ Service เปิดอยู่ ให้ใช้ truncate -s 0 file แทน rm
  6. ป้องกันไม่ให้เกิดซ้ำ: ตั้ง logrotate ให้ทุก Log, ตั้งการแจ้งเตือนดิสก์ที่ 80% และ 90% ก่อนเต็ม และเก็บ Backup ไว้นอกเครื่อง

ตัวอย่างที่ยกได้: "ใน Mini Project ผมเขียน Server Health Monitor ที่วัด Disk ด้วย df -P แล้วแจ้ง WARN ที่ 80% และ CRIT ที่ 90% พร้อมใช้ logrotate หมุน Log ของตัวเองทุกวัน เพราะ Log ที่ไม่ถูกหมุนเป็นสาเหตุดิสก์เต็มที่พบบ่อยที่สุด"

4. Load average คืออะไร ต่างจาก CPU % อย่างไร และถ้าเครื่อง 4 คอร์มี Load 6.0 แปลว่าอะไร (Mid-level)

คำตอบที่ดี: Load average คือค่าเฉลี่ยจำนวนงานที่กำลังใช้ CPU หรือรอคิว CPU อยู่ (บน Linux นับรวมงานที่รอ Disk I/O ในสถานะ D ด้วย) แสดง 3 ค่าคือเฉลี่ย 1, 5 และ 15 นาที ดูได้จาก uptime หรือ /proc/loadavg

  • CPU % บอกว่า CPU ยุ่งกี่เปอร์เซ็นต์ของเวลา ณ ช่วงหนึ่ง เต็มที่ได้แค่ 100%
  • Load บอกความยาวของคิว จึงเกินจำนวนคอร์ได้ และบอกได้ว่างานกำลัง "รอ" อยู่มากแค่ไหน
  • ต้องอ่าน Load เทียบกับจำนวนคอร์เสมอ (nproc) Load 6.0 บน 4 คอร์ หมายถึงโดยเฉลี่ยมีงาน 4 งานใช้ CPU และอีกราว 2 งานรอคิว เครื่องรับงานเกินกำลังประมาณ 50%
  • ดูแนวโน้มจาก 3 ค่า: ถ้า 1 นาทีสูงกว่า 15 นาทีมาก แปลว่าปัญหาเพิ่งเกิดและกำลังแย่ลง
  • ถ้า Load สูงแต่ CPU % ต่ำ ให้สงสัย I/O ช้า (ดิสก์หรือ Network storage) ดูช่อง wa ใน top หรือโปรเซสสถานะ D ใน ps

จุดเสริม: CPU % คำนวณจากส่วนต่างของตัวนับใน /proc/stat สองครั้ง ตามสูตร 100 × (ΔTotal − ΔIdle) ÷ ΔTotal โดยนับ iowait เป็นเวลาว่าง และ RAM ควรดูจาก MemAvailable ไม่ใช่ MemFree เพราะ Linux ใช้ RAM ว่างเป็น Cache ซึ่งคืนได้ทันทีเมื่อโปรแกรมต้องการ

5. สคริปต์รันด้วยมือได้ปกติ แต่พอใส่ใน cron กลับไม่ทำงาน คุณจะ Debug อย่างไร (Mid-level)

คำตอบที่ดี: สาเหตุเกือบทั้งหมดคือ "สภาพแวดล้อมของ cron ไม่เหมือน Terminal ของเรา" ไล่ตรวจตามลำดับนี้

  1. cron ทำงานอยู่ไหม และรันคำสั่งไหม: systemctl status cron แล้วดู journalctl -u cron (หรือ grep CRON /var/log/syslog ถ้ามี rsyslog) ว่ามีบรรทัด CMD (...) ของเรา บน WSL ต้องเปิด WSL ค้างไว้และ cron ต้องถูกสั่ง Start แล้ว
  2. เก็บ Output: ต่อท้ายบรรทัดด้วย >> /path/job.log 2>&1 ข้อความ Error ส่วนใหญ่จะบอกคำตอบเอง
  3. PATH สั้น: cron ใช้ PATH=/usr/bin:/bin คำสั่งใน /usr/sbin หรือ ~/.local/bin จะหาไม่เจอ ใช้ Absolute path หรือกำหนด PATH= ไว้บนสุดของ Crontab
  4. ไม่มีตัวแปรจาก ~/.bashrc: cron ไม่อ่านไฟล์นี้ ตัวแปรอย่าง API key หรือ alias จึงไม่มี ต้องกำหนดในสคริปต์หรือ source ไฟล์ที่ต้องการเอง
  5. Working directory: cron เริ่มที่ $HOME Path แบบ Relative ในสคริปต์จะชี้ผิดที่ แก้ด้วยการหาตำแหน่งจาก ${BASH_SOURCE[0]} แบบใน Mini Project
  6. เครื่องหมาย %: ในบรรทัด Crontab % หมายถึงขึ้นบรรทัดใหม่ ต้องเขียน \% เช่น date +\%F
  7. สิทธิ์และรูปแบบไฟล์: สคริปต์ต้องมี x มี Shebang ถูกต้อง และไม่มี CRLF จาก Windows
  8. จำลองสภาพแวดล้อม cron: env -i HOME="$HOME" PATH=/usr/bin:/bin /path/script.sh ถ้าพังแบบเดียวกัน ก็แก้ได้โดยไม่ต้องรอรอบถัดไป

ปิดท้ายด้วยการป้องกัน: ใส่ flock กันรันซ้อนเมื่องานใช้เวลานานกว่ารอบเวลา และทดสอบด้วยรอบทุกนาทีก่อนเปลี่ยนเป็นรอบจริง

  • The Linux Command Line (William Shotts) – หนังสือ Command line ฉบับเต็มที่ดาวน์โหลดได้ฟรี อธิบายตั้งแต่ ls จนถึงการเขียน Shell script อย่างเป็นระบบ เหมาะอ่านทบทวนส่วนที่ 2 ทั้งหมด ฟรี
  • GNU Bash Reference Manual – เอกสารอ้างอิงทางการของ Bash ใช้เปิดดูรายละเอียดของ Parameter expansion, [[ ]], getopts และ trap ฟรี
  • Linux man-pages (man7.org) – man page ฉบับออนไลน์ที่ค้นได้สะดวก รวมถึง proc(5) ที่อธิบายทุกช่องใน /proc/stat และ /proc/meminfo ที่ใช้ใน Mini Project ฟรี
  • ShellCheck – วางสคริปต์ในเว็บเพื่อตรวจได้ทันที และทุกรหัสคำเตือน (เช่น SC2086) มีหน้าอธิบายว่าผิดเพราะอะไรและแก้อย่างไร ฟรี
  • OverTheWire: Bandit – เกมฝึก Command line ผ่าน SSH ที่ผู้จัดเตรียมเครื่องไว้ให้ฝึกโดยเฉพาะ แต่ละด่านบังคับให้ใช้ find, grep, sort, Permission และ SSH เป็นการทบทวนที่สนุกและถูกกฎหมาย ฟรี
  • roadmap.sh: Linux – แผนที่หัวข้อ Linux แบบภาพรวม ใช้เช็กว่ายังขาดเรื่องไหนหลังจบหัวข้อนี้ ฟรี
  • tldr pages – ตัวอย่างการใช้คำสั่งแบบสั้นที่สุด อ่านบนเว็บได้ หรือใช้คำสั่ง tldr ที่ติดตั้งในส่วนที่ 2 ฟรี
  • Linux Professional Institute (LPI) – ผู้จัดสอบ Linux Essentials (010-200 ออกใหม่ 15 ต.ค. 2026 และ 010-160 สอบได้ถึงเมษายน 2027) และ LPIC-1 ตรวจรหัสข้อสอบและราคาล่าสุดในเว็บก่อนสมัคร มีค่าใช้จ่าย
