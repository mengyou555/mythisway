7.1Learning Roadmap

ภาพรวมเส้นทาง

AI Agent คือโปรแกรมที่ให้ LLM (Large Language Model) อย่าง Claude ตัดสินใจเองว่าจะทำอะไรต่อ เรียกใช้เครื่องมือ (Tools) เช่น ค้นเอกสาร อ่านไฟล์ คำนวณตัวเลข หรือบันทึกโน้ต แล้วนำผลที่ได้กลับมาคิดต่อเป็นรอบๆ จนงานเสร็จ ต่างจากแชตบอตทั่วไปที่ถามหนึ่งครั้งแล้วตอบหนึ่งครั้ง Agent ทำงานหลายขั้นแทนเราได้ เช่น "หายอดขายของสาขาเชียงใหม่จากเอกสารทั้งโฟลเดอร์ คำนวณว่าโตขึ้นกี่เปอร์เซ็นต์ แล้วสรุปเป็นโน้ตให้หน่อย"

หัวข้อนี้เป็นลำดับที่ 15 ของเส้นทางที่แนะนำ และอยู่ในช่วงท้ายของสาย AI เพราะ Agent คือการนำทุกอย่างที่เรียนมารวมกัน คุณต้องเขียน Python คล่อง เข้าใจ Prompt เข้าใจ API และเคยเรียก LLM มาแล้วในหัวข้อ AI Engineer ในหัวข้อนี้คุณจะเริ่มจากเข้าใจว่า Agent ต่างจากการเรียก LLM ครั้งเดียวและจาก Workflow อย่างไร จากนั้นเขียน Agent Loop ด้วยมือตัวเอง ให้เข้าใจทุกบรรทัด แล้วค่อยใช้ตัวช่วยของ SDK ต่อด้วยเรื่องที่ทำให้ Agent ใช้งานจริงได้ คือ Memory, Planning, Guardrails, การป้องกัน Prompt Injection, Trace Log และการวัดผล ปิดท้ายด้วย Multi-agent, MCP และ Mini Project Research Assistant Agent ที่ลง Portfolio ได้

ทุกตัวอย่างในหัวข้อนี้ รันได้โดยไม่ต้องมี API Key เพราะเราจะเขียน Fake Client ที่จำลองคำตอบของ Claude ให้มีรูปร่างเหมือนของจริงทุกอย่าง (ขอใช้ Tool ก่อน แล้วค่อยตอบจบ) ถ้าคุณมี API Key เมื่อไร โค้ดชุดเดียวกันจะสลับไปเรียก Claude จริงให้อัตโนมัติ เส้นทางนี้มี 12 ขั้นใน 3 ระดับ ใช้เวลารวมประมาณ 43–57 ชั่วโมง ถ้าเรียนวันละ 1–1.5 ชั่วโมง สัปดาห์ละ 6 วัน จะจบในราว 7 สัปดาห์

  1. Beginner Step 1 · Agent คืออะไร: Single Call, Workflow และ Agent
  2. Beginner Step 2 · เตรียมโปรเจกต์ agent-lab, API Key และ Mock Mode
  3. Beginner Step 3 · Tool Use พื้นฐาน: นิยาม Tool ด้วย JSON Schema แบบ strict
  4. Beginner Step 4 · Agent Loop แบบเขียนเองและ stop_reason
  5. Intermediate Step 5 · Parallel Tool Calls, Tool Errors และการออกแบบ Tool
  6. Intermediate Step 6 · Tool Runner ของ SDK และ Structured Outputs
  7. Intermediate Step 7 · Memory ระยะสั้นและระยะยาว
  8. Intermediate Step 8 · Planning Patterns: ReAct, Plan-and-Execute และ Reflection
  9. Advanced Step 9 · Guardrails, Human-in-the-loop และการป้องกัน Prompt Injection
  10. Advanced Step 10 · Observability และการประเมินผล Agent
  11. Advanced Step 11 · Multi-agent (Orchestrator-Workers) และ Model Context Protocol (MCP)
  12. Advanced Step 12 · Mini Project: Research Assistant Agent และการใช้งานจริง

IntermediateStep 5–813–17 ชม.รับมือกับการเรียกหลาย Tool พร้อมกันและ Tool ที่ล้มเหลว ใช้ Tool Runner ของ SDK ได้ เก็บสถานะของ Agent ด้วย Structured Outputs มี Memory ทั้งในบทสนทนาและใน SQLite และเลือก Planning Pattern ให้เหมาะกับงาน

เปรียบเทียบ

ถ้า LLM ธรรมดาคือ "ที่ปรึกษาที่ตอบคำถามเก่ง แต่ลุกจากเก้าอี้ไม่ได้" Agent ก็คือการให้ที่ปรึกษาคนนั้นมีผู้ช่วยหนึ่งคน (โปรแกรมของเรา) ที่คอยเดินไปหยิบแฟ้ม เปิดเครื่องคิดเลข หรือจดโน้ตให้ตามที่ที่ปรึกษาสั่ง ที่ปรึกษาสั่งได้ทีละเรื่อง ดูผลแล้วค่อยสั่งเรื่องต่อไป จนได้คำตอบที่ครบ งานของคุณในหัวข้อนี้คือการเขียน "ผู้ช่วย" คนนั้น และวางกฎว่าผู้ช่วยหยิบแฟ้มไหนได้ แฟ้มไหนต้องถามเจ้าของก่อน และต้องหยุดเมื่อไร

AI Agent คืออะไร และคำศัพท์ที่ต้องรู้

คำว่า "Agent" ถูกใช้หลายความหมายในบทความและโฆษณา หลักสูตรนี้ใช้นิยามที่ชัดและตรวจสอบได้ดังนี้: Agent คือระบบที่ LLM เป็นผู้ตัดสินใจเองว่าจะเรียก Tool ตัวไหน ด้วยข้อมูลอะไร กี่ครั้ง และเมื่อไรจึงหยุด โดยทำงานวนเป็นลูปภายใต้ขอบเขตที่โปรแกรมของเรากำหนด ถ้าลำดับขั้นถูกเขียนตายตัวไว้ในโค้ดของเรา สิ่งนั้นคือ Workflow ไม่ใช่ Agent

คำศัพท์ความหมายตัวอย่างในหัวข้อนี้
LLMโมเดลภาษาขนาดใหญ่ที่รับข้อความแล้วสร้างข้อความตอบ ตัวมันเองไม่มีสถานะ (Stateless) คือจำอะไรระหว่างการเรียกไม่ได้ ต้องส่งประวัติทั้งหมดไปทุกครั้งClaude Opus 5.5 รหัสโมเดล claude-opus-5-5
Tool (Function)ฟังก์ชันในโปรแกรมของเราที่บอก LLM ไว้ว่ามีอยู่ พร้อมชื่อ คำอธิบาย และรูปแบบข้อมูลขาเข้า LLM ไม่ได้รัน Tool เอง แค่ "ขอ" ให้โปรแกรมของเรารันให้search_docs, read_doc, calculator, save_note
Tool Useกลไกที่ LLM ตอบกลับมาเป็นบล็อก tool_use (มี id, name, input) แทนข้อความธรรมดา แล้วโปรแกรมของเราส่งผลกลับเป็นบล็อก tool_result ที่อ้าง tool_use_id เดียวกัน{"type": "tool_use", "name": "calculator", "input": {"a": 1410000, "b": 1250000, "op": "sub"}}
JSON Schemaรูปแบบมาตรฐานสำหรับบรรยายหน้าตาของข้อมูล JSON เช่น มี Field อะไร เป็นชนิดไหน Field ไหนบังคับ ใช้บอก LLM ว่า Tool รับข้อมูลแบบไหน"required": ["query"], "additionalProperties": false
Agent Loopลูปที่ส่งข้อความไปหา LLM ถ้า LLM ขอใช้ Tool ก็รัน Tool แล้วส่งผลกลับ วนจน LLM ตอบจบหรือชนเพดานที่เราตั้งไว้ฟังก์ชัน run_agent() ใน Step 4
stop_reasonเหตุผลที่ LLM หยุดสร้างคำตอบในรอบนั้น ค่าที่ต้องจัดการคือ end_turn (ตอบจบ), tool_use (ขอใช้ Tool), max_tokens (คำตอบถูกตัดเพราะยาวเกิน) และ refusal (ปฏิเสธ)if response.stop_reason == "tool_use":
Workflowระบบที่โค้ดของเรากำหนดลำดับขั้นตายตัว LLM ทำงานเฉพาะในแต่ละขั้น เช่น แปล แล้วสรุป แล้วจัดหมวดPrompt Chaining ที่เรียนในหัวข้อ Prompt Engineering
Guardrailกฎและกลไกที่จำกัดสิ่งที่ Agent ทำได้ เช่น จำนวนรอบสูงสุด งบ Token รายชื่อ Tool ที่อนุญาต และโฟลเดอร์ที่อ่านได้MAX_STEPS = 8, ALLOWED_TOOLS
Human-in-the-loopการให้คนอนุมัติก่อน Agent ทำสิ่งที่เปลี่ยนแปลงข้อมูลหรือย้อนกลับไม่ได้ เช่น เขียนไฟล์ ส่งอีเมล ลบข้อมูลsave_note ต้องตอบ y ก่อนจึงเขียนไฟล์
Prompt Injectionการแอบใส่คำสั่งไว้ในข้อมูลที่ Agent อ่าน (เอกสาร หน้าเว็บ อีเมล ผลของ Tool) เพื่อหลอกให้ Agent ทำสิ่งที่เจ้าของไม่ต้องการเอกสาร supplier_email.md ที่เขียนว่า "ignore previous instructions"
Traceบันทึกทุกขั้นของการทำงานของ Agent ว่าเรียก LLM กี่ครั้ง เรียก Tool อะไร ด้วยข้อมูลอะไร ได้ผลอะไร ใช้ Token และเวลาเท่าไรไฟล์ traces/run-001.jsonl
MCPModel Context Protocol มาตรฐานเปิดสำหรับเชื่อมแอป AI กับแหล่งข้อมูลและ Tools ภายนอก ทำให้เขียน Tool ครั้งเดียวแล้วใช้ได้กับหลายแอปMCP Server ที่มี Tool lookup_note

Single Call, Workflow และ Agent ต่างกันอย่างไร

ระบบที่ใช้ LLM มีความซับซ้อนได้หลายระดับ ยิ่งให้ LLM ตัดสินใจเองมากเท่าไร ระบบก็ยิ่งยืดหยุ่น แต่ก็ยิ่งแพงขึ้น ช้าลง และคาดเดาได้ยากขึ้น แผนภาพนี้แสดงความต่างของทั้งสามแบบ

Single Call : คำถาม --> [LLM] --> คำตอบ
              (เรียก LLM 1 ครั้ง ลำดับตายตัว)

Workflow    : คำถาม --> [LLM แปล] --> [LLM สรุป] --> [LLM จัดหมวด] --> คำตอบ
              (โค้ดของเรากำหนดว่ามีกี่ขั้น ขั้นไหนก่อนหลัง)

Agent       : คำถาม --> [LLM คิด] --ขอใช้ Tool--> [โปรแกรมรัน Tool]
                          ^                              |
                          +------ ส่งผลของ Tool กลับ -------+
                        (LLM ตัดสินใจเองว่าจะวนกี่รอบ และหยุดเมื่อไร)

จำนวนครั้งที่เรียก LLM1 ครั้งรู้ล่วงหน้า เช่น 3 ครั้งไม่รู้ล่วงหน้า ต้องมีเพดาน
ค่าใช้จ่ายและความเร็วถูกและเร็วที่สุดปานกลาง คาดการณ์ได้แพงและช้าที่สุด เพราะส่งประวัติซ้ำทุกรอบ
ทดสอบและ Debugง่ายปานกลาง ทดสอบทีละขั้นได้ยาก ต้องมี Trace Log และชุดทดสอบ
เหมาะกับงานแปล สรุป จัดหมวด ดึงข้อมูลจากข้อความงานที่ขั้นตอนชัดและเหมือนเดิมทุกครั้ง เช่น รับอีเมล จัดหมวด แล้วร่างคำตอบงานเปิดกว้างที่เดาจำนวนขั้นไม่ได้ เช่น ค้นคว้าจากหลายเอกสาร แก้บั๊กในโค้ด
ระวัง

อย่าสร้าง Agent ถ้าไม่จำเป็น เริ่มจากวิธีที่ง่ายที่สุดเสมอ ถ้าการเรียก LLM ครั้งเดียวพร้อม Prompt ที่ดีทำงานได้ ให้หยุดที่ตรงนั้น ถ้าขั้นตอนตายตัว ให้ใช้ Workflow ค่อยใช้ Agent เมื่องานต้องการความยืดหยุ่นจริงๆ และยอมรับต้นทุนกับความเสี่ยงที่เพิ่มขึ้นได้ งานที่ ไม่ควร ใช้ Agent เช่น งานที่ต้องได้ผลเหมือนเดิมทุกครั้งตามกฎหมายหรือบัญชี งานที่ต้องตอบภายในเสี้ยววินาที และงานที่ทำสิ่งย้อนกลับไม่ได้โดยไม่มีคนตรวจ

Prerequisites: ต้องรู้อะไรมาก่อน

หัวข้อนี้เป็นหัวข้อระดับสูงของสาย AI จึงต้องมีพื้นฐานหลายเรื่อง ถ้าเรียนตามเส้นทางที่แนะนำ คุณผ่านหัวข้อต่อไปนี้มาแล้ว ซึ่งแต่ละหัวข้อถูกใช้ในหัวข้อนี้โดยตรง

  • จำเป็นที่สุด ต้องเขียนฟังก์ชัน ใช้ dict และ list ซ้อนกันคล่อง ใช้ dataclass ได้ จัดการ Exception ด้วย try/except อ่านเขียนไฟล์ด้วย pathlib สร้าง venv และเขียนเทสต์ด้วย pytest เบื้องต้นได้
  • ต้องเขียน System Prompt ที่กำหนดบทบาท ขอบเขต และรูปแบบคำตอบได้ เข้าใจ Few-shot และ Prompt Chaining เพราะ Agent ที่ดีเริ่มจากคำสั่งที่ชัด
  • ต้องเข้าใจ JSON, Request/Response, Status Code และการออกแบบ Interface ที่ชัดเจน เพราะการออกแบบ Tool ก็คือการออกแบบ API ให้ LLM ใช้
  • ต้องเคยเรียก Claude API ด้วย Python SDK แล้ว เข้าใจ Token, Context Window, ค่าใช้จ่าย, Structured Outputs, การจัดการ Error และ RAG เบื้องต้น หัวข้อนี้ต่อยอดจากบท Tool Use Intro ของหัวข้อนั้นโดยตรง
  • และ ใช้ Terminal บน WSL ได้คล่อง ตั้ง Environment Variable เป็น และ Push โปรเจกต์ขึ้น GitHub ได้
  • เขียน CREATE TABLE, INSERT และ SELECT ได้ เพราะ Step 7 ใช้ SQLite เป็นหน่วยความจำระยะยาวของ Agent
  • และ ไม่บังคับในทุกขั้น แต่ช่วยมากในเรื่อง Logging, Retry, การวัดผล และการคิดแบบทดลองวัดผล (Experiment) ใน Step 10

  5. ทำไมห้ามเขียน API Key ลงในโค้ดแล้ว Push ขึ้น GitHub (หัวข้อ 17)

Security

ห้ามเขียน API Key ลงในไฟล์ .py ห้ามพิมพ์ Key ออกทางหน้าจอหรือ Log และห้าม Commit ไฟล์ .env ขึ้น GitHub ให้ใส่ .env ไว้ใน .gitignore ตั้งแต่วันแรก ตั้ง Spend Limit (เพดานค่าใช้จ่ายรายเดือน) ใน Claude Console ก่อนลองโหมด REAL และถ้าเผลอ Push Key ขึ้นไปแล้ว ให้ถือว่า Key นั้นรั่วแล้ว ต้องเข้าไปลบ (Revoke) และสร้างใหม่ทันที การลบ Commit ทีหลังไม่พอ

STEP 1

Agent คืออะไร: Single Call, Workflow และ Agent

2–3 วัน · 3–4 ชม.
หัวข้อย่อย
  • นิยาม Agent ที่ใช้ในหลักสูตร: LLM ที่ตัดสินใจเองว่าจะเรียก Tool ไหน ด้วย Input อะไร กี่ครั้ง และหยุดเมื่อไร โดยวนเป็นลูปภายใต้ขอบเขตที่โปรแกรมกำหนด และความต่างจากคำว่า "Agent" ในโฆษณาที่หมายถึงแชตบอตธรรมดา
  • Single LLM Call: เรียกครั้งเดียวตอบครั้งเดียว เหมาะกับการแปล สรุป จัดหมวด และดึงข้อมูลจากข้อความ เป็นจุดเริ่มต้นที่ควรลองก่อนเสมอ
  • Workflow 5 แบบที่พบบ่อย: Prompt Chaining (ต่อหลายขั้น), Routing (จัดหมวดแล้วส่งต่อ), Parallelization (แบ่งงานทำพร้อมกัน), Orchestrator-Workers (แตกงานแล้วรวมผล) และ Evaluator-Optimizer (ตรวจแล้วแก้วนซ้ำ)
  • Agent: เหมาะกับงานเปิดกว้างที่เดาจำนวนขั้นล่วงหน้าไม่ได้ เช่น ค้นคว้าจากหลายเอกสาร หาสาเหตุของบั๊ก หรือวิเคราะห์ข้อมูลที่ต้องลองหลายทาง
  • ส่วนประกอบของ Agent 6 ส่วน: Model (สมอง), Instructions หรือ System Prompt (หน้าที่และกฎ), Tools (มือ), Memory (ความจำ), Loop (การวนทำงาน) และ Guardrails (ขอบเขตความปลอดภัย)
  • ข้อจำกัดที่ต้องยอมรับ: ค่าใช้จ่ายสะสมทุกรอบ ความช้า ความผิดพลาดที่ทบต้น (ถ้าแต่ละขั้นถูก 95% งาน 10 ขั้นจะถูกทั้งหมดเพียงราว 60%) และการทดสอบที่ยากกว่าโปรแกรมทั่วไป
  • เมื่อไรไม่ควรสร้าง Agent: งานที่ขั้นตอนตายตัว งานที่ต้องได้ผลเหมือนเดิมทุกครั้งตามกฎหมายหรือบัญชี งานที่ต้องตอบเร็วมาก และงานที่ทำสิ่งย้อนกลับไม่ได้โดยไม่มีคนตรวจ
  • ตัวอย่าง Agent ในโลกจริง: Coding Agent ที่อ่านโค้ด รันเทสต์ และแก้ไฟล์ Research Agent ที่ค้นและสรุปเอกสาร Customer Support Agent ที่ค้นสถานะคำสั่งซื้อก่อนตอบลูกค้า และ Data Agent ที่เขียน SQL แล้วอ่านผลเพื่อถามต่อ

2–3 วัน · 3–4 ชม.
หัวข้อย่อย
  • Tool คืออะไรในมุมของ LLM: แค่ "เมนู" ที่บอกว่ามีฟังก์ชันอะไรให้ขอใช้ได้ LLM ไม่ได้รันโค้ดเอง โปรแกรมของเราเป็นผู้รันและตัดสินใจว่าจะยอมรันหรือไม่

  • เขียน description ให้ดี: บอกว่า Tool ทำอะไร ใช้เมื่อไร ไม่ควรใช้เมื่อไร คืนผลหน้าตาแบบไหน เพราะโมเดลเลือก Tool จากคำอธิบายนี้เป็นหลัก
  • ตั้งชื่อ Tool แบบ snake_case และเป็นกริยา + คำนาม เช่น search_docs, read_doc, save_note ไม่ใช้ชื่อกว้างอย่าง do_task

def run_tool(name: str, tool_input: dict) -> tuple[str, bool]:
    """รัน Tool ตามชื่อ คืนค่า (ผลลัพธ์, เป็น error หรือไม่)"""

STEP 4

Agent Loop แบบเขียนเองและ stop_reason

3 วัน · 4–5 ชม.
หัวข้อย่อย
  • ขั้นตอนของ Loop: ส่ง messages และ tools ไปหา Claude → ถ้า stop_reason == "tool_use" ให้เก็บคำตอบของ Assistant ทั้งก้อนลง messages → รันทุก Tool ที่ขอ → ส่งผลทั้งหมดกลับใน User Message เดียว → วนซ้ำจนได้ end_turn
  • จัดการ stop_reason ทุกค่า: end_turn จบงาน, tool_use ทำต่อ, max_tokens คำตอบถูกตัด ต้องเพิ่ม max_tokens หรือแบ่งงาน, refusal โมเดลปฏิเสธ ต้องหยุดและแจ้งผู้ใช้ และตรวจ stop_reason ก่อนอ่าน content ทุกครั้ง
  • ประวัติต้องครบและเรียงถูก: บล็อก tool_use ใน Assistant Message ต้องตามด้วย tool_result ที่มี tool_use_id ตรงกันใน User Message ถัดไปทันที และต้องส่งบล็อกเดิมของ Assistant กลับไปทั้งหมดโดยไม่ตัดทิ้ง
  • max_steps เป็นเพดานจำนวนรอบที่ต้องมีทุก Loop เมื่อครบแล้วให้หยุดอย่างสุภาพและบอกผู้ใช้ว่างานยังไม่เสร็จ แทนที่จะวนต่อไปเรื่อยๆ
  • Fake Client ที่เขียน "บท" ไว้ล่วงหน้า: รอบแรกคืน tool_use รอบสองอ่าน tool_result ที่ได้รับแล้วคืน end_turn ทำให้ทดสอบ Loop ได้ครบทุกเส้นทาง
  • พิมพ์ Trace ของทุกรอบ: เลขรอบ stop_reason ชื่อ Tool Input และผลลัพธ์ เพื่อเห็นการตัดสินใจของโมเดล
  • บั๊กที่พบบ่อย: ลืมเก็บ Assistant Message ก่อนส่ง tool_result (ได้ Error 400), ใส่ tool_use_id ผิด, แยก tool_result หลายตัวเป็นหลาย Message และ Loop ไม่มีทางออกเมื่อเจอ stop_reason ที่ไม่ได้คาดไว้

    for step in range(1, MAX_STEPS + 1):
        response = client.messages.create(model=MODEL, max_tokens=16000,
                                          tools=TOOLS, messages=messages)
        print(f"[step {step}] stop_reason={response.stop_reason}")
        if response.stop_reason != "tool_use":
            return "".join(b.text for b in response.content if b.type == "text")

                results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})
        messages.append({"role": "user", "content": results})
    return "หยุดเพราะครบจำนวนรอบสูงสุด"

import json
from concurrent.futures import ThreadPoolExecutor
from dataclasses import dataclass, field
from pathlib import Path

DOCS_DIR = Path("docs")


@dataclass
class Block:
    type: str
    id: str = ""
    name: str = ""
    input: dict = field(default_factory=dict)


def read_doc(name: str) -> str:
    path = DOCS_DIR / name
    if not path.is_file():
        available = ", ".join(sorted(p.name for p in DOCS_DIR.glob("*.md")))
        # ข้อความ error ที่ดีต้องบอกทางแก้ให้โมเดลด้วย
        raise FileNotFoundError(f"ไม่พบไฟล์ {name} ไฟล์ที่มีคือ: {available}")
    return path.read_text(encoding="utf-8")


def run_one(block: Block) -> dict:
    try:
        output = read_doc(**block.input)
        return {"type": "tool_result", "tool_use_id": block.id, "content": output}
    except Exception as exc:
        return {"type": "tool_result", "tool_use_id": block.id,
                "content": f"Error: {exc}", "is_error": True}

@beta_tool
def calculator(a: float, b: float, op: str) -> str:
    """คำนวณเลขคณิตพื้นฐาน

    Args:
        a: ตัวเลขตัวแรก
        b: ตัวเลขตัวที่สอง
        op: ชนิดการคำนวณ add, sub, mul หรือ div
    """
    ops = {"add": a + b, "sub": a - b, "mul": a * b, "div": a / b if b else 0}
    return str(ops[op])

หัวข้อย่อย
  • LLM ไม่มีความจำในตัว (Stateless): ความจำระยะสั้นของ Agent คือ messages ที่เราส่งไปทุกรอบ ยิ่งงานยาว ประวัติก็ยิ่งยาว ค่า Input Token ของแต่ละรอบก็ยิ่งสูง
  • Context Window และวิธีจัดการประวัติที่ยาว: เก็บเฉพาะ N รอบล่าสุด สรุปรอบเก่าเป็นข้อความสั้น และตัดผลของ Tool ที่ยาวมากให้เหลือเฉพาะส่วนสำคัญ โดยต้องไม่แยกคู่ tool_use กับ tool_result ออกจากกัน
  • นับ Token ก่อนส่งด้วย client.messages.count_tokens(model=MODEL, messages=[...], system="...") ห้ามใช้ tiktoken เพราะเป็นตัวนับของผู้ให้บริการอื่น นับผิดสำหรับ Claude โดยเฉพาะข้อความภาษาไทย
  • ความจำระยะยาว (Long-term Memory): เก็บข้อเท็จจริงที่ต้องใช้ข้ามการรันโปรแกรม เช่น ความชอบของผู้ใช้ ข้อสรุปจากงานก่อน ในไฟล์ JSON หรือฐานข้อมูล SQLite
  • ให้ Agent จัดการความจำเองผ่าน Tools remember(topic, content) และ recall(keyword) โดยใช้ SQL แบบมี Placeholder (?) เสมอ เพื่อป้องกัน SQL Injection
  • บันทึกและโหลดบทสนทนาทั้งก้อนเป็นไฟล์ JSON เพื่อทำงานต่อจากเดิมได้ (Session Persistence)
  • Prompt Caching สำหรับส่วนที่ยาวและไม่เปลี่ยน เช่น System Prompt และ Tool Definitions ใส่ cache_control={"type": "ephemeral"} แล้วตรวจผลที่ usage.cache_read_input_tokens (ส่วนที่สั้นกว่าขั้นต่ำของโมเดลจะไม่ถูก Cache)
  • ความเป็นส่วนตัว: ไม่เก็บข้อมูลส่วนบุคคลที่ไม่จำเป็น บอกผู้ใช้ว่า Agent จำอะไรไว้ และมีวิธีลบความจำ สอดคล้องกับ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล (PDPA)

# หน่วยความจำระยะยาวของ Agent ด้วย SQLite: จำข้อเท็จจริงข้ามการรันโปรแกรมได้
import sqlite3
from pathlib import Path

DB_PATH = Path("memory.db")


def connect() -> sqlite3.Connection:
    conn = sqlite3.connect(DB_PATH)
    conn.execute("""
        CREATE TABLE IF NOT EXISTS memories (
            topic      TEXT PRIMARY KEY,
            content    TEXT NOT NULL,
            updated_at TEXT NOT NULL DEFAULT (datetime('now'))
        )""")
    return conn


def remember(conn: sqlite3.Connection, topic: str, content: str) -> str:
    """Tool สำหรับให้ Agent บันทึกความจำ (หัวข้อเดิมจะถูกเขียนทับ)"""
    conn.execute(
        "INSERT INTO memories (topic, content) VALUES (?, ?) "
        "ON CONFLICT(topic) DO UPDATE SET content = excluded.content, updated_at = datetime('now')",
        (topic, content))  # ใช้ ? เสมอ ห้ามต่อ String เป็น SQL
    conn.commit()
    return f"บันทึกความจำหัวข้อ '{topic}' แล้ว"


def recall(conn: sqlite3.Connection, keyword: str) -> str:
    """Tool สำหรับค้นความจำด้วยคำค้น"""
    rows = conn.execute(
        "SELECT topic, content FROM memories WHERE topic LIKE ? OR content LIKE ? ORDER BY topic",
        (f"%{keyword}%", f"%{keyword}%")).fetchall()
    if not rows:
        return "ไม่พบความจำที่เกี่ยวข้อง"
    return "\n".join(f"- {topic}: {content}" for topic, content in rows)


if __name__ == "__main__":
    conn = connect()
    try:
        print(remember(conn, "รูปแบบรายงาน", "ผู้ใช้ชอบรายงานสั้น เป็นข้อๆ และมีตัวเลขเสมอ"))
        print(remember(conn, "สาขาที่สนใจ", "เชียงใหม่ และ ภูเก็ต"))
        print(recall(conn, "เชียงใหม่"))
        print(recall(conn, "ขอนแก่น"))
        total = conn.execute("SELECT COUNT(*) FROM memories").fetchone()[0]
        print("จำนวนความจำทั้งหมด:", total)
    finally:
        conn.close()  # ปิดการเชื่อมต่อเสมอ แม้จะเกิด error

STEP 8

Planning Patterns: ReAct, Plan-and-Execute และ Reflection

2–3 วัน · 3–4 ชม.
หัวข้อย่อย
  • ReAct (Reason + Act): คิดว่าจะทำอะไร → ลงมือเรียก Tool → ดูผล → คิดต่อ วนไปเรื่อยๆ Agent Loop ที่คุณเขียนใน Step 4 คือ ReAct แบบหนึ่งอยู่แล้ว เพียงแต่ความคิดของโมเดลเกิดขึ้นภายใน (Thinking) และเราขอให้มันเขียนเหตุผลสั้นๆ ก่อนเรียก Tool ได้ผ่าน System Prompt
  • Plan-and-Execute: ให้ LLM วางแผนทั้งหมดก่อนเป็น Structured Output (รายการขั้นตอน) แล้วโปรแกรมทำตามทีละขั้น ถ้าเจอสิ่งไม่คาดคิดค่อยให้วางแผนใหม่ (Re-plan) เหมาะกับงานยาวที่อยากให้ผู้ใช้ตรวจแผนก่อนเริ่ม
  • Reflection หรือ Evaluator-Optimizer: ให้ LLM ตรวจคำตอบของตัวเองหรือของ Agent อื่นเทียบกับเกณฑ์ที่ชัด เช่น "มีตัวเลขครบไหม อ้างอิงไฟล์ไหม" แล้วแก้ จำกัดจำนวนรอบการแก้เสมอ
  • เขียน System Prompt สำหรับ Agent: บทบาท ขอบเขตงาน รายการ Tools และเมื่อไรควรใช้ เงื่อนไขการหยุด รูปแบบคำตอบสุดท้าย และสิ่งที่ห้ามทำ
  • เงื่อนไขการหยุดที่ดี: อนุญาตให้ Agent ตอบว่า "ไม่พบข้อมูลในเอกสาร" ได้ แทนที่จะวนค้นต่อไม่รู้จบ หรือแต่งคำตอบขึ้นมาเอง
  • คุมความลึกของการคิดด้วย output_config={"effort": ...} งานวางแผนซับซ้อนใช้ high งานง่ายใช้ low เพื่อประหยัด แทนการปรับ temperature ซึ่งโมเดลรุ่นใหม่ไม่รองรับแล้ว
  • เลือก Pattern ให้เหมาะกับงาน: งานสั้นใช้ ReAct ล้วน งานยาวที่ต้องการความโปร่งใสใช้ Plan-and-Execute งานที่คุณภาพสำคัญมากเพิ่ม Reflection และชั่งน้ำหนักกับค่าใช้จ่ายที่เพิ่มขึ้นทุกครั้ง

# Plan-and-Execute: ให้ LLM วางแผนเป็น Structured Output (Pydantic) แล้วโปรแกรมทำตามทีละขั้น
import os
from typing import Literal

from pydantic import BaseModel, Field

MODEL = os.environ.get("CLAUDE_MODEL", "claude-opus-5-5")


class PlanStep(BaseModel):
    number: int
    action: str = Field(description="สิ่งที่ต้องทำในขั้นนี้")
    tool: Literal["search_docs", "read_doc", "calculator", "none"]


class Plan(BaseModel):
    goal: str
    steps: list[PlanStep]


# แผนจำลองสำหรับโหมด MOCK (หน้าตาเดียวกับที่ Claude คืนผ่าน messages.parse)
MOCK_PLAN_JSON = """{
  "goal": "หาว่าสาขาเชียงใหม่โตขึ้นกี่เปอร์เซ็นต์จากไตรมาส 1 ถึงไตรมาส 2",
  "steps": [
    {"number": 1, "action": "ค้นเอกสารยอดขายที่มีคำว่าเชียงใหม่", "tool": "search_docs"},
    {"number": 2, "action": "อ่านยอดขายไตรมาส 1 และ 2", "tool": "read_doc"},
    {"number": 3, "action": "คำนวณ (Q2 - Q1) / Q1", "tool": "calculator"},
    {"number": 4, "action": "สรุปคำตอบพร้อมอ้างอิงไฟล์", "tool": "none"}
  ]
}"""


def make_plan(question: str) -> Plan:
    if os.environ.get("ANTHROPIC_API_KEY"):
        import anthropic
        client = anthropic.Anthropic()
        response = client.messages.parse(
            model=MODEL, max_tokens=16000,
            system="คุณคือผู้วางแผนงานค้นคว้า แตกงานเป็นขั้นสั้นๆ ไม่เกิน 6 ขั้น",
            messages=[{"role": "user", "content": question}],
            output_format=Plan)
        return response.parsed_output
    return Plan.model_validate_json(MOCK_PLAN_JSON)  # ตรวจรูปแบบด้วย Pydantic เหมือนของจริง


plan = make_plan("สาขาเชียงใหม่โตขึ้นกี่เปอร์เซ็นต์จาก Q1 ถึง Q2")
print("เป้าหมาย:", plan.goal)
for step in plan.steps:
    print(f"  ขั้น {step.number} [{step.tool}] {step.action}")
print("จำนวนขั้นที่ต้องเรียก Tool:", sum(1 for s in plan.steps if s.tool != "none"))

  • Human-in-the-loop: Tool ที่เขียนไฟล์ ส่งข้อความ ลบข้อมูล หรือใช้เงิน ต้องถามผู้ใช้ก่อนทุกครั้ง แสดงให้เห็นว่าจะทำอะไรด้วยข้อมูลอะไร ถ้าผู้ใช้ปฏิเสธให้ส่ง tool_result แบบ is_error บอกโมเดลว่าไม่ได้รับอนุมัติ
  • Prompt Injection แบบตรง (ผู้ใช้พิมพ์หลอกเอง) และแบบอ้อม (Indirect) ที่ซ่อนมากับเอกสาร หน้าเว็บ อีเมล หรือผลของ Tool เช่น ข้อความ "IGNORE PREVIOUS INSTRUCTIONS" ในไฟล์ที่ Agent อ่าน
  • แนวป้องกันหลายชั้น: ถือว่าผลของ Tool เป็น "ข้อมูล" ไม่ใช่ "คำสั่ง" ห่อเนื้อหาภายนอกด้วยแท็กอย่าง <document> และเขียนกฎนี้ใน System Prompt จำกัดสิทธิ์ของ Tools ขออนุมัติก่อนทำสิ่งเสี่ยง และตรวจผลลัพธ์ก่อนนำไปใช้ต่อ
  • ความเสี่ยงที่ร้ายแรงที่สุดเกิดเมื่อ Agent มีครบสามอย่างพร้อมกัน คือ เข้าถึงข้อมูลลับ อ่านเนื้อหาที่คนนอกควบคุมได้ และส่งข้อมูลออกไปภายนอกได้ ให้ตัดอย่างน้อยหนึ่งอย่างออกเสมอ
  • จัดการ stop_reason == "refusal" และบันทึกเหตุการณ์ด้านความปลอดภัย (Tool ที่ถูกปฏิเสธ Path ที่ถูกบล็อก การไม่อนุมัติ) ลง Log เพื่อตรวจสอบภายหลัง
  • ไม่ส่งความลับให้โมเดลเห็น เช่น API Key รหัสผ่าน หรือข้อมูลส่วนบุคคลที่ไม่จำเป็นต่องาน เพราะสิ่งใดที่อยู่ใน Context อาจถูกหลอกให้เปิดเผยได้

from pathlib import Path

ALLOWED_TOOLS = {"search_docs", "read_doc", "calculator", "save_note"}  # Allowlist
WRITE_TOOLS = {"save_note"}  # Tool ที่เปลี่ยนแปลงข้อมูล ต้องให้คนอนุมัติ
DOCS_DIR = Path("docs").resolve()
MAX_TOTAL_TOKENS = 5000  # งบ Token ต่อหนึ่งงาน


def scripted_approver(answers):
    """ผู้อนุมัติจำลองสำหรับตัวอย่าง (โปรแกรมจริงใช้ input() ถามผู้ใช้)"""
    answers = iter(answers)

    def approve(name: str, tool_input: dict) -> bool:
        answer = next(answers)
        print(f"  [ขออนุมัติ] {name}({tool_input}) -> ผู้ใช้ตอบ {answer}")
        return answer == "y"
    return approve


def check_tool_call(name: str, tool_input: dict, approve) -> str | None:
    """คืนข้อความ Error ถ้าไม่ผ่าน หรือ None ถ้ารันได้"""
    if name not in ALLOWED_TOOLS:
        return f"Error: ไม่อนุญาตให้ใช้ Tool '{name}'"
    if name == "read_doc":
        target = (DOCS_DIR / tool_input["name"]).resolve()
        if not target.is_relative_to(DOCS_DIR):  # กัน ../ หลุดออกนอกโฟลเดอร์
            return "Error: อ่านได้เฉพาะไฟล์ในโฟลเดอร์ docs/ เท่านั้น"
    if name in WRITE_TOOLS and not approve(name, tool_input):
        return "Error: ผู้ใช้ไม่อนุมัติให้บันทึกไฟล์ ให้ตอบผู้ใช้โดยไม่บันทึก"
    return None


def wrap_untrusted(source: str, text: str) -> str:
    """ห่อเนื้อหาจากภายนอกด้วยแท็ก เพื่อให้ System Prompt สั่งได้ว่าข้อความในแท็กคือข้อมูลเท่านั้น"""
    return f'<document source="{source}">\n{text}\n</document>'

STEP 11

Multi-agent (Orchestrator-Workers) และ Model Context Protocol (MCP)

3 วัน · 4–5 ชม.
หัวข้อย่อย
  • Orchestrator-Workers: Agent หลัก (Orchestrator) แตกงานใหญ่เป็นงานย่อย ส่งให้ Worker แต่ละตัวทำโดยมี Context ของตัวเองแยกกัน แล้วรวมผลเป็นคำตอบเดียว
  • ทำ Worker ให้เป็น "Tool" ของ Orchestrator เช่น Tool delegate_research(topic, files) ที่ภายในรัน Agent Loop อีกชุดหนึ่ง แล้วคืนผลเป็น Structured Output สั้นๆ แทนบทสนทนาทั้งหมด
  • ส่งเฉพาะ Context ที่จำเป็นให้ Worker และให้ Worker คืนผลที่กระชับ เพื่อไม่ให้ Context ของ Orchestrator เต็ม และเลือกโมเดลให้เหมาะ เช่น Orchestrator ใช้ Opus ส่วน Worker ใช้ Sonnet หรือ Haiku
  • เมื่อไรคุ้มที่จะใช้ Multi-agent: งานกว้างที่แบ่งเป็นส่วนอิสระได้ (ค้นคว้าหลายหัวข้อพร้อมกัน) หรือข้อมูลมากเกิน Context ของ Agent เดียว เมื่อไรไม่คุ้ม: งานที่ทุกขั้นพึ่งพากันแน่น เพราะ Token จะเพิ่มขึ้นหลายเท่าและ Debug ยากขึ้นมาก ให้เริ่มจาก Agent เดียวเสมอ
  • MCP (Model Context Protocol): มาตรฐานเปิดที่แยก "ผู้ให้ Tools" (MCP Server) ออกจาก "แอป AI ที่ใช้ Tools" (Host และ MCP Client) ทำให้เขียน Tool ครั้งเดียวแล้วใช้ได้กับหลายแอป สิ่งที่ Server ให้ได้คือ Tools, Resources และ Prompts
  • Transport ของ MCP: stdio (เปิด Server เป็น Subprocess บนเครื่องเดียวกัน) และ Streamable HTTP (เรียกผ่านเครือข่าย)
  • ใช้ MCP ด้วย Python SDK mcp==2.3.0: สร้าง Server ด้วย MCPServer (ใน mcp 1.x ชื่อ FastMCP) เชื่อมด้วย Client(StdioServerParameters(...)) แล้ว list_tools() แปลงเป็น Tool Definition ของ Claude และส่งต่อการเรียกด้วย call_tool() ส่วน SDK ของ Anthropic มีตัวช่วย anthropic.lib.tools.mcp.mcp_tool สำหรับใช้กับ Tool Runner
  • ความปลอดภัยของ MCP Server: ติดตั้งเฉพาะ Server จากแหล่งที่เชื่อถือได้ อ่านว่าแต่ละ Tool ทำอะไร คำอธิบายของ Tool จาก Server ภายนอกก็เป็นช่องทาง Prompt Injection ได้ และใช้ Allowlist กับ Human-in-the-loop เหมือน Tools ของเราเอง
ทำไมต้องเรียน
ระบบ Agent ขนาดใหญ่ในบริษัทมักแบ่งงานให้หลาย Agent และดึง Tools มาจากหลายแหล่ง การรู้ทั้งข้อดีและต้นทุนของ Multi-agent ช่วยให้คุณไม่สร้างระบบที่ซับซ้อนเกินจำเป็น ส่วน MCP กลายเป็นวิธีมาตรฐานที่เครื่องมือ AI จำนวนมากใช้เชื่อมกับฐานข้อมูล ระบบไฟล์ และบริการภายนอก การเขียน MCP Server เองเป็นได้ทำให้คุณนำระบบภายในของบริษัทมาให้ Agent ใช้ได้อย่างเป็นระบบ

# MCP Server ขนาดเล็ก: เปิด Tool "lookup_note" ให้แอป AI ใดก็ได้ที่รองรับ MCP เรียกใช้
# ทดสอบกับ mcp==2.3.0 (ใน mcp 2.x คลาส FastMCP เปลี่ยนชื่อเป็น MCPServer)
from mcp.server.mcpserver import MCPServer

server = MCPServer("notes-server")

NOTES = {
    "agent": "Agent คือ LLM ที่วนลูปเรียก Tool จนงานเสร็จ ภายใต้ขอบเขตที่เรากำหนด",
    "mcp": "MCP คือมาตรฐานเปิดสำหรับเชื่อม Tools และข้อมูลเข้ากับแอป AI",
}


@server.tool()
def lookup_note(topic: str) -> str:
    """ค้นโน้ตความรู้ตามหัวข้อ เช่น agent หรือ mcp"""
    return NOTES.get(topic.lower(), f"ไม่พบโน้ตหัวข้อ {topic}")


if __name__ == "__main__":
    server.run()  # ค่าเริ่มต้นคือ transport แบบ stdio
# MCP Client: เปิด MCP Server เป็น Subprocess แล้วแปลง Tools ของมันเป็นรูปแบบที่ Claude ใช้ได้
import asyncio
import json
import sys

from mcp import Client, StdioServerParameters


async def main() -> None:
    params = StdioServerParameters(command=sys.executable, args=["notes_server.py"])
    async with Client(params) as mcp_client:
        listed = await mcp_client.list_tools()
        # แปลงเป็น Tool Definition ของ Claude เพื่อส่งเข้า messages.create(tools=...)
        claude_tools = [{"name": t.name, "description": t.description or "",
                         "input_schema": t.input_schema} for t in listed.tools]
        print(json.dumps(claude_tools, ensure_ascii=False, indent=2))
        # เมื่อ Claude ขอใช้ Tool นี้ ให้ส่งต่อไปที่ MCP Server
        result = await mcp_client.call_tool("lookup_note", {"topic": "MCP"})
        text = "".join(c.text for c in result.content if c.type == "text")
        print("is_error:", result.is_error)
        print("ผลลัพธ์:", text)


asyncio.run(main())

  1. เลือกระหว่าง Single Call, Workflow และ Agent ได้อย่างมีเหตุผล เพราะระบบที่เรียบง่ายที่สุดที่ทำงานได้มักถูกกว่า เร็วกว่า และเชื่อถือได้มากกว่า Agent เสมอ
  2. นิยาม Tool ด้วย JSON Schema แบบ strict และเขียนคำอธิบายที่ชัด เพราะโมเดลเลือก Tool และสร้าง Input จากชื่อ คำอธิบาย และ Schema เป็นหลัก
  3. เขียน Agent Loop ด้วยมือและจัดการ stop_reason ทุกค่า เพราะเป็นกลไกที่อยู่เบื้องหลังทุก Framework และเป็นทักษะที่ใช้ Debug ปัญหาของ Agent ได้ทุกแบบ
  4. จัดการ Parallel Tool Calls และ Tool Errors ด้วย is_error เพราะงานจริงมี Tool ที่ล้มเหลวทุกวัน และข้อความ Error ที่ดีทำให้โมเดลแก้ตัวเองได้
  5. ใช้ Tool Runner ของ SDK และ Structured Outputs เพราะช่วยลดโค้ดซ้ำ และทำให้สถานะของ Agent มีรูปแบบที่โปรแกรมอ่านได้แน่นอน
  6. ออกแบบ Memory ทั้งในบทสนทนาและในฐานข้อมูล เพราะต้องคุมขนาด Context และค่าใช้จ่าย ขณะที่ยังจำสิ่งที่สำคัญข้ามการใช้งานได้
  7. เลือกและเขียน Planning Pattern (ReAct, Plan-and-Execute, Reflection) เพราะงานแต่ละแบบต้องการระดับการวางแผนต่างกัน และแต่ละแบบมีต้นทุนต่างกัน
  8. ใส่ Guardrails และ Human-in-the-loop เพราะ Agent ลงมือทำสิ่งต่างๆ ได้จริง ความผิดพลาดจึงต้องถูกจำกัดด้วยงบประมาณ สิทธิ์ และการอนุมัติจากคน
  9. ป้องกัน Prompt Injection จากผลของ Tool เพราะเอกสาร หน้าเว็บ และอีเมลที่ Agent อ่านอาจมีคำสั่งแฝง และยังไม่มีวิธีป้องกันใดที่ได้ผล 100%
  10. เก็บ Trace Log และติดตาม Token กับค่าใช้จ่ายทุกขั้น เพราะเป็นวิธีเดียวที่จะรู้ว่า Agent ทำอะไร ผิดตรงไหน และใช้เงินไปกับอะไร
  11. วัดผล Agent ด้วยชุดทดสอบ Task Success Rate และ Trajectory Checks เพราะการแก้ Prompt หรือเปลี่ยนโมเดลโดยไม่มีตัวเลขเปรียบเทียบคือการเดา
  12. เขียนเทสต์ด้วย Fake Client และรู้จัก Multi-agent กับ MCP เพราะเทสต์ที่ไม่ต้องใช้ Key ทำให้ทีมพัฒนาได้เร็วและปลอดภัย และ MCP กับ Multi-agent คือวิธีที่ระบบ Agent ขนาดใหญ่ขยายตัว

  • ค้นหาตำแหน่งเดียวกันใน LinkedIn Jobs และดูโปรไฟล์ของคนที่ทำตำแหน่งนั้นอยู่ ว่ามีประสบการณ์ โปรเจกต์ และใบรับรองอะไร
  • อ่านรายงานผลสำรวจเงินเดือนประจำปีของบริษัทจัดหางาน และสังเกตว่ารายงานนั้นสำรวจเมื่อไร และนับตำแหน่งด้าน AI รวมอยู่ในกลุ่มใด
  • ถามคนที่ทำงานในสายนั้นจริงในชุมชนหรือกลุ่มสายเทค เพราะได้ข้อมูลที่ใกล้ความจริงและเป็นปัจจุบันที่สุด

เมื่อผ่าน Checkpoint ของ Step 12 และ Research Assistant Agent อยู่บน GitHub แล้ว แปลว่าคุณเข้าใจ AI Agent ในระดับที่นำไปสร้างงานจริงได้ ลำดับที่แนะนำต่อจากนี้คือ

  1. หัวข้อถัดไปในเส้นทาง ใช้ AI Coding Agent ช่วยสร้างเว็บแอป ความเข้าใจเรื่อง Agent Loop, Tools และ Guardrails จากหัวข้อนี้ทำให้คุณสั่งงาน ตรวจงาน และคุมความเสี่ยงของ Coding Agent ได้ดีกว่าคนที่ใช้เป็นกล่องดำ
  2. ต่อยอดจาก Step 9 สู่ความปลอดภัยของระบบ AI ทั้ง Prompt Injection การรั่วไหลของข้อมูล และการทดสอบเจาะระบบในแล็บของตัวเอง
  3. นำ Agent ไปห่อเป็น API Service ที่มี Authentication, Rate Limit, Queue สำหรับงานที่ใช้เวลานาน และ Logging แบบรวมศูนย์
  4. กลับไปรวม RAG กับ Agent: ให้ search_docs ใช้ Retrieval ที่ดีขึ้น (BM25 หรือ Embeddings) และวัดผล Retrieval ด้วย recall@k
  5. และ สร้าง Agent ฝั่ง TypeScript ด้วย @anthropic-ai/sdk หรือเขียน MCP Server ด้วย Node.js
