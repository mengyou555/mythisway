3.1Learning Roadmap

ภาพรวมเส้นทาง

Game Developer คือคนที่เปลี่ยนไอเดียเกมให้กลายเป็นโปรแกรมที่เล่นได้จริง งานหลักคือเขียนโค้ดควบคุมตัวละคร ศัตรู กติกา คะแนน เมนู เสียง และทำให้ทุกอย่างทำงานลื่นไหล 60 ครั้งต่อวินาทีโดยไม่สะดุด สิ่งที่ทำให้สายนี้ต่างจาก Backend หรือ Web คือโปรแกรมของเราไม่ได้รอคำสั่งเฉยๆ แต่ วนทำงานตลอดเวลา ในสิ่งที่เรียกว่า Game Loop ทุกเฟรมต้องอ่าน Input คำนวณการเคลื่อนที่ ตรวจการชน และวาดภาพใหม่ภายในเวลาประมาณ 16 มิลลิวินาที

หัวข้อนี้สอนด้วย Godot 4.7.2 (เวอร์ชัน Stable ล่าสุด ณ 19 ต.ค. 2026 ส่วน 4.8 ยังเป็น Beta) บน Windows และใช้ภาษา GDScript เป็นภาษาหลัก GDScript มีหน้าตาคล้าย Python ที่คุณเรียนมาแล้วใน จึงเริ่มได้เร็ว ส่วน C# เป็นทางเลือกเสริมของ Godot และเป็นภาษาหลักของ Unity ซึ่งเป็น Engine ที่ประกาศงานในไทยใช้บ่อย หัวข้อนี้จะบอกวิธีต่อยอดไป Unity/C# ไว้ในขั้นสุดท้ายด้วย

เส้นทางนี้แบ่งเป็น 14 ขั้นใน 3 ระดับ เริ่มจากรู้จักสายงานและทีมเกม เข้าใจ Game Loop และ Delta Time ด้วยการจำลองใน Python ก่อนเปิด Engine จากนั้นเรียน Editor ของ Godot และ GDScript ต่อด้วยการเคลื่อนที่ การชน Animation ด่าน กล้อง UI เสียง และการ Spawn ศัตรู ระดับสุดท้ายเป็นเรื่องที่แยกเกมของมือใหม่ออกจากเกมที่ดูเป็นมืออาชีพ คือสถาปัตยกรรมเกม การบันทึกข้อมูล State Machine ของ AI และ "Game Feel" แล้วจบด้วยการ Export เป็นไฟล์ .exe สำหรับ Windows และเวอร์ชัน Web เพื่อปล่อยบน itch.io

ใช้เวลารวมประมาณ 115–170 ชั่วโมง (ช่วงที่วางแผนไว้สำหรับหัวข้อนี้คือ 100–180 ชั่วโมง) ถ้าเรียนวันละ 1–1.5 ชั่วโมง สัปดาห์ละ 6 วัน จะจบในราว 18 สัปดาห์ หรือประมาณ 4–5 เดือน ผลงานสุดท้ายคือ Mini Project 2D Arcade Game: Star Dodger เกม Arcade แนวหลบศัตรูและเก็บดาว ที่มีเมนู ศัตรู คะแนน High Score ที่บันทึกลงดิสก์ เสียง หน้าจอ Game Over และไฟล์ Windows ที่ส่งให้เพื่อนเล่นได้จริง

  1. Beginner Step 1 · รู้จักสายงาน Game Developer ทีมเกม และ Pipeline การสร้างเกม
  2. Beginner Step 2 · Game Loop, Delta Time และคณิตศาสตร์ Vector
  3. Beginner Step 3 · ติดตั้ง Godot 4.7.2 และรู้จัก Node, Scene, Scene Tree
  4. Beginner Step 4 · GDScript พื้นฐานสำหรับคนที่รู้ Python
  5. Intermediate Step 5 · Input Map และการเคลื่อนที่ด้วย CharacterBody2D
  6. Intermediate Step 6 · Physics, Collision, Signals และ Groups
  7. Intermediate Step 7 · Sprite, Animation และ TileMapLayer
  8. Intermediate Step 8 · Camera2D, UI และเสียง
  9. Intermediate Step 9 · Timer, Spawning และกติกาของเกม
  10. Advanced Step 10 · Autoload, การสลับ Scene และการบันทึกข้อมูล
  11. Advanced Step 11 · State Machine และ AI ของศัตรู
  12. Advanced Step 12 · Tween และ Game Feel
  13. Advanced Step 13 · Export, Performance และ Git สำหรับโปรเจกต์ Godot
  14. Advanced Step 14 · Mini Project, เผยแพร่บน itch.io และต่อยอดสู่ตลาดงาน

เปรียบเทียบ

การทำเกมเหมือนการทำหนังแอนิเมชันที่คนดูกดปุ่มเปลี่ยนเรื่องได้ตลอดเวลา หนังธรรมดาวาดทุกเฟรมไว้ล่วงหน้า แต่เกมต้อง "วาดเฟรมถัดไปสดๆ" จากสิ่งที่ผู้เล่นเพิ่งกด Game Engine อย่าง Godot คือสตูดิโอสำเร็จรูปที่มีกล้อง เวที ระบบฟิสิกส์ และเครื่องเสียงให้พร้อม หน้าที่ของ Game Developer คือเขียนบทว่าทุกตัวละครต้องทำอะไรในแต่ละเฟรม

ทำไมหัวข้อนี้อยู่ท้ายสุด และทำไมเลือก Godot

ในลำดับที่หลักสูตรแนะนำ Game Developer อยู่ ลำดับที่ 19 (ลำดับสุดท้าย) ใน Phase 5 เหตุผลคือเป็นสายเฉพาะทางที่แยกตัวจากสายอื่นมากที่สุด เครื่องมือ (Game Engine) วิธีคิด (Game Loop) และตลาดงานต่างจาก Web, Backend และ Data อย่างชัดเจน หัวข้อนี้เป็นสาย Core ของเส้นทางอาชีพ Game Dev เท่านั้น ไม่ได้เป็นทักษะที่ควรรู้ (Good to know) ของสายอื่น จึงเรียนเป็นลำดับท้าย หรือ เลือกเรียนตามความสนใจ ได้ทันทีหลังจบ และ โดยไม่ต้องรอหัวข้ออื่น

ข้อดีของการเรียนเป็นลำดับท้ายคือคุณมีพื้นฐานครบแล้ว ทั้ง Terminal, Git, การเขียนโปรแกรม, JavaScript, Backend และ Security จึงต่อยอดเกมไปทำ Leaderboard ออนไลน์ ระบบ Analytics หรือปล่อยเกมบน Android ได้เอง ตารางด้านล่างเทียบ Engine ที่นิยม เพื่อให้เห็นว่าทำไมหลักสูตรนี้เริ่มที่ Godot

หมายเหตุ

แนวคิดหลักของ Game Development เช่น Game Loop, Delta Time, Vector, Collision Layer, State Machine และ Game Feel ใช้ได้กับทุก Engine เมื่อเข้าใจใน Godot แล้ว การย้ายไป Unity หรือ Unreal คือการเรียนชื่อเรียกและเครื่องมือใหม่ ไม่ใช่การเริ่มจากศูนย์

Prerequisites: ต้องรู้อะไรมาก่อน

หัวข้อที่ ต้อง เรียนจบก่อนมี 2 หัวข้อ

  • ต้องเข้าใจตัวแปร ชนิดข้อมูล if/for/while ฟังก์ชัน List, Dictionary และ Class เพราะ GDScript ใช้แนวคิดเหล่านี้ทั้งหมดด้วย Syntax ที่คล้าย Python มาก และใน Step 2 จะใช้ Python ใน WSL จำลอง Game Loop ก่อนเปิด Engine
  • ต้องใช้ git add, git commit, git push, ไฟล์ .gitignore และ GitHub ได้ เพราะทุกโปรเจกต์เกมในหัวข้อนี้ต้องเก็บใน Git และ Mini Project ต้องอยู่บน GitHub

ในลำดับที่แนะนำ คุณเรียนหัวข้อต่อไปนี้จบแล้วด้วย และจะได้ใช้ความรู้จากหัวข้อเหล่านี้ในบางขั้น

  • ใช้ Ubuntu ใน WSL สำหรับรัน Python, จัดการ Git และทดสอบ Web Export ด้วย Web Server ในเครื่อง
  • แนวคิด Event และ Callback ใน JavaScript ช่วยให้เข้าใจ Signal ของ Godot ได้เร็ว และความรู้เรื่อง Browser ใช้ตอน Export เกมเป็น Web
  • ถ้าต้องการ Export เกมเป็น Android ภายหลัง จะใช้ Android SDK และความเข้าใจเรื่อง APK/AAB จากหัวข้อนั้น
  • และ ใช้ต่อยอดทำ Leaderboard ออนไลน์ที่เกมส่งคะแนนไปเก็บบน Server
  • ช่วยให้เข้าใจว่าทำไมไฟล์ Save ของเกมเชื่อถือไม่ได้ และทำไมห้ามโหลดไฟล์ Resource ที่ไม่รู้ที่มา (Step 10)
  • ใช้ AI ช่วยเขียนโค้ดเกมได้ แต่ต้องระวังเป็นพิเศษ เพราะ AI จำนวนมากยังเขียนโค้ดแบบ Godot 3 ซึ่งใช้กับ Godot 4.7 ไม่ได้

นอกจากหัวข้อในหลักสูตร ควรมีพื้นฐานต่อไปนี้

  • คณิตศาสตร์ระดับมัธยมต้น ได้แก่ ระบบพิกัด x, y ทฤษฎีบทพีทาโกรัส และรู้จัก sin/cos คร่าวๆ ส่วนที่ซับซ้อนกว่านี้จะสอนใน Step 2 เท่าที่เกมต้องใช้
  • อ่านเอกสารภาษาอังกฤษได้ เพราะ Class Reference ของ Godot ที่อยู่ใน Editor และบนเว็บเป็นภาษาอังกฤษ
  • เครื่อง Windows 10 หรือ 11 แบบ 64-bit การ์ดจอที่รองรับ Vulkan หรือ Direct3D 12 จะใช้ Renderer ได้ครบทุกแบบ ถ้าเครื่องเก่า ให้ใช้ Renderer แบบ Compatibility (OpenGL 3.3) ซึ่งหลักสูตรนี้แนะนำสำหรับเกม 2D อยู่แล้ว Godot เป็นโปรแกรมที่เบามาก เครื่องที่ใช้เรียนหัวข้ออื่นได้ก็ใช้ Godot ได้
  • คีย์บอร์ดและเมาส์ ส่วนจอยเกม (Gamepad) เป็นทางเลือก ถ้ามีจะได้ทดสอบ Input Map กับจอยด้วย

Game Loop, Delta Time และคณิตศาสตร์ Vector

1 สัปดาห์ · 6–8 ชม.
หัวข้อย่อย
  • Game Loop 3 จังหวะ: Process Input → Update (คำนวณการเคลื่อนที่ การชน กติกา) → Render (วาดภาพ) วนซ้ำ 30 ถึง 144 ครั้งหรือมากกว่าต่อวินาที
  • FPS และ Frame Time: 60 FPS หมายถึงมีเวลาเฟรมละ 1000 ÷ 60 ≈ 16.67 มิลลิวินาที ถ้าโค้ดใช้เวลานานกว่านี้ เกมจะกระตุก
  • Delta Time: เวลาที่ผ่านไปตั้งแต่เฟรมก่อน (หน่วยวินาที) ต้องคูณความเร็วด้วย Delta เสมอ เพื่อให้ตัวละครเคลื่อนที่เท่ากันทุกเครื่อง ไม่ว่าเครื่องนั้นจะได้ 30 หรือ 144 FPS และคิดความเร็วเป็น "พิกเซลต่อวินาที" ไม่ใช่ "พิกเซลต่อเฟรม"
  • Variable Timestep กับ Fixed Timestep: การวาดภาพใช้ Delta ที่เปลี่ยนไปทุกเฟรม ส่วนฟิสิกส์ควรคำนวณด้วยช่วงเวลาคงที่ ใน Godot คือ _process(delta) กับ _physics_process(delta) ที่ค่าเริ่มต้นทำงาน 60 ครั้งต่อวินาที
  • ระบบพิกัด 2D ของ Godot: จุด (0, 0) อยู่มุมซ้ายบนของหน้าจอ แกน x เพิ่มไปทางขวา แกน y เพิ่มลงด้านล่าง (ตรงข้ามกับกราฟในวิชาคณิตศาสตร์) และมุมการหมุนใช้หน่วย เรเดียน แปลงจากองศาด้วย deg_to_rad()
  • Vector2: การบวก ลบ คูณด้วยตัวเลข และเมธอดที่ใช้บ่อย length(), normalized(), distance_to(), direction_to(), angle(), rotated() และ dot()
  • ทำไมการเดินเฉียงโดยไม่ Normalize จึงเร็วกว่าเดินตรงประมาณ 1.414 เท่า (√2) และแก้ด้วย normalized()
  • Interpolation: lerp() สำหรับเลื่อนค่าเข้าหาเป้าหมายแบบนุ่มนวล move_toward() สำหรับเร่งและเบรกด้วยอัตราคงที่ และแนวคิด Easing เบื้องต้น
  • จำลอง Game Loop ด้วย Python ใน WSL ก่อนเปิด Engine เพื่อให้เห็นผลของ Delta Time ด้วยตาตัวเอง

SPEED = 200.0         # ความเร็วที่ต้องการ: 200 พิกเซลต่อวินาที
PIXELS_PER_FRAME = 4  # วิธีที่ผิด: ขยับทีละ 4 พิกเซลต่อเฟรม

for fps in (30, 60, 144):
    delta = 1.0 / fps          # เวลาที่ผ่านไปในแต่ละเฟรม (วินาที)
    x_no_delta = 0.0
    x_with_delta = 0.0
    for frame in range(fps):   # วน 1 วินาทีพอดี
        x_no_delta += PIXELS_PER_FRAME
        x_with_delta += SPEED * delta
    print(f"{fps:>3} FPS | ไม่ใช้ delta: {x_no_delta:6.1f} px | ใช้ delta: {x_with_delta:6.1f} px")

    else:

# สถานะทั้งหมดที่ศัตรูเป็นได้ อยู่ได้ทีละสถานะเท่านั้น
enum State { IDLE, CHASE, STUNNED }

@export var speed: float = 150.0
@export var detect_radius: float = 250.0

var state: State = State.IDLE
var player: Node2D

func _ready() -> void:
    # หาผู้เล่นจากกลุ่ม "player" ครั้งเดียวตอนเริ่ม
    player = get_tree().get_first_node_in_group("player") as Node2D

func _physics_process(_delta: float) -> void:
    match state:
        State.IDLE:
            velocity = Vector2.ZERO
            if player and global_position.distance_to(player.global_position) < detect_radius:
                change_state(State.CHASE)
        State.CHASE:
            velocity = global_position.direction_to(player.global_position) * speed
            # ใช้ระยะเลิกไล่ที่ไกลกว่าระยะเริ่มไล่ เพื่อไม่ให้สลับสถานะไปมาถี่ๆ
            if global_position.distance_to(player.global_position) > detect_radius * 1.5:
                change_state(State.IDLE)
        State.STUNNED:
            velocity = Vector2.ZERO
    move_and_slide()

func change_state(new_state: State) -> void:
    print(State.keys()[state], " -> ", State.keys()[new_state])
    state = new_state

extends Camera2D

@export var decay: float = 2.0         # การสั่นลดลงเร็วแค่ไหน (ต่อวินาที)
@export var max_offset: float = 12.0   # ระยะสั่นสูงสุด หน่วยพิกเซล

var trauma: float = 0.0                # 0 = นิ่ง, 1 = สั่นแรงที่สุด

func add_trauma(amount: float) -> void:
    # เรียกตอนผู้เล่นโดนชน เช่น add_trauma(0.6)
    trauma = minf(trauma + amount, 1.0)

func _process(delta: float) -> void:
    if trauma > 0.0:
        trauma = maxf(trauma - decay * delta, 0.0)
        var power := trauma * trauma   # ยกกำลังสอง ให้สั่นแรงช่วงแรกแล้วค่อยๆ เบาลง
        offset = Vector2(randf_range(-1.0, 1.0), randf_range(-1.0, 1.0)) * max_offset * power
    else:
        offset = Vector2.ZERO

ไฟล์ด้านบนคือ shake_camera.gd ส่วนไฟล์ด้านล่างคือ star_pop.gd ที่ทำให้ Node เด้งขยายแล้วหดกลับ แนบกับ Node2D ที่มี Sprite2D เป็นลูก แล้วกด F6

extends Node2D

func pop() -> void:
    # สร้าง Tween ใหม่ทุกครั้ง แล้วต่อขั้นตอนเป็นลำดับ
    var tween := create_tween()
    tween.tween_property(self, "scale", Vector2(1.4, 1.4), 0.08).set_trans(Tween.TRANS_BACK).set_ease(Tween.EASE_OUT)
    tween.tween_property(self, "scale", Vector2.ONE, 0.12)
    tween.finished.connect(func() -> void: print("pop เสร็จ scale = ", scale))

func _ready() -> void:
    pop()
pop เสร็จ scale = (1.0, 1.0)

ภาพจะขยายเป็น 1.4 เท่าใน 0.08 วินาทีแบบเลยเป้าเล็กน้อย (TRANS_BACK) แล้วหดกลับขนาดเดิมใน 0.12 วินาที ข้อความใน Output ขึ้นเมื่อ Tween ทำงานครบทุกขั้น

extends SceneTree
# ตรวจความพร้อมของโปรเจกต์ก่อน Export (Smoke Test)
# รันจาก Command Line ด้วย --headless --script โดยไม่ต้องเปิด Editor

const REQUIRED_ACTIONS: Array[String] = ["move_left", "move_right", "move_up", "move_down", "pause"]
const REQUIRED_SCENES: Array[String] = [
    "res://scenes/main_menu.tscn",
    "res://scenes/game.tscn",
    "res://scenes/game_over.tscn",
    "res://scenes/player.tscn",
    "res://scenes/enemy.tscn",
    "res://scenes/star.tscn",
    "res://scenes/hud.tscn",
]
const TEST_SAVE_PATH := "user://smoke_test.cfg"

var passed: int = 0
var failed: int = 0

func check(ok: bool, label: String) -> void:
    # พิมพ์ผลทีละข้อ แล้วนับจำนวนข้อที่ผ่านและไม่ผ่าน
    if ok:
        passed += 1
        print("[PASS] ", label)
    else:
        failed += 1
        print("[FAIL] ", label)

func _initialize() -> void:
    var game_name: String = ProjectSettings.get_setting("application/config/name", "")
    var version: String = ProjectSettings.get_setting("application/config/version", "")
    print("Smoke test: %s v%s" % [game_name, version])

    # 1) ต้องตั้งเลขเวอร์ชันก่อนปล่อยเกม
    check(not version.is_empty(), "ตั้งเลขเวอร์ชันใน Project Settings แล้ว")

    # 2) Main Scene ต้องมีอยู่จริง ไม่อย่างนั้นไฟล์ .exe จะเปิดขึ้นมาแล้วไม่มีอะไรเลย
    var main_scene: String = ProjectSettings.get_setting("application/run/main_scene", "")
    check(ResourceLoader.exists(main_scene), "ตั้ง Main Scene และไฟล์มีอยู่จริง")

    # 3) ทุก Action ที่โค้ดเรียกใช้ต้องมีอยู่ใน Input Map
    for action in REQUIRED_ACTIONS:
        check(InputMap.has_action(action), "Input Action: " + action)

    # 4) ทุก Scene ต้องโหลดได้ (จับไฟล์ที่ถูกย้าย ลบ หรือเปลี่ยนชื่อ)
    for path in REQUIRED_SCENES:
        check(load(path) is PackedScene, "โหลด Scene ได้: " + path.get_file())

    # 5) ทุก Script ใน res://scripts/ ต้องไม่มี Parse Error
    # (Scene ยังโหลดผ่านได้แม้ Script ที่แนบอยู่จะเสีย จึงต้องตรวจแยก)
    var broken: Array[String] = []
    for file in DirAccess.get_files_at("res://scripts"):
        if file.ends_with(".gd"):
            var script := load("res://scripts/" + file) as GDScript
            if script == null or not script.can_instantiate():
                broken.append(file)
    var script_label := "Script ใน res://scripts/ ไม่มี Parse Error"
    if not broken.is_empty():
        script_label += " (ไฟล์ที่เสีย: %s)" % ", ".join(broken)
    check(broken.is_empty(), script_label)

    # 6) ต้องเขียนและอ่านไฟล์ใน user:// ได้ แบบเดียวกับระบบ High Score
    var config := ConfigFile.new()
    config.set_value("progress", "high_score", 4321)
    var save_err := config.save(TEST_SAVE_PATH)
    var loaded := ConfigFile.new()
    var load_err := loaded.load(TEST_SAVE_PATH)
    var round_trip_ok: bool = save_err == OK and load_err == OK and loaded.get_value("progress", "high_score", 0) == 4321
    check(round_trip_ok, "บันทึกและอ่านไฟล์ใน user:// ได้")
    # ลบไฟล์ทดสอบทิ้ง ไม่ให้ปนกับไฟล์ Save จริง (savegame.cfg)
    DirAccess.remove_absolute(TEST_SAVE_PATH)

    print("สรุป: ผ่าน %d ข้อ ไม่ผ่าน %d ข้อ" % [passed, failed])
    # Exit Code 0 = ผ่านทุกข้อ, 1 = มีข้อที่ไม่ผ่าน (ระบบ Build อัตโนมัติใช้ค่านี้ตัดสินได้)
    quit(1 if failed > 0 else 0)

Must-know Skills

รายการนี้คือทักษะที่ Game Developer สาย 2D ต้องทำได้จริง ไม่ใช่แค่เคยอ่าน เรียงตามลำดับที่เจอในเส้นทาง ทุกข้อมีขั้นที่ฝึกอยู่แล้วด้านบน ใช้เป็นรายการทบทวนก่อนสัมภาษณ์งานได้

  1. Game Loop และ Delta Time: ทุกการเคลื่อนที่ ตัวจับเวลา และค่าที่เปลี่ยนตามเวลาต้องคูณด้วย delta เกมจึงเร็วเท่ากันทั้งบนเครื่อง 30 FPS และ 144 FPS
  2. คณิตศาสตร์ Vector2 (normalized(), length(), distance_to(), direction_to(), lerp(), angle()): ใช้คำนวณทิศทาง ระยะ และการเล็งในแทบทุกบรรทัดของโค้ดเกม 2D และป้องกัน Bug ที่ตัวละครเดินทแยงเร็วกว่าเดินตรง
  3. Node, Scene, Scene Tree และ Instancing: เป็นวิธีที่ Godot จัดโครงสร้างทุกอย่างในเกม ถ้าแบ่ง Scene ดี ชิ้นส่วนจะนำกลับมาใช้ซ้ำและแก้ไขแยกกันได้ง่าย
  4. GDScript แบบมี Static Typing: การระบุ Type ทำให้ Editor เตือน Error ก่อนรันและเติมโค้ดได้แม่นขึ้น ซึ่งสำคัญมากเมื่อโปรเจกต์มีไฟล์มากกว่าสิบไฟล์
  5. Input Map และ Action: แยกปุ่มจริงออกจากโค้ด ทำให้รองรับคีย์บอร์ดและ Gamepad พร้อมกัน และเพิ่มหน้าตั้งค่าให้ผู้เล่นเปลี่ยนปุ่มเองได้ในภายหลัง
  6. CharacterBody2D กับ velocity และ move_and_slide(): เป็นวิธีมาตรฐานของ Godot 4 สำหรับตัวละครที่ผู้เล่นควบคุม ซึ่งชนกำแพงแล้วไถลไปตามผนังได้ถูกต้องโดยไม่ต้องคำนวณเอง
  7. Collision Layer, Collision Mask และ Area2D: เป็นตัวกำหนดว่าอะไรชนกับอะไรได้ ถ้าตั้งผิด ศัตรูจะชนกันเองหรือเก็บดาวไม่ได้ ซึ่งเป็น Bug ที่มือใหม่เจอบ่อยที่สุด
  8. Signal และ Group: ให้ Node สื่อสารกันโดยไม่ต้องรู้จักกันโดยตรง จึงย้าย ลบ หรือเปลี่ยน Node ได้โดยโค้ดส่วนอื่นไม่พัง
  9. UI ด้วย Control Node, Container, CanvasLayer และ Theme: HUD และเมนูที่จัดด้วย Container ไม่เพี้ยนเมื่อขนาดหน้าจอเปลี่ยน และ Theme ทำให้ทั้งเกมใช้สไตล์เดียวกันโดยแก้ที่จุดเดียว
  10. Autoload การสลับ Scene และการบันทึกข้อมูลใน user://: เกมทุกเกมต้องเก็บสถานะข้าม Scene และจำ High Score กับการตั้งค่าไว้หลังปิดเกม โดยไม่พังเมื่อไฟล์ Save หายหรือเสีย
  11. State Machine: ทำให้พฤติกรรมของผู้เล่นและศัตรูอ่านง่าย Debug ง่าย และเพิ่มสถานะใหม่ได้โดยไม่ต้องไล่แก้ if ซ้อนกันหลายชั้น
  12. Game Feel ด้วย Tween, Particle, Screen Shake และเสียง: เป็นส่วนที่เปลี่ยนเกมที่ "ทำงานได้" ให้เป็นเกมที่ "เล่นแล้วสนุก" และเป็นสิ่งแรกที่คนดู Portfolio สังเกตเห็น
  13. Export, Profiler และ Git สำหรับโปรเจกต์เกม: เกมต้องออกจาก Editor ไปถึงมือผู้เล่นได้ ลื่นไหลบนเครื่องทั่วไป และมีประวัติที่ทีมทำงานร่วมกันได้โดยไม่ทำไฟล์ของกันและกันหาย
  14. ทำเกมให้เสร็จ: จำกัด Scope, Playtest และปล่อยเกม: ผู้จ้างงานให้น้ำหนักกับเกมเล็กที่เสร็จและเปิดเล่นได้ทันที มากกว่าเกมใหญ่ที่ทำค้างไว้

Gameplay Programmerสร้างระบบที่ผู้เล่นสัมผัสโดยตรง เช่น การควบคุมตัวละคร ระบบต่อสู้ AI ของศัตรู และ Game Feel ทำงานใกล้ชิดกับ Game DesignerJunior–Midคณิตศาสตร์ Vector, Physics, State Machine, Animation, Tween, ใช้ Profiler เป็น และทำ Prototype ได้เร็ว
UI Programmer (สายเกม)สร้างเมนู HUD หน้าตั้งค่า และระบบ Inventory ให้ใช้ได้ทุกขนาดหน้าจอ และเลือกด้วย Gamepad ได้Junior–MidControl Node และ Container, Theme, การเลื่อน Focus ด้วย Gamepad, Animation ของ UI และความเข้าใจ UX
Technical Game Designerออกแบบกติกา ปรับสมดุลตัวเลขในเกม และสร้าง Prototype เองด้วย Script โดยไม่ต้องรอโปรแกรมเมอร์Junior–Midเขียน GDD, Scripting, การเก็บค่าตัวเลขของเกมไว้ใน Resource หรือไฟล์ข้อมูลแยกจากโค้ด, Spreadsheet สำหรับปรับสมดุล และการจัด Playtest
Game QA Tester / QA Engineerทดสอบเกมตาม Test Case เขียน Bug Report ที่ทำซ้ำได้ ทดสอบซ้ำหลังแก้ Bug และในระดับ Engineer จะเขียนการทดสอบอัตโนมัติJuniorความละเอียดรอบคอบ, การเขียน Bug Report ที่มีขั้นตอนทำซ้ำ, เข้าใจเลขเวอร์ชันและ Build, Git พื้นฐาน และสคริปต์ทดสอบแบบ Smoke Test ใน Step 14
Tools Programmerสร้างเครื่องมือภายในให้ทีม เช่น Plugin ของ Editor, ตัวแก้ด่าน และระบบ Build กับ Export อัตโนมัติMid–SeniorScript แบบ @tool และ EditorPlugin, Export จาก Command Line, GitHub Actions และ Python สำหรับงานอัตโนมัติ
Game Server / Backend Engineerสร้างระบบหลังบ้านของเกม เช่น Leaderboard, บัญชีผู้เล่น, Matchmaking และ Server ของเกม MultiplayerMidAPI Design , Backend , Go หรือ Node.js , SQL และความปลอดภัยของระบบ
Mobile Game Developerทำเกมสำหรับ Android และ iOS ปรับให้เล่นด้วยการแตะ ประหยัดแบตเตอรี่ และเชื่อมระบบโฆษณาหรือการซื้อในเกมJunior–MidUnity และ C# (พบในประกาศงานบ่อย) หรือ Godot กับ Android Export, Touch Input, การจูน Performance บนเครื่องสเปกต่ำ และพื้นฐาน Android
Technical Artistเชื่อมงานศิลป์กับโค้ด เช่น เขียน Shader ทำ Particle วางระบบ Animation และขั้นตอนนำเข้า Asset ให้ทีมMidShader, Particle, AnimationTree, Blender, ความเข้าใจ Performance ของการวาดภาพ และสื่อสารกับทั้งศิลปินและโปรแกรมเมอร์ได้
Indie Game Developer / Freelanceทำเกมคนเดียวหรือกับทีมเล็ก ตั้งแต่ไอเดีย โค้ด ภาพ เสียง ไปจนถึงการตลาดและการปล่อยเกมบน itch.io หรือ Steamทุกระดับทุกทักษะในเส้นทางนี้, การจำกัด Scope, การสร้างชุมชนผู้เล่น, การทำหน้าร้านค้าและวิดีโอตัวอย่างเกม และการจัดการเงินกับเวลาด้วยตัวเอง
Tip

ตำแหน่งที่มือใหม่เข้าได้ง่ายที่สุดคือ Junior Game Developer และ Game QA Tester งาน QA ทำให้เห็นกระบวนการผลิตเกมจริงตั้งแต่วันแรก และหลายคนย้ายจาก QA ไปเป็นโปรแกรมเมอร์ภายในบริษัทเดียวกัน ถ้าคุณมาจากสาย Backend อยู่แล้ว ตำแหน่ง Game Server / Backend Engineer คือทางลัดเข้าวงการเกมที่ใช้ทักษะเดิมได้มากที่สุด

ใบรับรอง

วงการเกมให้น้ำหนักกับผลงานมากกว่าใบรับรอง ผู้สัมภาษณ์มักขอลิงก์เกมที่เล่นได้และ Repository ของโค้ดก่อนถามถึงใบรับรอง ตารางนี้แสดงสถานะ ณ 19 ต.ค. 2026

ใบรับรองผู้ออกสถานะ ณ 19 ต.ค. 2026ความเกี่ยวข้องกับเส้นทางนี้

หมายเหตุ

เงินเดือนสายเกมต่างกันมากตามบริษัท ขนาดทีม ประเภทเกม (มือถือ, PC หรือ Console), Engine ที่ใช้ ประสบการณ์ และว่าทำงานกับบริษัทในไทยหรือต่างประเทศ หัวข้อนี้จึงไม่ระบุตัวเลขเงินเดือน ให้หาข้อมูลล่าสุดเองตามขั้นตอนด้านล่าง

  1. ค้นใน JobsDB และ LinkedIn ด้วยคำค้น Game Developer, Game Programmer, Gameplay Programmer, Unity Developer และ Godot แล้วกรองพื้นที่เป็นประเทศไทย
  2. เก็บประกาศ 15–20 ประกาศลง Spreadsheet โดยมีคอลัมน์ ตำแหน่ง, Engine, ภาษา, ประสบการณ์ที่ขอ, ช่วงเงินเดือน (เฉพาะประกาศที่ระบุ) และทักษะที่ขอ
  3. นับว่าทักษะใดถูกขอบ่อยที่สุด แล้วเทียบกับ Must-know Skills ด้านบน เพื่อเลือกว่าจะเรียนอะไรต่อ เช่น Unity, C# หรือ Multiplayer
  4. ดูช่วงเงินเดือนที่ LinkedIn แสดงในบางประกาศ และถามคนที่ทำงานจริงผ่านชุมชนนักพัฒนาเกมหรืองาน Meetup เพราะหลายประกาศไม่เปิดเผยตัวเลข
  5. ทำซ้ำทุก 3–6 เดือน เพราะ Engine และทักษะที่ตลาดต้องการเปลี่ยนเร็ว
Best Practice
  • มีเกมเล็กที่เสร็จ 2–3 เกม ดีกว่าเกมใหญ่ที่ทำค้างไว้ 1 เกม และทุกเกมควรมีลิงก์ itch.io ที่กดแล้วเล่นบน Browser ได้ทันที
  • Repository ของแต่ละเกมมี README ที่มีภาพหรือ GIF, วิธีเล่น, เทคนิคที่ใช้ และ Commit ที่อ่านแล้วรู้ว่าแก้อะไร
  • มีผลงานจาก Game Jam อย่างน้อย 1 งาน เพื่อแสดงว่าทำงานภายใต้เวลาจำกัดและทำงานกับคนอื่นได้
  • เขียน Devlog สั้นๆ อธิบายปัญหาที่เจอและวิธีแก้ เพราะผู้สัมภาษณ์มักถามว่า "Bug ที่ยากที่สุดที่เคยแก้คืออะไร"
  • เขียนโค้ดแบบมี Static Typing และตั้งชื่อตามแนวทางของ GDScript ให้สม่ำเสมอ เพราะผู้สัมภาษณ์มักเปิดอ่านโค้ดใน Repository จริง
