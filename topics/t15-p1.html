15.1Learning Roadmap

ภาพรวมเส้นทาง

TypeScript คือ JavaScript ที่เพิ่ม ระบบ Type เข้าไป คุณเขียนโค้ดแบบเดียวกับ JavaScript ที่เรียนมาแล้ว แต่บอกเพิ่มว่าตัวแปร Parameter และค่าที่ฟังก์ชันส่งกลับต้องเป็นข้อมูลชนิดไหน จากนั้นโปรแกรม tsc (TypeScript Compiler) จะตรวจโค้ดทั้งโปรเจกต์ ก่อนรัน และชี้บรรทัดที่ผิดให้ทันที เช่น ส่งข้อความ "65" ไปในช่องที่ต้องเป็นตัวเลข หรือเรียก field ที่สะกดผิด Bug แบบนี้ใน JavaScript จะโผล่ตอนผู้ใช้กดปุ่มจริง แต่ใน TypeScript จะเจอตั้งแต่ตอนพิมพ์โค้ดใน VS Code

บริษัทที่เขียนเว็บและ Backend ด้วย JavaScript ส่วนใหญ่ย้ายมาใช้ TypeScript แล้ว ทั้ง Frontend (React, Vue, Angular), Backend บน Node.js, แอปมือถือด้วย React Native และงาน AI ที่เรียก LLM API ผ่าน SDK ประกาศรับสมัครงานสาย Full-stack JavaScript จึงมักเขียนว่า "TypeScript" เป็นทักษะที่ต้องมี หัวข้อนี้อยู่ลำดับที่ 8 ของเส้นทางที่แนะนำ ต่อจาก ทันที เพราะตอนนี้คุณยังจำ JavaScript ได้ดี และ TypeScript ก็คือการต่อยอดความรู้ชุดเดิม ไม่ใช่การเรียนภาษาใหม่ตั้งแต่ศูนย์

เส้นทางนี้แบ่งเป็น 13 ขั้นใน 3 ระดับ เริ่มจากติดตั้ง TypeScript 7 และ Compile ไฟล์แรก ต่อด้วย Type พื้นฐาน Object และ Function ในระดับกลางจะเรียน Union, Narrowing, Class, Generics และการใช้ TypeScript กับ Node.js และหน้าเว็บ (DOM) ระดับสูงคือการสร้าง Type ใหม่จาก Type เดิม การตรวจข้อมูลจากภายนอกตอนรันจริงด้วย zod การเขียน Test และการย้ายโปรเจกต์ JavaScript เดิมมาเป็น TypeScript ปิดท้ายด้วย Mini Project Type-safe Task Manager ทุกตัวอย่างในหน้านี้รันจริงด้วย TypeScript 7.0.2 และ Node.js บน Ubuntu 24.04 ใน WSL2

ใช้เวลารวมประมาณ 35–49 ชั่วโมง (อยู่ในช่วง 30–50 ชั่วโมงที่ประเมินไว้สำหรับหัวข้อนี้) ถ้าเรียนวันละ 1–1.5 ชั่วโมง จะจบในราว 6 สัปดาห์ แต่ละขั้นมี Checkpoint บอกว่าต้องทำอะไรได้ก่อนเดินต่อ ให้ทำ Checkpoint ให้ผ่านจริงทุกข้อ

  7. Intermediate Step 7 · Classes, Access Modifiers และ Interface
  8. Intermediate Step 8 · Generics และ Constraints
  9. Intermediate Step 9 · Modules, Declaration Files, @types และ TypeScript กับ Node.js / DOM
  10. Advanced Step 10 · keyof, typeof, Indexed Access และ Utility Types
  11. Advanced Step 11 · Mapped Types, Conditional Types และ Template Literal Types
  12. Advanced Step 12 · Async, fetch และ Runtime Validation ด้วย zod
  13. Advanced Step 13 · Testing, ย้ายโปรเจกต์ JavaScript มาเป็น TypeScript, Tooling และ Mini Project

เปรียบเทียบ

เขียน JavaScript ล้วนเหมือนสร้างบ้านโดยไม่มีวิศวกรตรวจแบบ จะรู้ว่าคานรับน้ำหนักไม่ไหวก็ตอนเทปูนเสร็จและมีคนเข้าไปอยู่แล้ว ส่วน TypeScript เหมือนมีวิศวกรตรวจแบบแปลนทุกครั้งที่คุณแก้แบบ ถ้าขนาดเสาไม่ตรงกับน้ำหนักที่ต้องรับ วิศวกรจะแจ้งตั้งแต่ยังเป็นกระดาษ การแก้แบบบนกระดาษถูกกว่าการทุบบ้านที่สร้างเสร็จแล้วหลายเท่า ส่วน Type ก็คือตัวเลขขนาดและน้ำหนักที่เขียนกำกับไว้ในแบบ ซึ่งคนอื่นในทีมอ่านแล้วเข้าใจตรงกันด้วย

TypeScript คืออะไร ทำไมเรียนต่อจาก JavaScript

ก่อนเริ่ม ให้รู้จักคำศัพท์ต่อไปนี้ เพราะจะเจอทุกขั้นของหัวข้อนี้ และเป็นคำที่ใช้คุยกันในทีมจริง

คำศัพท์ความหมายตัวอย่าง
Typeชนิดของข้อมูล และกติกาว่าข้อมูลนั้นทำอะไรได้บ้าง เช่น number บวกลบได้ ส่วน string เรียก .toUpperCase() ได้number, string, boolean, { name: string }
Type Annotationการเขียนกำกับ Type เองด้วยเครื่องหมาย : หลังชื่อตัวแปรหรือ Parameterlet age: number = 28;
Type InferenceTypeScript เดา Type ให้เองจากค่าที่กำหนด ไม่ต้องเขียนกำกับทุกที่let age = 28; ได้ Type number อัตโนมัติ
Type Checker / tscโปรแกรมที่อ่านโค้ดทั้งโปรเจกต์แล้วตรวจว่าใช้ Type ถูกต้องไหม คำสั่งคือ tsc และในโปรเจกต์เรียกผ่าน npx tscnpx tsc --noEmit
Compile (Transpile)แปลงไฟล์ .ts เป็น .js ที่ Node.js และเบราว์เซอร์รันได้ โดยลบส่วนที่เป็น Type ทิ้งsrc/app.ts กลายเป็น dist/app.js
tsconfig.jsonไฟล์ตั้งค่าของโปรเจกต์ บอกว่าไฟล์อยู่ที่ไหน ผลลัพธ์ไปที่ไหน และตรวจเข้มแค่ไหน"strict": true, "outDir": "./dist"
Strict Modeชุดการตรวจแบบเข้มงวด เช่น ห้ามมี Parameter ที่ไม่รู้ Type และต้องจัดการค่า null ให้ชัดเจน ตั้งแต่ TypeScript 6.0 เปิดเป็นค่าเริ่มต้นแล้ว"strict": true
Declaration File (.d.ts)ไฟล์ที่มีแต่ Type ไม่มีโค้ดที่รันได้ ใช้อธิบาย Type ของโค้ด JavaScript ให้ TypeScript รู้จักvat.d.ts, แพ็กเกจ @types/node
Type Strippingความสามารถของ Node.js ที่ลบ Type ออกจากไฟล์ .ts แล้วรันได้ทันที โดย ไม่ตรวจ Typenode src/app.ts
Runtime Validationการตรวจข้อมูลตอนโปรแกรมรันจริง จำเป็นสำหรับข้อมูลจากภายนอก เพราะ Type หายไปหลัง CompileUserSchema.safeParse(body) ด้วย zod

สิ่งที่ TypeScript ช่วยในงานจริง

  • จับ Bug ก่อนรัน ส่ง Argument ผิดชนิด ลืมจัดการค่า null สะกดชื่อ field ผิด หรือลืมจัดการสถานะใหม่ที่เพิ่งเพิ่มเข้ามา จะถูกแจ้งตั้งแต่ตอนเขียนโค้ด
  • Editor ฉลาดขึ้นมาก VS Code แนะนำชื่อ field และเมธอดได้ถูกต้อง เปลี่ยนชื่อตัวแปรทั้งโปรเจกต์ได้อย่างปลอดภัย และกระโดดไปดูนิยามของฟังก์ชันได้ทันที
  • Type คือเอกสารที่ไม่มีวันล้าสมัย แค่อ่าน function addVat(price: number, rate?: number): number ก็รู้วิธีใช้ทันที และถ้าใครแก้ฟังก์ชันโดยไม่แก้ Type โค้ดจะ Compile ไม่ผ่าน
  • Refactor โค้ดขนาดใหญ่ได้อย่างมั่นใจ เมื่อเปลี่ยนรูปร่างของข้อมูล Compiler จะบอกทุกจุดที่ต้องแก้ตาม ไม่ต้องไล่หาด้วยตาเอง
  • เป็นมาตรฐานของตลาดงาน Framework และ Library ยุคใหม่เขียนด้วย TypeScript หรือมี Type มาให้ในตัว ตัวอย่างโค้ดในเอกสารทางการส่วนใหญ่ก็เป็น TypeScript

สิ่งที่ TypeScript ไม่ได้ ทำ ต้องรู้ไว้เพื่อไม่ให้เข้าใจผิด

  • ไม่ได้ตรวจข้อมูลตอนรันจริง Type ถูกลบทิ้งหลัง Compile ถ้า API ส่งข้อมูลผิดรูปแบบมา TypeScript ไม่รู้ ต้องใช้ Runtime Validation อย่าง zod ซึ่งเรียนใน Step 12
  • ไม่ได้ทำให้โปรแกรมรันเร็วขึ้น โค้ดที่ได้หลัง Compile ก็คือ JavaScript ธรรมดา ความเร็วเท่าเดิม
  • ไม่ได้แทนที่การเขียน Test Type ตรวจว่าข้อมูลถูกชนิด แต่ไม่ได้ตรวจว่าคำนวณถูก เช่น สูตร VAT ที่คูณผิดก็ยัง Compile ผ่าน จึงต้องมี Test ด้วย (Step 13)

TypeScript 7 ต่างจากเวอร์ชันก่อนอย่างไร

หลักสูตรนี้ใช้ TypeScript 7.0.2 ซึ่งเป็นเวอร์ชันล่าสุด ณ วันที่ 19 ต.ค. 2026 (ออกเมื่อ 8 ก.ค. 2026) TypeScript 7 คือการเขียน Compiler ใหม่ทั้งหมดด้วยภาษา Go เป็นโปรแกรม Native จึงตรวจโปรเจกต์ได้เร็วขึ้นมาก Microsoft รายงานว่าเร็วขึ้นราว 10 เท่าในโปรเจกต์ขนาดใหญ่ แต่ คำสั่งยังเป็น tsc เหมือนเดิม และภาษา TypeScript ที่คุณเขียนก็เหมือนเดิม บทความและตัวอย่างโค้ดของ TypeScript 5.x ส่วนใหญ่จึงยังใช้ได้ ต่างกันที่การตั้งค่าบางอย่างเท่านั้น

ตัวเลือกเก่าตัวเลือกอย่าง "target": "es5" และ "baseUrl" ยังใช้ได้ แต่ขึ้น Error TS5107 / TS5101 ว่า "deprecated" จนกว่าจะใส่ "ignoreDeprecations": "6.0"ถูกลบออกแล้ว ขึ้น Error TS5108 / TS5102 ว่า "has been removed" ได้แก่ target ES5, moduleResolution แบบ node (node10) และ classic, baseUrl, outFile, downlevelIteration, module แบบ AMD / UMD / System และการตั้ง esModuleInterop, allowSyntheticDefaultImports หรือ alwaysStrict เป็น falseใช้ "module": "nodenext" และ "target": "es2024" ตามตัวอย่างใน Step 1 ถ้าเจอ baseUrl ในโปรเจกต์เก่าให้ใช้ "paths" แทน

Prerequisites: ต้องรู้อะไรมาก่อน

TypeScript สร้างอยู่บน JavaScript ทั้งหมด จึงต้องเรียน ให้จบก่อน ตามเส้นทางที่แนะนำ คุณผ่านหัวข้อเหล่านี้มาแล้ว และจะได้ใช้ในหัวข้อนี้ทุกวัน

  • ต้องคล่องจริง: let/const, Arrow Function, Destructuring, Spread, Optional Chaining (?.), Nullish Coalescing (??), Array Methods (map, filter, reduce, find), Class, ES Modules (import/export), Promise และ async/await, fetch, try/catch, npm และ package.json และการเขียน Test เบื้องต้นด้วย node:test
  • ใช้ Terminal ใน Ubuntu (WSL2) สร้างโฟลเดอร์ แก้ไฟล์ และอ่านข้อความ Error ภาษาอังกฤษ
  • เก็บงานแต่ละขั้นเป็น Commit และ Push Mini Project ขึ้น GitHub
  • ถ้าเคยใช้ Type Hints ของ Python (def add(a: int, b: int) -> int) จะเข้าใจแนวคิดของ TypeScript เร็วขึ้นมาก เพราะคล้ายกัน ต่างกันที่ TypeScript มี tsc ตรวจให้ทุกครั้งที่ Build
  • ช่วยให้คิดเรื่อง "รูปร่างของข้อมูล" ได้ดี การออกแบบ Type ของ Object คล้ายการออกแบบคอลัมน์ของตาราง

STEP 1

TypeScript คืออะไร และเตรียมโปรเจกต์ด้วย TypeScript 7

1–2 วัน · 2–3 ชม.
หัวข้อย่อย
  • TypeScript คือ JavaScript ที่เพิ่มระบบ Type โค้ด JavaScript ที่ถูกต้องเกือบทั้งหมดเป็นโค้ด TypeScript ที่ถูกต้องด้วย และ Type ทั้งหมดจะถูกลบทิ้งตอน Compile (Type Erasure) จึงไม่มีผลกับความเร็วตอนรัน
  • Static Typing ต่างจาก Dynamic Typing อย่างไร: JavaScript รู้ชนิดของข้อมูลตอนรัน ส่วน TypeScript ตรวจก่อนรัน ตัวอย่างคลาสสิกคือ 55 + "65" ที่ JavaScript ต่อเป็นข้อความ "5565" โดยไม่เตือน
  • ติดตั้ง TypeScript แบบ Local ในแต่ละโปรเจกต์ด้วย npm install -D --save-exact typescript@7.0.2 @types/node@24.19.2 แล้วเรียกผ่าน npx tsc ทำไมไม่ควรติดตั้งแบบ Global (npm install -g): แต่ละโปรเจกต์อาจต้องใช้คนละเวอร์ชัน และ --save-exact ทำให้ทุกคนในทีมได้เวอร์ชันตรงกันทุกตัวอักษร
  • tsconfig.json ตัวเลือกหลัก: rootDir / outDir (โค้ดต้นฉบับอยู่ไหน ผลลัพธ์ไปไหน), module: "nodenext" และ target: "es2024" (เขียนแบบ ES Modules สำหรับ Node.js รุ่นใหม่), types: ["node"], strict, noUncheckedIndexedAccess และ exactOptionalPropertyTypes
  • npx tsc --init สร้าง tsconfig.json ตามค่าที่ทีม TypeScript แนะนำ และ npx tsc --showConfig แสดงค่าที่มีผลจริงทั้งหมด รวมถึงค่าที่ TypeScript เติมให้เอง
  • คำสั่งประจำวัน: npx tsc (ตรวจและ Compile ทั้งโปรเจกต์), npx tsc --noEmit (ตรวจอย่างเดียวไม่สร้างไฟล์), npx tsc --watch (ตรวจใหม่ทุกครั้งที่บันทึกไฟล์) และ Exit Code: 0 คือผ่าน 1 คือมี Error
  • อ่าน Error ของ tsc: รูปแบบคือ ไฟล์:บรรทัด:คอลัมน์ - error TSรหัส: ข้อความ ตามด้วยบรรทัดที่ผิดและเครื่องหมาย ~~~ ใต้จุดที่ผิด รหัสอย่าง TS2322 นำไปค้นหาได้
  • Node.js รันไฟล์ .ts ได้เองด้วย Type Stripping โดยไม่ต้องใส่ Flag ตั้งแต่ Node.js 22.18.0 และ 23.6.0 ขึ้นไป (Node 24 และ 26 จึงรองรับ) แต่ Node ไม่ตรวจ Type แค่ลบทิ้ง ไม่อ่าน tsconfig.json และรองรับเฉพาะ Syntax ที่ลบทิ้งได้ (Erasable) เท่านั้น
  • VS Code กับ TypeScript: เส้นหยักสีแดงใต้โค้ดที่ผิด, Hover ดู Type, F12 ไปที่นิยาม, F2 เปลี่ยนชื่อทั้งโปรเจกต์, Ctrl+. ดูวิธีแก้ที่ Editor แนะนำ

STEP 2

Primitive Types, Type Inference, Arrays และ Tuples

2 วัน · 2–3 ชม.
หัวข้อย่อย
  • Primitive Types: string, number (ตัวเลขทุกแบบ ไม่แยก int กับ float), boolean, bigint, symbol, null และ undefined และความต่างของ string (ตัวเล็ก ใช้เสมอ) กับ String (ตัวใหญ่ เป็น Object ห่อหุ้ม ไม่ควรใช้เป็น Type)
  • Type Annotation กับ Type Inference: เขียน Type เองเมื่อเป็น Parameter, Array ว่าง และค่าที่ส่งออกจาก Module ส่วนตัวแปรภายในที่มีค่าเริ่มต้นให้ TypeScript อนุมานเอง
  • Literal Type และการขยาย Type (Widening): const role = "admin" ได้ Type "admin" แต่ let role = "admin" ได้ Type string เพราะ let เปลี่ยนค่าได้
  • Array: number[] กับ Array<number> มีความหมายเดียวกัน, readonly string[] สำหรับข้อมูลที่ห้ามแก้ และ Array ว่างต้องระบุ Type เช่น const ids: number[] = []
  • Tuple: Array ที่จำนวนและชนิดของแต่ละช่องตายตัว เช่น [string, number], Tuple แบบตั้งชื่อช่อง [name: string, age: number], ช่องที่ไม่บังคับ [string, number?] และการแยกค่าด้วย Destructuring
  • noUncheckedIndexedAccess: อ่านค่าด้วย Index เช่น scores[10] จะได้ Type number | undefined เพราะ Index นั้นอาจไม่มีอยู่จริง ต้องจัดการด้วย ?? หรือ if ก่อนใช้
  • any แบบซ่อนอยู่: Strict Mode แจ้ง error TS7006: Parameter 'x' implicitly has an 'any' type. เมื่อลืมใส่ Type ให้ Parameter ซึ่งเป็นสัญญาณให้เติม Type ไม่ใช่ใส่ any
  • ดู Type ที่อนุมานได้ด้วยการ Hover ใน VS Code และทดลองใน TypeScript Playground

STEP 3

Object Types: Type Alias, Interface, Optional และ Readonly

2 วัน · 2–3 ชม.
หัวข้อย่อย
  • อธิบายรูปร่างของ Object ด้วย Object Type แบบเขียนตรงๆ { name: string; price: number } และตั้งชื่อให้ใช้ซ้ำได้ด้วย type หรือ interface
  • type กับ interface ต่างกันอย่างไร: interface ขยายต่อด้วย extends และรวมการประกาศชื่อเดียวกันได้ (Declaration Merging) ส่วน type ตั้งชื่อให้ Type อะไรก็ได้ รวมถึง Union และ Tuple ทีมส่วนใหญ่ใช้ interface กับรูปร่างของ Object และใช้ type กับ Union ให้เลือกแนวทางเดียวแล้วใช้ให้สม่ำเสมอ
  • Optional Property (phone?: string) และการอ่านอย่างปลอดภัยด้วย ?. และ ?? เมื่อเปิด exactOptionalPropertyTypes คำว่า "Optional" หมายถึง "ไม่มี field นี้" ไม่ใช่ "มี field แต่ค่าเป็น undefined"
  • readonly Property และ Readonly<T> ป้องกันการแก้ค่าตอน Compile เท่านั้น ตอนรันจริงยังแก้ได้ ถ้าต้องการห้ามแก้ตอนรันด้วยให้ใช้ Object.freeze()
  • Excess Property Check: เมื่อสร้าง Object ตรงๆ แล้วมี field ที่ไม่มีใน Type จะได้ error TS2353 ช่วยจับการสะกดชื่อ field ผิด
  • Index Signature { [sku: string]: number } สำหรับ Object ที่ key ไม่ตายตัว เช่น ตารางราคาสินค้า และ Object ซ้อนกันหลายชั้น
  • Structural Typing: TypeScript ดูที่ "รูปร่าง" ไม่ได้ดูที่ "ชื่อ" Object ใดก็ตามที่มี field ครบตาม Type ใช้แทนกันได้ แม้จะสร้างจาก Type คนละชื่อ
ทำไมต้องเรียน
ข้อมูลในงานจริงเกือบทั้งหมดเป็น Object ไม่ว่าจะเป็นผู้ใช้ สินค้า คำสั่งซื้อ หรือ Response จาก API การออกแบบ Type ของ Object ให้ดีคือการออกแบบ "สัญญา" ระหว่างส่วนต่างๆ ของโปรแกรม readonly ป้องกันการแก้ข้อมูลที่ไม่ควรแก้ เช่น id และ Optional Property ทำให้ Compiler บังคับให้จัดการกรณีที่ข้อมูลไม่มี ซึ่งเป็นต้นเหตุของ Error Cannot read properties of undefined ที่พบบ่อยที่สุดใน JavaScript

// interface: เหมาะกับรูปร่างของ Object ที่ขยายต่อได้
interface User {
  readonly id: number; // อ่านได้อย่างเดียว ห้ามแก้หลังสร้าง
  username: string;
  email: string;
  phone?: string; // optional: มีหรือไม่มีก็ได้
}

// extends: สร้าง interface ใหม่ที่มีทุกอย่างของ User และเพิ่ม role
interface Admin extends User {
  role: "admin";
}

// type alias: ตั้งชื่อให้ Type อะไรก็ได้ รวมถึง Object
type Address = {
  district: string;
  province: string;
};

const somchai: Admin = {
  id: 1,
  username: "somchai",
  email: "somchai@example.com",
  role: "admin",
};

const home: Address = { district: "บางรัก", province: "กรุงเทพมหานคร" };

// ใช้ optional property ต้องเช็กก่อนเสมอ
function contactOf(user: User): string {
  return user.phone ?? `${user.email} (ไม่มีเบอร์โทร)`;
}

somchai.email = "somchai.dev@example.com"; // แก้ได้ เพราะไม่ได้เป็น readonly
console.log(contactOf(somchai));
console.log(`${somchai.username} อยู่เขต${home.district} ${home.province}`);

STEP 4

Functions แบบมี Type และ Overloads

2 วัน · 2–3 ชม.
หัวข้อย่อย
  • Parameter ต้องมี Type เสมอใน Strict Mode ส่วน Return Type อนุมานได้ แต่ควรเขียนเองในฟังก์ชันที่ export ออกไปให้คนอื่นใช้ เพื่อให้ Error ชี้ที่ฟังก์ชันที่เขียนผิด ไม่ใช่ที่ผู้เรียกใช้
  • Optional Parameter (last?: string), Default Parameter (rate: number = 0.07) และ Rest Parameter (...numbers: number[])
  • Function Type (price: number) => number สำหรับ Callback และการตั้งชื่อด้วย type Discount = ... และ Contextual Typing: Arrow Function ที่ส่งให้ map หรือ filter ไม่ต้องเขียน Type ของ Parameter เพราะ TypeScript รู้จากบริบท
  • void สำหรับฟังก์ชันที่ไม่ส่งค่ากลับ และ never สำหรับฟังก์ชันที่ไม่มีวันจบปกติ เช่น ฟังก์ชันที่ throw ทุกครั้ง
  • Function Overloads: เขียนหลาย Signature ให้ฟังก์ชันเดียว แล้วตามด้วย Implementation ตัวเดียว ใช้เมื่อ Type ของผลลัพธ์ขึ้นกับ Type ของ Input และรู้ว่าเมื่อไรใช้ Union Parameter ธรรมดาก็พอ
  • Destructured Parameter แบบมี Type ({ name, price }: Product) และ Parameter ที่เป็น Object ตัวเลือก (Options Object) แทน Parameter หลายตัวเรียงกัน
  • ฟังก์ชัน async คืนค่าเป็น Promise<T> เสมอ เช่น async function load(): Promise<string[]> (เรียนเต็มใน Step 12)
ทำไมต้องเรียน
ฟังก์ชันคือหน่วยหลักของโปรแกรม เมื่อ Parameter และ Return Type ชัดเจน ทั้งทีมรู้วิธีเรียกใช้โดยไม่ต้องเปิดอ่านโค้ดข้างใน และ Compiler จะแจ้งทันทีเมื่อมีคนส่ง Argument ผิดชนิดหรือผิดจำนวน ซึ่งเป็น Bug ที่พบบ่อยมากเมื่อโปรเจกต์ใหญ่ขึ้นและมีคนแก้ฟังก์ชันเดียวกันหลายคน

2–3 ชั่วโมง Overloads อาจต้องอ่านทวนสองรอบ เพราะเป็นจุดที่มือใหม่สับสนว่า Signature ไหนที่คนภายนอกมองเห็น
// 1) กำหนด Type ของ Parameter และค่าที่ return
function addVat(price: number, rate: number = 0.07): number {
  return Math.round(price * (1 + rate) * 100) / 100;
}

// 2) Optional parameter (?) และ Rest parameter (...)
function formatName(first: string, last?: string): string {
  return last ? `${first} ${last}` : first;
}
function sumAll(...numbers: number[]): number {
  return numbers.reduce((a, b) => a + b, 0);
}

// 3) Function Type: บอกรูปร่างของฟังก์ชันที่รับเข้ามา
type Discount = (price: number) => number;
const memberDiscount: Discount = (price) => price * 0.9;
function checkout(price: number, discount: Discount): number {
  return addVat(discount(price));
}

// 4) Overloads: ฟังก์ชันเดียวรับ Input ได้หลายแบบ และได้ผลลัพธ์ที่ Type ต่างกัน
function parseAmount(input: string): number;
function parseAmount(input: string[]): number[];
function parseAmount(input: string | string[]): number | number[] {
  if (Array.isArray(input)) {
    return input.map((s) => Number(s.replace(/,/g, "")));
  }
  return Number(input.replace(/,/g, ""));
}

// 5) void: ฟังก์ชันที่ไม่ส่งค่ากลับ
function log(message: string): void {
  console.log(`[LOG] ${message}`);
}

log(`สมาชิกจ่าย: ${checkout(500, memberDiscount)}`);

หัวข้อย่อย
  • Union Type A | B: ค่าเป็นได้หลายแบบ เช่น number | string และใช้ได้เฉพาะสิ่งที่ทุกแบบมีร่วมกัน จนกว่าจะแยกแยะด้วย Narrowing (Step 6)
  • Literal Types และ Union ของ Literal เป็น "รายการค่าที่อนุญาต" เช่น type Status = "todo" | "doing" | "done" ซึ่งทำให้ Editor แนะนำค่าให้และจับการสะกดผิดได้
  • as const คู่กับ typeof และ [number] เพื่อสร้าง Union จาก Array ที่ใช้ตอนรันจริงด้วย จะได้มีรายการค่าเพียงที่เดียว (Single Source of Truth)
  • Intersection Type A & B: รวม field ของหลาย Type เข้าด้วยกัน เช่น Task & Timestamps และระวังกรณีที่ field ชื่อเดียวกันมี Type ขัดกันจนได้ never
  • enum กับ Union Literal: enum สร้างโค้ด JavaScript จริงตอน Compile จึงไม่ใช่ Syntax ที่ลบทิ้งได้ เมื่อเปิด erasableSyntaxOnly จะได้ error TS1294 และ Node.js รันตรงๆ ไม่ได้ แนวทางปัจจุบันคือใช้ Union Literal หรือ Object แบบ as const แทน
  • User-defined Type Guard value is Priority สำหรับตรวจข้อความที่มาจากภายนอก (เช่น Argument ของ CLI) ว่าอยู่ในรายการที่อนุญาตหรือไม่
  • ตัวดำเนินการ satisfies: ตรวจว่าค่าตรงตาม Type โดยไม่ทำให้ Type ที่อนุมานได้กว้างขึ้น เช่น const labels = { todo: "รอทำ", doing: "กำลังทำ", done: "เสร็จ" } satisfies Record<Status, string>
  • null และ undefined ใน Union เช่น string | null และการที่ Strict Mode (strictNullChecks) บังคับให้จัดการก่อนใช้

STEP 6

Narrowing, Discriminated Unions และ any / unknown / never

3 วัน · 3–4 ชม.
หัวข้อย่อย
  • Narrowing คือการที่ TypeScript ตามการไหลของโค้ด (Control Flow Analysis) แล้วรู้ว่าหลัง if หรือ switch ค่านั้นเหลือ Type อะไร
  • typeof Guard สำหรับ "string", "number", "boolean", "function", "undefined", "object" และกับดัก typeof null === "object"
  • Truthiness Narrowing (if (value)) และกับดักของค่า 0 กับ "" ที่ถูกมองเป็น false รวมถึง Equality Narrowing (value === null)
  • ตัวดำเนินการ in ("code" in value) และ instanceof สำหรับ Class, Error และ Date
  • Discriminated Union: ทุกแบบมี field ร่วมที่เป็น Literal ต่างกัน (เช่น kind) แล้วใช้ switch (p.kind) แยกแต่ละแบบ ภายในแต่ละ case ใช้ field เฉพาะของแบบนั้นได้
  • Exhaustive Check ด้วย never: ฟังก์ชัน assertNever(value: never) ใน default ทำให้ Compiler แจ้งทันทีเมื่อมีแบบใหม่ที่ยังไม่ได้จัดการ
  • any กับ unknown กับ never: any ปิดการตรวจและลามไปทั้งโค้ด, unknown คือ "ยังไม่รู้" ที่ต้อง Narrow ก่อนใช้ จึงปลอดภัย, never คือค่าที่เป็นไปไม่ได้ และตัวแปรใน catch (err) มี Type เป็น unknown ใน Strict Mode
  • Assertion Function asserts value is string สำหรับฟังก์ชันตรวจที่ throw เมื่อไม่ผ่าน
ทำไมต้องเรียน
นี่คือแนวคิดที่สำคัญที่สุดของ TypeScript ในงานจริง เพราะข้อมูลเกือบทุกอย่างมีหลายแบบ ทั้ง Response ที่สำเร็จหรือล้มเหลว คำสั่งหลายแบบใน CLI และ Event หลายชนิดในหน้าเว็บ Discriminated Union กับ Exhaustive Check ทำให้การเพิ่มแบบใหม่ปลอดภัย Compiler จะบอกทุกที่ที่ลืมแก้ ส่วนการใช้ unknown แทน any กับข้อมูลจากภายนอกคือนิสัยที่แยกนักพัฒนาที่ใช้ TypeScript เป็นจริงออกจากคนที่แค่เติม Type ให้ Error หายไป
ลงมือทำ

  • เพิ่มช่องทางจ่ายเงินแบบใหม่ qr เข้าไปใน Payment โดยยังไม่แก้ switch แล้วอ่าน Error ที่ assertNever

// Discriminated Union: ทุกแบบมี field "kind" ที่เป็น literal ต่างกัน
type Payment =
  | { kind: "cash"; amount: number }
  | { kind: "card"; amount: number; last4: string }
  | { kind: "promptpay"; amount: number; phone: string };

// ถ้ามาถึงฟังก์ชันนี้ได้ แปลว่าเราลืมจัดการบางกรณี
function assertNever(value: never): never {
  throw new Error(`ยังไม่ได้จัดการ: ${JSON.stringify(value)}`);
}

function describe(p: Payment): string {
  switch (p.kind) {
    case "cash":
      return `เงินสด ${p.amount} บาท`;
    case "card":
      return `บัตรลงท้าย ${p.last4} จำนวน ${p.amount} บาท`; // ตรงนี้ใช้ p.last4 ได้
    case "promptpay":
      return `พร้อมเพย์ ${p.phone} จำนวน ${p.amount} บาท`;
    default:
      return assertNever(p); // Exhaustive check
  }
}

// typeof และ instanceof narrowing กับค่า unknown
function toMessage(value: unknown): string {
  if (typeof value === "string") return `ข้อความ: ${value.toUpperCase()}`;
  if (typeof value === "number") return `ตัวเลข: ${value.toFixed(2)}`;
  if (value instanceof Error) return `Error: ${value.message}`;
  if (typeof value === "object" && value !== null && "code" in value) {
    return `มี code: ${String(value.code)}`;
  }
  return "ไม่รู้จักชนิดข้อมูลนี้";
}

STEP 7

Classes, Access Modifiers และ Interface

2 วัน · 2–3 ชม.
หัวข้อย่อย
  • ประกาศ field ของ Class พร้อม Type และกำหนดค่าใน constructor ถ้าลืมจะได้ error TS2564: Property 'x' has no initializer and is not definitely assigned in the constructor. (strictPropertyInitialization)
  • public, protected และ private ของ TypeScript ตรวจตอน Compile เท่านั้น ส่วน #private ของ JavaScript ซ่อนจริงตอนรันด้วย ควรใช้ # กับข้อมูลที่ต้องปกป้องจริง
  • readonly field, Getter (get historyCount()) และ Setter ที่ตรวจค่าก่อนกำหนด
  • implements เพื่อบังคับให้ Class ทำตาม Interface, abstract class และ abstract method ที่ Class ลูกต้องเขียนเอง
  • extends, super และคำว่า override ซึ่ง noImplicitOverride บังคับให้เขียน เพื่อป้องกันการ Override ผิดชื่อโดยไม่รู้ตัว
  • Parameter Properties (constructor(private name: string)) สร้างโค้ดเพิ่มตอน Compile จึงใช้ไม่ได้เมื่อเปิด erasableSyntaxOnly ให้ประกาศ field แล้วกำหนดค่าใน constructor เอง
  • static member และการใช้ Class เป็น Type (ชื่อ Class ใช้เป็น Type ของ Instance ได้)
  • เมื่อไรควรใช้ Class: ใช้กับสิ่งที่มีสถานะภายในและพฤติกรรม เช่น Repository หรือ Service ส่วนข้อมูลล้วนๆ อย่างผู้ใช้หรือสินค้า ใช้ interface กับ Object ธรรมดาจะง่ายกว่า
ทำไมต้องเรียน
Framework ฝั่ง Backend หลายตัว เช่น NestJS และ Angular ใช้ Class เป็นหลัก และโค้ดชั้น Service หรือ Repository ในงานจริงก็มักเป็น Class การรู้ว่า private ของ TypeScript ต่างจาก # ของ JavaScript อย่างไร และรู้ว่า Parameter Properties ใช้ไม่ได้กับ erasableSyntaxOnly จะทำให้อ่านโค้ดเก่าเข้าใจและเขียนโค้ดใหม่ที่เข้ากับ Node.js รุ่นปัจจุบันได้

// interface กำหนด "สัญญา" ว่า class ต้องมีอะไรบ้าง
interface Describable {
  describe(): string;
}

// abstract class: ใช้เป็นแม่แบบ สร้าง Object ตรงๆ ไม่ได้
abstract class Account implements Describable {
  readonly owner: string; // กำหนดครั้งเดียวใน constructor
  protected balance: number; // ใช้ได้ใน class นี้และ class ลูก
  #history: string[] = []; // private ของ JavaScript จริง มองไม่เห็นจากภายนอก

  constructor(owner: string, opening: number) {
    this.owner = owner;
    this.balance = opening;
    this.record(`เปิดบัญชี ${opening}`);
  }

  deposit(amount: number): void {
    if (amount <= 0) throw new Error("จำนวนเงินต้องมากกว่า 0");
    this.balance += amount;
    this.record(`ฝาก ${amount}`);
  }

  protected record(entry: string): void {
    this.#history.push(entry);
  }

  get historyCount(): number {
    return this.#history.length;
  }

  abstract monthlyFee(): number; // class ลูกต้องเขียนเอง

  describe(): string {
    return `${this.owner}: ยอดเงิน ${this.balance} บาท ค่าธรรมเนียม ${this.monthlyFee()} บาท`;
  }
}

class SavingsAccount extends Account {
  override monthlyFee(): number {
    return this.balance >= 10000 ? 0 : 20;

3 วัน · 3–4 ชม.
หัวข้อย่อย

// 1) Generic Function: T คือ "ช่องว่างของ Type" ที่จะถูกเติมตอนเรียกใช้
function firstOf<T>(items: readonly T[]): T | undefined {
  return items[0];
}

// 2) Generic Interface: รูปแบบผลลัพธ์ที่ใช้ซ้ำได้กับข้อมูลทุกชนิด
interface ApiResponse<T> {
  ok: boolean;
  data: T;
  fetchedAt: string;
}

// 3) Constraint: T ต้องมี id เป็น string เสมอ
interface Entity {
  readonly id: string;
}

class InMemoryRepository<T extends Entity> {
  #items = new Map<string, T>();

  save(item: T): void {
    this.#items.set(item.id, item);
  }
  findById(id: string): T | undefined {
    return this.#items.get(id);
  }
  findAll(): T[] {
    return [...this.#items.values()];
  }
}

// 4) keyof Constraint: K ต้องเป็นชื่อ field ที่มีอยู่จริงใน T
function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}

interface Product extends Entity {
  name: string;
  price: number;
}

STEP 10

keyof, typeof, Indexed Access และ Utility Types

3 วัน · 3–4 ชม.
หัวข้อย่อย
  • keyof T ได้ Union ของชื่อ field ทั้งหมด และ typeof ค่า ในตำแหน่งของ Type ได้ Type ของค่าที่มีอยู่แล้ว เช่น keyof typeof defaults
  • Indexed Access Type: Task["status"] ดึง Type ของ field เดียว และ (typeof LIST)[number] ดึง Type ของสมาชิกใน Array
  • Utility Types สำหรับแปลงรูปร่าง: Partial<T> (ทุก field ไม่บังคับ), Required<T> (ทุก field บังคับ), Readonly<T>, Pick<T, K> (เลือกบาง field), Omit<T, K> (ตัดบาง field) และ Record<K, V> (Object ที่มี key ครบตามรายการ)
  • Utility Types สำหรับฟังก์ชันและ Union: ReturnType<typeof fn>, Parameters<typeof fn>, Awaited<T> (แกะ Promise ออก), NonNullable<T>, Extract<T, U> และ Exclude<T, U>
  • รูปแบบ DTO ในงานจริง: ข้อมูลตอนสร้างคือ Omit<Task, "id"> ข้อมูลตอนแก้ไขคือ Partial<Pick<Task, "title" | "status">> ทำให้มีนิยามหลักเพียงที่เดียว
  • Record<Status, number> บังคับให้นับครบทุกสถานะ ถ้าเพิ่มสถานะใหม่ Compiler จะแจ้งทุกจุดที่ขาด
  • Non-null Assertion (tasks[2]!) คืออะไร ใช้เมื่อมั่นใจจริงเท่านั้น เพราะเป็นการบอก Compiler ว่า "เชื่อฉัน" โดยไม่มีการตรวจ
  • หลักการเลือกใช้: ใช้ Utility Types เมื่อทำให้มีนิยามหลักที่เดียว ไม่ใช่เพื่อความเท่ ถ้าซ้อนกันเกิน 2–3 ชั้นให้ตั้งชื่อ Type แยกเพื่อให้อ่านง่าย

  return { ...task, ...patch };
}

STEP 11

Mapped Types, Conditional Types และ Template Literal Types

3 วัน · 3–4 ชม.
หัวข้อย่อย
  • Mapped Type { [K in keyof T]: ... } วนทุก key ของ Type แล้วสร้าง Type ใหม่ และ Modifier readonly, ?, -readonly, -? ซึ่งเป็นวิธีที่ Partial, Required และ Readonly ถูกเขียนขึ้นจริง
  • Key Remapping ด้วย as เช่น สร้างชื่อเมธอด getTheme จาก field theme และการกรอง key ทิ้งด้วยการ Map เป็น never
  • Conditional Type T extends U ? X : Y และพฤติกรรมกระจายตัวเมื่อ T เป็น Union (Distributive Conditional Types)
  • คำว่า infer สำหรับดึง Type ที่ซ่อนอยู่ข้างใน เช่น T extends readonly (infer U)[] ? U : never ซึ่งเป็นวิธีที่ ReturnType และ Awaited ทำงาน
  • Template Literal Type `${Entity}:${Action}` สร้าง Union ของข้อความทุกแบบที่เป็นไปได้ และ Type สำเร็จรูป Uppercase, Lowercase, Capitalize, Uncapitalize
  • ตัวอย่างการใช้งานจริง: ชื่อ Event ที่อนุญาต, Path ของ API, ชื่อ Environment Variable และ Getter ที่สร้างจาก Config
  • ทดสอบ Type ด้วย // @ts-expect-error ซึ่งทำให้ Compile ไม่ผ่านถ้าบรรทัดถัดไป ไม่ มี Error ใช้ยืนยันว่า Type ปฏิเสธค่าที่ผิดจริง
  • ข้อจำกัด: Type ที่ซับซ้อนเกินไปอ่านยาก Error ยาว และทำให้ Compile ช้า ใช้เมื่อช่วยลดการเขียนซ้ำหรือป้องกัน Bug ได้ชัดเจนเท่านั้น

function makeGetters<T extends object>(obj: T): Getters<T> {
  const result: Record<string, () => unknown> = {};
  for (const key of Object.keys(obj) as (keyof T & string)[]) {
    const name = `get${key.charAt(0).toUpperCase()}${key.slice(1)}`;
    result[name] = () => obj[key];
  }
  return result as Getters<T>;
}

  • zod 4.6.7: z.object, z.string().min(), z.number().int().positive(), z.email(), z.enum(), z.array(), .optional(), z.iso.date() และ z.infer<typeof Schema> ที่สร้าง Type จาก Schema ให้เอง จึงมีนิยามเพียงที่เดียว

  • รูปแบบ Result<T> (Discriminated Union ของผลสำเร็จกับล้มเหลว) แทนการ throw เพื่อบังคับให้ผู้เรียกจัดการทั้งสองกรณี และการจัดการ Error ใน try/catch ที่ err เป็น unknown

// 1) Schema: กติกาของข้อมูลที่ "ต้อง" ได้รับ ใช้ตรวจตอนรันจริง
const UserSchema = z.object({
  id: z.number().int().positive(),
  username: z.string().min(3),
  email: z.email(),
  role: z.enum(["admin", "member"]),
});
const UserListSchema = z.array(UserSchema);
type User = z.infer<typeof UserSchema>; // ได้ Type จาก Schema ไม่ต้องเขียนซ้ำ

// 2) Result Type: บอกผลสำเร็จหรือล้มเหลวอย่างชัดเจน แทนการ throw
type Result<T> = { ok: true; data: T } | { ok: false; error: string };

async function fetchUsers(url: string): Promise<Result<User[]>> {
  const res = await fetch(url);
  if (!res.ok) return { ok: false, error: `HTTP ${res.status}` };
  const body: unknown = await res.json(); // ข้อมูลจากภายนอกถือว่า unknown เสมอ
  const parsed = UserListSchema.safeParse(body);
  if (!parsed.success) {
    const issues = parsed.error.issues.map((i) => `${i.path.join(".")} ${i.message}`);
    return { ok: false, error: `ข้อมูลผิดรูปแบบ ${issues.length} จุด\n   - ${issues.join("\n   - ")}` };
  }
  return { ok: true, data: parsed.data };
}

// 3) Server จำลองในเครื่องตัวเอง (127.0.0.1) มี 3 เส้นทาง
const server = createServer((req, res) => {
  res.setHeader("Content-Type", "application/json");
  if (req.url === "/api/users") {
    res.end(JSON.stringify([
      { id: 1, username: "somchai", email: "somchai@example.com", role: "admin" },
      { id: 2, username: "somsri", email: "somsri@example.com", role: "member" },
    ]));
  } else if (req.url === "/api/users-broken") {
    res.end(JSON.stringify([{ id: "3", username: "ab", email: "not-an-email", role: "guest" }]));
  } else {
    res.statusCode = 404;
    res.end(JSON.stringify({ message: "not found" }));
  }
});
server.listen(0, "127.0.0.1"); // พอร์ต 0 = ให้ระบบเลือกพอร์ตว่างให้
await new Promise<void>((resolve) => server.once("listening", () => resolve()));
const { port } = server.address() as AddressInfo;
const base = `http://127.0.0.1:${port}`;

for (const path of ["/api/users", "/api/users-broken", "/api/nothing"]) {

  • Discriminated Union สำหรับคำสั่ง: add, list, start, done, remove, stats และ help แยกด้วย field kind และมี Exhaustive Check ด้วย never
  • Generic Repository: Repository<T extends Entity> พร้อม JsonFileRepository<T> สำหรับใช้งานจริง และ InMemoryRepository<T> สำหรับ Test
  • ตรวจข้อมูลที่ขอบระบบ: ไฟล์ data/tasks.json ถูกตรวจด้วย zod ทุกครั้งที่อ่าน ถ้ามีคนแก้ไฟล์ผิดรูปแบบจะได้ข้อความบอกจุดที่ผิดชัดเจน และ Argument จาก Command Line ถูกแปลงเป็น Result ที่บอกเหตุผลเมื่อไม่ถูกต้อง
  • Build และ Test: tsconfig.json แบบ strict เดียวกับ ts-lab, Compile ด้วย TypeScript 7.0.2 และ Test ด้วย node:test

Must-know Skills

รายการนี้คือทักษะที่ผู้สัมภาษณ์และหัวหน้าทีมคาดหวังจากคนที่เขียน "TypeScript เป็น" จริงๆ ไม่ใช่แค่ใส่ : string ตามหลังตัวแปรได้ ให้ใช้เป็น Checklist ทบทวนตัวเองหลังเรียนครบ 13 ขั้น ถ้าข้อไหนยังอธิบายให้เพื่อนฟังไม่ได้ ให้กลับไปทำแบบฝึกหัดของขั้นนั้นอีกรอบ

  1. ตั้งค่าโปรเจกต์และ tsconfig.json แบบ strict ได้เอง เพราะตัวเลือกอย่าง strict, noUncheckedIndexedAccess, module: "nodenext" และ erasableSyntaxOnly เป็นตัวกำหนดว่า Compiler จะจับ Bug ได้มากแค่ไหน และโค้ดจะรันบน Node.js ได้หรือไม่
  2. อ่านข้อความ Error ของ tsc ให้ออก เพราะงานประจำวันของคนเขียน TypeScript คือการอ่านบรรทัดอย่าง error TS2322: Type 'string' is not assignable to type 'number'. แล้วรู้ทันทีว่าต้องแก้ที่ข้อมูล ที่ Type หรือที่ Logic
  3. ออกแบบ Object Types ด้วย type และ interface รวมถึง ? และ readonly เพราะ Type ของข้อมูลหลัก เช่น Task, User, Order คือเอกสารที่ทั้งทีมใช้คุยกัน และ Compiler ใช้ตรวจทุกไฟล์
  4. ใช้ Union, Literal Types และ Discriminated Unions แทน enum และ Boolean หลายตัว เพราะทำให้สถานะที่เป็นไปไม่ได้เขียนลงโค้ดไม่ได้ตั้งแต่แรก และ Exhaustive Check ด้วย never จะเตือนทันทีเมื่อมีคนเพิ่มกรณีใหม่แต่ลืมจัดการ
  5. Narrowing ด้วย typeof, in, instanceof และ Type Guard เพราะข้อมูลจริงมีหลายรูปแบบ และ TypeScript จะยอมให้ใช้ Property เฉพาะเมื่อเราพิสูจน์ให้ Compiler เห็นแล้วว่าค่านั้นเป็นแบบไหน
  6. เลือกใช้ unknown แทน any เพราะ any ปิดการตรวจทั้งหมดแบบเงียบๆ และลามไปทั้งโปรเจกต์ ส่วน unknown บังคับให้ตรวจก่อนใช้ ซึ่งเป็นสิ่งที่ Code Review ในบริษัทจริงมองหาเป็นอันดับแรก
  7. เขียน Generics พร้อม Constraints เช่น Repository<T extends Entity> เพราะทำให้เขียนโค้ดชุดเดียวที่ใช้กับข้อมูลหลายชนิดได้โดยไม่เสีย Type และเป็นพื้นฐานของการอ่าน Library อย่าง React, Express และ zod
  8. ใช้ Utility Types และ keyof / typeof / Indexed Access เพราะการสร้าง Type ใหม่จาก Type เดิม เช่น Omit<Task, "id"> สำหรับข้อมูลที่ยังไม่บันทึก ทำให้มีแหล่งความจริงที่เดียว เมื่อแก้ Type หลัก Type ที่เกี่ยวข้องจะเปลี่ยนตามเอง
  9. อ่านและเขียน Mapped Types, Conditional Types และ Template Literal Types ระดับพื้นฐาน เพราะ Type Definition ของ Library ส่วนใหญ่ใช้สิ่งเหล่านี้ ถ้าอ่านไม่ออกจะติดอยู่กับข้อความ Error ยาวๆ ที่ชี้ไปในไฟล์ .d.ts
  10. ตรวจข้อมูลที่ขอบระบบด้วย zod เพราะ Type หายไปตอนรันจริง ข้อมูลจาก API, ไฟล์ JSON, ฟอร์ม และคำตอบจาก LLM จึงต้องถูกตรวจด้วย Schema ก่อนเข้าสู่ส่วนที่ "เชื่อ Type" ได้
  11. เขียน Async Code และ fetch ให้มี Type ครบ รวมถึง Promise<T>, Awaited และ Result Type สำหรับ Error เพราะ Backend และ AI Engineer ทำงานกับ I/O ตลอดเวลา และ Error ที่ไม่ถูกจัดการคือสาเหตุหลักของระบบล่ม
  12. จัดการ Modules, .d.ts และแพ็กเกจ @types เพราะงานจริงต้องใช้ Library ที่เขียนด้วย JavaScript และต้องรู้ว่า Type มาจากไหนเมื่อเจอ TS7016: Could not find a declaration file for module
  13. เขียน Test ด้วย node:test และรัน tsc --noEmit ใน CI เพราะ Type ตรวจรูปร่างข้อมูล แต่ไม่ตรวจว่า Logic ถูกต้อง ทีมจริงจึงใช้ทั้งสองอย่างคู่กันทุกครั้งที่ Push
  14. ย้ายโปรเจกต์ JavaScript มาเป็น TypeScript ทีละขั้น เพราะงานแรกของนักพัฒนาหลายคนคือการดูแลโค้ดเดิม การใช้ allowJs, // @ts-check และ Test ครอบพฤติกรรมเดิม ทำให้ย้ายได้โดยระบบยังทำงานตลอด
  15. รู้ข้อจำกัดของเวอร์ชันเครื่องมือ เช่น TypeScript 7 กับเครื่องมือที่ยังต้องการ TypeScript API ของ 6.x และ Type Stripping ของ Node.js ที่ไม่ตรวจ Type เพราะการเลือกเวอร์ชันผิดทำให้เสียเวลาทั้งทีม

Best Practice

สิ่งที่แทนใบรับรองได้ดีที่สุดสำหรับ TypeScript คือ Repository บน GitHub ที่ผู้สัมภาษณ์เปิดดูแล้วเห็นสิ่งเหล่านี้ทันที

  • tsconfig.json ที่เปิด strict และ noUncheckedIndexedAccess และไม่มี any กระจายอยู่ในโค้ด
  • README ที่บอกวิธีติดตั้งและรันด้วยคำสั่งที่คัดลอกไปใช้ได้จริง
  • Test ที่รันผ่าน npm test และ GitHub Actions ที่ขึ้นเครื่องหมายผ่าน
  • Commit ที่มีข้อความชัดเจน และแสดงให้เห็นการ Refactor ทีละขั้น

เรื่องเงินเดือน

หลักสูตรนี้ไม่ใส่ตัวเลขเงินเดือน เพราะเงินเดือนต่างกันมากตามตำแหน่ง ประสบการณ์ ขนาดบริษัท อุตสาหกรรม เมือง และรูปแบบการทำงาน (ประจำ, Freelance, Remote ให้บริษัทต่างประเทศ) และตัวเลขที่เขียนไว้วันนี้จะล้าสมัยเร็ว ให้หาข้อมูลเองด้วยวิธีนี้

  1. ค้นหาประกาศงานบน JobsDB และ LinkedIn Jobs ด้วยคำค้น เช่น TypeScript, Node.js Developer, Full Stack Developer และกรองตามระดับประสบการณ์ที่ตรงกับคุณ
  2. เก็บประกาศที่ระบุช่วงเงินเดือนอย่างน้อย 15–20 ประกาศลงตาราง บันทึกตำแหน่ง ประสบการณ์ที่ต้องการ ทักษะที่ระบุ และช่วงเงินเดือน แล้วดูค่ากลางของกลุ่มที่ตรงกับคุณ
  3. อ่านรายงานเงินเดือนประจำปีของบริษัทจัดหางานและผลสำรวจนักพัฒนา โดยดูปีที่ทำสำรวจและกลุ่มตัวอย่างทุกครั้ง
  4. ถามคนที่ทำงานในตำแหน่งนั้นจริงผ่าน Community นักพัฒนา หรือถาม HR ตรงๆ ในการสัมภาษณ์รอบแรกว่าช่วงงบประมาณของตำแหน่งนี้คือเท่าไร
  5. สังเกตว่าประกาศที่ระบุ TypeScript, Testing และ CI มักต้องการทักษะครบกว่าประกาศที่ระบุแค่ JavaScript ใช้ข้อมูลนี้วางแผนว่าจะเรียนอะไรต่อ
